# 要件

## 元の要望
GitHub Issue #347「定期監査の失敗が人間に届かず、PRのCIとの間で行き詰まりが起きる」

### 誰が困っているか
リポジトリ所有者(人間)。コードを読まず、定期監査の結果を受けて対処の指示だけを出す立場にある。

### 現状
- 週次監査(audit-weekly)が 2026-09-14・09-21 に失敗した(Dependabotの #342・#346 の滞留を検知)。
- PRのCIには「週次監査の成功が10日無ければ失敗」の判定があり、2026-09-17 以降すべてのPRが detect-changes で失敗している。監査を通すには滞留PRを通す必要があり、PRを通すには監査の成功が必要という行き詰まりになっている。
- 約2週間、誰も気づかなかった。定期実行の失敗通知はcronを最後に書き換えた人にしか届かない(https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)。audit-weekly.yaml を書いたのはbotのため、人間には届いていない。canary-verify.yaml も同じ。

### 何を変えるか
- PRのCIの死活判定を「成功したか」から「実行されたか」に変える。
- 週次監査の結果を「逸脱なし/逸脱あり/判定不能」の3つに分ける。逸脱ありでもワークフロー自体は成功扱いにし、逸脱の内容はIssueで知らせる。
- 逸脱ありと監査の故障を別々のIssueで知らせる。どちらも固定タイトルで1件だけ持ち、再発したら追記、解消したら自動で閉じる。所有者を担当者にする。
- canary-verify の失敗も同じ方法で知らせる。
- 監査手順書・README・#310 の「失敗は既定の通知で届く」という前提を訂正する。

### 完了の確認
- マージ後に手動実行し、Issueの通知が所有者に届くことを人間が確認する。
- 行き詰まっていた #346 のCIが通る。

### 関連

## はじめに

この spec は、定期監査(週次監査・カナリア照合)の結果を、所有者に実際に届く形で知らせる。あわせて、この spec は、PRのCIが週次監査の「成功」を条件にしているために生じた行き詰まりを解消する。行き詰まりとは、監査が逸脱を見つけると全PRが止まり、逸脱を直すPRも通せなくなることを指す。

audit-automation spec(#310 段階1〜3)は、「逸脱はワークフローを失敗で終わらせるだけとし、通知はGitHub既定の失敗通知に乗る」と決めていた。しかし、GitHubの定期実行の失敗通知は、cronを最後に書き換えた利用者にしか届かない。両ワークフローを書いたのはbotのため、この前提は成り立っていなかった。この spec は、この前提の誤りを訂正し、audit-automation spec の要件4(死活検知)と要件6-4・6-5(書き込み禁止・失敗終了以外の対処禁止)を置き換える。この spec は、判定の基準(何を逸脱とするか)を変えない。

## 範囲

- この spec で決めること: 週次監査とカナリア照合の結果の3分類(逸脱なし/逸脱あり/判定不能)、結果に応じたIssueでの通知(起票・追記・自動クローズ)、PRのCIの死活確認を「実行されたか」の判定へ変えること、監査手順書・README・関連ワークフローの説明にある「既定の失敗通知で届く」という前提の訂正
- この spec で決めないこと: 判定基準そのものの変更(何を滞留・スキップ・カナリアの失敗とみなすか)、定期コンテナスキャンの通知(既にIssueで通知している)、逸脱の自動修正・Dependabotへの操作・カナリアPRへの書き込み、Issue操作そのものが失敗した場合の検知(見張りを見張る入れ子になるため、この spec はこの検知の欠落を受け入れる)、メトリクス記録(#334)、停止中のDependabot PR #342・#346 の個別対応
- この spec が前提にしていること: 所有者がIssueの担当者に割り当てられたとき、GitHubの通知が所有者に届くこと(導入時に人間が受信を確認する)。GitHub Actions の定期実行が、公開リポジトリで60日間活動が無いと自動停止すること(この spec は、この停止を、死活確認で検知される側の事象として扱う)

## 要件

### 要件1 監査結果の3分類

所有者は、「監査が逸脱を見つけた」ことと「監査そのものが正しく動かなかった」ことを見分けたい。前者は所有者の対処を待つ作業で、後者は仕組みの故障であり、急ぎ方も対処も違うからである。

1. 週次監査またはカナリア照合が実行されたら、監査は、結果を「逸脱なし」「逸脱あり」「判定不能」のいずれか1つに分類する。
2. 判定スクリプトの自己テストが失敗したら、または判定に必要な情報を取得・解釈できなかったら、監査は、結果を「判定不能」に分類する。
3. 複数の判定項目のうち1つでも判定不能があれば、監査は、全体の結果を「判定不能」とし、判定できた項目の逸脱もあわせて報告する。
4. 結果が「逸脱なし」または「逸脱あり」なら、監査は、ワークフローの実行を成功として終了する。
5. 結果が「判定不能」なら、監査は、ワークフローの実行を失敗として終了する。
6. 監査は、何を逸脱とみなすかの判定基準を、audit-automation spec の要件1〜3・5(定期スキャンの稼働確認、滞留しているDependabot PRの検知、必須チェックがスキップで通ったPRの検知、カナリア点検の照合)から変えない。

### 要件2 逸脱の通知

所有者は、監査が逸脱を見つけたら、画面を見に行かなくても知らせが届いてほしい。今は失敗が誰にも届かず、所有者は約2週間気づけなかったからである。

1. 結果が「逸脱あり」で、その監査の逸脱を知らせるIssueが開いていなければ、監査は、監査の種類ごとに決まったタイトルでIssueを1件作成し、所有者を担当者に割り当てる。
2. 結果が「逸脱あり」で、その監査の逸脱を知らせるIssueが既に開いていれば、監査は、新しいIssueを作らず、既存のIssueに今回の検出内容を追記する。
3. 監査は、逸脱のIssueに、逸脱の内容(対象のPR番号・チェック名・判定の根拠など、判定項目ごとの報告)、該当する監査の実行へのリンク、監査手順書の対処手順への案内を含める。
4. 結果が「逸脱なし」で、その監査の逸脱を知らせるIssueが開いていれば、監査は、そのIssueに解消した旨を追記して閉じる。
5. 所有者の承認待ちだけで止まっているDependabot PRがあれば、週次監査は、そのPRを逸脱として扱わない。逸脱のIssueがあれば、週次監査は、そのIssueの中で、承認待ちのPRを一覧として示す。

### 要件3 故障の通知

所有者は、監査そのものが動かなかったことも知らせてほしい。故障した監査は逸脱を見つけられず、何も言わないまま止まるからである。

1. 結果が「判定不能」で、その監査の故障を知らせるIssueが開いていなければ、監査は、逸脱のIssueとは別の、監査の種類ごとに決まったタイトルでIssueを1件作成し、所有者を担当者に割り当てる。
2. 結果が「判定不能」で、その監査の故障を知らせるIssueが既に開いていれば、監査は、新しいIssueを作らず、既存のIssueに今回の内容を追記する。
3. 監査は、故障のIssueに、判定できなかった項目と理由、該当する監査の実行へのリンク、再実行の方法を含める。週次監査の再実行の方法は、同じ実行の再実行を使い、新規の手動実行を使わないことである。
4. 結果が「逸脱なし」または「逸脱あり」で、その監査の故障を知らせるIssueが開いていれば、監査は、そのIssueに解消した旨を追記して閉じる。
5. Issueの作成・追記・クローズのいずれかに失敗したら、監査は、ワークフローの実行を失敗として終了する。

### 要件4 監査の死活確認の見直し

所有者は、監査が逸脱を見つけたこと自体でPRが止まらないようにしたい。PRが止まると、逸脱を直すPRまで止まり、行き詰まるからである。

1. PRのCIが実行されたら、CIは、週次監査の直近の完了した実行(結論を問わない)を確認する。この確認を、以下では死活確認と呼ぶ。
2. 週次監査の完了した実行が10日以上無ければ、CIは、そのPRのCIを失敗として終了し、監査が止まっている旨と直近の完了日時を報告に含める。
3. 週次監査の直近の実行が逸脱ありまたは判定不能であっても、その実行が10日以内に完了していれば、CIは、死活確認を成功として扱う。
4. 週次監査がまだ登録されていないか、完了した実行が一度も無ければ、CIは、死活確認を失敗として扱わない。
5. 週次監査の実行履歴を取得・解釈できなければ、CIは、死活確認を成功に倒さず、失敗として終了する。
6. CIは、死活確認をPRのCIでのみ行い、mainへのpushでは行わない。

### 要件5 前提の訂正と導入確認

所有者は、文書に書かれた通知の仕組みが実態と一致していてほしい。誤った前提が文書に残ると、次の設計で同じ誤りが繰り返されるからである。

1. 監査手順書は、監査の結果がIssueで届くことと、逸脱のIssueと故障のIssueそれぞれを受け取ったときの対処を記載する。
2. 監査手順書・README・監査ワークフローの説明は、「失敗は既定の通知で届く」という記述を残さない。これらの文書は、定期実行の失敗通知はcronを最後に書き換えた利用者にしか届かないという事実と、その根拠(公式ドキュメント)を記載する。
3. 監査手順書は、導入後に手動実行で通知のIssueを1回発生させ、所有者が通知を受け取れたことを人間が確認する手順を記載する。
4. 監査手順書は、Issue操作そのものが失敗した場合は通知されないという残余リスクを記載する。

### 要件6 運用特性

所有者は、通知を加えても、費用・攻撃面・保守負担が必要以上に増えないようにしたい。

1. 監査は、AIの呼び出しと、GitHub以外の外部サービスへの問い合わせを行わない。

   > 注記(2026-09-29): 本項のうち外部サービスへの問い合わせの禁止を、audit-inventory-metrics spec(#415)の要件6-1・6-6で、棚卸し(audit-inventory.yaml)に限って改めた。棚卸しは GitHub 以外の公開情報(endoflife.date・PyPI・Docker Hub)を読み取りで問い合わせ、送るのは製品やパッケージの名前だけで、リポジトリの内容や認証情報を送らない。AIの呼び出しの禁止は棚卸しにも維持し(同spec要件6-2)、週次監査とカナリア照合については本項の禁止をすべて維持する。理由: この禁止の元の理由は「外部の死活監視サービスへのリポジトリの情報の送信」であり、製品名を送って公開情報を受け取る問い合わせは想定していなかった(所有者了承 2026-09-28)。本文は監査証跡として当時のまま残す。

2. 監査は、書き込みをIssueの作成・追記・クローズと担当者の割り当てに限り、リポジトリの内容・PR・Dependabotへの書き込みを行わない。
3. 監査は、監査が作るIssueを、決まったタイトルとラベルで他のIssueと区別し、それ以外のIssueを操作しない。
4. 監査は、Issueを操作する判定ロジックを、既存の判定スクリプトと同等の自動テストで検証できる形で持つ。
