# 要件

## 元の要望
Issue #445: バックエンドを Go に置き換える

### きっかけ

> バックエンドをJava+SpringBootからPython+Djangoにリプレイスしたい

着手のときに、所有者が、置き換え先の言語を Python から Go に変えた。

### 困っていること

- Java / Spring Boot の保守と運用の負担が大きい(AIの提案を了承)
- このリポジトリはAIが開発しており、Java / Spring Boot より開発を進めやすい言語にしたい(AIの提案を了承)

### やりたいこと

- バックエンドを Java + Spring Boot から Go に置き換える
- サービスを止めずに、動いたまま切り替える
- Java と Spring を前提にした記述は、すべて書き換える
- 記述は、言語にあまり依存しない書き方にする。別の言語に置き換えることになったときに、同じ書き換えが起きないようにするため
  - 言語を書いてよいもの: README、`backend/` の中の説明(`backend/CLAUDE.md` など)、`.kiro/steering/tech.md`、`doc/` の設計図(AIの提案を了承)
  - 言語に依存しない書き方にするもの: ルートの `CLAUDE.md`、スキル、`doc/開発フロー/` などの手順書(AIの提案を了承)
- 使っていないものは、保守の手間が増えるので消す
  - 対象は、今の立ち上げ手順(`start-dev.sh` とAIによる起動)、CI、本番のどれでも使っていないもの。消す一覧は仕様を決める段階で所有者が確かめる(AIの提案を了承)

### どうなれば解決か

- 利用者から見た機能がすべて今のまま動く(利用者から見て何も変わらない)(AIの提案を了承)
- PDFとMarkdownの出力は、見た目も今と同じ(配置、フォント、文字の大きさ、表の色)(AIの提案を了承)
- 旧版で書き出したバックアップを、新版でそのまま戻せる(AIの提案を了承)
- 本番の既存データ(利用者と経歴書)をすべて引き継いでいる(AIの提案を了承)
- 切り替えの間と後に、利用者から見て次をすべて守る(AIの提案を了承)
  - 操作が失敗しない(保存、PDF出力、ログインなどがエラーにならない)
  - 保存した内容が消えない(Java版とGo版のどちらに届いた保存も、切り替え後に残っている)
  - ログアウトされない(切り替えの途中でも後でも、ログインし直さずに使い続けられる)
- 開発者向けのAPI説明画面を、開発環境で開ける。Swaggerである必要はなく、Go におけるスタンダードなものにする
- 今と同じ種類の自動品質チェックを、Go側にそろえてから切り替える
- 置き換えたあと、Java版はリポジトリから削除されている(AIの提案を了承)

### 決めた方式

- 言語は Go
- エコシステムは、現代の最新のベストプラクティスに基づく
- Webフレームワークは使わない。HTTP の受け口は、Go の標準ライブラリで作る(AIの提案を了承)
- API の仕様書(OpenAPI)を先に書き、HTTP の受け口の型は、仕様書からコードを生成して作る(AIの提案を了承)
- Go 版の作り方は、Java や Spring Boot の作りに合わせず、Go にとって最適で標準的なものを選ぶ。そのために直す量が増えてもよい
- 今のコードに、効率の悪い書き方や、避けるべきとされる書き方があれば、Go 版ではそれを引き継がずに書き換える
- Go で今と同じにできるかが分からない動きは、AIがすべて洗い出し、試しに作って確かめてから設計を書く
- 機能のまとまりごとの Go 版は、まとまりごとに別の spec で作る。この Issue の spec は、置き換えの進め方と、品質チェック、Java 版と Go 版を比べる検査、本番の切り替えの仕組み、Java 版の削除を受け持つ(AIの提案を了承)
- Java 版と同じ動きかどうかの正解は、今の Java 版が実際に返す応答と、実際に保存するデータとする。API の仕様書は、設計を書く前に今の Java 版から作る。要件と設計には、受け口ごとの細かい動きを書き写さない(AIの提案を了承)

### やらないこと

- 置き換えでは機能を足さず、仕様も変えない
- 置き換えの前に機能を増やさない。#444 は置き換えが終わるまで着手しない(AIの提案を了承)

## はじめに

KeirekiPro の backend は、Java と Spring Boot で作られている。Issue #445 で、所有者は、backend を Go に置き換えると決めた。置き換えは、backend のすべての機能を作り直す大きな作業であり、1つの PR では終わらない。そのうえ、本番には利用者がいて、置き換えの途中でも、利用者は今のままサービスを使い続ける。そのため、置き換えの進め方を誤ると、利用者の操作が失敗する、保存した内容が消える、利用者がログアウトされる、といったことが起きる。置き換えの進め方とは、何をどの順に作り、いつ本番を切り替え、所有者がどこで何をするかを指す。所有者は、この進め方を、この spec で最も大事なものとした。

この spec では、まず進め方を決め、そのうえで、置き換えたあとの backend が守ることを決める。機能のまとまりごとの Go 版は、この spec では作らず、まとまりごとの別の spec で作る。1つの spec が backend のすべての機能を受け持つと、1つのまとまりで設計の誤りが見つかっただけで、関係の無いまとまりの分まで、所有者が設計とタスクを承認し直すことになるためである。

この spec の「所有者」は、このリポジトリの CODEOWNERS に書かれた人を指す。所有者は、本番への出荷を承認する人でもある。「Java 版」は今の Java と Spring Boot の backend を指し、「Go 版」は、この spec で作る Go の backend を指す。「利用者」は、本番の KeirekiPro を使う人を指す。「画面」は、今の frontend を指す。「切り替え」は、本番で利用者の操作を受ける backend を、Java 版から Go 版に替えることを指す。

## 範囲

- この spec で決めること: この spec では、次の3つを決める。
  - 置き換えの進め方。この spec は、置き換えの進め方として、次の7つを決める。
    - 作る順番
    - 機能のまとまりごとの spec に分けること
    - main に入れる単位
    - 本番を切り替える時と方法
    - Java 版に戻す方法
    - 所有者がする操作
    - Claude が止まって所有者に報告するとき
  - Go 版が守ること。この spec は、Go 版が守ることとして、次の7つを決める。機能のまとまりごとの spec も、ここで決めたことを守る。
    - 利用者から見た機能
    - PDF と Markdown の出力
    - バックアップ
    - 本番のデータ
    - 切り替えの間と後の利用者の使い心地
    - 品質チェック
    - API の説明画面
  - 置き換えたあとのリポジトリ。この spec は、Java 版をどう削除するか、Java と Spring を前提にした記述をどう書き換えるか、使っていないものをどう削除するかを決める。
- この spec で決めないこと: この spec では、次の5つを決めない。
  - 機能のまとまりごとの Go 版の作り。まとまりごとの Go 版の作りは、まとまりごとの spec で決める
  - 機能を足すことと、仕様を変えること。Issue の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである。Issue #444 も、置き換えが終わるまで扱わない
  - 画面の作り直し。置き換えの間も後も、画面は今のまま動く
  - 本番の作りを、置き換えに要る分を超えて変えること。たとえば、本番のサーバの台数と、平日の昼だけ本番を動かす時間割は、この spec では変えない
  - この spec が main に入った時点ですでに書かれていた spec の書き換え。Claude は、それらの spec を、その時点の記録として残す
- この spec が前提にしていること: この spec は、次の4つを前提にする。
  - 本番は、日本の時刻で、平日の 08:00 から 20:00 だけ動いている。backend は 08:00 に1台で動き始め、20:00 に止まる。データベースは 07:50 に動き始め、20:05 に止まる。Claude は、2026-11-07 に、このリポジトリの本番の設定でこの時間割を確かめた
  - 本番への出荷は、所有者が起動し、所有者が承認したときだけ動く。本番の設定の変更の反映(terraform apply)も、所有者だけが行う。Claude は、どちらも起動しない
  - 本番で backend を新しい版に替えるとき、新しい版が動き始めてから古い版が止まる。そのため、出荷の途中のしばらくの間、古い版と新しい版の両方が、利用者の操作を受ける
  - 今の PDF のテンプレートは、頁の大きさと余白の指定、改頁の指定、表、文字の大きさと色の指定だけを使っており、PDF を作る部品だけが読める独自の指定を使っていない。Claude は、2026-11-07 に、テンプレート `templates/resume/pdf/simple.html` を読んでこれを確かめた。このため、Go 版でも、同じテンプレートの指定から同じ見た目の PDF を作れる見込みがある

## 要件

### 要件1 置き換えを段階に分け、どの段階でも本番を今のまま動かす

置き換えは大きく、1つの PR では終わらない。また、置き換えの途中でも、所有者は、frontend の出荷や Java 版の不具合の直しのために、本番への出荷を行う。そのとき、作りかけの Go 版が本番に出てしまうと、利用者の操作が失敗する。そこで、Claude は、置き換えを段階に分けて PR ごとに main に入れ、どの PR を main に入れたあとでも、本番が今のまま動くようにする。

1. Claude は、置き換えを、次の6つの段階に分け、この順に進める。
   - 段階1: 今と同じにできるかが分からない動きをすべて洗い出し、試しに作って確かめる
   - 段階2: Go 版の品質チェックと、Java 版と Go 版を比べる検査をそろえる
   - 段階3: 機能のまとまりごとの spec で Go 版を作り、Java 版と同じ動きになることを確かめる
   - 段階4: 本番を切り替える準備をする
   - 段階5: 本番を切り替える
   - 段階6: Java 版を削除し、Java と Spring を前提にした記述を書き換え、使っていないものを消す
2. Claude は、Go 版の品質チェックと、Java 版と Go 版を比べる検査をそろえる段階2から、Java 版を削除する段階6までの作業を、1つ以上の PR に分けて main に入れる。Claude は、この spec の PR の本文に、この spec を指す行と、Issue #445 を指す行を書く。Claude は、機能のまとまりごとの spec の PR の本文に、そのまとまりの spec を指す行と、そのまとまりの Issue を指す行を書く。
3. 段階5で切り替えるまでは、所有者が main から本番に出荷しても、本番では Java 版が利用者の操作を受ける。Go 版の作りかけが main にあっても、Go 版は本番で利用者の操作を受けない。
4. どの PR を main に入れたあとでも、所有者が main から本番に出荷すれば、backend の出荷は成功し、続く frontend の出荷も今のとおりに動く。
5. Claude は、Java 版を削除するまでの間に main に入れる PR で、本番のデータベースの表の形を変えない。表の形を変えると、Java 版に戻したときに、Java 版がデータを読めなくなるおそれがあるためである。
6. Claude は、Java 版か Go 版の一方の動きを直す PR を main に入れるときに、もう一方にも同じ機能があれば、同じ PR でもう一方も同じように直す。この決まりは、機能のまとまりごとの spec で Go 版を作る段階3から、Java 版を削除するまでの間に当てはまる。Java 版と Go 版の動きが食い違ったまま切り替えると、直したはずの不具合が、切り替えか、Java 版に戻す出荷で戻るためである。
7. 置き換えの途中でも、Dependabot の PR の扱いと、Java 版の部品の脆弱性の直しは、今のとおりに続ける。
8. Claude は、Java 版の削除と、Java と Spring を前提にした記述の書き換えと、使っていないものの削除をすべて終えた PR でだけ、Issue #445 を閉じる。それより前の PR では、Issue #445 を閉じない。

### 要件2 今と同じにできるかが分からない動きを、設計を書く前にすべて試しに作って確かめる

置き換えで、Claude が作り終えてから「今と同じにできない」と分かると、Claude は、作ったものを捨て、所有者が承認した spec も作り直すことになる。設計を書いてから分かったときも、Claude は設計と要件を直し、所有者は承認し直すことになる。そこで、Claude は、設計を書く前に、今と同じにできるかが分からない動きをすべて洗い出し、試しに作って確かめる。

1. Claude は、この spec の設計を書く前に、Go 版で今と同じにできるかが分からない動きを、Java 版の今のコードと設定からすべて洗い出す。洗い出す動きには、少なくとも次の4つを含める。
   - Go 版が、今の PDF と同じ見た目の PDF を作れること。同じ見た目とは、配置、フォント、文字の大きさ、表の色、改頁の位置が同じことを指す
   - Java 版がログインさせた利用者を、Go 版がそのまま受け入れられること。また、Go 版がログインさせた利用者を、Java 版がそのまま受け入れられること
   - Go 版が、今のデータベースに保存されているパスワードで、利用者をログインさせられること
   - Go 版が、Java 版が書き出したバックアップを戻せること。また、Java 版が、Go 版が書き出したバックアップを戻せること
2. Claude は、洗い出した動きを1つずつ試しに作り、今と同じにできるかを確かめる。Claude は、洗い出した動きの一覧と、動きごとに確かめた方法と結果を、設計を書く前に調べたことを残す記録(`research.md`)に書く。
3. Claude は、試しに作ったコードを、そのまま Go 版のコードとして main に入れない。Go 版のコードは、Go 版の品質チェックをそろえたあとに main に入れるためである。
4. 確かめた結果、今と同じにできないものがあれば、Claude は、設計を書く前に止まり、何が今と同じにならないかと、その違いが利用者に何をもたらすかを所有者に報告する。今と同じにできないものをどう扱うかは、所有者が決める。
5. 機能のまとまりごとの spec でも、Claude は、そのまとまりの設計を書く前に、そのまとまりで新しく見つかった、今と同じにできるかが分からない動きを試しに作って確かめる。

### 要件3 Go 版の品質チェックを、Go 版の機能より先にそろえる

このリポジトリでは、人はコードをレビューしない。品質は、自動の品質チェックが守っている。Go 版のコードが品質チェックの無いまま main に入ると、誤りがあっても止まらずに本番に出る。そこで、Claude は、Go 版の機能を main に入れる前に、Go 版の品質チェックをそろえる。

1. Claude は、Go 版の品質チェックを、Java 版の品質チェックと同じ種類でそろえる。同じ種類とは、次の9つを指す。
   - 書式をそろえる検査
   - 誤りやすい書き方を見つける静的な検査。静的な検査とは、プログラムを動かさずに、コードを読んで調べる検査である
   - 層の間の依存の向きを守っているかの検査
   - 単体テストと結合テスト
   - テストで動いたコードの割合(カバレッジ)が、決めた値を下回ると止める検査
   - コードを少し書き換えたときにテストが気づくかを調べる検査(変異テスト)
   - 脆弱性のある部品と、公開から72時間たっていない部品を止める検査
   - ソースコードの脆弱性の診断と、本番のイメージの脆弱性の検査。イメージとは、本番で動かすプログラムと、プログラムを動かす土台をまとめたものである
   - 本番と同じ形のイメージを組み立てて動かす検査
2. 開発者は、自分の PC が Windows・macOS・Linux のどれでも、Java 版の品質チェックと同じく、決まった1つのコマンドで Go 版の品質チェックを動かせる。CI でも、Go 版のコードを変えた PR では、Go 版の品質チェックが必ず動く。
3. Claude は、Go 版の品質チェックの合格の基準を、Java 版の基準より緩くしない。Go 版のカバレッジの基準は、Java 版の行の割合の基準である 93% を下回らない。Java 版には分岐の割合の基準もあり、その値は 73% である。分岐の割合のように、Go 版で標準的に測れない割合があるときは、Claude は、その割合の代わりにどの検査で同じ守りを保つかを、理由を添えて設計に書く。
4. 週次監査は、Go 版の品質チェックが飛ばされたままマージされた PR を見つけられる。Claude は、必須の検査を足すときに、必須の検査の期待一覧への登録も同じ PR に入れる。
5. Go 版のコードが main に入るのは、Go 版の品質チェックを足す PR か、それより後の PR に限る。
6. 部品の版を上げる PR を自動で作る仕組みは、Go 版の部品の版を上げる PR も作る。Dependabot が直さない部品の脆弱性を直す PR を作る仕組みは、Go 版の部品の脆弱性を直す PR も作る。

### 要件4 機能のまとまりごとに別の spec で Go 版を作り、Java 版と同じ動きになることを機械で確かめる

利用者から見た機能を今のままにするには、Go 版が、Java 版と同じ要求に同じ応答を返し、同じデータを保存しなければならない。人はコードを読まないので、Claude は、同じかどうかを機械で確かめる。また、Java 版の細かい動きを要件と設計に書き写すと、実装の途中で書き漏らした動きが見つかるたびに、Claude は spec を直し、所有者は承認し直すことになる。そこで、Claude は、今の Java 版の実際の動きを正解にして、Java 版と Go 版に同じ要求を送り、応答と保存されたデータを比べる。

1. Claude は、段階3で、Go 版を機能のまとまりごとに作る。Claude は、まとまりごとに Issue #445 の子の Issue を起票し、まとまりごとに別の spec で進める。Claude は、まとまりの分け方と順番を、この spec の設計に書く。
2. Claude は、機能のまとまりごとの spec の要件に、この spec の要件を書き写さない。機能のまとまりごとの spec の要件は、この spec の要件のうち、そのまとまりに当てはまるものを指す。
3. Claude は、この spec の設計を書く前に、今の Java 版が受け付けるすべての API を、API の仕様書に書く。
4. Java 版と同じ動きかどうかの正解は、今の Java 版が実際に返す応答と、実際に保存するデータとする。Claude は、要件と設計に、受け口ごとの細かい動きを書き写さない。実装の途中で Java 版の細かい動きが見つかったときは、Claude は、spec を直さずに、Go 版のコードを Java 版の動きに合わせる。
5. Claude は、機能のまとまりごとに、Java 版と Go 版に同じ要求を送り、応答と、データベースとログインの状態の保存先に残ったデータを比べる検査を作る。比べる要求には、画面が送る正しい要求に加えて、入力の誤り、権限の無い操作、ログインが切れたときのように、画面がエラーを見せる要求を含める。
6. 比べた結果に違いがあれば、その PR は main に入らない。ただし、比べる検査は、利用者が目にしない動きを Claude が意図して変え、変えた動きの一覧に載せた違いでは、PR を止めない。
7. Java 版を削除するまでは、比べる検査は CI で動き続ける。あとから Java 版か Go 版のどちらかを直した PR で動きが食い違ったら、その PR は main に入らない。

### 要件5 本番の切り替えは、所有者が選んだ時に1回の出荷で行い、1回の出荷で Java 版に戻せる

切り替えで Go 版に不具合が見つかったとき、すぐに Java 版に戻せなければ、利用者は、直るまでサービスを使えない。また、本番を変える操作は所有者だけが行うので、操作の手順が分かりにくいと、所有者が誤った順番で操作するおそれがある。そこで、Claude は、切り替えを所有者の1回の出荷で行えるようにし、Java 版に戻す操作も1回の出荷で済むようにする。

1. 段階4で、Claude は、切り替えに要る本番の設定の変更を、Java 版のままでも本番が今のまま動く形で、先に main に入れる。所有者は、切り替えの出荷より前に、その変更を本番に反映する(terraform apply)。
2. 段階4で、Claude は、所有者が1回の出荷で本番を Go 版に切り替えられるようにする。また、所有者が1回の出荷で本番を Java 版に戻せるようにする。Java 版に戻す出荷は、Java 版をリポジトリから削除するまで使える。
3. Claude は、切り替えの手順書を作る。手順書には、所有者がする操作を順番に書き、操作ごとに、押す場所か打つコマンドと、うまくいったかの見分け方を書く。手順書には、切り替えの出荷を、本番が動いている平日の 08:00 から 20:00 の間に行うことも書く。本番が止まっている時間には、データベースも止まっているので、Go 版が動き始められないためである。
4. 切り替えの出荷の時刻は、所有者が選ぶ。
5. 切り替えの出荷が終わったら、Claude は、出荷の結果を読み、本番で Go 版が利用者の操作を受けているかを確かめて、所有者に報告する。所有者が画面で確かめることが残るときは、Claude は、確かめる操作を短く示す。
6. 所有者が切り替えのあとに Java 版に戻したときも、Go 版に届いた保存は残る。利用者は、Java 版に戻したときもログアウトされない。所有者は、Java 版に戻したあとに、もう一度本番を Go 版に切り替えることもできる。
7. 切り替えの出荷が途中で失敗したときは、本番は Java 版のまま動き続ける。
8. Go 版は、本番の動きの記録(ログ)を、Java 版と同じ場所に書く。所有者と Claude は、切り替えのあとも、今と同じ場所で本番の動きの記録を読める。

### 要件6 Java 版を消すのは、所有者が切り替えのあとの動きを確かめてからにする

Java 版をリポジトリから消すと、1回の出荷で Java 版に戻す操作は使えなくなる。切り替えの直後に消すと、あとから Go 版に不具合が見つかったときに、利用者は、直るまでサービスを使えなくなる。そこで、Java 版を消してよいかは、所有者が決める。

1. Claude は、所有者が「Java 版を消してよい」と答えるまで、Java 版をリポジトリから消さない。Claude は、切り替えのあとに、消してよいかを所有者に尋ねる。尋ねるときは、切り替えてから何日たったかと、その間に Go 版で見つかった不具合を示す。
2. 所有者が消してよいと答えたら、Claude は、Java 版のコードと、Java 版だけが使っていた品質チェック、CI の設定、本番の設定を、リポジトリから消す。本番の設定から消したものは、所有者が本番に反映する(terraform apply)。
3. Java 版を消したあとは、本番への出荷と品質チェックは、Go 版だけで今のとおりに動く。
4. Claude は、Go 版の作り方の説明を、Go 版のコードを main に入れる PR で足す。Claude は、Java と Spring を前提にした記述の書き換えと、使っていないものの削除を、Java 版を削除する段階6で終える。Java 版がリポジトリにある間は、Java 版の説明も正しいまま残すためである。

### 要件7 所有者がする操作と進み具合を、所有者が見て分かるようにする

この置き換えは長く続き、途中で会話が途切れることもある。所有者は、今どこまで進んでいて、次に自分が何をすればよいかが分からないと、承認や出荷を止めてしまうか、誤った時に行ってしまう。そこで、Claude は、所有者がする操作を前もって決めておき、所有者が進み具合を機能のまとまりごとに見られるようにする。

1. 所有者がこの置き換えでする操作は、原則として次の6つとする。
   - spec の各段階のコマンドを打つことと、各段階の承認
   - ゲート設定を変える PR と、所有者の承認が要るほかの PR の承認。ゲート設定には、`.github/` と `.claude/` などがある
   - 本番の設定の変更の反映(terraform apply)
   - 切り替えの出荷と、Java 版に戻す出荷
   - 切り替えのあとに、画面で確かめること
   - Java 版を消してよいかの判断
2. 6つのほかの操作が要ると分かったときは、Claude は、その操作が要る理由と、Claude が自分でできない理由を添えて、所有者に頼む。
3. 所有者の承認が要る PR を作ったときは、Claude は、承認が要る理由と、その PR を main に入れたときに本番で何が起きるかを、所有者に1つの返事で示す。本番で何も起きないときは、Claude は、何も起きないことを示す。
4. 所有者は、機能のまとまりごとに、Go 版を作り終えたか、Java 版と同じ動きだと確かめたか、本番で動いているかを、1か所で見られる。
5. 会話が途切れても、Claude は、リポジトリと GitHub の記録から進み具合を読み直して続ける。

### 要件8 決めた方式のとおりに作れないと分かったら、止まって所有者に報告する

所有者は、Issue の「決めた方式」で、Webフレームワークを使わないこと、API の仕様書を先に書くこと、Go にとって標準的な作り方を選ぶことを決めた。作る途中で、決めた方式のとおりに作れないと分かったときに、Claude が自分で方式を変えると、所有者が知らないうちに、所有者が決めた方式が変わってしまう。そこで、Claude は、止まって所有者に報告する。

1. 決めた方式のとおりに作れない機能が見つかったら、Claude は、その機能を作るのを止め、何が方式のとおりに作れないかと、その理由と、とれる案を所有者に報告する。方式のとおりに作れない機能をどう扱うかは、所有者が決める。
2. Java 版と Go 版に同じ要求を送って比べる検査で、Java 版と同じ動きにできない違いが見つかったら、Claude は、その違いを生む Go 版のコードを main に入れず、違いと、その違いが利用者に何をもたらすかを所有者に報告する。
3. Claude は、同じ失敗が3回続いたときに止まって所有者に報告することを、今の決まりのとおりに行う。

### 要件9 利用者から見た機能を変えず、意図して変えたものは一覧にする

所有者は、利用者から見て何も変わらないことを求めた。一方で、所有者は、今のコードの効率の悪い書き方や、避けるべきとされる書き方を Go 版に引き継がないことも決めた。書き方を直すと、画面からは送られない要求への応答のように、利用者が目にしない動きが変わることがある。そこで、Claude は、利用者から見える動きは変えず、利用者が目にしない動きを変えたときは、所有者が確かめられる一覧にする。

1. 置き換えの間も後も、今の画面は、直さずにそのまま動く。Go 版は、画面が使う URL、送り受けするデータの形、ログインの状態を持つ Cookie の名前と性質、ほかのサイトから送られた偽の要求を見分けるために画面が送るヘッダの名前を、Java 版と同じにする。
2. Go 版は、画面に出るエラーの文言と、エラーになる条件を、Java 版と同じにする。エラーになる条件には、入力の長さの上限などがある。
3. Go 版は、送るメールの件名と本文を、Java 版と同じにする。
4. Go 版は、今あるセキュリティの対策を弱めない。たとえば、ログインの状態の有効な時間、2段階認証、パスワードの再設定の手順、ほかのサイトから送られた偽の要求を断ること、確認のメールを送り直せる間隔の制限は、Java 版と同じに守る。
5. Claude は、Go の標準的な作り方にするために、または今の効率の悪い書き方を直すために、利用者が目にしない動きを変えてよい。たとえば、形の誤った要求に、Java 版がサーバの誤りとして答えているものを、Go 版は要求の誤りとして答えてよい。
6. Claude は、利用者が目にしない動きを変えたら、変えた動きを1つずつ一覧にする。一覧には、変えた動き、Java 版の動き、Go 版の動き、画面に影響が無い理由を書く。所有者は、設計の承認のときと、切り替えの出荷の前に、この一覧を見られる。
7. Claude は、主な操作の応答にかかる時間を、Java 版と Go 版で測って比べる。Go 版の応答の時間が、設計で決めた幅を超えて Java 版より長くなる操作があれば、Claude は、切り替えの前に、その操作を受け持つ Go 版を直す。直せなければ、Claude は所有者に報告する。

### 要件10 PDF と Markdown の出力の見た目を変えない

利用者は、KeirekiPro で作った職務経歴書を、PDF と Markdown で出力して、応募先に渡す。出力の見た目が変わると、利用者は、置き換えのあとに出力した書類を確かめ直さなければならない。そこで、Claude は、Go 版の出力を、Java 版の出力と同じ見た目にする。

1. Go 版が作る PDF は、Java 版が作る PDF と、配置、フォント、文字の大きさ、表の色、改頁の位置が同じである。
2. Go 版が作る Markdown は、Java 版が作る Markdown と、文字が1つも違わない。
3. Claude は、Go 版が作る PDF と Markdown が、Java 版が作る PDF と Markdown と同じかを、いろいろな経歴書のデータで機械で比べる。比べるデータには、項目が空の経歴書、勤務先と案件が多くて複数の頁になる経歴書、長い文と改行を含む経歴書、利用者が選べる2つのフォントのそれぞれを選んだ経歴書を含める。
4. Claude は、頁を画像にして比べるなど、見た目の違いを見つけられる方法で、PDF を比べる。Claude は、PDF の比べ方と、許す違いの大きさを、設計に書く。

### 要件11 Java 版で書き出したバックアップを、Go 版でそのまま戻せる

利用者は、バックアップを書き出して手元に持っている。置き換えのあとにそのバックアップを戻せないと、利用者は、手元のバックアップを使えなくなる。そこで、Claude は、Go 版が、Java 版が書き出したバックアップを戻せるようにする。

1. Go 版は、Java 版が書き出したバックアップを、そのまま戻せる。戻した結果は、Java 版で戻した結果と同じである。
2. Go 版は、書き出すバックアップの形を、Java 版と同じにする。Java 版に戻したときに、Go 版で書き出したバックアップを Java 版で戻せるようにするためである。
3. 形の誤ったバックアップと、版の違うバックアップを、Go 版は Java 版と同じに拒み、同じエラーを画面に返す。

### 要件12 本番のデータを、すべてそのまま引き継ぐ

本番には、利用者と経歴書のデータ、アップロードされた画像、利用者のパスワードがある。これらを Go 版が読めないと、利用者は、自分のデータを失うか、ログインできなくなる。そこで、Go 版は、本番のデータを移し替えずに、そのまま読み書きする。

1. Go 版は、本番のデータベースのデータを、移し替えずにそのまま読み書きする。
2. 利用者は、置き換えの前と同じパスワードで、Go 版にログインできる。Google か GitHub のアカウントでログインしていた利用者も、同じアカウントでログインできる。
3. 利用者がアップロードした画像は、置き換えのあとも同じに表示される。
4. Go 版は、今のデータベースの表の形を変えてきた履歴を引き継ぐ。Java 版を削除したあとに表の形を変えるときも、Go 版は、その履歴の続きとして表の形を変える。

### 要件13 切り替えの間と後に、操作が失敗せず、保存が消えず、ログアウトされない

この spec の前提のとおり、切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受ける。そのため、同じ利用者の操作が、続けて別の版に届くことがある。そこで、Claude は、Java 版と Go 版が、互いが保存したものを読めるようにする。

1. 切り替えの間と後に、利用者の保存、PDF の出力、ログイン、ログアウト、2段階認証、パスワードの再設定、メールアドレスの確認は、エラーにならない。
2. Java 版に届いた保存も、Go 版に届いた保存も、切り替えのあとに残っている。
3. 切り替えの前に Java 版でログインした利用者は、切り替えの途中でも後でも、ログインし直さずに使い続けられる。
4. 途中の手順をまたぐ操作は、途中で別の版に届いても、最後まで終えられる。途中の手順をまたぐ操作とは、外部のアカウントでのログイン、2段階認証、パスワードの再設定、新規の登録のメールアドレスの確認のように、1つ目の要求と2つ目の要求の間で状態を覚えておく操作を指す。
5. Java 版を削除したあとに、Go 版がログインの状態の保存の形を変えるときも、利用者はログアウトされず、途中の手順をまたぐ操作は最後まで終えられる。
6. Claude は、切り替えの出荷より前に、この要件で挙げたことが成り立つかを機械で確かめる検査を作る。この検査は、Java 版と Go 版の両方を、同じデータベースと、ログインの状態の同じ保存先につないで動かす。この検査は、途中の手順をまたぐ操作と、ログインしたままの利用者の操作について、1つ目の要求を一方の版に送り、2つ目からの要求をもう一方の版に送っても、操作が最後まで終わることを確かめる。この検査は、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方を確かめる。この検査は、Java 版を削除するまで CI で動き続ける。この検査が通らない PR は、main に入らない。切り替えの間と後に利用者の操作が最後まで終わるかを、本番の切り替えで初めて確かめることにならないようにするためである。

### 要件14 開発者向けの API の説明画面を、開発環境で開ける

今は、開発者が開発環境で API の説明画面を開き、API の一覧と、送るデータと返るデータの形を見られる。所有者は、この画面を Go 版でも残し、Swagger である必要はなく、Go における標準的なものにすると決めた。

1. 開発者は、開発環境で Go 版を動かしたときに、API の説明画面を開ける。
2. API の説明画面は、Issue の「決めた方式」で先に書くと決めた API の仕様書から作られる。仕様書と、Go 版が実際に受け付ける API が食い違うと、品質チェックが止める。
3. 本番では、今と同じく、利用者は API の説明画面を開けない。
4. Claude は、API の説明画面の URL を、Java 版の URL に合わせない。Claude は、開発者が開く URL を、開発の手順の文書に書く。

### 要件15 Java と Spring を前提にした記述を書き換え、言語に依存しない書き方にする

このリポジトリの決まりと手順書の多くは、backend が Java と Spring Boot であることを前提に書かれている。置き換えたあとにそのまま残ると、Claude と開発者は、無くなった Java 版の手順に従おうとして誤る。また、所有者は、将来また別の言語に替えるときに、同じ書き換えが起きないようにしたいと考えている。そこで、Claude は、Java と Spring を前提にした記述をすべて書き換え、言語を書かなくてよい文書は、言語に依存しない書き方にする。

1. Claude は、リポジトリの文書、決まり、スキル、手順書、設定のうち、Java と Spring を前提にした記述を、すべて Go 版に合わせて書き換える。
2. 言語を書いてよいのは、README、`backend/` の中の説明、`.kiro/steering/tech.md`、`doc/` の設計図に限る。`backend/` の中の説明には、`backend/CLAUDE.md` などがある。
3. Claude は、ルートの `CLAUDE.md`、スキル、`doc/開発フロー/` などの手順書を、言語の名前と、言語に固有の道具の名前を書かない書き方にする。たとえば、手順書には「backend の品質チェックを動かす」のように書き、どの道具で動かすかは、言語を書いてよい文書に書く。
4. 書き換えたあとに、言語を書いてよい文書と spec の記録(`.kiro/specs/`)のほかに、Java、Spring、Gradle のように Java 版だけが使う言語と道具の名前が残っていない。

### 要件16 使っていないものを消す

使っていないものが残っていると、Claude と開発者は、それを直すべきか残すべきかを毎回考えることになり、保守の手間が増える。そこで、Claude は、使っていないものを消す。ただし、Claude が、使っていないかの見立てを誤ると、要るものを消してしまう。そのため、消す一覧は所有者が確かめる。

1. 消す対象は、今の立ち上げの手順、CI、本番のどれでも使っていないものである。今の立ち上げの手順とは、`start-dev.sh` と、Claude による起動を指す。
2. Claude は、消す一覧を設計に書く。一覧には、消すものごとに、使っていないと判断した理由を書く。所有者は、設計を承認するときに、この一覧を確かめる。
3. Claude は、所有者が一覧で消してよいとしたものだけを消す。
