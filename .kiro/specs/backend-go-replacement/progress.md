## Java 版と Go 版の応答の時間を比べた結果

Claude は、開発環境で `bash .claude/scripts/parallel/run-check.sh backend-go make compat-perf` を動かし、結果をここに書く。
測り方は design.md の「perf(応答の時間の比べ方)」のとおりで、時間を測らない要求を20回送ったあと、同じ要求を200回ずつ送り、95パーセンタイルを比べる。
Go 版の上限は「Java 版の95パーセンタイル × 1.2 + 20ミリ秒」である。Claude は、Go 版を直して測り直したら、その操作の行を書き換える。

- 2段階認証の確認は、確認のコードを1回しか使えないので、測る回ごとにログインの段を送り直して、届いたメールの確認のコードを使う
- 新規の登録は、同じメールアドレスで登録を繰り返す。測る回ごとに応答を確かめ、Java 版と Go 版のどちらも、繰り返した登録に 202 を返した
- 名前を変える操作は、測る回ごとに同じ名前を送る。1回目のあとは名前が変わらないが、どちらの版も、名前を検査し、利用者を読み、利用者を書き、利用者の情報を読み直す処理を、毎回行う
- マスタと経歴書の5つの操作は、6つの欄のすべてに項目を持つ経歴書(`fixtures/resumes/fonts.sql`)を使って測る。経歴書の基本の情報とプロジェクトの項目を直す操作は、測る回ごとに同じ値を送る。どちらの版も、経歴書の名前が変わらないときは、ほかの経歴書との名前の重なりを確かめない。そのため、基本の情報を直す操作の時間には、名前の重なりを確かめる時間が入らない
- 出力の2つの操作は、6つの欄のすべてに項目を持ち、PDF が2頁になる経歴書(`fixtures/resumes/fonts.sql` の経歴書 401)を使って測る。PDF の出力は、画面の PDF の保存と同じ本文(`fixtures/resumes/fonts-NotoSansJP.json`)を送る
- PDF の出力を同時に2件送ったときの、Go 版のコンテナのメモリの最大は 108.3MB で、上限の 1792.0MB の内側だった。上限は、本番のタスク定義の memoryReservation の 1792MB である(2026-11-26 に測った)
- バックアップの2つの操作は、6つの欄のすべてに項目を持つ経歴書(`fixtures/resumes/fonts.sql` の経歴書 401)を使って測る。戻しは、経歴書 401 を書き出したファイル(`fixtures/backups/java-401.json`)を送る。同じファイルを続けて戻すと名前の重なりで断られるので、測る回ごとに、ログインと、経歴書の一覧の最初の経歴書を消す要求を送り直してから戻す
- 職歴を足す操作は、経歴書 401 を使って測る。同じ経歴書に職歴を足し続けると、期間の重なりと、1つの経歴書の職歴の数の上限の30件で断られる。そのため、測る回ごとに、ログインと、経歴書の一覧の最初の経歴書を消す要求と、経歴書 401 を書き出したファイルを戻す要求を送り直してから、戻した経歴書に職歴を1件足す
- Go 版の本番のイメージは、起動から `/healthz` が 200 を返すまでに 246ms かかり、上限の10秒の内側だった。応答の時間を比べたときの Go 版の起動で測った(2026-11-26 に測った)

## 所有者がする操作

所有者がこの置き換えでする操作は、原則として次の6つである。

1. spec の各段階のコマンドを打つことと、各段階の承認
2. ゲート設定を変える PR と、所有者の承認が要るほかの PR の承認
3. 本番の設定の変更の反映(`terraform-apply.yaml` を、`plan_only` を付けて1回、外して1回動かす)
4. 切り替えの出荷と、Java 版に戻す出荷
5. 切り替えのあとに、画面で確かめること
6. Java 版を消してよいかの判断

6つのほかの操作が要ると分かったときは、Claude は、その操作が要る理由と、Claude が自分でできない理由を添えて、所有者に頼む。

## PR の本文の決まり

- この spec の PR の本文には、`Spec: .kiro/specs/backend-go-replacement` と `Refs: #445` を書く
- 段階4〜6の PR の本文には、その段階の子の Issue を指す `Refs: #<番号>` も書く。その段階の最後の PR の本文には、その段階の子の Issue を閉じる `Closes #<番号>` も書く
- まとまりの spec の PR の本文には、そのまとまりの spec を指す `Spec: .kiro/specs/<名前>` と、そのまとまりの子の Issue を指す行を書く
- 所有者の承認が要る PR の本文には、「承認が要る理由」と「main に入れたときに本番で起きること」の2つの欄を書く。PR を作ったときの所有者への返事に、この2つの欄をそのまま写す。本番で何も起きない PR では、2つ目の欄に「本番で起きることは無い」と書く
- 段階3から Java 版を削除するまでは、Java 版か Go 版の一方の動きを直す PR で、もう一方にも同じ機能があれば、同じ PR でもう一方も同じように直す
- Issue #445 を閉じるのは、段階6の作業をすべて終えた PR だけである。それより前の PR では `Closes #445` を書かない
- ワークフロー close-linked-issues は、子の Issue がすべて閉じると親の Issue も閉じる。2026-11-24 に段階3の最後の子の Issue #774 が閉じたとき、段階4〜6に子の Issue が無かったので、このワークフローが Issue #445 を閉じた。Claude は Issue #445 を開き直し、段階4〜6の子の Issue を足した。Claude は、Issue #445 の子の Issue を足すか消すときは、残る作業がすべてどれかの子の Issue に入っていることを確かめる
