# 本番を Go 版に切り替える手順書

この手順書は、本番の backend を Java 版から Go 版に切り替えるときと、Java 版に戻すときと、もう一度 Go 版に切り替えるときに、所有者がする操作を順番に書く。操作の中身は、この手順書の後ろの「操作」の節に、操作1から操作6として書く。

## 始める前に守ること

- 出荷は、本番が動いている平日の 08:00 から 20:00 の間に起動してください。本番は 20:00 に止まり、データベースも 20:05 に止まります。本番が止まっている時間には、Go 版が動き始められません。
- 出荷は、20:00 の30分前の 19:30 までに終えてください。2026-08-21 から 2026-11-24 までの10回の本番の出荷は、承認を待つ時間も含めて5分から42分かかりました。そのため、出荷は 18:45 より前に起動してください。
- 切り替えのあとに、Java 版に戻す出荷が要ることもあります。戻す出荷も 19:30 までに終えられるよう、切り替えの出荷は時間に余裕を持って始めてください。
- 出荷の時刻は、所有者が選びます。Claude は時刻を決めません。
- Java 版に戻す出荷は、Java 版と比べる検査を消す PR(段階6の PR 6-1)が main に入るまで使えます。PR 6-1 が main に入ったあとは、Java 版に戻せません。そのため、PR 6-1 より前に Go 版の不具合が見つかったときは、Claude が段階6を止めて、Java 版を消してよいかを所有者にもう一度尋ねます。

## 場面ごとの操作の順番

### 本番を Go 版に切り替える

1. 操作1: 本番の設定の変更を反映する
2. 操作2: 切り替えの前に、手元で Go 版に繋いだ画面を確かめる
3. 操作3: 切り替えの出荷をする
4. 操作4: Claude に「切り替えた」と書く
5. 操作5: 本番の画面で確かめる

操作2は、必ず操作3より前に行ってください。操作2で見分け方と違う操作か画面を見つけたときは、操作3に進まないでください。

2026-11-26 の時点で、操作1は済んでいます。2026-11-26 の朝に PR #946 が main に入ったあとの `Terraform Apply` の実行(番号 45723363595)で、本番に反映しました。そのあとに terraform の変更が main に入ったかは、Claude が操作2の前に確かめて、会話に書きます。Claude が「terraform の変更は入っていない」と書いたときは、操作1を飛ばして操作2から始めてください。

### Java 版に戻す

次のどちらかが起きたら、所有者は Java 版に戻します。

- Claude が、出荷のあとの Go 版のログに、5xx の応答の行を見つけた。5xx の応答とは、サーバの中で処理が失敗したことを表す応答である
- 所有者が操作5で確かめた操作のどれかが、見分け方と違った

戻すときの操作の順番は、次のとおりです。

1. 操作6: Java 版に戻す出荷をする
2. 操作4: Claude に「戻した」と書く
3. 操作5: 本番の画面で確かめる

Java 版に戻しても、Go 版で保存した値は残ります。利用者は、Java 版に戻してもログアウトされません。

### もう一度 Go 版に切り替える

Java 版に戻したあと、Claude が原因を直す PR を出し、その PR が main に入ったら、所有者はもう一度切り替えます。

1. 操作2: 切り替えの前に、手元で Go 版に繋いだ画面を確かめる
2. 操作3: 切り替えの出荷をする
3. 操作4: Claude に「切り替えた」と書く
4. 操作5: 本番の画面で確かめる

本番の設定の変更は、1回目の切り替えのときに反映が済んでいるので、操作1は要りません。ただし、そのあとに terraform の変更が main に入ったときは、Claude が操作2の前にそう書きます。そのときは、操作2の前に操作1を行ってください。操作2は、必ず操作3より前に行ってください。

## 操作

### 操作1: 本番の設定の変更を反映する

本番の設定は、terraform の変更が main に入っただけでは変わりません。所有者は、`Terraform Apply` のワークフローを2回動かして、本番に反映します。2回に分けるのは、所有者が本番との差分を見てから、本番に反映するかを決めるためです。

1回目は、差分を見るだけの実行です。

1. GitHub のリポジトリの「Actions」タブを開き、左の一覧の「Terraform Apply」を押します。
2. 右の「Run workflow」を押し、「Branch」が `main` であることを見ます。
3. 「チェックを付けると、差分をログに出したところで止まり、本番には適用しない」の欄にチェックを付けて、緑の「Run workflow」を押します。
4. 起動した実行を開き、「Review deployments」を押します。`production` にチェックを付けて、「Approve and deploy」を押します。
5. 実行が終わると、実行の概要に「本番には適用していません」が出ます。出たら、会話に「1回目が終わった」と書きます。実行が赤のバツで終わったときと、「本番には適用していません」が出ないときは、2回目に進まず、会話に「1回目が失敗した」と書いてください。Claude がログを読んで原因を調べます。
6. Claude が、実行のログの差分を読み、PR の本文に書いた変わるはずの資源と値と照らした結果を、会話に書きます。

2回目は、本番に反映する実行です。Claude が「差分は PR の本文のとおり」と書いたときだけ、2回目に進みます。

1. 1回目と同じく、「Actions」タブの「Terraform Apply」で「Run workflow」を押します。
2. 「チェックを付けると、差分をログに出したところで止まり、本番には適用しない」の欄のチェックを外して、緑の「Run workflow」を押します。
3. 起動した実行を開き、「Review deployments」を押します。`production` にチェックを付けて、「Approve and deploy」を押します。
4. 実行が緑のチェックで終われば、反映は終わりです。赤のバツで終わったときは、会話に「2回目が失敗した」と書いてください。Claude がログを読んで原因を調べます。

うまくいったかの見分け方: 次のコマンドを打つと、本番の Redis の秘密の値に入っているキーの名前が並びます。並んだ名前の中に `redis-username` があれば、反映できています。このコマンドは、キーの名前だけを出し、値は出しません。

秘密の値は、いつもの読むだけの権限では読めません。そのため、このコマンドは `keirekipro-admin` の権限で動かします。最初に6桁のコードを聞かれたら、認証アプリのコードを入れてください。

```powershell
(aws secretsmanager get-secret-value --secret-id keirekipro/redis --query SecretString --output text --profile keirekipro-admin | ConvertFrom-Json).PSObject.Properties.Name
```

`redis-username` が無いときと、コマンドがエラーを出したときは、出た文をそのまま会話に貼ってください。

### 操作2: 切り替えの前に、手元で Go 版に繋いだ画面を確かめる

この操作は、所有者がこの置き換えでする6つの操作(要件7)には入っていません。Claude がこの操作を所有者に頼む理由は、次の2つです。

- 操作2が要る理由: 所有者が、Issue #935 の会話で、本番を切り替える前に Go 版の画面を自分の目で確かめると決めたためです。
- Claude が操作2を自分でできない理由: 手元の開発環境の利用者のパスワードは所有者のものであり、Claude はそのパスワードを入れられないためです。

所有者が操作2を始める前に、Claude は次のことをします。所有者は、会話に「操作2を始める」と書くだけです。

1. Claude は、本体のフォルダを main の最新にし、worktree で作られて残っている開発環境のコンテナを消します。データベースと部品のデータは残ります。
2. Claude は、`backend-go` のコンテナを消してから、本体のフォルダで `start-dev.sh` を動かし、Go 版を本体のフォルダのコードで起動し直します。
3. Claude は、Java 版に繋いだ画面の開発サーバを止め、Go 版に繋いだ画面の開発サーバを、同じアドレスで起動します。
4. Claude は、所有者が開くアドレス `http://localhost:5173` を会話に書きます。

所有者の操作は、次のとおりです。

1. 作業PCのブラウザで、Claude が書いた `http://localhost:5173` を開きます。
2. 手元の開発環境の利用者でログインします。
3. 経歴書を1つ開きます。
4. 経歴書の項目を1つ書き換えて、保存します。
5. ブラウザの画面を開き直して、書き換えた値が残っていることを見ます。
6. PDF を出力して、PDF を開きます。
7. 会話に「確かめた」と書きます。

うまくいったかの見分け方: 途中でログインの画面に戻らず、保存した値が画面を開き直しても残り、PDF が開けることです。

見分け方と違ったときは、違った操作と、画面に出た文を、そのまま会話に書いてください。そのときは、操作3の切り替えの出荷をしないでください。Claude が違いの原因を調べて、原因を直す PR を出します。その PR が main に入ったら、操作2をやり直します。

所有者が「確かめた」と書いたあと、Claude は次のことをします。

1. Claude は、確認の間の Go 版のログに 5xx の応答の行が無いかを読み、結果を会話に書きます。
2. Claude は、Go 版に繋いだ画面の開発サーバを止め、`start-dev.sh` で、Java 版に繋いだ画面の開発サーバを起動し直します。

Claude が「5xx の行は無い」と書いたら、操作3に進めます。Claude が「5xx の行がある」と書いたときは、操作3に進まないでください。Claude が原因を調べて、原因を直す PR を出します。その PR が main に入ったら、操作2をやり直します。

### 操作3: 切り替えの出荷をする

1. GitHub のリポジトリの「Actions」タブを開き、左の一覧の「Production Release」を押します。
2. 右の「Run workflow」を押し、「Branch」が `main` であることを見ます。
3. 「バックエンドの版」の選び欄で `go` を選びます。ほかの欄は、初めの値のままにします。
4. 緑の「Run workflow」を押します。
5. 起動した実行を開き、「Review deployments」が出たら押します。`production` にチェックを付けて、「Approve and deploy」を押します。「Review deployments」は、backend の出荷と frontend の出荷で1回ずつ、合わせて2回出ます。2回目は、backend の出荷が終わってから出るので、実行の画面を開いたまま待ってください。

うまくいったかの見分け方: 実行の画面を下に送ると、「Backend の出荷の版」の欄に「出荷する版: `go`」が出ています。そして、`backend-release` と `frontend-release` の仕事が、どちらも緑のチェックで終わっています。

出荷が赤のバツで終わったときは、すぐに会話に「切り替えの出荷が失敗した」と書いてください。backend の出荷が失敗したときは、多くの場合、本番は Java 版のまま動き続けます。ただし、backend の出荷が起動の完了を待つ間に時間切れで失敗し、そのあとで Go 版の起動が成功したときは、Go 版が動いています。また、backend の出荷が終わったあとに frontend の出荷が失敗したときは、本番の backend はすでに Go 版で動いています。そのため、どちらの出荷が失敗したときも、Claude は、ログと本番で動いている backend のイメージのタグを読み、本番が今どちらの版で動いているかと、次にすることを会話に書きます。

### 操作4: Claude に報告する

出荷が終わったら、会話に、切り替えたときは「切り替えた」、Java 版に戻したときは「戻した」と書きます。

Claude は、次のことを確かめて、1つの返事に書きます。

- 出荷の実行の結果
- 本番で動いている backend のイメージの版。切り替えたときは、イメージのタグが `go-` で始まることを確かめます。戻したときは、`go-` で始まらないことを確かめます
- 出荷のあとの backend のログに、5xx の応答の行が無いか
- 所有者が操作5でする操作

Claude の環境に本番の AWS を読む権限が無いときは、Claude が打つコマンドを1つずつ会話に書きます。所有者はそのコマンドを打ち、出た結果を会話に貼ってください。

うまくいったかの見分け方: Claude が、出荷の結果とログを確かめた返事を書くことです。

### 操作5: 本番の画面で確かめる

1. 本番の画面を、ログインしたままのブラウザで開きます。
2. 経歴書を1つ開きます。
3. 経歴書の項目を1つ書き換えて、保存します。
4. ブラウザの画面を開き直して、書き換えた値が残っていることを見ます。
5. PDF を出力して、PDF を開きます。
6. 結果を会話に書きます。

うまくいったかの見分け方: 途中でログインの画面に戻らず、保存した値が画面を開き直しても残り、PDF が開けることです。

Go 版に切り替えたあとで見分け方と違ったときは、違った操作と、画面に出た文を、そのまま会話に書いてから、操作6の Java 版に戻す出荷をしてください。

Java 版に戻したあとで見分け方と違ったときも、違った操作と、画面に出た文を、そのまま会話に書いてください。このときは、Java 版に戻す前からあった不具合か、戻したことで起きた不具合かを、Claude がログを読んで調べ、結果と次にすることを会話に書きます。

### 操作6: Java 版に戻す出荷をする

1. GitHub のリポジトリの「Actions」タブを開き、左の一覧の「Production Release」を押します。
2. 右の「Run workflow」を押し、「Branch」が `main` であることを見ます。
3. 「バックエンドの版」の選び欄で `java` を選びます。
4. 「フロントエンドをデプロイする」のチェックを外します。Java 版に戻すときは、画面を出し直す必要が無いためです。
5. 緑の「Run workflow」を押します。
6. 起動した実行を開き、「Review deployments」が出たら押します。`production` にチェックを付けて、「Approve and deploy」を押します。

うまくいったかの見分け方: 実行の画面を下に送ると、「Backend の出荷の版」の欄に「出荷する版: `java`」が出ています。そして、`backend-release` の仕事が緑のチェックで終わっています。

戻す出荷が赤のバツで終わったときは、すぐに会話に「戻す出荷が失敗した」と書いてください。Claude は、ログを読んで原因を調べ、本番が今どちらの版で動いているかと、もう一度戻す出荷をするかどうかを会話に書きます。

## 出荷の版の決まり方

「Production Release」の「バックエンドの版」には、次の3つがあります。

| 選ぶ値 | 出荷する版 |
|---|---|
| `current`(初めの値) | 今の本番と同じ版 |
| `java` | Java 版 |
| `go` | Go 版 |

`current` を選んだ出荷は、本番のサービスが今動かしているイメージのタグを読みます。タグが `go-` で始まれば Go 版を、そうでなければ Java 版を出荷します。そのため、切り替えのあとに、版を選ばずにいつもの出荷をしても、本番は Go 版のまま動きます。
