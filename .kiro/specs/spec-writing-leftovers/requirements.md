# 要件

## 元の要望
Issue #477: spec の書き方の変更(#474)で残った問題を直し、古い書き方の spec をなくす

### きっかけ

#474 の実装(PR #476)の途中で AI が見つけた5つの問題について、所有者が1つの Issue でまとめて直すと決めた。

### 困っていること

1. 新しい tasks.md の雛形(`.kiro/settings/templates/specs/tasks.md`)の完了条件の節に、「上記フォーマット」「detail item に記載する」「受け入れ基準」という分かりにくい言い回しが残っている
2. spec.json の `spec_format` が2でも欄無しでもない値のとき、spec を書くスキルは止まるが、`/spec-review` と、作業を止める判定(`spec-review-scan.sh`)は今の書き方の spec として扱う。扱いがそろっていない
3. `/kiro-spec-tasks` の決まり(`tasks-generation.md`)の2か所が、新しい design.md の雛形に無い見出し「Architecture Pattern & Boundary Map」を名指ししている
4. spec.json の `ready_for_implementation` を true にするスキルが無い。一方で、PR の spec の検査(`check-spec-backing.sh`)は true を求める
5. spec-readable-writing の design.md が、雛形の説明のために `{{NUMBER}}` `{{TITLE}}` を本文に書いている。200行を超える PR がこの spec を `Spec:` に書くと、プレースホルダの検査が赤になる

### やりたいこと

- 上の5つを、1つの Issue でまとめて直す
- 古い書き方の spec をすべて新しい書き方に書き換え、`spec_format` の印と、古い書き方のための仕組みをなくす
- #474 の spec の design.md にある `{{NUMBER}}` `{{TITLE}}` も、同じく書き換えで直す

### 決めた方式

今回だけの特例として、spec の書き換えを次の順に進める。

1. Claude が、すべての spec を書き換える
2. Fable 5.1 のサブエージェントが、書き換えの前と後で中身が同じかだけを確かめる。書き換え前の本文がこれまでの仕様なので、書き換え前のほうを正とする。サブエージェントは、ほかの観点では一切確かめない
3. 確かめた結果に問題が無ければ、Claude は、書き換えた spec のすべての段階を承認済みとして記録してよい。所有者は承認し直さない

## はじめに

#474 で、spec の書き方は、所有者が読んで分かる日本語の書き方(新しい書き方)に変わった。そのとき、すでにあった spec は古い書き方のまま残り、spec を扱う道具は spec.json の印 `spec_format` で新旧を見分けることになった。Claude は、この spec で、古い書き方の spec をすべて新しい書き方に書き換えて、印と古い書き方のための仕組みをなくす。あわせて、Claude は、#474 の実装の途中で見つかり、元の要望の「困っていること」に挙げた問題を直す。

## 範囲

- この spec で決めること: 古い書き方の spec の書き換えと、その確かめ方と、承認の記録。印と古い書き方のための仕組みをなくすこと。tasks.md の雛形の完了条件の節の言い回し、タスクを作る決まりが指す見出し、200行を超えるPRの検査が承認を確かめる方法
- この spec で決めないこと: spec の requirements.md・design.md・tasks.md 以外のファイル(research.md、`reviews/` の審査の記録など)の書き方。書き換える spec が決めた仕様の中身
- この spec が前提にしていること: 新しい書き方は `.kiro/settings/rules/spec-writing.md` が決める

## 要件

### 要件1 古い書き方の spec を新しい書き方に書き換える

古い書き方の spec が残ると、spec を書く道具と読む道具は、2つの書き方を見分け続けなければならず、仕組みが複雑になる。所有者は、印を持ち込んで仕組みを複雑にするより、今ある spec をすべて新しい書き方に書き換えると決めた。

1. Claude は、古い書き方の spec(spec.json に `spec_format` の欄の無い spec)のすべてについて、requirements.md・design.md・tasks.md を、`.kiro/settings/rules/spec-writing.md` の決まりと新旧の見出しと目印の対応表に沿って新しい書き方に書き換える。
2. Claude は、書き換えで、spec が決めた中身を変えない。Claude は、書き換え前の本文に無い決めごとを足さず、書き換え前の本文にある決めごとを削らない。書き換える spec の記述が今の仕組みと食い違っていても、Claude はその記述を直さない。
3. Claude は、書き換えで、要件・項目・タスクの番号を変えない。Claude は、タスクの完了の印(`[x]`)と、追加のIssueを示す印(`(#N)` など)を、新しい書き方での置き場所に移して残す。
4. Claude は、Issueの本文や既存の文書から引用した部分を、引用元のまま残す。
5. 新しい書き方ですでに書かれた spec でも、本文が雛形の説明のために `{{英大文字}}` の形の文字を書いていれば、Claude はその文字を、意味を変えずに、書き込まれずに残った空欄と取り違えられない書き方に書き換える。Claude は、この書き換えも、書き換えの前後で中身が同じかを Fable 5.1 のサブエージェントに確かめさせる対象と、中身が同じと確かめた spec を承認済みとして記録する対象に含める。
6. 新旧の見出しと目印の対応表で新しい名前が「なし」とされる見出しの節(既存の構成の分析、参考資料、要件と部品の対応表など)は、Claude は、その節の中身を同じファイルの中に残す。中身が書き換え後の別の箇所(各部品の「対応する要件」の行など)にすでに表れていれば、Claude はその節を立てない。表れていなければ、Claude はその節を日本語の見出しの節として残す。

### 要件2 書き換えの前後で中身が同じかを Fable 5.1 が確かめる

書き換え前の本文は、所有者が承認し、実装の基準になった仕様である。書き換えで中身が変わると、所有者が承認していない仕様が承認済みとして残る。そこで、所有者は、書き換え前の本文を正として、別のモデルが書き換えの前後を比べると決めた。

1. Claude は、spec を書き換えたら、Fable 5.1 のサブエージェントに、書き換え前の本文と書き換え後の本文を比べさせる。サブエージェントは、両者の中身が同じかどうかだけを確かめる。サブエージェントは、書き方の良し悪しや仕様の正しさなど、ほかの観点では確かめない。
2. 比べる中身は、spec が決めたこと(要件と項目、設計で決めたこと、タスクとその完了の状態、番号)である。`.kiro/settings/rules/spec-writing.md` が求める書き方の違い(見出しと目印の名前、節の並び、文の形、利用者の立場を名乗る行を書き直した理由の段落)は、サブエージェントは食い違いとして扱わない。
3. サブエージェントは、書き換え前の本文を正とする。食い違いを見つけたら、サブエージェントは、書き換え後のどのファイルのどの記述が、書き換え前のどの記述と食い違うかを返す。
4. サブエージェントが食い違いを返したら、Claude は、書き換え後の本文を書き換え前の中身に合わせて直し、サブエージェントにもう一度確かめさせる。
5. サブエージェントが同じ spec を3回確かめても食い違いが残ったら、Claude はその spec の書き換えを止め、残った食い違いを所有者に知らせる。Claude は、その spec の本文を書き換え前の状態に戻し、spec.json を書き換えない。
6. Claude は、サブエージェントが確かめた結果を、spec ごとに記録として残す。

### 要件3 中身が同じと確かめた spec を承認済みとして記録する

所有者は、今回だけの特例として、中身が同じと確かめられた spec を、所有者が承認し直さなくても承認済みとして扱うと決めた。書き換えた spec が承認済みとして扱われなければ、その spec を `Spec:` に書く200行を超えるPRは、承認の検査で赤になる。

1. 特例として、Claude は、書き換えの間、書き換える spec の承認を取り消さない。Claude は、サブエージェントが中身が同じと確かめるまで、spec.json の承認の記録を変えない。
2. サブエージェントが中身が同じと確かめたら、Claude は、書き換えた段階ごとに、書き換える前の承認(承認者と日時)と書き換えの理由を、spec.json の承認の履歴(`approval_history`)に追記する。そのあと、Claude は、その段階を特例による承認済みとして spec.json に記録する。所有者は承認し直さない。
3. 本文を書き換えなかった段階では、Claude は承認の記録を変えない。
4. Claude は、特例で記録した承認が、所有者が本文を読んで出した承認ではなく、Issue #477 の特例によるものだと、spec.json の記録から分かるようにする。
5. 承認を確かめる仕組み(200行を超えるPRの検査と、作業を止める判定)は、特例で承認済みにした spec を、所有者が承認した spec と同じく承認済みとして扱う。
6. Claude は、この特例を今回の書き換えにだけ使う。これより後に承認済みの spec を直すときは、Claude は今までどおり承認を取り消し、所有者の承認を得る。

### 要件4 書き方の印と古い書き方のための仕組みをなくす

すべての spec が新しい書き方になれば、spec.json の印も、古い書き方のための雛形・決まり・道具の分かれ道も要らなくなる。印と古い書き方のための分かれ道を残すと、それらは、印の値が想定外のときの扱いが道具ごとにずれるように、仕組みを複雑にする元になる。

1. すべての spec の書き換えと確かめが終わったら、Claude は、すべての spec.json から印 `spec_format` を消す。Claude は、新しい spec を作るときも、spec.json に印を書かない。
2. spec を書く道具、読む道具、審査する道具(スキル、点検役と審査役、作業を止める判定、200行を超えるPRの検査)は、新しい書き方だけを扱う。どの道具も、spec の書き方を見分けない。
3. Claude は、古い書き方のためだけにある雛形と決まりを消す。
4. Claude は、CLAUDE.md と `.kiro/settings/rules/spec-writing.md` から、古い書き方と印についての記述を消す。
5. どれかの spec の書き換えを止めたときは、Claude は、印と古い書き方のための仕組みを消さず、この spec の変更を出荷しない。Claude は、所有者がどう進めるかを決めるまで待つ。

### 要件5 tasks.md の雛形の完了条件の節を分かる言葉で書く

所有者は、tasks.md の雛形の完了条件の節を読んでも、「上記フォーマット」がどこを指すのか、「detail item」が何なのか、「受け入れ基準」が「受入基準」と同じものなのかが分からない。

1. tasks.md の雛形の完了条件の節は、`.kiro/settings/rules/spec-writing.md` の文の書き方に沿う。節の文は、「上記フォーマット」「detail item」のように、指す先の分からない言葉や英語の言い回しを使わない。
2. 節の文は、タスクの箇条書きの欄を、雛形と見本にある欄の名前(「完了の確かめ方」「受入基準とテストの対応」など)で指す。
3. 節の文は、「受入基準」の表記を、雛形と見本と同じ1つにそろえる。
4. Claude は、節が決める中身(受入基準とテストの対応を書くこと、verify を通すこと、テストの無効化などで見かけの合格を作らないこと、新しいテストが対象を壊すと失敗するのを確かめること)を変えない。

### 要件6 タスクを作る決まりが、設計の雛形にある見出しを指す

Claude がタスクを作るときに読む決まりが、design.md の雛形に無い見出しを名指ししていると、Claude は、部品の境界を design.md のどこで確かめればよいかが分からない。

1. Claude が `/kiro-spec-tasks` で読む決まりは、design.md の部品の境界を、design.md の雛形にある見出しの名前で指す。

### 要件7 3つの段階の承認がそろえば、200行を超えるPRの検査を通る

今は、所有者が3つの段階を承認しても、`ready_for_implementation` を true にする道具が無い。そのため、新しく作った spec を `Spec:` に書く200行を超えるPRは、承認がそろっていても検査で赤になる。

1. 200行を超えるPRの検査は、所有者が requirements・design・tasks の3つの段階をすべて承認した spec を、所有者がほかに何もしなくても、承認がそろっていると判定する。
2. 200行を超えるPRの検査は、3つの段階のどれかが承認されていない spec を、今までどおり、承認がそろっていないと判定する。
3. 200行を超えるPRの検査は、新しいIssueのために開き直して承認が取り消された spec を、3つの段階が承認し直されるまで、承認がそろっていないと判定する。
