# Requirements Document

## Project Description (Input)
Issue #472: 着手の入口を1つにし、specの要否をAIが着手時に判断する

### きっかけ

`/kiro-spec-init` を打つのは所有者なので、spec が要るかどうかを所有者が決めなければならないが、所有者にはその判断ができない。起票の直後ならAIが案内できるが、Issueだけ先に切っておき、着手は後になることもある。

### 困っていること

- `/kiro-spec-init` を打つのは所有者なので、spec が要るかどうかを所有者が判断する必要があるが、できない
- `/request` でIssueを作った直後ならAIが判断して `/kiro-spec-init` を依頼できるが、起票してすぐ作業に取り掛かるとは限らない。とりあえずIssueだけ切ることもある
- spec 無しで動き始めて、あとで spec が必要になることがある。そのときどうするかが決まっていない。そもそもそうならないようにしたい
- 逆に、spec が必要と想定して spec 駆動で始めたが、実際はごく小規模で終わることがある

### やりたいこと

- 所有者が着手時にすることは、spec の要否にかかわらず1つだけにする。AIがその時点のコードを調べてから進め方を決め、理由を添えて示す(AIの提案を了承)
- AIが spec の要否を判断する基準は、変更の種類と不確かさにする(新しい機能か、設計上の選択があるか、依頼に抜けがあるか、取り消しにくい変更か)。行数は着手時の基準にしない。200行の検査は、すり抜けを止める最後の網として今のまま残す(AIの提案を了承)
- すでに spec がある機能を直す・広げるIssueでは、「その spec を更新する」「新しい spec を作る」「spec 無しで直す」のどれにするかも、着手時にAIが合わせて決める(AIの提案を了承)
- 着手するIssueが1つの spec に収まらないとAIが判断したら、分け方を理由付きで所有者に示す(AIの提案を了承)

### どうなれば解決か

- AIが「spec 不要」と判断したときは、判断と理由を伝えたら、所有者の返事を待たずに実装を始める。所有者は、判断がおかしいと思ったときだけ止める(AIの提案を了承)
- spec 無しで実装している途中で spec が要ると気づいたら、AIはその時点で実装を止める。「spec に切り替える」か「変更を小さく分けて spec 無しのまま進める」かをAIが決め、理由を添えて所有者に示す。spec に切り替えるときは、所有者にコマンドを依頼する(AIの提案を了承)
- spec で進めている途中でごく小さい変更だと気づいても、そのまま spec で最後まで進める(AIの提案を了承)
- AIが「1つの spec に収まらない」と判断して分け方を示したときは、所有者の了承を待ってから進む(AIの提案を了承)

### やらないこと

- 3段階の承認は変えない。段階を省く軽い spec も作らない(AIの提案を了承)
- spec を始めるコマンドは所有者が打つままにする。AIが代わりに打たない(AIの提案を了承)

## Introduction

Issueに着手するとき、spec を作るかどうかを決める役が今は誰にも割り当てられていない。spec を始めるコマンドを打つのは所有者なので、判断も所有者に委ねられているが、所有者にはその判断ができない。起票の直後であればAIが次の手順を案内するが、その案内は残らず、起票から着手までに時間が空くと使えない。spec 無しで着手したときに所有者が何をすればよいかの決まりも無い。

本specは、所有者が着手時にする操作を spec の要否に依らず1つにし、AIがその時点のコードを調べてから進め方(spec 不要・新しい spec・既存の spec の更新・分割)を決めて理由とともに示すようにする。あわせて、spec 無しで進めている途中で spec が要ると分かったとき、spec で進めている途中で小さい変更だと分かったときの扱いを決める。

## Boundary Context

- **In scope**:
  - 所有者がIssueに着手させるときにすることを、spec が要るかどうかに関係なく1つにする
  - 所有者が着手させたら、AIが進め方を決めて、その判断と理由を所有者に示す。進め方は「spec を作らずに実装する」「新しい spec を作る」「すでにある spec を直す」「Issueを分ける」のどれかである
  - AIが決めた進め方ごとに、AIが所有者の返事を待つかどうかを決める
  - AIの見立てが途中で外れたときに、AIがどうするかを決める。外れ方は2つある。spec を作らずに実装している途中で spec が要ると分かったときと、spec で進めている途中で小さい変更だと分かったときである
  - AIが1つのIssueを分けて進めるときのIssueの扱いを決める。AIは分けた部分ごとに新しいIssueを作り、元のIssueは分けた部分がすべて終わるまで閉じないようにする
  - AIが、別のIssueのためにすでにある spec を直すときの扱いを決める。AIは、spec のどの部分がどのIssueのためのものかを見分けられるようにし、直す前に所有者がした承認の記録を残す
  - CLAUDE.md、README、Issueを起票した直後にAIが出す案内を、この進め方に合わせて書き直す
- **Out of scope**:
  - 200行の検査(size-check)の変更。上限・数え方・止まったときの判定は今のまま残す
  - 3段階の承認の変更、段階を省く軽い spec
  - spec を始めるコマンドをAIが所有者に代わって打つこと
  - spec 無しのPRがIssue本文の「決めた方式」から外れたときに止める仕組み(#473 で扱う)
  - 要望の聞き取りと起票の中身(`/request` と起票の決まり。起票を終えたときの案内だけを本specで変える)
- **Adjacent expectations**:
  - spec の各段階の生成・審査(`/spec-review`)・承認・承認の取り消しは、既存の決まりのとおりに行われる。ただし、すでにある spec を更新するときの審査の基準と、取り消す前の承認の記録の残し方は本specで定める(要件5)
  - spec 無しで進めた変更の出荷は、既存の出荷手順(`/ship`)で行われる
  - マージ後のIssueのクローズは既存の仕組み(issue-close-and-auto-merge-guarantee spec)が行う。PR本文の `Closes` に書かれたIssueはマージで閉じる
  - 自動レビュー(codex-review)は、PR本文の `Spec:` が指す spec、それが無ければ `Refs:` のIssue本文を判定の基準にする。この判定のしかたは変えない
  - 出荷手順の、PR本文に `Closes` と `Refs:` を書く決まりは変えない
  - `.claude/` 配下の変更は、既存の決まりにより所有者の承認を経て反映される

## Requirements

### Requirement 1: 着手の入口

**Objective:** 所有者として、Issueに着手させるときにすることを、spec が要るかどうかに依らず1つにしたい。spec の要否は私には判断できないため。

#### Acceptance Criteria

1. The 着手の手順 shall 所有者がIssueに着手させるときの操作を、spec の要否に依らず1つにする
2. When 所有者が着手の操作をしたとき, the 着手の手順 shall 対象のIssueの本文を読み、その時点のコードを調べてから進め方を決める
3. The 着手の手順 shall Issueのコメントを、進め方を決めるときの要望として扱わない
4. If 着手の対象として指定されたIssueが存在しない、または閉じている場合, then the 着手の手順 shall 着手せず、その旨を所有者に伝える
5. If 着手の対象のIssueに対応する spec がすでに作られている場合, then the 着手の手順 shall 進め方を決め直さず、その spec の進み具合と、所有者が次に打つコマンドを示す
6. If 着手の対象のIssueがすでに分けて進められている場合(要件9), then the 着手の手順 shall 分け方を決め直さず、分けた部分のIssueとそれぞれが閉じているかどうかを示す
7. When Issueの起票を終えたとき, the 起票の手順 shall spec の要否を案内せず、着手させるときの操作を案内する

### Requirement 2: spec の要否を判断する基準

**Objective:** 所有者として、AIが着手の時点で分かることを基準に spec の要否を決めてほしい。実装を終えるまで分からない基準で決めると、途中で spec が必要になるため。

#### Acceptance Criteria

1. The 着手の手順 shall spec が要るかどうかを、次の4つの観点で判断する
   - 観点1「新しい機能か」: 今は無い機能や動きを足す変更なら当たる。今ある機能を、本来の動きに直すだけの変更は当たらない
   - 観点2「作り方を選ぶ必要があるか」: 作り方が複数考えられ、どれを選ぶかで出来上がるものや後からの直しやすさが変わる変更なら当たる。作り方がほぼ1つに決まる変更は当たらない
   - 観点3「Issueの本文だけで完成の形が決まらないか」: AIが、所有者の決めていない動き(失敗したときにどうするか、誰に何が届くか など)を自分で補わないと作れない変更なら当たる。Issueの本文で完成したときの動きが決まる変更は当たらない
   - 観点4「PRを差し戻しても元に戻らないか」: 保存されているデータの形を変える・消す変更や、外部に何かを送る変更のように、マージしたあとでPRを差し戻しても元の状態に戻らない変更なら当たる。PRを差し戻せば元に戻る変更は当たらない
2. If 4つの観点のいずれか1つでも当たる場合, then the 着手の手順 shall spec が要ると判断する
3. When 4つの観点のどれにも当たらないとき, the 着手の手順 shall spec は要らないと判断する
4. The 着手の手順 shall 変更の行数の見込みを、着手時の判断の基準に使わない

### Requirement 3: 判断の示し方

**Objective:** 所有者として、AIの判断と理由を見て、おかしいときに気づけるようにしたい。判断を任せても、覆す手段は持っていたいため。

#### Acceptance Criteria

1. When 進め方を決めたとき, the 着手の手順 shall 判断と理由を所有者に示す
2. The 理由 shall 4つの観点のそれぞれについて、当たるかどうかと、そう判断した根拠(調べたコードやIssue本文の箇所)を含む
3. The 着手の手順 shall 判断を示すとき、所有者にしてほしいこと(何もしなくてよい、打つコマンド、了承)を最初に示す

### Requirement 4: spec が要らないときの進み方

**Objective:** 所有者として、spec が要らない変更は、私が返事をしなくても進んでほしい。毎回返事をする手間を無くしたいため。

#### Acceptance Criteria

1. When spec は要らないと判断したとき, the 着手の手順 shall 判断と理由を示したあと、所有者の返事を待たずに実装を始める
2. When spec 無しで実装している間に所有者が止めたとき, the 着手の手順 shall 実装を止め、所有者の指示に従って進め方を決め直す

### Requirement 5: spec が要るときの進み方

**Objective:** 所有者として、spec が要るときは、何を打てばよいかを示してほしい。spec で進めることへの同意は、私がコマンドを打つことで示したいため。

#### Acceptance Criteria

1. When 新しい spec が要ると判断したとき, the 着手の手順 shall 所有者が打つ、spec を始めるコマンドを示す
2. While spec が要ると判断し、所有者がまだコマンドを打っていない間, the 着手の手順 shall 実装を始めない
3. The 着手の手順 shall spec を始めるコマンドと spec の各段階のコマンドを、所有者に代わって実行しない
4. When すでに spec がある機能を直す・広げるIssueに着手するとき, the 着手の手順 shall 「その spec を更新する」「新しい spec を作る」「spec 無しで直す」のどれにするかを決め、理由とあわせて示す
5. When すでにある spec を更新すると決めたとき, the 着手の手順 shall 所有者が打つコマンドと、取り消される承認の段階を示す
6. When すでに spec がある機能を spec 無しで直すと決めたとき, the 着手の手順 shall 要件4に従って進める
7. When すでにある spec を更新するとき, the spec の審査 shall 元のIssueと新しいIssueの両方の本文を基準にし、新しいIssueの要望の取りこぼしと、どちらのIssueにも無い追加を判定する
8. The 更新した spec shall 要件・設計・タスクのそれぞれが、元のIssueと新しいIssueのどちらに対するものかを、本文の中で見分けられる形にする
9. When すでにある spec を更新するために承認を取り消すとき, the 着手の手順 shall 取り消す段階の承認者・日時・対象のIssueを、取り消しのあとも読める形で残す

### Requirement 6: 1つの spec に収まらないとき

**Objective:** 所有者として、Issueを分けて進めるときは、分け方を見てから決めたい。分けると何を作るかの単位が変わり、それを決めるのは私であるため。

#### Acceptance Criteria

1. When 着手の対象のIssueが1つの spec に収まらないと判断したとき, the 着手の手順 shall 分け方と、分けたそれぞれの進め方(spec の要否を含む)と、その理由を所有者に示す
2. While 所有者が分け方を了承していない間, the 着手の手順 shall 分けたどの部分にも着手しない
3. When 所有者が分け方の修正を求めたとき, the 着手の手順 shall 修正した分け方を示し、改めて了承を待つ
4. When 所有者が分け方を了承したとき, the 着手の手順 shall 要件9に従って分けた部分ごとのIssueを起票し、部分ごとに、示した進め方(要件4または要件5)で進める

### Requirement 7: spec 無しの実装の途中で spec が要ると分かったとき

**Objective:** 所有者として、spec 無しで進めている途中で spec が要ると分かったら、その時点で止まってほしい。実装を終えてから差し戻されるより、やり直しが小さく済むため。

#### Acceptance Criteria

1. When spec 無しで実装している途中で、4つの観点のいずれかに当たると分かったとき, the 着手の手順 shall その時点で実装を止める
2. When 実装を止めたとき, the 着手の手順 shall 「spec に切り替える」か「変更を小さく分けて spec 無しのまま進める」かを決め、理由を添えて所有者に示す
3. When spec に切り替えると決めたとき, the 着手の手順 shall 所有者に spec を始めるコマンドを依頼し、spec の実装の段階に入るまで実装を再開しない
4. When 変更を小さく分けて spec 無しのまま進めると決めたとき, the 着手の手順 shall 分け方と理由を示したあと、所有者の返事を待たずに、要件9に従って分けた部分ごとのIssueを起票して進める(要件6の分割と異なり、所有者の了承を待たない)
5. The 着手の手順 shall 受入基準4で起票する部分のIssueの本文を、元のIssueの本文からの抜き出しだけで構成し、元のIssueに無い要望を加えない
6. The 着手の手順 shall 変更を小さく分けて spec 無しのまま進める道を、分けたどの部分も4つの観点のどれにも当たらないときに限って選ぶ
7. If spec 無しで出したPRが200行の検査で止まった場合, then the 着手の手順 shall 受入基準2から6と同じく、spec に切り替えるか小さく分けるかを決めて理由を示す

### Requirement 8: spec で進めている途中で小さい変更だと分かったとき

**Objective:** 所有者として、spec で始めた変更は、小さいと分かっても spec で最後まで進めてほしい。途中で進め方を切り替える判断を求められたくないため。

#### Acceptance Criteria

1. While spec で進めている間, when ごく小さい変更だと分かったとき, the 着手の手順 shall spec の段階を省かず、spec で最後まで進める
2. The 着手の手順 shall spec で進めている変更を spec 無しに切り替えることを、所有者に提案しない

### Requirement 9: 分けて進めるIssueの扱い

**Objective:** 所有者として、1つのIssueを分けて進めたときに、どの部分が残っているかが分かり、全部が終わる前に元のIssueが閉じないようにしたい。閉じたIssueは終わった作業に見え、残りの作業を見落とすため。

#### Acceptance Criteria

1. When 1つのIssueを分けて進めると決まったとき(要件6の了承、または要件7の受入基準4), the 着手の手順 shall 分けた部分ごとにIssueを起票する
2. The 分けた部分のIssue shall 本文に、元のIssueの本文と分け方のうち、その部分に当たることだけを含む
3. The 分けた部分のIssueと元のIssue shall 互いの関係(どのIssueから分けたか、どの部分に分けたか)を、どちらからも辿れる形で示す
4. The 着手の手順 shall 分けた部分の進め方の判断と出荷を、その部分のIssueを対象にして行う
5. While 分けた部分のIssueのうち、まだ閉じていないものがある間, the 元のIssue shall 開いたままである
6. When 分けた部分のIssueがすべて閉じたとき, the 元のIssue shall 閉じる

### Requirement 10: 文書の整合

**Objective:** 所有者として、文書に書かれた進め方が実際の進め方と一致していてほしい。文書が古いままだと、AIも私も古い進め方に従ってしまうため。

#### Acceptance Criteria

1. The CLAUDE.md と README shall 着手の入口が1つであること、AIが着手時に進め方を決めること、判断の基準が要件2の4つの観点であることを記載する
2. The CLAUDE.md と README shall 行数を着手時の判断の基準として記載せず、200行の検査がすり抜けを止める最後の網であることを記載する
3. The README の、人間が打つコマンドの表 shall 着手させるときの操作を含む
4. The 起票の決まり shall 起票を終えたときの案内を、要件1の受入基準7に合わせる
5. The 起票の決まり shall 分けた部分のIssueの起票(要件9)を、起票の対象として含み、要件7の受入基準4による起票を、所有者の了承を得ずに起票する例外として記載する
6. The spec の審査の手順 shall すでにある spec を更新したときの判定の基準(要件5の受入基準7)を記載する
7. The CLAUDE.md と spec の審査の手順の、承認の取り消しの決まり shall 要件5の受入基準9と食い違わない
