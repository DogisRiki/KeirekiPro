# 要件

## 元の要望
Issue #472: 着手の入口を1つにし、specの要否をAIが着手時に判断する

### きっかけ

`/kiro-spec-init` を打つのは所有者なので、spec が要るかどうかを所有者が決めなければならないが、所有者にはその判断ができない。起票の直後ならAIが案内できるが、Issueだけ先に切っておき、着手は後になることもある。

### 困っていること

- `/kiro-spec-init` を打つのは所有者なので、spec が要るかどうかを所有者が判断する必要があるが、できない
- `/request` でIssueを作った直後ならAIが判断して `/kiro-spec-init` を依頼できるが、起票してすぐ作業に取り掛かるとは限らない。とりあえずIssueだけ切ることもある
- spec 無しで動き始めて、あとで spec が必要になることがある。そのときどうするかが決まっていない。そもそもそうならないようにしたい
- 逆に、spec が必要と想定して spec 駆動で始めたが、実際はごく小規模で終わることがある

### やりたいこと

- 所有者が着手時にすることは、spec の要否にかかわらず1つだけにする。AIがその時点のコードを調べてから進め方を決め、理由を添えて示す(AIの提案を了承)
- AIが spec の要否を判断する基準は、変更の種類と不確かさにする(新しい機能か、設計上の選択があるか、依頼に抜けがあるか、取り消しにくい変更か)。行数は着手時の基準にしない。200行の検査は、すり抜けを止める最後の網として今のまま残す(AIの提案を了承)
- すでに spec がある機能を直す・広げるIssueでは、「その spec を更新する」「新しい spec を作る」「spec 無しで直す」のどれにするかも、着手時にAIが合わせて決める(AIの提案を了承)
- 着手するIssueが1つの spec に収まらないとAIが判断したら、分け方を理由付きで所有者に示す(AIの提案を了承)

### どうなれば解決か

- AIが「spec 不要」と判断したときは、判断と理由を伝えたら、所有者の返事を待たずに実装を始める。所有者は、判断がおかしいと思ったときだけ止める(AIの提案を了承)
- spec 無しで実装している途中で spec が要ると気づいたら、AIはその時点で実装を止める。「spec に切り替える」か「変更を小さく分けて spec 無しのまま進める」かをAIが決め、理由を添えて所有者に示す。spec に切り替えるときは、所有者にコマンドを依頼する(AIの提案を了承)
- spec で進めている途中でごく小さい変更だと気づいても、そのまま spec で最後まで進める(AIの提案を了承)
- AIが「1つの spec に収まらない」と判断して分け方を示したときは、所有者の了承を待ってから進む(AIの提案を了承)

### やらないこと

- 3段階の承認は変えない。段階を省く軽い spec も作らない(AIの提案を了承)
- spec を始めるコマンドは所有者が打つままにする。AIが代わりに打たない(AIの提案を了承)

### 追加の要望(Issue #524)
/start が今ある動きを直す変更まで spec が要ると判断し、時間と費用がかかりすぎる

#### きっかけ

開いているセッションがすべて spec が要ると判断されていることに所有者が気づき、判断が過剰だと指摘して、直すと決めた。

#### 困っていること

- 開いている5つのセッション(#522、#507、#479、#520、#511)は、どれも今ある動きの不具合直しなのに、`/start` がすべて spec が要ると判断した。
- spec で進めると、費用と時間がかかり、開発が遅くなる。

#### どうなれば解決か

- 今ある動きを直す変更で、`/start` が spec が要ると判断しすぎない。直す変更にも大小があり、小さいものは spec を作らずに進む。

## はじめに

今は、Issueに着手するときに spec を作るかどうかを決める役を、誰も受け持っていない。spec を始めるコマンドを打つのは所有者なので、spec を作るかどうかの判断も所有者に委ねられている。しかし、所有者にはその判断ができない。起票の直後であれば、Claude が次の手順を所有者に案内する。ただし、その案内はどこにも残らないので、起票から着手までに時間が空くと、所有者はその案内を使えない。spec 無しで着手したときに所有者が何をすればよいかも、今は決まっていない。

この spec は、所有者が着手のときにする操作を、spec が要るかどうかに依らず1つにする。所有者がその操作をしたら、Claude はその時点のコードを調べてから進め方を決め、決めた進め方を理由とともに所有者に示す。進め方は、spec を作らずに実装する、新しい spec を作る、すでにある spec を更新する、Issueを分ける、のどれかである。あわせて、この spec は、spec 無しで進めている途中で spec が要ると分かったときと、spec で進めている途中で小さい変更だと分かったときに、Claude がどうするかを決める。

この spec で着手の判断を始めたあと、Claude は、今ある動きを直すIssueのほとんどを、spec が要ると判断した。直すIssueは観点1(新しい機能か)には当たらないが、観点2(作り方を選ぶ必要があるか)と観点3(Issueの本文だけで完成の形が決まらないか)のどちらにも当たったからである。Claude が作り方を2つ思い浮かべれば観点2に当たり、Issueの本文に無い細かい場合分けが1つでもあれば観点3に当たる定義だったため、Claude は、安全側に寄るだけで、直すIssueを spec が要ると判断した。そこで、この spec は、観点1から観点3の定義を、所有者や利用者から見える結果を基準にした定義に直す。あわせて、Claude が所有者に1回だけ尋ねてから spec 無しで進む道と、spec 無しで進めたときに Claude が決めたことをPR本文に残す形を決める。(#524)

## 範囲

- この spec で決めること:
  - 所有者がIssueに着手させるときにすることを、spec が要るかどうかに関係なく1つにする
  - 所有者が着手させたら、AIが進め方を決めて、その判断と理由を所有者に示す。進め方は「spec を作らずに実装する」「新しい spec を作る」「すでにある spec を直す」「Issueを分ける」のどれかである
  - AIが決めた進め方ごとに、AIが所有者の返事を待つかどうかを決める
  - AIの見立てが途中で外れたときに、AIがどうするかを決める。外れ方は2つある。spec を作らずに実装している途中で spec が要ると分かったときと、spec で進めている途中で小さい変更だと分かったときである
  - AIが1つのIssueを分けて進めるときのIssueの扱いを決める。AIは分けた部分ごとに新しいIssueを作り、元のIssueは分けた部分がすべて終わるまで閉じないようにする
  - AIが、別のIssueのためにすでにある spec を直すときの扱いを決める。AIは、spec のどの部分がどのIssueのためのものかを見分けられるようにし、直す前に所有者がした承認の記録を残す
  - CLAUDE.md、README、Issueを起票した直後にAIが出す案内を、この進め方に合わせて書き直す
  - 今ある動きを直す変更を spec が要ると判断しすぎないように、AIが spec の要否を判断する4つの観点のうち、観点1から観点3の定義を直す(#524)
  - spec を作らずに進めるときに、AIが所有者に1回だけ尋ね、答えをIssueの本文に書き足してから進む道を決める(#524)
  - spec を作らずに進めたときに、AIが決めたことを所有者が後から確かめられるように、PR本文に残す形を決める(#524)
- この spec で決めないこと:
  - 200行の検査(size-check)の変更。上限・数え方・止まったときの判定は今のまま残す
  - 3段階の承認の変更、段階を省く軽い spec
  - spec を始めるコマンドをAIが所有者に代わって打つこと
  - spec 無しのPRがIssue本文の「決めた方式」から外れたときに止める仕組み(#473 で扱う)
  - 要望の聞き取りと起票の中身(`/request` と起票の決まり)。この spec は、起票を終えたときの案内だけを変える
  - 観点の数と、観点4(PRを差し戻しても元に戻らないか)の定義の変更(#524)
  - 直す変更のPRに、不具合を再現するテストを必ず入れる決まり(#524)
- この spec が前提にしていること:
  - Claude と所有者は、spec の各段階の生成・審査(`/spec-review`)・承認・承認の取り消しを、既存の決まりのとおりに行う。ただし、この spec は、すでにある spec を更新するときの審査の基準と、承認を取り消す前に承認の記録を残すしかたを、要件5(spec が要るときの進み方)で定める
  - Claude は、spec 無しで進めた変更を、既存の出荷手順(`/ship`)で出荷する
  - マージ後のIssueのクローズは、既存の仕組み(issue-close-and-auto-merge-guarantee spec)が行う。PR本文の `Closes` に書かれたIssueは、PRのマージで閉じる
  - 自動レビュー(codex-review)は、PR本文の `Spec:` が指す spec を判定の基準にする。`Spec:` が無ければ、自動レビューは `Refs:` のIssueの本文を判定の基準にする。この spec は、この判定のしかたを変えない
  - 承認済みの spec の要件か設計に書かれた動きを spec 無しで変えたとき、Claude はその spec の本文を直さない。その spec の本文は、次にその spec を更新するときに直す(#524)
  - 自動レビューは、Issueの本文の「決めた方式」の節の項目を、PR本文に理由が書かれていても外れを許さない基準として読む。ただし、所有者の操作のようにPRの変更から確かめられない項目は、自動レビューは判定しない。Claude が「決めた方式」の節に書き足した所有者の答えも、同じ扱いを受ける(#524)
  - この spec は、出荷手順の、PR本文に `Closes` と `Refs:` を書く決まりを変えない
  - `.claude/` 配下の変更は、既存の決まりにより、所有者の承認を経て反映される

## 要件

### 要件1 着手の入口

所有者は、Issueに着手させるときにすることを、spec が要るかどうかに依らず1つにしたい。spec が要るかどうかを、所有者は判断できないからである。

1. Claude は、所有者がIssueに着手させるときの操作を、spec が要るかどうかに依らず1つにする。
2. 所有者が着手の操作をしたら、Claude は、対象のIssueの本文を読み、その時点のコードを調べてから進め方を決める。
3. Claude は、Issueのコメントを、進め方を決めるときの要望として扱わない。
4. 着手の対象として指定されたIssueが存在しないか、閉じていれば、Claude は着手せず、着手しないことを所有者に伝える。
5. 着手の対象のIssueに対応する spec がすでに作られていれば、Claude は進め方を決め直さず、その spec の進み具合と、所有者が次に打つコマンドを示す。
6. 着手の対象のIssueがすでに分けて進められていれば(要件9の分けて進めるIssueの扱いで分けたIssue)、Claude は分け方を決め直さず、分けた部分のIssueと、それぞれが閉じているかどうかを示す。
7. Issueの起票を終えたら、Claude は spec が要るかどうかを案内せず、着手させるときの操作を案内する。

### 要件2 spec の要否を判断する基準

所有者は、Claude が着手の時点で分かることを基準に、spec が要るかどうかを決めてほしい。実装を終えるまで分からない基準で決めると、途中で spec が必要になるからである。

所有者は、今ある動きを直す変更を、Claude が安全側に寄っただけの判断で spec にしてほしくない。spec で進めると時間と費用がかかり、開発が遅くなるからである。所有者はコードを読まないので、所有者が決めるべきことは、所有者や利用者から見える結果に限られる。(#524)

1. Claude は、spec が要るかどうかを、次の4つの観点で判断する。(#524 で変更)
   - 観点1「新しい機能か」: 今は無い機能を足し、所有者や利用者が新しく使えるもの(画面・API・コマンド・手順・通知)ができる変更なら当たる。今ある機能を本来の動きに直す変更は当たらない。直すために中の仕組みを足しても、所有者や利用者が新しく使うものが増えなければ当たらない。今ある動きを意図して変えるだけの変更は、この観点では当たらないとし、観点2と観点3で判断する
   - 観点2「作り方を選ぶ必要があるか」: 次のどちらかの変更なら当たる。1つは、作り方によって、マージしたあとに所有者や利用者が見るもの・すること・受け取るものが変わり、どの結果にするかを、Issueの本文からも、受入基準7に書く3つの材料(今の動き、Issueの目的、既存の文書)からも決められず、所有者に1回尋ねても決まらない変更である。もう1つは、Issueの本文の「決めた方式」に沿ったまま作れる作り方が1つも無い変更と、承認済みの spec が作ると決めた範囲の中で作れる作り方が1つも無い変更である。承認済みの spec が作ると決めた範囲とは、その spec の設計の「作るもの」の節に書かれた範囲を指す。承認済みの spec が作ると決めた範囲を変える変更では、Claude は、要件5のすでに spec がある機能を直すときの決め方(その spec を更新するか、新しい spec を作るか)で進め方を決める。「決めた方式」から外れる作り方は、Claude は候補から外し、候補に外れる作り方があることだけでは当たると判断しない。どの作り方でも所有者や利用者から見える結果が同じで、違うのが中の作りと後からの直しやすさだけの変更は当たらない。見える結果には、かかる時間の違いを含めない。ただし、Issueの本文が時間について要望しているときは、かかる時間の違いも見える結果に含める
   - 観点3「Issueの本文だけで完成の形が決まらないか」: Issueの本文で決まっていない、所有者や利用者から見える動きがあり、その動きを受入基準7に書く3つの材料(今の動き、Issueの目的、既存の文書)のどれからも決められず、所有者に1回尋ねても決まらない変更なら当たる。決まっていない動きをすべて3つの材料から決められる変更と、所有者に1回尋ねれば決まる変更は当たらない
   - 観点4「PRを差し戻しても元に戻らないか」: 保存されているデータの形を変える・消す変更や、外部に何かを送る変更のように、マージしたあとでPRを差し戻しても元の状態に戻らない変更なら当たる。PRを差し戻せば元に戻る変更は当たらない
2. 4つの観点のうち1つでも当たれば、Claude は spec が要ると判断する。
3. 4つの観点のどれにも当たらなければ、Claude は spec は要らないと判断する。
4. Claude は、変更の行数の見込みを、着手時の判断の基準に使わない。
5. 観点2の1つ目の条件(作り方によって見える結果が変わる)に当たると判断するときは、Claude は、作り方ごとに異なる、所有者や利用者から見える結果を、根拠に書く。観点2の2つ目の条件(「決めた方式」か承認済みの spec の範囲の中で作れる作り方が無い)に当たると判断するときは、Claude は、沿えない「決めた方式」の項目か、外れる承認済みの spec の範囲の箇所と、それに沿ったまま作れる作り方が無い理由を、根拠に書く。観点3に当たると判断するときは、Claude は、決まっていない見える動きと、その動きを3つの材料のどれからも決められない理由を、根拠に書く。Claude がこれらを書けなければ、Claude はその観点に当たらないと判断する。(#524)
6. Claude は、所有者に尋ねる問いが次の4つの条件をすべて満たすときに限り、「所有者に1回尋ねれば決まる」とする。1つ目は、Claude が問いをすべて1回にまとめて出せることである。2つ目は、どの問いの答えも、ほかの問いの答えによって変わらないことである。3つ目は、Claude が問いごとに推奨する答えを付けられることである。4つ目は、所有者がコードを読まずに答えられることである。(#524)
7. Claude は、Issueの本文で決まっていない見える動きを決める材料を、次の3つとする。1つ目は、今の動きのまま変えないことである。2つ目は、Issueの本文の「どうなれば解決か」に書かれた目的である。3つ目は、既存の文書(承認済みの spec、README、CLAUDE.md、スキルの手順)に書かれた本来の動きである。(#524)

### 要件3 判断の示し方

所有者は、Claude の判断と理由を見て、判断がおかしいときに気づけるようにしたい。判断を Claude に任せても、所有者はその判断を覆す手段を持っていたいからである。

1. 進め方を決めたら、Claude は、判断と理由を所有者に示す。
2. Claude は、理由に、4つの観点のそれぞれについて、当たるかどうかと、そう判断した根拠(調べたコードやIssue本文の箇所)を書く。
3. Claude は、判断を示すとき、所有者にしてほしいこと(何もしなくてよい、打つコマンド、了承、問いへの答え)を最初に示す。(#524 で変更)
4. spec は要らないと判断し、所有者に尋ねる問いがあるときは、Claude は、判断と理由を示すときに、問いとそれぞれの推奨する答えをあわせて示す。Claude は、問いごとに、その問いで決まる、所有者や利用者から見える動きを書く。(#524)

### 要件4 spec が要らないときの進み方

所有者は、spec が要らない変更は、所有者が返事をしなくても進んでほしい。所有者は、毎回返事をする手間を無くしたいからである。

ただし、所有者や利用者から見える動きのうち、所有者が決めるべきものが残るときは、所有者は1回だけ答えて決めたい。spec の3つの段階を読んで承認するより、推奨の付いた問いに答えるほうが、所有者の手間が少ないからである。所有者は、spec を作らずに進めた変更でも、Claude が何を決めたかを後から確かめたい。(#524)

1. spec は要らないと判断し、所有者に尋ねる問いが無ければ、Claude は、判断と理由を示したあと、所有者の返事を待たずに実装を始める。(#524 で変更)
2. spec 無しで実装している間に所有者が止めたら、Claude は実装を止め、所有者の指示に従って進め方を決め直す。
3. spec は要らないと判断し、所有者に尋ねる問いがあれば、Claude は、所有者が答えるまで実装を始めない。所有者が答えたら、Claude は、答えをIssueの本文の「決めた方式」の節に書き足してから、所有者の返事をそれ以上待たずに実装を始める。所有者が推奨のとおりに答えた項目には、Claude は末尾に「(AIの提案を了承)」の印を付ける。「決めた方式」の節が無ければ、Claude は節を作って書き足す。(#524)
4. 所有者の答えを受けても、所有者や利用者から見える動きのうち、3つの材料(今の動き、Issueの目的、既存の文書)からも答えからも決められないものが残ったら、Claude は判断を「spec が要る」に改め、改めた判断と理由を示す。そのあと、Claude は要件5の spec が要るときの進み方(所有者が打つコマンドを示し、所有者が打つまで実装を始めない)に従う。(#524)
5. spec 無しで出すPRの本文に、Claude は「AIが決めたこと」の節を必ず置く。Claude はこの節に、選んだ作り方と選ばなかった作り方とその理由、Issueの本文に無かった見える動きをどう決めたかと、その動きを決めた材料(今の動きのまま、Issueの目的、既存の文書の箇所、所有者の答え)を書く。Claude が決めたことが無ければ、Claude はこの節に「無し」と書く。(#524)
6. Claude は、Issueの本文で決まっておらず、3つの材料(今の動き、Issueの目的、既存の文書)のどれからも決められない見える動きに限って、所有者に問う。3つの材料のどれかで決められる動きは、Claude は所有者に問わずに決める。(#524)
7. spec 無しで、承認済みの spec の要件か設計に書かれた、所有者や利用者から見える動きを変えるときは、Claude は、PR本文の「AIが決めたこと」の節に、食い違うことになる spec と、その本文の箇所を書く。(#524)

### 要件5 spec が要るときの進み方

所有者は、spec が要るときは、何を打てばよいかを示してほしい。spec で進めることへの同意は、所有者がコマンドを打つことで示したいからである。

1. 新しい spec が要ると判断したら、Claude は、所有者が打つ、spec を始めるコマンドを示す。
2. spec が要ると判断し、所有者がまだコマンドを打っていない間は、Claude は実装を始めない。
3. Claude は、spec を始めるコマンドと spec の各段階のコマンドを、所有者に代わって実行しない。
4. すでに spec がある機能を直す、または広げるIssueに着手するときは、Claude は「その spec を更新する」「新しい spec を作る」「spec 無しで直す」のどれにするかを決め、理由とあわせて示す。
5. すでにある spec を更新すると決めたら、Claude は、所有者が打つコマンドと、取り消される承認の段階を示す。
6. すでに spec がある機能を spec 無しで直すと決めたら、Claude は、要件4の spec が要らないときの進み方(判断と理由を示したあと、所有者の返事を待たずに実装を始める)に従って進める。
7. すでにある spec を更新するときは、Claude は、spec の審査で、元のIssueと新しいIssueの両方の本文を基準にし、新しいIssueの要望の取りこぼしと、どちらのIssueにも無い追加を判定する。
8. Claude は、更新した spec の要件・設計・タスクのそれぞれが、元のIssueと新しいIssueのどちらに対するものかを、本文の中で見分けられる形で書く。
9. すでにある spec を更新するために承認を取り消すときは、Claude は、取り消す段階の承認者・日時・対象のIssueを、取り消しのあとも読める形で残す。

### 要件6 1つの spec に収まらないとき

所有者は、Issueを分けて進めるときは、分け方を見てから決めたい。Issueを分けると何を作るかの単位が変わり、その単位を決めるのは所有者だからである。

1. 着手の対象のIssueが1つの spec に収まらないと判断したら、Claude は、分け方と、分けたそれぞれの進め方(spec が要るかどうかを含む)と、その理由を所有者に示す。
2. 所有者が分け方を了承していない間は、Claude は、分けたどの部分にも着手しない。
3. 所有者が分け方の修正を求めたら、Claude は、修正した分け方を示し、改めて所有者の了承を待つ。
4. 所有者が分け方を了承したら、Claude は、要件9の分けて進めるIssueの扱いに従って、分けた部分ごとのIssueを起票する。そのあと、Claude は部分ごとに、示した進め方(要件4の spec が要らないときの進み方、または要件5の spec が要るときの進み方)で進める。

### 要件7 spec 無しの実装の途中で spec が要ると分かったとき

所有者は、spec 無しで進めている途中で spec が要ると分かったら、Claude にその時点で止まってほしい。実装を終えてから差し戻されるより、やり直しが小さく済むからである。

1. spec 無しで実装している途中で、4つの観点のいずれかに当たると分かったら、Claude はその時点で実装を止める。
2. 実装を止めたら、Claude は「spec に切り替える」か「変更を小さく分けて spec 無しのまま進める」かを決め、理由を添えて所有者に示す。
3. spec に切り替えると決めたら、Claude は、所有者に spec を始めるコマンドを依頼し、spec の実装の段階に入るまで実装を再開しない。
4. 変更を小さく分けて spec 無しのまま進めると決めたら、Claude は、分け方と理由を示したあと、所有者の返事を待たずに、要件9の分けて進めるIssueの扱いに従って、分けた部分ごとのIssueを起票して進める。要件6の1つの spec に収まらないときの分け方と異なり、Claude はこの分け方では所有者の了承を待たない。
5. Claude は、この要件の受入基準4(変更を小さく分けて spec 無しのまま進めるとき)で起票する部分のIssueの本文を、元のIssueの本文からの抜き出しだけで作り、元のIssueに無い要望を加えない。
6. Claude は、変更を小さく分けて spec 無しのまま進める道を、分けたどの部分も4つの観点のどれにも当たらないときに限って選ぶ。
7. spec 無しで出したPRが200行の検査で止まったら、Claude は、この要件の受入基準2から6(実装を止めたあとに、spec に切り替えるか小さく分けるかを決めて進めること)と同じく、spec に切り替えるか小さく分けるかを決めて理由を示す。
8. spec 無しで実装している途中で、Issueの本文で決まっておらず3つの材料(今の動き、Issueの目的、既存の文書)のどれからも決められない、所有者や利用者から見える動きが見つかり、所有者に1回尋ねれば決まるときは、Claude は実装を止め、問いとそれぞれの推奨する答えを所有者に示す。所有者が答えたら、Claude は、要件4の spec が要らないときの進み方と同じく答えをIssueの本文に書き足してから、実装を再開する。(#524)

### 要件8 spec で進めている途中で小さい変更だと分かったとき

所有者は、spec で始めた変更は、小さいと分かっても spec で最後まで進めてほしい。所有者は、途中で進め方を切り替えるかどうかの判断を求められたくないからである。

1. spec で進めている間に、ごく小さい変更だと分かっても、Claude は spec の段階を省かず、spec で最後まで進める。
2. Claude は、spec で進めている変更を spec 無しに切り替えることを、所有者に提案しない。

### 要件9 分けて進めるIssueの扱い

所有者は、1つのIssueを分けて進めたときに、どの部分が残っているかが分かり、全部が終わる前に元のIssueが閉じないようにしたい。閉じたIssueは終わった作業に見えるので、所有者は残りの作業を見落とすからである。

1. 1つのIssueを分けて進めると決まったら(要件6で所有者が分け方を了承したとき、または要件7の受入基準4で変更を小さく分けて spec 無しのまま進めると決めたとき)、Claude は、分けた部分ごとにIssueを起票する。
2. Claude は、分けた部分のIssueの本文に、元のIssueの本文と分け方のうち、その部分に当たることだけを書く。
3. Claude は、分けた部分のIssueと元のIssueの互いの関係(どのIssueから分けたか、どの部分に分けたか)を、どちらのIssueからも辿れる形で示す。
4. Claude は、分けた部分の進め方の判断と出荷を、その部分のIssueを対象にして行う。
5. 分けた部分のIssueのうち、まだ閉じていないものがある間は、元のIssueは開いたままである。
6. 分けた部分のIssueがすべて閉じたら、元のIssueは閉じる。

### 要件10 文書の整合

所有者は、文書に書かれた進め方が実際の進め方と一致していてほしい。文書が古いままだと、Claude も所有者も古い進め方に従ってしまうからである。

1. Claude は、CLAUDE.md と README に、着手の入口が1つであること、Claude が着手時に進め方を決めること、判断の基準が要件2の4つの観点であることと、観点ごとの定義が要件2の受入基準1のとおりであることを書く。(#524 で変更)
2. Claude は、CLAUDE.md と README に、行数を着手時の判断の基準として書かず、200行の検査がすり抜けを止める最後の網であることを書く。
3. Claude は、README の、人間が打つコマンドの表に、着手させるときの操作を載せる。
4. Claude は、起票の決まりの、起票を終えたときの案内を、要件1の受入基準7(起票を終えたら spec が要るかどうかを案内せず、着手させるときの操作を案内する)に合わせる。
5. Claude は、起票の決まりに、分けた部分のIssueの起票(要件9の分けて進めるIssueの扱い)を起票の対象として含める。Claude は、要件7の受入基準4(変更を小さく分けて spec 無しのまま進めるとき)による起票を、所有者の了承を得ずに起票する例外として起票の決まりに書く。
6. Claude は、spec の審査の手順に、すでにある spec を更新したときの判定の基準(要件5の受入基準7。元のIssueと新しいIssueの両方の本文を基準にし、取りこぼしと、どちらのIssueにも無い追加を判定する)を書く。
7. Claude は、CLAUDE.md と spec の審査の手順の、承認の取り消しの決まりを、要件5の受入基準9(取り消す段階の承認者・日時・対象のIssueを、取り消しのあとも読める形で残す)と食い違わないように書く。
8. Claude は、起票の決まりに、着手のときと spec 無しの実装の途中で所有者が問いに答えたことを、Claude がIssueの本文の「決めた方式」の節に書き足すことを書く。Claude は、この書き足しを、起票したIssueの本文を所有者に断らずに書き換えない決まりと、所有者が「AIの提案を了承」しただけの方式を本文に載せない決まりの例外として書く。(#524)
9. Claude は、出荷の手順に、spec 無しで出すPRの本文に「AIが決めたこと」の節を置くことを書く。(#524)
10. Claude は、CLAUDE.md と README に、spec が要らないと判断しても所有者に尋ねる問いがあるときは、Claude が答えを待つことと、答えをIssueの本文の「決めた方式」の節に書き足すことを書く。(#524)
