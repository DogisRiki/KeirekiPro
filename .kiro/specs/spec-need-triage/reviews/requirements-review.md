### 申告

**1. 1つのIssueを分けたあとも、同じIssueのまま複数のPRで進める** — 要件6.4、要件9

- Issue の記載: あり(「分け方を理由付きで所有者に示す」「了承を待ってから進む」。いずれも「AIの提案を了承」の印)。分けた部分と元のIssueの関係(同じIssueで進めるのか、Issueも分けるのか)は書かれていない
- 決めたこと: 元のIssueを1つのまま残し、分けた部分ごとにPRを出す。最後の部分がマージされるまでIssueを閉じない(要件9)
- 他にありえた選択肢: 部分ごとに新しいIssueを起票し、元のIssueは分け方を示す親として残す(GitHub のサブIssueを使う形も含む)。または、元のIssueは最初の部分で閉じ、残りを新しいIssueにする
- 外れていた場合: 出荷手順の `Closes` 必須(`ship/SKILL.md` L41「例外なく必須」、`CLAUDE.md` L78)、マージ後にIssueを閉じる仕組みの「`Refs:` だけのIssueには所有者宛ての知らせを付ける」動作(`close-linked-issues.sh` L24・L417〜432)、codex-review の判定基準(`Refs:` のIssue本文)の3つが「1PR = 1Issue」を前提に動いているため、同じIssueで複数PRを出すと、部分がマージされるたびに手当てが要る(指摘 R1-1-1、R1-1-2)

**2. 既存の spec の更新を「承認を取り消して、その段階から作り直す」形にした** — 要件5.5

- Issue の記載: あり(「その spec を更新する」。「AIの提案を了承」の印)。更新のしかたは書かれていない
- 決めたこと: 所有者が打つコマンドと、取り消される承認の段階を示す。つまり `CLAUDE.md` の「承認済みの段階の本文を直す前に承認を取り消す」規則に乗せ、既存の spec の本文を書き換える
- 他にありえた選択肢: 既存の spec には触れず、差分だけを新しい spec として作る(「新しい spec を作る」に寄せ、「更新する」の道を無くす)。または、既存の spec に追記だけして承認の取り消しはしない
- 外れていた場合: 承認済みの spec の本文と `reviews/` の記録に、別のIssueに対する変更が混ざり、どの承認がどのIssueに対するものかを後から追えなくなる。spec-review が判定の基準にするIssue(`spec.json` の `issue`)も1つしか持てない(指摘 R1-1-4)

**3. 起票の直後にも spec の要否を案内しない** — 要件1.6

- Issue の記載: あり(きっかけに「起票の直後ならAIが案内できる」)。起票直後の案内をどうするかは書かれていない
- 決めたこと: 起票を終えたときは spec の要否を案内せず、着手させるときの操作だけを案内する(`file-issue/SKILL.md` Step 6 を置き換える)
- 他にありえた選択肢: 起票直後は要否の見込みも添えて案内し、着手時に改めて判断する
- 外れていた場合: 所有者が起票直後に見込みを知れないだけで、判断は着手時に行われる。手戻りは小さい

- 外れていた場合: 元のIssueに由来する要件が、新しいIssueを基準にすると「勝手な追加」に見える(指摘 R1-2-3)。所有者が承認する対象(新しいIssueに対する差分なのか、spec 全体なのか)が定まらないまま承認が進む

**3. 要件7で分けるときは、所有者の返事を待たずに部分のIssueを起票する** — 要件7.4
