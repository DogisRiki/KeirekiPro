# 要件

## 元の要望
Issue #815: spec の審査役が、Fable と Opus のそれぞれの最新のモデルを自動で使うようにする

### きっかけ

Fable 5.2 が出たあとも spec の審査に Fable 5.1 が使われていることに所有者が気づき、審査役を Fable 5.2 に切り替えることと、新しいモデルが出るたびに手で切り替えなくて済むようにすることを求めた。

### 困っていること

- Fable 5.2 が出ても、spec の審査役は Fable 5.1 のまま動いている。
- Fable 5.3 や Opus 5.6 のような新しいモデルが出るたびに、審査役のモデルを手で切り替えなければならない。

### やりたいこと

- spec の審査役が、Fable と Opus のそれぞれで、その系統の最新のモデルを自動で使う。
- 所有者が spec ごとに選べる審査役のモデルとして、Fable 5.1 を残さない。(AIの提案を了承)
- Fable の審査役が使用量の上限で止まったときは、その時点の最新の Opus に替えて審査を続ける。(AIの提案を了承)
- spec を進めている途中で審査役のモデルが新しいモデルに替わってよい。
- 作業の集計に、Fable 5.2 の審査役が使った料金も出す。(AIの提案を了承)
- 作業の集計を出すときに、料金表に無いモデルがあれば、AI が公式の料金ページを読んで料金表に足す PR を作る。所有者は、その PR を承認するだけでよい。(AIの提案を了承)

### どうなれば解決か

- spec の審査役が Fable 5.2 で動く。
- Claude Code の版が上がって新しい Fable や Opus を使えるようになったとき、所有者が何も操作しなくても、審査役が新しいモデルで動き、往復ごとの審査の記録に、実際に動いたモデルが残る。(AIの提案を了承)

## はじめに

spec の審査役は、spec の各段階の本文を、本文を書いた会話とは別の会話で審査する。今の審査役は、所有者が Opus を選ばない限り Fable 5.1 で動き、所有者が Opus を選んだ spec では Opus 5.5 で動く。審査役のモデルの版は、審査役の定義のファイルと、審査が済んだことを記録する仕組みのファイルに書き込まれている。そのため、新しいモデルが出ても、誰かがこれらのファイルを直すまで、審査役は古いモデルで動く。

この spec は、審査役が、Fable と Opus のそれぞれの系統の最新のモデルで動くようにする。この spec の「最新のモデル」は、そのとき使っている Claude Code で使える、その系統のモデルのうち、いちばん新しい版のモデルを指す。あわせて、この spec は、作業の集計が、新しいモデルの使用料を数えられるようにする。

## 範囲

- この spec で決めること:
  - この spec は、Claude が審査役をどの系統のどのモデルで起動するかと、Fable の審査役が使用量の上限で止まったときにどのモデルに替えるかを決める。
  - この spec は、往復ごとの審査の記録に Claude がどのモデルを書くかと、審査が済んだことを仕組みがどのモデルの審査について記録するかを決める。
  - この spec は、作業の集計の料金表に Fable 5.2 を足すことと、料金表に無いモデルが見つかったときに Claude が料金表に足す PR を作ることを決める。
  - この spec は、CLAUDE.md と `/spec-review` の手順のうち、審査役のモデルについて書いた文を、新しい動きに合わせる。
- この spec で決めないこと:
  - この spec は、次の3つを、spec `spec-review` が決めたとおりのままにする。
    - 審査役が何を審査するか
    - 往復の上限の数
    - 審査役の指摘を Claude がどう扱うか
  - この spec は、審査役でない会話のモデルを変えない。審査役でない会話とは、本文を書く会話、点検役、確認役、補助役である。
  - この spec は、作業の集計の表の形と所見の書き方を、spec `ai-work-usage-report` が決めたとおりのままにする。
  - 集計のコメントとして GitHub にすでに出した作業の集計を、料金表を直したあとに出し直すことは、この spec ではしない。
- この spec が前提にしていること:
  - Fable と Opus の新しいモデルは、Claude Code の版が上がったときに使えるようになる。
  - Claude が Agent ツールで審査役を起動するときの指定には、系統だけを書け、版を書けない。版を書けるのは、審査役の定義のファイルと、`.claude/settings.json` の `env` の欄に書く環境変数のような、仕組みのファイルだけである。仕組みのファイルに版を書いておくと、新しいモデルが出るたびに、誰かがそのファイルを直すことになる。仕組みのファイルに版を書くやり方は、要件1の3で決めた、仕組みのファイルを直さずに審査役を新しいモデルで動かすことと食い違う。
  - Claude Code は、系統だけで指定された審査役を、その系統が本体の会話のモデルと同じ系統のときは、本体の会話と同じ版で動かす。本体の会話とは、Claude が審査役を起動する会話である。
  - モデルの公表価格の出どころは、Anthropic の公式の料金ページ(https://platform.claude.com/docs/en/about-claude/pricing)である。
  - 料金表は `.claude/` の下にあるので、料金表を直す PR は、所有者が承認するまでマージされない。

## 要件

### 要件1 審査役は、所有者が選んだ系統の最新のモデルで動く

今は、新しいモデルが出るたびに、所有者か Claude が、審査役の定義のファイルと、審査が済んだことを記録する仕組みのファイルを直さなければならない。直すまでの間、審査役は古いモデルで動き続ける。Fable 5.2 が出たあとも審査役が Fable 5.1 で動いていたのは、このためである。そこで、所有者が選ぶのは系統だけにし、版は仕組みが選ぶ。

1. 所有者が審査役のモデルを選んでいない spec と、所有者が Fable を選んだ spec では、Claude は、Fable の最新のモデルで審査役を起動する。この spec を書いた時点の Fable の最新のモデルは Fable 5.2 である。本体の会話が Fable の系統で動いているときは、この要件の5のとおり、審査役は本体の会話と同じ版で動く。
2. 所有者が Opus を選んだ spec では、Claude は、Opus の最新のモデルで審査役を起動する。本体の会話が Opus の系統で動いているときは、この要件の5のとおり、審査役は本体の会話と同じ版で動く。
3. Claude Code の版が上がって Fable か Opus の新しいモデルを使えるようになったら、Claude は、次に起動する審査役から新しいモデルで動かす。そのために、所有者も Claude も、仕組みのファイルを直す必要が無い。本体の会話が審査役と同じ系統で動いているときは、この要件の5のとおり、審査役は本体の会話と同じ版で動く。
4. 所有者が spec ごとに選べるのは、Fable と Opus のどちらの系統かだけである。所有者が会話で「Fable 5.1」のように版を指定して審査役のモデルを選んだら、Claude は、指定された版の系統を、所有者が選んだ系統として記録する。Claude は、返事に次の3つを書く。1つ目は、所有者が版を選べないことである。2つ目は、その spec の審査役が、その系統の最新のモデルで動くことである。3つ目は、この要件の5のとおり、本体の会話が審査役と同じ系統で動いているときは、審査役が本体の会話と同じ版で動くことである。Claude は、所有者が指定した版で審査役を起動しない。
5. 本体の会話が審査役と同じ系統で動いているときは、審査役は、本体の会話と同じ版で動く。本体の会話がその系統の最新でない版で動いていると、審査役も最新でない版で動く。たとえば、Opus 5.6 が出たあとも本体の会話が Opus 5.5 で動いていると、Opus の審査役は Opus 5.5 で動く。Claude は、このときも往復を止めず、所有者に尋ねない。所有者は、審査役が実際に動いた版を、要件4の往復ごとの審査の記録で確かめる。

### 要件2 Fable の審査役が使用量の上限で止まったら、その時点の Opus の最新のモデルに替えて審査を続ける

今は、Fable 5.1 の審査役が使用量の上限で止まったら、Claude が Opus 5.5 に替えて審査を続ける。審査役が最新のモデルで動くようになっても、Fable の審査役が上限で止まったときに、Claude が審査を止めずに続けられるようにする必要がある。

1. Fable の審査役が使用量の上限で止まったら、Claude は、所有者に尋ねずに、その時点の Opus の最新のモデルで、同じ審査を審査役にさせ直す。本体の会話が Opus の系統で動いているときは、要件1の5のとおり、審査役は本体の会話と同じ版で動く。

### 要件3 spec の途中で審査役のモデルが替わっても、審査を続ける

1つの spec の審査は、何日にもわたって何往復も続く。その間に Claude Code の版が上がると、前の往復と次の往復で、審査役のモデルが替わる。所有者は、このときも審査を止めずに進めることを望んでいる。

1. 審査役が前の往復と違うモデルで動いても、Claude は、往復を止めず、所有者に尋ねない。
2. 審査役のモデルが替わったことだけを理由に、Claude は、審査の範囲を本文の全体に広げない。前回からの差分を審査させる往復では、Claude は、モデルが替わっても前回からの差分を審査させる。
3. 審査役のモデルが替わったことだけを理由に、Claude は、承認済みの段階を審査し直さない。

### 要件4 往復ごとの審査の記録に、実際に動いたモデルを残す

審査役のモデルを仕組みが選ぶようになると、所有者は、どの往復がどのモデルで審査されたのかを、仕組みのファイルからは読めなくなる。そこで、Claude は、往復ごとの審査の記録に、実際に動いたモデルを残す。

1. Claude は、往復ごとの審査の記録に、その往復の審査を最後まで行った審査役のモデルを、系統の名前と版の番号(例 Fable 5.2)で書く。Claude は、起動しようとしたモデルではなく、実際に動いたモデルを書く。
2. その往復の審査を Opus のモデルが行ったときは、Claude は、モデルに続けて、Opus のモデルが審査した理由を書く。理由は、所有者が Opus を選んだためか、Fable の審査役が使用量の上限で止まって Claude が Opus に替えたためかのどちらかである。
3. Fable の審査役が使用量の上限で止まった往復では、Claude は、使用量の上限で止まった Fable の審査役のモデルを、系統の名前と版の番号で書く。止まった審査役が使った量が分かるときは、Claude は、その量も書く。
4. 実際に動いたモデルを読み取れなかったときは、Claude は、モデルを推し量って書かず、読み取れなかったことを書く。
5. Claude は、審査が終わったときに所有者に出す報告にも、往復ごとに、往復ごとの審査の記録と同じ書き方でモデルを書く。往復ごとの審査の記録の書き方とは、実際に動いたモデルの書き方と、Opus のモデルが審査した理由の書き方と、使用量の上限で止まった Fable の審査役のモデルの書き方と、モデルを読み取れなかったときの書き方であり、この要件の1から4で決めたとおりである。
6. この spec より前の往復の記録に書いたモデル(Fable 5.1、Opus 5.5)は、その往復で実際に動いたモデルなので、Claude は書き換えない。

### 要件5 新しいモデルの審査も、審査が済んだものとして記録される

仕組みは、審査役が審査を済ませたことを記録する。Claude が、記録の無い段階の承認を所有者に求めようとすると、仕組みは Claude を止める。今の仕組みは、Fable 5.1 か Opus 5.5 で動いた審査だけを記録する。このままでは、審査役が新しいモデルで動くと、審査を済ませても記録が残らず、Claude が止まる。

1. 審査役が Fable か Opus の系統のモデルで審査を済ませたら、仕組みは、モデルの版によらず、審査が済んだことを記録する。
2. Fable か Opus の新しいモデルを使えるようになったら、仕組みは、新しいモデルの審査も記録する。そのために、所有者も Claude も、仕組みのファイルを直す必要が無い。
3. 審査役が動いたモデルを仕組みが読み取れて、そのモデルが Fable でも Opus でもない系統のモデル(Sonnet、Haiku など)だったときは、仕組みは、審査が済んだことを記録しない。

### 要件6 作業の集計に、Fable 5.2 の審査役の使用料が載る

今の料金表には Fable 5.2 が無い。そのため、作業の集計は、Fable 5.2 で動いた審査役の使用料を「価格が分からない」とし、全体の使用料の合計にも入れない。審査役が Fable 5.2 で動くようになると、審査に使った使用料の多くが集計から抜ける。

1. 作業の集計のモデルごとの表で、Fable 5.2 の行に、Fable 5.2 の公表価格で換算した使用料が載る。
2. 作業の集計の全体の使用料の合計に、Fable 5.2 の使用料が入る。

### 要件7 料金表に無いモデルや価格が見つかったら、Claude が料金表に足す PR を作る

新しいモデルが出るたびに所有者が料金表を直すと、直すまでの間、作業の集計は、そのモデルの使用料を数えない。所有者は、料金表を直す作業を Claude に任せ、Claude が作った PR を承認するだけで済ませたい。

1. Claude が作業の集計を GitHub にコメントとして書いたときに、集計に価格が分からないモデルがあれば、Claude は、公式の料金ページを読み、料金表に価格を足す PR を作る。料金表に無いモデルなら、Claude は、そのモデルの価格を足す。料金表にあるモデルでも、速い出力の価格のように、集計に要る種類の価格が料金表に無いときは、Claude は、その種類の価格を足す。
2. Claude は、足すモデルの公表価格のうち、料金表が持つ種類の価格を、公式の料金ページに載っている値のとおりにすべて足す。公式の料金ページが値で載せている価格は、Claude は、倍率で求め直さずに、載っている値を使う。公式の料金ページが、価格を値ではなく基本の価格に掛ける倍率で示しているときは、Claude は、ページに書かれた倍率で求めた値を、ページに載っている値として扱う。速い出力のキャッシュの価格がこれに当たる。
3. Claude は、料金表に価格を足すときに、料金表にすでにあるモデルのうち公式の料金ページに載っているモデルの価格も、料金ページと突き合わせる。値が違っていたら、Claude は、同じ PR で、公式の料金ページの値に直す。作業の集計が価格を確かめた日として示す日が、料金ページに載っているすべてのモデルに当てはまるようにするためである。料金ページに載っていない古いモデルの価格は、Claude は、変えずに料金表に残す。そのモデルを使った古い会話の使用料を、作業の集計が数え続けられるようにするためである。
4. Claude は、PR の本文に、足したモデルとその価格、直したモデルとその直す前と後の価格、読んだ公式の料金ページの場所と読んだ日を書く。
5. 公式の料金ページにそのモデルが載っていなければ、Claude は、そのモデルの価格を推し量って料金表に足さない。そのときは、Claude は、価格が見つからなかったモデルの名前を、会話の相手に返事で書く。
6. そのモデルの価格を料金表に足す PR がすでに開いていれば、Claude は、同じモデルの価格を足す PR をもう1つ作らない。
7. Claude は、PR を作ったあと、PR の承認のほかの作業を所有者に頼まない。
8. 作業の集計は、会話の記録からモデルの名前を読み取れなかった応答を、価格が分からないものとして数えることがある。Claude は、こうした応答を、PR を作るきっかけにしない。名前の分からないモデルの価格は、公式の料金ページで探せないためである。

### 要件8 審査役のモデルについての決まりの文を、版の番号で書かない形に直す

CLAUDE.md と `/spec-review` の手順には、審査役のモデルを「既定は Fable 5.1 で、所有者は spec ごとに Opus 5.5 を選べる」のように、版の番号で書いた文がある。このままでは、所有者と Claude が、今も版が決まっていると読み違える。

1. CLAUDE.md と `/spec-review` の手順には、審査役のモデルが、版の番号ではなく、Fable と Opus の系統の最新のモデルとして書かれている。あわせて、CLAUDE.md と `/spec-review` の手順には、要件1の5のとおり、本体の会話が審査役と同じ系統で動いているときは審査役が本体の会話と同じ版で動くことが書かれている。
2. CLAUDE.md の、会話の要約に残すことの決まりは、Fable の審査役から Opus の審査役に替えたかどうかを、版の番号を書かずに残すよう求める。
