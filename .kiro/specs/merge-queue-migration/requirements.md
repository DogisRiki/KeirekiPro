# 要件

## はじめに

この spec は、必須ステータスチェック18本を `merge_group` イベントに対応させ、ブランチ保護を merge queue へ切り替える。

今、このリポジトリは `Require branches to be up to date before merging` を無効にしている。この設定を無効にした理由は、複数のPRが同時に開いたときに、1本目のマージで残りのPRが out-of-date になって止まり、人間が Update branch を押す運用になっていたことである。この運用は、自律運用の前提と両立しなかった。その結果、今のリポジトリでは、古い base で緑になったPRがそのままマージされる。

公式は、merge queue をこの設定の代わりと位置づけている。merge queue は、マージの対象を、最新の base と先行するPRの変更に重ねた一時ブランチで検証する。merge queue を使えば、人間の操作を増やさずに、マージしたあとの状態に対する検証を取り戻せる。

ただし、公式ドキュメントは「必須チェックのワークフローは `merge_group` イベントで発火させなければならない」と明記している。結果を報告しないチェックは、キュー側のタイムアウトで失敗として扱われる。**1本でも対応していないチェックが残ると、キューが詰まり、すべてのPRがマージできなくなる。** 一部のチェックだけに当てはめることはできないため、この spec は、18本すべての扱いを一度に決める。

## 範囲

- この spec で決めること: 必須ステータスチェック18本の `merge_group` への対応、ブランチ保護の merge queue への切り替え、**自動マージの予約方法の調整**(下の節で理由を書く)、切り替えに伴う文書の更新
- この spec で決めないこと: 検査そのものの判定ロジックの変更(何を検知するかは変えない)、`Require branches to be up to date` を再び有効にすること、必須チェックの追加と削除、Trivy ゲートの導入(#181 で扱う)
- この spec が前提にしていること: 所有者の承認が必要なPR(`.github/` の変更、ゲート設定の変更、pre-merge-check ラベルの付いたPR)は、切り替えたあとも、所有者が承認するまで進まない

### 自動マージの予約方法をこの spec で決める理由

今、自動マージの予約には `gh pr merge --auto --squash` を使っている。このコマンドは、`.github/workflows/` の Dependabot 向けのワークフローと、`.claude/skills/ship/SKILL.md` の2箇所に現れる。merge queue を有効にしたときに、このコマンドがそのままキューへの投入の予約として働くかどうかは、まだ確かめていない。働かない場合は、切り替えと同時に出荷が止まる。自動マージの予約方法は切り替えから切り離せないため、この spec は、予約方法の調整を決めることに含める。

`.claude/` 配下は、ゲート設定として所有者の承認の対象にあたる。そのため、`.claude/` 配下の調整が必要になった場合は、Claude は、所有者の承認を経たうえで `.claude/` 配下を変更する。

## 要件

### 要件1 マージ列に対する結果の報告

所有者は、必須チェックのすべてがマージ列に対して結果を返してほしい。1本でも結果を報告しないチェックがあると、キューが詰まり、すべてのPRがマージできなくなるからである。

1. PRがマージ列に追加されたら、CIパイプラインは、必須ステータスチェック18本のすべてについて、キュー側のタイムアウトより前に成功か失敗を報告する。
2. 設計文書は、対照表を含む。対照表は、必須ステータスチェック18本の一覧と、各チェックのマージ列での扱い(再実行か引き継ぎか)と、その扱いを実現するワークフロー上の記述箇所を対応づける。
3. 必須ステータスチェックの構成が変わったら、対照表は、実際の必須チェックの一覧と件数に一致するように更新される。
4. CIパイプラインは、マージ列で報告するチェックの名前を、プルリクエストで報告する名前と一致させる。
5. マージ列での検証が失敗したら、CIパイプラインは、対象のPRをキューから外し、mainへ取り込まない。

### 要件2 マージしたあとの状態に対する再検証

所有者は、マージしたあとに成り立つ状態そのものを検証してほしい。個別のPRが緑でも、重ね合わせた結果が壊れることがあるからである。

1. PRがマージ列に追加されたら、CIパイプラインは、最新の base と先行するPRの変更を重ねた状態に対して、テスト、E2E、コンテナのビルド、IaCの静的検査、Gradle本体の検証を実行する。
2. マージ列の検証を実行している間、CIパイプラインは、変更検知の起点を、プルリクエストの差分ではなく、マージ列の base と head の比較に切り替える。
3. 変更検知が対象の変更を拾えないときは、CIパイプラインは、依存する検査をスキップして成功と報告せず、検知そのものの失敗として扱う。
4. CIパイプラインは、変更が無い領域の検査をスキップしてよい。ただし、CIパイプラインは、スキップした事実を実行ログに残す。

### 要件3 プルリクエスト単位で確定する判定の扱い

所有者は、マージ列で再現できない判定を、マージ列で再実行させないでほしい。マージ列には、プルリクエストの本文、ラベル、レビューの状態、作成者が存在しない。また、一部の検査は、使っているアクションがマージ列のイベントに対応していない。そのため、これらの判定をマージ列で再実行しても、同じ判定にならないか、そもそも動かないからである。

1. PRがマージ列に追加されたら、CIパイプラインは、プルリクエストの本文、ラベル、レビューの状態、作成者に依存する判定と、マージ列で技術的に実行できない検査について、プルリクエストの段階で確定した結果を引き継ぐ。
2. CIパイプラインは、引き継ぐ判定を、検査回避の検知、差分のサイズの検査、入手先と防御設定の承認、pre-merge-check ラベル、AIレビュー、シークレットの走査、公開からの経過時間の検査に限る。
3. プルリクエストの段階で判定が失敗していれば、CIパイプラインは、そのPRをマージ列に到達させない。
4. CIパイプラインは、引き継ぎの対象とした判定ごとに、なぜ再実行できないのかと、マージ列で無条件に成功を報告することで残るリスクを、文書に記録する。

### 要件4 依存の検査の保証の水準を保つ

所有者は、切り替えによって、依存の脆弱性とクールダウンの担保が弱まらないようにしてほしい。backend の依存は Gradle の解決の結果に依存し、変更を重ね合わせると解決の結果が変わりうるからである。

1. CIパイプラインは、切り替えたあとも、そのPRで新しく増えた脆弱性と、公開から72時間未満のパッケージを、マージの前に検出する。
2. マージ列で依存グラフの比較が技術的に成り立たないときは、CIパイプラインは、プルリクエストの段階の判定を引き継ぐ。そのうえで、CIパイプラインは、重ね合わせによって解決が変わる場合を検出できないことを、残るリスクとして文書に記録する。
3. 依存グラフのスナップショットが空になったら、CIパイプラインは、切り替えたあとも、それを検出して失敗する。
4. CIパイプラインは、mainへのpushで依存グラフを送信する経路を、切り替えによって壊さない。

### 要件5 切り替えのときの安全

所有者は、切り替えでリポジトリがマージできない状態に陥らないようにしてほしい。すべてのPRが止まると、復旧するまで何も出荷できなくなるからである。

1. キューのステータスチェックのタイムアウトを設定しているときは、CIパイプラインは、その値に、最も実行時間の長い必須チェックの上限を下回らない値を使う。
2. 同時実行の制御グループがプルリクエストの番号を参照しているときは、CIパイプラインは、その参照を、マージ列でも一意に定まる値へ切り替える。
3. マージ列でジョブに必要な権限が足りないときは、CIパイプラインは、権限の不足を成功として報告しない。
4. Dependabot のプルリクエストの必須チェックがすべて緑になったら、CIパイプラインは、人間の操作なしに、そのPRをマージ列へ投入する。
5. 所有者がPRを承認したら、CIパイプラインは、承認によって結果が変わるチェックを、切り替えたあとも、プルリクエストの段階で成功へ更新する。
6. mainブランチは、切り替えたあとも squash でマージされ、マージコミットも rebase も生じない。

### 要件6 運用の引き継ぎと文書

所有者は、切り替えたあとの運用の手順が実態と一致していてほしい。手順と実態がずれると、所有者は、監査で何を見るべきかが分からなくなるからである。

1. 切り替えが完了したら、監査手順から、週次の項目の「Update branch を押す」の記述が削除される。
2. ワークフローを変更したら、README のワークフロー一覧表と Mermaid の図が、実態に合わせて更新される。
3. 監査手順は、マージ列が詰まった場合に人間が確かめる手順を載せる。
4. 基盤構築手順は、ブランチ保護の設定表と必須チェックの一覧を、切り替えたあとの実態に合わせて載せる。
5. 基盤構築手順は、今、実態とずれている2点を解消する。1点目は、`Require branches to be up to date` が有効と書かれているが、実際は無効であることである。2点目は、必須チェックの一覧が15本で、`docker-smoke` `detect-changes` `detect-terraform-changes` が書かれていないことである。
6. 基盤構築手順は、人間が行う設定の作業として、merge queue を有効にすること、キューのマージ方式(squash)を指定すること、キューのタイムアウトを指定すること、`Require branches to be up to date` を戻さないことを明示する。
