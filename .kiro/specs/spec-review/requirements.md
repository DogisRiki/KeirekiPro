# 要件

## はじめに

この spec は、spec の文書(requirements.md・design.md・tasks.md)を、書いたモデルとは別のモデルにレビューさせ、指摘と対応を記録として残す仕組みを導入する。この spec では、spec を生成するメインの Claude のセッションを「実装セッション」と呼び、spec をレビューするサブエージェントを「レビュー役」と呼ぶ。

このリポジトリは、人間がコードをレビューしない自律開発パイプラインで開発しており、人間が判断するのは spec の承認だけである。PR の段階の codex-review は spec を判定の基準として使うため、spec 自体の誤りを検出しない。したがって、spec の誤りは、承認を通過したあと、どの工程でも止まらない。

今は、レビューの方法が確立しておらず、所有者が毎回口頭でサブエージェントを起動している。そのため、レビューの観点は毎回変わり、指摘と対応の記録も残らない。所有者は、レビューが効いているかをあとから確かめられない。

## 範囲

- この spec で決めること: spec の文書のレビューの起動、観点、往復、記録、レビューの実施の機械強制。あわせて、この spec は、`.claude/hooks/` の既存フック4本と `CLAUDE.md` の Git規約の実行前提を、新規フックと同じ形に揃えることを決める(`check-verify-before-stop.sh` の更新時刻の取得の修正を含む)
- この spec で決めないこと: 実装コードのレビュー(PR の段階の codex-review が担う)、spec の生成そのもの(cc-sdd が担う)、別ベンダーのモデルの導入
- この spec が前提にしていること: この spec は cc-sdd のスキルを変更しない。この spec は、レビューの手順を独立したスキルとして cc-sdd の外に置く

## 要件

### 要件1 レビューの起動

所有者は、spec の各段階の生成直後に、レビューが自動で走ってほしい。所有者は、承認するときに、本文と指摘の両方を手元に置きたいからである。

1. requirements.md・design.md・tasks.md のどれかを生成したら、実装セッションは続けてレビューを起動する。
2. レビュー役は、spec を書いたモデルとは別のモデルで動く。
3. 実装セッションがレビューを起動せずにセッションを終えようとしたら、リポジトリはセッションの終了をブロックし、レビューが実施されていないことを知らせる。
4. 所有者は、レビューを起動するためのコマンドを自分で入力しなくてよい。
5. 実装セッションは、その段階のレビューが完了するまで、所有者に承認を求めない。

### 要件2 観点の固定

所有者は、レビュー役が何を見るかを、段階ごとに決めておきたい。観点が決まっていれば、レビューの厳しさが spec ごとにぶれないからである。

1. リポジトリは、段階ごとの観点をファイルとして持つ。
2. レビュー役は、起動のたびに、その段階の観点のファイルを読む。
3. requirements の観点は、申告、要望の取りこぼし、要望に無い追加、厳密になっていない要件、検証する手段が無い要件、要件同士の矛盾、steering との整合、誤字脱字を含む。
4. design の観点は、申告、要件カバレッジ、設計のチェックリストの記載と本文の矛盾、境界と本文の食い違い、設計の中の矛盾、実現できない設計、前の段階への指摘、誤字脱字を含む。
5. tasks の観点は、申告、要件カバレッジ、design カバレッジ、スコープの膨張、完了条件の必須項目の有無、並列と依存の妥当性、tasks の中の矛盾、前の段階への指摘、誤字脱字を含む。
6. design の観点は、design のチェックリストについて、実測したという主張に、いつ何をどう確かめたかが書かれているかを見る項目を含む。
7. レビュー役は、AI が解釈で決めた箇所を、ほかにありえた選択肢と、外れたときの影響とともに申告する。
8. レビュー役が申告する対象は、段階ごとに決まっている。requirements では、レビュー役は、Issue に書かれていない部分を解釈で埋めた箇所を申告する。design では、レビュー役は、人間の承認が要る領域に触れる決定、運用から見える振る舞い、あとから変えにくい決定を申告する。tasks では、レビュー役は、やらないと決めたことと、テストを省略可能にしたことを申告する。
9. レビュー役は、ほかにありえた選択肢を書けないものを申告しない。
10. レビュー役は、spec の本文、Issue の本文、steering、リポジトリの実ファイルを自分で読む。レビュー役は、実装セッションが作った要約を判定の材料にしない。

### 要件3 指摘の重大度と対応

所有者は、直すべき指摘と、記録に留める指摘を分けてほしい。指摘が分かれていれば、所有者が読む量と往復の回数を抑えられるからである。

1. レビュー役は、指摘を高・中・低の3段階に分ける。
2. レビュー役は、指摘の重大度を、承認のあとに気づけるかどうかと、戻る範囲によって決める。
3. 実装セッションは、高と中の指摘だけを直す。
4. 実装セッションは、低の指摘を記録に残し、低の指摘では本文を直さない。
5. 実装セッションは、指摘ごとの処置を記録に書く。

### 要件4 往復と収束

所有者は、レビューの往復に上限を設けたい。上限が無いと、同じ論点で往復が限りなく続くからである。

1. 高と中の指摘が0件になったら、レビューはその時点で終わる。
2. サイクルは、1つの段階について、レビューを新しく始めてから終えるまでの一連の往復を指す。
3. レビューは、1つのサイクルにつき最大3往復で打ち切られる。
4. 3往復で高か中の指摘が残ったら、実装セッションは、残った指摘を未解決として記録し、本文を直さずにレビューを終える。
5. 未解決を残した段階について所有者が修正を選んだら、実装セッションは、新しいサイクルとしてレビュー役に本文の全体を読ませ、往復の上限を新たに与える。
6. 2往復目以降のレビューを起動するときは、実装セッションは新しいレビュー役を起動し、直前の1往復分の記録と、そのサイクルで却下された指摘の一覧(全往復分)を渡す。
7. レビュー役は、却下された指摘を再提出しない。ただし、却下の理由が事実として誤っているときは、レビュー役はその指摘を再提出してよい。

### 要件5 記録

所有者は、指摘と対応をファイルに残したい。記録が残れば、所有者は承認の根拠をあとから追え、レビューが効いているかを測れるからである。

1. リポジトリは、レビュー役が書くファイルと、実装セッションが書くファイルを分けて持つ。
2. レビュー役は、spec の本文と、実装セッションが書く記録のファイルを書き換えない。
3. 記録のファイルは追記式にする。記録の書き手は、過去の往復の記載を書き換えない。
4. 記録のファイルは、最終行に往復の回数と未解決の件数を持つ。
5. 記録のファイルは、実装コードのレビューの判定基準に混ざらない場所に置く。

### 要件6 前の段階への差し戻し

所有者は、前の段階の穴を、レビューの途中でその場で直されたくない。その場で直されると、所有者が承認したものが黙って書き換わるからである。

1. レビュー役は、前の段階の穴を見つけたら、その穴を、いまの段階の指摘と分けて記録する。
2. 実装セッションは、前の段階の穴をその場で直さず、往復を止めて所有者に報告する。
3. 実装セッションは、その報告に、その spec で何回目の差し戻しかを含める。
4. 差し戻しが2回目以降なら、実装セッションは、spec の分割と、requirements からの作り直しを、選択肢として報告に含める。
5. 所有者が修正を選んだら、実装セッションは、その段階とそれ以降の段階の承認を取り消してから本文を直す。
6. 修正のあとに再レビューするときは、実装セッションは、レビュー役に本文の全体を読ませ、往復の上限を新たに与える。
7. 承認済みの段階の本文を再生成または修正するときは、実装セッションは、差し戻しがあったかどうかによらず、その段階と後続の段階の承認を取り消してから再生成または修正する。

### 要件7 実施の機械強制

所有者は、レビューが実施されていないときに、指示だけでなく機械でも止めたい。機械で止まれば、レビューの実行漏れが承認まで進まないからである。

1. リポジトリでは、実装セッションではない主体が、レビューが完了した事実を記録する。
2. 記録する主体は、レビューの完了を示す印があるときに限り、レビューが完了した事実を記録する。
3. レビュー役が動いたモデルを確認できるときは、記録する主体は、そのモデルが所有者の定めたモデルでなければ、レビューが完了した事実を記録しない。
4. リポジトリは、レビュー役が動いたモデルを確認できない経路があることを受け入れる。その経路では、記録する主体は、指定と異なるモデルで動いたレビューを検出できない。
5. 次のどれかに当てはまる段階があれば、リポジトリはセッションの終了をブロックする。
   - レビューが実施されていない
   - レビューの完了を示す印が無い
   - 処置が書かれていない指摘がある
   - 最新の往復に処置「修正」が残っている(直したあとに再レビューしていない)
   - レビューが完了した事実の記録が無い
   - レビュー役が書く記録ファイルが、レビューの完了後に変わっている
   - 本文が、レビュー役が書く記録ファイルより新しい
6. リポジトリは、同じ入力に対してセッションの終了を2回までブロックし、3回目は通す。
7. リポジトリがブロックするかどうかを判定する対象は、生成済みで、人間の承認が無い段階に限る。
8. リポジトリは、判定のときに、自動承認(承認者名が人間でないもの)を未承認として扱う。
9. 承認にあたる操作が行われる時点で、未解決の指摘か、レビューが完了していない段階があれば、実装セッションはその一覧を所有者に示し、所有者の了承を得てから進む。

### 要件8 既存の仕組みとの関係

所有者は、既存の仕組みとこの spec の仕組みの役割の重なりを整理したい。役割が重なったままだと、同じことを弱い形で二重に行うことになるからである。

1. リポジトリは、cc-sdd が生成するスキルのファイルを変更しない。
2. リポジトリは、同じモデルで design を対話でレビューする既存のスキルを使わないことを、規約に明記する。
3. リポジトリは、既存の事前調査のスキルがレビューではなく調査であることを、規約に明記する。
4. PR の段階のレビューは、spec 自体の不備を審査しない。リポジトリは、この現状を保つ。
5. リポジトリは、既存のフックと新規のフックを、同じ実行前提(bash と perl の JSON::PP。jq に依存しない)で動く状態にする。リポジトリは、その前提を、各フックの冒頭と CLAUDE.md の Git規約に同じ文言で書く。
6. GNU 系と BSD 系で書式が異なるコマンドを使うときは、フックは、両方の書式を順に試し、得た値が期待する形式であることを確かめてから使う。
7. 既存のフックに、特定のOSでだけ失敗し、その失敗が握りつぶされて検査が無言で通る箇所があれば、リポジトリはその箇所を直す。既知の箇所は1件で、`check-verify-before-stop.sh` の更新時刻の取得である。
