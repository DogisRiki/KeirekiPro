# 要件

## 元の要望(Issue #193 の本文)

実装開始までのspec文書のレビュー方法とフローが決まっていない

#### 課題

spec駆動開発の実装開始前フェーズ(requirements.md / design.md / tasks.md)について、
レビューの方法とフローが決まっていない。

#182 のspec初運用では次の暫定運用になっており、場当たりで進んでいる。

- 生成時のセルフレビューゲート(スキル組み込み)は通っている
- それとは別に、所有者が別セッションのAI(Fable 5)へ都度依頼してレビューし、
  指摘を所有者が手でコピペして実装セッションに渡している
- この往復の手間が大きく、恒久的な方法として設計されたものではない

#### 前提(調査済みの事実)

- 同一モデルのセルフレビューには自己選好バイアスがあり、生成と評価は別モデルに
  分けるのが定石(研究・実践とも)
- 世の中の実践は「書いたモデルと別ベンダーのモデルにレビューさせ、人間が最終判定」が定番。
  Claude Codeからスキル経由で別AI CLI(Codex等)を相談役として呼ぶ運用例がある
- 全フェーズに多モデルを回すとコストが増えるため「普段は1つ、重要なものだけ2つ目」の
  段階適用が現実的とされる
- 本リポジトリはPR段階のレビュアーとしてCodexを採用済み(codex-review。現在は未設定で停止中)
- cc-sdd組み込みの `/kiro-validate-design` / `/kiro-validate-gap` との役割分担も未整理

#### 決めること

1. spec文書のレビューを誰が(どのAI/人間が)、どのフェーズで、どう起動するか
2. 指摘の受け渡し方法(コピペを無くす。ファイル渡し・スキル化・別AI CLI連携などが候補)
3. cc-sdd組み込みのvalidate系スキルとの役割分担
4. codex-review(PR段階)との役割分担。設計の指摘が実装後に出る構造を作らないこと

#### 決めないこと(このIssueの時点では)

どの案を採るかはまだ決めない。候補の比較と決定はこのIssueの対応の中で行う。

関連: #192(codex CLI等のセットアップが絡む場合、セットアップ手順の整備と合流する可能性がある)

#### やりたいこと

- 選んだモデルはその後の段階でも使う。途中でも、次の審査から選び直せる。(AIの提案を了承)
- Fable 5.1 が上限で動かないときは、所有者に尋ねずに Opus 5.5 に替えて審査を続け、替えたことを報告で知らせる。(AIの提案を了承)

#### どうなれば解決か

- Fable 5.1 が上限に達していても、spec の審査が止まらずに承認まで進められる。(AIの提案を了承)
- Fable 5.1 以外で審査した段階は、審査の記録と報告にどのモデルで審査したかが書かれ、所有者はそれを見てそのまま承認できる。(AIの提案を了承)
- Fable 5.1 の使う量に数字の目標は置かない。減ったことは、審査1回あたりの量を前後で比べて示す。(AIの提案を了承)

#### やらないこと

- 審査役以外での Fable 5.1 の使い方(所有者が頼む「Fable と壁打ち」や調査)は対象にしない。(AIの提案を了承)

### 追加の要望(Issue #900)
後ろの段階の審査が前の段階の文に食い違いを見つけても、作るものが変わらなければ、前の段階の承認を取り消さないようにする

#### きっかけ

#803 の改善のあとも spec の手戻りが減らないため、所有者が、#772 と #725 の手戻りの原因と改善策を確定するよう求めた。

#### 困っていること

- #803 の改善のあとも、#772 と #725 で spec の手戻りが多く発生している。
- 所有者が design を承認して `/kiro-spec-tasks` を打ったあとに、tasks の審査が design の文に食い違いを見つけると、食い違いが小さくても design の承認が取り消される。所有者は、design の承認と `/kiro-spec-tasks` をやり直すことになる。(AIの提案を了承)

#### やりたいこと

- 後ろの段階の審査が前の段階の文に食い違いを見つけても、作るものが変わらないときは、前の段階の承認が取り消されない。所有者は、前の段階の承認と、後ろの段階を作るコマンドをやり直さなくて済む。(AIの提案を了承)
  - 作るものが変わらない食い違いとは、前の段階の文が古い、足りない、節どうしで数や名前が合わない、という食い違いである。
  - 作るものが変わる食い違いとは、受入基準、外から見える動き、権限、方式の選び直しに関わる食い違いである。作るものが変わるときは、今までどおり前の段階の承認が取り消される。
- 作るものが変わるかどうかを、本文を書いた Claude が自分で決めて、承認の取り消しを避けることはできない。(AIの提案を了承)
- 所有者は、承認が取り消されないまま直された前の段階の文を、後ろの段階を承認する前に、直す前の文と直した後の文を並べて読める。(AIの提案を了承)
- 前の段階の審査が、後ろの段階で書くと記録した軽い食い違いを、後ろの段階がそのとおりに書いているときは、後ろの段階の審査が、前の段階に戻る指摘として出し直さない。(AIの提案を了承)

#### どうなれば解決か

- 直した手順を、#771、#772、#725 の spec で tasks の審査が design の承認を取り消した回に当てると、作るものが変わらない食い違いだけだった回では、design の承認が取り消されない。(AIの提案を了承)
- 同じ確かめで、作るものが変わる食い違いを含む回では、design の承認が取り消される。(AIの提案を了承)

#### やらないこと

- design の審査の観点は足さない。(AIの提案を了承)
- tasks の審査が design を読むことは止めない。(AIの提案を了承)
- design のファイルの一覧とテストの方針は無くさない。(AIの提案を了承)
- requirements、design、tasks の3段階の承認は変えない。(AIの提案を了承)
- 審査の往復の数を減らすことは、この要望では扱わない。(AIの提案を了承)

## はじめに

この spec は、spec の文書(requirements.md・design.md・tasks.md)を、書いたモデルとは別のモデルにレビューさせ、指摘と、指摘ごとの処置を記録として残す仕組みを導入する。この spec では、spec を生成するメインの Claude のセッションを「実装セッション」と呼び、spec をレビューするサブエージェントを「レビュー役」と呼ぶ。

このリポジトリは、人間がコードをレビューしない自律開発パイプラインで開発されている。人間は実装のコードを読まず、人間が作るものの中身を文で確かめるのは spec の承認のときである。PR の段階の codex-review は spec を判定の基準として使うため、spec 自体の誤りを検出しない。したがって、spec の誤りは、承認を通過したあと、どの工程でも止まらない。

この spec を始める前は、レビューの方法が確立していなかった。所有者は、毎回口頭でサブエージェントを起動していた。そのため、レビューの観点は毎回変わり、指摘と、指摘をどう扱ったかの記録も残らなかった。所有者は、レビューが効いているかをあとから確かめられなかった。

## 範囲

- この spec で決めること: spec の文書のレビューの起動、観点、往復、記録、レビューの実施の機械強制。あわせて、この spec は、`.claude/hooks/` の既存フック4本と `CLAUDE.md` の Git規約の実行前提を、新規フックと同じ形に揃えることを決める(`check-verify-before-stop.sh` の更新時刻の取得の修正を含む)。さらに、この spec は、レビュー役のモデルの選び方、Fable 5.1 が上限に達したときのモデルの切り替え、直したあとのレビューの範囲、レビュー役が使った量の記録を決める(#559 で変更)。さらに、この spec は、後ろの段階のレビューが前の段階の穴を見つけたときに、作るものが変わるかどうかで前の段階の承認を取り消すかを分けることと、承認を取り消さずに直した前の段階の文のレビューと所有者への見せ方を決める(#900 で変更)
- この spec で決めないこと: 実装コードのレビュー(PR の段階の codex-review が担う)、spec の生成そのもの(cc-sdd が担う)、別ベンダーのモデルの導入、レビュー役以外での Fable 5.1 の使い方(所有者が頼む壁打ちや調査)(#559 で変更)。design のレビューの観点を足すこと、tasks のレビュー役が design を読むのを止めること、design のファイルの一覧とテストの方針を無くすこと、requirements・design・tasks の3段階の承認を変えること、レビューの往復の数を減らすこと(#900 で変更)
- この spec が前提にしていること: この spec は cc-sdd のスキルを変更しない。この spec は、レビューの手順を独立したスキルとして cc-sdd の外に置く

## 要件

### 要件1 spec の各段階を生成したら、実装セッションが続けてレビューを起動する

所有者は、spec の各段階の本文が生成された直後に、レビューが自動で始まってほしい。所有者は、承認するときに、本文と指摘の両方を手元に置きたいからである。

1. requirements.md・design.md・tasks.md のどれかを生成したら、実装セッションは続けてレビューを起動する。
2. レビュー役は、所有者が選んだモデルで動く。(#559 で変更)
3. 実装セッションがレビューを起動せずにセッションを終えようとしたら、リポジトリはセッションの終了をブロックし、レビューが実施されていないことを知らせる。
4. 所有者は、レビューを起動するためのコマンドを自分で入力しなくてよい。
5. 実装セッションは、その段階のレビューが完了するまで、所有者に承認を求めない。

### 要件2 レビュー役が見る観点を、段階ごとにファイルで決めておく

所有者は、レビュー役が何を見るかを、段階ごとに決めておきたい。観点が決まっていれば、レビューの厳しさが spec ごとにぶれないからである。

1. リポジトリは、段階ごとの観点をファイルとして持つ。
2. レビュー役は、起動のたびに、その段階の観点のファイルを読む。
3. requirements の観点は、申告、要望の取りこぼし、要望に無い追加、厳密になっていない要件、検証する手段が無い要件、要件同士の矛盾、steering との整合、誤字脱字を含む。
4. design の観点は、申告、要件カバレッジ、design のチェックリストの記載と本文の矛盾、境界と本文の食い違い、design の中の矛盾、実現できない設計、前の段階への指摘、誤字脱字を含む。
5. tasks の観点は、申告、要件カバレッジ、design カバレッジ、スコープの膨張、完了条件の必須項目の有無、並列と依存の妥当性、tasks の中の矛盾、前の段階への指摘、誤字脱字を含む。
6. design の観点は、design のチェックリストについて、実測したという主張に、いつ何をどう確かめたかが書かれているかを見る項目を含む。
7. レビュー役は、AI が解釈で決めた箇所を、ほかにありえた選択肢と、外れたときの影響とともに申告する。
8. レビュー役が申告する対象は、段階ごとに決まっている。requirements では、レビュー役は、Issue に書かれていない部分を解釈で埋めた箇所を申告する。design では、レビュー役は、人間の承認が要る領域に触れる決定、運用から見える振る舞い、あとから変えにくい決定を申告する。tasks では、レビュー役は、やらないと決めたことと、テストを省略可能にしたことを申告する。
9. レビュー役は、ほかにありえた選択肢を書けないものを申告しない。
10. レビュー役は、spec の本文、Issue の本文、steering、リポジトリの実ファイルを自分で読む。レビュー役は、実装セッションが作った要約を判定の材料にしない。

### 要件3 レビュー役が指摘を高・中・低に分け、実装セッションは高と中の指摘だけを直す

所有者は、直すべき指摘と、記録に留める指摘を分けてほしい。指摘が分かれていれば、所有者が読む量と往復の回数を抑えられるからである。

1. レビュー役は、指摘を高・中・低の3段階に分ける。
2. レビュー役は、指摘の重大度を、承認のあとに気づけるかどうかと、戻る範囲によって決める。
3. 実装セッションは、高と中の指摘だけを直す。
4. 実装セッションは、低の指摘を記録に残し、低の指摘では本文を直さない。
5. 実装セッションは、指摘ごとの処置を記録に書く。

### 要件4 レビューの往復を、1つのサイクルにつき3往復までで打ち切る

所有者は、レビューの往復に上限を設けたい。上限が無いと、同じ論点で往復が限りなく続くからである。

1. 高と中の指摘が0件になったら、レビューはその時点で終わる。
2. サイクルは、1つの段階について、レビューを新しく始めてから終えるまでの一連の往復を指す。
3. レビューは、1つのサイクルにつき最大3往復で打ち切られる。
4. 3往復で高か中の指摘が残ったら、実装セッションは、残った指摘を未解決として記録し、本文を直さずにレビューを終える。
5. 未解決を残した段階について所有者が修正を選んだら、実装セッションは、新しいサイクルを始め、往復の上限を新たに与える。(#559 で変更)
6. 2往復目以降のレビューを起動するときは、実装セッションは新しいレビュー役を起動し、直前の1往復分の記録と、そのサイクルの全往復で却下された指摘の一覧を渡す。
7. レビュー役は、却下された指摘を再提出しない。ただし、却下の理由が事実として誤っているときは、レビュー役はその指摘を再提出してよい。

### 要件5 指摘と、指摘ごとの処置をファイルに残す

所有者は、指摘と、指摘ごとの処置をファイルに残したい。記録が残れば、所有者は承認の根拠をあとから追え、レビューが効いているかを測れるからである。

1. リポジトリは、レビュー役が書くファイルと、実装セッションが書くファイルを分けて持つ。
2. レビュー役は、spec の本文と、実装セッションが書く記録のファイルを書き換えない。
3. 記録の書き手は、記録のファイルに追記だけをする。記録の書き手は、過去の往復の記載を書き換えない。
4. 記録のファイルは、最終行に往復の回数と未解決の件数を持つ。
5. 記録のファイルは、実装コードのレビューの判定基準に混ざらない場所に置く。

### 要件6 前の段階への差し戻し

所有者は、前の段階の穴を、レビューの途中でその場で直されたくない。その場で直されると、所有者が承認したものが、所有者の知らないうちに書き換わるからである。

1. レビュー役は、前の段階の穴を見つけたら、その穴を、いまの段階の指摘と分けて記録する。
2. 実装セッションは、前の段階の穴をその場で直さず、往復を止めて所有者に報告する。ただし、1回の往復で見つかった前の段階の穴が、すべて作るものが変わらない穴のときは、実装セッションは、往復を止めずに、要件13の「作るものが変わらない食い違いでは前の段階の承認を取り消さない」のとおり前の段階の本文を直す。(#900 で変更)
3. 実装セッションは、その報告に、その spec で何回目の差し戻しかを含める。
4. 差し戻しが2回目以降なら、実装セッションは、spec の分割と、requirements からの作り直しを、選択肢として報告に含める。
5. 所有者が修正を選んだら、実装セッションは、その段階とそれ以降の段階の承認を取り消してから本文を直す。
6. 修正のあとに再レビューするときは、実装セッションは、新しいサイクルを始め、往復の上限を新たに与える。(#559 で変更)
7. 承認済みの段階の本文を再生成または修正するときは、実装セッションは、差し戻しがあったかどうかによらず、その段階と後続の段階の承認を取り消してから再生成または修正する。ただし、要件13のとおり作るものが変わらない穴だけで前の段階の本文を直すときは、実装セッションは、前の段階とその後続の段階の承認を取り消さない。(#900 で変更)

### 要件7 レビューが済んでいない段階があれば、セッションの終了を機械で止める

所有者は、レビューが実施されていないときに、セッションの終了を、指示だけでなく機械でも止めたい。機械で止まれば、レビューの実行漏れが承認まで進まないからである。

1. リポジトリでは、実装セッションではない主体が、レビューが完了した事実を記録する。
2. 記録する主体は、レビューの完了を示す印があるときに限り、レビューが完了した事実を記録する。
3. レビュー役が動いたモデルを確認できるときは、記録する主体は、そのモデルが Fable 5.1 と Opus 5.5 のどちらでもなければ、レビューが完了した事実を記録しない。(#559 で変更)
4. リポジトリは、レビュー役が動いたモデルを確認できない経路があることを受け入れる。その経路では、記録する主体は、指定と異なるモデルで動いたレビューを検出できない。
5. 次のどれかに当てはまる段階があれば、リポジトリはセッションの終了をブロックする。
   - レビューが実施されていない
   - レビューの完了を示す印が無い
   - 処置が書かれていない指摘がある
   - 最新の往復に処置「修正」が残っている。これは、実装セッションが本文を直したあとに、再レビューしていないことを指す
   - レビューが完了した事実の記録が無い
   - レビュー役が書く記録ファイルが、レビューの完了後に変わっている
   - 本文が、レビュー役が書く記録ファイルより新しい
6. リポジトリは、同じ入力に対してセッションの終了を2回までブロックし、3回目は通す。
7. リポジトリがブロックするかどうかを判定する対象は、生成済みで、人間の承認が無い段階に限る。
8. リポジトリは、判定のときに、承認者名が人間でない自動承認を、未承認として扱う。
9. 承認にあたる操作が行われる時点で、未解決の指摘か、レビューが完了していない段階があれば、実装セッションはその一覧を所有者に示し、所有者の了承を得てから進む。

### 要件8 既存のスキルとフックとの役割の重なりを整理し、フックを同じ実行前提で動かす

所有者は、既存の仕組みとこの spec の仕組みの役割の重なりを整理したい。役割が重なったままだと、同じことを弱い形で二重に行うことになるからである。

1. リポジトリは、cc-sdd が生成するスキルのファイルを変更しない。
2. リポジトリは、同じモデルで design を対話でレビューする既存のスキルを使わないことを、規約に明記する。
3. リポジトリは、既存の事前調査のスキルがレビューではなく調査であることを、規約に明記する。
4. PR の段階のレビューは、spec 自体の不備を審査しない。リポジトリは、この現状を保つ。
5. リポジトリは、既存のフックと新規のフックを、同じ実行前提で動く状態にする。その実行前提は、bash と perl の JSON::PP があることで、jq には依存しない。リポジトリは、その前提を、各フックの冒頭と CLAUDE.md の Git規約に同じ文言で書く。
6. GNU 系と BSD 系で書式が異なるコマンドを使うときは、フックは、両方の書式を順に試し、得た値が期待する形式であることを確かめてから使う。
7. リポジトリは、既存のフックのうち、特定のOSでだけ失敗し、その失敗が無視されて、検査が何も知らせずに通る箇所を直す。既知の箇所は1件で、`check-verify-before-stop.sh` の更新時刻の取得である。

### 要件9 レビュー役のモデルを所有者が選ぶ (#559)

所有者が週に複数の spec で開発すると、2〜3日で Fable 5.1 の使える量が上限に達し、上限が解けるまで開発が止まる。所有者は、Fable 5.1 が使えない間も、別のモデルでレビューを続け、承認まで進めたい。

1. 所有者は、spec を始めるときに、その spec のレビュー役のモデルを Fable 5.1 と Opus 5.5 のどちらにするかを選べる。(#559)
2. 所有者は、モデルを選ばずに spec を進めてもよい。所有者がモデルを選んでいない spec では、レビュー役は、今までと同じく Fable 5.1 で動く。所有者がモデルを選べるようになる前から進めている spec には、選んだモデルの記録が無いので、その spec でもレビュー役は Fable 5.1 で動く。(#559)
3. 実装セッションは、所有者が選んだモデルを、会話の中ではなく spec ごとに記録する。そのため、所有者が段階ごとに新しいセッションを開いても、レビュー役は、所有者が選び直さないまま、その spec で選んだモデルで動く。たとえば、所有者が requirements の段階で Opus 5.5 を選び、design を新しいセッションで作ったときも、design のレビュー役は Opus 5.5 で動く。(#559)
4. 所有者は、spec を始めたあとも、その spec のレビュー役のモデルを選び直せる。たとえば、所有者は、requirements のレビューを Fable 5.1 で終えて承認したあと、design を作る前に、Opus 5.5 に選び直せる。また、所有者は、1つの段階のレビューが往復している間に Fable 5.1 の残りが少なくなったときに、Opus 5.5 に選び直せる。所有者が選び直したあと、実装セッションが次に起動するレビュー役から、レビュー役は選び直したモデルで動く。(#559)
5. レビュー役が Fable 5.1 で動く spec は、所有者が Fable 5.1 を選んだ spec と、所有者がモデルを選んでいない spec である。そうした spec で Fable 5.1 が上限に達していてレビュー役が動かないときは、実装セッションは、所有者に尋ねずに、Opus 5.5 でレビュー役を起動し直してレビューを続ける。(#559)
6. 実装セッションが Fable 5.1 の上限のためにレビュー役のモデルを Opus 5.5 に替えるのは、そのときのレビュー役の起動に限る。実装セッションは、spec に記録した所有者の選んだモデルを書き換えない。所有者がモデルを選んでいない spec に、実装セッションは Opus 5.5 を記録しない。次にレビュー役を起動するときは、Fable 5.1 の上限が解けているかもしれないので、実装セッションはまず Fable 5.1 でレビュー役を起動する。Fable 5.1 がまだ上限に達していれば、実装セッションは、またレビュー役のモデルを Opus 5.5 に替える。(#559)
7. Opus 5.5 のレビュー役も上限に達していて動かないときは、実装セッションはレビューを止め、レビュー役が上限で動かないことを所有者に知らせる。(#559)
8. 上限に達したこと以外の理由でレビュー役が動かないときは、実装セッションはモデルを替えない。上限に達したこと以外の理由とは、たとえば、通信が切れたこと、Anthropic のサービスが混み合っているか止まっていること、所有者がレビュー役を途中で止めたことである。実装セッションは、レビュー役が動かなかったことと、その理由を所有者に知らせる。(#559)

### 要件10 レビューしたモデルを記録と報告に書く (#559)

所有者は、Fable 5.1 以外のモデルでレビューした段階も、そのまま承認したい。そのために、所有者は、承認するときに、どのモデルがレビューしたかを知っておきたい。

1. 実装セッションは、往復ごとに、レビュー役が動いたモデルを、実装セッションが書く記録のファイルに書く。(#559)
2. 実装セッションは、所有者への報告に、往復ごとのレビュー役のモデルを書く。(#559)
3. 実装セッションがレビュー役のモデルを Fable 5.1 から Opus 5.5 に替えた往復があれば、実装セッションは、替えたことと、Fable 5.1 が上限に達していたために替えたことを、所有者への報告に書く。(#559)
4. 所有者は、Opus 5.5 でレビューした段階も、Fable 5.1 でレビューした段階と同じ操作で承認できる。(#559)

### 要件11 直したあとのレビューは直した箇所と影響を受ける箇所だけを見る (#559)

所有者は、レビュー役が Fable 5.1 を使う量を減らしたい。本文を少し直しただけでレビュー役が本文の全体をもう一度レビューすると、レビュー役は直していない箇所のレビューに量を使うからである。

1. 段階の本文を生成したあとの最初のレビューでは、レビュー役は本文の全体をレビューする。(#559)
2. 前回のレビューのあとに本文が直されたときは、レビュー役は、直された箇所と、その直しで影響を受ける箇所だけをレビューする。直された箇所とは、前回のレビューのときの本文と今の本文を比べた差分の全部を指す。差分には、書き方の点検で直した箇所と、所有者が直した箇所も含まれる。本文が直されたときとは、次の4つの場面を指す。(#559)
   - 2往復目以降の往復
   - 未解決を残した段階を所有者が直すことにしたあとの、新しいサイクル
   - 前の段階への差し戻しで本文を直したあと
   - 所有者が承認の前に本文を直したあと
3. 実装セッションは、レビュー役を起動するときに、前回のレビューのときの本文と今の本文の差分を、要約せずにそのままレビュー役に渡す。実装セッションは、差分のうちどこをレビューするかを選ばない。(#559)
4. レビュー役は、直しで影響を受けると判断した箇所と、そう判断した理由を、レビュー役が書く記録のファイルに書く。(#559)
5. 実装セッションが、前回のレビューのときの本文と今の本文を比べられないときは、実装セッションは、レビュー役に本文の全体をレビューさせる。(#559)
6. レビュー役は、どのモデルで動くかによらず、この範囲でレビューする。(#559)

### 要件12 レビュー役が使った量を比べられるようにする (#559)

所有者は、レビュー役が使う量に数字の目標を置かない。所有者は、レビュー1回あたりの量が減ったことを、変更の前と後の数字で確かめたい。

1. 実装セッションは、往復ごとに、レビュー役が使った量(トークンの数)を、実装セッションが書く記録のファイルに書く。実装セッションがこの量を記録のファイルに書くのは、レビュー役が使った量がレビュー役が終わってから分かるためである。(#559)
2. 所有者は、この変更を出荷するPRの本文で、変更の前と後のレビュー1回あたりの量を比べた結果を見られる。(#559)

### 要件13 作るものが変わらない食い違いでは前の段階の承認を取り消さない (#900)

所有者が design を承認して `/kiro-spec-tasks` を打ったあとに、tasks のレビュー役が design の文に食い違いを見つけると、今は、食い違いが小さくても design の承認が取り消される。所有者は、design の承認と `/kiro-spec-tasks` をやり直すことになる。#803 の改善のあとも、#772 と #725 の spec ではこの手戻りが多く起きた。所有者は、作るものが変わらない食い違いでは、前の段階の承認と、後ろの段階を作るコマンドをやり直したくない。

1. レビュー役は、前の段階の穴を見つけたら、穴ごとに、作るものが変わる穴か、作るものが変わらない穴かを決める。レビュー役は、決めた結果を、要件6の1でいまの段階の指摘と分けて記録した、その穴の記録に書く。レビュー役は、前の段階の穴にも、いまの段階の指摘と同じく、高・中・低のどれかを付けて、その穴の記録に書く。(#900)
2. 作るものが変わる穴とは、受入基準、外から見える動き、権限、方式の選び直しのどれかに関わる穴である。作るものが変わらない穴とは、前の段階の文が古い、足りない、節どうしで数や名前が合わない、のどれかに当たり、受入基準、外から見える動き、権限、方式の選び直しのどれにも関わらない穴である。両方の説明に当たる穴は、作るものが変わる穴とする。(#900)
3. レビュー役は、作るものが変わるかどうかを決められない穴を、作るものが変わる穴として記録する。レビュー役が作るものが変わるかどうかを書いていない穴も、実装セッションは、作るものが変わる穴として扱う。(#900)
4. 実装セッションは、レビュー役が作るものが変わる穴と記録した穴を、作るものが変わらない穴として扱わない。本文を書いた実装セッションが、自分で作るものが変わらないと決めて、承認の取り消しを避けることはできない。(#900)
5. 1回の往復で見つかった前の段階の穴が、すべて作るものが変わらない穴のときは、実装セッションは、往復を続け、所有者に尋ねずに、前の段階の承認を残したまま前の段階の本文を直す。実装セッションは、これらの穴を、いまの段階の指摘と同じく扱う。実装セッションは、高と中の穴を直すか、誤検知なら理由を書いて却下し、低の穴は記録に残して直さない。実装セッションは、作るものが変わらない穴のうち高と中の穴を、要件4の1と4で数える高と中の指摘に入れる。そのため、高か中の穴が見つかった往復では、レビューは終わらない。要件14の1の、承認を取り消さずに直した前の段階の本文のレビューは、前の段階の本文を直したあとの次の往復で行われる。3往復目で見つかった高か中の穴は、実装セッションが、要件4の4のとおり、前の段階の本文を直さずに未解決として記録する。(#900)
6. 1回の往復で見つかった前の段階の穴に、作るものが変わる穴が1つでもあるときは、実装セッションは、要件6の2から5のとおり、往復を止めて所有者に報告し、所有者が修正を選んだら承認を取り消してから直す。この場面では、実装セッションは、5の、所有者に尋ねずに前の段階の承認を残したまま前の段階の本文を直す手順に従わない。同じ往復で見つかった作るものが変わらない穴も、実装セッションは、承認を取り消したあとに一緒に直す。(#900)
7. 実装セッションは、作るものが変わらない穴で前の段階の本文を直したことを、要件6の3で報告する差し戻しの回数に数えない。(#900)
8. この要件の前の段階は、いまレビューしている段階より前の、承認済みの段階を指す。tasks のレビューで requirements の穴が見つかったときは、requirements と design の両方の承認が、この要件の対象になる。(#900)
9. リポジトリは、承認済みの段階の本文を直す前にその段階と後続の段階の承認を取り消すという規約に、この要件の例外を書く。(#900)
10. 5のとおり3往復目で未解決として記録した、作るものが変わらない穴を、所有者があとで直すことを選んだときも、実装セッションは、前の段階の承認を残したまま前の段階の本文を直す。実装セッションは、そのあと新しいサイクルを始め、直した本文は、新しいサイクルの最初の往復で、要件14の1のとおりレビューされる。(#900)

### 要件14 承認を取り消さずに直した前の段階の文をレビューし、所有者に見せる (#900)

承認を取り消さずに前の段階の本文を直すと、所有者が承認したものが、所有者の知らないうちに書き換わるおそれがある。所有者は、その直しが本当に作るものを変えていないかを、本文を書いた実装セッション以外の者に確かめさせたい。また、所有者は、後ろの段階を承認する前に、直す前の文と直した後の文を読みたい。

1. 実装セッションが承認を取り消さずに前の段階の本文を直したら、レビュー役は、要件11と同じく、直した箇所と、その直しで影響を受ける箇所に限って、その直しをレビューする。(#900)
2. そのレビューで、直しが作るものを変えているとレビュー役が判断したら、レビュー役は、それを作るものが変わる穴として記録する。実装セッションは、往復を止めて所有者に報告する。所有者が直しを残すことを選んだら、実装セッションは、直した段階とその後続の段階の承認を取り消す。所有者が直しを残さないことを選んだら、実装セッションは、前の段階の本文を直す前の文に戻す。(#900)
3. 実装セッションは、承認を取り消さずに前の段階の本文を直したら、直した段階と、直した時刻と、もとになった穴のIDを、spec ごとの記録に追記する。記録の書き手は、この記録を書き換えたり消したりしない。(#900)
4. 実装セッションは、後ろの段階の承認を求める報告に、承認を取り消さずに直した前の段階の、直す前の文と直した後の文を並べて書く。(#900)
5. 所有者は、会話を終えたあとや別の会話からも、承認を取り消さずに直した前の段階の、直す前の文と直した後の文を、記録のファイルで並べて読める。(#900)
6. 所有者が直した後の文に同意しないときは、所有者は、前の段階の承認を取り消して直し直すことを選べる。所有者がそれを選んだら、実装セッションは、要件6の5のとおり、その段階とそれ以降の段階の承認を取り消してから直す。(#900)
7. 承認を取り消さずに直した前の段階の本文が、直したあとにレビューされていなければ、リポジトリはセッションの終了をブロックする。要件7の7は、ブロックするかどうかを判定する対象を、生成済みで人間の承認が無い段階に限っている。承認を取り消さずに直した段階は承認済みだが、直したあとのレビューが済んでいるかの判定に限り、リポジトリはその段階も判定の対象にする。(#900)

### 要件15 前の段階のレビューが後ろの段階に回した食い違いを出し直さない (#900)

前の段階のレビューで、軽い食い違いを、後ろの段階で書くと記録して終えることがある。実装セッションが後ろの段階の本文にそのとおりに書いたのに、後ろの段階のレビュー役がその食い違いを前の段階の穴として出し直すと、所有者は、前の段階で済ませた判断をもう一度することになる。

1. 前の段階のレビューの記録とは、レビュー役が書く記録と、実装セッションが書く処置の記録である。後ろの段階のレビュー役は、次の2つがそろう食い違いを、前の段階の穴として記録しない。1つ目は、前の段階のレビューの記録に、その食い違いを後ろの段階で書くと記録されていることである。2つ目は、後ろの段階の本文に、その記録のとおりに書かれていることである。これは、レビュー役が前の段階の穴をいまの段階の指摘と分けて記録するという要件6の1の、例外である。(#900)
2. 後ろの段階の本文に、前の段階のレビューの記録のとおりに書かれていないときは、後ろの段階のレビュー役は、その食い違いを、いまの段階の指摘として記録する。(#900)

### 要件16 直した手順を過去の回に当てて確かめる (#900)

所有者は、直した手順が手戻りを減らすことを、実際に手戻りが起きた回で確かめたい。

1. 所有者は、この変更を出荷するPRの本文で、直した手順を、#771、#772、#725 の spec で tasks のレビューが design の承認を取り消した回のそれぞれに当てた結果を見られる。(#900)
2. 結果には、回ごとに、前の段階の穴ごとの作るものが変わるかどうかと、design の承認が取り消されるかどうかが書かれる。(#900)
3. 作るものが変わらない穴だけだった回では、design の承認は取り消されない。作るものが変わる穴を含む回では、design の承認は取り消される。(#900)
4. この確認では、作るものが変わるかどうかを、直した手順のとおりにレビュー役が決める。実装セッションは決めない。(#900)
