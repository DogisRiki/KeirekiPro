# 調査と設計の判断の記録

## まとめ
- **機能**: `issue-method-deviation-gate`
- **調査の範囲**: 既存の仕組みの拡張(codex-review.yml の判定の基準を足す)
- **主な発見**:
  - codex-review.yml は、PR本文の `Spec:` のパスが実在しないときだけ、`Refs: #N` のIssueのタイトルと本文を `spec.md` に書き出して判定の基準にする(158〜174行目)。Issue本文を基準にするPRを見分ける場所は、この分岐の中にある
  - 今のプロンプトは「設計判断や検証方法がIssueの記述と異なる場合でも、pr-body.txt に理由が記載されていれば適合とする」(220〜222行目)と「spec適合は『要求が未実装』または『受け入れ基準に対応するテストが無い』場合のみ CHANGES_REQUESTED」(234〜236行目)を定めている。この2つが、「決めた方式」から外れたPRを通してしまう原因である
  - ジョブは `vars.CODEX_REVIEW_ENABLED == 'true'` のときだけ動く(42行目)。#166 で費用を理由に止めてあり、2026-10-06 時点でリポジトリの変数は1つも設定されていない(`gh api repos/DogisRiki/KeirekiPro/actions/variables` の `total_count` が0)
  - 直近200件のIssueのうち、本文に `## 決めた方式` の見出しを持つのは #445 と #477 の2件だけである

## 調べたこと

### 「決めた方式」をどう見つけるか
- **きっかけ**: 要件1の項目1は、Issue本文に「決めた方式」の見出しがあるときだけ判定を足す。見出しの有無を誰が判定するかを決める必要があった
- **見たもの**: `.claude/skills/file-issue/SKILL.md` の「本文の書式」(見出しは `## 決めた方式`。中身の無い見出しは省く)、`codex-review.yml` の Prepare review context
- **分かったこと**: Issue本文の見出しは起票の決まりで `## 決めた方式` に決まっている。`spec.md` の先頭には、ワークフローが `# <タイトル>` の行を足す。Webの画面で書いたIssueの本文は、改行が CRLF になることがある
- **設計への影響**: 見出しの有無と節の中身は、スクリプトで機械的に抜き出す。Codex に見出しを探させない。CRLF の `\r` は抜き出す前に取り除く。コードブロックの中の `## ` は見出しとして扱わない

### スクリプトのテストをどこで流すか
- **きっかけ**: 抜き出すスクリプトを足すと、そのテストを CI で流す場所が要る
- **見たもの**: `guardrails.yaml` の `Test spec backing check`(124行目)、`close-linked-issues.yaml`、`dependency-gate.yaml`
- **分かったこと**: このリポジトリは、スクリプトを使うワークフローの中で、使う前にそのスクリプトのテストを流す形にそろえている
- **設計への影響**: codex-review.yml の中で、抜き出す前にテストを流す。ただし、ジョブが動かない間(`CODEX_REVIEW_ENABLED` が `true` でない間)はテストも流れない。そのため、Claude は実装のときに手元のコンテナでテストを流して確かめる

## 比べた案

| 案 | 中身 | よい点 | 弱い点 | 結論 |
|---|---|---|---|---|
| A. プロンプトだけを直す | Codex に `spec.md` から「決めた方式」の見出しを探させる | 変えるファイルが1つ | 見出しの有無の判定を Codex に任せることになり、見落としてもジョブは緑になる。見出しが無いPRでも、プロンプトの文面が変わる | 採らない |
| B. スクリプトで抜き出し、見出しがあるときだけプロンプトに観点を足す | `extract-decided-method.sh` が節を抜き出し、ワークフローが中身のあるときだけ観点の節を足す | 見出しの有無の判定をテストで確かめられる。見出しが無いPRと spec のPRでは、プロンプトが今と1文字も変わらない | ファイルが2つ増える | 採る |
| C. 別のジョブで判定する | codex-review とは別に「決めた方式」だけを判定するジョブを作る | 自動レビューの停止中も動かせる | 所有者が「自動レビューが動いているときだけ動かす」と答えた(要件の段階の質問の選択肢2)。必須チェックの追加になり、所有者に提案する変更が増える | 採らない |

## 設計の判断

### 判断: 観点の節は、見出しがあるときだけプロンプトの末尾に足す
- **背景**: 要件2は、「決めた方式」の見出しが無いPRと spec のPRの判定を今のまま残す
- **比べた案**:
  1. 今のプロンプトの例外の文(220〜222行目)を書き換える
  2. 今のプロンプトは変えず、見出しがあるときだけ、例外を打ち消す観点の節を足す
- **選んだ案**: 2
- **理由**: 見出しが無いときにプロンプトが今と同じになるので、要件2を文面の比較だけで確かめられる
- **引き換え**: 観点の節が、今のプロンプトの2つの規則を名指しで打ち消す形になる。Codex が打ち消しを読み落とすおそれがあるので、観点の節の中で、打ち消す規則を引用して書く
- **あとで確かめること**: 所有者が自動レビューを再開したあと、「決めた方式」のあるIssueのPRで、Codex が項目ごとの表を出すかを実物で確かめる

### 判断: 外れの指摘の重さは High にする
- **背景**: 今のプロンプトは、Blocker か High が1件以上あればその軸を CHANGES_REQUESTED にする
- **選んだ案**: 「沿っていない」項目ごとに、spec適合の指摘として High を付ける。High の定義には「検査のすり抜け」が入っているので、今の基準と食い違わない
- **理由**: 判定の規則を新しく足さず、今の規則(High なら CHANGES_REQUESTED)に乗せられる

### 判断: 抜き出しに失敗したら、ジョブを失敗にする
- **背景**: 抜き出しのスクリプトが失敗したまま進むと、「決めた方式」が無いものとして判定され、外れたPRが通る
- **選んだ案**: Prepare review context の手順は既定のシェル(`bash -e`)で動くので、スクリプトが0以外で終わったら手順が失敗し、ジョブが赤になる。今の Evaluate verdict と同じく、判定できないときは通さない側に倒す

## 危険と手当て
- Codex がプロンプトの観点を守らず、外れたPRに LGTM を出す — 観点の節に、打ち消す規則の引用と、出力の表の形を書く。出荷後、所有者が自動レビューを再開したときに、実物で確かめる手順をPR本文に書く
- 自動レビューの停止中は、この spec の判定もテストも動かない — 所有者の答えどおりの扱い。requirements.md の範囲の節の前提に書いてある
- PRがスクリプトを書き換えて抜き出しを空にする — スクリプトは `.github/` の下に置くので、CODEOWNERS により所有者の承認がないとマージされない。ワークフロー本体を書き換えるのと同じ守りになる
