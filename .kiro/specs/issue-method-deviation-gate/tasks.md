## 実装のメモ

- `.github/` への書き込みは、設定(settings.json の拒否)で止められる。Claude は、scratchpad の `impl/.github/` に同じパスでファイルを作り、リポジトリの `.github` に重ねたコンテナでテストを流す
- 抜き出しのテストは、`codex-review.yml` の中でだけ流れる(design の審査の低の指摘 D1-1-4)。自動レビューが止まっている間は CI で流れないので、Claude は、このPRでは手元のコンテナで流した結果をPR本文に書く
- 観点の節は「沿っていない」項目に High を付けさせる。Codex がその High をコード品質の軸に数えても、どちらかの軸が `CHANGES_REQUESTED` ならジョブは赤になるので、マージが止まることは変わらない(design の審査の低の指摘 D1-1-2)
- Claude は、`/ship` で書くPR本文に、所有者が自動レビューを再開したときに実物で確かめる手順を書く。手順は、「決めた方式」の見出しを持つIssueと、その方式から外れた変更のPRを用意し、spec適合が `CHANGES_REQUESTED` になることと、コメントに項目ごとの表が出ることを見るものにする
- Issue本文の取得に失敗して赤になったPRの扱いは、`/review-loop` に手順が無い(design の審査の低の指摘 D1-1-1)。Claude は、`/review-loop` を変えない。再実行の案内は、抜き出しを判定の基準を決める処理に足すタスク(2.1)で足すエラーの文面に任せる

- 1.2: スクリプトは、見出しの末尾の空白として半角の空白とタブだけを認める。全角の空白や `## 決めた方式 ##` の見出しは節にならず、観点が足されない側に倒れる。起票の決まりの書式が `## 決めた方式` のあいだは問題ない。awk は `LC_ALL=C` で呼び、文書は標準入力から渡す(パスに `=` があると awk が代入として読むため)
- 2.1: 手元での確かめは scratchpad の `harness21/` で行った。手順の `run:` の中身を取り出し、偽の `gh` と一時ファイルの `GITHUB_ENV` `RUNNER_TEMP` で、ubuntu:24.04 のコンテナで動かす。`gh issue view` の `2>/dev/null` は、取得に失敗した理由をログに出すために外した
- 2.2: 観点の節の文面は、design.md の手順3のブロックから機械で取り出して写した(scratchpad の `harness22/apply.py`)。プロンプトの組み立ての確かめは `harness22/run.sh` で、`なし` の `prompt.md` が変更前と1バイトも違わないことを `cmp` で見る
## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめてから、コードを元に戻す。
