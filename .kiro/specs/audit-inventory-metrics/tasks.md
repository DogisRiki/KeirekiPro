# Implementation Plan

## KeirekiPro 完了条件(全タスク共通)

1. **acceptance criteria の引用とテスト対応付け**: 各タスクは、対応する requirements.md の受入基準と、それを検証するテスト(`.github/scripts/tests/` 配下のファイル名)を detail に持つ。テストが無い受け入れ基準を残さない。ワークフロー・設定・文書のタスクは、設計の契約との突合と、マージ後の確認(タスク7.2)で確かめる
2. **verify の実行**: 変更領域の多くは `.github/`・`doc/`・`README.md`・`.kiro/` で、既存の verify Skill の対象外。代わりに、guardrails.yaml と同じ検査を手元で通す
   - 同梱テスト: ホストで直接実行しない(ホストに jq が無く、赤を期待するテストが誤った理由で通るため)。alpine コンテナ(`bash jq coreutils grep curl git` を入れる)へリポジトリをマウントし、`bash` で起動する
   - shellcheck: `.github/scripts` のシェルスクリプトに `koalaman/shellcheck:v0.11.0` を流す(`-S style` でも警告を残さない)
   - actionlint: 変更したワークフローに `rhysd/actionlint:1.7.12` を流す
   - `docker/terraform/` を変えるタスク(1.3)は `/verify-terraform` を通す
3. **ゴールハック禁止**: テストのskip化・アサーション削除で完了条件を満たさない。既存のテストの期待値を変えるときは、設計で決めた契約の変更に限り、PR本文の `Test-Change-Justification` に理由を書く
4. 新規テストは対象コードを一時的に壊して赤くなることを確認してから戻す
5. **着手前の前提**: `.github/` 配下の編集は、自動の安全確認に止められることがある。止められたら回避せず、所有者に権限モードの切り替えを依頼する。`.github/` とゲート設定を含むため、PRは所有者の承認が要る
