## 所有者の指摘による修正(2026-09-28、承認前)

サイクル1の収束後、承認前に所有者の指摘を受けて本文を直した。サイクル2でレビューする。

- 要件7-4(導入直後に手動で1回実行する手順を監査手順書に書く)を削除した。所有者の指摘: 一度きりの作業を手順書に書く意味が無い。導入直後の手動実行は、実装のタスクのマージ後の確認で扱う(Boundary Context の Out of scope に明記)
- 要件3-4 のカバレッジの取り方を具体化した。所有者は「月1回の実行の中で測り直す」案を退けた。壁打ち(Fable 5.1)を経て、main で最後にテストを実行したCIが出した値と、その実行の日付・コミットを並べる形にした。測り直しはしない
- 要件3-6 に、CIの結果の保存期間内に main でテストを実行したCIが無い場合も「取得できず」とすることを足した
- 要件3-9 を足し、CI が main で出したカバレッジの結果を90日(公開リポジトリの上限)保存することを定めた。現在は7日(`ci.yaml` の frontend-test-results / backend-check-results)

## 所有者の判断による修正(2026-09-29、承認の取り消し後)

design の段階で、Dependabot の既定の待ち期間(公開から3日)が ghcr.io の tflint には効かないことが分かった(dependabot-core `docker/README.md` の Cooldown publication dates の節と `docker/lib/dependabot/docker/update_checker.rb` の `registry_tag_release_date`・`using_dockerhub?` を一次資料で確認)。所有者は、ほかの依存と同じく公開から72時間待つ仕組みを入れると判断した。CLAUDE.md の規約に従い、requirements と design の承認を取り消してから直した。サイクル3でレビューする。

- 要件4-5 に、tflint を digest でも固定することを足した
- 要件4-6〜4-9 を足した: 公開から72時間経っていない tflint の更新PRは自動マージを予約しない、1日1回見直して予約する、公開日時を取れないときは予約せずPRにコメントして所有者にメンションする、公開日時は公開した側が書き換えられない値だけを使う
- Boundary Context の In scope に上記の仕組みを足した
