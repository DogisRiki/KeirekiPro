# 要件

## 元の要望

出典: #415「監査の棚卸しとメトリクスを機械で集めて月1回届ける」

### 背景

監査手順の定期作業(#411 で1つの表にまとめた)のうち、次の作業は人間の判断を含まず、調べて書き写しているだけになっている。

- 月次: tflint・tflint の AWS 用ルールセット・checkov・Trivy の、使っている版と最新版の差を調べる
- 半期: Java・Node.js・PostgreSQL(開発と本番のRDS)・Redis/Valkey(開発と本番)・Terraform・Docker(dind)・LocalStack のサポート期限を、配布元のサイトを開いて調べる
- 月次: mutation スコアを、台帳のIssueで前月の行と比べる
- 半期: カバレッジの実測と基準値を並べる

人間が半期ごとに見ていたはずの Docker(dind)は、2025-05-03 にサポートが切れたまま気づかれていなかった(#406)。

一方で、定期の確認をやめてよいわけではない。確認の目的は誰も気づかない劣化を拾うことにあり、判断は人間に残す。

### やりたいこと

**事実を機械が集め、月1回、人間に届ける。判定はしない。人間は届いた表を読んで判断する。**

1. **棚卸し**: 上の版とサポート期限を月1回集めて、1つの表にして届ける
   - 使っている版はリポジトリのファイルから読む。最新版とサポート期限は、GitHub のリリース情報、endoflife.date、PyPI から取る
   - 表には事実(使っている版、最新版、サポート期限の日付、期限切れか)を並べるだけにする。「期限まで1年」のような根拠の無い数字で判定しない
   - 外部が落ちた月は、その行が「取得できず」になるだけにする
   - 振り返り(`retrospective` ラベル)のIssueの件数も載せる(半期のレビュー基準の見直しの材料)
2. **メトリクス**: mutation スコアとカバレッジを、月1回、比べられる形で届ける
   - 今の台帳は、全件を測り直した回と前回の結果を使った回の区別が記録されず、前月と正しく比べられない
   - 今の台帳は本文の書き換えで更新しており、所有者に通知が届かない
   - 全件を測り直した回どうしの差と、カバレッジの実測と基準値を並べる
3. **Dependabot に任せられるものは任せる**
   - tflint: Dependabot は Dockerfile の `FROM` の行しか読まない。`FROM` で指す書き方に直す。赤くなったときにほかのイメージの更新を巻き込まないよう、まとめPR(group)から外す
   - checkov: `RUN` の中の `pip install` は読まれない。Python の依存ファイルに移し、pip のレーンを足す

### 制約

- **週次監査を巻き込まない。** 週次監査は判定の1つでも判定不能になると全体を判定不能にし、逸脱のIssueに触らなくなる。棚卸しは別のワークフローにし、外部の失敗が既存の判定を止めないようにする
- 棚卸しが止まったことは、週次監査の既存の確認(定期実行の最終成功からの日数を見る仕組み)で見つける。見張りの仕組みを新しく増やさない
- 監査の spec(`.kiro/specs/audit-automation/requirements.md` の要件6-2)は「GitHub の API 以外の外部サービスへ問い合わせない」としている。元の理由は「外部の死活監視サービスへのデータ送信」で、製品名を送って公開情報を受け取る問い合わせは想定していなかった。この要件の改訂を所有者の承認で行う(2026-09-28、所有者了承済み)
- 届け先は、#347 で承認した Issue の通知(所有者を担当者にし、メンションを付ける)を使う。新しい通知の経路を作らない
- AIの呼び出しは行わない

### 完了したら

監査手順の定期作業の表を、「届いたIssueのコメントを読む」形に書き換える。

Refs: #310

## はじめに

この spec は、監査手順の定期作業のうち、人間の判断を含まず「調べて書き写す」だけになっている部分を機械に移す。移す対象は、ツールとランタイムの版・サポート期限の棚卸しと、mutation スコア・カバレッジの推移である。

機械は、事実を集めて月1回届けるだけで、良し悪しの判定をしない。この spec は、判定のためのしきい値(「期限まで1年」「5ポイント低下」など)を、根拠が無いため持ち込まない。人間は、届いた表を読んで、版の更新やテストの追加を判断する。この spec は、定期の確認そのものを残し、人間が配布元のサイトや台帳を開いて比べる手間を無くす。

あわせて、この spec は、Dependabot が読めない書き方になっている tflint と checkov を、Dependabot が更新できる形に改める。

この spec は、audit-automation spec の要件6-2と audit-notification spec の要件6-1(GitHub以外の外部サービスへ問い合わせない)を、棚卸しに限って改める。これらの要件の元の理由は「外部の死活監視サービスへのリポジトリの情報の送信」であり、これらの要件は、製品名を送って公開情報を受け取る問い合わせを想定していなかった(所有者了承 2026-09-28)。この spec は、週次監査とカナリア照合の問い合わせ先を変えない。

## 範囲

- この spec で決めること: 棚卸し(使っている版・最新版・サポート期限の収集と、月1回の報告)、mutation スコアの台帳への測定方式の記録と、全件測定の回どうしの差の報告、カバレッジの実測と基準値の報告、CI が main で出したカバレッジの結果の保存期間の延長、tflint と checkov の版の更新を Dependabot に任せる変更、tflint の更新PRを公開から72時間経つまでマージしない仕組み(公開日時が取れない更新と中身だけの更新は自動でマージせず所有者に知らせる)、棚卸しが止まったことの検知、監査手順の定期作業の表の書き換え、audit-automation と audit-notification の外部問い合わせの要件の改訂
- この spec で決めないこと: 版やスコアの良し悪しの判定と、それに基づく逸脱の報告・ワークフローの失敗、版の更新やテストの追加そのもの(報告を読んだ人間が指示する)、Trivy の版の更新の自動化(2本の宣言の一致は週次監査が既に確かめている)、週次監査とカナリア照合の判定基準・問い合わせ先の変更、利用量(`/usage`)の確認、AIレビューのモデルの見直し、導入直後に棚卸しを手動で1回実行して成功の記録を作ること(一度きりの作業のため、手順書ではなく実装のタスクのマージ後の確認で扱う)
- この spec が前提にしていること: 所有者がIssueの担当者に割り当てられたとき、またはメンションされたとき、GitHubの通知が所有者に届くこと(audit-notification で確認済みの経路)。Dependabot が Dockerfile の `FROM` の行と Python の依存の宣言ファイルを読み、更新のPRを作ること。mutation testing の測定そのもの(`mutation-report.yaml`)が、毎月最初の定期実行で全件を測り直すこと。CI が main でテストを実行したときに、カバレッジの値を結果として保存すること(保存の期間はこの spec で延ばす)

## 要件

### 要件1 棚卸しの収集

所有者は、Dependabot が扱わない版とサポート期限を、配布元のサイトを開かずに知りたい。人間が半期ごとに見るはずだった Docker(dind)は、サポートが切れたまま気づかれていなかったからである。

1. 棚卸しは、月に1回、次の対象について事実を集める: tflint、tflint の AWS 用ルールセット、checkov、Trivy、Java、Node.js、PostgreSQL(開発環境と本番)、Redis(開発環境)、Valkey(本番)、Terraform、Docker(dind)、LocalStack
2. 棚卸しは、対象ごとに、リポジトリに書かれている使っている版を、リポジトリのファイルから読み取る。
3. 棚卸しは、対象ごとに、配布元が公開している最新のリリースの版を、使っている系列(メジャー版)に限らずに集める。
4. 対象の配布元または公開の集約元がサポート期限を公表していれば、棚卸しは、使っている系列のサポート期限の日付と期限切れかどうか、および公開されている最新の系列を、公表されている値のまま集める。
5. 対象のサポート期限が公表されていなければ、棚卸しは、サポート期限の欄を「公表なし」とする。
6. 棚卸しは、振り返り(`retrospective` ラベル)のIssueの件数を集める。ラベルが存在しなければ、棚卸しは件数を0件とし、ラベルが無いことを併記する。
7. 棚卸しは、集めた値の良し悪しを判定せず、しきい値との比較を行わない。

### 要件2 棚卸しの届け方

所有者は、集めた事実を1つの表で受け取り、読むだけで版の更新を判断したい。

1. 事実を集め終えたら、棚卸しは、対象ごとに1行の表(対象・使っている版・書いてある場所・最新のリリースの版・使っている系列のサポート期限・期限切れかどうか・最新の系列)を作り、表の下に振り返りのIssueの件数とラベルの有無を併記する。
2. 表を作ったら、棚卸しは、決まったタイトルの台帳のIssueに、表をコメントとして追加する。
3. 棚卸しは、コメントで所有者にメンションし、台帳のIssueの担当者に所有者を割り当てる。
4. 台帳のIssueが存在しなければ、棚卸しは、決まったタイトルとラベルで台帳のIssueを作成する。
5. ある対象の最新版またはサポート期限を取得できなかったら、棚卸しは、その欄を「取得できず」とし、理由を表の下に併記したうえで、他の対象の報告を続ける。
6. 使っている版をリポジトリのファイルから読み取れなかったら、棚卸しは、その欄を「読み取れず」とし、書いてある場所を併記する。
7. 表を台帳のIssueに書けなかったら、棚卸しは、ワークフローの実行を失敗として終了する。
8. 表を台帳のIssueに書けたら、棚卸しは、取得できなかった欄の有無にかかわらず、ワークフローの実行を成功として終了する。

### 要件3 メトリクスの記録と届け方

所有者は、mutation スコアとカバレッジを、前月と正しく比べられる形で受け取りたい。今の台帳は、測り方の違う回を区別できず、更新しても所有者に通知が届かないからである。

1. mutation スコアを台帳に記録するとき、メトリクス記録は、その回が全件を測り直した回か、前回の結果を使った回かを、行ごとに記録する。
2. 全件を測り直した回の記録を終えたら、メトリクス記録は、backend と frontend それぞれについて、直前の全件を測り直した回のスコアとの差を計算する。
3. 全件を測り直した回の記録を終えたら、メトリクス記録は、今回のスコア、直前の全件の回のスコア、その差を、台帳のIssueにコメントとして追加し、所有者にメンションする。
4. メトリクス記録は、項目3で台帳のIssueに追加するコメントと同じコメントに、backend と frontend それぞれについて、main で最後にテストを実行したCIが出したカバレッジの値と、そのCIの実行の日付とコミット、その時点の基準値を並べる。メトリクス記録は、カバレッジを別に測り直さない。
5. 直前の全件を測り直した回の記録が無ければ、メトリクス記録は、差の欄を「比較対象なし」とする。
6. スコアまたはカバレッジを取得できなかったら、メトリクス記録は、その欄を「取得できず」とし、他の欄の報告を続ける。CIの結果が保存されている期間に main でテストを実行したCIが無かったときも、メトリクス記録は、カバレッジの欄を「取得できず」とし、その旨を併記する。
7. 前回の結果を使った回では、メトリクス記録は、台帳への記録だけを行い、コメントによる通知を行わない。
8. メトリクス記録は、スコアやカバレッジの良し悪しを判定せず、しきい値との比較を行わない。
9. CI が main でテストを実行したら、CI は、カバレッジの結果を、公開リポジトリで保存できる最長の期間(90日)保存する。

### 要件4 Dependabot への移管

所有者は、Dependabot が扱える形に直せる版は、Dependabot に更新のPRを作らせたい。人が見て気づくのを待つより確実だからである。

1. tflint の新しい版が公開されたら、Dependabot は、tflint の版を上げるPRを作る。
2. Dependabot は、tflint の更新を、他のベースイメージの更新とまとめたPRに含めない。
3. checkov の新しい版が公開されたら、Dependabot は、checkov の版を上げるPRを作る。
4. tflint または checkov の版を上げるPRが作られたら、CI は、terraform の静的検査をそのPRで実行する。
5. 開発環境は、tflint と checkov の版を、移管の前と同じく明示的な版の指定で固定する。開発環境は、tflint をイメージの中身の指紋(digest)でも固定し、同じ版の名前のまま中身が差し替えられても気づけるようにする。
6. tflint の更新PRの版が、公開から72時間経っていなければ、自動マージは、そのPRのマージを予約しない(Dependabot の既定の待ち期間は、tflint の置き場では効かないため)。
7. 項目6のとおり公開から72時間経っていないために予約しなかった tflint の更新PRが開いている間は、自動マージは、1日1回、公開から72時間経ったかを確かめ、経っていれば予約する。自動マージは、項目8に当たるPR(公開日時を取得できないPRと、版が変わらず中身だけが変わったPR)を、この確かめの対象にしない。
8. tflint の更新PRの版の公開日時を取得できなかったら、または版が変わらず中身(digest)だけが変わったら、自動マージは予約せず、その理由をPRにコメントし、所有者にメンションする(中身だけの変更は、公開日時で待ちを判断できず、同じ版の名前での差し替えにあたるため)。
9. 自動マージは、公開日時として、公開した側が後から書き換えられない値だけを使う。

### 要件5 止まったことの検知と既存の監査への影響

所有者は、棚卸しが止まったら気づきたい。一方で、所有者は、外部のサービスの不調で既存の週次監査が止まることを避けたい。

1. 棚卸しの成功した実行が35日以上無ければ、週次監査は、それを逸脱として報告する。
2. 棚卸しは、週次監査・カナリア照合とは別に実行する。週次監査とカナリア照合は、棚卸しの実行の失敗や外部の問い合わせの失敗を、自身の判定不能や失敗として扱わない。ただし、棚卸しの成功した実行が35日以上無いときに、週次監査がそれを逸脱として報告することは、この扱いから除く。
3. 外部のサービスへの問い合わせが失敗したら、棚卸しは、その失敗を週次監査の判定不能として扱わせない。
4. 棚卸しは、見張りの仕組みを新しく作らず、週次監査が既に行っている定期実行の最終成功日の確認に加わる。

### 要件6 外部への問い合わせと運用特性

所有者は、外部への問い合わせを解禁しても、リポジトリの情報が外に出たり、費用や保守の負担が必要以上に増えたりしないようにしたい。

1. 棚卸しは、GitHub 以外への問い合わせを、公開情報の読み取りに限る。棚卸しが送るのは製品やパッケージの名前だけであり、棚卸しはリポジトリの内容や認証情報を送らない。
2. 棚卸しは、AIの呼び出しを行わない。
3. 棚卸しは、書き込みを、台帳のIssueの作成・コメントの追加・担当者の割り当てに限る。
4. 棚卸しとメトリクス記録は、台帳のIssueを決まったタイトルで他のIssueと区別し、それ以外のIssueを操作しない。
5. 棚卸しとメトリクス記録は、収集と報告のロジックを、既存の判定スクリプトと同等の自動テストで検証できる形で持つ。
6. audit-automation spec と audit-notification spec は、外部問い合わせを禁じた要件に、この spec で棚卸しに限って改めた旨と理由を注記する。週次監査とカナリア照合については、両 spec は禁止を維持する。

### 要件7 監査手順の更新

所有者は、手順書の定期作業が、届いた報告を読む形に変わっていてほしい。

1. 監査手順書は、定期作業の表のうち、版とサポート期限の確認と、mutation スコア・カバレッジの確認を、届いた台帳のIssueのコメントを読んで判断する作業として記載する。
2. 監査手順書は、判断を人間が行うことと、しきい値を設けていないことを記載する。
3. 監査手順書は、棚卸しが止まったときは週次監査の逸脱として届くことを記載する。
