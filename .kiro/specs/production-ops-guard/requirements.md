# 要件

## 元の要望
Issue #489: AI が本番を変える操作を、コマンドの書き方によらず起動できないようにする

### きっかけ

#481 の作業中(PR #488)に AI が見つけ、所有者が起票を指示。

### 困っていること

CLAUDE.md は、本番デプロイと `terraform apply` を AI が起動しないと決めている(人間の専権)。
いまは `.claude/settings.json` の禁止の一覧で止めているが、禁止の一覧は、書いたとおりの文字の並びに当たるかどうかでしか判定しない(Claude Code の公式文書のとおり)。
そのため、同じ操作でも、コマンドの書き方を変えると禁止の一覧に当たらず、止まらないことがある。本番デプロイのワークフローの起動も同じである。

### やりたいこと

- AI が、本番を変える操作(インフラの変更と削除、本番デプロイのワークフローの起動)を、コマンドの書き方によらず起動できないようにする(AIの提案を了承)

## はじめに

CLAUDE.md は、本番デプロイと `terraform apply` を所有者だけが起動すると決めている。今、Claude がこれらを起動しないことを支えているのは、`.claude/settings.json` の禁止の一覧とフックである。どちらも Claude が書いたコマンドの文字の並びを見るだけなので、Claude が同じ操作を別の書き方で打つと、禁止の一覧とフックはその操作を止めない。

Claude が本番に届く道筋は4つある。1つ目は、所有者が `aws login` しているあいだに、所有者のPCから AWS を直接操作する道筋である。Claude は所有者と同じ Windows のユーザーで動くので、所有者のログインで得た一時的な鍵を Claude も使える。2つ目は、GitHub の本番のワークフローを起動する道筋である。Claude が使うボットの鍵は、今はワークフローの起動と承認の権限を持っている。3つ目は、所有者のPCにある所有者自身の GitHub のログイン(`gh` のログインと、git が覚えている鍵)を使う道筋である。Claude の `gh` がボットの鍵を使うのは、Claude Code の設定でボットの設定の置き場を指しているからにすぎない。Claude がこの指定を外して `gh` を打つと、所有者の名義で GitHub を操作でき、所有者は production の承認者なので、本番の実行の承認も通る。4つ目は、所有者の Chrome をログインしたまま操作する拡張(Claude in Chrome)で、GitHub や AWS のコンソールを操作する道筋である。

この spec は、4つの道筋のどれからも、Claude が単独では本番を変えられないようにする。あわせて、所有者が障害のときに自分のPCの CLI で AWS を変える手段と、所有者と Claude が AWS の状態を読んで調べる手段を残す。

## 範囲

- この spec で決めること: Claude が、AWS の本番環境と、本番を変える GitHub のワークフロー(本番デプロイの `release.yaml`、フロントエンドを戻す `frontend-rollback.yaml`、インフラを反映する `terraform-apply.yaml`)を、コマンドの書き方やブラウザの操作によらず単独では変えられないこと。所有者が本番を変える手段と、所有者と Claude が AWS の状態を読む手段が残ること。所有者が最初に1回だけ行う準備
- この spec で決めないこと: Claude in Chrome の製品そのものの動き。Claude in Chrome が所有者に許可を求める単位が1回の操作ごとでないと設計で分かったら、Claude は requirements に戻して所有者に判断を求める。本番を変えるワークフローの中身(デプロイの手順、terraform の構成)。所有者が自分の判断で、本番を変える鍵や多要素認証のコードを Claude に渡したときの扱い。所有者以外の人に本番を変える権限を渡すこと。Claude が所有者のPCの Windows の設定に意図して細工し、所有者の操作を横取りすること(要件3に書いた例外)。GitHub のワークフローの中で、Claude が書いたコードやワークフローが、リポジトリの秘密と本番の AWS の権限に触れる道の見直し(別の Issue で扱う)
- この spec が前提にしていること: GitHub の production の環境は、今のまま所有者(DogisRiki)の承認とブランチの制限を求め、AWS の OIDC の信頼ポリシーは今のまま main と production の環境を条件にする。所有者のPCの Windows は、管理者の権限を使う前に確認の画面を出す設定(ユーザーアカウント制御)のままにする。所有者は Claude Desktop を管理者として起動しない。所有者は、Claude in Chrome で github.com と AWS のコンソールに「常に許可」を出さない。所有者は、Claude Desktop の中のブラウザで GitHub と AWS にサインインしない

## 要件

### 要件1 Claude は所有者のPCから AWS を変えられない

所有者は障害の調査のために `aws login` を使い、そのあいだは Claude も同じPCで aws コマンドを打てる。今は、Claude が打つコマンドの書き方しだいで、AWS の本番を変える操作が通ってしまう。そこで、Claude が手にできる鍵そのものは、AWS を変える力を持たない。

1. Claude が所有者のPCから AWS の本番のリソースを作る・変える・消す操作をしようとしたら、AWS がその操作を拒み、本番は変わらない。所有者が `aws login` しているあいだも、AWS は同じくその操作を拒む。
2. AWS が、Claude が所有者のPCから本番のリソースを作る・変える・消す操作を拒むことは、Claude の操作の書き方によらない。書き方とは、aws コマンドのオプションの並べ方、変数やスクリプトのファイルを通した呼び出し、aws コマンド以外のプログラム(terraform や、AWS を操作するライブラリを使ったプログラム)からの呼び出し、Docker のコンテナの中からの呼び出しを指す。
3. Claude が作業フォルダのファイル、Claude Code の設定、フックを書き換えても、AWS は、Claude が所有者のPCから本番のリソースを作る・変える・消す操作を拒み続ける。
4. Claude は、所有者のPCにある所有者の普段のログインの鍵を使って、本番のデータを変えるのに使える秘密の値(データベースのパスワード、アプリが使う鍵など)を、AWS から読めない。秘密の値には、terraform の state に入っている秘密も含む。
5. AWS に操作を拒まれたら、Claude は別の書き方で同じ操作を試さず、何をしようとして拒まれたかを所有者に伝える。
6. Claude が、普段のログインの鍵から、AWS を変えられる権限へ切り替えようとしても(スイッチロール)、その場でスマホの認証アプリの6桁のコードを入れていなければ、AWS はその切り替えを拒む。
7. 例外として、所有者が `aws login` を打ってブラウザで新しくサインインした(6桁のコードを入れた)直後の1分間は、Claude が切り替えを試すと、AWS はその切り替えを通してしまう。所有者は、このすきを受け入れた。所有者が `aws login` で、すでにサインインしているマネジメントコンソールのセッションを選んだときは、このすきは生まれない。

### 要件2 所有者と Claude は AWS の状態を今までどおり読める

所有者は、障害のときに aws コマンドで AWS の状態を見て、Claude と共有しながら調べている。aws コマンドで AWS の状態を見るほうが、コンソールで見るより速いからである。Claude も、所有者のログイン中に AWS の状態を読んで調べている。止める対象は AWS を変える操作だけであり、所有者と Claude は AWS の状態を読む操作を今のまま使える。

1. 所有者が普段のターミナルで `aws login` したら、所有者と Claude は、今と同じ aws コマンドで AWS の状態を読める。所有者が普段のターミナルで行う手順は、`aws login` を打つことのまま変わらない。
2. 所有者と Claude が読める情報は、障害の調査に使う情報(リソースの状態、設定、ログ、メトリクス)である。ただし、所有者も、Claude と同じく、普段のログインでは、本番のデータを変えるのに使える秘密の値を読めない。

### 要件3 所有者は障害のときに自分のPCの CLI で AWS を変えられる

障害のときは、止まったデータベースを起動するなど、所有者がすばやく AWS を変える必要がある。所有者はコンソールが遅いので CLI を使いたい。また、`aws login` を入れたのはセキュリティを強めるためなので、その仕組みは活かしたい。一方で、所有者が AWS を変えられる鍵を Claude も読めると、Claude が手にできる鍵に AWS を変える力を持たせないという止め方が崩れる。そこで、所有者は、AWS を変えるときだけ、Claude には越えられない確認を通る。

1. 所有者が、管理者として開いたターミナルで、スマホの認証アプリの6桁のコードを入れたら、所有者はそのターミナルの aws コマンドで AWS を変えられる。管理者として開くとは、Windows がターミナルを開く前に出す確認の画面で、所有者がボタンを押すことを指す。
2. 所有者がコードを入れたあとの15分は、所有者はコードを入れ直さずに、そのターミナルで AWS を変えられる。15分を過ぎたら、所有者はコードを入れ直す。
3. 所有者が、管理者として開いたターミナルで認証アプリのコードを入れて AWS を変えられるあいだも、Claude が所有者のPCから AWS の本番のリソースを作る・変える・消す操作をしようとしたら、AWS はその操作を拒む。所有者が、管理者として開いたターミナルで認証アプリのコードを入れて得た鍵を、Claude は読めない。例外として、Claude が所有者のPCの Windows の設定(環境変数、ターミナルやシェルが起動するときに読む設定、AWS CLI の設定ファイルなど)に意図して細工したときは、この spec はその鍵を守りきれない。Claude は所有者と同じ Windows のユーザーで動き、管理者として開いたターミナルも同じユーザーの設定を読むからである。
4. 所有者が普段のターミナルで AWS を変える操作をしたら、AWS はその操作を拒む。
5. 所有者が普段のログインで AWS のマネジメントコンソールを開いたら、所有者は今と同じく AWS の状態を見られるが、AWS を変える操作は AWS が拒む。所有者がマネジメントコンソールで AWS を変えるときは、マネジメントコンソールにサインインし直し(このとき6桁のコードを入れる)、サインインしてから1分以内にスイッチロールで変更用の権限に切り替えてから操作する。1分を過ぎると AWS は切り替えを拒むので、所有者はサインインからやり直す。マネジメントコンソールのスイッチロールには6桁のコードを入れる欄が無いので、所有者はサインインのときに入れた6桁のコードで切り替える。
6. 所有者が変更用の権限に切り替えたあとも、IAM の利用者・ロール・ポリシーを作る・変える・消す操作は、AWS が拒む。所有者が IAM を変えるときは、terraform apply のワークフローか、AWS のルートユーザーで行う。変更用の権限が万一 Claude の手に渡っても、Claude が自分の権限を広げられないようにするためである。

### 要件4 Claude は本番のワークフローを起動も承認もできない

本番のジョブは所有者の承認を待つので、Claude が起動しても本番は変わらない。それでも、Claude が起動すると実行が作られ、所有者に承認の依頼が届く。これは Issue の「起動できない」を満たさない。また、Claude の鍵が承認の権限を持っていると、所有者の承認という歯止めの意味が薄れる。そこで、Claude の鍵は、ワークフローの起動と承認の権限を持たない。さらに、所有者のPCには所有者自身の GitHub のログインもあり、Claude はそれを使える。ボットの鍵だけを絞っても、Claude が所有者のログインを使えば、本番のワークフローを起動し、承認まで通せる。そこで、Claude は所有者のログインも使えない。

1. Claude が `release.yaml`、`frontend-rollback.yaml`、`terraform-apply.yaml` のどれかを起動しようとしたら、GitHub がその操作を拒み、実行は作られない。所有者に承認の依頼も届かない。
2. GitHub が、Claude が `release.yaml`、`frontend-rollback.yaml`、`terraform-apply.yaml` のどれかを起動する操作を拒むことは、Claude の操作の書き方によらない。書き方とは、`gh workflow run` のワークフローの指し方(名前・ファイル名・番号)、`gh api` や curl から GitHub の API を直接呼ぶこと、別のプログラムからの呼び出しを指す。
3. Claude は、承認を待っている本番の実行を承認できない。
4. Claude は、本番以外のワークフローも、手で起動・再実行・取り消しできなくなる。今の手順の中で、Claude がワークフローを手で起動・再実行・取り消しする場面は無い。
5. 所有者は、今と同じく、本番のワークフローを起動し、承認できる。
6. GitHub に操作を拒まれたら、Claude は別の書き方で同じ操作を試さず、何をしようとして拒まれたかを所有者に伝える。
7. Claude が、所有者のPCにある所有者自身の GitHub のログイン(`gh` のログイン、git が覚えている鍵)を使って、本番のワークフローを起動しようとしても、承認しようとしても、GitHub はその操作を拒むか、Claude はそのログインを使えない。Claude が作業フォルダのファイル、Claude Code の設定、フックを書き換えても、このことは変わらない。
8. 所有者は、同じPCで、自分の名義の `gh` と git を使い続けられる。所有者が自分の名義の `gh` を使うときの手順が今より増える場合は、増える手順を設計で示し、所有者が設計を承認するときに決める。
9. 例外として、Claude がワークフローのファイルを足すか変えて push し、そのワークフローに本番のワークフローを起動させる道は、この spec では塞がない。この道は、ワークフローの中で Claude が書いたコードが秘密と本番の権限に触れる道として、別の Issue で扱う。この道で作られた本番の実行も、所有者が承認しない限り本番を変えない。

### 要件5 Claude はブラウザで本番を変えるとき所有者の許可を要する

Claude in Chrome を使うと、Claude は所有者としてログインした GitHub と AWS のコンソールを操作できる。この道筋では、Claude は所有者本人として操作するので、所有者の承認の歯止めも越えられる。所有者は、この道筋も止める対象に入れると決めた。個人向けの Claude in Chrome には、特定のサイトでの操作を拒否する設定が無い。そこで、所有者が許可しない限り、Claude はブラウザで GitHub と AWS のコンソールを操作できない。

1. Claude が Claude in Chrome で github.com か AWS のコンソールを操作しようとしても、所有者がその操作を許可しない限り、操作は行われない。所有者が許可する単位は、1回の操作ごととする。
2. 所有者が、Claude が github.com か AWS のコンソールで行う操作を許可するかどうかを決めるときに、何の操作を許可するのかが分かるように、Claude は、許可を求める前に、どのページで何をするかを所有者に伝える。

### 要件6 Claude の今の作業は止まらない

止め方を強めた結果、Claude の毎日の作業が止まると、自律で開発する仕組みが回らなくなる。そこで、Claude の作業のうち本番を変えない作業は、今のまま動く。

1. Claude は、今と同じく、ブランチを push し、PRとIssueを作り、コメントを書き、ワークフローの実行の様子とログを読める。
2. Claude は、今と同じく、ワークフローのファイルを変えたPRを作れる。
3. Claude の品質チェック(frontend、backend、terraform の fmt・validate・tflint・checkov)は、今と同じく動く。
4. 仕組みが Claude のボットの鍵を使って動かしているワークフロー(自動マージの予約など)は、今と同じく動く。

### 要件7 所有者が最初に1回だけ行う準備を手順書で示す

止め方のうち、AWS の利用者と権限、所有者のPCの設定、Claude が GitHub を操作するときの身元と権限は、所有者しか変えられない。Claude はこれらを変える権限を持たないからである。所有者が迷わずに準備を終え、障害のときに手順を探さずに済むよう、Claude は手順を文書で示す。

1. Claude は、所有者が最初に1回だけ行う準備(AWS の利用者と権限の設定、所有者のPCの設定、Claude が GitHub を操作するときの身元と権限の作り直し)の手順を、既存の環境構築の手順書に書く。所有者は、この準備のあと、毎回の手作業を増やさない。例外は、障害のときに AWS を変える手順と、Claude がブラウザで GitHub と AWS のコンソールを操作するときの許可だけである。Claude が GitHub を操作するときの身元と権限を作り直す手段によって所有者の準備の量が変わるので、Claude は設計で、手段ごとの所有者の準備を示す。
2. Claude は、障害のときに所有者が AWS を変える手順(管理者としてターミナルを開き、コードを入れ、aws コマンドを打つ)を、所有者が障害のときに開く手順書に書く。
3. Claude は、準備が済んだあとに一度だけ行う確かめ方を、手順書ではなく、この spec を出荷するPRの本文に書く。確かめ方は、Claude が AWS を変える操作と本番のワークフローの起動を試して拒まれること、所有者が管理者として開いたターミナルで AWS を変えられることを含む。Claude が試す操作は、拒まれなかったときにも本番を変えない操作(権限があるかだけを確かめる操作など)にする。
