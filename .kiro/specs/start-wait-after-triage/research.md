# 調査の記録

## 要約

- **機能**: `start-wait-after-triage`
- **調べた範囲**: 既存の仕組みを広げる変更(Extension)として、`/start` の手順書と、着手の進み方を説明する CLAUDE.md と README の箇所、表を書く前の書き換えを止めるフック、#568 の確かめで使った場面を動かす仕組みを調べた。あわせて、判断と観点ごとの理由の表が出なかった原因を、試しの記録と所有者の着手の会話の記録で調べた
- **主な発見**:
  - 表が出るか出ないかを分けたのは、着手した Claude が「spec が要らず、所有者に尋ねる問いも無く、Issueが小さく直し方が明らかだ」と判断したかどうかである。所有者の画面を通すか(Desktop)、通さないか(`claude -p`)は、表の有無を分けていない。所有者の Desktop での着手でも、同じ条件で表が出なかった

## 決めたこと

### 決めたこと: 報告の「してほしいこと」で所有者に返事を求める

- **背景**: 表が出た着手は、どれも所有者に何かを求める報告だった。表が出なかった着手は、所有者に何も求めない報告だった
- **比べた案**:
  1. 「してほしいこと」は今のまま「何もしなくて大丈夫です」にし、止まることだけを手順に足す
  2. 「してほしいこと」を、判断を読んで返事をするよう求める文に替え、止まることを手順に足す
- **選んだ案**: 2
- **理由**: 1では、報告が所有者に何も求めないままなので、着手した Claude が報告を省いてよいものとして扱う形が残る。2は、問いがあるときとコマンドを打つ依頼のときと同じく、所有者の返事が無ければ先へ進めない報告になる
- **引き換えにすること**: 所有者は、spec の要らない小さなIssueでも、着手のたびに1回返事をする

### 決めたこと: ブランチは、所有者が進めてよいと返事をしてから作る

- **背景**: 今の手順は、spec が要らず問いも無いときは、判断を示したあとすぐにブランチを作る。問いがあるときと spec が要るときは、報告の前にブランチを作る。まとめる提案があるときは、答えを受けてからブランチを作る
- **比べた案**:
  1. 問いがあるときと同じく、報告の前にブランチを作って `session.sh claim` で記録する
  2. まとめる提案があるときと同じく、報告の前にはブランチを作らず、所有者が進めてよいと返事をしてから作る
- **選んだ案**: 2
- **理由**: 試しの F0 と G0 では、着手した Claude はブランチを作った直後に「これから書き換えます」と書いて書き換えに進んだ。報告の前にブランチを作ると、着手した Claude が実装を始めた流れのまま報告を省くおそれが残る。返事を待つ間は、Step 1.5 の `check-start` が書いた着手の予約が、ほかのセッションにIssueが作業中であることを示す(要件の「この spec が前提にしていること」)。所有者が別の進め方を指示して spec が要る判断に変わったときは、spec が要るときの手順がそのときにブランチを作る
- **引き換えにすること**: 返事を待つ間、写しの作業フォルダはブランチを作る前のブランチのままである。所有者が返事をする前に同じ作業フォルダで別の作業をしても、Issueのブランチは無い

### 決めたこと: 試しは #568 の場面を動かす仕組みで行い、合否を会話の記録と写しの状態で決める

- **背景**: 要件は、#568 の確かめと同じ条件で、小さく直し方が明らかなIssueの着手を3回させることを求める。#568 の場面を動かす仕組みは、その条件を作れる
- **比べた案**:
  1. 新しい試しの仕組みを作り、コミットする
  2. #568 の場面を動かす仕組みと E0 の題材を使い、合否を決める小さなスクリプトだけを scratchpad に足す
- **選んだ案**: 2
- **理由**: #568 の仕組みは、写しの作り方、身代わりの gh、書き込みで会話を止める方法をすでに持つ。E0 の題材は、表が出なかった側の条件で、#568 の S1 と同じIssueである。合否は、会話の記録(返答の本文の表と、ファイルを書き換えるツールの呼び出し)と、試しのあとの写しの `git status` で決める。`git status` を見るのは、着手した Claude が Bash のコマンドでファイルを書き換えたときも見落とさないためである
- **引き換えにすること**: 仕組みはコミットしないので、scratchpad が消えたら作り直す手間がかかる

### 決めたこと: フックを外した試しを先に行い、結果でフックを残すか決める

- **背景**: 要件は、フックを外した状態の3回の試しの結果で、フックを残すか取り除くかを決めることを求める
- **選んだ案**: Claude は、手順書と文書を書き換えたコミットに、フックを取り除く変更も入れる。そのコミットで3回試す。3回とも合格なら、取り除いたままにする。表の前に書き換えようとした着手があり、残りが合格なら、Claude はフックを戻し、説明の文と止めるときの文を書き換えたコミットで、もう3回試す。それ以外の結果なら、Claude は決めずに所有者に報告する
- **理由**: 場面を動かす仕組みは、コミットした文書でしか試せない。フックを外した状態を1つのコミットにしておけば、写しの中でフックが動かないことを確かめられる。フックを戻すときは、取り除いたコミットのフックのファイルと登録を元に戻すだけで済む

## 危ないことと備え

- 所有者に返事を求める報告に変えても、着手した Claude が表を省くおそれがある(原因の見立ては直に確かめていない) — 3回の試しで確かめる。合格に届かなければ、Claude は合格と書かずに所有者に報告し、所有者が決めるまで出荷しない
- 試しは `claude -p` で動かすので、所有者の Desktop の画面での動きとは違う点が残る — 会話の記録の調べで、表の有無を分けたのは画面の違いではないと分かっている。Desktop での動きは、出荷のあとの所有者のふだんの着手で見る
- 着手した Claude が、表を書いたあとに所有者の返事を待たずに進むおそれがある — 試しの合否の決め方に、返答を終えるまでに書き換えが無いことと、写しの作業の木が変わっていないことを入れる
- 試しのモデルが、所有者がふだん使うモデルと違うおそれがある — 試しは `run-scene.sh` の既定の `claude-opus-5-5` で動かし、試しの記録にモデルを書く

## この spec の範囲の外で見つけたこと

- 所有者の着手の会話の記録では、表が出た着手でも、表がブランチを作ったあとに出ることが多かった。spec が要るときと問いがあるときは、今の手順書が報告の前にブランチを作ると決めているので、この順番は手順書どおりである
- 問いに答えたあとの「返事を待たずに上の手順2から実装を始める」と、実装の途中で小さく分けるときの「何もしなくて大丈夫です」は、要件の「この spec で決めないこと」に入るので、この spec では変えない
- 所有者が判断への返事で進め方を直すよう指示したとき、Claude はその指示をIssueの本文の「決めた方式」に書き足さない。file-issue の決まりが、着手のときにIssueの本文を書き換えてよい場合を、`/start` の問いへの答えを書き足すときと、まとめるときの2つに限っているためである。実装の途中で所有者が指示を出したとき(`/start` の SKILL.md の Step 8)も同じである。codex-review はIssueの本文だけを判定の基準にするので、所有者の指示に沿って作った変更が、Issueの本文と食い違うと判定されるおそれがある。この spec では file-issue の決まりを変えない
