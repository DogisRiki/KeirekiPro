# 要件

## 元の要望
Issue #662: Spring Boot を 4 系の最新に上げて、本番のコンテナイメージから CRITICAL の脆弱性を無くす

### きっかけ

所有者は、バックエンドを Python に移す予定を持っていた。しかし所有者は、本番の backend のコンテナイメージに出ている深刻度 CRITICAL の脆弱性を放置できないと考え、Spring Boot を 4 系の最新に上げることを求めた。

### 困っていること

- 本番の backend のコンテナイメージには、深刻度 CRITICAL の脆弱性が2件含まれている。2件は #525 と #562 である。所有者は、この2件を放置できない

### やりたいこと

- Claude は、backend の Spring Boot を 4 系の最新に上げる
- Claude は、上げる先を 4.1 系の最新の正式版にする。Claude は、4.2 系の正式版が出るのを待たない。(AIの提案を了承)
- Claude は、backend のほかの部品も、上げられるものはすべて最新の版に上げる。(AIの提案を了承)
- Claude は、backend を組み立てる道具である Gradle も、最新の版に上げる。(AIの提案を了承)
- Claude は、コンテナの脆弱性検査が2件を見逃すための設定を、同じ変更の中で消す。(AIの提案を了承)

### どうなれば解決か

- 今ある道具と CI は、上げたあとも、今と同じように確実に動く
- アプリの動きは、上げる前と一切変わらない
- 今あるテストと品質チェックは、上げたあとに、すべて通る。(AIの提案を了承)
- API は、上げたあとも、同じ入力に対して、上げる前と同じ応答を返す。(AIの提案を了承)
- アプリが出力する PDF と Markdown は、上げたあとも、同じ入力に対して、上げる前と同じ中身になる。(AIの提案を了承)
- コンテナの脆弱性検査は、上げたあとの backend のコンテナイメージを調べたときに、#525 と #562 の2件を検出しない。Claude は、2件を見逃すための設定を消した状態で、この検査を行う。(AIの提案を了承)

### やらないこと

- Claude は、Java の版を上げない
- Claude は、frontend と terraform の部品の版を上げない。(AIの提案を了承)


### 決めた方式

- Claude は、backend の品質チェックの道具(checkstyle、spotbugs、pmd、jacoco、pitest の JUnit 用の部品)の版と、その設定も最新に上げる。新しい版の道具が今のコードに新しい指摘を出したときは、Claude はアプリの動きを変えずに書き方を直す。(AIの提案を了承)

## はじめに

本番の backend のコンテナイメージには、深刻度 CRITICAL の脆弱性が2件含まれている。2件は #525 と #562 であり、どちらも Spring Boot 3 系が使う部品の古い版に含まれている。今は、コンテナの脆弱性検査が2件を見逃す設定が入っているので、コンテナの脆弱性検査は通っている。

この spec は、Claude が backend の Spring Boot を 4.1 系の最新の正式版に上げるときに守ることを決める。Claude は、あわせて、backend のほかの部品と、backend を組み立てる道具の Gradle と、backend の品質チェックの道具も、最新の版に上げる。この spec では、部品や道具を新しい版に替えることを「上げる」と呼ぶ。

上げたあとも、利用者と所有者から見えるアプリの動きは、上げる前と変わらない。

## 範囲

- この spec で決めること: 次の3つである。
  - backend の部品、Gradle、品質チェックの道具を、どの版に上げるか
  - 上げたあとも、API の応答、出力するファイルとメール、本番の運用から見える動き、保存されたデータの読み書き、開発の道具と CI が、上げる前と変わらないこと
  - コンテナの脆弱性検査が2件を見逃す設定を消すこと
- この spec で決めないこと: 次の4つである。
  - Java の版
  - frontend と terraform の部品の版
  - 本番へのデプロイ。デプロイは所有者が行う
  - 2件のほかの脆弱性を、コンテナの脆弱性検査が見逃す設定を足すかどうか。2件のほかの脆弱性とは、上げたあとの本番の backend のコンテナイメージで、コンテナの脆弱性検査が2件のほかに見つけた脆弱性である。足すかどうかは所有者が決める
- この spec が前提にしていること: 次の2つである。
  - この変更は、backend の組み立ての設定、品質チェックの設定、CI の設定を変える。そのため、この変更の PR は、所有者が承認するまで自動ではマージされない
  - backend は、ログインの状態を、利用者のブラウザが持つ署名付きの値と、一時的な保存先に文字列で書いた値で保っている。backend は、ログインの状態をサーバのセッションには保存していない

## 要件

### 要件1 backend の部品と道具を最新の版に上げる

2件の脆弱性は、Spring Boot 3 系が使う部品の古い版に含まれている。所有者は、Spring Boot を 4.1 系の最新に上げるだけでなく、ほかの部品と道具も上げられるものはすべて最新にすることを了承した。ただし、Spring Boot が版をまとめて決めている部品の版は、Spring Boot の開発者が、組み合わせて動くことを確かめた版である。`backend/gradle/libs.versions.toml` の注記にも、Spring Boot が決めた版から外すのは脆弱性を直すときだけにすると書いてある。そこで、Claude は、Spring Boot が版を決めている部品を Spring Boot が決めた版に合わせ、それ以外の部品と道具を最新の版に上げる。

1. Claude は、backend の Spring Boot を、4.1 系の正式版のうち最も新しい版に上げる。Claude は、4.2 系の版を使わない。Claude は、正式版の前に出る試しの版も使わない。
2. この spec で「最も新しい正式版」とは、Claude が版を決める時点で、公開から72時間を過ぎた正式版のうち最も新しい版を指す。Claude が公開から72時間を過ぎた版に限るのは、このリポジトリの必須の検査が、公開から72時間たっていない版を使う変更を止めるためである。Claude は、版を決めた日を PR の本文に書く。版を決めたあとに新しい版が公開されても、Claude は、その版に上げ直さない。ただし、版を決めたあとに、使う版の既知の脆弱性が見つかることがある。そのときは、Claude は、既知の脆弱性がある部品だけを直した版に上げるこの要件の決まりか、コンテナの脆弱性検査が2件のほかに見つけた脆弱性をまず部品の版を上げて直す要件8の決まりに従い、その部品を、版を決めた日のあとに公開された直した版にも上げる。その版も、公開から72時間を過ぎた版に限る。
3. この spec で「backend の部品」とは、`backend/gradle/libs.versions.toml` と `backend/build.gradle` に宣言した部品とプラグインを指す。プラグインとは、Gradle に足している機能の部品である。宣言した部品が引き込む部品とは、宣言した部品が動くために要る部品として、Gradle が一緒に取り込む部品を指す。Claude は、宣言した部品が引き込む部品の版を、引き込む側の部品が決めた版に従わせる。
4. Spring Boot が版をまとめて決めている部品については、Claude は、上げた Spring Boot が決めた版を使う。Spring Boot と、ほかの部品の両方が版を決めている部品も、Claude は Spring Boot が決めた版に従わせる。ただし、Spring Boot が決めた版に既知の脆弱性があり、その脆弱性を直した版が出ているときは、Claude は、その部品だけを直した版に上げる。宣言した部品が引き込む部品に既知の脆弱性があるときも、Claude は同じく、その部品だけを直した版に上げる。
5. Spring Boot が版を決めていない backend の部品については、Claude は、それぞれの最も新しい正式版に上げる。Claude は、Gradle も最も新しい正式版に上げる。Spring Boot のほかにも、自分が引き込む部品の版をまとめて決める部品がある。たとえば、Spring Cloud AWS は、AWS の部品の版を決めている。Claude は、そうした部品が引き込む部品の版を、その部品が決めた版に従わせる。
6. 部品の作り手が更新をやめ、別の作り手がその部品を引き継いで、別の名前で出していることがある。たとえば、PDF を作る部品の openhtmltopdf がそうである。Claude は、別の作り手が引き継いだ部品に移らない。Claude は、今と同じ名前の部品のうち、最も新しい正式版に上げる。引き継いだ部品は、別の作り手が直した別の部品である。そのため、Claude が引き継いだ部品に移ると、PDF の出力のような backend の動きが変わるおそれが大きい。Claude が移らないのは、このおそれがあるためである。一方、同じ作り手が部品の名前を改めたときは、Claude は、新しい名前の部品に移る。Spring Boot 4 と、Spring Boot 4 が版を決める部品には、名前を改めたものがある。新しい名前の部品に移ったときも、API の応答、PDF と Markdown とメールの中身、本番の運用から見える動き、保存されたデータの読み書きは、上げる前と同じである。
7. Claude は、backend の品質チェックの道具を、それぞれの最も新しい正式版に上げる。品質チェックの道具とは、checkstyle、spotbugs、pmd、jacoco、pitest の JUnit 用の部品の5つである。
8. 品質チェックの設定のファイルのうち、道具の配布元が配っているファイルを写して使っているものは、Claude が、上げた版の配布元が配っているファイルに替える。今そうしているファイルは、checkstyle の `google_checks.xml` である。このリポジトリが写したあとに加えた変更があれば、Claude は、その変更を替えたあとのファイルにも入れる。上げる前のファイルにあった規則を、上げた版の配布元が外していたときは、Claude は、その規則を替えたあとのファイルに残す。
9. 品質チェックの設定のファイルのうち、このリポジトリが自分で書いたものは、Claude が、上げた版で書き方が変わったときだけ書き直す。品質チェックの道具は、書き直したあとの設定で、上げる前と同じか、それより厳しい検査をする。
10. Claude は、最も新しい版では動かない部品や道具を、組み合わせて動く版のうち最も新しい版に止める。最も新しい版では動かないとは、最も新しい版に上げると、Java 21 で動かないか、ほかの部品や道具と組み合わせて動かないことを指す。Claude は、止めた部品や道具ごとに、止めた版と止めた理由を PR の本文に書く。
11. Claude は、Java の版を 21 のまま変えない。Claude は、frontend と terraform の部品の版を変えない。
12. Claude は、版を変えた部品と道具ごとに、上げる前の版と上げたあとの版を PR の本文に書く。

### 要件2 API は上げる前と同じ応答を返す

frontend と、API を呼ぶ利用者は、今の応答の形を前提に動いている。所有者は、上げたあとも同じ入力に同じ応答が返ることを求めた。Spring Boot 4 では、JSON を読み書きする部品が新しい系統に替わる。Claude が何も対策をしないと、新しい系統の部品は、JSON の項目の並び順や、値が空の項目の扱いを変える。

1. backend は、上げたあとも、同じ要求に対して、上げる前と同じ状態コードと、同じ中身の応答を返す。応答の中身が同じとは、JSON の項目の名前、項目の並び順、値の書き方、値が空の項目を出すか出さないか、応答のヘッダが、すべて同じであることを指す。応答のヘッダとは、応答に付く付帯の情報で、ダウンロードするファイルの名前を含む。値の書き方には、日付と時刻の書き方を含む。
2. 上げる前の backend どうしでも要求のたびに変わる値は、Claude が、上げる前と同じかを比べる対象から外す。そうした値には、応答した日時を示すヘッダ、ログインやログインの延長で発行する Cookie の値、署名と期限を含む一時的な URL がある。Claude は、外した値については、次のことが上げる前と同じかを比べる。
   - Cookie: 名前と属性
   - 署名と期限を含む一時的な URL: 行き先のファイルと、その URL でファイルを取得できること
   - そのほかの値: 値が入る項目と、値の形
3. backend は、上げたあとも、上げる前に受け付けていた要求を同じように受け付ける。backend は、上げる前に断っていた要求を、上げたあとも同じ状態コードと同じエラーの中身で断る。たとえば、値が空の項目を含む要求と、JSON のあとに余分な文字が続く要求も、backend は上げる前と同じように扱う。
4. backend がエラーの応答に載せる文言は、上げたあとも、上げる前と同じ日本語の文言である。
5. backend が応答する URL と HTTP メソッドの組は、上げたあとも、上げる前と同じである。HTTP メソッドとは、GET や POST のような要求の種類である。上げたことで、backend が新しい URL に応答し始めることはない。
6. ログインとログアウトの流れは、上げたあとも、上げる前と同じである。この流れには、外部のサービスのアカウントでログインする流れと、2段階の認証を含む。backend が返す Cookie の名前と属性も、上げる前と同じである。
7. ブラウザがほかのサイトの画面から backend を呼ぶことを、backend が許す範囲は、上げたあとも、上げる前と同じである。

### 要件3 PDF と Markdown とメールは上げる前と同じ中身になる

利用者は、職務経歴書の PDF と Markdown を、応募先への提出に使う。今のテストは、PDF と Markdown を作る部品を、テスト用の偽物に差し替えて動かしている。そのため、今のテストが通っても、上げたあとの出力が上げる前と同じであることは確かめられない。backend は、メールを文面の型から作る。そのため、型を読む部品が替わると、メールの文面が変わるおそれがある。

1. backend は、上げたあとも、同じ職務経歴書から、上げる前と同じ見た目の PDF を出力する。同じ見た目とは、ページの数と、各ページに描かれる文字・線・画像とそれらの位置が、すべて同じであることを指す。PDF のファイルに書き込まれる作成日時は、出力するたびに変わるので、Claude は比べる対象にしない。
2. backend は、上げたあとも、同じ職務経歴書から、上げる前と1文字も違わない Markdown を出力する。
3. backend が送るメールは、上げたあとも、上げる前と同じ差出人、件名、本文になる。

### 要件4 本番の運用から見える動きを変えない

所有者は、本番の backend のログと、backend が動いているかどうかの確認の結果を、今の形のまま読んで運用している。Spring Boot 4 は、ログの設定の名前の一部と、いくつかの機能の既定の動きを変える。Claude が何も対策をしないと、backend は、上げる前には外部に送っていなかった記録を送り始めるおそれがある。

1. backend は、上げたあとも、上げる前と同じ項目名と同じ形式でログを出力する。backend は、ログに付く処理の追跡の番号も、上げる前と同じ項目名(`trace.id` と `span.id`)で出力する。
2. 本番の backend は、上げたあとも、動いているかどうかの確認の URL に対して、上げる前と同じく、動いているかどうかだけを返す。本番の backend は、その URL で、中の詳しい情報を返さない。
3. backend は、上げたあとも、処理の追跡の記録を外部に送らない。上げる前の backend も、追跡の記録を外部に送っていない。
4. 本番の backend は、上げたあとも、上げる前と同じ本番の設定のまま起動する。本番の設定には、秘密の値の読み込みと、データベースと一時的な保存先への接続を含む。
5. 本番の backend は、止めるように指示されたときに、上げる前と同じく、処理中の要求を終えてから止まる。

### 要件5 保存されたデータを上げる前と上げたあとの両方で読み書きできる

上げた版を本番に出したあとに不具合が見つかると、所有者は、PR を取り消して前の版に戻すことがある。所有者は、上げた版を出したときと、前の版に戻したときのどちらでも、利用者のデータを失わず、利用者にログインし直させずに済ませたい。

1. Claude は、データベースの表の形を変えない。上げた backend は、上げる前の backend が作った表とデータを、そのまま読み書きする。
2. 上げた backend は、データベースの変更の履歴を記録する表も、上げる前の backend が読める形のまま使う。データベースの変更の履歴とは、どの変更をいつデータベースに当てたかの記録である。
3. 上げた backend は、上げる前の backend が一時的な保存先に書いた値を読める。上げる前の backend も、上げた backend が一時的な保存先に書いた値を読める。一時的な保存先の値には、ログインの状態を保つための値と、メールで送った確認の番号を含む。
4. ログインしている利用者は、上げた版を出したときと、前の版に戻したときのどちらでも、ログインし直さずに使い続けられる。

### 要件6 開発の道具と CI を上げる前と同じように使える

所有者と Claude は、開発用のコンテナと、品質チェックのコマンドと、CI で、backend の変更を確かめている。上げたことでこれらが動かなくなると、Claude は以後の backend の変更を確かめられなくなる。

1. 開発用のコンテナの中で backend を起動するコマンドは、上げたあとも、上げる前と同じコマンドのまま動く。
2. backend の品質チェックのコマンドは、上げたあとも、上げる前と同じコマンドのまま動き、上げる前と同じか、それより多い種類の検査を行う。
3. 上げたあとの PR では、CI の backend に関わるジョブがすべて成功する。ただし、所有者の承認を待つ検査は、所有者が承認するまで成功にならない。
4. 本番のコンテナイメージを組み立てる手順は、上げたあとも、上げる前と同じ手順のまま成功する。組み立てたイメージは、Java 21 で backend を起動する。
5. 週に1回の変異テストは、上げたあとも、上げる前と同じ対象のクラスについて結果を出す。変異テストとは、コードをわざと少し変えて、今のテストがその変化を見つけられるかを確かめる検査である。

### 要件7 品質チェックの基準を下げない

このリポジトリでは、人間はコードを読まない。コードの品質は、自動の検査が担保している。所有者は、品質チェックの道具を上げたときに新しい指摘が出たら、アプリの動きを変えずにコードの書き方を直すと決めた。Claude が検査を緩めてコードを検査に通すと、自動の検査は品質を担保しなくなる。

1. Claude は、品質チェックの基準を、上げる前より緩めない。品質チェックの基準とは、テストが通るコードの割合の下限と、検査の規則の種類と、規則ごとの厳しさである。
2. 新しい版の道具が今のコードに新しい指摘を出したときは、Claude は、アプリの動きを変えずにコードの書き方を直して、指摘を無くす。Claude は、指摘を検査から外す設定を足して、指摘を消さない。
3. 今あるテストは、上げたあとに、すべて通る。Claude は、テストのコードを、新しい版の部品の書き方に合わせて直してよい。ただし、Claude は、テストを消すことも、テストを飛ばす設定を足すことも、テストが確かめる内容を減らすこともしない。

### 要件8 コンテナの脆弱性検査が2件を検出しなくなる

今は、コンテナの脆弱性検査が2件を見逃す設定が入っているので、コンテナの脆弱性検査は通っている。所有者は、2件を見逃すのではなく、2件を無くすことを求めた。

1. Claude は、コンテナの脆弱性検査が #525 と #562 の2件を見逃すための設定を、上げる変更と同じ PR の中で消す。
2. コンテナの脆弱性検査は、2件を見逃す設定を消した状態で、上げたあとの本番のコンテナイメージを調べたときに、2件を検出しない。

### 要件9 上げる前と同じであることを確かめた結果を所有者に示す

今のテストだけでは、PDF の見た目のように、上げる前と同じであることを確かめられない動きがある。所有者はコードを読まないので、上げる前と同じであることの根拠を、PR の本文で読めるようにしたい。

1. Claude は、上げる前と同じにすると決めた動きごとに、確かめた方法と結果を PR の本文に書く。上げる前と同じにすると決めた動きとは、API の応答、PDF と Markdown とメールの中身、本番の運用から見える動き、保存されたデータの読み書きである。
2. PDF と Markdown については、Claude は、同じ職務経歴書を、上げる前の版と上げたあとの版の両方で出力して比べる。比べる職務経歴書には、すべての項目を埋めたものと、埋めなくてよい項目を空にしたものを含める。Claude は、比べた結果を PR の本文に書く。
3. 確かめた結果が、この spec の要件のどれかに届かないときは、Claude は、合格と書かない。Claude は、届かない要件と、上げる前との違いと、その違いでも Issue の目的を満たすと考える理由を、PR の本文と所有者への報告に書く。所有者が合否を決めるまで、Claude は出荷しない。
