## はじめに

Issue #445 で、所有者は、backend を Java と Spring Boot から Go に置き換えると決めた。置き換えの進め方と、Go 版が守ることは、spec `backend-go-replacement` が決めている。この spec では、spec `backend-go-replacement` を「置き換えの spec」と呼ぶ。置き換えの spec は、機能のまとまりごとの Go 版を、まとまりごとの別の spec で作ると決めた。この spec は、そのうちバックアップのまとまりを受け持つ。Claude は、この spec で、Issue #774 の「やりたいこと」に挙げた2つの操作の Go 版を作る。今の Go 版は、この2つの操作の要求に、未実装であることを示す答えを返す。

2つの操作は、次のように働く。

- バックアップの書き出し: GET の操作である。Java 版は、利用者の1つの経歴書の中身を JSON のファイルにして、ファイルを保存させる答えを返す。画面は、利用者がバックアップの画面で経歴書を選んで書き出すときに、この操作を使う。画面は、答えの Content-Disposition のヘッダからファイルの名前を取り、利用者のパソコンにファイルを保存する
- バックアップの戻し: POST の操作である。Java 版は、要求の本文のバックアップから、要求を送った利用者の新しい経歴書を作り、状態の番号 201 と、作った経歴書の情報で答える。画面は、利用者がバックアップの画面で拡張子 `.json` のファイルを選んで戻すときに、この操作を使う。画面は、選んだファイルの中身を JSON として読み、読んだ値をそのまま要求の本文にして送る。戻しが成功すると、画面は、作った経歴書の編集の画面に移る

この spec の「所有者」「Java 版」「Go 版」「利用者」「画面」「切り替え」は、置き換えの spec と同じものを指す。「バックアップのファイル」は、書き出しの操作が答えの本文として返し、利用者のパソコンに保存されるファイルを指す。「筋書き」は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査が、版に送る要求の並びと、期待する答えを書いたものを指す。「項目」は、経歴書の1つの欄に入れた1件の記録を指す。経歴書の欄は、職歴、プロジェクト、資格、ポートフォリオ、SNS、自己PR の6つである。

Issue #774 の「どうなれば解決か」は、2つの操作について、置き換えの spec の18の受入基準を満たすことを求めている。置き換えの spec は、まとまりごとの spec に置き換えの spec の要件を書き写さず、当てはまる要件を指すと決めている。そこで、この spec は、18の受入基準のそれぞれを、次の表のとおりに受け持つ。表で「置き換えの spec のとおり」とした受入基準は、2つの操作に固有の決めごとが無い。Claude は、その受入基準を、置き換えの spec の文のとおりに2つの操作に当てはめる。

## 範囲

- この spec で決めること: この spec では、次の3つを決める。
  - バックアップの書き出しと戻しの Go 版
  - ほかの利用者の経歴書の書き出しの要求と、退会してすでに居ない利用者の要求に、Go 版が返す答え
  - 2つの操作について、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査に足す筋書き
- この spec で決めないこと: この spec では、次の5つを決めない。
  - ほかのまとまりの操作の Go 版
  - ログインの状態の検査と、偽の送信の検査。Claude は、認証のまとまりの spec `backend-go-auth` で作った検査を、作り直さずにそのまま使う
  - 機能を足すことと、仕様を変えること。Issue #445 の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである。たとえば、形の誤ったバックアップのファイルに今より分かりやすいエラーの文言を返すことは、仕様を変えることなので、この spec では扱わない
  - バックアップのファイルの版を上げること。Go 版が書き出すバックアップのファイルの版は、Java 版と同じ `1.0` のままとする
  - 本番の切り替え。本番の切り替えは、置き換えの spec が受け持つ
- この spec が前提にしていること: この spec は、次の5つを前提にする。
  - 置き換えの spec の段階2で、Go 版の土台と、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査と、今の Java 版から作った API の仕様書が作られ、main に入っている。API の仕様書には、2つの操作も書かれている
  - 認証、利用者、マスタと経歴書、出力のまとまりの Go 版は、main に入っている。マスタと経歴書のまとまりの Go 版は、経歴書と6つの欄の項目を読み書きし、経歴書を作るときに、作れる経歴書の数の上限と、経歴書の名前の重なりを確かめる
  - 置き換えの spec の段階1で、Claude は、Java 版が書き出したバックアップのファイルを Go で読んで書き直し、書き直したファイルを Java 版が状態の番号 201 で戻せることを確かめた。Claude は、そのとき、Go 版がバックアップのファイルを戻す処理と、バックアップのファイルの版を確かめる処理を、Go で試しに作らなかった
  - 置き換えの spec の段階1で、Claude は、Java 版が書き出すバックアップのファイルと、Go の標準の書き方で書いたファイルでは、`<` `>` `&` と、行や段落の区切りを表す一部の文字の書き方が違うことを確かめた。書き方とは、文字をそのまま書くか、`\u003c` のように番号で書くかの違いである。どちらの書き方でも、JSON として読んだ文字は同じになる
  - Java 版のバックアップの書き出しは、データベースから読んだ項目を、並べる順を指定せずに読んで、そのまま書く。そのため、Java 版のファイルの中の項目の並びは、データベースの中の行の置かれ方で変わる。Claude は、要件8の受入基準1で2つの操作の動きを試しに作ったときに、同じファイルを Java 版で2回戻してそれぞれを書き出すと、プロジェクトの並びが2つのファイルで違うことと、開発環境の見本の経歴書を書き出すと、項目が画面に出る順の逆に並ぶことを確かめた。画面と PDF は、経歴書を読み出すときに項目を決まった順に並べ替えるので、画面と PDF に出る項目の並びは、データベースの中の行の置かれ方で変わらない。変えた動きの一覧には、経歴書の中の項目を名前で並べる順の違いが、所有者が受け入れた違いとして載っている。Go 版は、ポートフォリオ、SNS、自己PR の項目を、Go の標準の日本語の並び順で並べる

## 要件

### 要件1 書き出しと戻しを、今の画面を直さずに Go 版で使えるようにする

切り替えのあとも、利用者は、今の画面で経歴書のバックアップを書き出して手元に持ち、必要なときに戻す。画面は、保存するファイルの名前を、答えの Content-Disposition のヘッダから取る。また、画面は、答えの状態の番号で、利用者に見せるものを変える。状態の番号が 400 か 404 のときは、画面は、答えの本文のエラーの文言を見せる。状態の番号が 500 のときは、画面は、答えの本文を使わず、決まったサーバの誤りの知らせを見せる。そのため、Go 版の答えの状態の番号かヘッダが Java 版と違うと、利用者は、違う名前のファイルを受け取るか、違うエラーを見る。そこで、Go 版は、2つの操作で画面が送る要求に、Java 版と同じ答えを返す。

戻しの操作では、画面は、利用者が選んだファイルの中身を確かめずに送る。そのため、画面が送る要求には、どちらの版も書き出していない、形の誤ったファイルから作った要求も含まれる。Java 版は、そのような要求の一部に、サーバの誤りとして状態の番号 500 で答える。置き換えの spec の設計は、Java 版が 500 で答える要求のうち、画面が送る要求には、Go 版が Java 版と同じ答えを返すと決めた。Go 版が 500 を 400 に変えると、利用者は、決まったサーバの誤りの知らせの代わりにエラーの文言を見ることになり、利用者が見るものが変わるためである。

1. Go 版は、2つの操作の次の要求に、Java 版と同じ HTTP の状態の番号と、同じ Content-Type のヘッダと、同じ答えの本文で答える。書き出しの要求には、Go 版は、Java 版と同じ Content-Disposition のヘッダでも答える。答えの本文が同じかどうかは、書き出しの成功の答えではバックアップのファイルを決めた要件3が、戻しの成功の答えでは戻した経歴書を決めた要件2が、エラーの答えでは断る条件とエラーの文言を決めた要件4が決める。同じかどうかの正解は、今の Java 版が実際に返す答えとする。
   - 書き出しで、Accept のヘッダを `application/json` にし、経歴書の ID の場所に ID の形の文字を入れた要求
   - 戻しで、利用者が選んだ、拡張子が `.json` で中身を JSON として読めるファイルから、画面が作って送る要求。ファイルの中身は、どの形でもよい。たとえば、Java 版か Go 版が書き出したファイル、項目の欠けたファイル、値の型の違うファイル、知らない名前の欄を持つファイル、中身が JSON のオブジェクトでなく配列や数のファイルから作った要求も、この要求に含まれる。Java 版がこの要求にサーバの誤りとして状態の番号 500 で答えるときも、Go 版は、同じ状態の番号 500 と、同じ答えの本文で答える。ただし、この要求が、受入基準2に書いた、退会してすでに居ない利用者のログインの状態を持つ要求に当たるときは、Go 版は、受入基準2の2つ目の例外に従う
2. 受入基準1で、Go 版が Java 版と同じ答えを返すと決めた原則には、次の2つの例外がある。
   - Go 版は、受入基準1に挙げた2つの要求のほかの要求には、Java 版と違う答えを返してよい。受入基準1に挙げた2つの要求は、書き出しで Accept のヘッダを `application/json` にし、経歴書の ID の場所に ID の形の文字を入れた要求と、戻しで、利用者が選んだ、拡張子が `.json` で中身を JSON として読めるファイルから画面が作って送る要求である。この2つの要求のほかの要求は、たとえば、書き出しで Accept のヘッダに `application/json` の無い要求、書き出しで経歴書の ID の場所に ID の形でない文字を入れた要求、戻しで本文が JSON として読めない要求、戻しで Content-Type のヘッダが JSON でない要求である。画面は、このような要求を送らない。Claude は、Java 版と答えが変わる要求を、変えた動きの一覧に載せる
   - 退会してすでに居ない利用者のログインの状態を持つ要求には、Go 版は、退会してすでに居ない利用者の要求への答えを決めた要件5の受入基準3のとおりに答える。Java 版がこの要求に状態の番号 500 で答えるときは、この例外が受入基準1の文より優先する
3. 利用者は、今の画面で、Go 版を相手に、次の2つを終えられる。
   - 経歴書のバックアップを書き出し、Java 版と同じ名前のファイルとして保存すること
   - 保存したバックアップのファイルを戻し、戻した経歴書の編集の画面に移ること。ただし、利用者が作れる経歴書の数の上限に達しているときと、ファイルの中の経歴書と同じ名前の経歴書を利用者が持っているときは、Go 版は、要件4の受入基準3と4のとおりに戻しを断る

### 要件2 戻した経歴書を、Java 版で戻した経歴書と同じにする

利用者は、置き換えの前に Java 版で書き出したバックアップのファイルを手元に持っている。置き換えのあとにそのファイルを戻して、Java 版で戻したときと違う経歴書ができると、利用者は、戻した経歴書を確かめ直して直さなければならない。そこで、Go 版は、Java 版と同じ経歴書を作る。

1. 利用者が、Java 版が状態の番号 201 で戻すバックアップのファイルを Go 版で戻したら、Go 版は、Java 版が同じファイルを戻したときと同じ経歴書を作る。同じ経歴書とは、経歴書の名前、日付、姓、名と、6つの欄の項目と、それぞれの項目の値と、項目の数が同じ経歴書である。Java 版が状態の番号 201 で戻すバックアップのファイルには、Java 版が書き出したファイルも、Go 版が書き出したファイルも含まれる。経歴書と項目の ID と、作った日時と直した日時は、戻した時に新しく決まるので、同じでなくてよい。
2. ファイルの中に無い欄と値を、Go 版は、Java 版と同じに補う。たとえば、Java 版は、6つの欄のどれかが無いファイルでは、その欄を項目の無い欄として戻す。プロジェクトの工程が無いファイルでは、すべての工程を選んでいないものとして戻す。プロジェクトの技術が無いファイルでは、技術を選んでいないものとして戻す。姓と名の両方が無いか空のファイルでは、氏名の無い経歴書として戻す。
3. Go 版が作った経歴書は、要求を送った利用者の経歴書になる。

### 要件3 書き出すバックアップのファイルを、Java 版と同じにする

所有者が本番を Java 版に戻したとき、利用者は、Go 版で書き出したバックアップのファイルを Java 版で戻す。ファイルの形が Java 版と違うと、Java 版がそのファイルを戻せないか、違う経歴書を作る。また、利用者は、手元のファイルをテキストエディタで開いて、中身を見ることがある。そのとき、Go 版のファイルの文字の書き方が Java 版と違うと、利用者は、Java 版で書き出したファイルと違う文字の並びを見る。そこで、Go 版は、書き出すバックアップのファイルを、Java 版と同じにする。

1. Go 版は、バックアップのファイルに、Java 版と同じ名前の欄を、同じ並びで書き、同じ値を入れる。Go 版は、Java 版が書かない欄を、Java 版と同じく書かない。Java 版が書かない欄は、たとえば、入っていない姓と名、終わりの年月の無い職歴とプロジェクト、項目の無い欄である。Go 版は、ファイルの版を `1.0` と書き、書き出した日時を世界標準時で書く。書き出した日時は、書き出した時刻で決まるので、Java 版と同じでなくてよい。
2. Go 版は、バックアップのファイルの中の項目を、経歴書を読み出すときと同じ順に並べる。つまり、ファイルの中の項目は、画面に出る項目と同じ順に並ぶ。範囲の前提に書いたとおり、Java 版のファイルの中の項目の並びは、データベースの中の行の置かれ方で変わり、1つに決まらない。そこで、Go 版のファイルの中の項目の並びは、Java 版のファイルの並びと違ってよい。この違いは、置き換えの spec の要件11の受入基準2が例外とした、名前で並べる順の違いに含まれない。また、利用者は、ファイルをテキストエディタで開いたときに、この違いを目にする。そのため、この違いは、置き換えの spec の要件9の受入基準9の、所有者が受け入れた違いに当たる。所有者は、この requirements を承認することで、この違いを受け入れる。Claude は、この違いを変えた動きの一覧に載せ、一覧の「画面に影響が無い理由」に、バックアップのファイルの中の6つの欄の項目の並びが変わることと、所有者が受け入れた日を書く。
3. Go 版は、バックアップのファイルの文字を、Java 版と同じ書き方で書く。Java 版がそのまま書く文字を、Go 版もそのまま書く。Java 版が番号で書く文字を、Go 版も番号で書く。利用者がバックアップのファイルをテキストエディタで開いたとき、Go 版のファイルの文字の並びは、受入基準1で違ってよいとした書き出した日時と、受入基準2で違ってよいとした項目の並びのほかは、Java 版のファイルと同じになる。
4. Go 版は、答えの Content-Disposition のヘッダのファイル名を、Java 版と同じ規則で、経歴書の名前から作る。経歴書の名前が日本語のときと、ファイル名に使えない文字を含むときも、ヘッダの文字は Java 版と同じになる。

### 要件4 戻しで断る条件と、画面に出るエラーの文言を、Java 版と同じにする

戻しに失敗すると、画面は、backend が答えに入れたエラーの文言を利用者に見せる。利用者は、その文言を読んで、別のファイルを選ぶか、経歴書を減らすか、経歴書の名前を変えるかを決める。Go 版の文言が Java 版と違うと、利用者は、何をすればよいかを今と同じように読み取れない。Go 版が Java 版より緩く断ると、Java 版では戻せない経歴書が作られる。Go 版が Java 版より厳しく断ると、利用者は、今は戻せるファイルを戻せなくなる。そこで、Go 版は、断る条件と、確かめる順と、エラーの文言を、Java 版と同じにする。

1. Go 版は、Java 版と同じく、次の順で戻しの要求を確かめる。1つの要求が2つ以上の条件に当たるときも、Go 版は、Java 版と同じく、順の早い条件のエラーの文言で答える。受入基準2から6の文は、要求が、順のより早い条件に当たらないときの答えを決める。
   1. ファイルの中の値を、決まった型の値として読めること(受入基準6)
   2. ファイルの版が `1.0` であること
   3. 要求を送った利用者が、作れる経歴書の数の上限に達していないこと
   4. ファイルの中の経歴書の名前が、要求を送った利用者のほかの経歴書の名前と重ならないこと
   5. ファイルの中の経歴書と項目の値が、Java 版が戻しで確かめる値の決まりを満たすこと。この決まりは、Java 版が経歴書と項目を作るときに確かめる決まりで、利用者が画面で経歴書と項目を保存するときの決まりより少ない(受入基準5)
2. ファイルの版が `1.0` でないか、版が書かれていない要求には、Go 版は、Java 版と同じく、状態の番号 400 と「サポートされていないバックアップバージョンです。」の文言で答える。
3. 利用者が作れる経歴書の数の上限に達しているときは、Go 版は、Java 版と同じく、状態の番号 400 と、今の数と上限の数を入れた、上限に達したことを示す文言で答える。
4. ファイルの中の経歴書の名前が、利用者のほかの経歴書の名前と重なるときは、Go 版は、Java 版と同じく、状態の番号 400 と「この職務経歴書名は既に登録されています。」の文言で答える。
5. ファイルの中身が、受入基準1の5番目の、Java 版が戻しで確かめる値の決まりを満たさないときは、Go 版は、Java 版と同じく、状態の番号 400 と、「バックアップファイルが不正なためリストアできません。」の文と「別のバックアップファイルでお試しください。」の文を改行でつないだ文言で答える。決まりを満たさない中身は、たとえば、名前の無い経歴書、50文字を超える経歴書の名前、姓と名の片方だけを入れた経歴書、始まりの年月より前の終わりの年月、https の形でないリンクである。利用者が画面で経歴書と項目を保存するときの決まりのうち、次の決まりを、Java 版の戻しは確かめない。Go 版も、Java 版と同じく、戻しではこれらを確かめない。
   - 年月と日付が 1900 年から 2100 年の範囲にあること
   - 職歴の期間が、ほかの職歴の期間と重ならないこと
   - リンクの長さ
   - 姓と名の両方が無いか空のときに、姓と名を入れること。Go 版は、そのファイルを、要件2の受入基準2のとおり、氏名の無い経歴書として戻す。姓と名の片方だけを入れたファイルは、Java 版と同じく、入れていないほうが無いとして断る
   - プロジェクトの工程を選ぶこと。Go 版は、工程が無いファイルを、要件2の受入基準2のとおり、すべての工程を選んでいないものとして戻す
   - 欄ごとの項目の数の上限
6. Java 版が、ファイルの中の値を読めないとして、状態の番号 400 と「入力エラーがあります。」の文言で答える要求には、Go 版も同じに答える。そのような要求は、たとえば、日付の欄に日付の形でない文字を入れたファイルから作った要求である。

### 要件5 ほかの利用者の経歴書を、書き出せないようにする

経歴書には、利用者の氏名と職歴が入っている。Go 版がほかの利用者の経歴書のバックアップを書き出すと、利用者の経歴が他人に読まれる。利用者は、自分の経歴書が読まれたことに、画面で気づけない。そこで、Go 版は、利用者が自分の経歴書だけを書き出せるようにする。

1. 利用者が、無い経歴書の書き出しの要求を送ったら、Go 版は、Java 版と同じく、状態の番号 404 と「対象の職務経歴書データが存在しません。」の文言で答える。
2. 利用者が、ほかの利用者の経歴書の書き出しの要求を送ったら、Go 版は、その経歴書を書き出さず、受入基準1の、無い経歴書の要求への答えと同じ答えを返す。要求を送った人が、答えから、その経歴書があるかどうかを見分けられないようにするためである。
3. 退会してすでに居ない利用者のログインの状態を持つ要求が届いたら、Go 版は、2つの操作のどちらでも、その要求に Java 版と同じ答えを返す。認証のまとまりの spec が、すでに居ない利用者の要求はログインの状態の検査を通るとし、その要求への答えを、操作を作るまとまりの spec で Java 版と同じにすると決めたためである。Java 版がこの要求にサーバの誤りとして状態の番号 500 で答えるときは、Go 版は、要求の誤りか、対象が無いことを示す状態の番号で答える。Claude は、どちらで答えるかを設計で決め、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。退会してすでに居ない利用者は、Java 版の答えでも Go 版の答えでも書き出しと戻しを終えられないので、利用者ができることは変わらない。

### 要件6 Java 版と Go 版を比べる検査で、2つの操作の答えが同じことを確かめる

Claude は、Go 版の2つの操作が Java 版と同じかを、機械で確かめる。書き出しのファイルは、経歴書のデータによって、書かれる欄と、項目の並びが変わる。戻しの答えは、ファイルの中身によって、断る条件と、補う欄が変わる。そこで、Claude は、いろいろな経歴書とファイルで、Java 版と Go 版に同じ要求を送り、答えを比べる。

1. Claude は、2つの操作について、Java 版と Go 版を比べる検査の筋書きを書く。筋書きには、次の要求を含める。
   - 書き出しの要求を、次の経歴書に送る要求
     - 作った直後の、名前と日付だけを持つ経歴書
     - 6つの欄のすべてに項目を持ち、プロジェクトのすべての工程と技術の分類に値を入れた経歴書
     - 終わりの年月の無い職歴とプロジェクトを持つ経歴書
     - 経歴書の名前が日本語の経歴書と、ファイル名に使えない文字を含む経歴書
     - 利用者が経歴書に `<` `>` `&` `"` `'` の文字と改行と絵文字を書いた経歴書
     - 6つの欄のそれぞれに2件以上の項目を、名前の順とも期間の順とも違う順に足した経歴書
     - 項目を足したあとに、項目の値を直した経歴書
   - Java 版が書き出したファイルを戻す要求。Claude は、この要求に、書き出しの要求に使った経歴書から書き出したファイルを使う
   - 要件4の受入基準2から6の、断る条件ごとに、その条件に当たる要求。Claude は、要件4の受入基準1の順を確かめるために、2つ以上の条件に当たる要求も含める。Claude は、要件4の受入基準5の、ファイルの中身が Java 版が戻しで確かめる値の決まりを満たさない条件に当たる要求に、姓だけを入れたファイルから作った要求を含める
   - 要件4の受入基準5に挙げた、Java 版の戻しが確かめない決まりに当たるファイルの戻しの要求。Claude は、少なくとも、期間の重なる2件の職歴を持つファイル、1900 年より前の年月を持つファイル、256文字以上のリンクを持つファイルから作った要求を含める
   - 要件1の受入基準1の、形の誤ったファイルから作った要求。Claude は、少なくとも、経歴書の中身が無いファイル、6つの欄のどれかが無いファイル、項目の中に値の無い要素を持つファイル、値の型の違うファイル、知らない名前の欄を持つファイル、中身が JSON のオブジェクトでないファイルから作った要求を含める
   - 無い経歴書の書き出しの要求と、ほかの利用者の経歴書の書き出しの要求
   - 退会してすでに居ない利用者のログインの状態を持つ、書き出しの要求と戻しの要求
   - 置き換えの spec の設計が、まとまりごとに足すと決めた、ログインが切れたあとの要求と、偽の送信の検査に通らない要求
2. Java 版と Go 版を比べる検査は、状態の番号と、Content-Type と Content-Disposition のヘッダと、答えの本文を比べる。また、Java 版と Go 版を比べる検査は、要求のあとにデータベースに残ったデータも比べる。戻しが作った経歴書と、断った要求のあとに経歴書が作られていないことを確かめるためである。Java 版と Go 版を比べる検査は、JSON として読んだ値で比べるので、要件3の受入基準3で決めた文字の書き方の違いを見つけられない。Claude は、Go 版が書き出したファイルの文字の並びが Java 版と同じことを、別の、機械による確認で確かめる。確かめ方は、設計で決める。要件3の受入基準2で、ファイルの中の項目の並びは Java 版と違ってよいとしたので、Java 版と Go 版を比べる検査は、書き出しの答えの本文を比べるときに、6つの欄のそれぞれの中の項目の並びを比べない。Claude は、Go 版のファイルの中の項目が経歴書を読み出すときと同じ順に並ぶことを、Go 版のテストで確かめる。
3. Go 版は、次の要求に、要求の誤りか、対象が無いことを示す状態の番号で答えてよい。その要求は、受入基準1の筋書きに含める要求のうち、要件1の受入基準1に挙げた、画面が送る要求でないもので、Java 版が状態の番号 500 で答えると分かった要求である。Claude は、どちらで答えるかを設計で決め、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。要件1の受入基準1の要求に Java 版が 500 で答えるときは、Go 版は、要件1の受入基準1のとおり、同じ 500 で答える。ただし、退会してすでに居ない利用者の要求には、Go 版は、退会してすでに居ない利用者の要求への答えを決めた要件5の受入基準3のとおりに答える。
4. 置き換えの spec は、主な操作の応答にかかる時間を Java 版と Go 版で測って比べると決めた。置き換えの spec の設計は、バックアップの書き出しと戻しを、測る操作に含めた。Claude は、6つの欄のそれぞれに項目を入れた経歴書で、書き出しの時間と、その経歴書から書き出したファイルの戻しの時間を測る。項目の少ない経歴書で測ると、利用者が書き出す経歴書より軽い要求しか測れないためである。

### 要件7 版をまたいでも、バックアップを書き出して戻せる

所有者が本番を Java 版に戻したとき、利用者は、Go 版で書き出したバックアップのファイルを Java 版で戻す。また、切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受けるので、利用者が一方の版で書き出したファイルの戻しの要求が、もう一方の版に届くことがある。もう一方の版がそのファイルを戻せないと、利用者は、手元のバックアップを使えない。そこで、Claude は、一方の版が書き出したファイルを、もう一方の版が戻せることを確かめる。

1. 利用者は、一方の版で書き出したバックアップのファイルを、もう一方の版で戻せる。ただし、利用者が作れる経歴書の数の上限に達しているときと、ファイルの中の経歴書と同じ名前の経歴書を利用者が持っているときは、もう一方の版は、要件4の受入基準3と4のとおりに戻しを断る。戻した経歴書には、書き出した経歴書の名前、日付、姓、名と、6つの欄の項目の値が出る。戻した経歴書は、戻しに使った版でない版でも読める。
2. Claude は、版をまたいで確かめる検査に、一方の版で6つの欄のすべてに項目を持つ経歴書を書き出し、もう一方の版でそのファイルを戻し、最初の版で戻した経歴書を読む筋書きを足す。戻しの前に、Claude は、書き出した経歴書の名前と重ならないように、書き出した経歴書を消す。版をまたいで確かめる検査は、この筋書きを、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方で動かす。版をまたいで確かめる検査は、戻しが成功することと、戻した経歴書の値が、書き出した経歴書の値と同じことを確かめる。版をまたいで確かめる検査は CI で動く。この検査が通らない PR は main に入らない。

### 要件8 Java 版と同じにできるかを設計の前に試し、置き換えの spec の進み具合の表に、このまとまりの状態を書く

Claude が、設計を書いたあとや作り終えたあとに、Go 版の2つの操作を Java 版と同じにできないと分かると、所有者は spec を承認し直すことになる。そこで、Claude は、確かめていない動きを設計の前に試し、Java 版と同じにできないと分かったら止まって所有者に報告する。また、所有者は、置き換えがどこまで進んだかを、置き換えの spec の進み具合の表で、機能のまとまりごとに見る。そこで、Claude は、このまとまりの状態を、その表に書く。

1. Claude は、この spec の設計を書く前に、Claude が置き換えの spec でまだ試しに作っていない、2つの操作の動きを試しに作り、Java 版と同じになるかを確かめる。試しに作る動きには、少なくとも次の7つを含める。Claude は、試しに作った方法と結果を、この spec の research.md に書く。
   - Java 版が書き出したファイルを Go で戻した経歴書が、Java 版が同じファイルを戻した経歴書と同じになること
   - Go で書いたバックアップのファイルの文字の並びが、要件3の受入基準3のとおり、Java 版のファイルと同じになること。Claude は、利用者が経歴書に `<` `>` `&` と、行や段落の区切りを表す文字と、絵文字を書いた経歴書で確かめる
   - 要件6の受入基準1の、形の誤ったファイルから作った要求に、Java 版が返す答え。Claude は、中身が JSON のオブジェクトでないファイルについて、画面がその中身をどう送るかもあわせて確かめる
   - 退会してすでに居ない利用者の戻しの要求に、Java 版が返す答え
   - Java 版が書き出したファイルの中の項目の並び。Claude は、両方の版で、同じ項目を同じ順に足した経歴書と、項目の値を直した経歴書と、ファイルを戻してできた経歴書を書き出して、項目の並びを比べる
   - Java 版の戻しが長さを確かめない値で、データベースに入る長さを超える値を持つファイルの戻しに、Java 版が返す答え。Claude は、少なくとも、256文字以上のリンクを持つファイルで確かめる
   - 答えの Content-Disposition のヘッダのファイル名。Claude は、経歴書の名前が日本語のときと、ファイル名に使えない文字を含むときも、Go 版のヘッダが Java 版のヘッダと同じになるかを確かめる
2. 試しに作った結果、Java 版と同じにできない動きが見つかったら、Claude は、設計を書く前に止まる。Claude は、何が同じにならないかと、その違いが利用者に何をもたらすかを、所有者に報告する。
3. Claude は、置き換えの spec の進み具合の表の、バックアップのまとまりの行に、この spec の場所と、まとまりの状態を書く。Claude は、状態を、作り終えたら「作り終えた」にし、Java 版と Go 版を比べる検査に通ったら「比べる検査に通った」にする。
