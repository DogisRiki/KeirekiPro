# 要件

## 元の要望
Issue #501: AIの作業時間とトークン使用料を Issue ごとに集計し、GitHub 上に蓄積する

### きっかけ

> spec駆動においてどれくらいの作業時間(開始から終了までの日数ではなくAIが作業した総時間)がかかり、どれくらいのトークン使用料(詳細内訳)が発生したかを終了時に集計し、どこかに蓄積して改善のあてにしたい。

### やりたいこと

- AIが作業した総時間(開始から終了までの日数ではない)と、トークン使用料(詳細な内訳)を、Issue の終了時に集計する
- 集計した結果を蓄積し、改善のあてにする
- 対象は、spec で進めた Issue と spec 無しで進めた Issue の両方にする(AIの提案を了承)
- 集計に含めるAIは、Claude の本体のセッションと、本体から呼ばれる補助役(審査役など)にする(AIの提案を了承)
- トークン使用料は、トークン数と、公表価格で換算した金額で表す(AIの提案を了承)
- 内訳は、段階ごと・モデルごと・トークンの種類ごとに分ける(AIの提案を了承)
- レビューの往復回数を集計に加える。対象は spec の審査、実装のタスクごとのレビュー、PR の Codex レビュー(Codex は回数だけ)にする(AIの提案を了承)
- 実装まで進んだあとに、要件・設計・タスクの修正が必要になって手戻りしたことも分かるようにする
- 次の手戻りも分かるようにする: 承認の前に所有者が spec の直しを求めた、spec を作る途中で前の段階に戻って直した、PR を出したあと CI の自動チェックが失敗してコードを直した、同じ失敗を3回続けて直せずAIが作業を止めて所有者に報告した、実装の途中で Issue を分けた(AIの提案を了承)
- Issue の終了は PR がマージされたときとし、その時点で集計する(AIの提案を了承)
- これまでに終わった Issue のさかのぼりの集計は、毎回動く仕組みには入れず、この Issue の作業として一度だけ行う。対象は、会話記録が残る Issue と、この Issue(#501)である
- 蓄積した集計は GitHub 上で見られるようにする(AIの提案を了承)
- 集計のたびに、AIが過去と比べて目立つ点の所見を添える(AIの提案を了承)
- AIが所見から直す案を作ったときは、所有者に尋ねてから起票する(AIの提案を了承)

### どうなれば解決か

PR がマージされるたびに、その Issue の集計が GitHub 上で見られ、蓄積の一覧に1行増える。集計の中身は次のとおり(AIの提案を了承)。

**Issue ごとの集計**

- 開始日と終了日(PR がマージされた日)、spec の有無
- 全体の合計: AIの作業時間、トークン数、使用料
- 段階ごとの表: 段階ごとに、AIの作業時間、そのうち待ち時間、審査役などが同時に動いた時間、トークン数、使用料と、その合計
  - spec ありの段階: 要件、要件の審査、設計、設計の審査、タスク、タスクの審査、実装、実装中の spec の直し、出荷とレビュー対応
  - spec 無しの段階: 着手の判断、実装、出荷とレビュー対応
- モデルごとの表: モデルごとに、役割、入力・キャッシュ書き込み・キャッシュ読み込み・出力のトークン数、使用料
- 往復と手戻りの表(spec 無しの Issue では spec に関わる行が無い)

  | 項目 | 回数の分け方 |
  |---|---|
  | spec の審査役との往復 | 要件・設計・タスク別 |
  | 承認の前に、所有者が spec の直しを求めた | 要件・設計・タスク別 |
  | spec を作る途中で、前の段階に戻って直した | 回数と、どの段階からどの段階へ |
  | 実装の途中で、spec に戻って直した | 要件・設計・タスク別 |
  | 実装したコードに、タスクごとのレビュー役が問題を見つけ、コードを直した | 回数 |
  | PR の Codex レビューとの往復 | 回数 |
  | PR を出したあと、CI の自動チェックが失敗し、コードを直した | 回数 |
  | 同じ失敗を3回続けて直せず、AIが作業を止めて所有者に報告した | 回数 |
  | 実装の途中で、Issue を分けた | 有無 |

- AIの所見: 過去と比べて目立つ点。直す案があれば、それも添える

**蓄積の一覧**(Issue が終わるたびに1行増える)

- 列: Issue、spec の有無、終了日、AIの作業時間、トークン数、使用料、実装中に spec へ戻った回数(要件・設計・タスクへ戻った回数の合計)

**言葉の意味**

- AIの作業時間: AIが動いていた時間。所有者の返事を待っている時間は入れない
- そのうち待ち時間: AIの作業時間のうち、CI や品質チェックが終わるのを待っていた時間
- 審査役などが同時に動いた時間: AIの作業時間の裏で審査役などが動いていた時間。AIの作業時間には足さない
- 使用料: 公表価格で換算した金額

### やらないこと

- PR の Codex レビューの使用料は集計しない(AIの提案を了承)
- Issue の作業中に使用料や作業時間がいつもより大きく増えても、AIはその場では何もしない。増えたことは、終わったあとの集計と所見で分かればよい(AIの提案を了承)

### 決めた方式

- `/ship` がマージを見届けずに会話を終えた PR は、マージのあと、その PC で次に Claude の会話を開いたときに、Claude が集計して GitHub に出す。集計には見届けを終えたあとの作業も入り、終了日には実際にマージされた日を書く。(AIの提案を了承)
- 使う量の上限で会話が止まっていた時間は、AIの作業時間に入れない。全体の合計には、上限で止まった回数と止まっていた時間を別に書く。(AIの提案を了承)
- Issue を起票する前の `/request` の会話は、集計に入れない。開始日は、`/start` を打った日にする。
- 本体の会話が同じ Issue のために別に起こしたセッションの作業時間とトークン使用料は、その Issue の集計に入れる。(AIの提案を了承)
- 往復と手戻りの表に、次の3つの行を回数で足す。「spec 無しで始め、実装の途中で spec に切り替えた」「200行の検査で PR が止まった」「自動レビューが、Issue の決めた方式から外れたとして PR を止めた」。(AIの提案を了承)
- 集計と所見は、公開しているこのリポジトリの GitHub 上に置く。集計と所見には、作業時間とトークン数と使用料と回数と所見だけを書き、会話の中身は書かない。(AIの提案を了承)

### 追加の要望(Issue #659)
AIの作業の集計の一覧に、Issue の題名の列を足す

#### きっかけ

所有者が、AIの作業の集計の一覧(#654)を見て、Issue の題名も一覧に出したいと求めた。

#### やりたいこと

- AIの作業の集計の一覧に、Issue の題名の列を足す。
- 題名の全文を出すと、ほかの列が折り返されて一覧が見にくくなるので、題名を短く切って出す。

#### どうなれば解決か

- AIの作業の集計の一覧の表に、Issue の列の次に「題名」の列がある。
- 題名の列には、Issue の題名の初めの20文字が出る。題名が20文字より長いときは、20文字のあとに「…」が付く。
- Issue の列の番号にマウスを置くと、その Issue の題名の全文が出る。
- 一覧に今ある行にも、題名が出る。

#### 決めた方式

- 一覧に今ある行への題名の書き足しは、毎回動く仕組みに入れず、題名の列を足す変更が main に入ったあとに一度だけ行う。

## はじめに

所有者は、AI が1つの Issue を仕上げるまでに、どれだけ動き、どれだけトークンを使い、どこで手戻りしたかを数字で見られない。そのため、所有者は、開発の仕組みのどこを直せば作業時間と使用料が減るかを、数字をもとに決められない。そこで、Claude は、Issue を閉じる PR がマージされるたびに、その Issue の AI の作業時間とトークン数と使用料と、往復と手戻りの回数を集計し、GitHub 上に置く。Claude は、集計のたびに蓄積の一覧に1行を足し、過去の集計と比べて目立つ点を所見として添える。

## 範囲

- この spec で決めること: 次の6つである。
  - 集計する時点と、集計に入れる作業の範囲
  - AI の作業時間とトークン数と使用料の数え方
  - Issue ごとの集計と蓄積の一覧に載せる中身
  - 所見と、所見から作った直す案の扱い
  - 公開しているリポジトリに置く中身の制限
  - この spec の仕組みが main に入る前に終わった Issue と #501 の、一度だけ行うさかのぼりの集計
- この spec で決めないこと: 次の5つである。
  - 集計を見て、開発の仕組みを実際に直すこと。直す案は、別の Issue で進める
  - Claude Code の使う量の週ごとの上限を、どこまで使ったかの割合
  - 作業の途中で使用料や AI の作業時間が増えたときに、その場で何かをすること
  - PR のマージによらずに閉じた Issue の集計。こうした Issue の作業をどの Issue の集計に入れるかは、要件2「集計に入れる作業の範囲」で決める
  - 着手のときに分けた元の Issue の、着手の判断の作業
- この spec が前提にしていること: 次の5つである。
  - 開発に参加する人は、それぞれ自分の PC(Windows・macOS・Linux のどれか)で Claude Code を動かす。開発に参加する人は、Claude Code を、ターミナルで動かしても、デスクトップアプリで動かしてもよい
  - Claude Code は、会話の記録を、会話を動かした PC の中に残す。Claude Code は、既定の設定では、最後に動いてから30日たった会話の記録を消す
  - 1つの Issue の作業は、1台の PC で進める
  - 別の PC で動かした会話の記録は、ほかの PC からは読めない
  - 開発に参加する人の PC の Claude は、このリポジトリの所有者か共同作業者のアカウントで GitHub にログインする

## 要件

### 要件1 Issue を閉じる PR がマージされたら、Claude がその Issue を集計して GitHub に出す

所有者は、Issue が終わるたびに、その Issue にかかった AI の作業と使用料を見たい。会話の記録は Claude を動かした PC の中にしか無いので、Claude は、その PC で会話が動いているときにしか集計を作れない。そこで、Claude は、マージを見届けた会話か、その PC で次に開いた会話で、その Issue を集計する。

1. Issue は、本文に `Closes #<Issue の番号>` を書いた PR が main にマージされたときに終わる。1つの Issue のために PR を2つ以上出したときは、Claude は、`Closes` を書いた PR がマージされたあとに、それまでに出したすべての PR の作業を1つの集計にまとめる。
2. `/ship` が Issue を閉じる PR のマージを見届けたら、Claude は、同じ会話の中で、その Issue の集計を GitHub に出す。
3. `/ship` が Issue を閉じる PR のマージを見届けないまま、会話が終わることがある。そのときは、その会話を動かしていた PC で次に Claude の会話が始まったら、Claude は、この spec の仕組みが main に入ったあとにマージされ、まだ集計していない Issue を探し、その Issue の集計を GitHub に出す。その PC で次に会話が始まったときに Claude が出す集計には、`/ship` がマージを待つのをやめたあとの作業も入る。Claude は、終了日に、実際にマージされた日を書く。
4. Claude は、Issue を閉じる PR を出した PC で、その Issue を集計する。Issue を閉じる PR を出した PC とは別の PC では、Claude は、その別の PC に会話の記録が無い Issue を集計しない。
5. Claude は、1つの Issue の集計を、GitHub に1回だけ出す。2つの会話が同じ Issue を同時に集計しようとしても、GitHub に出る集計は1つである。
6. GitHub に集計を出せなかったら、Claude は、出せなかったことと理由を、その会話の中で、会話の相手に書く。Claude は、その Issue をまだ集計していない Issue として残し、集計を出せなかった会話を動かした PC で次に会話を開いたときに、その Issue の集計を GitHub に出し直す。
7. Claude は、集計を出すために、所有者にも開発者にもコマンドを打つよう頼まない。
8. Claude は、Claude Code をターミナルで動かした会話からも、デスクトップアプリで動かした会話からも、この要件のほかの項目のとおりに集計を作る。デスクトップアプリを入れていない PC でも、Claude は集計を作る。
9. #501 は、この spec の仕組みを main に入れる PR が本文に書いた Issue である。Claude は、`/ship` がマージを見届けた会話で集計を出すときに、#501 を集計しない。Claude は、マージを見届けないまま会話が終わったあとに、その PC で次に会話が始まって集計を出すときにも、#501 を集計しない。Claude は、#501 を、要件10「この spec の仕組みが main に入る前に終わった Issue を、一度だけさかのぼって集計する」のとおりにだけ集計する。

### 要件2 集計に入れる作業の範囲

所有者は、Issue を仕上げるために AI が動いた分を、漏らさずに、ほかの Issue の分を混ぜずに見たい。動いた分が漏れたり、ほかの Issue の分が混ざったりすると、所有者は、Issue どうしを比べても、開発の仕組みのどこを直せばよいかを数字をもとに決められないためである。

1. Claude は、次の会話を、その Issue の集計に入れる。
   - 会話がその Issue を受け持ってから、Issue を閉じる PR がマージされるまでに、その Issue のために動いた本体の会話
   - 本体の会話から呼ばれた補助役の会話。補助役には、spec の審査役、書き方の点検役、タスクごとの確認役、原因を調べる補助役を含む
   - 本体の会話が同じ Issue のために別に起こしたセッションの会話と、そのセッションから呼ばれた補助役の会話
2. Claude は、Issue を起票する前の `/request` の会話を、集計に入れない。
3. 1つの会話が続けて2つ以上の Issue を受け持ったときは、Claude は、その会話を Issue ごとの時間の区切りで分け、それぞれの Issue の集計に入れる。Claude は、1つの作業を2つの Issue の集計に重ねて入れない。
4. 会話は、所有者か開発者が `/start #<Issue の番号>` を打ったときに、その Issue を受け持つ。ただし、次の2つの Issue には `/start` が打たれないので、会話は次のときにその Issue を受け持つ。
   - 実装の途中で Issue を分けたときの、最初の部分の Issue: 会話は、分ける前の元の Issue に `/start` が打たれたときに、最初の部分の Issue を受け持つ。Claude は、分ける前の元の Issue の作業を、最初の部分の Issue の集計に入れる。Claude は、最初の部分の Issue の集計の、往復と手戻りの表の「実装の途中で、Issue を分けた」の行に「有」と書く
   - 着手のときにほかの Issue とまとめて、開いたままにした Issue: 会話は、ほかの Issue にまとめて閉じた Issue に `/start` が打たれたときに、開いたままにした Issue を受け持つ。Claude は、ほかの Issue にまとめて閉じた Issue に `/start` が打たれてから、Issue をまとめるまでの作業を、開いたままにした Issue の集計に入れる
5. 集計の開始日は、会話がその Issue を初めて受け持った日とする。
6. Claude は、PR の Codex レビューの使用料を集計に入れない。Claude は、Codex レビューについては、往復の回数だけを往復と手戻りの表に入れる。
7. Claude は、会話がその Issue を受け持ってから集計するまでに、その Issue のために動いた会話を、1つも漏らさずに記録に残す。Claude Code が途中で古い会話の記録を消しても、Claude は、消えた会話の AI の作業時間とトークン数と回数を集計に入れる。この決まりは、この spec の仕組みが main に入ったあとに会話が受け持った Issue に当てはまる。
8. 記録に残した会話のうち、集計のときに作業時間とトークン数と回数を読めない会話があったら、Claude は、読めた分だけで集計し、集計に「会話の記録の一部を読めなかった」と書く。Claude は、読めない会話があることを、集計から黙って落とさない。

### 要件3 AI の作業時間の数え方

所有者は、開始から終了までの日数ではなく、AI が実際に動いた時間を知りたい。所有者の返事を待つ時間や、使う量の上限で止まっていた時間が入ると、集計が AI の作業の量を多く見せてしまう。

1. AI の作業時間は、その Issue の本体の会話、補助役の会話、別に起こしたセッションの会話のどれかが動いていた時間とする。Claude は、2つ以上の会話が同時に動いていた時間を、1回だけ数える。
2. Claude は、所有者の返事を待っていた時間を、AI の作業時間に入れない。所有者が画面を確かめている時間と、所有者が PR を承認するまでの時間も、所有者の返事を待っていた時間とする。Claude Code が権限の確認で所有者の承認を待っていた時間も、所有者の返事を待っていた時間とする。
3. Claude は、使う量の上限で会話が止まっていた時間を、AI の作業時間に入れない。Claude は、上限で止まった回数と止まっていた時間を、全体の合計の欄に別に書く。
4. 「そのうち待ち時間」は、AI の作業時間のうち、会話が考えることも調べることもせずに、コマンドや外の仕組みが終わるのを待っていた時間とする。待ち時間には、少なくとも次の時間が入る。
   - CI の検査が終わるのを待っていた時間
   - 品質チェックと、品質チェックの順番待ちが終わるのを待っていた時間
   - Docker の開発環境の起動と、イメージの組み立てが終わるのを待っていた時間
   - PR のマージと、GitHub のワークフローが終わるのを待っていた時間
   - Claude が、終わるのを待たずに次の作業に進めるように動かしたコマンドが、終わるのを待っていた時間
   - Anthropic の API が混雑したために、会話が再試行を待っていた時間
5. Claude は、本体の会話が補助役の終わりを待っているだけの時間を、本体の会話が動いていた時間に数えず、補助役の会話が動いていた時間として数える。その時間が待ち時間かどうかは、その時間に補助役の会話が何をしていたかで、4の「そのうち待ち時間」の決まりのとおりに決める。たとえば、補助役の会話が品質チェックの終わりを待っていた時間は、待ち時間に入る。Claude は、本体の会話が補助役の終わりを待っているだけの時間を、審査役などが同時に動いた時間に入れない。補助役を待つ時間を本体の会話の時間にも数えると、補助役が動いた時間の全部が、同時に動いた時間に入ってしまうためである。
6. 「審査役などが同時に動いた時間」は、補助役の会話か別に起こしたセッションの会話が、ほかの会話と同時に動いていた時間とする。Claude は、この時間を AI の作業時間に足さない。

### 要件4 トークン数と使用料の数え方

所有者は、使用料の詳しい内訳から、どこで多く使ったかを知りたい。合計の金額だけでは、所有者は、どの段階やどのモデルやどの種類のトークンを減らせば使用料が下がるかを決められないためである。

1. Claude は、トークン数を、入力、キャッシュの書き込み、キャッシュの読み込み、出力の4種類に分けて数える。全体の合計と段階ごとの表のトークン数は、4種類の合計とする。
2. 使用料は、トークン数を公表価格で換算した金額とする。Claude は、公表価格が値を分けている条件ごとに、その条件の価格で換算する。たとえば、公表価格が、キャッシュの書き込みの価格を、キャッシュを保持する時間ごとに分けているときは、Claude は、キャッシュの書き込みのトークン数を、キャッシュを保持する時間ごとに分けて換算する。Claude は、モデルごとの表に、トークン数を、換算の条件ではなく、入力、キャッシュの書き込み、キャッシュの読み込み、出力の4種類に分けて書く。Claude は、使用料を米ドルで書く。
3. Claude は、集計に、換算に使った価格の出どころと、その価格を確かめた日を書く。公表価格が変わったときに、所有者が、古い集計と新しい集計がどの価格で換算されたかを見分けられるようにするためである。
4. 公表価格が分からないモデルがあったら、Claude は、そのモデルのトークン数だけを書き、使用料の欄に「価格が分からない」と書く。Claude は、分からない価格を推して埋めない。

### 要件5 Issue ごとの集計に載せる中身

所有者は、1つの Issue について、全体の量と、どの段階とどのモデルで多く使ったかを、1か所で見たい。全体の量と内訳が別々の場所にあると、所有者は、どの段階とどのモデルが全体の量を大きくしたのかを見比べにくいためである。

1. Claude は、Issue ごとの集計の最初に、開始日、終了日、spec の有無、全体の合計を書く。全体の合計は、AI の作業時間、トークン数、使用料の3つである。spec 無しで始めて実装の途中で spec に切り替えた Issue は、spec ありとする。
2. Claude は、段階ごとの表に、段階ごとの AI の作業時間、そのうち待ち時間、審査役などが同時に動いた時間、トークン数、使用料と、それらの合計の行を書く。
3. spec ありの Issue の段階は、着手の判断、要件、要件の審査、設計、設計の審査、タスク、タスクの審査、実装、実装中の spec の直し、出荷とレビュー対応とする。spec 無しの Issue の段階は、着手の判断、実装、出荷とレビュー対応とする。
4. どの段階にも当たらない作業は、Claude が段階ごとの表の「その他」の行に入れる。段階ごとの表の合計の行は、全体の合計と一致する。
5. Claude は、モデルごとの表に、モデルと役割の組ごとに1行を書く。各行には、入力、キャッシュの書き込み、キャッシュの読み込み、出力のトークン数と、使用料を書く。役割は、本体の会話、補助役の種類、別に起こしたセッションのどれかである。
6. Claude は、集計の最後に、所見を書く。

### 要件6 往復と手戻りの表

所有者は、手戻りがどこで何回起きたかを見て、開発の仕組みのどこを直すかを決めたい。手戻りの回数が分からないと、所有者は、開発の仕組みのどこを直せば手戻りが減るかを、数字をもとに決められないためである。

1. Claude は、往復と手戻りの表に、次の行を書く。spec 無しの Issue では、Claude は spec に関わる行を書かない。

   | 項目 | 回数の分け方 |
   |---|---|
   | spec の審査役との往復 | 要件・設計・タスク別 |
   | 承認の前に、所有者が spec の直しを求めた | 要件・設計・タスク別 |
   | spec を作る途中で、前の段階に戻って直した | 回数と、どの段階からどの段階へ |
   | 実装の途中で、spec に戻って直した | 要件・設計・タスク別 |
   | 実装したコードに、タスクごとの確認役が問題を見つけ、コードを直した | 回数 |
   | PR の Codex レビューとの往復 | 回数 |
   | PR を出したあと、CI の自動チェックが失敗し、コードを直した | 回数 |
   | 同じ失敗を3回続けて直せず、AI が作業を止めて所有者に報告した | 回数 |
   | 実装の途中で、Issue を分けた | 有無 |
   | spec 無しで始め、実装の途中で spec に切り替えた | 回数 |
   | 200行の検査で PR が止まった | 回数 |
   | 自動レビューが、Issue の決めた方式から外れたとして PR を止めた | 回数 |

2. 起きなかった項目には、Claude は 0 か「無し」を書く。
3. Claude は、この spec の仕組みが main に入ったあとに会話が受け持った Issue では、表のすべての項目を数える。Claude は、数えるための記録を作業の途中で残す。
4. Claude は、次の2つのときだけ、数えられなかった項目に「数えられない」と書き、0 と書かない。
   - この spec の仕組みが main に入る前に、会話が受け持った Issue を集計するとき
   - 要件2「集計に入れる作業の範囲」で、作業時間とトークン数と回数を読めない会話があったとき

### 要件7 蓄積の一覧

所有者は、Issue どうしを並べて、作業時間と使用料と手戻りがどう変わってきたかを見たい。Issue ごとの集計を1つずつ開くだけでは、所有者は、開発の仕組みを直したあとに作業時間と使用料と手戻りが減ったかどうかを確かめにくいためである。

1. Claude は、GitHub 上の1つの蓄積の一覧に、Issue の集計を出すたびに1行を足す。
2. 一覧の列は、Issue、題名、spec の有無、終了日、AI の作業時間、トークン数、使用料、実装中に spec へ戻った回数とする。実装中に spec へ戻った回数は、要件・設計・タスクへ戻った回数の合計である。題名の列に何を書くかは、要件11「蓄積の一覧に、Issue の題名を出す」で決める。(#659 で変更)
3. 所有者は、一覧の各行から、その Issue の集計を開ける。
4. 一覧の行は、終了日の古い順に並ぶ。
5. 2つの会話がほぼ同時に一覧に行を足しても、一覧の行は消えず、重ならない。
6. GitHub 上の蓄積の一覧は1つだけである。開発に参加する人の PC の Claude が、所有者と共同作業者のどのアカウントで GitHub にログインしていても、その Claude は同じ一覧に行を足す。開発に参加する人を増やしたときや、ログインするアカウントを替えたときに、一覧が2つに分かれると、所有者が Issue どうしを1か所で並べて見られなくなるためである。
7. このリポジトリの所有者と共同作業者のほかの人は、蓄積の一覧に書き込めない。

### 要件8 所見と直す案

所有者は、数字だけでなく、過去と比べて何が目立つかを、集計のたびに読みたい。数字だけでは、所有者は、どの数字が過去の集計より大きいかを、蓄積の一覧から自分で探さなければならないためである。所見から直す案が出ても、所有者は、起票するかどうかを自分で決めたい。

1. Claude は、所見に、蓄積の一覧の過去の行と比べて目立つ点を書く。比べる過去の行が無いときは、Claude は、所見に「比べる過去の集計が無い」と書く。
2. Claude は、所見から開発の仕組みを直す案を作ったら、その案を所見に書く。
3. 直す案を起票するかどうかは、所有者だけが決める。集計を出した会話の相手が所有者のときは、Claude は、その会話の中で、案を起票するかどうかを所有者に尋ねる。
4. 集計を出した会話の相手が所有者でないときは、Claude は、案を所見に残し、その会話では起票するかどうかを尋ねない。所有者が次に Claude の会話を始めたら、Claude は、所有者がまだ答えていない案を並べて書き、起票するかどうかを所有者に尋ねる。
5. 所有者が起票すると答えるまで、Claude は案を起票しない。所有者が起票しないと答えた案を、Claude は、もう一度尋ねない。
6. Claude は、Issue の作業の途中では、使用料や AI の作業時間がいつもより増えても、集計も所見も作らない。

### 要件9 公開しているリポジトリに置く中身と、Claude が読むもの

このリポジトリは公開されているので、GitHub に置いた集計と所見は誰でも読める。所有者は、集計から作業の中身や手元の情報が漏れないようにしたい。また、誰でもコメントと Issue を書けるので、所有者は、ほかの人が書いたものに集計が左右されないようにしたい。

1. Claude は、GitHub に置く集計と蓄積の一覧と所見に、作業時間、トークン数、使用料、回数、日付、Issue と PR の番号、Issue の題名、段階とモデルと役割の名前、所見と直す案の文だけを書く。(#659 で変更)
2. Claude は、会話の文、ファイルの中身、コマンドの出力、PC の中のファイルの場所とユーザー名を、集計にも所見にも書かない。
3. Claude は、所見で作業に触れるときは、段階と表の項目の名前で触れ、会話の文を引かない。
4. Claude は、このリポジトリの所有者と共同作業者のほかの人が書いたコメントを、集計を出したかどうかの判断に使わない。Claude は、所有者と共同作業者のほかの人が作った Issue を、蓄積の一覧として使わない。公開しているリポジトリには、誰でもコメントと Issue を書けるためである。ほかの人が集計に似せたコメントを書くと、Claude がその Issue の集計を出さなくなるおそれがある。ほかの人が一覧に似せた Issue を作ると、Claude がその Issue に一覧の行を足すおそれがある。
5. 集計する Issue を誰が起票したかは、Claude がその Issue を集計するかどうかに関わらない。

### 要件10 この spec の仕組みが main に入る前に終わった Issue を、一度だけさかのぼって集計する

所有者は、この spec の仕組みが main に入る前に終わった Issue の数字も、蓄積の一覧で、この spec の仕組みが main に入ったあとの Issue と並べて見たい。この spec の仕組みが main に入る前の Issue の数字が無いと、所有者は、開発の仕組みを直したあとに作業時間と使用料と手戻りが減ったかを、比べる元の数字無しに決めることになるためである。所有者は、さかのぼりの集計を、毎回動く仕組みに入れず、#501 の作業として一度だけ行いたい。

1. この spec の仕組みが main に入ったあと、所有者が Claude の会話でさかのぼりの集計を頼んだら、Claude は、さかのぼりの集計を、その会話の中で行う。Claude は、さかのぼりの集計を、この spec の仕組みの手順によらずに行う。この spec の仕組みは、さかのぼりの集計のための手順を持たない。Claude は、さかのぼりの集計を、所有者に頼まれずに始めない。(PR #651 で変更済み)
2. さかのぼりの集計の対象は、次の2つである。
   - この spec の仕組みが main に入る前に、Issue を閉じる PR がマージされた Issue のうち、所有者が頼んだ会話を動かした PC に、その Issue を受け持った会話の記録が残っている Issue
   - この spec の仕組みを main に入れる PR が本文に書いた Issue(#501)
3. Claude は、対象の Issue ごとに、要件2「集計に入れる作業の範囲」から要件6「往復と手戻りの表」までの5つの要件と、要件9「公開しているリポジトリに置く中身と、Claude が読むもの」のとおりに集計を作る。Claude は、要件1の5の、1つの Issue の集計を GitHub に1回だけ出す決まりのとおりに、集計を GitHub に出す。Claude は、要件7「蓄積の一覧」のとおりに、蓄積の一覧に行を足す。
4. Claude は、対象の Issue を、終了日の古い順に集計する。Claude は、対象の Issue ごとに、要件8「所見と直す案」のとおりに所見を書く。終了日の古い順に集計すれば、Claude は、どの Issue の所見でも、その Issue より前に終わった Issue の行と比べられるためである。
5. Claude は、さかのぼりの集計で出した集計を、ふつうの集計と同じ形で書き、さかのぼりの集計であることを書かない。Claude Code が、この spec の仕組みが main に入る前の会話の記録のうち古いものを、すでに消していることがあるので、Claude は、消えた会話の分を、さかのぼりの集計に入れられない。数えるための記録が無かった項目には、Claude は、要件6の4のとおりに「数えられない」と書く。(PR #651 で変更済み)
6. Claude は、集計を出し済みの Issue を、さかのぼりの集計で出し直さない。さかのぼりの集計が途中で止まったときは、所有者がもう一度頼めば、Claude は、まだ集計を出していない対象の Issue だけを集計する。
7. さかのぼりの集計で、ある Issue の集計を GitHub に出せなかったら、Claude は、出せなかったことと理由を会話の相手に書き、残りの対象の Issue を集計せずに止まる。Claude は、出せなかった Issue の集計を、次に会話を開いたときに出し直さない。さかのぼりの集計は、毎回動く仕組みに入れない一度だけの作業だからである。Claude は、所有者がもう一度さかのぼりの集計を頼んだときに、出せなかった Issue と残りの対象の Issue を、この要件の6の、まだ集計を出していない対象の Issue だけを集計する決まりのとおりに集計する。

### 要件11 蓄積の一覧に、Issue の題名を出す (#659)

所有者は、蓄積の一覧の各行が何の作業の数字かを、Issue を1つずつ開かずに見分けたい。一覧に Issue の番号しか無いと、所有者は、行ごとに Issue を開かないと、どの作業の数字かが分からないためである。ただし、題名の全文を一覧に出すと、ほかの列が折り返されて一覧が見にくくなる。そこで、Claude は、一覧に題名を短く切って書き、題名の全文は、所有者が Issue の番号にマウスを置いたときに出るようにする。

1. 蓄積の一覧の表には、Issue の列の次に、題名の列がある。(#659)
2. Claude は、題名の列に、Issue の題名の初めの20文字を書く。題名が20文字より長いときは、Claude は、20文字のあとに「…」を付ける。Claude は、全角の文字も半角の文字も、1字を1文字と数える。(#659)
3. 所有者が一覧の Issue の列の番号にマウスを置くと、その Issue の題名の全文が出る。(#659)
4. Claude は、一覧に行を足すときの Issue の題名を、その行に書く。行を足したあとに Issue の題名が変わっても、Claude は、その行の題名を書き換えない。一覧のほかの列も、行を足したときの値のまま変わらないためである。(#659)
5. 題名の列を足す変更が main に入ったときに一覧にある行にも、題名が出る。Claude は、それらの行の題名を、題名の列を足す変更が main に入ったあとに、会話の中で一度だけ書き足す。この spec の仕組みは、それらの行に題名を書き足すための手順を持たない。それらの行への書き足しは、一度だけ行えば済む作業だからである。Claude は、題名を書き足すときに、一覧の行を消さず、行のほかの列の値を変えない。それらの行には、行を足したときの題名の記録が無いので、Claude は、題名を書き足すときの Issue の題名を書く。(#659)
6. Issue の題名にどんな文字が入っていても、一覧の表の列はずれない。そのときも、ほかの行の見え方は変わらず、題名の文字はそのまま出る。題名を一覧に書いたことで、アカウントに通知が届くことは無く、ほかの Issue の記録に一覧の Issue へのつながりが載ることも無い。たとえば、題名には、表の列の区切りに使う「|」、「@」に続けてアカウントの名前を書いたもの、「<!--」、「#」に続けて Issue の番号を書いたものが入ることがある。「<!--」は、GitHub が、そのあとの文字を画面に出さなくする印である。Issue の題名は、このリポジトリの所有者と共同作業者のほかの人も書ける。そのため、所有者は、題名にどんな文字が入っていても、一覧の表の列がずれないことと、アカウントに通知が届かないことと、ほかの Issue の記録に一覧の Issue へのつながりが載らないことを求める。(#659)
