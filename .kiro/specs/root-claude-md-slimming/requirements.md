## はじめに

ルートの CLAUDE.md は、Claude Code がどの会話の始めにも読み込み、会話を圧縮したあとにも読み直す文書である(https://code.claude.com/docs/en/memory の「Instructions seem lost after `/compact`」の節)。Claude が 2026-10-18 に main のルートの CLAUDE.md を測ると、208行、24,807バイトだった。Claude Code の公式の文書は、CLAUDE.md を1ファイルあたり200行より短くすることを勧め、長いファイルは文脈を多く使い、決まりが守られにくくなると書いている(同じページの「Write effective instructions」の節)。ルートの CLAUDE.md の1行は長く、同じ決まりがスキルの手順などほかの文書にも書かれていることがある。

そこで、Claude は、今の AI の判断と作業の質を下げずに、ルートの CLAUDE.md を、どの会話でも要る決まりだけにして軽くする。Claude は、ほかの決まりを、その決まりが要る場面で必ず読まれる場所に移す。あわせて、Claude は、ルートの CLAUDE.md がまた膨らむ変更を PR の検査で止める仕組みを作る。

## 範囲

- この spec で決めること: ルートの CLAUDE.md の決まりを、残す・移す・短くして残す・消すに分けること。移した決まりが要る場面で必ず読まれること。移したあとも Claude が今と同じように動くことを確かめること。どの会話の始めにも読み込まれる量の上限と、その上限を超える変更を止める PR の検査
- この spec で決めないこと: backend・frontend・terraform の CLAUDE.md。所有者が CLAUDE.md を読みやすいか。Claude Code のメモリ(`MEMORY.md` など)と、スキルの一覧の説明文。これらもどの会話の始めにも読み込まれるが、この spec の対象はリポジトリのルートの CLAUDE.md である。決まりの中身を変えること(決まりを足す、強める、弱める)。ほかの spec の本文の書き直し
- この spec が前提にしていること: Claude Code は、ルートの CLAUDE.md を、どの会話の始めにも読み込み、会話を圧縮したあとにも読み直す。`.github/` と `.claude/` の下のファイルを変える PR は、所有者が承認するまでマージされない(`.github/CODEOWNERS`)。新しい必須のチェックを GitHub のブランチの決まりに足す操作は、所有者が行う

## 要件

### 要件1 ルートの CLAUDE.md には、どの会話でも要る決まりだけを残す

ルートの CLAUDE.md が長いと、Claude は決まりを守りにくくなり、どの会話でも文脈を多く使う。一方で、所有者は、今の AI の質を絶対に下げたくない。そこで、Claude は、決まりの中身を変えずに、決まりの置き場所だけを変える。

1. Claude は、ルートの CLAUDE.md の記述を1つずつ、「残す」「移す」「短くして残す」「消す」のどれか1つに分ける。分ける記述には、決まりの文のほか、表の行、コードの行、説明の文を含める。この spec で「決まり」と書くときは、これらの記述のすべてを指す。
2. 決まりが要る場面が、特定のスキルを実行している間か、特定の場所のファイルを扱う間に限られる決まりは、Claude は「移す」に分ける。それ以外の決まりは、Claude は「残す」に分ける。ただし、Claude は、消してよい決まりを「消す」に、フックや CI がすでに機械的に止めている決まりを「短くして残す」に分ける。また、要る場面(スキルが起動する補助役の会話を含む)で必ず読まれ、会話を圧縮したあとにも読まれる行き先が無い決まりは、Claude は「移す」に分けず、「残す」に分ける。
3. Claude が「消す」に分けてよい決まりは、次の2つだけである。1つ目は、同じ決まりがほかの文書にも書かれていて、その文書がその決まりの要るどの場面でも必ず読まれ、会話を圧縮したあとにも読まれる決まりである。2つ目は、指している物(スキル、コマンド、ファイル、ワークフローなど)がリポジトリから無くなり、もう使われない決まりである。
4. フックや CI がすでに機械的に止めている決まりを短くするときも、Claude は、何が止められるかと、止められたときに Claude がすること(人間への提案など)を、ルートの CLAUDE.md に残す。決まりのうち、フックや CI が止めない部分は、Claude は文を変えずに残す。
5. Claude は、決まりを移すときと短くするときに、決まりの中身を変えない。Claude は、決まりを足さず、強めず、弱めない。「残す」に分けた決まりは、Claude は、参照の直しを除いて文を変えずに残す。
6. Claude は、決まりを、開発に参加する全員の Claude が読むリポジトリの中の文書に移す。Claude は、決まりを、所有者の PC にしか無い場所(Claude Code のメモリなど)に移さない。
7. リポジトリの中の文書やスクリプトが、移した決まりや消した決まりを「CLAUDE.md の〜」のように指しているときは、Claude はその記述を、移した先か残した先を指すように直す。
8. 同じ決まりが、「残す」か「短くして残す」に分けた決まりとほかの文書の両方に書かれているときは、Claude はほかの文書の写しを消す。ただし、そのほかの文書が使われる場面のうち、ルートの CLAUDE.md が読み込まれていない場面(ルートの CLAUDE.md を読まずに動く補助役など)があるときは、Claude はその写しを消さない。また、ほかの承認済みの spec の要件のために「短くして残す」に分けた決まりについては、Claude は、全文を置いた文書の写しを消さない。
9. ほかの承認済みの spec の要件が、ある決まりをルートの CLAUDE.md に書くことを求めているときは、Claude は、その決まりを「消す」にも「移す」にも分けない。その決まりの要るどの場面でも必ず読まれ、会話を圧縮したあとにも読まれるほかの文書に、その決まりの全文があるか、全文を置けるときは、Claude は、その決まりを「短くして残す」に分け、全文をその文書に置く。このとき、Claude は、その spec の要件がルートの CLAUDE.md に書くことを求める中身をすべて、短い文にしてルートの CLAUDE.md に残し、決まりの全文がある文書と節を、その短い文の中で示す。そのような文書に全文を置けないときは、Claude は、その決まりを「残す」に分ける。Claude は、その spec の本文を書き直さない。

### 要件2 決まりごとの行き先を対応表で示す

所有者は CLAUDE.md を読まない。所有者が、決まりが1つも失われていないことを確かめられるように、Claude は決まりごとの行き先を1つの表にする。

1. Claude は、設計の段階で、ルートの CLAUDE.md の決まりをすべて1行ずつ載せた対応表を作り、spec のディレクトリに残す。ルートの CLAUDE.md のどの記述も、対応表のどれかの行に入る。所有者は、設計を承認するときに、この対応表を読める。
2. Claude は、対応表の各行に、決まりの文、決まりの分け方(残す・移す・短くして残す・消す)、行き先の文書と節、その決まりが要る場面を載せる。
3. 「移す」に分けた行と、同じ決まりがほかの文書にあるために「消す」に分けた行には、Claude は、その決まりが要る場面で行き先の文書かほかの文書が必ず読まれる理由と、会話を圧縮したあとにも読まれる理由を書く。
4. 「消す」に分けた行には、Claude は消した理由を書く。同じ決まりがほかの文書にあるときは、Claude はその文書と節を書く。指している物が無くなったときは、Claude は、無くなった物と、無くなったことを確かめた方法を書く。
5. ほかの文書の写しを消した決まりの行には、Claude は、写しを消した文書と節を書く。
6. 設計の段階のあとに、main のルートの CLAUDE.md に決まりが足されるか直されたときは、Claude は、PR を出す前に、足された決まりと直された決まりも対応表に載せ、ほかの決まりと同じく分ける。
7. フックや CI が止めているために「短くして残す」に分けた行には、Claude は、その決まりを止めているフックか CI のファイル、そのフックか CI が本当に止めることを確かめた方法、短くするときに外した文を書く。
8. ほかの承認済みの spec の要件のために「短くして残す」に分けた行には、Claude は、ルートの CLAUDE.md に書くことを求めている spec の名前と、その要件と受入基準の中身、決まりの全文がある文書と節、その文書がその決まりの要るどの場面でも必ず読まれる理由と会話を圧縮したあとにも読まれる理由、短くするときに外した文を書く。

### 要件3 移したあとも、新しい会話で今と同じように動くことを確かめる

決まりを移すと、その決まりが要る場面で Claude が決まりを読まないおそれがある。所有者は、置き場所を変えたことで AI の質が下がっていないことを、実際に Claude を動かした結果で確かめたい。

1. Claude は、PR を出す前に、変更後の文書を読み込んだ新しい会話で、決まりが効く場面を動かす。場面には、`/start`、`/ship`、spec の各段階の流れを含める。
2. Claude は、「移す」と「短くして残す」に分けた決まりと、同じ決まりがほかの文書にあるために「消す」に分けた決まりと、ほかの文書の写しを消した決まりのすべてについて、その決まりが効く場面を1つ以上動かす。1つの場面で複数の決まりを確かめてもよい。
3. Claude は、場面を動かした会話が、変更前の文書ではなく変更後の文書を読み込んだことを、会話の記録から確かめる。
4. 場面の会話が、その場面に効く今の決まりのとおりに動いたら、Claude はその場面を合格とする。
5. Claude は、場面ごとに、場面の名前、確かめた決まり、会話がしたこと、合格か不合格かを記録し、spec のディレクトリに残す。
6. 不合格の場面があったら、Claude は、決まりの行き先か書き方を直し、その場面と、直した文書を読むほかの場面を動かし直す。不合格の場面が残っている間は、Claude は PR を出さない。
7. Claude は、場面の会話に、リポジトリの外へ何かを送らせない。場面の会話は、push、PR の作成、Issue の起票、GitHub へのコメント、マージをしない。リポジトリの外へ送る手順を含む場面では、Claude は、会話が送る直前まで今の決まりのとおりに動いたかを確かめる。
8. Claude は、場面の会話に、所有者の作業フォルダと、ほかのセッションの着手の記録を変えさせない。
9. 所有者は、場面を動かす作業をしない。Claude が場面の会話を始め、結果を確かめる。

### 要件4 会話を圧縮したあとも、移した決まりが守られることを確かめる

Claude Code は、会話を圧縮したあとに、ルートの CLAUDE.md を読み直す。一方で、移した先の文書は、圧縮のあとに読み直されないか、一部しか読み直されないことがある。そのため、所有者は、圧縮のあとにも移した決まりが守られることを確かめたい。

1. Claude は、「移す」に分けた決まりと、同じ決まりがほかの文書にあるために「消す」に分けた決まりと、ほかの承認済みの spec の要件のために「短くして残す」に分けた決まりのすべてについて、行き先の文書かほかの文書を読み込んだあとに会話を圧縮し、圧縮のあとにその決まりが効く場面を1つ以上動かす。
2. 圧縮のあとの会話が今の決まりのとおりに動いたら、Claude はその場面を合格とする。
3. Claude は、圧縮のあとの場面にも、新しい会話での場面と同じく、次のことを当てはめる。Claude は、場面の会話が変更後の文書を読み込んだことを、会話の記録から確かめる。Claude は、場面ごとの記録を spec のディレクトリに残す。不合格の場面があったら、Claude は直して動かし直し、不合格の場面が残っている間は PR を出さない。Claude は、場面の会話に、リポジトリの外へ何かを送らせず、所有者の作業フォルダとほかのセッションの着手の記録を変えさせない。所有者は場面を動かす作業をせず、Claude が場面の会話を始め、結果を確かめる。

### 要件5 どの会話の始めにも読み込まれる量が上限を超える変更を、PR の検査で止める

一度軽くしても、決まりを足し続けると、ルートの CLAUDE.md はまた膨らむ。所有者は、膨らむ変更が人の目を通らずにマージされることを、機械で止めたい。

1. main に向けたすべての PR で、検査が、どの会話の始めにも読み込まれるリポジトリの文書の量を測る。測る文書は、ルートの CLAUDE.md と、ルートの CLAUDE.md と同じくどの会話の始めにも読み込まれるリポジトリの中の文書(ルートの CLAUDE.md が読み込みを指定した文書を含む)である。
2. 測った量が上限を超えたら、検査は失敗し、その PR はマージされない。
3. 検査が失敗したときは、検査は、測った量、上限、測った文書の一覧を出す。あわせて、検査は、決まりを移すか短くして上限に収めることと、上限を上げる変更を自分の判断で入れないことを、Claude に向けた文で出す。
4. 測った量が上限以下なら、検査は成功する。
5. 検査が、測る文書か上限の値を読めないときは、検査は失敗する。
6. Claude は、この検査を必須のチェックとして期待一覧(`.github/audit/required-checks.json`)に登録する変更を、この spec の PR に含める。
7. Claude は、上限の値を、軽くしたあとの量をもとに設計の段階で決め、値と決めた理由を design.md に書く。所有者は、設計を承認するときに上限の値を確かめる。

### 要件6 上限を上げる変更は、所有者が承認するまでマージされない

上限を上げる変更が自動でマージされると、検査は膨らむ変更を止められなくなる。所有者は、上限を上げるかどうかを自分で決めたい。

1. 上限の値を上げる PR は、所有者が承認するまでマージされない。
2. 検査の測り方を変える PR と、この検査を外す PR も、所有者が承認するまでマージされない。
3. Claude の PR がこの検査で止まったら、Claude は、決まりを移すか短くして上限に収める。上限を上げる必要があると Claude が判断したときは、Claude は、上限を上げる理由を添えて所有者に提案し、上限を上げる変更を自分の判断で PR に入れない。
