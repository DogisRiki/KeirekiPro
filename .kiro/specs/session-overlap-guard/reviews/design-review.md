### 申告

**1. ほかの作業フォルダの spec の変更が main に入っているかを、差分を `origin/main` に逆向きに当てられるかで判定する** — design.md 部品「session.sh check-spec」手順4、research.md「比べた案」

- Issue の記載: なし。Issue は「別のセッションで作業中の spec」としか書いていない
- 決めたこと: W の分かれ目からの spec の差分(前後の行を含めない)を `origin/main` に逆向きに当て、当てられれば「直していない」、当てられなければ「直している」とする
- 他にありえた選択肢: PR の状態(マージ済みかどうか)で判定する。コミットの先祖関係で判定する(squash のため不可)。3方向のマージで判定する(隣の行で衝突するため不可。research.md で試して除外)
- 外れていた場合: 先のセッションの PR がマージされたあとに、main が同じ行をさらに別の中身に変えていると、先のセッションが開いている限り「直している」と出続ける。所有者が「やめていない」と答えると、Claude は「マージのあとに打ち直すよう」知らせるが、すでにマージ済みなので打ち直しても同じ問いに戻る。抜けるには、所有者が「やめた」と答える(先のセッションの記録を消す)か、先のセッションを閉じるしかない。research.md の「弱いところ」に書かれているが、design.md の「失敗したときの扱い」には出ていない

**2. `/start` の最初の調べが空だったセッションは、ブランチを作る前から「作業中のセッション」に数えられる** — design.md 部品「session.sh check-start の変更」予約の書き込み、research.md「危うさと手当て」

- Issue の記載: あり。「後から始めたセッションがそれに気づいて止まる」「先のセッションがまだIssueを調べている途中でも」(要件1.2)
- 決めたこと: `check-start` が `issues/<N>.json` を予約として書く。作業中のセッションの見分け方(`issues/` に同じ `session_id` か `folder` の記録がある)は変えないので、`/start` を打っただけで判断の前に止めた・閉じ忘れたセッションも、開いている間は作業中に数えられる。`capacity.active`(返答している途中のものだけ)と `folder_conflict` と `started` の問いに影響する
- 他にありえた選択肢: 予約を別の種類の記録(たとえば `reservations/`)に置き、作業中の見分け方には数えない。または、`claim` だけを錠の中で行い、ブランチを作る時点で断る(research.md の案2)
- 外れていた場合: `/start` を打って判断の報告を読んだだけで何もしなかったセッションが、ほかのセッションの `/start` で「やめたか」の問いの相手になる。所有者が「やめた」と答えれば進めるので、手戻りは問い1回にとどまる

**3. spec を直すコマンドの手順を続けるときに、`git merge origin/main` でブランチに main の最新を取り込む** — design.md 部品「kiro-spec-init スキルの変更」手順4、research.md「判断: main の最新の取り込みは `git merge origin/main` で行う」

- Issue の記載: なし。要件2.7 が「取り込む」「取り込めないときは止まる」と定めている
- 決めたこと: `origin/main` が HEAD の先祖でなければ `git merge origin/main` を打つ。失敗したら `MERGE_HEAD` があるときだけ `git merge --abort` を打ち、理由を伝えて止まる
- 他にありえた選択肢: spec のディレクトリだけを `origin/main` から写す(このセッションの変更を消すので除外)。取り込まずに進め、衝突は `/ship` の取り込みに任せる
- 外れていた場合: ブランチにマージコミットが増える(`/ship` も同じことをするので新しい形ではない)。このセッションの作業フォルダに、main が変えたファイルへのコミットしていない変更があると、git は hunk が重ならなくてもマージを始めずに断る。このときは要件2.7の「取り込めないとき」として止まり、所有者が手で取り込むことになる

**4. spec の予約は書いてから600秒で切れる** — design.md 部品「session.sh check-spec」状態の持ち方、research.md「判断: spec を直すコマンドの同時の打ち込みは、10分で切れる予約で止める」

- Issue の記載: なし。要件2.5 が「2つの調べが同じ時に重なっても片方だけに書き換えさせる」と定めている
- 決めたこと: 調べが空だったセッションが `specs/<feature>.json` を書き、600秒の間だけほかのセッションの `check-spec` が `starting` として止める。600秒たったあとは、手順4の差分の判定だけが止める
- 他にありえた選択肢: 予約を `/kiro-spec-init` の終わりに消す(途中で止まると残るので除外)。調べと書き換えを1つの錠に入れる(書き換えはスキルの手順なので不可)
- 外れていた場合: 先のセッションの `/kiro-spec-init` が、`check-spec` のあと600秒より長く spec を書かずにいる(所有者が問いに答えないまま置いた、など)と、あとのセッションが進んでしまう。あとのセッションが spec を書いたあとに先のセッションが書くと、同じ spec を2つのセッションが直す状態に戻る

**5. 予約だけの作りかけの「やめた」は `end` で先のセッションの記録を消し、先のセッションは `claim` で断られて止まる** — design.md 部品「session.sh claim と takeover の変更」、処理の流れ「`/start` の最初の調べ(同じIssue)」の決めごと、research.md「判断: 予約だけの作りかけの「やめた」は `end` で扱う」

- Issue の記載: なし。要件1.4 が「やめた」のあとの進み方を定めている
- 決めたこと: `takeover --from` を使わず、`end` で記録を消して `check-start` を呼び直す。先のセッションが動き続けていれば、ブランチを作って `claim` を呼んだ時点で終了コード1で止まる
- 他にありえた選択肢: 予約だけのときも `takeover --from` で扱う(写すものが無いのに、いまの作業フォルダがきれいでないと断られるので除外)。先のセッションを止めずに、あとのセッションが止まる
- 外れていた場合: 先のセッションの Claude は、Issueの本文とコードを調べ終え、ブランチを作ってから止まる。その調べは無駄になり、作ったブランチが作業フォルダに残る。先のセッションが「問いがあるとき」の報告を出す前に止まるので、所有者はそのセッションで答えを求められない
