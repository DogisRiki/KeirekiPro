## サイクル1 往復1(2026-10-11)

### 申告

**1. 作業中のセッションが無い作業フォルダに残った spec の変更は、あとのセッションを止めない** — requirements.md 要件2 受入基準1・6

- Issue の記載: あり。「別のセッションで作業中の spec を、あとから始めたセッションでも直そうとしたとき、あとのセッションがそれに気づいて、spec を書き換える前に止まる」(AIの提案を了承)。「作業中」の語で範囲が絞られている
- 決めたこと: 止める対象を「ほかの作業中のセッション」の作業フォルダにある、main にまだ入っていない spec の変更に限った。セッションが閉じられた作業フォルダにその spec の変更(コミット済みで PR が開いたままのものを含む)が残っていても、あとのセッションは止まらずに進む
- 他にありえた選択肢: セッションの作業中かどうかに依らず、main にまだ入っていない同じ spec の変更がどこかの作業フォルダかブランチにあれば止める(または、そのことを所有者に示してから尋ねる)
- 外れていた場合: 先のセッションを閉じたあとに PR が残っている間に、あとのセッションが同じ spec を main から直し進める。2つの PR が同じ spec のファイルを別々に変えるので、あとの PR が main に合わせる段階で衝突し、所有者が気づくのは PR の段階になる

**2. 同じ spec を直しているかの調べは、`/kiro-spec-init #<Issue番号> <spec の名前>` を打ったときだけ行う** — requirements.md 範囲「この spec で決めないこと」2つ目・3つ目、要件2 受入基準1

- Issue の記載: あり。確かめ方に「両方で spec を直すコマンドを打つ。あとのセッションは spec を書き換えずに止まる」。「どうなれば解決か」の「直そうとしたとき」がどの時点かは書かれていない
- 決めたこと: `/start` の判断の段階と、spec の各段階のコマンド(要件・設計・タスクの生成、審査、実装)では調べず、既存の spec を直すコマンドのときだけ調べる
- 他にありえた選択肢: `/start` の判断が「spec <feature> を直す」になった時点でも調べ、コマンドを打つよう依頼する前に所有者に知らせる。または、spec のファイルを書き換えるすべてのコマンドで調べる
- 外れていた場合: `/start` の時点では何も知らされず、所有者がコマンドを打ってから初めて止まるので、コマンドを打つ手間が1回無駄になる。実害は手間にとどまり、spec が二重に直されることは起きない

**3. spec を直すコマンドの手順を続けるときは、その spec をこのセッションの作業フォルダで main の最新に合わせてから書き換える** — requirements.md 要件2 受入基準7

- Issue の記載: なし。Issue は「止まる」ことだけを求めており、先のセッションの直しがマージされたあとの続け方は書かれていない
- 決めたこと: 先のセッションの直しがマージされたあとに所有者がコマンドを打ち直すと、マージされた直しを含んだ spec を直せるよう、書き換える前に spec を main の最新に合わせる
- 他にありえた選択肢: 合わせずにそのまま直す(衝突は PR をマージするときに `git merge origin/main` で表面化する)。または、このセッションのブランチが main より古いときは止まって、所有者にブランチを作り直してもらう
- 外れていた場合: この決めごと自体が無いと、打ち直したあとのセッションが古い spec を直し、PR の段階で衝突する。決めごとの中身の曖昧さは、指摘 R1-1-1 に書いた

**4. 「やめた」と答えたら、先のセッションの spec の変更を引き継がずに進む** — requirements.md 要件2 受入基準3

- Issue の記載: なし。Issue には、止まったあとの所有者の答えと Claude の動きは書かれていない
- 決めたこと: 所有者が「やめた」と答えたら、あとのセッションは先のセッションの作業フォルダに残った spec の変更を引き継がず、main の最新の spec を直す。「やめた」以外なら止まり、マージのあとに打ち直すよう知らせる
- 他にありえた選択肢: 同じIssueのときと同じく、先のセッションの作りかけ(spec の変更)を引き継ぐかどうかを尋ねる
- 外れていた場合: 先のセッションで途中まで直した spec の変更がそのまま放置され、所有者があとでその変更を使いたいときは、先のセッションのIssueに `/start` を打ち直して引き継ぐ手順を踏むことになる。二重の直しは起きない

### 申告

**1. 「main にまだ入っていない」かどうかは、ファイルの中身で判定する** — requirements.md 要件2 受入基準1(往復2の修正で足された部分)

- Issue の記載: なし。Issue は「別のセッションで作業中の spec」としか書いておらず、作業中かどうかの見分け方は書かれていない
