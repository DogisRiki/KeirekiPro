# 調べたことと設計の判断

## まとめ

- spec の名前: `session-overlap-guard`
- 調べの範囲: 既存の仕組みの拡張(spec `parallel-sessions` で作った `session.sh` と、スキル `/start` `/kiro-spec-init`)
- 分かったこと:
  - `session.sh check-start` は調べるだけで記録を書かない。Issueの記録 `issues/<N>.json` を書くのは、`/start` の Step 7 でブランチを作った直後の `session.sh claim` だけである(`.claude/scripts/parallel/session.sh` の `kp_session_check_start` と `kp_session_claim`、`.claude/skills/start/SKILL.md` の Step 7 の手順1)。そのため、先のセッションがIssueの本文とコードを調べている数分の間、ほかのセッションの `check-start` には何も見えない
  - `claim` は、Issueの記録がすでにあれば、誰の記録かを確かめずに `folder` `branch` `session_id` を書き直す。2つのセッションの `check-start` がどちらも空を返すと、あとから `claim` したほうが記録を奪う
  - `/kiro-spec-init` の更新の形(`.claude/skills/kiro-spec-init/SKILL.md` の Update Mode Steps)は、ほかの作業フォルダを一切見ない
  - このリポジトリのPRは squash でマージされる(`.github/scripts/reserve-auto-merge.sh` の `gh pr merge --auto --squash`)。ブランチのコミットは、マージのあとも main の先祖にならない

## 調べた記録

### 着手の記録を書く時点

- きっかけ: Issue #507 の「きっかけ」の1つ目(2つのセッションで同じ #490 に `/start` を打つと、どちらも止まらなかった)
- 見たもの: `session.sh` の `kp_session_check_start`(JSON を出すだけ)、`kp_session_claim`(記録があれば無条件に書き直す)、`/start` の Step 1.5 と Step 7
- 分かったこと: `check-start` から `claim` までの間(Step 2 から Step 6 の調べと判断)に、ほかのセッションから着手が見えない。2つの `check-start` が同じ時に動いたときに片方だけを通す仕組み(錠)も無い
- 設計への影響: `check-start` が、調べの結果がすべて空のときに、その場で着手の記録(予約)を書く。調べと記録の書き込みを1つの錠の中で行い、同じ時に動いた2つの `check-start` の片方だけが予約を書けるようにする

### 同じ spec を直しているかの見分け方

- きっかけ: 要件2の受入基準1(main にまだ入っていない変更を中身で判定する)
- 見たもの: `git merge-tree --write-tree` の公式の文書(https://git-scm.com/docs/git-merge-tree)と、`git apply` の公式の文書(https://git-scm.com/docs/git-apply)の `--cached` `--check` `-R` `--unidiff-zero`。作業PCの git は 2.56.0
- 試したこと(2026-10-11、scratchpad の一時的なリポジトリ): 枝のブランチで1行目を変え、main で2行目を変えたあと、枝の変更を squash で main に入れた
  - `git merge-tree --write-tree <main> <枝>` は、squash で入れたあとも終了コード1(衝突)を返した。隣り合う行を両側が変えると、git は衝突とみなすためである。そのため、マージの木で見る案は、squash のあとも「直している」と取り違える
  - 枝の変更を `git diff -U0`(前後の行を含めない差分)で取り、main の木を読み込んだ一時的な索引に `git apply --cached --check -R --unidiff-zero` で逆向きに当てると、次のとおりになった。squash で入れる前は失敗した(main に入っていない)。squash で入れたあとは成功した(main に入っている)。squash のあとに隣の行がさらに変わっても成功した。main が同じ行を別の中身に変えたときは失敗した。枝が spec を変えていないときは差分が空になった
- 設計への影響(はじめの設計。のちに取りやめた): ほかの作業フォルダの spec のディレクトリの中身を一時的なコミット S にまとめ、S と `origin/main` の分かれ目から S までの spec のディレクトリの差分を、前後の行を含めずに取る。差分を `origin/main` に逆向きに当てられれば、変更はすべて main に入っているとみなす

### 差分を逆向きに当てる判定の誤りと、作り直した判定(2026-10-11、タスク2.1の実装のレビューで見つかった)

- きっかけ: タスク2.1の実装をレビューしたエージェントが、はじめの設計の判定が要件2の受入基準1を満たさないことを、実際に `check-spec` を呼んで見つけた
- 分かったこと:
  - 行を消しただけの変更のかたまりを、前後の行を含めずに逆向きに当てると、「前後を見ない行の挿入」になり、どこにでも当てられる。そのため、ほかの作業フォルダが行を消しただけで、まだマージしていなくても、「main に入っている」と取り違える。先頭の行を消したとき、ファイルを空にしたときも同じだった
  - 書き換えた先の中身が `origin/main` の同じファイルの別の行にあると、`git apply` が位置をずらして当て、これも「main に入っている」と取り違える
  - はじめに Claude が試したのは書き換えの場合だけで、行を消す場合を試していなかった
- 作り直しの途中で試して退けた案: ファイルごとに、ほかの作業フォルダが消した行と足した行を中身と数で数え、`origin/main` の変更に同じ中身の行が同じ数以上あれば「入っている」とみなす案。12通りの場面では期待どおりだったが、行の位置を見ないので、`origin/main` が同じファイルの別の場所で同じ中身の行(空行など)を消していると、「入っている」と取り違える
- 作り直しの途中で試して退けた案(2つ目): 変更のかたまりを位置で重なりごとにまとめ、まとまりの中で行の対応(最長共通部分列)を取って比べる案。design の2回目のレビュー(D2-1-1)で、まとまりの中に同じ中身の行(空行など)が2つあると、対応のつけ方で答えが変わることが分かった。例: ファイルの2行目と4行目が空行で、ほかの作業フォルダが2行目を消し、`origin/main`(マージしていない)が3行目を書き換えて4行目を消すと、main の空行を4行目に対応させたときに「入っている」と取り違える
- 作り直した判定: ファイルごとに、ほかの作業フォルダの変更のかたまりそれぞれについて、分かれ目のファイルの行の位置で重なるか接する `origin/main` の変更のかたまりを集め、行の位置だけで比べる。置き換えた行がどれも main のかたまりの範囲に入っていて、足した行が main のかたまりの足した行の中に同じ順で現れるときだけ、「入っている」とみなす(design.md の部品「session.sh check-spec」の手順4)
- 試したこと: scratchpad の判定のスクリプト `pos-judge.pl` と、場面を作る `pos-probe.sh` で、次の30通りを試し、すべて期待どおりだった(2026-10-11。差分の作り方は `--diff-algorithm=myers --indent-heuristic --inter-hunk-context=0` に固定し、環境変数 `GIT_DIFF_OPTS` を外した。`GIT_DIFF_OPTS=-u3` を置いたまま打つと、同じ場面を「入っている」と取り違えることも確かめた。`--inter-hunk-context=0` を付けないと、`git config diff.interHunkContext 3` を置いたときに、4行目を消し main が3行目と5行目を書き換えた場面を「入っている」と取り違えることを確かめた)
  - 「直している」になるべき場面: マージしていない書き換え(main が隣の行を変えていても)、main が同じ行を別の中身に変えた、マージのあと main が同じ行をさらに書き換えた、行を1行消した、先頭の行を消した、ファイルを空にした、`a` を `c` に書き換え main の別の行に `c` がある、2行目の空行を消し main が4行目の空行を消した、2行目の空行を消し main が3行目を書き換えて4行目の空行を消した、4行目の空行を消し main が2行目の空行を消して3行目を書き換えた、3行目と4行目を消し main が4行目だけを書き換えた、4行目を消し main が3行目と5行目を書き換えた(`diff.interHunkContext` を置いた場合も、`GIT_DIFF_OPTS` を置いた場合も)、4行目を消し main が4行目と5行目の間に行を足した、行を1行足した、main が同じ中身の行を別の場所に足した、新しいファイルを足した、spec のディレクトリを消した
  - 「直していない」になるべき場面: squash でマージしたあとに隣の行がさらに変わった、行を消した変更を squash でマージした、空行を消した変更を squash でマージした(隣の行の変更ありも)、4行目の空行を消した変更を squash でマージし3行目も書き換えた、3行目と4行目を消した変更を squash でマージした、行を足した変更を squash でマージし直後の行も変わった、行を足した変更を squash でマージし直前の行も変わった、新しいファイルを squash でマージした、spec のディレクトリを消した変更を squash でマージした、古い main から作ったブランチで spec を変えていない
- 設計への影響: design.md の部品「session.sh check-spec」の手順4を、この判定に書き換えた。テストの方針に、上の場面を足した

## 設計の判断

### 判断: 着手の予約を `check-start` が書く

- きっかけ: 要件1の受入基準1と3
- 比べた案:
  1. `check-start` が予約を書く
  2. `claim` だけを錠の中で行い、記録があれば断る
- 選んだ案: 1。あわせて、`claim` も、記録がほかのセッションのものなら断る
- 理由: 2では、あとのセッションが止まるのが、Issueの本文とコードを調べ終えてブランチを作るときになる。要件1の受入基準2は、先のセッションがまだブランチを作っていなくても止まることを求める
- 失うもの: 予約だけのIssueの記録(`branch` が空の記録)が増える。予約したセッションが閉じれば、予約は作業中に数えなくなり、次の `check-start` が上書きする
- あとで確かめること: 先のセッションが予約したあと、所有者が「やめた」と答え、あとのセッションが予約を取り直したときに、先のセッションの `claim` が断られること(requirements の審査の指摘 R1-2-2)

### 判断: 予約だけの作りかけの「やめた」は `end` で扱う

- きっかけ: 要件1の受入基準4と、審査の指摘 R1-1-3
- 比べた案:
  1. 既存の作りかけと同じく `takeover --from` を呼ぶ
  2. 予約だけ(作りかけの種類が `started` だけ)のときは、そのセッションの記録を `end` で消し、`check-start` を呼び直す
- 選んだ案: 2
- 理由: 予約だけのときは、写す作りかけが無い。`takeover --from` は、いまの作業フォルダがきれいでないと断り、前の作業フォルダの土台がいまのブランチに無いと断るので、写すものが無いのに着手を止めてしまう。予約に加えて spec やブランチもあるときは、既存の問いと同じ1つの問いで尋ね、「やめた」なら既存どおり `takeover` で引き継ぐ

### 判断: spec を直すコマンドの同時の打ち込みは、10分で切れる予約で止める

- きっかけ: 要件2の受入基準5
- 比べた案:
  1. 調べと spec の書き換えを1つの錠の中で行う
  2. 調べが空だったセッションが、spec の名前ごとの予約を書く。予約は10分で切れる
  3. 予約を書き、`/kiro-spec-init` の終わりに消す
- 選んだ案: 2
- 理由: 1は、spec の書き換えを Claude がスキルの手順で行うので、スクリプトの錠の中に入れられない。3は、`/kiro-spec-init` が途中で止まると予約が残り、所有者が問いに答えないと消えない。`/kiro-spec-init` は spec.json と requirements.md を書くだけなので、10分あれば書き終える。書き終えたあとは、中身の調べ(変更のかたまりを位置で重ねて比べる調べ)が止める
- 失うもの: 先のセッションの `/kiro-spec-init` が10分より長くかかり、まだ spec を書いていないときに、あとのセッションが進んでしまう

### 判断: main の最新の取り込みは `git merge origin/main` で行う

- きっかけ: 要件2の受入基準7
- 比べた案:
  1. ブランチに `origin/main` をマージする
  2. spec のディレクトリだけを `origin/main` から写す
- 選んだ案: 1
- 理由: 2は、このセッションがその spec に加えた変更を消す。1なら、git がこのセッションの変更を残したまま main の直しを取り込み、同じ箇所が別々に変わっていれば衝突として止まる。`/ship` も、PRのブランチを main に合わせるときに同じ `git merge origin/main` を使っている(`.claude/skills/ship/SKILL.md` の「手元での取り込み」)

### 判断: spec を直しているかを、変更のかたまりの位置だけで比べて判定する

- きっかけ: 要件2の受入基準1と、タスク2.1の実装のレビューで見つかったはじめの判定の誤り
- 比べた案: 「比べた案」の表の、差分を逆向きに当てる案、消した行と足した行を中身と数で比べる案、まとまりの中で行の対応を取る案、変更のかたまりを位置だけで比べる案
- 選んだ案: 変更のかたまりを位置だけで比べる案
- 理由: 行の中身や行の対応で比べる案は、同じ中身の行(空行など)が近くにあると、どの行を比べるかで答えが変わる。M の行の位置は、W の変更と main の変更の両方で同じ M を基準にするので、取り違えが起きない
- 要件の定めどおりに「入っている」とする場面: W が行を消しただけで、main がその行を別の中身に書き換えているときは、W が消した行の中身は main に無いので、「入っている」とみなす。要件2の受入基準1は、W の変更が main に中身として入っているかで判定すると定めているためである
- 失うもの: main が、W の変更と同じ中身を、W と違う位置の区切りでまとめて書いていると(git の差分の区切りが W の差分と違うと)、「直している」とみなす。このときは、所有者が「やめた」と答えれば進める。止まる側に倒れるので、二重の直しは起きない

## 危うさと手当て

- 予約を書くと、`/start` を打っただけで着手をやめたセッションも、開いている間は作業中に数えられる。手当て: ほかのセッションで同じIssueに `/start` を打つと、Claude が「やめたか」を尋ね、「やめた」なら `end` で記録を消して進む
- 錠を持ったまま `session.sh` が落ちると、錠が残る。手当て: lib.sh の `_kp_lock` は、60秒より古い錠を壊して取り直す
- セッションのIDが無いとき(SessionStart のフックの文が見つからないとき)は、予約の持ち主のセッションを見分けられない。手当て: 持ち主のセッションのIDが空の予約は、ほかのセッションの `check-start` で `started` として出さない(今までどおりブランチを作るまで見えない)。`claim` は作業フォルダで持ち主を見分ける
