# 要件

## 元の要望
Issue #507: 別のセッションと同じIssueや同じ spec に手を付けても、あとから始めたセッションが止まらない

### きっかけ

- #481 の確かめとして、2つのセッションで同じ #490 に `/start` を打ったところ、どちらのセッションも止まらずに作業を始めた(2026-10-06)。
- #507 と #520 を2つのセッションで並行して進めていたところ、2つが同じ spec を直していることに所有者が気づき、起票を指示した(2026-10-09。#530 から統合)。

### 困っていること

- 同じIssueを2つのセッションで続けて始めると、後から始めたセッションが気づかずに作業を進めることがある。同じIssueの作業が2つ並び、PRが2つできるおそれがある。(AIの提案を了承)
- 別々のIssueを2つのセッションで始めたとき、2つのIssueが同じ spec を直すことになっても、どちらのセッションも止まらない。2つのセッションが同じ spec を別々に直し進め、所有者が気づくまで、承認のやり直しと直しが二重に進む。(AIの提案を了承)

### どうなれば解決か

- 同じIssueを別のセッションでも始めようとしたとき、後から始めたセッションがそれに気づいて止まる。2つのセッションでほぼ同時に `/start` を打ったときも同じとする。(AIの提案を了承)
- 別のセッションで作業中の spec を、あとから始めたセッションでも直そうとしたとき、あとのセッションがそれに気づいて、spec を書き換える前に止まる。(AIの提案を了承)
- 確かめ方:
  - 2つのセッションで、同じIssueに数秒差で `/start` を打つ。片方だけが作業を進め、もう片方は止まる。(AIの提案を了承)
  - 2つのセッションで、同じ spec を直す別々のIssueに `/start` を打ち、両方で spec を直すコマンドを打つ。あとのセッションは spec を書き換えずに止まる。(AIの提案を了承)

## はじめに

この spec でいうセッションは、所有者が Claude Code で開く会話の1つを指す。並行して進めるセッションは、それぞれ別の作業フォルダ(worktree)を持つ。作業中のセッションとは、所有者が開いたままにしていて、`/start` で着手したIssueの作業を続けているセッションを指す。所有者が閉じたセッションや、所有者が「やめた」と答えたセッションは、作業中のセッションに当たらない。

今の仕組みでは、Claude は、`/start` の最初の調べで同じIssueの作りかけ(spec、ブランチ、コミットしていない変更)を探す。しかし、Claude が「このIssueに着手した」ことを残すのは、Issueを調べ終えてブランチを作ったときである。そのため、先に `/start` を打ったセッションがIssueを調べている間に、別のセッションで同じIssueに `/start` を打つと、あとのセッションは作りかけを見つけられずに作業を始める。

また、Claude は、既存の spec を新しいIssueのために直すコマンドを所有者が打ったときに、ほかのセッションが同じ spec を直しているかどうかを調べない。そのため、別々のIssueを進める2つのセッションが、同じ spec を別々に直し進める。

この spec は、どちらの場合も、あとから手を付けたセッションが気づいて止まるようにする。

## 範囲

- この spec で決めること:
  - 同じIssueに2つのセッションで `/start` を打ったときに、あとのセッションが止まること。2つの `/start` がほぼ同時のときと、先のセッションがまだIssueを調べている途中のときも含める
  - 既存の spec を新しいIssueのために直すコマンド(`/kiro-spec-init #<Issue番号> <spec の名前>`)を打ったときに、ほかの作業中のセッションが同じ spec を直していたら、あとのセッションが spec を書き換える前に止まること
  - 止まったときに Claude が所有者に示すことと、所有者の答えに応じた Claude の動き
- この spec で決めないこと:
  - 同じ作業フォルダで2つ目のセッションを始めたときの動きと、同じIssueの作りかけを引き継ぐときの動き。これらは spec `parallel-sessions` で決めたとおりのままにする
  - `/start` の判断の段階で、ほかのセッションが同じ spec を直しているかどうかを調べること
  - spec の各段階のコマンド(要件・設計・タスクの生成、審査、実装)を打ったときの調べ。既存の spec をほかのIssueのために直すときは、所有者が必ず spec を直すコマンド(`/kiro-spec-init #<Issue番号> <spec の名前>`)を先に打つので、Claude はそのコマンドのときだけ、ほかのセッションが同じ spec を直しているかどうかを調べる
  - 新しい spec の名前がほかのセッションの spec と重なるときの動き。今の `/kiro-spec-init` の決まりのままにする
  - PRで走るチェック(GitHub Actions)で、同じIssueや同じ spec の重なりを止めること
- この spec が前提にしていること:
  - 所有者は、並行して進めるセッションを、worktree を選んで開く
  - セッションが作業中かどうかの見分け方は、spec `parallel-sessions` で決めたとおりとする
  - この spec の変更の多くは、所有者の承認が要るファイル(`.claude/` の下)に及ぶ。そのため、この spec のPRは、所有者が承認するまで自動ではマージされない

## 要件

### 要件1 同じIssueに2つのセッションで `/start` を打つと、あとのセッションが止まる

同じIssueの作業が2つのセッションで並ぶと、同じIssueのブランチやPRが2つでき、どちらが正しいか分からなくなる。所有者は、先のセッションがまだIssueを調べている途中でも、あとのセッションに止まってほしい。2つのセッションでほぼ同時に `/start` を打ったときも、所有者は片方だけに進んでほしい。

1. 所有者があるセッションで `/start #N` を打ち、Claude の最初の調べでIssue #N の作りかけも、Issue #N に着手した作業中のセッションも見つからなかったら、Claude は、その最初の調べを終えた時点から、このセッションをIssue #N に着手したセッションとして扱う。Claude は、このセッションがIssueの本文とコードを調べ終えてブランチを作る前から、このセッションがIssue #N に着手したことがほかのセッションに分かるようにする。
2. 所有者が別のセッションで `/start #N` を打ったときに、Issue #N に着手した作業中のセッションがほかにあれば、あとのセッションの Claude は、spec もブランチも作らずに止まる。先のセッションがまだ spec もブランチも作っていなくても、Claude は止まる。Claude は、先のセッションの作業フォルダの場所と、先のセッションを始めた時刻と最後に操作された時刻を所有者に示し、先のセッションをやめたかどうかを尋ねる。
3. 2つのセッションの最初の調べが同じ時に重なっても、Claude は、片方のセッションだけをIssue #N に着手したセッションとして扱う。もう片方のセッションの Claude は、spec もブランチも作らずに止まり、Issue #N に着手したセッションとして扱われたほうのセッションをやめたかどうかを所有者に尋ねる。
4. 先のセッションをやめたかどうかの問いに所有者が「やめた」と答えたら、あとのセッションの Claude は、`/start` の手順を続ける。そのあとは、Claude は、あとのセッションをIssue #N に着手したセッションとして扱う。所有者が「やめた」以外で答えたら、あとのセッションの Claude は、このセッションではIssue #N の作業をしない。
5. 先のセッションを所有者が閉じていて、Issue #N の作りかけも残っていないときは、あとのセッションの Claude は、所有者に尋ねずに `/start` の手順を続ける。
6. 同じセッションで所有者が `/start #N` を打ち直したときは、Claude は、そのセッション自身を理由に止まらない。

### 要件2 ほかの作業中のセッションが直している spec を直そうとすると、あとのセッションが止まる

2つのセッションが同じ spec を別々に直すと、承認のやり直しと直しが二重に進み、所有者が気づくまで無駄な作業が続く。所有者は、あとから同じ spec を直そうとしたセッションに、spec を書き換える前に止まってほしい。また、所有者は、先のセッションの直しがマージされたあとには、あとのセッションでその spec の直しを続けられるようにしたい。

1. 所有者があるセッションで、既存の spec を新しいIssueのために直すコマンド(`/kiro-spec-init #<Issue番号> <spec の名前>`)を打ったら、Claude は、spec を書き換える前に、ほかの作業中のセッションがその spec を直しているかどうかを調べる。ほかのセッションがその spec を直しているとは、そのセッションの作業フォルダに、その spec のファイルの変更のうち main にまだ入っていないもの(コミットしていない変更と、コミットしたがマージされていない変更)があることを指す。main にまだ入っていない変更とは、そのセッションが加えた変更のうち、main の最新の spec のファイルに中身として入っていないものを指す。このリポジトリのPRは squash でマージされるので、Claude は、そのセッションのコミットが main に含まれるかどうかでは判定しない。
2. ほかの作業中のセッションがその spec を直していたら、Claude は、spec のファイルを1つも書き換えずに止まる。Claude は、spec の名前と、そのセッションの作業フォルダの場所と、そのセッションが着手しているIssueの番号と、そのセッションを始めた時刻と最後に操作された時刻を所有者に示し、そのセッションをやめたかどうかを尋ねる。ほかの作業中のセッションが2つ以上その spec を直していたら、Claude は、すべてのセッションを示してから、セッションごとに尋ねる。
3. そのセッションをやめたかどうかの問いに所有者が「やめた」と答えたら、Claude は、そのセッションを作業中のセッションとして扱わずに、調べをやり直す。その spec を直しているほかの作業中のセッションが残っていなければ、Claude は、spec を直すコマンドの手順を続ける。
4. そのセッションをやめたかどうかの問いに所有者が「やめた」以外で答えたら、Claude は、spec のファイルを書き換えずに止まる。Claude は、ほかのセッションの直しがマージされたあとに同じコマンドを打ち直すよう、所有者に知らせる。
5. 2つのセッションで同じ spec を直すコマンドがほぼ同時に打たれ、2つの調べが同じ時に重なっても、Claude は、片方のセッションだけに spec を書き換えさせる。もう片方のセッションの Claude は、spec のファイルを書き換えずに止まり、書き換えを進めるセッションをやめたかどうかを所有者に尋ねる。
6. その spec の main にまだ入っていない変更が、作業中のセッションの無い作業フォルダにだけあるときは、Claude は止まらずに、spec を直すコマンドの手順を続ける。
7. Claude が spec を直すコマンドの手順を続けるときは、Claude は、spec を書き換える前に、main の最新にあるその spec の直しを、このセッションの作業フォルダに取り込む。そのため、ほかのセッションの直しがマージされたあとに所有者がコマンドを打ち直すと、Claude は、マージされた直しを含んだ spec を直す。このセッションの作業フォルダに、その spec の main にまだ入っていない変更(このセッションが前に直した分)があるときは、Claude は、その変更を消さずに main の最新の直しを取り込む。Claude が main の最新の直しを取り込めないとき(このセッションの変更と main の最新の直しが同じ箇所を別々に変えているときなど)は、Claude は spec のファイルを書き換えずに止まり、取り込めなかった理由を所有者に知らせる。

### 要件3 調べられないときは進まない

ほかのセッションの様子を調べられないまま Claude が進むと、所有者が止めたかった重なりを Claude が見逃す。所有者は、Claude が調べられなかったときには、Claude に進まずに、調べられなかったことを知らせてほしい。

1. 同じIssueに着手したセッションの調べ、または同じ spec を直しているセッションの調べを、Claude が終えられなかったときは、Claude は、`/start` の手順も spec を直すコマンドの手順も続けず、spec もブランチも作らない。Claude は、調べを終えられなかったことと、その理由を所有者に知らせる。
