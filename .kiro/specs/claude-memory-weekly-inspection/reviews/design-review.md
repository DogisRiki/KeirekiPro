### 申告

**1. 点検を OS の予定の仕組み(タスク スケジューラ・launchd・cron)で起動し、判断を `claude -p` に任せる** — 全体の構成、部品「memory-inspect.sh の enable と disable」

- Issue の記載: あり。「所有者が何も打たなくても、点検が週に1回、自動で行われる」。動かす仕組みは書かれていない(requirements の「この spec で決めないこと」で design に渡された)
- 決めたこと: 開発者の PC の OS の予定の仕組みに週1回の予定を登録し、スクリプトが `claude -p` を呼ぶ。開発者は `enable` を1回打つ
- 他にありえた選択肢: Claude Desktop の予定のタスク。Anthropic のクラウドの予定。会話の始めに前の点検から7日を過ぎていたら動かす

**2. 点検の中の Claude に道具を1つも渡さず、直し方を `edit`・`append_index_line`・`delete` の3つの JSON に限り、事実の調べを10種類の読むだけのコマンドに限る。呼び出しは3回まで** — 部品「点検の中の Claude を呼ぶ部品」「inspect-prompt.md と plan-schema.json」「memory-inspect.pl apply」

- Issue の記載: あり。「点検で見つけた汚染は、種類を問わず Claude が直し」。直し方の形は書かれていない
- 決めたこと: 点検の中の Claude は判断だけを返し、スクリプトが機械で確かめて書き換える。新しいメモリファイルは作れない
- 他にありえた選択肢: 点検の中の Claude に Edit と読む道具を渡して直接直させる。読む道具と読むだけの `git` `gh` の許可だけを渡す。直し方の種類を増やす(行の挿入、ファイルの新規作成)
- 外れていた場合: 要件3 受入基準1-5(重複を1つのメモリファイルにまとめる)、1-6(目次の行の中身をメモリファイルに移す)、1-9(メモリファイルを1つにまとめる)は、`edit` の `old` に当て先の文を含めてつなぎ足す形でしか書けない。点検の中の Claude がその形で書けないと、直しが「行わなかった」として毎週報告に載り、Issue の「種類を問わず直す」が満たされないまま誰も止めない。直すには JSON の形・確認・prompt を作り直す

- Issue の記載: あり。「点検の報告が毎回所有者に届く」。届け方は書かれていない(requirements 要件4 受入基準3 で「会話の始め」と決まった)

- 他にありえた選択肢: 既存の `usage-hook.sh` のように `.claude/hooks/` にラッパーを置く。フックを足さず、既存の SessionStart のフック(`usage-hook.sh`)に知らせを足す。OS の通知で届ける

**4. 点検の状態(設定・記録・報告・比べる元)を git の共通ディレクトリの `keirekipro-memory-inspection/` に置き、比べる元はファイルと行のハッシュだけにする** — データの形

- Issue の記載: あり。「点検ごとの記録が残る」「直す前のメモリの控えを作らない」「所有者のPCの中だけに置く」。置き場所は書かれていない

- 他にありえた選択肢: `~/.claude/projects/<名前>/` の下やメモリのディレクトリの隣に置く。行のハッシュではなく、行の文そのものを残す(控えに当たるので Issue の「やらないこと」に反する)

**6. Windows の予定は、登録した開発者がログオンしている間だけ動き、電池で動いていても動き、逃した回を遅れて動かさない(`-StartWhenAvailable` を付けない)** — 部品「memory-inspect.sh の enable と disable」

**7. 置き場所の誤り(種類10)の案を了承した PR がマージされたあと、メモリの側の記述は、次の点検が重複と二重記述(種類5)として消す。マージを見届ける印を足さない** — 部品「memory-inspection のスキル」の「移す先の案を了承したあとの流れ」

- 他にありえた選択肢: 案を了承した Issue の番号を記録に残し、マージを確かめてから消す。会話の中の Claude がマージを見届けた会話で消す
