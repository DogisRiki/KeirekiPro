## 実装のメモ

- `.claude/settings.json` と `.claude/hooks/` の下は、Claude が書けない(`settings.json` の `deny`)。所有者が置くまで、Claude は `.claude/settings.json` を本来の場所に書こうとしない。`.claude/scripts/`、`.claude/skills/`、`doc/` は書ける
- `.claude/` の下のファイルは、`cp` や `cmp` で読むときも `deny` に止められることがある。Claude は、写しを作るときは Read と Write を使い、一致を確かめるときは、止められたら Read で両方の中身を読んで比べる
- 置き場所: Claude は、`.claude/settings.json` の完成版を、作業フォルダの中の `.claude/.state/claude-memory-weekly-inspection/place-1/settings.json` に作る。`.claude/.state/` は git の管理外で、`deny` の対象に当たらない
- 検査用の写し: タスク7.1で、Claude は、作業フォルダを `git archive HEAD` で scratchpad の一時フォルダに写し、まだコミットしていない `.claude/scripts/memory/`、`.claude/skills/memory-inspection/`、`.claude/skills/memory-inspect-now/`、`doc/開発フロー/参加者セットアップ手順.md` と、`place-1/settings.json` を本来のパスで重ね、そこでテストと shellcheck を流す
- 3つの環境: Claude は、bash のテストを次の3つの環境で流す。テストの対象のフォルダは、タスク1からタスク6では作業フォルダ、タスク7.1では検査用の写し、タスク8.1では本来の場所である
  1. Git Bash: この PC の Git Bash で、テストを流す
  2. Linux のコンテナ: Claude は、テストの対象のフォルダを、`docker run --rm -v "<フォルダ>:/src:ro" alpine` で読むだけの形で渡し、コンテナの中で `/src` を別のフォルダに写してから、`apk add --no-cache bash perl perl-utils git` のあとで同じテストを流す
  3. bash 3.2 のコンテナ: Claude は、テストの対象のフォルダを、`docker run --rm -v "<フォルダ>:/src:ro" bash:3.2` で読むだけの形で渡し、コンテナの中で `/src` を別のフォルダに写してから、`apk add --no-cache perl git` のあとで同じテストを流す。`bash:3.2` は GNU bash 3.2.57 で、macOS の `/bin/bash` と同じ版である
- macOS で動く書き方: スクリプトとテストは、bash 3.2 にある機能と、macOS にあるコマンドの形だけを使う。時間の上限は perl の `alarm` で作り、`timeout` を使わない。Claude は、`stat -c`、`date -d`、引数の無い `sed -i` を使わない。`bash:3.2` のイメージは busybox のコマンドを持つので、3つの環境のテストでは、これらのコマンドの形の違いを見つけられないためである
- 名前で起動する偽のコマンドの1行目: テストが `PATH` の先頭に置いて名前で起動する偽のコマンドは、1行目を `#!/usr/bin/env bash` にする。`bash:3.2` のイメージは `/bin/bash` を持たないためである

- タスク4.3で分かったこと: apply は、prepare が書いた種類11の汚染も含むすべての汚染に、`fingerprint`(種類とファイル名と空白をそろえた記述を \0 で区切って続けた文字の列の SHA-256)と `new` と `existed_before` を書く。`existed_before` は、記述をバイトのまま今のファイルで探すので、記述が原文どおりでない汚染と CRLF のファイルの汚染では偽になる。決まりの見直しの案と移す先の案と点検のやり方の案は、外したあとに K と R と M の番号を振る。`missed.json` の `proposed_in` は、直しを書いたあとにロックを取らずに書くので、会話の側で見落としを書く部品(5.x)を作るときは、同じ時に書き込んで片方が消えないように、読み直してから書く形にそろえる
- タスク4.4で分かったこと: 報告を作る部分は `report_text($record)` で、記録だけから UTF-8 のバイトの列を返すので、4.5 の finalize はそのまま使える(finalize は snapshot.json を書かない)。apply は、直しが1つも無くても、比べる元を書き直すためにメモリのロックを必ず取る。点検の間にほかから書き換わったファイルは、比べる元に読んだときのハッシュを書き、行ごとのハッシュは前の比べる元のものを引き継ぐ(読んだときの中身を持っていないため)。apply が比べる元を書くようになったので、2回の点検を続けて動かすテストでは、あいだにメモリファイルを書き換えると、2回目に種類11の汚染が F1 として先に入り、そのあとの番号がずれる
- タスク4.5で分かったこと: finalize は、ロックが空くのを待っている決まった曜日と時刻の点検の回の場所(record.json がまだ無い)を扱わないので、5.x で回を始める部品が回の場所を先に作っても、finalize に消されない。finalize は、書いている途中の直しをメモリの中身で見分けるため、メモリのロックを取ってから動く。5.x で apply を呼ぶ部品と finalize を呼ぶ部品を同じ時に動かしても、finalize はロックを取れずに何もしない。--run で渡した回は、終わった回(completed と interrupted)なら書き替えない。--run で作る record.json には reverts の欄が無いので、4.7 で reverts を読むときは欄が無い記録も空の配列として扱う
- タスク4.6で分かったこと: 会話の中の操作のうち show・shown・history・answer・missed は、memory-inspect.sh が引数をそのまま memory-inspect.pl に渡し、引数の確かめは memory-inspect.pl が行う。4.7 の revert も同じ形で渡す。missed は、メモリのロックの中で missed.json を読み直してから書くので、5.x で見落としを書く部品はこのサブコマンドを呼べばよい。テストで `$(...)` を使ったあとに `$?` を読むと、置き換えの側の終了コードになるので、確かめたいコマンドの直後に終了コードを控える
- タスク4.7で分かったこと: revert は、メモリのロックの中でその回の record.json を読み直してから戻すので、5.x で apply や finalize と同じ時に打たれても、書いている途中の直しと混ざらない。ロックを取れないときは、取っている回の ID を載せた理由を出して終了コード 1 で終わる。戻したファイルの比べる元は revert が snapshot.json に書くので、次の回の prepare は戻したファイルを会話を通らない書き換えにしない
- タスク4.7の確かめで見つかった、spec の中の食い違い(未解決・出荷の報告と PR の本文に書く): 要件4の受入基準5は、戻した直しを次の点検でしないことを求める。design の「直し方の確認」は、戻された直しを断る確かめを edit と delete にしか持たないので、開発者が append_index_line を戻しても、次の回の apply は同じ行をまた目次に足す。append_index_line を戻したときの reverted.json の restored_text は空になる
- 所有者に尋ねること(タスク2.1の確認役の気づき。まだ尋ねていない): design の utterances は、中身が文字の列の行だけを開発者の発言として返す。しかし本物の記録では、開発者が画像を付けて打った文は中身が配列の形で、直近14日の開発者の行の約1,590件のうち25件がこの形だった。この25件は utterances に出ないので、点検の中の Claude は、開発者が画像と一緒に打った指示を「開発者の発言に無い」と読み違えるおそれがある。直すには design の変更が要る。親の会話の Claude は、次に所有者に返事をするときに、直すかを3行で尋ねる
- タスク5.1で分かったこと: 点検の中の Claude を呼ぶ部分は `inspect_with_claude <回の ID> <比べる材料> <claude の場所>` で、失敗の理由を標準エラーに1文で出して 0 でない値を返すので、5.2 の run はその理由を finalize の `--reason` に渡せる。点検の中の Claude の標準エラーはそのまま流れるので、5.2 で run.log に足すときは、理由の1文と混ざることを考える。全体の上限の60分は inspect_calls を始めた時から数える。時間の上限を掛けてプロセスの組ごと止める部分は memory-inspect.pl の `timed` で、ほかの段にも使える。テストの memory の a.md は、直しの old が本文の全体に当たると apply が断るので、本文の一部だけを old にする。全体の上限のテストは、負荷の高い時に揺れないよう、上限との差を大きく取る。Git Bash から perl の `-e` に日本語を渡すと文字が崩れて置き換えが当たらないので、日本語を含む書き換えは Edit の道具で行う
- タスク5.2で分かったこと: 前の回の後始末から点検のロックを外すまでは `inspect_run <回の ID> <scheduled|now> <claude の場所>` で、呼ぶ側が回の場所を作って点検のロックを取ってから呼ぶ。inspect_run は終わるときに `[memory-inspection] finished: <回の ID> completed|interrupted` を出し、完了で 0、中断で 0 でない値を返す。点検する時刻かの判断は memory-inspect.pl の `due`(点検するときだけ回の ID と claude の場所と PATH の3行を出す)、run.log を短くするのは `logtrim <ファイル>` である。run がロックの空きを待つ間隔は、テストだけが使う環境変数 `KP_MEMORY_INSPECTION_RETRY_SEC`(既定は30秒)で替える。run のテストは、曜日と時刻をこの PC の時刻の帯で読むので、`TZ=JST-9` を付けて流す

## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えたファイルを使うテストが、すべて成功している。`1.` や `2.` の見出しのタスクを大きなまとまりと呼ぶ。大きなまとまりの最後のタスクでは、加えて、そのまとまりのタスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめてから、コードを元に戻す。
