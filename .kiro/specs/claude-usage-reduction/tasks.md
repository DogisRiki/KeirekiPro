## 実装のメモ

- `.claude/settings.json` と `.claude/hooks/` の下は、Claude が書けない(`settings.json` の `deny`)。所有者が置くまで、Claude はそれらを本来の場所に書こうとしない。CLAUDE.md、`.claude/skills/`、`.claude/agents/` は書ける
- `.claude/` の下のファイルは、`cp` や `cmp` で読むときも `deny` に止められることがある。Claude は、写しを作るときは Read と Write を使い、一致を確かめるときは、止められたら Read で両方の中身を読んで比べる
- 置き場所: Claude は、`.claude/settings.json` と `.claude/hooks/` の下に置くファイルの完成版を、作業フォルダの中の `.claude/.state/claude-usage-reduction/`(置き場所)の `place-1/` に、リポジトリと同じ並びで作る。`.claude/.state/` は git の管理外(`.gitignore` の7行目)で、`deny` の対象(`.claude/settings.json` と `.claude/hooks/**`)に当たらない。scratchpad に置かないのは、scratchpad が会話ごとに別の場所になり、所有者の返事が新しい会話で来たときや、別の実装役が続きを作るときに見つからないためである
- タスク4.1の進め方: タスク4.1は `_保留:_` なので、`/kiro-impl` は、自律で進めるときに、実装役を起動せずにタスク4.1を飛ばす。親の会話の Claude は、`/kiro-impl` の Step 3 の繰り返しが終わったあと、Step 4 の `/kiro-validate-impl` を流す前に、タスク4.1を自分で進める。テストが通ったら、親の会話の Claude は、タスク4.1の `_保留:_` の行を消して完了の印を付け、コミットする
- 検査用の写し: Claude は、テストと shellcheck を、作業フォルダを `git archive HEAD` で scratchpad の一時フォルダに写し、そこに `place-1/` のファイルを本来のパスで重ねたフォルダで流す。テストはリポジトリの最上位を自分の場所から決めるので、この写しの中では `lib.sh` とタスク2の文書(コミット済み)が見つかる。まだリポジトリに無いファイルを `docker -v` で作業フォルダに重ねると、作業フォルダに0バイトのファイルが残るので、Claude はそうしない
- Linux のコンテナ: Claude は、検査用の写しを alpine のコンテナに写し、`apk add --no-cache bash perl git` のあとで同じテストを流す
- 親の会話の Claude が、所有者に依頼する。実装役の補助役は、所有者に依頼する手前で止まり、用意したもの(置き場所のパス)を親の会話に返す。確認役は、置く前の成果を置き場所のパスで確かめる。タスク1.1と3.1の成果は置き場所にあり、`git diff` に出ないためである
- 共通の完了条件の1(確かめるテストの無い受入基準を残さない)には、次の例外がある。要件1の受入基準2(所有者が効き目を Claude の画面で確かめ、Claude は繰り返しの作業を頼まない)、要件4の受入基準2・4(審査の往復の回数の上限・タスクごとの確認・Codex レビューを減らさないことと、承認する段階と所有者が打つコマンドを変えないこと)、要件6の受入基準1〜6(縮めたか区切った会話で上限と尋ね直しを確かめること、PR を確かめを待たずに出すこと、結果を示すこと、出荷の報告で1回だけ頼むこと、条件に合う会話が無ければ終えること)である。Claude は、これらの受入基準を、タスク3.1・4.2・4.3の「受入基準とテストの対応」の行に書いた方法で確かめる
- 出荷のとき: 親の会話の Claude は、`/ship` で PR 本文の `## マージのあとの確かめ` の節と出荷の報告に、タスク4.2で書いた頼みの文を1回ずつ書き、PR を出したあとに、PR 本文と出荷の報告に頼みの文が1回だけあることを照合する。照合の前に、Claude は `git fetch origin main` を流す
- 差分の照合: Claude は、差分を照合する前に `git fetch origin main` を流し、変えたファイルを `git merge-base origin/main HEAD` のコミットと比べる。main の先端と比べると、並行するほかの PR の変更も違いに出るためである
- タスク4.3の完了の印: タスク4.3は、PR がマージされたあとに行うので、この spec の PR では `_保留:_` のまま出す。`/kiro-validate-impl` を流すときには、タスク4.1はすでに完了の印が付いているので、`_保留:_` はタスク4.3だけである。`/kiro-validate-impl` が `_保留:_` を報告したら、Claude は、それがタスク4.3であることと、確かめに使う会話を作ることを出荷の報告で所有者に頼むことを確かめる。完了の印を付けるための PR は作らない

## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめてから、コードを元に戻す。
