# 要件

## 元の要望
Issue #480: Git Bash が引数のパスを書き換えて、起票の題名に手元のインストール先のパスが入る

### きっかけ

#477 の作業中に Claude が起票した #479 の題名に、手元の Git のインストール先のパスが入った。同じことは2回目である。所有者は、メモリに書くだけでは防げないとして、別の Issue で直すと決めた。

### 困っていること

- Claude が Git Bash で `/` で始まる文字列を引数に渡すと、Git Bash がそれを Windows のパスとみなし、Git のインストール先(`C:/Program Files/Git/`)を付けて書き換える。#479 の題名がこの形で起票された。同じことが2回起きている
- 書き換わったパスは手元の環境のもので、Windows でない人や、別の場所や別のドライブに入れている人には意味が通らない

### やりたいこと

- Claude がこの書き換えを起こさないことを、メモリに頼らず仕組みで防ぐ(AIの提案を了承)

## はじめに

Windows の作業PCでは、Claude はコマンドを Git Bash で実行する。Git Bash は、Claude がコマンドの引数に書いた `/` で始まる文字列を Windows のパスとみなし、Git のインストール先(`C:/Program Files/Git/` など)を頭に付けてから、プログラムに渡すことがある。Claude はこの書き換えに気づかないまま、書き換わった文字列を Issue の題名などに記録してしまう。#479 の題名は、この形で `/kiro-spec-quick` が `C:/Program Files/Git/kiro-spec-quick` に書き換わって起票された。同じことは2回起きている。

今は、この書き換えを防ぐ手段が、Claude のメモリの記述しかない。メモリは Claude が読み落とせば効かないので、2回目を防げなかった。

この spec は、Claude が実行するコマンドで、この書き換えが起きないことを、メモリに頼らずに保証する。

## 範囲

- この spec で決めること: Claude が作業PCで実行するコマンドの引数が、Git Bash に書き換えられずにプログラムに届くこと。書き換えを防いだ結果、Claude の作業(品質チェック、並行作業のスクリプト、フック、起票、コミット、PRの作成)が今までどおり動くこと
- この spec で決めないこと: 所有者が自分の端末で打つコマンドの扱い。CI(GitHub Actions)で動くコマンドの扱い。CI は Linux で動くので、この書き換えは起きない。すでに起票された Issue やPRの題名の直し。#479 の題名は直してある
- この spec が前提にしていること: Windows の作業PCには、CLAUDE.md の Git規約のとおり Git for Windows(Git Bash を含む)が入っている。macOS と Linux の作業PCでは、この書き換えは起きない

## 要件

### 要件1 Claude が書いた引数を書き換えずにプログラムへ届ける

Claude が引数に書いた文字列が、気づかないうちに手元のパスへ書き換わると、Issue の題名やPRの本文やコミットメッセージのように、所有者と審査役が読む記録の意味が壊れる。書き換わったパスは手元の環境のものなので、Windows でない人や、Git を別の場所や別のドライブに入れている人には意味が通らない。そこで、Claude が実行するコマンドで、この書き換えが起きないようにする。

1. Claude が Windows の作業PCでコマンドを実行したら、Claude が書いた引数は、Claude が書いたとおりの文字でプログラムに届くか、プログラムに届く前にコマンドの実行が止められる。Git Bash がどの形の引数を書き換えるか(引数の先頭が `/` で始まるもの、`--title=/…` のように `=` の後ろが `/` で始まるもの、`:` で区切ったパスの並びなど)に依らず、Git のインストール先のパスが付くなどして書き換わった文字列は、プログラムに届かない。
2. 書き換わった文字列をプログラムに届けないという決まりは、コマンドの種類を問わず、Claude が実行するすべてのコマンドに当てはまる。Issue やPRを扱うコマンドだけに限らない。
3. 書き換わった文字列をプログラムに届けないという決まりは、Claude が作業を任せたサブエージェントが実行するコマンドにも当てはまる。
4. 書き換わった文字列をプログラムに届けないという決まりは、Claude がメモリの記述を読んだかどうかに依らずに成り立つ。Claude がコマンドを書くたびに書き換えを防ぐ書き方を思い出す必要は無い。
5. Claude が書いたコマンドが、書き換えを防ぐために実行の前に止められたら、Claude には、止められた理由と、止められずに実行できる書き方が伝わる。Claude は、その書き方でコマンドを書き直して実行できる。
6. Claude がパスのつもりで `/` で始まる形(`/c/Users/…` や `/tmp/…` など)で書いた文字列も、ほかの引数と同じく、書き換えられずにプログラムに届くか、届く前に実行が止められる。Git Bash は、パスのつもりで書いた文字列と、`/kiro-spec-quick` のようにパスでない文字列とを見分けられないからである。Windows 向けのプログラムがその形のパスを解釈できずにエラーで終わったら、Claude は、そのパスをドライブ文字の形(`C:/Users/…`)か、作業フォルダからの相対の形で書き直して実行する。

### 要件2 今の作業を壊さない

書き換えを防ぐ変更のせいで、Claude が今まで実行できていたコマンドが動かなくなると、品質チェックや出荷が止まり、自律の作業が進まなくなる。そこで、書き換えを防いだあとも、Claude の今の作業が今までどおり動くようにする。

1. リポジトリに書かれたコマンド(CLAUDE.md とスキルの手順に書かれたコマンド、`.claude/scripts/` などのスクリプト、`start-dev.sh`)を Claude が書かれたとおりに実行したら、そのコマンドは、この spec の変更のあとも、変更の前と同じ結果で終わる。品質チェック、並行作業のスクリプト、`/start` と `/ship` の手順のコマンドも、これに含まれる。
2. Claude Code がセッションの始めと終わり、コマンドの実行の前、ファイルの書き込みのあとなどに動かすフックは、この spec の変更のあとも、変更の前と同じ判定をする。
3. macOS と Linux の作業PCでは、Claude が実行するコマンドの動きは、この spec の変更の前と変わらない。

### 要件3 作業PCごとの設定を要らなくする

書き換えを防ぐために作業PCごとに設定が要ると、設定を忘れた作業PCでは書き換えが起きる。それでは、メモリに頼る今の状態と変わらない。そこで、リポジトリの内容だけで書き換えを防げるようにする。

1. 所有者と参加者は、この spec の変更を取り込んだリポジトリで Claude を使うだけで、Claude が書いた引数が書き換えられずにプログラムへ届く。所有者と参加者が、作業PCごとに設定を足したり、Git for Windows のほかにプログラムを入れたりする必要は無い。
2. 所有者が新しく worktree を選んでセッションを開いたときも、そのセッションの Claude が書いた引数は、書き換えられずにプログラムへ届く。

### 要件4 防ぎ方が外れたことに気づける

書き換えを防ぐ手段が、あとの変更で知らないうちに外れると、書き換えが再び起きるまで誰も気づかない。そこで、書き換えを防ぐ手段が働いているかを、Claude が品質チェックと同じように確かめられるようにする。

1. 書き換えを防ぐ手段には、それが働いているかを確かめる自動のテストがある。
2. 誰かが書き換えを防ぐ手段を外すか壊す変更をしたら、そのテストが失敗する。
