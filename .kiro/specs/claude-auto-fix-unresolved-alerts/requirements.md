# 要件

## 元の要望
Issue #725: frontend-vuln-fix と backend-vuln-fix が警告を消せなかったときに、Claude が直す PR を作る

### きっかけ

#723 の出荷のあとに、AI が「検査が通らない組では PR が作られず、失敗は実行の記録にだけ残る」と説明した。所有者が、それでは気づきにくいと考え、直す PR まで Claude を使って自動で作ることを求めた。

#532 の要件を決めるときに、所有者が、CodeQL の週1回の診断で main に見つかった警告も、この Issue で Claude に直させると決めた。

### 困っていること

frontend-vuln-fix と backend-vuln-fix が警告を消す PR を作れずに実行が失敗で終わったとき、失敗は Actions の実行の記録にしか残らない。所有者は、Actions の画面を開かないと、警告が消えずに残っていることに気づけない。

### やりたいこと

- frontend-vuln-fix と backend-vuln-fix が警告を消す PR を作れなかったときに、Claude を使って、警告を消す PR を自動で作る。
- CodeQL の週1回の診断で main に見つかった警告についても、Claude を使って、警告を消す PR を自動で作る。

### どうなれば解決か

- frontend-vuln-fix か backend-vuln-fix が警告を消す PR を作れずに実行が失敗で終わったときは、Claude が直し方を考え、警告を消す PR を作る。
- Claude が作った PR は、ほかの PR と同じ必須の検査がすべて通らないとマージされない。(AIの提案を了承)
- Claude も警告を消せなかったときは、仕組みが Issue を起票する。Issue には、消せなかった警告の URL が書いてある。(AIの提案を了承)
- 同じ部品と版の組の PR か Issue が開いているときは、仕組みは新しく作らない。(AIの提案を了承)
- 週次監査が、CodeQL の週1回の診断で main に見つかった警告を Issue に書いたときは、Claude が直し方を考え、警告を消す PR を作る。


### 決めた方式

- 本番で動いているイメージに脆弱性が見つかり、仕組みがラベル `container-vuln` の Issue を起票したときは、修正版がある脆弱性について、Claude が脆弱性を消す PR を作る。修正版がまだ無いときは、Claude は PR を作らず、Issue はそのまま残る。(AIの提案を了承)
- Dependabot の PR が、脆弱性ではない理由で赤のまま止まり、週次監査がその PR を見つけたときは、Claude が、止まった原因を直す PR を別に作る。Claude は Dependabot の PR を閉じず、Dependabot へのコマンドも打たない。(AIの提案を了承)
- 仕組みが GitHub Actions の中で動かす Claude の費用は、所有者の Claude の契約で払う。API キーは使わない。
- 仕組みは、Claude と、Claude が変えたコードを動かすワークフローの実行を、main とは別の専用のブランチで起動する。その実行が作るキャッシュを、main のワークフローが読まないようにするためである。(AIの提案を了承)

## はじめに

この spec は、今ある検査とワークフローが自分では直せずに残る警告と止まった PR を、この spec の仕組みが GitHub Actions の中で Claude を動かして直すようにする。所有者が Actions の画面を開かなくても、残った警告に気づけるようにするためである。

## 範囲

- この spec で決めること: 次の4つである。
  - 仕組みが Claude を動かすきっかけ
  - Claude が作る PR と、Claude がしてはいけないこと
  - Claude が直せなかったときと動けなかったときの Issue
  - Claude を動かすための鍵の登録と取り替えの手順
- この spec で決めないこと: 次の4つである。
  - 次の5つの直し方。この spec が5つの直し方を決めないのは、5つの直し方を所有者が決めるか、5つの直し方の変更が `.github/` の変更として所有者の承認を要するためである
    - CI の道具の版を上げるワークフローの失敗
    - Trivy の版の食い違い
    - コンテナの脆弱性の抑制の期限切れ
    - カナリアの検知の失敗
    - ruleset と期待一覧の食い違い
  - 本番へのリリース。Claude の変更の PR がマージされても、本番で動くイメージが変わるのは、所有者がリリースしたあとである
  - 必須の検査の中身
  - codex-review を動かすかどうか
- この spec が前提にしていること: 次の3つである。
  - frontend-vuln-fix と backend-vuln-fix は、今と同じく毎日動き、作れる PR は今と同じく自分で作る
  - 依存の入手先とビルドの設定を変える PR は、今と同じく、所有者が承認するまでマージされない
  - Claude を動かす費用は、所有者の Claude の契約の使える量から払う

## 要件

### 要件1 仕組みが Claude を動かすのは、今ある検査と週次監査が見つけた警告と止まった Dependabot の PR だけにする

このリポジトリは公開されており、誰でも Issue とコメントを書ける。誰でも Claude を動かせると、他人が、所有者の Claude の契約の使える量を使えてしまう。また、Claude が、他人の書いた指示に従って変更を作るおそれがある。そこで、仕組みは、Claude を動かすきっかけを、今ある検査と週次監査が見つけた警告と、止まった Dependabot の PR に限る。

1. frontend-vuln-fix か backend-vuln-fix が、警告を消す PR を作れずに失敗で終わったら、仕組みは、警告が消えずに残った部品と修正版の組ごとに Claude を動かす。仕組みは、backend-vuln-fix の Java 版の部品の警告と、Go 版の部品と標準ライブラリの警告の両方を対象にする。Go 版の標準ライブラリの警告は、今の backend-vuln-fix と同じく、1つの組にまとめる。
2. 週次監査が、main に開いたままの CodeQL の警告を数えたら、仕組みは、開いたままの警告ごとに Claude を動かす。
3. 本番で動いているイメージの脆弱性を調べる検査がラベル `container-vuln` の Issue を起票したら、仕組みは、その Issue の脆弱性について Claude を動かす。ただし、脆弱性に修正版が無いときは、仕組みは、Claude を動かさず、Issue にコメントも付けない。Issue はそのまま残る。
4. 週次監査が、赤のまま止まった Dependabot の PR を見つけたら、仕組みは、その PR ごとに Claude を動かす。ただし、仕組みは、赤の検査が次の5つの検査のどれかだけの PR では、Claude を動かさない。5つの検査とは、新しい脆弱性を見つける検査 dependency-review と、要件2の4に書いた escape-hatch、dependency-gate、pre-merge-check、dependency-cooldown の4つの検査である。dependency-review だけが赤の PR は、脆弱性が理由で止まっている。4つの検査の赤は、所有者の承認か、依存の版の公開から72時間経つことを待っている赤である。どちらも、Claude がコードを直しても緑にならないためである。
5. 所有者は、手で仕組みを動かして、この要件の1から4の対象のうち残っているものすべてについて、Claude を動かせる。1から4の対象とは、frontend-vuln-fix と backend-vuln-fix が消せなかった警告、main に開いたままの CodeQL の警告、ラベル `container-vuln` の Issue の修正版がある脆弱性、止まった Dependabot の PR である。
6. 仕組みが Claude を動かすのは、次のときだけである。
   - この要件の1から4に書いた4つのきっかけ。4つのきっかけとは、frontend-vuln-fix か backend-vuln-fix の失敗、週次監査が数えた main の CodeQL の警告、ラベル `container-vuln` の Issue の起票、週次監査が見つけた止まった Dependabot の PR である
   - この要件の5に書いた、所有者の手での起動
   - 要件2の4に書いた、Claude の変更の PR の必須の検査の赤
   - 要件2の9と要件6に書いた、次の日の動かし直し

   仕組みは、利用者が書いた Issue、コメント、PR をきっかけにして、Claude を動かさない。

### 要件2 仕組みは、警告が消えると確かめた変更だけを PR にする

Claude の変更の PR が検査に通らないまま並ぶと、所有者は、どの PR を見ればよいかが分からなくなる。CodeQL の警告を直しかけの PR は、まだ直していない穴の場所を公開することにもなる。そこで、仕組みは、直したことを確かめてから PR を作る。

1. 仕組みは、1つの警告、1つの脆弱性、または1つの止まった Dependabot の PR につき、Claude の変更の PR を1つ作る。ただし、frontend-vuln-fix と backend-vuln-fix の警告については、仕組みは、今の2つのワークフローと同じく、部品と修正版の組ごとに PR を1つ作る。
2. 仕組みは、PR を作る前に、main に Claude の変更を足したコードに対象の警告や脆弱性が残らないことと、変えた領域の品質チェックに通ることを確かめる。確かめられないときは、仕組みは、PR を作らず、要件4のとおり、その対象を直せなかったものとして扱う。
3. Claude の変更の PR は、ほかの PR と同じ必須の検査をすべて通り、必要な所有者の承認がそろったときにだけ、自動でマージされる。
4. Claude の変更の PR の必須の検査が赤になったら、仕組みは Claude を動かす。Claude は、その検査が赤になった原因を直す。仕組みは、Claude が直した変更を PR に足す。ただし、escape-hatch、dependency-gate、pre-merge-check、dependency-cooldown の4つの必須の検査の赤では、仕組みは Claude を動かさない。この4つの赤は、所有者の承認か、依存の版の公開から72時間経つことを待っている赤で、Claude がコードを直しても緑にならないためである。
5. Claude の変更の PR で同じ必須の検査が3回続けて赤になったら、仕組みは、Claude を動かすのをやめ、その PR を閉じる。そのあと、仕組みは、要件4のとおり、その対象を直せなかったものとして扱い、閉じた PR の URL を、直せなかったことを知らせる Issue かコメントに書く。
6. Claude の変更の PR がマージされる前に、対象の警告や脆弱性が別の理由で消えたら、仕組みは、その PR を閉じる。
7. ラベル `container-vuln` の Issue の脆弱性について、Claude の変更の PR がマージされたら、仕組みは、その Issue に、本番で脆弱性が消えるのは所有者がリリースしたあとであることを書いたコメントを付ける。
8. main から作ったイメージに、ラベル `container-vuln` の Issue の脆弱性がもう無いときは、仕組みは PR を作らない。仕組みは、ラベル `container-vuln` の Issue に、main では消えていて、所有者がリリースすれば本番でも消えることを書いたコメントを付ける。
9. Claude の変更が、依存を、公開から72時間経っていない版に変えるときは、仕組みは、その変更の PR を dependency-cooldown がどう扱うかで、扱いを分ける。dependency-cooldown は、72時間経っていない版に変える PR を、次の2つのどちらかに扱う。1つ目は、記録のコメントを書いて、所有者の承認を求める扱いである。2つ目は、記録のコメントを書かずに赤にする扱いである。仕組みは、Claude の変更の PR を dependency-cooldown がどちらに扱うかを、dependency-cooldown の検査と同じ結果になるように確かめる。今の dependency-cooldown は、たとえば次の4つのときに、記録のコメントを書かずに赤にする。1つ目は、版が本番で動く部品の high か critical の開いている警告の最初の修正版でないときである。2つ目は、前の版と違う者が署名しているときである。3つ目は、変更で入る部品が悪意のある部品の一覧に載っているときである。4つ目は、frontend の部品の版が pnpm の72時間の待ちの除外の欄に無いときである。この分け方は、対象が何の警告か、何の脆弱性か、どの Dependabot の PR かによらない。
   - dependency-cooldown が記録のコメントを書いて所有者の承認を求めるときは、仕組みは、72時間を待たずに、その変更で PR を作るか、その変更を PR に足す。frontend の部品では、Claude は、今の frontend-vuln-fix と同じく、その版を pnpm の72時間の待ちの除外の欄に足す。足さないと、dependency-cooldown が記録のコメントを書かずに赤にするためである。仕組みが72時間を待たずに PR を作るか変更を PR に足すのは、深刻な警告を、72時間のあいだ本番に残さないためである。今の frontend-vuln-fix と、backend-vuln-fix の Java 版のジョブも、本番で動く部品の high か critical の警告の最初の修正版だけを、72時間待たずに PR にする
   - dependency-cooldown が記録のコメントを書かずに赤にするときは、仕組みは、その変更で PR を作らない。仕組みは、その変更を PR にも足さない。仕組みは、次の日に、同じ対象について Claude をもう一度動かす。仕組みがその変更で PR を作らず、PR にも足さないのは、dependency-cooldown が赤にした PR は、誰かが検査を動かし直すまで止まるためである。今の backend-vuln-fix の Go 版のジョブは、公開からの時間を見ずに PR を作る。仕組みは、Go 版の部品と標準ライブラリの脆弱性でも、この分け方に従う

### 要件3 仕組みは、検査を弱める変更を PR にせず、Claude に所有者の権限の操作をさせない

Claude は、所有者が見ていない GitHub Actions の中で動く。Claude が検査を弱めたり、所有者だけがしてよい操作をしたりすると、検査が警告を止める役目を果たさなくなる。検査を弱めないことと、所有者だけがしてよい操作をしないことを Claude 自身に任せると、誰も、Claude がその2つを守ったかを機械で確かめられない。そこで、仕組みが、Claude の変更と Claude に渡す権限を確かめる。

1. 仕組みは、Claude の変更にゲートの設定のファイルが含まれるときは、その変更を PR にしない。ゲートの設定のファイルとは、`.github/`、`.claude/`、`eslint.config.js`、`vite.config.ts`、`backend/gradle/quality.gradle`、`backend/config/`、ArchUnit のテスト、`CODEOWNERS` である。そのあと、仕組みは、要件4のとおり、その対象を直せなかったものとして扱う。
2. 仕組みは、Claude の変更に、テストを飛ばす変更、アサーションを消す変更、カバレッジと lint の対象から外す変更、コンテナの脆弱性の抑制を足す変更、CodeQL の警告を消すための注釈を足す変更が含まれるときは、その変更を PR にしない。そのあと、仕組みは、要件4のとおり、その対象を直せなかったものとして扱う。
3. 仕組みは、Claude に、GitHub の中身を変える権限を渡さない。PR を作ること、PR に変更を足すこと、Issue を起票すること、コメントを付けること、PR と Issue を閉じることは、仕組みが行う。Claude は、PR をマージする操作、auto-merge を予約する操作、main への push、CodeQL と Dependabot の警告を却下する操作、Dependabot の PR を閉じる操作、Dependabot へのコマンドを打つ操作のどれもできない。
4. 仕組みは、Dependabot の PR を閉じず、Dependabot へのコマンドも打たない。止まった Dependabot の PR については、仕組みは、Claude が止まった原因を直した変更を、Dependabot の PR とは別の PR にする。
5. 仕組みは、Claude に材料として渡す文を、警告の説明、依存の更新の説明、仕組みが書いた Issue と PR の本文、赤になった必須の検査の名前とその検査の実行の記録に限る。赤になった検査の実行の記録を渡すのは、Claude が、要件1の4の止まった Dependabot の PR と、要件2の4の必須の検査が赤になった Claude の変更の PR で、赤の原因を知るためである。仕組みは、利用者が書いた Issue、PR、コメントを、Claude に渡さない。仕組みは、Claude に渡す指示の文に、材料に書かれた指示に従わないことを書く。

### 要件4 Claude が直せなかったときは、仕組みが Issue で所有者に知らせる

Claude が直せなかった警告が実行の記録にしか残らないと、所有者は今と同じく気づけない。そこで、直せなかったときは、仕組みが Issue を起票する。

1. Claude が警告、脆弱性、または止まった Dependabot の PR を直せなかったら、仕組みは、直せなかったものごとに Issue を起票する。Issue には、直せなかった警告か脆弱性の URL を書く。止まった Dependabot の PR では、その PR の URL を書く。
2. ラベル `container-vuln` の Issue の脆弱性を Claude が直せなかったときは、仕組みは、新しい Issue を起票せず、その Issue に、Claude が直せなかったことを書いたコメントを付ける。
3. 同じ警告、同じ脆弱性、または同じ Dependabot の PR について、Claude の変更の PR が開いているときは、仕組みは、Claude を動かさず、新しい PR も Issue も作らない。frontend-vuln-fix と backend-vuln-fix の警告では、同じ部品と修正版の組について開いている PR があるときに、仕組みは、新しい PR も Issue も作らない。
4. 仕組みは、同じ対象について次の2つのどちらかに当たるときは、要件1の1から4に書いた4つのきっかけでは Claude を動かさない。4つのきっかけとは、frontend-vuln-fix か backend-vuln-fix の失敗、週次監査が数えた main の CodeQL の警告、ラベル `container-vuln` の Issue の起票、週次監査が見つけた止まった Dependabot の PR である。
   - 直せなかったことを知らせる Issue が開いている
   - ラベル `container-vuln` の Issue に、Claude が直せなかったことを書いたコメントが付いている

   ただし、所有者が要件1の5のとおり手で仕組みを動かしたときは、仕組みは Claude を動かす。そのとき Claude がまた直せなかったら、仕組みは、新しい Issue を起票せず、開いている Issue かラベル `container-vuln` の Issue に、また直せなかったことを書いたコメントを付ける。
5. 直せなかったことを知らせる Issue の対象が消えたら、仕組みは、その Issue に、消えたことを書いたコメントを付けて閉じる。対象が消えたとは、警告か脆弱性が開いたままでなくなったこと、または Dependabot の PR が閉じたかマージされたか検査に通ったことを指す。

### 要件5 公開される文に、CodeQL の警告の中身を書かない

CodeQL の警告は、このリポジトリのコードにある、まだ直していない穴を指す。リポジトリは公開されているので、穴の場所と中身を PR や Issue に書くと、攻撃の手がかりを公開することになる。週次監査も、同じ理由で、Issue に警告の数とリンクだけを書いている。

1. CodeQL の警告を直す PR の題名と本文、コミットのメッセージ、直せなかったことを知らせる Issue の題名と本文とコメントは、仕組みが、決まった文と警告の URL で書く。仕組みは、これらに、Claude が書いた文と、警告のファイルの名前、行、規則の名前、警告の説明を入れない。
2. 仕組みが CodeQL の警告を直す PR を作るのは、要件2の2で、警告が消えることと品質チェックに通ることを確かめたときだけにする。

### 要件6 Claude が動けなかったときも、所有者が気づけるようにする

Claude は、動くたびに、所有者の Claude の契約の使える量を使う。所有者の Claude の契約の使える量が上限に達したとき、Claude を動かす鍵が切れたとき、実行が時間切れになったときなどは、Claude は動けない。動けなかったことに所有者が気づけないと、警告は今と同じく残る。

1. 鍵が無いことと切れたことのほかの理由で Claude が動けなかったら、仕組みは、次の日に、同じ対象について Claude をもう一度動かす。ほかの理由とは、所有者の Claude の契約の使える量が上限に達したこと、実行が時間切れになったこと、Claude の側の障害などである。同じ対象で3日続けて Claude が動けなかったら、仕組みは、要件4の1と同じく、その対象の URL を書いた Issue を起票する。Issue には、動けなかった理由を書く。
2. この要件の1で起票した Issue は、同じ対象で3日続けて Claude が動けなかったことを知らせる Issue である。その Issue が開いていても、仕組みは、次の日からも同じ対象について Claude を動かす。Claude の変更の PR ができたら、仕組みは、その Issue に PR の URL を書いたコメントを付けて閉じる。Claude が直せなかったら、仕組みは、その Issue に直せなかったことを書いたコメントを付け、そのあとは要件4の4のとおりに扱う。
3. Claude を動かす鍵が無いか、切れていて、Claude が動けなかったら、仕組みは、鍵を取り替えるよう求める Issue を1つ起票する。その Issue が開いている間は、仕組みは、鍵を取り替えるよう求める Issue を新しく起票しない。鍵を取り替えたあとに Claude が動けたら、仕組みは、その Issue に、動けたことを書いたコメントを付けて閉じる。
4. 鍵を取り替えたら、仕組みは、鍵が切れて動けなかった対象について、次の日までに Claude をもう一度動かす。

### 要件7 Claude を動かす鍵の登録と取り替えの手順を、基盤構築手順に書く

Claude を動かす鍵は、所有者の Claude の契約から作るもので、作ってから1年で切れる。取り替えの手順が書かれていないと、鍵が切れるたびに、所有者は手順を調べ直すことになる。

1. この spec を実装する Claude は、基盤構築手順の、リポジトリに登録する秘密の値の一覧に、Claude を動かす鍵を足す。この spec を実装する Claude は、一覧に、鍵の作り方と、鍵が無いときや切れたときに何が止まるかを書く。
2. この spec を実装する Claude は、基盤構築手順に、鍵が切れたときと切れる前に、鍵を作り直して登録し直す手順を書く。この spec を実装する Claude は、この手順を、Claude の契約を持つ開発者が、Windows・macOS・Linux のどれでも打てるコマンドで書く。
3. この spec を実装する Claude は、この spec の仕組みを入れる PR の本文の「マージのあとにすること」に、今のリポジトリに初めて鍵を登録する手順を書く。この手順は1回きりなので、この spec を実装する Claude は、この手順を基盤構築手順に書かない。
