## はじめに

Issue #445 で、所有者は、backend を Java と Spring Boot から Go に置き換えると決めた。置き換えの進め方と、Go 版が守ることは、spec `backend-go-replacement` が決めている。この spec では、spec `backend-go-replacement` を「置き換えの spec」と呼ぶ。置き換えの spec は、機能のまとまりごとの Go 版を、まとまりごとの別の spec で作ると決めた。この spec は、そのうち利用者のまとまりを受け持ち、Issue #771 の「やりたいこと」に挙げた7つの操作の Go 版を作る。この spec では、この7つの操作を「利用者の操作」と呼ぶ。

利用者の操作は、ログインした利用者が、自分のアカウントを見て変えるための操作である。利用者の操作には、次の7つがある。

- 利用者の情報を見ること
- 名前とプロフィール画像と2段階認証の設定を変えること
- 退会すること
- メールアドレスの確認のメールを送ること
- メールアドレスとパスワードを設定すること
- パスワードを変えること
- Google か GitHub のアカウントとの連携を解除すること

この spec の「所有者」「Java 版」「Go 版」「利用者」「画面」「切り替え」は、置き換えの spec と同じものを指す。この spec では、spec `backend-go-auth` を「認証の spec」と呼ぶ。「ログインの状態」「筋書き」は、認証の spec と同じものを指す。「ログインの状態」は、ログインした利用者のブラウザが Cookie に持ち、要求ごとに backend に送る値である。「筋書き」は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査が、版に送る要求の並びと、期待する答えを書いたものである。「プロフィール画像」は、利用者が画面からアップロードし、画面が利用者の名前の横に出す画像を指す。

Issue #771 の「どうなれば解決か」は、利用者の操作について、置き換えの spec の19の受入基準を満たすことを求めている。置き換えの spec は、まとまりごとの spec に置き換えの spec の要件を書き写さず、当てはまる要件を指すと決めている。そこで、この spec は、19の受入基準のそれぞれを、次の表のとおりに受け持つ。表で「置き換えの spec のとおり」とした受入基準は、利用者の操作に固有の決めごとが無い。Claude は、その受入基準を、置き換えの spec の文のとおりに利用者の操作に当てはめる。

## 範囲

- この spec で決めること: この spec では、次の2つを決める。
  - 利用者の操作の Go 版
  - 利用者の操作について、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査に足す筋書き
- この spec で決めないこと: この spec では、次の5つを決めない。
  - ほかのまとまりの操作の Go 版。たとえば、経歴書の保存、PDF と Markdown の出力、バックアップの Go 版は、それぞれのまとまりの spec で作る
  - 利用者がメールアドレスの確認のリンクを開いたときに確認を受け付ける操作と、ログインの状態の検査。この2つの Go 版は、認証の spec で作ってある。この spec の Go 版は、この2つをそのまま使う
  - ほかのサイトから送られた偽の要求を断る検査。この検査は、置き換えの spec で作ってある
  - 利用者の操作の機能を足すことと、仕様を変えること。Issue #445 の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである
  - 本番の切り替え。本番の切り替えは、置き換えの spec が受け持つ
- この spec が前提にしていること: この spec は、次の4つを前提にする。
  - 次の5つは、置き換えの spec の段階2である、Go 版の品質チェックと、Java 版と Go 版を比べる検査をそろえる段階で作られ、main に入っている。
    - Go 版の土台
    - Java 版と Go 版を比べる検査
    - 版をまたいで確かめる検査
    - 検査で AWS の代わりに使う偽のサービス。この偽のサービスは、アップロードした画像を版ごとに覚え、画像を見せるための署名付きの URL への要求に答える
    - 利用者の操作の API の仕様書
  - 認証の spec の Go 版は、main に入っている。認証の spec の Go 版には、ログインの状態の検査と、利用者がメールアドレスの確認のリンクを開いたときに確認を受け付ける操作がある。確認を受け付ける操作は、メールアドレスとパスワードを設定した利用者が、設定待ちのメールアドレスを確認する場合も受ける
  - Claude は、置き換えの spec の設計を書く前に、プロフィール画像として受け入れるファイルの見分け方を試しに作った。Java 版と同じにはできなかったので、Go 版は、中身が PNG、JPEG、GIF のファイルだけを受け入れる。所有者は、この違いを 2026-11-07 に受け入れた。この違いは、置き換えの spec の変えた動きの一覧に載っている
  - 一方で、Claude は、置き換えの spec と認証の spec の設計を書く前に、次の3つを試しに作っていない。
    - アップロードした画像を置き場所に置くときに付ける名前と、画像を見せるための URL
    - 利用者の名前の前後の空白の取り除き方と、利用者の名前の文字数の数え方
    - 退会の完了のメールの件名と本文

## 要件

### 要件1 利用者の操作を、今の画面を直さずに Go 版で使えるようにする

切り替えのあとも、利用者は、今の画面で自分のアカウントを見て変える。Go 版の答えが Java 版と少しでも違うと、画面はエラーを出すか、利用者の変更を正しく見せられない。たとえば、答えの項目の名前が1つ違うだけで、画面は利用者の名前かプロフィール画像を出せなくなる。そこで、Go 版は、利用者の操作に、Java 版と同じ答えを返す。

1. Go 版は、利用者の操作の要求に、Java 版と同じ HTTP の状態の番号、同じ本文、同じ Cookie の名前と性質で答える。同じかどうかの正解は、今の Java 版が実際に返す答えとする。
2. 利用者は、今の画面で、Go 版を相手に、次の操作を終えられる。
   - 自分の情報を見る
   - 名前と、プロフィール画像と、2段階認証を使うかどうかの設定を変える
   - メールアドレスとパスワードを設定し、届いたメールのリンクでメールアドレスを確認する
   - 確認の済んでいないメールアドレスに、確認のメールを送り直す
   - パスワードを変える
   - Google か GitHub のアカウントとの連携を解除する
   - 退会する
3. Go 版は、利用者の操作で、入力の誤りとして断る条件と、画面に出るエラーの文言を、Java 版と同じにする。断る条件には、名前の長さの上限、プロフィール画像の大きさと縦と横の長さの上限、パスワードの長さと使う文字の決まりがある。
4. Go 版は、利用者の操作で送るメールの宛先と件名と本文を、Java 版と同じにする。利用者の操作が送るメールは、メールアドレスの確認のメールと、退会の完了のメールの2種類である。
5. 利用者が退会したら、Go 版は、Java 版が消すものと同じものを消す。消すものには、その利用者の情報と経歴書と、アップロードしたプロフィール画像がある。
6. 利用者の操作に、すでに居ない利用者のログインの状態を持つ要求が届いたら、Go 版は、その要求を Java 版と同じ答えで断る。断るときに Java 版が Cookie を消すなら、Go 版も同じ Cookie を消す。認証の spec の要件2の受入基準3のとおり、ログインの状態の検査は、要求を送った利用者がまだ居るかを確かめないためである。

### 要件2 アップロードしたプロフィール画像を、置き換えの前と同じに表示する

本番には、利用者が Java 版でアップロードしたプロフィール画像が置いてある。Go 版がその画像を見つけられないと、切り替えのあとに、利用者のプロフィール画像が消えたように見える。また、切り替えの途中で Go 版がアップロードを受けた画像を Java 版が見つけられないと、Java 版に戻す出荷のあとに、同じことが起きる。そこで、Go 版は、Java 版と同じ置き場所に、Java 版と同じ名前で画像を置き、Java 版と同じ名前で画像を読む。

1. 利用者が Java 版でアップロードしたプロフィール画像は、Go 版が答える利用者の情報でも、同じ画像として表示される。
2. 利用者が Go 版でアップロードしたプロフィール画像は、Java 版が答える利用者の情報でも、同じ画像として表示される。
3. 利用者がプロフィール画像を別の画像に替えたら、Go 版でも Java 版でも、替えたあとの画像が表示される。

### 要件3 今あるセキュリティの対策を弱めない

利用者の操作は、パスワードやメールアドレスのように、アカウントを守るための設定を変える。Go 版で今あるセキュリティの対策が弱まると、ほかの人が利用者のアカウントを乗っ取るか、利用者が自分のアカウントに入れなくなるおそれがある。しかも、利用者は、今あるセキュリティの対策が弱まったことに画面で気づけない。そこで、Go 版は、今あるセキュリティの対策を、Java 版と同じに守る。

1. 利用者がパスワードを変えるときに、Go 版は、Java 版と同じく、今のパスワードが合わなければ変えない。パスワードを持つ利用者がメールアドレスとパスワードを設定するときも、Go 版は、Java 版と同じく、今のパスワードが合わなければ設定しない。
2. 利用者がパスワードを変えたときと、退会したときに、Go 版は、Java 版と同じく、その利用者のすべての端末のログインの状態を使えなくする。
3. Go 版は、確認のメールを同じメールアドレスに送り直せる間隔の制限と、確認のリンクの有効な時間を、Java 版と同じにする。新しい確認のリンクを送ると前の確認のリンクが使えなくなることも、Go 版は Java 版と同じに守る。
4. Go 版は、2段階認証の設定を変えられる条件を、Java 版と同じにする。管理者は、2段階認証を使わない設定にできない。確認の済んだメールアドレスとパスワードの両方を持たない利用者は、2段階認証を使う設定にできない。
5. Go 版は、Google か GitHub のアカウントとの連携を解除できる条件を、Java 版と同じにする。確認の済んだメールアドレスとパスワードの両方を持たない利用者は、残り1つの連携を解除できない。利用者がログインする手段を失わないようにするためである。
6. Go 版は、プロフィール画像を見せるための URL を使える時間を、Java 版と同じにする。

### 要件4 版をまたいでも、利用者の操作を終えられ、保存が消えない

切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受けるので、同じ利用者の続けた要求が、別々の版に届くことがある。一方の版が保存したものをもう一方の版が読めないと、利用者が変えたはずの設定が戻って見えるか、利用者がログインできなくなる。そこで、Go 版は、利用者の操作で保存するものを、Java 版と互いに読めるようにする。

1. 利用者が一方の版で変えた名前、プロフィール画像、2段階認証を使うかどうかの設定、メールアドレス、パスワード、Google か GitHub のアカウントとの連携は、もう一方の版でも、変えたあとのとおりに見える。
2. 利用者が一方の版でメールアドレスとパスワードを設定したら、利用者は、届いたメールのリンクで、もう一方の版でもメールアドレスを確認できる。利用者は、一方の版で設定したか変えたパスワードで、もう一方の版にもログインできる。
3. 利用者が一方の版でパスワードを変えたか、退会したら、その前のログインの状態は、もう一方の版でも使えない。
4. この要件の受入基準1から3は、利用者が変えたものがもう一方の版でも見えること、もう一方の版でもメールアドレスを確認でき、ログインできること、前のログインの状態がもう一方の版でも使えないことを決めている。Claude は、この3つのそれぞれについて、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方の筋書きを、版をまたいで確かめる検査に足す。この検査は CI で動く。この検査が通らない PR は、main に入らない。

### 要件5 Java 版と Go 版を比べる検査で、利用者の操作の答えと残したものが同じことを確かめる

人はコードを読まないので、Claude は、Go 版が Java 版と同じかを、機械で確かめる。利用者の操作は、答えのほかに、データベース、ログインの状態の保存先、アップロードした画像の置き場所、送ったメールに結果を残す。答えだけを比べると、Claude は、保存したものの違いや、消し残した画像を見落とす。そこで、Claude は、Java 版と Go 版に同じ要求を送り、答えと残したものの両方を比べる。

1. Claude は、利用者の操作のすべてについて、Java 版と Go 版を比べる検査の筋書きを書く。筋書きには、画面が送る正しい要求に加えて、次の要求を含める。
   - 入力に誤りのある要求。プロフィール画像の大きさ、縦と横の長さ、ファイルの形式の誤りを含める
   - 今のパスワードが合わない要求
   - 2段階認証の設定を変えられる条件に当たらない要求と、連携を解除できる条件に当たらない要求
   - 確認のメールを送り直せる間隔の制限に当たる要求と、確認の要るメールアドレスが無い利用者の要求
   - ログインの状態を持たない要求と、ログインの状態が切れた要求
   - 退会した利用者のログインの状態を持つ要求を、次の2つの場合に分けて含める。Java 版では、退会した利用者のログインの状態がログインの状態の検査を通るかどうかは、その利用者が退会の前に、パスワードの変更のような、すべての端末のログインの状態を使えなくする操作をしたかどうかで変わるためである
     - 退会の前に、すべての端末のログインの状態を使えなくする操作を一度もしていない利用者の要求。Java 版では、この要求は、ログインの状態が切れるまで、ログインの状態の検査を通り、その先の操作ごとの処理で断られる。Java 版と Go 版を比べる検査は、この要求で、要件1の受入基準6で決めた、すでに居ない利用者の要求を断るときの答えと Cookie の削除を比べる
     - 退会の前に、すべての端末のログインの状態を使えなくする操作をした利用者の要求。Java 版では、この要求は、ログインの状態の検査で断られる
   - 偽の要求を見分けるヘッダを付けない要求
2. Java 版と Go 版を比べる検査は、答えに加えて、データベースとログインの状態の保存先に残ったもの、アップロードした画像の置き場所に残ったもの、送ったメールの宛先と件名と本文を比べる。
3. 画像を見せるための URL と確認のリンクの値のように、要求のたびに違う値になるものについて、Java 版と Go 版を比べる検査は、値が違うことでは PR を止めない。Java 版と Go 版を比べる検査は、その値の形が Java 版と同じかを確かめる。
4. 利用者の操作には、Java 版がサーバの誤りとして状態の番号 500 で答えている、形の誤った要求がある。Go 版は、このような要求に、要求の誤りとして状態の番号 400 で答える。たとえば、2MB を超えるファイルを送る要求がある。画面は 1MB を超える画像を送る前に断るので、この違いは利用者の目に触れない。Claude は、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。
5. 置き換えの spec は、主な操作の応答にかかる時間を Java 版と Go 版で測って比べると決めている。Claude は、利用者の操作では、利用者の情報を見ることと、利用者の名前を変えることの2つを、主な操作として測る。

### 要件6 API の説明画面で、ログインした開発者に、その開発者の情報が返ることを確かめる

開発者は、開発環境の API の説明画面の「Try it out」で、Go 版に要求を送って答えを確かめる。認証の spec の要件6の受入基準3は、ログインした開発者の要求に Go 版がその開発者への答えを返すことを、利用者のまとまりの spec で確かめると決めた。認証の spec が main に入った時点では、ログインの要る操作の Go 版が無かったためである。そのため、Claude は、その時点では、ログインした開発者への答えを確かめられなかった。

1. 開発者が、開発環境の API の説明画面の「Try it out」で Go 版にログインしてから、利用者の情報を見る操作を呼ぶと、Go 版は、ログインした開発者の情報を返す。

### 要件7 Java 版と同じにできるかを設計の前に試し、進み具合を表に書く

Claude が、設計を書いたあとや作り終えたあとに、Go 版の動きを Java 版と同じにできないと分かると、所有者は spec を承認し直すことになる。そこで、Claude は、確かめていない動きを設計の前に試し、Java 版と同じにできないと分かったら止まって所有者に報告する。

1. Claude は、この spec の設計を書く前に、Claude が置き換えの spec と認証の spec でまだ試しに作っていない利用者の操作の動きを試しに作り、Java 版と同じになるかを確かめる。試しに作る動きには、少なくとも、次の3つを含める。Claude は、試しに作った方法と結果を、この spec の research.md に書く。
   - アップロードした画像を置き場所に置くときに付ける名前と、画像を見せるための URL
   - 利用者の名前の前後の空白の取り除き方と、利用者の名前の文字数の数え方
   - 退会の完了のメールの件名と本文
2. 試しに作った結果、Java 版と同じにできない動きが見つかったら、Claude は、設計を書く前に止まる。Claude は、何が同じにならないかと、その違いが利用者に何をもたらすかを、所有者に報告する。
3. Claude は、置き換えの spec の進み具合の表の、利用者のまとまりの行に、この spec の場所と、まとまりの状態を書く。Claude は、状態を、spec を作り始めたら「spec の作成中」にし、作り終えたら「作り終えた」にし、Java 版と Go 版を比べる検査に通ったら「比べる検査に通った」にする。
