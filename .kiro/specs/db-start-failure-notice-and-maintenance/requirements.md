# 要件

## 元の要望
Issue #526: 朝のDBの起動に失敗しても自動でやり直し、バックエンドにつながらない間はメンテ画面を出す

### きっかけ

2026-10-08 の朝、DBの定時の起動が失敗してサービスが使えなくなり、ALBの異常のアラームが届いた。その際、利用者にメンテ画面が出ていないことに所有者が気づき、メンテ画面の出し方も見直すことにした。

2026-10-14、所有者は、自動のやり直しを含む設計を、個人開発の無料の実験用アプリには過剰と判断し、DBの起動に失敗したときは通知するだけにすると決めた。

### 困っていること

- バックエンドにつながらないのに、利用者にメンテ画面が出ていない

### やりたいこと

- 朝のDBの定時の起動に失敗したら、所有者に通知する
- 時間外の停止でも障害でも、バックエンドにつながらないときは利用者にメンテ画面を出す(AIの提案を了承)
- メンテ画面の利用者への案内を、時間外の停止と障害とで分ける。時間外の停止の案内は今のままにする(AIの提案を了承)

### どうなれば解決か

- 朝のDBの定時の起動に失敗したら、今のアラームと同じ宛先に通知のメールが1通届く(AIの提案を了承)
- 営業時間中にバックエンドにつながらないときは、障害の案内のメンテ画面が出る(AIの提案を了承)
- 時間外にバックエンドにつながらないときは、時間外の案内のメンテ画面が出る(AIの提案を了承)

### 決めた方式

- 朝のDBの起動の時刻は、今の 7:50 のままにする(AIの提案を了承)

### やらないこと

- 朝のDBの起動に失敗したときに、自動でやり直すこと
- AWSの空きが長く戻らないときに、別のゾーンや別の種類のDBで動かすこと(AIの提案を了承)
- DBが原因でバックエンドが動けないときに、ALBの異常のアラームを止めること。今のまま届いてよい(AIの提案を了承)

## はじめに

KeirekiPro の本番環境は、平日 7:50 にDBを、8:00 にバックエンドを定時に起動し、夜に定時に止めている。2026-10-08 の朝、DBの定時の起動が失敗し、サービスが使えなくなった。このとき、所有者にはDBの起動の失敗が知らされず、利用者にはメンテ画面が出なかった。

この spec は、朝のDBの起動に失敗したときに、本番環境が所有者にメールで通知するようにする。あわせて、バックエンドにつながらない間は利用者にメンテ画面を出し、メンテ画面の案内を時間外の停止と障害とで分ける。

## 範囲

- この spec で決めること: 平日の朝のDBの起動に失敗したときの所有者への通知、バックエンドにつながらないときに利用者に出す画面と案内
- この spec で決めないこと: 起動に失敗したDBを自動で起動し直すこと。AWS の空きが長く戻らないときに、別のゾーンや別の種類のDBで動かすこと。DBが原因でバックエンドが動けないときの ALB の異常のアラーム。DB以外(バックエンドなど)の起動の失敗を所有者に知らせること
- この spec が前提にしていること: 本番環境は、今と同じく、平日の 7:50 にDBを起動し、8:00 にバックエンドを起動し、20:00 にバックエンドを止め、20:05 にDBを止める。今のアラームのメールの宛先は、所有者がメールの受け取りを確認済みである。営業時間は、今のメンテ画面の案内のとおり、日本時間の平日 8:00〜20:00 である

## 要件

### 要件1 朝のDBの起動に失敗したら、所有者にメールで通知する

2026-10-08 の朝は、DBの起動に失敗しても所有者に知らせが届かなかった。個人開発の無料の実験用アプリなので、所有者は、起動の自動のやり直しまでは求めず、失敗を知ることだけを求める。

1. 平日 7:50 の定時の起動でDBが起動できなかったら、本番環境は、所有者に通知のメールを送る。本番環境は、このメールを、今のアラームのメールと同じ宛先に送る。
2. 本番環境は、起動の指令が断られた場合を、起動に失敗したとみなす。起動の指令が通ったあとにDBが立ち上がらずに止まった場合は、AWS がDBの異常の知らせ(カテゴリ failure の RDS のイベント)を出したときに限り、本番環境は起動に失敗したとみなす。AWS がその知らせを出さない場合は、本番環境はこの通知を送らない。その場合は、8:00 にバックエンドが動けなくなるので、所有者は今の ALB の異常のアラームのメールで気づく。
3. 本番環境は、起動に失敗してから10分以内に通知のメールを送る。
4. 本番環境は、1回の起動の失敗につき、通知のメールを1通だけ送る。ただし、AWS がまれに同じメールを2通届けることは、この spec では防がない。
5. 通知のメールは、今のアラームのメールと同じく、AWS が英語の決まった形で送るものでよい。所有者は、メールの件名か本文から、DBの朝の起動に失敗したことか、DBが異常の状態に入ったことが分かる。
6. DBが起動できた日は、本番環境は、起動の指令が断られたことの通知のメールを送らない。AWS がDBの異常の知らせを出したときは、本番環境は、朝の起動と関わらない時刻でも通知のメールを送る。DBが異常の状態に入ったことは、所有者がいつでも知りたいことだからである。
7. 本番環境は、起動に失敗したDBを自動で起動し直さない。DBの朝の起動の時刻は、今の 7:50 のままである。本番環境は、今の起動の指令の送り直し(AWS の側で最大2回)を、今のまま残す。
8. 本番環境は、ALB の異常のアラームのメールを、今のまま送る。通知のメールが届く日も、所有者には ALB の異常のアラームのメールが届いてよい。

### 要件2 バックエンドにつながらないときは、利用者にメンテ画面を出す

2026-10-08 の朝は、バックエンドにつながらないのに、利用者にメンテ画面が出なかった。利用者は、サービスを使えない理由を画面で分かるようになる。

1. 利用者がサービスの画面を開いたときか、画面を操作したときに、バックエンドにつながらなければ、利用者の画面はメンテ画面に切り替わる。バックエンドにつながらないときとは、バックエンドが止まっているとき、バックエンドが起動の途中のとき、DBが動いていないためにバックエンドが動けないときを指す。
2. 利用者の端末に応答がまったく返らないときは、利用者の画面は、今のまま「サーバーで問題が発生しました」の画面に切り替わる。利用者自身の通信が切れているだけのときに、利用者にサービス側の障害だと誤解させないためである。
3. バックエンドが応答したうえで処理の誤りを返したときは、利用者の画面は、今のまま動く。
4. バックエンドにつながるようになったあとも、メンテ画面を開いたままの利用者の画面は、今と同じく、利用者がページを開き直すまでメンテ画面のままである。

### 要件3 メンテ画面の案内を、時間外の停止と障害とで分ける

今のメンテ画面は、時間外の停止の案内だけを出す。営業時間中の障害のときにメンテ画面が「平日 8:00〜20:00 に再度アクセスしてください」と案内すると、利用者は、いつ使えるようになるのかを読み違える。そこで、メンテ画面は、案内を時間外の停止と障害とで分けて出す。

1. メンテ画面を出す時刻が日本時間の平日 8:00〜20:00 の間なら、メンテ画面は障害の案内を出す。障害の案内の見出しは「ただいまご利用いただけません」、本文は「サービスに接続できない状態です。復旧までしばらくお待ちいただき、時間をおいて再度アクセスしてください。」である。
2. メンテ画面を出す時刻がそれ以外(平日の 20:00 から翌朝 8:00 まで、土日の終日)なら、メンテ画面は時間外の案内を出す。時間外の案内の見出しは「メンテナンス中」、本文は「現在サービスは停止中です。平日 8:00〜20:00 に再度アクセスしてください。」で、今の案内と同じである。
3. メンテ画面は、8:00 ちょうどを営業時間に含め、20:00 ちょうどを時間外に含める。
4. メンテ画面は、営業時間中か時間外かを、利用者の端末の地域の設定によらず日本時間で決める。
5. メンテ画面は、祝日を平日と同じく扱う。本番環境は今も祝日にDBとバックエンドを定時に起動しているので、祝日にバックエンドにつながらないときは障害である。
6. 毎朝 8:00 からバックエンドの起動が終わるまでの数分間に、メンテ画面は障害の案内を出す。障害の案内の文は、障害と言い切らない文にしてあるので、起動の途中の数分間に出ても、利用者を誤解させない。

### 要件4 決めたふるまいを、テストと本番での確認で確かめられる

このリポジトリの開発では、人間がコードを読まない。そのため、所有者は、通知のメールとメンテ画面のふるまいが作られたことを、テストと本番での確認で知る必要がある。

1. このリポジトリの品質チェックで動くテストは、利用者の画面がメンテ画面に切り替わるかどうかと、メンテ画面が障害の案内と時間外の案内のどちらを出すかを確かめる。テストは、バックエンドにつながらないとき・端末に応答がまったく返らないとき・バックエンドが処理の誤りを返したときと、営業時間の始まりと終わりの時刻の前後を確かめる。
2. Claude は、通知のメールが届くことを、このリポジトリのテストでは確かめない。Claude は、所有者が変更を本番に入れたあとに、通知のメールが宛先に届くことを確かめる手順をPR本文に書く。Claude は、その手順を、DBの起動を実際に失敗させずに所有者が確かめられるものにする。Claude は、DBが起動できた日に通知のメールが届かないことを確かめる手順も、PR本文に書く。
3. Claude は、本番環境が起動の失敗を見分ける条件(起動の指令が断られた場合と、AWS がDBの異常の知らせを出した場合)と、本番環境が起動の失敗から10分以内に1通の通知を出すように作られていることを、AWS の公式の文書の記述に基づいて決め、design に根拠の URL を書く。AWS が通知を配信するときの遅れは、この spec では防がない。Claude は、この条件が AWS の実際の知らせと合っていることを、本番でDBの起動を失敗させて確かめることはしない。
4. Claude は、起動に失敗したDBを自動で起動し直さないことと、ALB の異常のアラームを変えないことを、PR で動く terraform の plan の差分で確かめる。Claude は、その差分で、DBを起動する指令の時刻と送り直しの回数が変わっていないことと、DBを起動する指令を出すものが新しく足されていないことと、ALB の異常のアラームが変わっていないことを確かめる。
