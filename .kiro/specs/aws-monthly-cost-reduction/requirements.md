# 要件

## 元の要望
Issue #614: AWS の月額の利用料金を、セキュリティを落とさずに税込1万円未満に下げる

### きっかけ

所有者が、セキュリティを今より落とさずに、AWS の月額の利用料金を1万円未満に下げることを求めた。

### 困っていること

- AWS の月額の利用料金が、税込で毎月約12,000円かかっている。

### やりたいこと

- AWS の月額の利用料金を下げる。
- アプリを使える時間は、ほかの変更で1万円を切れないときだけ短くする。(AIの提案を了承)
- 後で Lambda に移すと要らなくなる変更でも、今1万円を切るために行ってよい。(AIの提案を了承)

### どうなれば解決か

- AWS の月額の利用料金が、税込で1万円未満になる。(AIの提案を了承)
- 1万円は、1ドル154円で換算した額(税込で約64.9ドル)として判定する。(AIの提案を了承)
- 判定には、変更をすべて本番に入れたあとの、最初の丸ごと1か月の請求を使う。(AIの提案を了承)

### やらないこと

- 今の守りを1つも外さない。守りとは、WAF の6つのルール、GuardDuty、通信と保存の暗号化、ALB やデータベースへ届く先の制限、シークレットの暗号化と読める役割の制限を指す。置き換えるときは、同じ守りを新しい仕組みにも付ける。(AIの提案を了承)
- アプリを使える時間を短くするときも、平日の9時から19時までは残す。
- Secrets Manager を Parameter Store に移さない。
- 利用者にログインし直してもらうのは、変更を本番に入れるときと、変更が失敗して元に戻すときだけにする。(AIの提案を了承)
- Lambda Web Functions への移行は、この Issue に含めない。Lambda Web Functions が Python に対応したら、別に起票する。(AIの提案を了承)
- backend を Python と Django に移すことは、この Issue に含めない。(AIの提案を了承)

## はじめに

KeirekiPro の本番環境は AWS で動いている。AWS の月額の利用料金は、税込で毎月約12,000円かかっている。

この spec では、AWS の月額の利用料金を税込1万円未満に下げるために、本番環境で使う AWS のサービスと、その設定をどう変えるかを決める。この spec では、そのために本番環境に加える変更を、「料金を下げる変更」と呼ぶ。Claude は、後で backend を Lambda Web Functions に移すと要らなくなる変更も、料金を下げる変更に含めてよい。

## 範囲

- この spec で決めること: 次の8つである。
  - 料金が1万円未満に下がったかどうかの判定のしかた
  - アプリの稼働時間を短くしてよい場合
  - 料金を下げる変更のあとも残す、今のセキュリティの対策
  - 料金を下げる変更のあとも変えない、利用者の使い勝手
  - 料金を下げる変更のあとも続ける、所有者への異常のメール
  - 料金を下げる変更を本番に入れたあとに所有者が確かめることと、失敗したときに本番環境を元に戻す手順
  - セキュリティの対策と、異常のメールを送る仕組みが残ることを、所有者が確かめる表
  - 料金を下げる変更のあとの本番環境に合わせて直す設計書
- この spec で決めないこと: 次の2つである。
  - backend を Lambda Web Functions に移すこと
  - backend を Python と Django に移すこと
- この spec が前提にしていること: 次の4つである。
  - アプリの稼働時間とは、利用者がアプリを使える時間である。アプリの稼働時間は、今のメンテ画面の案内のとおり、日本時間の平日 8:00〜20:00 である
  - 本番環境は、今、日本時間の平日 7:50 にDBを起動し、8:00 に backend を起動し、20:00 に backend を止め、20:05 にDBを止める
  - GuardDuty は、所有者が、このリポジトリの設定の外で有効にしている
  - terraform apply と、本番のデプロイと、AWS のコマンドは、所有者が実行する

## 要件

### 要件1 AWS の月額の利用料金を、税込1万円未満に下げる

所有者は、今あるセキュリティの対策を1つも減らさずに、毎月約12,000円かかっている AWS の利用料金を1万円未満に下げたい。AWS の料金を円に直した額は為替で変わるので、所有者は、料金が1万円未満に下がったかを判定するときに使う、ドルを円に直す率と、判定に使う月を、前もって決めた。

1. 所有者は、料金を下げる変更をすべて本番に入れたあとの最初の丸ごと1か月を、判定の月とする。丸ごと1か月とは、ある月の1日からその月の月末までを指す。所有者は、判定の月の AWS の請求の、ドルで示された税込の合計額に154を掛ける。掛けた額が10,000円未満なら、所有者は、この spec の目的を満たしたと判定する。
2. 所有者は、判定の換算を1ドル154円で固定する。所有者は、判定の月の実際の為替を判定に使わない。
3. Claude は、design.md に、料金を下げる変更のあとの AWS の月額の見積もりを、AWS のサービスごとに書く。Claude は、見積もりの単価ごとに、出どころの URL と、単価を確かめた日付を書く。Claude は、見積もりの税込の合計額に154を掛けた額が10,000円未満になるように、料金を下げる変更の中身を design.md で決める。
4. 所有者は、判定の月の AWS の請求の税込の合計額に154を掛けた額が10,000円以上になったら、そのあとに何をするかを決める。所有者が判定の月の請求の内訳を貼ったら、Claude は、内訳を design.md の見積もりと比べ、見積もりを上回った AWS のサービスと、上回った額を所有者に示す。

### 要件2 アプリの稼働時間は、ほかの料金を下げる変更だけでは AWS の月額の利用料金を1万円未満にできないときに限って短くする

アプリの稼働時間を短くすると、利用者がアプリを使えない時間が増える。そこで、所有者は、アプリの稼働時間を短くせずに AWS の月額の利用料金を1万円未満にできるなら、アプリの稼働時間を今のまま残したい。

1. Claude は、design.md に、アプリの稼働時間を今の日本時間の平日 8:00〜20:00 のままにしたときの、AWS の月額の利用料金の見積もりを書く。その見積もりの税込の合計額に154を掛けた額が10,000円未満なら、Claude は、design.md でアプリの稼働時間を今のまま変えない。
2. Claude は、design.md でアプリの稼働時間を短くしてよい。ただし、Claude がアプリの稼働時間を短くしてよいのは、アプリの稼働時間を今のままにした見積もりの税込の合計額に154を掛けた額が10,000円以上になるときに限る。アプリの稼働時間を短くするときは、Claude は、短くしたあとのアプリの稼働時間と、そのアプリの稼働時間での月額の見積もりを、design.md に書く。
3. アプリの稼働時間を短くするときも、Claude は、日本時間の平日 9:00〜19:00 をアプリの稼働時間に残す。
4. アプリの稼働時間を短くしたら、本番環境は、短くしたあとのアプリの稼働時間が始まる時刻に、利用者がアプリを使えるようにしておく。
5. アプリの稼働時間を短くしたら、メンテ画面は、時間外の案内に、短くしたあとのアプリの稼働時間を出す。メンテ画面は、短くしたあとのアプリの稼働時間の中では障害の案内を出し、そのアプリの稼働時間の外では時間外の案内を出す。

### 要件3 今あるセキュリティの対策を、料金を下げる変更のあとも1つも減らさない

所有者は、料金を下げるために、セキュリティを今より落としたくない。料金を下げる変更で AWS のサービスを別のサービスに替えるときも、所有者は、替える前のサービスに付いていたセキュリティの対策が、替えたあとのサービスにも付いていることを求める。

1. 本番環境は、WAF の6つのルールを、今と同じ動きで残す。WAF とは、インターネットから届いた通信のうち、攻撃に見えるものを backend に届く前に止める仕組みである。6つのルールは、日本の外からの通信を止めるルール、ログインなどの認証の通信の回数を接続元ごとに限るルール、API の通信の回数を接続元ごとに限るルール、よくある攻撃の形の通信を止めるルール、悪用が知られている入力を止めるルール、DBを不正に操作する入力(SQLインジェクション)を止めるルールである。本番環境は、ルールごとの回数の上限と、今は止めずに数えるだけにしている項目も、今と同じにする。
2. 本番環境は、GuardDuty を有効のまま保つ。GuardDuty とは、AWS の中の不審な動きを見つけて所有者に知らせる仕組みである。
3. 本番環境は、今暗号化している通信を、料金を下げる変更のあとも暗号化する。今暗号化している通信には、利用者の端末とアプリの間の通信と、backend とDBの間の通信と、backend とキャッシュの間の通信がある。キャッシュとは、ログインの状態のように、すぐに読み書きしたい短い間のデータを置く場所である。
4. 本番環境は、今暗号化して保存しているデータを、料金を下げる変更のあとも暗号化して保存する。今暗号化して保存しているデータには、DBの中身と、DBのバックアップと、利用者が上げた画像がある。
5. インターネットから届く通信のうち、WAF を通ったものだけが backend に届く。本番環境には、WAF を通らずにインターネットから backend に届く通信の経路が無い。
6. DBとキャッシュには、backend からの通信だけが届く。本番環境には、インターネットからDBとキャッシュに届く通信の経路が無い。キャッシュは、今と同じく、キャッシュのパスワードを知っている backend からの読み書きだけを受け付ける。
7. 本番環境は、シークレットを、今と同じく Secrets Manager に置く。シークレットとは、DBのパスワードやキャッシュのパスワードのように、知られると不正に使われる値である。本番環境は、シークレットを暗号化して保存し、シークレットを読める役割を今と同じく限る。新しいサービスのためにシークレットを足すときも、本番環境は、そのシークレットを Secrets Manager に置いて暗号化して保存し、そのシークレットを読める役割を限る。
8. 料金を下げる変更で AWS のサービスを別のサービスに替えたら、本番環境は、替えたあとのサービスにも、この要件に書いたセキュリティの対策を付ける。
9. 本番環境は、料金を下げる変更を本番に入れている途中にも、この要件に書いたセキュリティの対策が働かない時間を作らない。

### 要件4 料金を下げる変更のあとも、利用者は今と同じくアプリを使える

所有者は、AWS の料金を下げるために、利用者に不便をかけたくない。ただし、所有者は、料金を下げる変更を本番に入れるときに、利用者全員に一度だけログインし直してもらうことを認めた。料金を下げる変更でログインの状態を保存する仕組みを替えると、利用者のログインの状態が消えることがあるためである。また、所有者は、料金を下げる変更が失敗して、その変更を元に戻したときに、利用者がもう一度ログインし直すことも認めた。

1. 料金を下げる変更のあとも、利用者は、今と同じ機能を使える。
2. 利用者がログインし直すのは、料金を下げる変更を本番に入れたときと、料金を下げる変更を元に戻したときだけである。利用者は、今と同じく、ログインしてから7日のあいだ、ログインし直さずにアプリを使える。
3. 料金を下げる変更を本番に入れても、利用者が保存したデータは消えない。利用者が保存したデータには、アカウントと、職務経歴書と、画像がある。
4. 料金を下げる変更を本番に入れても、アプリの稼働時間の中にアプリは止まらない。
5. 料金を下げる変更を本番に入れても、パスワードの再設定のメールのリンクと、二段階認証のコードは、期限が来るまで使える。これは、利用者がアプリの稼働時間の中に受け取ったリンクとコードに当てはまる。

### 要件5 料金を下げる変更のあとも、本番環境の異常を、今と同じくメールで所有者に送る

所有者は、本番環境の異常を、今はアラームが送る異常のメールで知っている。料金を下げる変更で異常のメールが届かなくなると、所有者は、サービスが止まっていることを知らないまま過ごすことになる。

1. 料金を下げる変更のあとも、本番環境は、今のアラームがメールを送っている8種類の異常について、今と同じ宛先にメールを送る。8種類の異常は、次のとおりである。
   - backend の CPU の使用が多い
   - backend のメモリの使用が多い
   - backend が利用者にエラーの応答を返すことが多い
   - backend が応答しない
   - DBの CPU の使用が多い
   - DBの空き容量が少ない
   - キャッシュのメモリの使用が多い
   - DBの朝の起動に失敗したか、DBが異常の状態に入った
2. 本番環境は、異常の種類ごとに、異常が起きてからメールを送るまでの時間を、今のアラームより長くしない。本番環境は、異常が起きてもメールを送らない場合を、今より増やさない。Claude は、今のアラームが見ている値を料金を下げる変更のあとに見られなくなる異常について、代わりに見る値と、その値で同じ種類の異常を見つけられる理由を、design.md に書く。

### 要件6 料金を下げる変更が失敗したときに本番環境を元に戻す手順を、PR の本文に書く

料金を下げる変更を本番に入れると、terraform apply が本番環境の AWS のサービスを作り直す。そのため、PR のマージを取り消しても、本番環境は元に戻らない。所有者は、terraform apply が失敗したときや、apply のあとにアプリが動かなくなったときに、本番環境を元に戻す手順をすぐに使えるようにしておきたい。

1. Claude は、PR の本文の「マージのあとにすること」に、本番環境を料金を下げる変更の前の状態に戻す手順を書く。手順には、所有者が打つコマンドと、元に戻ったかの見分け方を書く。
2. Claude は、PR の本文の「マージのあとにすること」に、terraform apply のあとに所有者が確かめることを書く。確かめることは、利用者として今と同じ機能を使えることと、WAF を通らずに backend に届く通信の経路が無いことと、異常のメールが届くことの3つである。Claude は、それぞれについて、所有者がする画面の操作かコマンドと、うまくいったかの見分け方を書く。

### 要件7 セキュリティの対策と、異常のメールを送る仕組みが残ることを、所有者が表で確かめられる

所有者はコードを読まない。そのため、所有者は、料金を下げる変更のあとも今のセキュリティの対策と異常のメールを送る仕組みが残ることを、コードではなく表で確かめたい。

1. Claude は、design.md に表を書く。表の行は、要件3に書いたセキュリティの対策の1つずつと、要件5に書いた8種類の異常の1つずつである。Claude は、対策の行に、今その対策を受け持つ AWS のサービスと、料金を下げる変更のあとにその対策を受け持つ AWS のサービスを書く。Claude は、異常の行に、今その異常のメールを送っている AWS のサービスと、料金を下げる変更のあとにその異常のメールを送る AWS のサービスを書く。
2. Claude は、PR の本文に、WAF の6つのルールの設定を変えたかどうかを書く。ここでの設定とは、ルールごとの名前、優先の順、止めるか数えるだけかの動き、回数の上限、数えるだけにしている項目である。WAF のルールの設定を書いたファイルを PR で変えたときは、Claude は、変える前と後の設定をルールごとに PR の本文の表に並べ、同じであることを示す。

### 要件8 設計書を、料金を下げる変更のあとの本番環境に合わせる

`doc/インフラ設計` の設計書は、本番環境の AWS のサービスの組み合わせを説明している。料金を下げる変更のあとに設計書が古いままだと、所有者と Claude は、本番環境を設計書のとおりだと思い違える。

1. Claude は、`doc/インフラ設計` の設計書を、料金を下げる変更のあとの本番環境に合わせて直す。
