### 申告

**1. 使える時間を短くするかどうかを、実際の請求ではなく design の見積もりで決める** — 要件2.1、要件2.2

- Issue の記載: あり。「アプリを使える時間は、ほかの変更で1万円を切れないときだけ短くする。(AIの提案を了承)」。見積もりで決めるか、実際の請求で決めるかは書かれていない
- 決めたこと: design に書く見積もり(税込の合計額に154を掛けた額)が10,000円未満なら時間を今のまま保ち、見積もりで届かないときに限り短くする。実際の請求は判定の月(要件1.1)で見る
- 他にありえた選択肢: ほかの変更だけを先に本番に入れ、最初の丸ごと1か月の請求を見てから、届かなかったときだけ時間を短くする(判定が1か月以上遅れる代わりに、見積もりの誤りで時間を短くしすぎることが無い)
- 外れていた場合: 見積もりが実際より高ければ、短くしなくてもよかった時間を短くする。見積もりが実際より低ければ、判定の月に1万円を超え、要件1.4のとおり所有者が決め直すことになる

**2. 変更を本番に入れる間も、使える時間の中にアプリを止めない** — 要件4.4

- Issue の記載: なし。利用者への影響で Issue にあるのは「ログインし直してもらうのは一度だけ」と「平日9時から19時までは残す」だけ
- 決めたこと: 使える時間の中に、変更を本番に入れることでアプリが止まることは無い
- 他にありえた選択肢: 使える時間の中に短い停止を1回認める(本番に入れる作業を、backend とDBが動いている時間に行える)
- 外れていた場合: 変更を本番に入れる作業が、backend とDBが止まっている時間(平日20:05〜翌7:50と土日)に限られる。DBが止まっていると適用できない変更があるため、手順書(要件6)が複雑になるか、所有者が手でDBを起動する段階が要る

**3. 今のアラームが知らせる8種類の異常を、構成を変えたあとも同じ宛先にメールで知らせる** — 要件5

- Issue の記載: なし。Issue の「守り」の一覧(WAF、GuardDuty、暗号化、届く先の制限、シークレット)にアラームは入っていない
- 決めたこと: 今のアラームが知らせている8種類の異常を、置き換えたあとも、今より遅くならず、知らせない場合が増えないように、同じ宛先にメールで知らせる(要件5.1〜5.3)
- 他にありえた選択肢: アラームを守りの対象にせず、置き換えた仕組みで見られる異常だけを知らせる(異常の種類が減ることを認める)
- 外れていた場合: 置き換えた仕組みで同じ値を見られないとき、design で代わりの見張り方を考える手間が増える。逆にこの要件が無いと、所有者がサービスの停止に気づけなくなる

**4. GuardDuty は、所有者がこのリポジトリの設定の外で有効にしている** — 範囲の節「この spec が前提にしていること」、要件3.2

- Issue の記載: あり。「守りとは、WAF の6つのルール、GuardDuty、…を指す」。GuardDuty がどこで設定されているかは書かれていない
- 決めたこと: GuardDuty はリポジトリの terraform に無く(`terraform/` に guardduty の記述が無いことを確かめた)、所有者が外で有効にしていると前提にした
- 他にありえた選択肢: GuardDuty を terraform に取り込んで管理の対象にする。または、所有者が有効にしているかを確かめる手順を要件6の手順書に入れる
- 外れていた場合: GuardDuty が実は有効でなければ、要件3.2「有効のまま保つ」を確かめる手段がリポジトリに無いまま、「守りを外さない」の判定が成り立たなくなる

**5. パスワードの再設定のリンクと二段階認証のコードは、変更を本番に入れたことで期限の前に使えなくなることは無い** — 要件4.5

- Issue の記載: なし。Issue にあるのは「ログインし直してもらうのは一度だけ」だけ
- 決めたこと: 使える時間の中に受け取った再設定のリンクと二段階認証のコードは、変更を本番に入れたことで期限の前に使えなくならない
- 他にありえた選択肢: ログインの状態と同じく、変更を本番に入れるときの一度は消えてよいとする。リポジトリの実装では、再設定のトークンと二段階認証のコードは、ログインの状態(リフレッシュトークン)と同じキャッシュ(`RedisPasswordResetTokenStore` `RedisTwoFactorAuthCodeStore` `RedisRefreshTokenStore`)に置かれているため、キャッシュを置き換えればログインの状態と一緒に消える
- 外れていた場合: キャッシュを置き換える方式では、要件4.4のとおり使える時間の外に本番に入れるときだけ満たせる(使える時間の外は backend が止まっているので、期限の短いトークンは次の朝までに切れている)。使える時間の中に入れる方式を design が選ぶと、キャッシュの中身を写す仕組みが要る

**6. 変更を本番に入れる手順書と、PR で守りを確かめることを、要件にした** — 要件6、要件7

- Issue の記載: なし
- 決めたこと: 所有者が手で行う手順書(段階ごとのコマンド、戻し方、入れたあとに確かめること、請求の読み方)と、設計書の更新と、PR での WAF の設定の確かめと、design への守りと異常の受け持ちの対応表を要件にした
- 他にありえた選択肢: 手順書と対応表を design と PR 本文の書き方に委ね、要件にしない
- 外れていた場合: 作る文書が増えるだけで、本番環境の動きは変わらない
