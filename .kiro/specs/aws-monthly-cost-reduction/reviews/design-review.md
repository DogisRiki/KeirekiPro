### 申告

**1. ALB のセキュリティグループを変えず、CloudFront のオリジン向けのプレフィックスリストで VPC オリジンからの通信を許す** — 使う既存の仕組み、部品「セキュリティグループ」、安全の節の最後の箇条

- Issue の記載: なし(「ALB やデータベースへ届く先の制限」を外さないことだけが書いてある)
- 決めたこと: ALB のセキュリティグループ `keirekipro-alb-sg` の、プレフィックスリスト `com.amazonaws.global.cloudfront.origin-facing` から 443 を許すルールを、そのまま VPC オリジンからの通信の許可に使う
- 他にありえた選択肢: VPC オリジンが作る `CloudFront-VPCOrigins-Service-SG` からの 443 を許すルールに替える。または両方を許す
- 外れていた場合: VPC オリジンからの通信の送り元がプレフィックスリストに当たらないと、切り替えのあとに API がすべて届かなくなる。所有者は週末の確かめで気づき、元に戻す手順で戻すことになる。このリポジトリの材料では、公式文書が両方の形を挙げているという design の記載を確かめられなかった

**2. 1万円までの余裕が約80円しかないまま、シークレットをまとめる案と Fargate のメモリを減らす案を今は採らない** — 作らないもの、部品「月額の見積もり」、月額の見積もりの節

- Issue の記載: 「税込で1万円未満になる」「1ドル154円で換算」「最初の丸ごと1か月の請求で判定」
- 決めたこと: 見積もりは約9,920円で、余裕は約80円である。2つの案は、判定の月に1万円を超えたときの候補として残す
- 他にありえた選択肢: 2つの案のどちらか、または両方を今入れて、余裕を約270円から約470円にする
- 外れていた場合: LCU、GuardDuty、RDS のバックアップなどが見積もりより少し増えるだけで判定の月に1万円を超え、案を入れてからさらに1か月の請求を待つことになる

**3. ALB を同じ資源の名前のまま作り直し、作り直しの間は API に届かない形で、金曜の夜か週末に切り替える** — 全体の構成、処理の流れ、移行の節

- Issue の記載: 「利用者にログインし直してもらうのは、変更を本番に入れるときの一度だけ」
- 決めたこと: 新しい ALB と並べて切り替えず、古い ALB を消してから新しい ALB を作る。切り替えは金曜の 20:15 以降か週末に行う
- 他にありえた選択肢: 別の資源の名前で internal の ALB を並べ、ターゲットグループを分けて切り替える(checkov の凍結の一覧の作り直しを所有者に提案する必要がある)
- 外れていた場合: apply が途中で失敗すると、元に戻すまで API に届かない。週末の中に戻せなければアプリの稼働時間に食い込む(指摘 D1-1-5)

**4. 元に戻したときは、利用者がもう一度ログインし直す** — 移行の節の元に戻す手順の4

- Issue の記載: 「利用者にログインし直してもらうのは、変更を本番に入れるときの一度だけにする」
- 決めたこと: 元に戻す手順では、利用者が2度目のログインをすることを認める
- 他にありえた選択肢: 元に戻した場合も含めて1度に収める手立て(古いキャッシュに残るログインの状態を使える期間の中に戻す、など)を design に書く
- 外れていた場合: 失敗して戻したときに、要件4の2の「一度だけ」を満たさない。所有者がこれを認めるかどうかを、承認のときに決める必要がある

**5. キャッシュに使用量の上限(保存量 1GB、毎秒 1000 ECPU)を付け、メモリのアラームを 300MB のバイト数で鳴らす** — 部品「ElastiCache Serverless」「キャッシュのメモリのアラーム」

- Issue の記載: なし
- 決めたこと: 上限に達したら、期限付きのキーから追い出すか、要求を絞る。アラームは 300MB で鳴らす
- 他にありえた選択肢: 上限を付けない、上限を大きくする、アラームの閾値を上限に対する割合で決める
- 外れていた場合: 利用が増えたときに、ログインの状態が7日より早く消えるか、要求が絞られて応答が遅くなる。上限を変えたときにアラームの閾値の見直しを忘れると、鳴るのが遅れる
