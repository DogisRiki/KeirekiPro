## 実装のメモ

- `.claude/settings.json` と `.claude/hooks/` は、Claude が書けない(`settings.json` の permissions の deny)。所有者が写すまで、Claude はそれらを本来の場所に書こうとしない。Claude は、所有者への依頼を、所有者に3つのファイルを写してもらうタスク2.3 の1回にまとめる。`.claude/agents/` と `.claude/skills/` は deny されていないので、Claude が直接直す
- 置き場所: Claude は、`.claude/settings.json` と `.claude/hooks/` の下に置くファイルの完成版を、作業フォルダの中の `.claude/.state/owner-readable-writing/`(置き場所)の `place-1/` に、リポジトリと同じ並びで作る。`.claude/.state/` は git の管理外で、deny の対象に当たらない。scratchpad に置かないのは、scratchpad が会話ごとに別の場所になり、所有者の返事が新しい会話で来たときや、別の実装役が続きを作るときに見つからないためである
- 検査用の写し: Claude は、テストと shellcheck を、作業フォルダを `git archive HEAD` で scratchpad の一時フォルダに写し、そこに `place-1/` のファイルを本来のパスで重ねたフォルダで流す。まだリポジトリに無いファイルを `docker -v` で作業フォルダに重ねると、作業フォルダに0バイトのファイルが残るので、Claude はそうしない
- 実装の記録のファイル: 実装役は tasks.md を書けないので、1.1 のフォルダとファイルの数、1.3 の対応の表、1.5 の確かめの表、3.3 の直した書式の一覧を、`.kiro/specs/owner-readable-writing/pr-notes.md` に書く。確認役は、これらの完了の確かめ方を `pr-notes.md` で確かめる
- タスク2.3の進め方: タスク2.3は `_保留:_` なので、`/kiro-impl` は、自律で進めるときに、実装役を起動せずにタスク2.3を飛ばす。親の会話の Claude は、`/kiro-impl` の Step 3 の繰り返しが終わったあと、Step 4 の `/kiro-validate-impl` を流す前に、タスク2.3を自分で進める。テストが通ったら、親の会話の Claude は、タスク2.3の `_保留:_` の行を消して完了の印を付け、コミットする。実装役は、フックとテストを作るタスク2.1 と、settings.json の写しを作るタスク2.2 で、所有者に依頼せず、置き場所に作ったものを確認役に渡す。確認役は、タスク2.1 と 2.2 で作ったフック、テスト、settings.json の写しを、置き場所のパスで確かめる。置き場所は git の管理外で、成果が `git diff` に出ないためである
- `settings.json` のフックの登録は、所有者が写したあとに新しく始めた会話から働く。Claude Desktop では、動いている会話には設定の変更が当たらない
- CLAUDE.md と点検役とスキルの手順をつなぐタスク3は、1.2 で作る `owner-writing.md` の見出しの名前を使うので、Claude は、タスク3を 1.2 のあとに始める。CLAUDE.md に1行を足すタスク3.1、点検役の定義を直すタスク3.2、報告の書式を直すタスク3.3 は、互いに別のファイルを直すので、並行に進められる。決まりの要点を渡すフックを作るタスク2は、design が決めた決まりのファイルの見出しの組み立て(`## 決まり` と `### `)だけを使い、テストでは一時のフォルダに置いた決まりのファイルを読む。そのため、Claude は、タスク2を、書き方の決まりのファイルと例の一覧を作るタスク1と並行に進められる。
- 出荷のとき: 親の会話の Claude は、`/ship` で、PR 本文に `## マージのあとの作業` の節を置き、出荷の報告と PR 本文に、マージしたら Claude に伝えてほしいことを1回ずつ書く。頼みの文は「PR をマージしたら、そのことを Claude に1回伝えてください。伝えられたら、Claude がメモリから移した書き方の決まりを消します。」とする。PR 本文には、`pr-notes.md` の 1.3 の対応の表、1.5 の確かめの表、3.3 の直した書式の一覧も貼る
- タスク5の完了の印: Claude は、この spec の PR では、タスク5を `_保留:_` のまま出す。`/kiro-validate-impl` を流すときには、タスク2.3はすでに完了の印が付いているので、`_保留:_` はタスク5だけである。`/kiro-validate-impl` が `_保留:_` を報告したら、Claude は、それがタスク5であることと、出荷の報告に頼みの文があることを確かめる。完了の印を付けるための PR は作らない
- 共通の完了条件の1(確かめるテストの無い受入基準を残さない)の例外は、文がわかりやすいか、文が決まりから外れるかを判断する受入基準と、Claude の振る舞いを決める受入基準と、リポジトリの外のメモリを扱う受入基準である。Claude は、例外とした理由を、それぞれのタスクの「受入基準とテストの対応」の行に書いた。
- 共通の完了条件の2(verify のスキル)は、この spec が `frontend/` `backend/` `terraform/` を変えないので当てはまらない。代わりに、Claude は、決まりの要点を渡すフックを作るタスク2の小タスク2.1、2.2、2.3 の完了の確かめ方のとおりに、`.claude/hooks/tests/` のテストを Git Bash と Linux のコンテナで流し、CI と同じ shellcheck を流す
- CLAUDE.md の大きさ: 出荷の前に main を取り込んだら、main の変更とタスク3.1 の1行を合わせた CLAUDE.md が、CI の検査 `check-claude-md-size.sh` の上限の 19000 バイトを 419 バイト超えた。Claude は、上限を上げず、タスク3.1 の1行を「所有者に送る文は `.kiro/settings/rules/owner-writing.md` を読んで書き、送る前に自分で読み直す。わかりにくいと言われたら同ファイルの手順で決まりと例を足す」に縮め、CLAUDE.md を 18993 バイトにした。読み直す文の種類と、読み直しに別のエージェントを動かさないことは、`owner-writing.md` の冒頭の節と「送る前の読み直し」の節に書いてあるので、1行からは外した

## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめてから、コードを元に戻す。
