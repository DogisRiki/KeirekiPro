# 調査と設計の判断の記録

## まとめ

- 調べた範囲: 今の書き方の決まりの置き場所(`.kiro/settings/rules/spec-writing.md`、CLAUDE.md、Claude Code のメモリ)、所有者の承認が要る場所(`.github/CODEOWNERS`)、所有者の入力のたびに動く今のフック(`.claude/settings.json` の `UserPromptSubmit`)、報告の書式を定めるスキルの手順
- 分かったこと:
  - `.kiro/` は `.github/CODEOWNERS` に書かれていない。`.kiro/settings/rules/` に置いたファイルは、所有者の承認を待たずにマージされる
  - `.claude/settings.json` には、`UserPromptSubmit` で動くフックが2つある(`notify-spec-review.sh` と `session-registry.sh`)。`notify-spec-review.sh` は、標準出力に書いた文を、Claude が読む文脈として渡している
  - `spec-writing.md` を名指しで読むファイルは、スキルの手順、エージェントの定義、spec の雛形、CLAUDE.md を合わせて 22 ある
  - 報告の書式のうち、書き方の決まりから外れるものは、`/start` の Step 6 の理由の表(根拠のマスに文を詰める)と、`/spec-review` の Step 7 の報告の見本(「高 0件 / 中 0件」のように斜線でつなぎ、「往復」「レビュー役」のような作業の中の呼び名を使う)の2つである

## 調べたこと

### 所有者の入力のたびに文脈を渡す方法

- 調べた先: Claude Code の公式の説明(https://code.claude.com/docs/en/hooks)と、このリポジトリの `notify-spec-review.sh`
- 分かったこと: `UserPromptSubmit` のフックが終了コード0で標準出力に書いた文は、Claude が読む文脈として、所有者の入力と一緒に Claude に渡る。渡せる文の長さには上限があり、`notify-spec-review.sh` の注記は1万字としている
- 設計への影響: 書き方の決まりのファイルから決まりの名前と1文の決まりだけを抜き出して渡せば、上限の内に収まる。例の文は渡さず、ファイルの場所を添える

### 決まりの置き場所

- 調べた先: `.github/CODEOWNERS`
- 分かったこと: 所有者の承認が要るのは `/.github/` `/.claude/` などで、`/.kiro/` と `CLAUDE.md` は含まれない
- 設計への影響: 書き方の決まりのファイルと例の一覧を `.kiro/settings/rules/` に置く。フックの本体(`.claude/hooks/`)は決まりの中身を持たず、ファイルを読むだけにする。こうすると、例を足す PR は `.kiro/` だけを直し、所有者の承認を待たない

## 比べた案

| 案 | 費用 | 決まりを忘れにくいか | 採否 |
|---|---|---|---|
| 送る文を毎回別のエージェントに読ませる | 送るたびに数万トークン | 忘れにくい | 不採用(所有者が退けた) |
| CLAUDE.md に書くだけ | 増えない | 会話が長くなると忘れやすい | 単独では不採用 |
| CLAUDE.md の1行と、入力のたびに決まりの要点を渡すフック | 入力1回につき約3千字 | 決まりが毎回、会話の新しい位置に来る | 採用 |

表の補足: CLAUDE.md は会話の始めにだけ読み込まれる。会話が長くなると、決まりは会話の古い位置に残るだけになる。フックで入力のたびに渡すと、Claude が返事を書く直前に決まりが目に入る。

## 設計の判断

### 判断: 決まりの名前と1文の決まりだけをフックで渡す

- 背景: 書き方の決まりのファイルには、決まりごとに外れた文の例と直した文の例を書くので、ファイル全体は1万字を超えうる
- 比べた案: ファイル全体を渡す案、要点の節をファイルの中に別に書く案、見出しと最初の1文を抜き出す案
- 選んだ案: 見出しと最初の1文を抜き出す案
- 理由: ファイル全体を渡すと、上限を超え、入力のたびの費用も大きい。要点の節を別に書くと、同じ決まりを1つの文書に2回書くことになる。見出しと最初の1文を抜き出せば、決まりの本文は1か所のままになる
- 引き換えにしたこと: Claude は、例の文を見たいときに、ファイルを自分で開く

### 判断: spec-writing.md を読むスキルを書き換えない

- 背景: 7つの決まりを `spec-writing.md` から移すと、`spec-writing.md` を名指しで読む 22 のファイルが、移した決まりを読めなくなる
- 選んだ案: `spec-writing.md` の冒頭に、spec の本文には書き方の決まりのファイルの決まりも当てはまることを書く。スキルの手順は、要件で決まった `spec-style-checker` の定義だけを直す
- 理由: スキルは `spec-writing.md` を最初から読むので、冒頭の文で書き方の決まりのファイルにたどり着く。加えて、フックが入力のたびに決まりの要点を渡す。22 のファイルを直すと、所有者が承認する差分が大きくなる

## 危険と対策

- Claude が要点を読んだうえで見落とす: 対策は、例の一覧での確かめ(要件3)と、所有者の指摘を例に足す流れ(要件4)である。読み直しを機械で強制する手段は無い
- 決まりが増えて要点が1万字に近づく: フックは、抜き出した文が9千字を超えたら、超えた分を渡さず、ファイルの場所を開くよう添える
