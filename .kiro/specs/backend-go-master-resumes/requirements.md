## はじめに

Issue #445 で、所有者は、backend を Java と Spring Boot から Go に置き換えると決めた。置き換えの進め方と、Go 版が守ることは、spec `backend-go-replacement` が決めている。この spec では、spec `backend-go-replacement` を「置き換えの spec」と呼ぶ。置き換えの spec は、機能のまとまりごとの Go 版を、まとまりごとの別の spec で作ると決めた。この spec は、そのうちマスタと経歴書のまとまりを受け持ち、Issue #772 の「やりたいこと」に挙げた26の操作の Go 版を作る。この spec では、この26の操作を「マスタと経歴書の操作」と呼ぶ。今の Go 版は、マスタと経歴書の操作の要求に、未実装であることを示す答えを返す。

マスタと経歴書の操作は、次の2種類に分かれる。

- マスタの操作: 資格の名前、SNS の名前、技術スタックの名前の一覧を返す3つの操作である。画面は、利用者が経歴書を編集するときに、この一覧を入力の候補として見せる
- 経歴書の操作: 残りの23の操作である。経歴書の操作は、経歴書の一覧の取得、経歴書の作成、経歴書1件の取得、経歴書の削除、基本の情報の更新と、経歴書の6つの欄の項目の追加、更新、削除からなる。6つの欄は、職歴、プロジェクト、資格、ポートフォリオ、SNS、自己PR である。経歴書の作成には、利用者が持っている経歴書をコピーして新しい経歴書を作ることも含む

この spec の「所有者」「Java 版」「Go 版」「利用者」「画面」「切り替え」は、置き換えの spec と同じものを指す。「筋書き」は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査が、版に送る要求の並びと、期待する答えを書いたものを指す。「項目」は、経歴書の1つの欄に入れた1件の記録を指す。たとえば、職歴の欄に入れた1社分の記録が、1つの項目である。

Issue #772 の「どうなれば解決か」は、マスタと経歴書の操作について、置き換えの spec の16の受入基準を満たすことを求めている。置き換えの spec は、まとまりごとの spec に置き換えの spec の要件を書き写さず、当てはまる要件を指すと決めている。そこで、この spec は、16の受入基準のそれぞれを、次の表のとおりに受け持つ。表で「置き換えの spec のとおり」とした受入基準は、マスタと経歴書の操作に固有の決めごとが無い。Claude は、その受入基準を、置き換えの spec の文のとおりにマスタと経歴書の操作に当てはめる。

## 範囲

- この spec で決めること: この spec では、次の4つを決める。
  - マスタと経歴書の操作の Go 版
  - ほかの利用者の経歴書についての要求と、退会してすでに居ない利用者の要求に、Go 版が返す答え
  - マスタと経歴書の操作について、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査に足す筋書き
  - Java 版と Go 版を比べる検査と、版をまたいで確かめる検査で、Java 版を本番と同じく日本の時間帯で動かすこと
- この spec で決めないこと: この spec では、次の4つを決めない。
  - ほかのまとまりの操作の Go 版。たとえば、Claude は、経歴書を PDF と Markdown で書き出す操作の Go 版を出力のまとまりの spec で作り、経歴書のバックアップと戻しの Go 版をバックアップのまとまりの spec で作る
  - ログインの状態の検査。Claude は、認証のまとまりの spec `backend-go-auth` で作った検査を、作り直さずにそのまま使う
  - 機能を足すことと、仕様を変えること。Issue #445 の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである
  - 本番の切り替え。本番の切り替えは、置き換えの spec が受け持つ
- この spec が前提にしていること: この spec は、次の4つを前提にする。
  - 置き換えの spec の段階2は、Go 版の品質チェックと、Java 版と Go 版を比べる検査をそろえる段階である。次の4つは、段階2で作られ、main に入っている。Go 版の土台、Java 版と Go 版を比べる検査、版をまたいで確かめる検査、今の Java 版から作った API の仕様書である。API の仕様書には、マスタと経歴書の操作も書かれている
  - 認証のまとまりの Go 版は、main に入っている。認証のまとまりの Go 版には、ログインの要る操作の前にログインの状態を確かめる検査も入っている
  - 置き換えの spec の段階1は、今と同じにできるかが分からない動きを試しに作って確かめる段階である。Claude は、段階1で、マスタと経歴書の操作に当たる動きのうち、次の6つを試しに作らなかった。
    - 日時を日本の時刻で保存すること
    - プロジェクトの技術スタックのような、文字列の並びを1つの列に入れる列の読み書き
    - プロジェクトの項目の保存のように、データベースへの1回の送信で複数の書き込みをする箇所
    - 期間か、取得の年月か、名前が同じ項目どうしを、ID の順に並べること
    - 入力の前後の空白の取り除き方と文字数の数え方
    - 要求の中の ID の読み方
  - 変えた動きの一覧には、ポートフォリオ、SNS、自己PR の項目の並び順の違いが、所有者が受け入れた違いとして載っている。Java 版は、これらの項目を Java の日本語の並べ方で並べる。Go 版は、これらの項目を Go の日本語の並べ方で並べる

## 要件

### 要件1 マスタと経歴書の操作を、今の画面を直さずに Go 版で使えるようにする

切り替えのあとも、利用者は、今の画面で経歴書を作り、直す。Go 版の答えの形が Java 版と少しでも違うと、画面は、経歴書を表示できないか、利用者が入れた値を取り違える。たとえば、画面は、職歴の項目が今も続いているかを `isActive` の名前で送り、`active` の名前で受け取る。Go 版が受け取る名前か返す名前を1つ取り違えるだけで、画面は、続いている職歴を終わった職歴として表示する。そこで、Go 版は、マスタと経歴書の操作に、Java 版と同じ答えを返す。

1. Go 版は、マスタと経歴書の操作の要求に、Java 版と同じ HTTP の状態の番号と、同じ本文で答える。同じかどうかの正解は、今の Java 版が実際に返す答えとする。ただし、ポートフォリオ、SNS、自己PR の項目の並び順は、変えた動きの一覧に所有者が受け入れた違いとして載っているので、Go 版は、これらの項目を Go の日本語の並べ方で並べてよい。また、Go 版は、ほかの利用者の経歴書に項目を足す要求には、Java 版と同じ答えではなく、要件3の受入基準3のとおり、無い経歴書の要求と同じ答えを返す。Go 版は、Java 版がサーバの誤りとして状態の番号 500 で答えている要求には、Java 版と同じ答えではなく、要件4の受入基準4のとおり、要求の誤りか、対象が無いことを示す状態の番号で答える。
2. 利用者は、今の画面で、Go 版を相手に、次の4つを終えられる。
   - 経歴書を新しく作ることと、持っている経歴書をコピーして新しい経歴書を作ること
   - 経歴書の一覧を見ることと、経歴書を削除すること
   - 基本の情報を直すことと、6つの欄の項目を足し、直し、消すこと
   - 資格、SNS、技術スタックを入れるときに、入力の候補を見ること

### 要件2 入力の誤りとして断る条件と、画面に出るエラーの文言を、Java 版と同じにする

利用者が経歴書に誤った値を入れると、画面は、backend が答えに入れたエラーの文言を利用者に見せる。Go 版が Java 版より緩く断ると、Java 版では保存できない経歴書が保存され、そのあとの PDF の出力のような操作が失敗するおそれがある。Go 版が Java 版より厳しく断ると、利用者は、今は保存できる経歴書を保存できなくなる。そこで、Go 版は、入力の誤りとして断る条件とエラーの文言を、Java 版と同じにする。

1. Go 版は、マスタと経歴書の操作で、入力の誤りとして断る条件と、答えに入れるエラーの文言を、Java 版と同じにする。断る条件には、少なくとも次の5種類を含める。
   - 入力欄ごとの、入力が要るかどうか、長さの上限、値の形。値の形とは、年月の書き方や、リンクが https で始まることを指す
   - 経歴書の数の上限と、欄ごとの項目の数の上限。たとえば、Java 版では、1人の利用者が作れる経歴書は50件までである
   - 1人の利用者の中で、経歴書の名前が重ならないこと
   - 経歴書の名前に使えない文字と、姓と名に使える文字
   - 期間の決まり。たとえば、Java 版は、終了の年月が開始の年月より前の期間と、職歴どうしの期間の重なりを断る

### 要件3 ほかの利用者の経歴書を、読めず、変えられないようにする

経歴書には、利用者の氏名と職歴が入っている。Go 版がほかの利用者の経歴書を返すと、利用者の経歴が他人に読まれる。Go 版がほかの利用者の経歴書への変更を受け付けると、利用者の経歴書が他人に書き換えられる。しかも、利用者は、自分の経歴書が読まれたことに画面で気づけない。そこで、Go 版は、利用者が自分の経歴書だけを読み、変えられるようにする。

1. 利用者が、ほかの利用者の経歴書か、その経歴書の項目についての要求を送ったら、Go 版は、その経歴書を返さず、変えない。Go 版は、その要求に、Java 版が無い経歴書の要求に返す答えと同じ答えを返す。要求を送った人が、答えから、その経歴書があるかどうかを見分けられないようにするためである。
2. 利用者が、自分の経歴書と、別の経歴書の項目を組にした要求を送ったら、Go 版は、その項目を変えない。Go 版は、その要求に、Java 版が無い項目の要求に返す答えと同じ答えを返す。
3. ほかの利用者の経歴書に項目を足す要求に、Java 版は、その経歴書のその欄の項目の数が上限に達しているときだけ、上限に達したことを示す答えを返す。上限に達していないときは、Java 版は、無い経歴書の要求と同じ答えを返す。Go 版は、この要求にも、無い経歴書の要求と同じ答えを返す。要求を送った人が、ほかの利用者の経歴書があるかどうかを、上限の答えから見分けられないようにするためである。画面は、ほかの利用者の経歴書に項目を足す要求を送らないので、この違いは利用者の目に触れない。Claude は、この違いを、変えた動きの一覧に載せる。
4. 退会してすでに居ない利用者のログインの状態を持つ要求が届いたら、Go 版は、その要求に Java 版と同じ答えを返す。認証のまとまりの spec が、すでに居ない利用者の要求はログインの状態の検査を通るとし、その要求への答えを、操作を作るまとまりの spec で Java 版と同じにすると決めたためである。Java 版がこの要求にサーバの誤りとして答えるときは、Go 版は、要件4の受入基準4のとおり、要求の誤りか、対象が無いことを示す状態の番号で答える。

### 要件4 Java 版と Go 版を比べる検査で、答えと保存したデータが同じことを確かめる

人はコードを読まないので、Claude は、Go 版が Java 版と同じかを、機械で確かめる。経歴書の操作は、答えのほかに、データベースに経歴書を保存する。答えだけを比べると、Claude は、保存したデータの違いを見落とす。そこで、Claude は、Java 版と Go 版に同じ要求を送り、答えと、データベースに残ったデータの両方を比べる。マスタと経歴書の操作は、メールを送らず、ログインの状態の保存先にも書かないので、Claude は、メールとログインの状態の保存先を比べない。

1. Claude は、マスタと経歴書の操作のすべてについて、Java 版と Go 版を比べる検査の筋書きを書く。筋書きには、画面が送る正しい要求に加えて、次の要求を含める。
   - 入力の誤りとして断る条件の種類ごとに、その条件に当たる要求
   - 経歴書の数が上限に達した利用者が経歴書を作る要求と、項目の数が上限に達した欄に項目を足す要求
   - 経歴書をコピーして新しい経歴書を作る要求
   - 無い経歴書の要求と、無い項目の要求
   - ほかの利用者の経歴書と、その経歴書の項目についての要求
   - 退会してすでに居ない利用者のログインの状態を持つ要求
2. Java 版と Go 版を比べる検査は、答えに加えて、データベースに残ったデータを比べる。
3. Java 版と Go 版を比べる検査は、要求のたびに違う値になるものについては、値が違うことでは PR を止めない。要求のたびに違う値になるものとは、たとえば、経歴書と項目の ID と、経歴書の作成と更新の日時である。Java 版と Go 版を比べる検査は、その値の形が Java 版と同じかを確かめる。また、Java 版と Go 版を比べる検査は、1つの筋書きの中で、Java 版で前の要求の答えと同じ値になる値が、Go 版でも前の要求の答えと同じ値になるかを確かめる。たとえば、Java 版では、利用者が項目を直したあとも、その項目の ID は変わらない。ただし、作成と更新の日時については、Java 版と Go 版を比べる検査は、同じ要求を受けて2つの版がそれぞれ保存した日時の差が、設計で決めた幅の内側にあることも確かめる。Go 版が Java 版と違う時差で日時を保存すると、Go 版で保存した経歴書の日時が、画面の一覧で何時間もずれて見えるためである。Claude は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査で、Java 版を本番と同じく日本の時間帯で動かす。検査の環境の Java 版が本番と違う時間帯で動くと、検査は、本番と違う時刻を正解として Go 版の日時を比べることになるためである。
4. マスタと経歴書の操作には、Java 版がサーバの誤りとして状態の番号 500 で答えている要求がある。たとえば、項目の ID の場所に ID の形でない文字を入れた要求がある。Go 版は、このような要求に、要求の誤りか、対象が無いことを示す状態の番号で答える。Claude は、要求ごとにどちらで答えるかを、設計で決める。画面は、このような要求のうち、退会してすでに居ない利用者の要求でないものを送らない。そのため、これらの要求への Go 版と Java 版の答えの違いは、利用者の目に触れない。退会してすでに居ない利用者の要求では、Java 版の答えでも Go 版の答えでも、その利用者は操作を終えられないので、利用者ができることは変わらない。Claude は、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。
5. 置き換えの spec は、主な操作の応答にかかる時間を Java 版と Go 版で測って比べると決めている。Claude は、マスタと経歴書の操作では、経歴書の一覧の取得、経歴書1件の取得、基本の情報の更新、プロジェクトの項目の更新、技術スタックのマスタの取得の5つを、主な操作として測る。Claude は、測る経歴書の6つの欄のそれぞれに、項目を入れておく。項目の無い経歴書で測ると、利用者が使う経歴書より少ないデータの要求しか測れないためである。

### 要件5 版をまたいでも、経歴書の保存が残り、続けて直せる

切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受けるので、同じ利用者の続けた保存が、別々の版に届くことがある。一方の版が保存した経歴書をもう一方の版が読めないと、利用者は、経歴書を開けないか、保存したはずの内容を失う。そこで、Go 版は、Java 版が保存した経歴書を読み書きでき、Java 版も、Go 版が保存した経歴書を読み書きできるようにする。

1. 利用者は、一方の版で作った経歴書と、一方の版で足した項目を、もう一方の版で読み、直し、消せる。どちらの版に届いた保存も、切り替えのあとに残っている。
2. Java 版は、本番では時間帯を日本に設定したコンテナで動くので、経歴書の作成と更新の日時を、要求を受けた時の日本の時刻として保存する。Go 版は、本番と、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査のどの環境でも、経歴書の作成と更新の日時を、要求を受けた時の日本の時刻として保存する。一方の版が保存した経歴書の作成と更新の日時を、もう一方の版は、同じ時刻として返す。画面は、経歴書の一覧に、経歴書ごとの作成と更新の日時を見せる。2つの版が返す時刻がずれると、利用者は、経歴書の更新の日時が変わったように見える。
3. Claude は、版をまたいで確かめる検査に、経歴書の作成から経歴書の削除までを続けて行う筋書きを足す。この筋書きには、次の3つの段を含める。
   - 一方の版で作った経歴書に一方の版で項目を足し、その項目を、もう一方の版で直し、消す段
   - 一方の版が保存した経歴書を、もう一方の版で読む段
   - 読んだ経歴書の項目の値と、作成と更新の日時が、保存した版の答えの値と同じであることを確かめる段
   版をまたいで確かめる検査は、この筋書きを、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方で動かす。版をまたいで確かめる検査は、前の段の答えから値を取り出し、あとの段の答えの値と比べられる。Claude は、この比べ方で、3つ目の段の、もう一方の版で読んだ経歴書の項目の値と、作成と更新の日時が、保存した版の答えの値と同じであることを確かめる。版をまたいで確かめる検査は CI で動く。この検査が通らない PR は main に入らない。

### 要件6 Java 版と同じにできるかを設計の前に試し、置き換えの spec の進み具合の表に、このまとまりの状態を書く

Claude が、設計を書いたあとや作り終えたあとに、Go 版の動きを Java 版と同じにできないと分かると、所有者は spec を承認し直すことになる。そこで、Claude は、確かめていない動きを設計の前に試し、Java 版と同じにできないと分かったら止まって所有者に報告する。また、所有者は、置き換えがどこまで進んだかを、置き換えの spec の進み具合の表で、機能のまとまりごとに見る。そこで、Claude は、このまとまりの状態を、その表に書く。

1. Claude は、この spec の設計を書く前に、Claude が置き換えの spec でまだ試しに作っていない、マスタと経歴書の操作の動きを試しに作り、Java 版と同じになるかを確かめる。試しに作る動きには、少なくとも次の9つを含める。Claude は、試しに作った方法と結果を、この spec の research.md に書く。
   - 資格と SNS の名前の一覧の並び。Java 版は、この2つの一覧を返すときに並べ方を指定していない
   - 経歴書の作成と更新の日時の、保存の仕方と読み方。Java 版は、この日時を、時差を持たない日時として作る
   - 入力の前後の空白の取り除き方と、長さの上限を確かめるときの文字の数え方。たとえば、絵文字のような文字を何文字と数えるかである
   - リンクが https の形かどうかの判定
   - 年月と日付の書き方の読み方。たとえば、`2024-1` のような書き方を受け付けるかどうかである
   - プロジェクトの技術スタックの保存の仕方と読み方。Java 版は、技術スタックの種類ごとに、名前の並びを1つの列に入れて保存する
   - プロジェクトの項目の保存。Java 版は、プロジェクトの項目と、その項目の技術スタックを、データベースへの1回の送信で保存する
   - 期間か、取得の年月か、名前が同じ項目どうしの並び。Java 版は、6つの欄の項目を、期間か、取得の年月か、名前で並べ、それが同じ項目どうしを ID の順に並べる
   - 要求の中の経歴書と項目の ID の読み方。たとえば、大文字で書いた ID を受け付けるかどうかである
2. 試しに作った結果、Java 版と同じにできない動きが見つかったら、Claude は、設計を書く前に止まる。Claude は、何が同じにならないかと、その違いが利用者に何をもたらすかを、所有者に報告する。
3. Claude は、置き換えの spec の進み具合の表の、マスタと経歴書のまとまりの行に、この spec の場所と、まとまりの状態を書く。Claude は、状態を、作り終えたら「作り終えた」にし、Java 版と Go 版を比べる検査に通ったら「比べる検査に通った」にする。
