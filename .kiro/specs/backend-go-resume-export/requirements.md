## はじめに

Issue #445 で、所有者は、backend を Java と Spring Boot から Go に置き換えると決めた。置き換えの進め方と、Go 版が守ることは、spec `backend-go-replacement` が決めている。この spec では、spec `backend-go-replacement` を「置き換えの spec」と呼ぶ。置き換えの spec は、機能のまとまりごとの Go 版を、まとまりごとの別の spec で作ると決めた。この spec は、そのうち出力のまとまりを受け持つ。Claude は、この spec で、Issue #773 の「やりたいこと」に挙げた2つの操作の Go 版を作る。この spec では、この2つの操作を「出力の操作」と呼ぶ。今の Go 版は、出力の操作の要求に、未実装であることを示す答えを返す。

出力の操作は、利用者の経歴書を、PDF か Markdown のファイルにして返す。2つの操作は、次のように違う。

- 設定を付けない出力: GET の操作である。要求を送る側は、要求の Accept のヘッダで、PDF か Markdown かを選ぶ。Java 版は、PDF を既定のフォントと文字の大きさと表の見出しの色で作り、ファイルを保存させる答えを返す。画面は、利用者が経歴書を Markdown で保存するときに、この操作を使う。画面は、この操作で PDF を求める要求を送らない
- 設定を付けた出力: POST の操作である。要求を送る側は、要求の本文で、出力の形式と、出し方と、PDF の設定を選ぶ。出し方は、ファイルを画面に表示させる「inline」と、ファイルを保存させる「attachment」の2つである。PDF の設定は、フォントと、タイトル、日付、氏名、見出しの4つの文字の大きさと、表の見出しの色である。画面は、PDF のプレビューを見せるときと、プレビューで選んだ設定で PDF を保存するときに、この操作を使う

この spec の「所有者」「Java 版」「Go 版」「利用者」「画面」「切り替え」は、置き換えの spec と同じものを指す。「筋書き」は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査が、版に送る要求の並びと、期待する答えを書いたものを指す。「出力の前提」は、Java 版が経歴書を出力する前に確かめる、経歴書に入っていなければならないものを指す。出力の前提は、経歴書の名前、日付、姓、名と、職歴、プロジェクト、自己PR のそれぞれ1件以上の項目である。「項目」は、経歴書の1つの欄に入れた1件の記録を指す。

Issue #773 の「どうなれば解決か」は、出力の操作について、置き換えの spec の20の受入基準を満たすことを求めている。置き換えの spec は、まとまりごとの spec に置き換えの spec の要件を書き写さず、当てはまる要件を指すと決めている。そこで、この spec は、20の受入基準のそれぞれを、次の表のとおりに受け持つ。表で「置き換えの spec のとおり」とした受入基準は、出力の操作に固有の決めごとが無い。Claude は、その受入基準を、置き換えの spec の文のとおりに出力の操作に当てはめる。

## 範囲

- この spec で決めること: この spec では、次の4つを決める。
  - 出力の操作の Go 版。Go 版が PDF と Markdown を作るときに使う、文書の元の形(テンプレート)も含む
  - ほかの利用者の経歴書の出力の要求と、退会してすでに居ない利用者の要求に、Go 版が返す答え
  - 出力の操作について、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査に足す筋書き
  - PDF を比べる部品が、Java 版の PDF と Go 版の PDF を比べる方法。置き換えの spec の設計が決めた比べ方では、PDF を比べる部品は、要件2の受入基準4で所有者が受け入れた違いのために、どの PDF も違うと判定する。そこで、Claude は、この spec の設計で比べ方を決め直す
- この spec で決めないこと: この spec では、次の4つを決めない。
  - ほかのまとまりの操作の Go 版。たとえば、Claude は、経歴書のバックアップと戻しの Go 版を、バックアップのまとまりの spec で作る
  - ログインの状態の検査。Claude は、認証のまとまりの spec `backend-go-auth` で作った検査を、作り直さずにそのまま使う
  - 機能を足すことと、仕様を変えること。Issue #445 の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである
  - 本番の切り替え。本番の切り替えは、置き換えの spec が受け持つ
- この spec が前提にしていること: この spec は、次の5つを前提にする。
  - 置き換えの spec の段階2で、次の6つが作られ、main に入っている。
    - Go 版の土台
    - Java 版と Go 版を比べる検査と、版をまたいで確かめる検査
    - 今の Java 版から作った API の仕様書。API の仕様書には、出力の操作も書かれている
    - HTML から A4 の PDF を作る Go 版の部品。この部品は、起動したまま持つ Chromium で PDF を作る
    - PDF を比べる部品。この部品は、頁の数、フォント、文字の大きさ、表の色、頁ごとの文字、文字の位置を比べる
    - 比べる経歴書のデータ。データには、項目が空の経歴書、職歴とプロジェクトが多く3頁以上になる経歴書、長い文と改行を含む経歴書、2つのフォントのそれぞれを選ぶ要求の本文、4つの文字の大きさと表の見出しの色を既定と違う値にした要求の本文がある
  - 認証のまとまりと、マスタと経歴書のまとまりの Go 版は、main に入っている。マスタと経歴書のまとまりの Go 版は、経歴書と6つの欄の項目を読み書きする
  - 置き換えの spec の段階1で、Claude は、Java 版が PDF を作ったときと同じデータを Java 版のテンプレートに入れた HTML を Chromium で PDF にし、Java 版の PDF と比べた。頁の数と改頁の位置は同じになり、文字の位置は1〜2pt ずれた。置き換えの spec の research.md は、実際の経歴書で Go 版が作る PDF と Java 版の PDF の違いが、PDF を比べる部品の許す違いの大きさに収まるかを、出力のまとまりの、Java 版と Go 版を比べる検査で初めて確かめると書いている
  - Claude は、置き換えの spec の段階1で、出力の操作に当たる動きのうち、次の4つを Go で試しに作らなかった。Markdown の本文と、答えの Content-Disposition のヘッダのファイル名は、Java 版の動きだけを確かめた。
    - PDF の設定の値の直し方
    - PDF の本文の中で、利用者が書いた文字を HTML として読まれない形に書き換えること
    - Markdown の本文を作ること
    - 答えの Content-Disposition のヘッダのファイル名を作ること
  - 変えた動きの一覧には、出力に関わる次の3つの違いが、所有者が受け入れた違いとして載っている。
    - 経歴書の中の項目を名前で並べる順。Go 版は、経歴書の中の項目を、Go の標準の日本語の並び順で並べる
    - 入力の足りない経歴書の出力。Go 版は、要求の Accept のヘッダによらず、状態の番号 400 と、足りない項目の一覧を返す
    - PDF の文字の位置と、PDF から写したときの「〜」。Go 版の PDF では、文字の位置が 1〜2pt ずれる。Go 版の PDF から「〜」を写すと、写した文字は「〜」(U+301C)のままになる

## 要件

### 要件1 出力の操作を、今の画面を直さずに Go 版で使えるようにする

切り替えのあとも、利用者は、今の画面で経歴書を PDF と Markdown で出力し、応募先に渡す。画面は、保存するファイルの名前を、答えの Content-Disposition のヘッダから取る。また、画面は、答えの PDF をプレビューの枠に表示する。Go 版の答えの状態の番号かヘッダが Java 版と違うと、画面は、ファイルを保存できないか、違う名前で保存するか、プレビューを表示できない。そこで、Go 版は、出力の操作で画面が送る要求に、Java 版と同じ答えを返す。一方、画面が送らない要求の扱いまで Java 版に合わせると、Go 版は、Java の部品の中の Accept のヘッダの見分け方のような動きを写すことになる。Go 版がその動きを写しても、利用者が得るものは無い。Go 版が Java 版と違う答えを返してよい要求は、受入基準1の原則への3つの例外を決めた受入基準2に当たる要求である。Go 版は、その要求を Go の普通の扱い方で扱う。

1. Go 版は、出力の操作の次の4種類の要求に、Java 版と同じ HTTP の状態の番号と、同じ Content-Type と Content-Disposition のヘッダで答える。答えの本文が同じかどうかは、PDF と Markdown の見た目を決める要件2と、断る条件とエラーの文言を決める要件3が決める。同じかどうかの正解は、今の Java 版が実際に返す答えとする。4種類のうち、初めの3種類は、画面が送る要求である。
   - 設定を付けない出力で、Accept のヘッダを `text/markdown, application/json` にした要求
   - 設定を付けた出力で、Accept のヘッダを `application/pdf, application/json` にし、本文の形式を `pdf`、出し方を `inline` にした要求
   - 設定を付けた出力で、Accept のヘッダを `application/pdf, application/json` にし、本文の形式を `pdf`、出し方を `attachment` にした要求
   - 設定を付けない出力で、Accept のヘッダを `application/pdf, application/json` にした要求。画面はこの要求を送らない。しかし、API の仕様書は、設定を付けない出力が、Accept に `application/pdf` を含む要求に既定の設定の PDF を返すと書いている。Go 版がこの要求に Java 版と違う答えを返すと、Issue #445 で所有者が変えないと決めた仕様が変わる。そこで、Go 版は、この要求にも Java 版と同じ答えを返す

   設定を付けた出力の2種類の要求では、PDF の設定の値は、要件3の受入基準1の断る条件に当たらない値のどれでもよい。画面は、4つの文字の大きさを 0.5 刻みに直し、表の見出しの色を小文字の6桁の16進数で送る。Go 版は、画面が送らない値、たとえば 0.5 刻みでない文字の大きさや、大文字の16進数や赤と緑と青の値で書いた色を受け取ったときも、Java 版と同じに値を直して PDF を作る。
2. 4種類の要求に、Java 版と同じ状態の番号とヘッダで答えるという受入基準1の原則には、次の3つの例外がある。
   - 受入基準1の4種類の要求のほかの要求には、Go 版は、Java 版と違う答えを返してよい。そのような要求は、たとえば、設定を付けた出力で形式を `markdown` にした要求、Accept のヘッダに `application/pdf` も `text/markdown` も無い要求、Accept のヘッダに `application/json` の無い要求、経歴書の ID の場所に ID の形でない文字を入れた要求である。ただし、Accept のヘッダに `application/json` を含み、本文が要件3の受入基準1の断る条件に当たる要求には、Go 版は、要件3のとおり Java 版と同じに断る。Accept のヘッダに `application/json` の無い要求には、本文が断る条件に当たるときも、Go 版は、断る答えの形を Java 版と違うものにしてよい。画面は、どの要求でも、Accept のヘッダに `application/json` を付けて送るためである。Claude は、Java 版と答えが変わる要求を、変えた動きの一覧に載せる
   - 出力の前提を満たさない経歴書の出力の要求のうち、本文が要件3の受入基準1の断る条件に当たらない要求には、Go 版は、変えた動きの一覧のとおり、Accept のヘッダによらず、状態の番号 400 と、足りない項目の一覧で答える
   - Java 版がサーバの誤りとして状態の番号 500 で答える要求には、Go 版は、Java 版と同じ答えではなく、要件5の受入基準3のとおり、要求の誤りか、対象が無いことを示す状態の番号で答える
3. 利用者は、今の画面で、Go 版を相手に、次の3つを終えられる。
   - PDF のプレビューを見ること
   - プレビューで選んだ設定で、PDF を保存すること
   - Markdown を保存すること

### 要件2 Go 版が作る PDF と Markdown を、Java 版と同じ見た目にする

利用者は、出力した PDF と Markdown を応募先に渡す。出力の見た目が変わると、利用者は、置き換えのあとに出力した書類を確かめ直さなければならない。置き換えの spec の要件10は、Go 版の PDF と Markdown を Java 版と同じ見た目にすると決め、同じとみなす範囲を決めた。この spec は、その範囲を、出力の操作の答えの本文に当てはめる。ただし、Claude が設計の前に試しに作ったところ、Go 版の PDF には、Java 版と同じにできない3つの違いが見つかった。所有者は、2026-11-23 に、この3つの違いを受け入れ、Go 版を Java 版に無理に合わせないと決めた。この3つの違いは、受入基準4が決める。

1. Go 版は、要件1の受入基準1の、Java 版と同じに答える4種類の要求に答えて作る PDF を、Java 版が同じ要求に答えて作る PDF と同じ見た目にする。同じ見た目とみなす範囲は、置き換えの spec の要件10の受入基準1が決めた、PDF の見た目を同じとみなす範囲とする。ただし、Go 版の PDF は、受入基準4の、頁の大きさと、PDF から写した字と、長い文の折り返しの3つの点で、Java 版の PDF と違ってよい。設定を付けた出力では、利用者が選んだフォントと、4つの文字の大きさと、表の見出しの色が、Java 版と同じく PDF に出る。設定を付けない出力では、Go 版は、Java 版と同じ既定の設定で PDF を作る。既定の設定は、フォントが Noto Sans JP、タイトルの文字の大きさが 16、日付が 10、氏名が 10、見出しが 11.5、表の見出しの色が `#d9d9d9` である。
2. Go 版は、要件1の受入基準1の、Java 版と同じに答える4種類の要求に答えて作る Markdown を、置き換えの spec の要件10の受入基準2のとおり、Java 版が同じ要求に答えて作る Markdown と1文字も違わないものにする。利用者が経歴書に `<` `>` `&` `"` `'` の文字を書いたときも、Go 版は、その文字を、Java 版と同じ形に書き換えて Markdown に出す。
3. Go 版は、答えの Content-Disposition のヘッダのファイル名を、Java 版と同じ規則で、経歴書の名前から作る。経歴書の名前が日本語のときも、ヘッダの文字は Java 版と同じになる。画面は、このファイル名で、利用者のパソコンにファイルを保存する。
4. Go 版の PDF は、次の3つの点で Java 版の PDF と違ってよい。Go 版は、PDF を Chromium で作るので、この3つの点を Java 版と同じにできない。Claude は、この3つの違いを、所有者が受け入れた違いとして、変えた動きの一覧に載せる。
   - 頁の大きさ: Java 版の用紙は、幅 595.275pt、高さ 841.875pt である。Go 版の用紙は、幅 594.96pt、高さ 841.92pt になる。Chromium は、頁の大きさを 0.96pt 刻みでしか作れないためである。違いは幅で 0.315pt、高さで 0.045pt なので、利用者は、印刷しても画面で見ても違いに気づかない
   - PDF から写した字: Java 版の PDF から字を写すと、「年」「理」「行」「力」などの漢字が、見た目の同じ、番号の違う字(CJK 互換漢字)になり、「-」が、行の終わりで改行させないハイフンの字である U+2011 になる。Go 版の PDF から字を写すと、利用者が経歴書に書いたとおりの字になる。利用者が PDF から写した字で検索するときは、Go 版の字のほうが見つかる
   - 長い文の折り返し: Go 版の字の幅は Java 版よりわずかに狭く、36字で 0.24pt 狭い。そのため、長い文では、Go 版の行に、Java 版より1字か1語多く入ることがある。Go 版の字の幅は Chromium が決めるので、Claude は、折り返しを Java 版に合わせられない。Claude は、所有者が受け入れた折り返しの違いに、折り返しの違いから起きる次の4つの動きを含める。所有者が、Go 版を Java 版に無理に合わせないと決めたためである。
     - 同じ段落の、多く入った行より後ろの字が、前の行に移る
     - 段落の行の数が、Java 版より少なくなることがある
     - 段落の行の数が少なくなると、同じ項目の、その段落より後ろの部分と、その項目より下の項目が、上に上がる。上がる幅は、減った行の高さまでである。表の行の高さがほかの欄で決まるときは、上がらないこともある
     - 項目が上に上がると、改頁の位置が変わり、頁の数が減ることがある

### 要件3 断る条件と、画面に出るエラーの文言を、Java 版と同じにする

出力に失敗すると、画面は、backend が答えに入れたエラーの文言を利用者に見せる。とくに、出力の前提を満たさない経歴書では、利用者は、エラーの文言を読んで、経歴書に何を足せばよいかを知る。Go 版の文言が Java 版と違うと、利用者は、何を足せばよいかを今と同じように読み取れない。Go 版が Java 版より緩く断ると、Java 版では出力できない経歴書の PDF ができる。Go 版が Java 版より厳しく断ると、利用者は、今は出力できる経歴書を出力できなくなる。そこで、Go 版は、断る条件とエラーの文言を、Java 版と同じにする。

1. Go 版は、設定を付けた出力の要求の本文で、入力の誤りとして断る条件と、答えに入れるエラーの文言を、Java 版と同じにする。断る条件には、少なくとも、次の5種類の決まりのどれかを本文が満たさないことを含める。
   - 形式と出し方が入力されていることと、選べる値であること
   - 形式が `pdf` のときに、PDF の設定が入力されていること
   - フォントが入力されていることと、選べる値であること
   - 4つの文字の大きさが入力されていることと、6以上72以下であること
   - 表の見出しの色が入力されていることと、6桁の16進数か、0以上255以下の赤と緑と青の値の、どちらか一方だけで書かれていること

   画面は、この5種類の断る条件に当たる要求を送らない。それでも、Go 版は、Accept のヘッダに `application/json` を含む要求では、この5種類の条件で、Java 版と同じに断る。置き換えの spec の要件9の受入基準2が、エラーの文言と断る条件を Java 版と同じにすると決めたためである。
2. 利用者が、自分の経歴書のうち、出力の前提を満たさない経歴書の出力の要求を送ったら、Go 版は、出力せず、Java 版と同じエラーの文言で答える。その文言は、出し方が `inline` のときは「入力エラーがあるため、PDFプレビューを表示できません。」で始まり、それ以外のときは「職務経歴書をエクスポートできません。」で始まる。その文言では、始まりの文のあとに、足りないものごとの文言が、Java 版と同じ順に続く。状態の番号は、要件1の受入基準2のとおり、Accept のヘッダによらず 400 とする。
3. 利用者が、無い経歴書の出力の要求を送ったら、Go 版は、Java 版と同じく、状態の番号 404 と「対象の職務経歴書データが存在しません。」の文言で答える。
4. Go 版は、Java 版と同じく、設定を付けた出力の要求の本文を受入基準1の断る条件で確かめてから、経歴書があるかと、経歴書の持ち主と、出力の前提を確かめる。そのため、本文が断る条件に当たる要求には、Go 版は、Accept のヘッダによらず、経歴書が無いときも、ほかの利用者の経歴書のときも、出力の前提を満たさない経歴書のときも、本文の誤りとして断る。Go 版は、その答えに、足りない項目の一覧を入れない。Accept のヘッダに `application/json` を含む要求では、Go 版は、断る答えを、受入基準1のとおり Java 版と同じにする。本文が断る条件に当たらない要求にだけ、Go 版は、出力の前提を満たさない経歴書への答えを決めた受入基準2と、無い経歴書への答えを決めた受入基準3と、ほかの利用者の経歴書と退会してすでに居ない利用者の要求への答えを決めた要件4のとおりに答える。

### 要件4 ほかの利用者の経歴書を、出力できないようにする

経歴書には、利用者の氏名と職歴が入っている。Go 版がほかの利用者の経歴書を出力すると、利用者の経歴が他人に読まれる。また、Go 版がほかの利用者の経歴書について、出力の前提の足りないものを答えると、要求を送った人は、その経歴書があることと、その中身の一部を知る。利用者は、自分の経歴書が読まれたことに、画面で気づけない。そこで、Go 版は、利用者が自分の経歴書だけを出力できるようにする。

1. 利用者が、ほかの利用者の経歴書の出力の要求を送ったら、Go 版は、その経歴書を出力せず、Java 版が無い経歴書の要求に返す答えと同じ答えを返す。その経歴書が出力の前提を満たさないときも、Go 版は、足りないものの一覧を返さず、無い経歴書の要求と同じ答えを返す。要求を送った人が、答えから、その経歴書があるかどうかと、その中身を見分けられないようにするためである。
2. 退会してすでに居ない利用者のログインの状態を持つ要求が届いたら、Go 版は、その要求に Java 版と同じ答えを返す。認証のまとまりの spec が、すでに居ない利用者の要求はログインの状態の検査を通るとし、その要求への答えを、操作を作るまとまりの spec で Java 版と同じにすると決めたためである。Java 版がこの要求にサーバの誤りとして答えるときは、Go 版は、要件5の受入基準3のとおり、要求の誤りか、対象が無いことを示す状態の番号で答える。

### 要件5 Java 版と Go 版を比べる検査で、出力の答えが同じことを確かめる

Claude は、Go 版の出力が Java 版と同じかを、機械で確かめる。出力の操作は、経歴書のデータによって、頁の数、改頁の位置、表の幅が変わる。Go 版と Java 版の出力が、1つのデータで同じでも、ほかのデータで違うことがある。そこで、Claude は、置き換えの spec の要件10の受入基準3が求めるいろいろなデータで、Java 版と Go 版に同じ要求を送り、答えを比べる。

1. Claude は、出力の操作について、Java 版と Go 版を比べる検査の筋書きを書く。筋書きには、次の要求を含める。
   - Java 版と同じに答える、要件1の受入基準1の4種類の要求を、次の経歴書と要求の本文で送る要求
     - 出力の前提を満たし、資格、ポートフォリオ、SNS の欄と、プロジェクトの任意の欄が空の経歴書。置き換えの spec の段階2で置いた「項目が空の経歴書」のデータは、氏名と職歴、プロジェクト、自己PR の項目を持たないので、出力の前提を満たさない。そこで、Claude は、置き換えの spec の要件10の受入基準3の「項目が空の経歴書」を、出力の前提を満たす中で項目が最も少ない経歴書として比べる
     - 職歴とプロジェクトが多く、3頁以上になる経歴書
     - 長い文と改行を含む経歴書
     - 経歴書の名前が日本語の経歴書
     - 利用者が経歴書に `<` `>` `&` `"` `'` の文字を書いた経歴書
   - 設定を付けた出力で、2つのフォントのそれぞれを選んだ要求と、4つの文字の大きさと表の見出しの色を既定と違う値にした要求。Claude は、4つの文字の大きさに、既定の値から 0.5 だけ違う値を入れる。あわせて、Claude は、画面が送らない値として、0.5 刻みでない文字の大きさと、大文字の16進数で書いた色と、赤と緑と青の値で書いた色を入れた要求も筋書きに含める
   - 要件3の受入基準1の断る条件の種類ごとに、その条件に当たる要求。Claude は、そのうち1つを、無い経歴書に送る要求にする
   - 出力の前提を満たさない経歴書の出力の要求。Claude は、この要求に、設定を付けない出力の PDF と Markdown の要求と、設定を付けた出力の `inline` と `attachment` の要求を含める
   - 無い経歴書の要求
   - ほかの利用者の経歴書の要求。Claude は、この要求に、その経歴書が出力の前提を満たす場合と、満たさない場合の両方を含める
   - 退会してすでに居ない利用者のログインの状態を持つ要求
2. Java 版と Go 版を比べる検査は、状態の番号と、Content-Type と Content-Disposition のヘッダと、答えの本文を比べる。Java 版と Go 版を比べる検査は、PDF の本文を、受入基準5で決め直した PDF の比べ方で比べ、Markdown とエラーの本文を、Java 版の答えと比べる。また、Java 版と Go 版を比べる検査は、出力のあとにデータベースに残ったデータも比べる。Go 版が出力の途中で経歴書を書き換えると、利用者の経歴書が変わるためである。
3. Java 版が出力の操作のある要求にサーバの誤りとして状態の番号 500 で答えることが分かったら、Go 版は、その要求に、要求の誤りか、対象が無いことを示す状態の番号で答える。Claude は、要求ごとにどちらで答えるかを、設計で決める。Claude は、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。画面は、正しく作った経歴書の出力で、このような要求を送らない。ただし、退会してすでに居ない利用者の要求は、この限りでない。退会してすでに居ない利用者の要求では、Java 版の答えでも Go 版の答えでも、その利用者は出力を終えられないので、利用者ができることは変わらない。
4. 置き換えの spec は、主な操作の応答にかかる時間を Java 版と Go 版で測って比べると決めた。置き換えの spec の設計は、PDF の出力と Markdown の出力を、測る操作に含めた。Claude は、出力の操作では、設定を付けた出力で PDF を作る要求と、設定を付けない出力で Markdown を作る要求の、応答にかかる時間を測る。Claude は、測る経歴書の6つの欄のそれぞれに項目を入れ、PDF が複数の頁になる経歴書にする。項目の少ない経歴書で測ると、利用者が出力する経歴書より軽い要求しか測れないためである。Claude は、PDF の出力では、置き換えの spec の設計のとおり、同時に2件を送ったときのメモリの最大も測る。
5. Claude は、PDF を比べる部品を直し、Java 版の PDF と Go 版の PDF を比べられるようにする。置き換えの spec の設計が決めた比べ方は、頁の大きさの違いを許さず、PDF から写した字をそのまま比べる。また、その比べ方では、PDF を比べる部品は、PDF から字を写す道具が語と行を区切った単位で、字を組にする。PDF を比べる部品は、頁の画像の、同じ色の画素がつながった広がりを箱として、表の見出しと罫線の色を取る。Claude が試しに作ったところ、2つの版では、同じ見た目の PDF でも、語と行の区切りと罫線の描き方が違った。そのため、その比べ方では、PDF を比べる部品は、どの PDF も違うと判定した。直した部品は、次の3つを満たす。Claude は、どう比べるかと許す違いの大きさを、この spec の設計で決める。
   - 直した部品は、要件2の受入基準4の、頁の大きさと、PDF から写した字と、長い文の折り返しの3つの違いと、語と行の区切りと罫線の描き方の違いを、違いと判定しない
   - 直した部品は、要件2の受入基準4の、頁の大きさと、PDF から写した字と、長い文の折り返しの3つの違いのほかに、置き換えの spec の要件10の受入基準1が同じでなければならないとした、頁の数、フォント、文字の大きさ、表の色、改頁の位置、頁ごとの文字、文字の位置のどれかが違えば、違いと判定する。直した部品は、文字の位置が 2pt を超えてずれれば、違いと判定する
   - ただし、直した部品は、要件2の受入基準4の長い文の折り返しの4つの動きから起きた、頁の数と改頁の位置と頁ごとの文字と文字の位置の違いを、違いと判定しない。そのときも、直した部品は、経歴書の全体の字の並びと、それぞれの字のフォントと文字の大きさと色のどれかが違えば、違いと判定する。全体の字の並びが違うときは、利用者が経歴書に書いた字が抜けたか増えたので、折り返しの違いから起きた違いではないためである

### 要件6 版をまたいでも、保存した経歴書を出力できる

切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受けるので、利用者が一方の版で保存した経歴書の出力の要求が、もう一方の版に届くことがある。もう一方の版がその経歴書を出力できないと、利用者は、保存したはずの内容を応募先に渡せない。そこで、Claude は、一方の版が保存した経歴書を、もう一方の版が出力できることを確かめる。

1. 利用者は、一方の版で作り、一方の版で項目を足した経歴書を、もう一方の版で PDF と Markdown で出力できる。出力には、保存した版で入れた項目の値が出る。出力の操作は経歴書を書き換えないので、出力のあとも、どちらの版に届いた保存も残っている。
2. Claude は、版をまたいで確かめる検査に、一方の版で経歴書を作って出力の前提を満たす項目を足し、もう一方の版でその経歴書を PDF と Markdown で出力する筋書きを足す。版をまたいで確かめる検査は、この筋書きを、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方で動かす。版をまたいで確かめる検査は、PDF と Markdown の出力が成功することと、Markdown の本文に、保存した版で入れた項目の値が出ていることを確かめる。版をまたいで確かめる検査は CI で動く。この検査が通らない PR は main に入らない。

### 要件7 Java 版と同じにできるかを設計の前に試し、置き換えの spec の進み具合の表に、このまとまりの状態を書く

Claude が、設計を書いたあとや作り終えたあとに、Go 版の出力を Java 版と同じにできないと分かると、所有者は spec を承認し直すことになる。そこで、Claude は、確かめていない動きを設計の前に試し、Java 版と同じにできないと分かったら止まって所有者に報告する。また、所有者は、置き換えがどこまで進んだかを、置き換えの spec の進み具合の表で、機能のまとまりごとに見る。そこで、Claude は、このまとまりの状態を、その表に書く。

1. Claude は、この spec の設計を書く前に、Claude が置き換えの spec でまだ試しに作っていない、出力の操作の動きを試しに作り、Java 版と同じになるかを確かめる。試しに作る動きには、少なくとも次の6つを含める。Claude は、試しに作った方法と結果を、この spec の research.md に書く。
   - Java 版と Go 版を比べる検査の筋書きに入れる、要件5の受入基準1の経歴書のデータでの PDF の見た目。Claude は、Go 版で作った PDF と Java 版の PDF を PDF を比べる部品で比べ、2つの PDF の違いが、置き換えの spec の設計が決めた許す違いの大きさに収まるかを確かめる
   - PDF の本文の中で、利用者が書いた `<` `>` `&` `"` `'` の文字と改行が、Java 版の PDF と同じ文字で出ること
   - Markdown の本文。Claude は、Go 版で作った Markdown が、Java 版の Markdown と1文字も違わないかを確かめる
   - 答えの Content-Disposition のヘッダのファイル名。Claude は、経歴書の名前が日本語のときも、Go 版のヘッダが Java 版のヘッダと同じになるかを確かめる
   - PDF の設定の値の直し方。Java 版は、4つの文字の大きさを 0.5 刻みに丸め、表の見出しの色を小文字の16進数の形に直してから PDF を作る
   - PDF を同時に2件作ったときのメモリの最大
2. 試しに作った結果、Java 版と同じにできない動きが見つかったら、Claude は、設計を書く前に止まる。Claude は、何が同じにならないかと、その違いが利用者に何をもたらすかを、所有者に報告する。
3. Claude は、置き換えの spec の進み具合の表の、出力のまとまりの行に、この spec の場所と、まとまりの状態を書く。Claude は、状態を、作り終えたら「作り終えた」にし、Java 版と Go 版を比べる検査に通ったら「比べる検査に通った」にする。
