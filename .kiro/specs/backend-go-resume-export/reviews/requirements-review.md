### 申告

**1. 置き換えの spec の「項目が空の経歴書」を、出力の前提を満たす中で項目が最も少ない経歴書として比べる** — 要件5の受入基準1の1つ目の箇条の1つ目

- Issue の記載: あり。Issue #773 は、置き換えの spec の要件10の受入基準3を満たすことを求めている。その受入基準は、比べるデータに「項目が空の経歴書」を含めると書いている(どれもAIの提案を了承)
- 決めたこと: 段階2で置いた `empty.sql` は出力の前提を満たさず、PDF も Markdown もできないので、資格、ポートフォリオ、SNS とプロジェクトの任意の欄を空にした経歴書を新しく置いて、その PDF と Markdown を比べる。`empty.sql` の経歴書は、出力の前提を満たさない要求として比べる
- 他にありえた選択肢: `empty.sql` の経歴書の、出力の前提を満たさない答え(400 と一覧)を比べるだけで、項目が空の経歴書を比べたとする。または、出力の前提を満たすいちばん小さい経歴書(職歴、プロジェクト、自己PR が1件ずつ)に加えて、空にできる欄をすべて空にした経歴書を足す
- 外れていた場合: 置き換えの spec が考えていた「空の欄の出し方」(空の欄の見出しを出すか、表を出さないか)が比べられず、空の欄のある経歴書で、Go 版の PDF と Markdown の形が Java 版と違っても、比べる検査が止めない

**2. 応答の時間は、設定を付けた出力の PDF と、設定を付けない出力の Markdown だけを測る** — 要件5の受入基準4

- Issue の記載: あり。置き換えの spec の要件9の受入基準7(主な操作の応答の時間を比べる)を満たすことを求めている(AIの提案を了承)
- 決めたこと: 測る操作を、画面がふだん使う2つの要求に絞る。測る経歴書は、6つの欄のすべてに項目があり、PDF が複数の頁になるものにする
- 他にありえた選択肢: プレビューの `inline` の要求を別に測る(画面は設定を変えるたびに 500ms の待ちのあとで送り直すので、いちばん多く送られる)。3頁以上の経歴書(`many-pages.sql`)で測る
- 外れていた場合: 頁の多い経歴書や、プレビューを続けて送り直したときだけ遅くなる Go 版の作りを、切り替えの前に見つけられない
