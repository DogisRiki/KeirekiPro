## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えたファイルを使うテストが、すべて成功している。`1.` や `2.` の見出しのタスクを大きなまとまりと呼ぶ。大きなまとまりの最後のタスクでは、加えて、そのまとまりのタスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめる。Claude は、新しいテスト1件につき1か所だけを、作業フォルダの外の写しで壊し、そのテストだけを流す。壊した写しの作り方と流し方は、`.kiro/steering/tech.md` の「テストの完全性」に従う。

## 実装のメモ

- 2.1: `memory-files.pl` の `memory_dir` は `$HOME` をそのまま使うので、Git Bash では `/c/Users/...` の形で出る。点検のスキルの手順で、この値を Read などの道具にそのまま渡さない
- 2.1: `list` は、リンクの名前をそのまま `-e "<メモリのディレクトリ>/<名前>"` で確かめ、ファイルがあればそのリンクを `dangling` に出さない。2.2 の `prune-index` も同じ判定にそろえる
- 2.3: `JSON::PP` は1秒におよそ1MBしか JSON を読めない。会話の記録を読む処理は、行のバイトの列を `index` で絞ってから JSON として読む。道具の結果の行まで読むと、約1GBの記録で名前を4つ渡した `origins` が1分43秒かかった。道具の結果の行を飛ばすと7.4秒で終わった
- 2.3: テストの一時のディレクトリは、Git Bash の `pwd` では `/tmp/…` の形で返る。`/c/…` の形の場所が要るテストは、`pwd -W` の `C:/…` の形から作る
- 3: テストで偽のコマンドの場所を PATH に入れるときは、`C:/…` の形でなく `pwd` の形にする。PATH の中の場所は `:` で区切られる。そのため、`C:/…` の形の場所は2つに割れ、偽のコマンドが見つからない
- 8.1: テストで改行の形を替えて目次を書くときは、`printf` の書式に変数を入れない。shellcheck が指摘するので、`$'\r\n'` の値を `printf '%s'` の引数の中に入れる
- 全体の確認: 設計の「手順1 前の点検の片付け」には、`schedule` が `removed` で `state` が `failed` のときに「前の点検の予定を外した。」を示す決まりが無く、要件6の受入基準3に届かなかった。また、設計の「手順8 確かめて消し、結果を示す」には、`delete` の結果の `error` の示し方が無く、`error` で `delete` が 1 で終わると、同じ呼び出しで消したメモリファイルを示さずに点検が止まった。Claude は、2026-11-03 の `/kiro-validate-impl` のあとに、点検のスキルの手順にこの2つの決まりを足した。設計の本文は直していない。どちらも、状態の場所かメモリファイルを消せなかったときだけに起きるためである
