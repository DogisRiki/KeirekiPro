# 調べた結果と設計の判断

## 要約

- 対象の spec: `claude-memory-one-by-one-inspection`
- 調べ方: 既存の仕組みの作り直し(Extension)。軽い調べ方(`design-discovery-light.md`)で進めた
- 分かったことのうち、設計を決めたもの:
  - 前の点検は、`.claude/scripts/memory/` の7つのファイル(約6,600行。テストを含む)と、スキル2つと、`.claude/settings.json` の会話の始めのフックでできている。新しい点検は、点検の中の Claude を別のプロセスで呼ばず、会話の中の Claude が点検する。そのため、前の点検のファイルの大半が要らなくなる
  - 前の点検の予定は、OS ごとに名前が決まっている。予定は、本体の作業フォルダの `.claude/scripts/memory/memory-inspect.sh run` を動かす。本体の作業フォルダからこのファイルが無くなれば、残った予定はメモリに触れずに終わる
  - 会話の記録(`~/.claude/projects/<名前>/*.jsonl`)は、この PC では30日ほどで消えている。いまあるメモリファイルの多くは、書いた会話の記録が残っていない

## 調べたこと

### 前の点検の部品と、作り直しで残すもの

- きっかけ: 要件6が前の点検の予定と報告と記録の片付けを求め、要件1が点検を開発者が動かしたときだけにすることを求めた
- 調べた場所: `.claude/scripts/memory/memory-inspect.sh` `memory-inspect.pl` `transcript-scan.pl` `windows-launcher.cs` `inspect-prompt.md` `plan-schema.json` `tests/test-memory-inspect.sh`、`.claude/skills/memory-inspection/SKILL.md` `.claude/skills/memory-inspect-now/SKILL.md`、`.claude/settings.json`、`.kiro/specs/claude-memory-weekly-inspection/design.md`
- 分かったこと:
  - 点検の状態の場所は `<git の共通ディレクトリ>/keirekipro-memory-inspection/` である。中に `config.json`、回ごとの `runs/<回の ID>/`(`record.json` と `report.md`)、`snapshot.json`、`run.log`、`locks/`、Windows の起動用のプログラム `windows-launcher.exe` がある
  - 予定の名前は、`<git の共通ディレクトリ>` の場所の SHA-256 の先頭8文字(以下、予定の印)から作る。Windows はタスク スケジューラの `KeirekiPro memory inspection <予定の印>`、macOS は launchd の `com.keirekipro.memory-inspection.<予定の印>`(plist は `~/Library/LaunchAgents/` の下)、Linux は利用者の crontab の、末尾に `# keirekipro-memory-inspection <予定の印>` の付いた行である
  - 予定は、どれも本体の作業フォルダの `.claude/scripts/memory/memory-inspect.sh` に `run` を渡して動かす。Windows では、`windows-launcher.exe` が bash.exe にスクリプトの場所を渡す
  - 会話の始めのフックは、`.claude/settings.json` の `SessionStart` の `memory-inspect.sh session-context` である。`permissions.allow` に `Bash(bash .claude/scripts/memory/memory-inspect.sh *)` がある
  - 本体の作業フォルダとメモリのディレクトリの求め方(`git rev-parse --path-format=absolute --git-common-dir` の親を本体の作業フォルダとし、その場所の英数字でない文字を `-` に替えた名前の `~/.claude/projects/<名前>/memory` をメモリのディレクトリとする)と、目次の行が指すファイルの読み方(`index_links`)と、会話の記録の選び方(`transcript-scan.pl` の `project_dirs` `each_line` `developer_text`)は、新しい点検でもそのまま使える
  - 前の点検のテストは CI で流れていない。`.github/workflows/` に、`.claude/scripts/memory/` のテストを呼ぶ行は無い
- 設計への影響: 新しい点検は、使える求め方を新しいスクリプトに移し、前の点検のファイルを消す。会話の始めのフックと許可の行を `.claude/settings.json` から外す

### 会話の記録の形と残り方

- きっかけ: 要件3の受入基準2の2が、メモリファイルを最初に書いた会話の記録から、きっかけの発言を示すことを求めた
- 調べた場所: この PC の `~/.claude/projects/` の下の記録
- 分かったこと:
  - 記録のディレクトリは、作業フォルダごとに分かれる。本体の作業フォルダの名前の記録と、worktree ごとの `<本体の名前>--claude-worktrees-<名前>` の記録がある。メモリのディレクトリは、本体の作業フォルダの名前の下の1つだけである
  - メモリファイルを書いた行は、`message.content` の `tool_use` で、`name` が `Write` か `Edit` で、`input.file_path` がメモリファイルの場所である。Windows では、場所が `C:\Users\...` の形で書かれる
  - この PC に今あるメモリファイル12個のうち、書いた `tool_use` が記録に残っていたのは、この会話の中で読んだものを除くと見つからなかった。メモリファイルの名前を含む記録の行の多くは、会話の始めにメモリを読み込んだ行だった
- 設計への影響: 点検の部品は、メモリファイルの名前を含む行だけを JSON として読み、書き込みの `tool_use` を探す。最初に見つかった書き込みが `Write` でないときは、そのメモリファイルを作った会話の記録は残っていないとみなす。会話の記録が無いメモリファイルが多いことを前提に、きっかけの事柄の「分からない」の書き方を決める

### 選択肢の画面(AskUserQuestion)

- きっかけ: 要件4が、メモリファイル1つごとに選択肢の画面で尋ねることと、答える時点で3つの事柄を読めることを求めた
- 調べた場所: Claude Code の AskUserQuestion の道具の説明と、公式の文書
- 分かったこと:
  - 1回の呼び出しに並べられる問いは1から4、1つの問いの選択肢は2から4である。問いの見出し(`header`)は12文字までである(https://code.claude.com/docs/en/agent-sdk/user-input.md)
  - 選択肢の `preview` の欄は、SDK では表示の形を設定したときだけ使える。CLI の端末で表示されることは変更履歴から読み取れるが、デスクトップアプリでの表示の形と長さの上限は、公式の文書で確かめられなかった(https://code.claude.com/docs/en/changelog.md)
  - 問いに答えずに閉じたときと、スキップしたときに、道具の結果として Claude に何が返るかは、公式の文書に無い
  - AskUserQuestion は、Agent の道具で動かした補助役の中では使えない(https://code.claude.com/docs/en/agent-sdk/user-input.md の Limitations)
  - スキルの frontmatter の `allowed-tools` には、どの道具の名前も書ける。書いた道具は、許可の確認を省くだけである(https://code.claude.com/docs/en/skills.md)
- 設計への影響:
  - 3つの事柄は、表示が確かめられない `preview` に入れず、選択肢の画面を出す直前の返事の本文に書く。問いの文には、メモリファイルの名前と、本文の何番目の事柄かを書く
  - 選んだ選択肢の名前が「消す」「消さない」「点検を中止する」のどれでもなく、「その他」の文も無い問いは、すべて答えが無い問いとして扱う。スキップと閉じたときの結果の形を決め打ちしないためである。実装のときに、デスクトップアプリで、スキップしたときと閉じたときの結果を手で確かめる
  - 点検は、会話の中の Claude が直接行う。補助役に点検を任せると、選択肢の画面を出せない

## 設計の判断

### 判断: 会話の中の Claude が点検し、別のプロセスの Claude を呼ばない

- きっかけ: 要件1と要件4が、開発者が動かした会話の中で、開発者に1つずつ尋ねることを求めた
- ほかの案: 前の点検と同じく、`claude -p` で点検の中の Claude を呼び、判断の結果だけを会話に返す
- 選んだ案: 点検のスキルの手順に従って、会話の中の Claude が、重複の判断ときっかけの読み取りと推奨を書く
- 理由: 開発者に尋ねるのは会話の中の Claude なので、別のプロセスに判断を分けると、判断の理由を会話の中の Claude が説明できない。前の点検の報告が分かりにくかった理由の1つでもある
- 引き換えにしたこと: 点検の中で読む文書と記録の量だけ、会話が長くなる。メモリファイルは12個ほどで、会話の要約が起きる量にはならない見込みである
- 実装で確かめること: メモリファイルが20個あるときに、点検の全体で会話が要約されずに終わるか

### 判断: 前の点検の部品を消して、残った予定を無害にする

- きっかけ: 要件6の受入基準2が、本体の作業フォルダに変更が入ったあとは、残った予定がメモリを点検せず、書き換えないことを求めた
- ほかの案: `memory-inspect.sh` を残し、`run` を何もしないサブコマンドにする
- 選んだ案: `memory-inspect.sh` を消す。予定が動かすファイルが無いので、bash はファイルが無いことを出して終わる
- 理由: 何もしない `run` を残すと、あとで誰かが `run` に処理を足したときに、残った予定がまた動き出す
- 引き換えにしたこと: 残った予定は、外されるまで、週に1回、ファイルが無いことの失敗を OS の記録に残す。開発者が点検のスキルを1回動かせば、予定は外れる

### 判断: 前の点検の片付けを、点検のスクリプトと別のファイルにする

- きっかけ: 要件6の受入基準3から5
- ほかの案: 点検のスクリプトのサブコマンドにする
- 選んだ案: `old-inspection-cleanup.pl` を別のファイルにする
- 理由: 片付けは、すべての開発者の PC で前の点検が片付いたら要らなくなる。別のファイルにしておけば、あとで1つのファイルを消すだけで外せる
- 引き換えにしたこと: 本体の作業フォルダと git の共通ディレクトリの求め方を、点検のスクリプトから読み込んで使う

### 判断: 消す直前に、示したときの中身と同じかを SHA-256 で確かめる

- きっかけ: 要件5の受入基準6
- ほかの案: 消す直前に Claude がファイルを読み直し、示した全文と目で比べる
- 選んだ案: 一覧の部品が、メモリファイルごとに中身の SHA-256 を出す。Claude は、示したときの SHA-256 を消す部品に渡し、消す部品は、今の中身の SHA-256 が同じときだけ消す
- 理由: Claude が全文を目で比べると、1文字の違いを見落とすことがある。消したメモリファイルは戻せない
- 引き換えにしたこと: Claude は、会話の中で、メモリファイルごとの SHA-256 を覚えておく必要がある。会話が要約されても消えないように、CLAUDE.md の要約の決まりに足す

### 判断: リポジトリの文書は、`git fetch origin main` のあとの `origin/main` から読む

- きっかけ: requirements.md の言葉の定義「リポジトリの文書」が、main ブランチの最新の内容にある文書を比べる先にすると決めた
- ほかの案: 手元の `origin/main` を取り込み直さずに使う。GitHub の API で文書を1つずつ読む
- 選んだ案: 点検の始めに `git fetch origin main` を1回打ち、`git grep` と `git show` で `origin/main` を読む
- 理由: 手元の `origin/main` は、開発者が最後に取り込んだときのままである。GitHub の API で読むと、100ほどの文書を1つずつ取り寄せることになり、点検が遅くなる
- 引き換えにしたこと: `git fetch` は、`.git` フォルダの中の git 自身のファイル(`FETCH_HEAD`、`refs/remotes/origin/main` か `packed-refs`、その reflog、取り寄せたオブジェクト)を書き、条件によっては git の自動の掃除(`gc --auto`)も動かす。作業フォルダのファイルと、Git のほかのブランチは変わらない。取り込みに失敗したときは、手元の `origin/main` を使い、そのことを1行で示す
- 要件との関係: design の審査(D1-1-13)で、この書き込みを要件7の受入基準2が許していないことが分かった。所有者は、requirements に戻り、受入基準2に「git が `.git` フォルダの中の git 自身のファイルを書き換えることは除く」の例外を足した。この判断は、その例外の範囲で `git fetch` を使う

### 判断: 重複の判断で比べるのは、メモリファイルの決まりと事実で、出来事の記録は比べない

- きっかけ: 要件2の受入基準2の「決まりと事実のすべて」
- ほかの案: メモリファイルの本文のすべての文を比べる
- 選んだ案: frontmatter と、`**Why:**` の行のうち、いつ誰が何を言ったかという出来事だけの文は比べない。出来事の文に、リポジトリや道具についての事実が含まれるときは、その事実を比べる
- 理由: 出来事の記録は、リポジトリの文書には書かれない。出来事の記録まで比べると、尋ねずに消せるメモリファイルが無くなり、要件2が働かない
- 引き換えにしたこと: 出来事の記録だけがメモリに残る理由になっていたメモリファイルが、尋ねられずに消える。消したメモリファイルは、要件2の受入基準5のとおり一覧で示す

### 判断: 点検のスキルは README の「主なカスタムスキル」で案内し、参加者セットアップ手順の第5節は消す

- きっかけ: 要件6の受入基準6と7。所有者が、点検のスキルは README に書けばよく、参加者セットアップ手順には要らないと決めた
- ほかの案: 第5節を、点検のスキルを動かす手順に書き直す
- 選んだ案: 第5節を見出しから5-3の最後の行まで消し、README の「主なカスタムスキル」の表に `/memory-inspect-now` の行を足す
- 理由: 点検は予定の登録が要らないので、開発者が PC を用意するときにすることが無い。参加者セットアップ手順は PC を用意する手順だけを書く文書である
- 引き換えにしたこと: 前の点検の予定を登録していた開発者は、参加者セットアップ手順から予定を外す手順を読めなくなる。前の点検の予定は、最初の点検が外す(要件6の受入基準3)

## まとめた点、作らずに済ませた点、小さくした点

- まとめた点: 要件2の重複の削除と、要件5の了承のあとの削除は、同じ消す部品 `delete` を使う。どちらも、示したときか読んだときの SHA-256 を渡し、同じときだけ消して目次の行も消す
- 作らずに済ませた点: 前の点検の報告、記録、直しを戻す仕組み、ロック、予定の登録は作らない。要件4の受入基準7のとおり、答えを次の点検に残さないので、記録の置き場も要らない
- 作らずに済ませた点: 新しいライブラリは足さない。perl の `JSON::PP` と `Digest::SHA` は perl に標準で入っている
- 小さくした点: リポジトリの文書の検索は、新しい部品を作らず、Claude が `git grep` と `git show` を打つ

## 危ういことと備え

- 会話が要約されると、Claude が「消す」と答えられたメモリファイルと SHA-256 を失う。CLAUDE.md の要約の決まりに、点検の途中の答えを残すことを足す
- 会話の記録が大きいと、きっかけを探す時間が長くなる。点検の部品は、メモリファイルの名前を含まない行を JSON として読まずに飛ばす
- メモリファイルの中に、外から入った指示が書かれていることがある。点検のスキルの手順が、中身を材料としてだけ読むことを決め、消す部品はメモリのディレクトリの中の `.md` だけを消す

## 実装のときに確かめたこと

2026-11-02 に、実装の会話の中で、所有者と次のことを確かめた。Claude は、作り話のメモリファイル2つを使い、本物のメモリファイルの中身を使わなかった。

### 3つの事柄をどこに書くか

- 確かめたこと: 3つの事柄を返事の本文に書き、同じ返事で選択肢の画面を出す形を、所有者に見せた
- 所有者の答え: 所有者は、この形を採らないと決めた。メモリファイルが30個あれば、Claude は30個の全文を返事の本文に書くことになり、開発者は本文と選択肢の画面を行き来して読むことになるためである。画面が出ている間に本文を読めたかどうかは、所有者は確かめなかった
- 確かめたこと: 3つの事柄を、`消す` と `消さない` の選択肢の `preview` に入れて出した
- 分かったこと: デスクトップアプリは、`preview` を、選んでいる選択肢のすぐ下に、ほかの選択肢との間に出す。`preview` は Markdown として表示され、メモリファイルの全文をそのまま入れると、`---` の行のすぐ上の行が大きな見出しになる。全文をコードの囲みに入れると、見出しにならない
- 所有者の答え: 所有者は、`preview` の形を採らないと決めた。`消す` の選択肢だけが上にあり、その下に本文が出るためである
- 確かめたこと: 3つの事柄を、問いの文(`question`)に入れて出した。1つの画面に問いを2つ並べた
- 分かったこと: デスクトップアプリは、問いの文を、選択肢より上の枠に、改行を保ったまま出す。問いの文は Markdown として表示されず、行の頭の空白は表示されない。1つの画面の問いの数は、画面の右上に「2 件中 1 番目」と出る
- 所有者の答え: 所有者は、問いの文に3つの事柄を入れる形を良いと答えた
- 設計への影響: 「手順5 4つずつ示して尋ねる」は、3つの事柄を返事の本文に書かず、問いの文に入れる。1つの画面に問いを4つまで並べる形は変えない

### きっかけの書き方

- 確かめたこと: きっかけの事柄に、日付と、きっかけになった発言の引用だけを書いて見せた
- 所有者の答え: 所有者は、日付と引用だけでは何を言っているのか分からないと答えた
- 確かめたこと: きっかけの事柄を、「<日付> の会話で、所有者が「<発言>」と書いた。Claude は、その発言を受けて、<何のために>、このメモリを書いた。」の形で書いて見せた
- 所有者の答え: 所有者は、この形を良いと答えた
- 設計への影響: 「手順4 きっかけと推奨を用意する」は、発言の引用に加えて、誰がどの会話で何と書いたので、Claude が何のためにそのメモリファイルを書いたのかを、文で書く

### 選択肢の画面の答えが無いときの道具の結果

- スキップを押した問い: 道具の結果は、その問いの答えが `[No preference]` である
- 所有者が選択肢の画面に答えずにチャット欄に文を送った問い: 道具の結果は、その問いの答えが `[User did not answer this question — they sent a message instead. ...]` である。送った文は、道具の結果には入らず、次の会話の文として届く。このあと、Claude の返事は止まらずに続いた
- 答えずに画面を閉じた問い: 所有者は、デスクトップアプリの選択肢の画面に閉じる操作を見つけられなかった。閉じたときの結果の形は確かめられなかった
- 設計への影響: 無い。設計は、選んだ `label` が「消す」「消さない」「点検を中止する」のどれでもなく、「その他」の文も無い問いを、すべて答えが無い問いとして扱う。上の2つの形は、どちらもこれに当たる

### 会話の記録の `Write` の結果

- 確かめたこと: scratchpad のファイルを `Write` で作ってから、同じファイルを `Write` で上書きし、この会話の記録から2つの結果の行を読んだ
- 分かったこと: `toolUseResult.type` は、作ったときが `create`、上書きしたときが `update` だった。どちらの行にも `content` `filePath` `originalFile` `structuredPatch` `type` `userModified` がある
- 設計への影響: `origins` は、最も早い書き込みが、結果が `update` の `Write` なら、そのメモリファイルを作った会話の記録が残っていないとみなし、`first-write-not-kept` を返す
