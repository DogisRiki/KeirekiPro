# 要件

## はじめに

所有者は今、依存の更新のたびに承認の操作をしている。この spec は、その承認の操作を無くす。ただし、この spec は承認を単に外すのではなく、承認が担っていた役割を機械の関門に置き換える。

置き換えに必要な関門のうち、クールダウン(公開直後の版を使わないこと)、メジャー更新の除外、lockfile の固定、新しく増えた脆弱性の検知は、すでにある。残る穴は2つある。1つ目は、backend に公開直後の版を足す経路に、クールダウンが効かないことである。2つ目は、Gradle wrapper の配布物を、どの検査も検証していないことである。

この spec は、この2つの穴を塞ぐ関門を足し、同じ変更で `dependency-gate` の判定の対象を縮める。検査の追加と承認の撤廃を別の変更に分けると、検知が無いまま承認だけが外れる期間ができる。そのため、この spec は、検査の追加と承認の撤廃を1つの変更でまとめて行う。

この spec に対応するIssueは、#182(やること4・5・6)である。

## 範囲

- この spec で決めること:
  - backend に追加されるパッケージの、公開からの経過時間の検査
  - Gradle wrapper の配布元・チェックサム・jar の検証
  - `dependency-gate` の判定の対象の縮小
  - 上の3つに伴う運用文書の更新
- この spec で決めないこと:
  - frontend のクールダウンの検査。pnpm のリゾルバがクールダウンを強制しているため、この spec の機能は frontend のクールダウンを担わない
  - Dependabot が作ったPRへの、クールダウンの検査の適用
  - フォークから出されたPRへの、クールダウンの検査の適用。フォークから出されたPRでは依存グラフの送信が成り立たず、検査が追加されたパッケージを特定できないためである
  - 既存の依存に対する、さかのぼった検査。検査は、そのPRで新しく追加されたパッケージだけを判定の対象にする
  - `escape-hatch` / `pre-merge-check` / CODEOWNERS による承認の見直し。これらは脆弱性と関係の無い関門であるためである
  - Dependabot のPRの自動マージ(#127 が扱う)
  - コンテナイメージの検査(#181 が扱う)
- この spec が前提にしていること:
  - 新しく増えた脆弱性の検知は、`dependency-review` が担う。この spec の機能は、脆弱性の有無を判定しない
  - frontend で公開直後の版を止めることは、pnpm の `minimumReleaseAge` が担う
  - Dependabot のバージョンの更新で公開直後の版を止めることは、Dependabot 自身の既定のクールダウンが担う
  - 新しく作った検査を必須チェックに登録する操作は、所有者が行う。この spec の機能は、登録そのものを行わない
  - 同じ失敗が3回続いたときに作業を止めて人間に報告することは、開発エージェントの既存の規約が担う。この spec の機能は、その判断の材料を報告に含めることまでを受け持つ

## 要件

### 要件1 依存のクールダウンの検査

所有者は、公開直後のパッケージが承認なしにマージされることを防ぎたい。悪意のある版の多くは公開から数時間で削除されるため、版を寝かせるだけで、その大半を避けられるからである。

1. backend の依存の定義を変えるPRが作られたら、依存のクールダウンの検査は、そのPRで新しく追加されたパッケージを、推移的な依存を含めて特定する。
2. 新しく追加されたパッケージのどれかが公開から72時間を経過していなければ、依存のクールダウンの検査は、チェックを失敗させる。
3. チェックを失敗させるとき、依存のクールダウンの検査は、該当したパッケージと、待機が明ける時刻を報告する。
4. パッケージの公開時刻を取得できなければ、依存のクールダウンの検査は、チェックを失敗させる。
5. PRの作成者が Dependabot なら、依存のクールダウンの検査は、判定を行わずにチェックを成功させる。
6. 依存のクールダウンの検査は、公開時刻が分かっているパッケージについて、その実際の公開時刻に基づく判定を返す。
7. 1つのPRで多くのパッケージが72時間未満に当たったら、依存のクールダウンの検査は、待機が明ける最も遅い時刻を明示する。依存のクールダウンの検査は、再実行すべき時期を報告の1回の閲覧で判断できる形で報告する。
8. そのPRで新しく追加されたパッケージが無ければ、依存のクールダウンの検査は、チェックを成功させる。

**補足**: 判定の基準の72時間は、frontend の `minimumReleaseAge` と、Dependabot の既定のクールダウンと同じ値である。項目6(公開時刻が分かっているパッケージを、実際の公開時刻で判定すること)を置くのは、索引の更新が正典より遅れる情報源を判定に使うと、公開済みの版を「存在しない」と誤って判定する事象が、実際に観測されているためである。項目7(待機が明ける最も遅い時刻を明示すること)は、Spring Boot のように BOM が多くの推移的な依存を同時に持ち込む更新で、該当が一斉に出ることを想定している。

### 要件2 Gradle wrapper の検証

所有者は、ビルドが取得する Gradle 本体の配布物が公式のものであることを、機械で確かめたい。wrapper はビルドの実行環境そのものであり、wrapper が差し替えられると、それ以降のすべての検査が信用できなくなるからである。

1. リポジトリは、Gradle wrapper の設定に、公式に公表された配布物のチェックサムを持つ。
2. Gradle wrapper の設定が指す配布元のホストが公式の配布元でなければ、Gradle wrapper の検査は、チェックを失敗させる。
3. Gradle wrapper の設定が持つチェックサムが公式に公表された値と一致しなければ、Gradle wrapper の検査は、チェックを失敗させる。
4. リポジトリの中の wrapper の実行ファイルが公式のリリースのチェックサムと一致しなければ、Gradle wrapper の検査は、チェックを失敗させる。
5. Dependabot が Gradle wrapper のバージョンを更新するPRを作ったら、Gradle wrapper の検査は、そのPRを通す。
6. Gradle wrapper の設定を変えないPRが作られたら、Gradle wrapper の検査は、チェックを成功させる。

**補足**: 項目1(設定に公式のチェックサムを持つこと)は、Dependabot がチェックサムを保つための前提である。設定にチェックサムの項目が無ければ、Dependabot はその項目を管理せず、バージョンだけを更新する。

項目2(配布元のホストの検査)と項目3(チェックサムの検査)は、信頼の根が同じであるため、独立した2つの防御にはならない。配布元のホストが侵害されると、配布物と公表されたチェックサムの両方が同時に偽装される。実際に効いているのは項目2の検査であり、この spec は、項目3の検査を、手作業による書き換えとの食い違いを見つけるものと位置づける。この spec は、この限界を運用文書に記録する。

### 要件3 依存の定義の承認の撤廃

所有者は、依存のバージョンの更新を、承認の操作なしにマージさせたい。承認が担っていた役割が機械の関門に置き換わり、承認を続ける理由が無くなるからである。

1. 依存のバージョンの宣言だけを変えるPRが作られたら、依存の変更のゲートは、所有者の承認を求めない。
2. パッケージの取得元の設定を変えるPRが作られたら、依存の変更のゲートは、所有者の承認を求める。
3. インストールのときに実行されるスクリプトの定義を変えるPRが作られたら、依存の変更のゲートは、所有者の承認を求める。
4. 供給網の対策の設定を変えるPRが作られたら、依存の変更のゲートは、所有者の承認を求める。
5. ビルドスクリプトを変えるPRが作られたら、依存の変更のゲートは、所有者の承認を求める。

**補足**: 承認を外す対象は、frontend のパッケージの定義と lockfile、backend のバージョンカタログと wrapper の設定である。承認を残す対象は、レジストリの設定、インストールのフック、overrides と供給網の対策の設定を含むワークスペースの設定、ビルドスクリプトである。

承認を外したあとも、プロジェクト自身のパッケージの定義に任意のコマンドを書ける経路は残る。この経路は、エージェントが書いたコードがCIと開発環境で実行されることを、すでに受け入れている範囲にある。そのため、この経路は新しい信頼の水準を求めるものではない。この spec は、この残るリスクを運用文書に記録する。

### 要件4 検査そのものの健全さ

所有者は、追加した検査が壊れたまま緑を返す状態を避けたい。検査が形だけ通っている状態は、検査が無い状態より危ないからである。

1. 継続的インテグレーションは、新しく作った各検査の判定の処理に対する自動テストを、その検査の判定より先に実行する。
2. 判定の処理の自動テストが失敗したら、継続的インテグレーションは、その検査を失敗させる。
3. 判定の処理の自動テストは、境界値、判定できないときの扱い、対象外とする条件を確かめる。

### 要件5 失敗したときの運用

所有者は、外部の要因で検査が赤になったときに、作業が限りなく滞ることを避けたい。エージェントが自力で解消できない赤は、人間に引き渡す必要があるからである。

1. 外部への問い合わせが原因で検査が失敗したら、検査は、失敗の原因が外部の要因であることを、待てば解消する失敗と区別できる形で報告する。
2. クールダウンによって検査が失敗したら、検査は、時間がたてば解消することを報告に含める。
3. 検査は、失敗の報告に、人間が介入すべきか再実行を待てばよいかを判断する材料を含める。

### 要件6 運用文書の更新

所有者は、監査を行う。所有者は、追加した検査と変わった承認の範囲を、文書から追えるようにしたい。人間がコードを読まない体制では、文書が実態と食い違うと監査が成り立たないからである。

1. 新しく作った検査を入れたら、Claude は、運用文書の監査の対象の自動チェックの一覧に、その検査を加える。
2. 承認の対象の範囲が変わったら、Claude は、運用文書の承認が必要な変更の記述を、実態に合わせて直す。
3. Claude は、新しく作った検査を必須チェックに登録する手順と、登録の順序に関する制約を、運用文書に書く。
4. Claude は、Gradle wrapper の配布元のホストの検査とチェックサムの検査が信頼の根を共有することと、パッケージの定義に任意のコマンドを書ける経路が残ることを、受け入れた残るリスクとして運用文書に書く。
5. ワークフローを追加したか変えたときは、Claude は、プロジェクトの説明の文書のワークフローの一覧と図を、同じ変更の中で直す。
