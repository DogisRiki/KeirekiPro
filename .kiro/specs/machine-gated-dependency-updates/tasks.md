# Implementation Plan

すべて1つのPRで出荷する。検査の追加(2章・3.1・3.2)と承認の撤廃(3.3)を別のPRに分けると、
検知が無いまま承認だけが外れる期間ができるため。

`.github/` 配下はエージェントが書き込めない。新規ファイルは全文を提示し、既存ファイルの修正は
実行コマンドを提示して、所有者に配置してもらう。各タスクの完了は配置後の状態で判定する。

- [ ] 1. 前提の整備

- [x] 1.1 Gradle 配布物のチェックサムを設定に追加する
  - `backend/gradle/wrapper/gradle-wrapper.properties` に、現在の配布物に対応する公式の
    チェックサムを追加する
  - 値は公式の配布元から取得する。取得時にリダイレクトが返るため追従する。追従しないと
    HTML断片を掴み、以降の検証が恒久的に不一致になる
  - **完了条件**: 配布物のキャッシュを削除した状態で、誤った値では検証が停止し、正しい値では
    起動することを確認する。そのうえで `/verify-backend` をPASSさせる
  - **`/verify-backend` が通ることを値の正しさの根拠にしない。** Gradle の検証は配布物の
    ダウンロード時にしか行われず、キャッシュ済みの環境では誤った値でも素通りすることを
    実測で確認した。開発コンテナには配布物がキャッシュされているため、キャッシュを消さずに
    通っても何も確認したことにならない
  - この項目が無いと、依存更新の仕組みがチェックサムを管理対象にせず、バージョンだけが
    進んで検証が赤になる
  - _Requirements: 2.1_

- [ ] 2. 検査スクリプトの実装

- [x] 2.1 (P) 公開経過時間を判定する検査を作る
  - そのPRで新しく追加されたパッケージを、推移的依存を含めて特定する。入力は依存グラフの
    差分比較のみとし、ビルド定義やロックファイルは解析しない
  - 対象は maven のエコシステムに限る。追加が0件なら判定を行わず成功で終える
  - 各パッケージの公開時刻を成果物の配布元から取得する。Maven Central を先に引き、
    見つからないときだけ Gradle Plugin Portal へフォールバックする。索引が正典より遅れる
    検索APIは使わない
  - 公開から72時間を経過していないものが1件でもあれば失敗させる。1件でも公開時刻を
    取得できない場合も失敗させる
  - 報告を2種類に分ける。クールダウンによる失敗には該当一覧と待機が明ける最も遅い時刻、
    および時間の経過で解消する旨を含める。判定不能には問い合わせ先と外部要因である旨を含める
  - 判定処理のテストを同時に作る。境界値(72時間ちょうどが通り、それ未満が落ちる)、
    判定不能の扱い、フォールバックの発火、追加0件、多数該当時に最も遅い時刻が報告に
    現れることを検証する。外部への問い合わせはスタブする
  - **完了条件**: テストをローカルで実行して全ケースがPASSする。判定処理を一時的に壊すと
    テストが赤くなることを確認してから戻す
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.6, 1.7, 1.8, 4.3, 5.1, 5.2, 5.3_
  - _Boundary: DependencyCooldownCheck_

- [x] 2.2 (P) Gradle 配布物の同一性を検証する検査を作る
  - 変更範囲を自分で判定する。wrapper 関連の変更が差分に含まれないときは、外部への
    問い合わせを一切行わずに成功で終える
  - 判定に使う条件は2つ。wrapper のディレクトリ配下の変更があること、または追加・変更された
    jar があること。後者は、ディレクトリ外に置かれた偽装ファイルを取りこぼさないため
  - 配布元のホストが公式であることを検証する。公式でなければ失敗させる
  - 設定が持つチェックサムが公式に公表された値と一致することを検証する。一致しなければ
    失敗させる。チェックサムの項目が存在しない場合も失敗させる
  - 公式値の取得ではリダイレクトに追従する
  - 判定処理のテストを同時に作る。対象外の差分で外部照会が発生しないこと、ディレクトリ外の
    jar 追加で照会が走ること、公式でないホスト、値の不一致、項目の欠落がそれぞれ落ちることを
    検証する。外部への問い合わせはスタブする
  - **完了条件**: テストをローカルで実行して全ケースがPASSする。判定処理を一時的に壊すと
    テストが赤くなることを確認してから戻す
  - _Requirements: 2.2, 2.3, 2.6, 4.3, 5.1, 5.3_
  - _Boundary: GradleWrapperCheck_

- [ ] 3. CIへの組み込みと承認範囲の縮小

- [ ] 3.1 公開経過時間の検査をワークフローに組み込む
  - 依存グラフの送信ジョブの後段に、新しいジョブとして追加する。前段や別ワークフローに
    置くと、送信が済む前に比較して追加パッケージを取りこぼす
  - 判定スクリプトのテストを判定より先に実行する。テストが落ちたら検査も落とす
  - 対象外をジョブ単位の条件で表現する。同一リポジトリのPRであること、作成者が依存更新の
    自動化によるものでないこと、生成ジョブが成功していること、送信ジョブが失敗していないこと
  - 生成ジョブの成功を明示的に要求する。生成が失敗すると送信はスキップになり、
    スキップは失敗ではないため条件をすり抜ける
  - 依存グラフの差分比較にはトークンによる認証が要る。ジョブに読み取り権限を与え、
    スクリプトへトークンを渡す
  - **完了条件**: 変更後のワークフローが所有者によって配置され、依存を追加しないPRで
    このジョブが成功する
  - _Requirements: 1.5, 4.1, 4.2_
  - _Depends: 2.1_

- [ ] 3.2 (P) 配布物の検証をワークフローに組み込む
  - ずるの検査を担うワークフローに、新しいジョブとして追加する。アクション参照の固定検査と
    目的が同じ「ビルドが取得する外部成果物の同一性の検証」であるため
  - ジョブは常時実行する。実行条件の判定はスクリプトと jar 照合のステップ側で行う
  - jar の公式チェックサムとの照合を行うステップを置く。このステップにも同じ実行条件を付ける。
    照合を行う仕組み自体も公式のチェックサム一覧を取得するため、条件を付けないと外部依存が残る
  - 判定スクリプトのテストを判定より先に実行する
  - 差分の判定に基点と先端の比較を使うため、チェックアウトで履歴を全て取得する
  - **完了条件**: 変更後のワークフローが所有者によって配置され、wrapper を変更しないPRで
    このジョブが成功し、外部への問い合わせが発生しない

  - _Boundary: WrapperJob_
  - _Depends: 2.2_

- [ ] 3.3 承認が必要な変更の対象を縮小する
  - 依存のバージョン宣言にあたるものを対象から外す。frontend のパッケージ定義とロックファイル、
    backend のバージョンカタログと wrapper の設定が該当する
  - 取得元の設定、インストール時に実行されるスクリプトの定義、供給網対策の設定、
    ビルドスクリプトは対象として残す
  - バージョンカタログは現在の判定式に含まれている。明示的に外さないと対象のまま残り、
    カタログへ移した意味が消える

    この報告は判定に使っていないため削除する
  - 判定式の設計根拠を説明した冒頭の記述は、残す対象に対して引き続き有効であるため変更しない
  - 既存のテストを縮小後の対象に合わせて入れ替える。外した対象の変更が緑になること、
    残した対象の変更が赤になることをそれぞれ検証する
  - **完了条件**: テストをローカルで実行して全ケースがPASSする。バージョンカタログだけを
    変更した差分で緑、取得元の設定を変更した差分で赤になる

## Implementation Notes

- **1.1**: `distributionSha256Sum` の検証は**配布物のダウンロード時にのみ行われる**。
  実測で確認した。誤った値を入れてもキャッシュ済みの環境では素通りし、キャッシュを削除して
  初めて期待値と実際の値が照合されて停止した。
  つまり Gradle 自身の検証は、配布物を取得し直す環境(CIランナー)でしか効かない。
  値そのものが書き換えられた場合を捉えるには、公表値と突き合わせるCI側の検査(2.2)が要る。
  この非対称は 2.2 の設計根拠を補強するものであり、運用文書にも残す価値がある
- **2.1 / 2.2**: 外部から値を取る箇所で「取得失敗」と「空の結果」を同じに扱うと fail-open に
  なる。レビューで3回同じ類型を指摘された(比較APIの `|| true`、`git diff` の `|| true`、
  ヘッダ取得のフォールバック)。加えて、パイプの終端が `sed` だと `gh` の失敗自体を拾えない。
  以降、外部から値を取る箇所を作るたびに、取得の成否と結果の空を区別しているかを先に確認する
- **2.1**: 静的解析は引数位置に現れた関数名を参照と数えない。テストで変更操作を関数名で
  渡す設計にすると SC2329 が出る。コマンド位置で呼ぶ形にすれば抑制指示が要らない
- **2.1**: 比較APIは head 側スナップショットの取り込み前でもエラーにせず 200 を返す。
  取り込み数の不一致は `x-github-dependency-graph-snapshot-warnings` ヘッダ(base64)で
  知らされる。警告が無いときもヘッダ自体は存在し、値が空になる
