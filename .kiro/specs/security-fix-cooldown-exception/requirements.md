# 要件

## 元の要望
Issue #641: すぐに当てるべき脆弱性を直した版を、公開から72時間待たずに入れられるようにする

### きっかけ

#625 で CI の Node.js の版を手で上げたあと、所有者が、すぐに当てるべき脆弱性の修正は72時間待たずに入れられるようにしたいと求めた。

### 困っていること

- 脆弱性を直した版も、ほかの版と同じく、公開から72時間経つまで入れられない。そのため、すぐに当てるべき脆弱性の修正が、72時間遅れる。

### やりたいこと

- すぐに当てるべき脆弱性を直した版を、72時間待たずに入れられるようにする。

### どうなれば解決か

- 本番で動く frontend と backend の部品に、high か critical の脆弱性の警告が出たとき、警告が示す最初の修正版は、公開から72時間経っていなくても入る。(AIの提案を了承)
- 72時間待たずに入るのは、警告が示す最初の修正版だけである。同じ変更で新しく入るほかの部品は、今と同じく72時間経つまで入らない。(AIの提案を了承)
- 72時間待たずに入れる版か、同じ変更で新しく入る部品が、悪意のある部品として公表されていれば、その変更は入らない。(AIの提案を了承)
- 72時間待たずに入れる版の署名の鍵が、前の版の署名の鍵と違えば、その版は72時間経つまで入らない。(AIの提案を了承)
- 72時間待たずに入れた版は記録に残り、週次の監査の報告に一覧で載る。(AIの提案を了承)
- CI の Node.js、Trivy、Codex CLI、Terraform の脆弱性を直した版は、所有者が指示したときだけ、72時間待たずに入る。そのときは、配布元の署名を確かめてから入る。(AIの提案を了承)

### やらないこと

- 開発のときだけ使う部品の、脆弱性を直した版を、72時間待たずに入れること。開発のときだけ使う部品は、今と同じく72時間待つ。(AIの提案を了承)
- 開発環境の Docker イメージの扱いを変えること。(AIの提案を了承)

### 決めた方式

- 脆弱性を直した版を72時間待たずに入れる変更は、PR が自動で作られても、所有者が承認するまでマージされない。
- 所有者の承認を待つあいだに、PR で入るすべての版が公開から72時間経っても、その PR は、frontend でも backend でも、所有者が承認するまでマージされない。(AIの提案を了承)

## はじめに

このリポジトリでは、frontend と backend の部品の版は、公開から72時間経つまで入らない。この spec では、この決まりを「72時間の待ち」と呼ぶ。72時間の待ちがあるのは、公開から間もない版が、公開元を乗っ取った者の出した悪意のある版であっても、まだ誰も気づいていないことがあるためである。72時間の待ちは、脆弱性を直した版にも同じく効く。そのため、すぐに当てるべき脆弱性の修正も、72時間遅れる。

この spec は、本番で動く部品に、深刻度が high か critical の脆弱性の警告が出たときに、警告が示す最初の修正版を、72時間待たずに入れられるようにする。最初の修正版とは、警告が、その脆弱性を直した版として挙げる版のうち、いちばん古い版である。72時間待たずに入る版は、72時間の待ちの代わりになる2つの確認を通ってから入る。1つ目は、悪意のある部品として公表されていないかの確認である。2つ目は、署名した者が前の版と同じかの確認である。

この spec は、CI で使う Node.js、Trivy、Codex CLI、Terraform の4つの道具についても、所有者が指示したときに、脆弱性を直した版を72時間待たずに入れる決まりを定める。

この spec では、部品の版が「入る」とは、その版に上げる変更がマージできることと、マージのあとに CI と開発者の環境と本番の配布物の組み立てがその版を入れられることの両方を指す。

## 範囲

- この spec で決めること: この spec では、次の4つを決める。
  - 本番で動く frontend と backend の部品で、72時間待たずに入る版の条件
  - 72時間待たずに入れる前に行う確認と、確認で止めたときに示すこと
  - CI の Node.js、Trivy、Codex CLI、Terraform の版を、72時間待たずに変える条件
  - 72時間待たずに入れた版の記録と、週次監査での報告
- この spec で決めないこと: この spec では、次の8つを決めない。
  - 脆弱性を直す変更を誰が作るか。変更は、Dependabot と AI と開発者のどれが作ってもよい。frontend の修正の PR を自動で作ることは Issue #630 で、backend の修正の PR を自動で作ることは Issue #643 で決める
  - 脆弱性の警告を所有者に届けること。これは Issue #642 で決める
  - CI が道具を入れるたびに、道具の署名を確かめること。これは Issue #644 で決める
  - CI の道具の版を自動で上げることと、CI の道具の版にも72時間の待ちを機械で効かせること。これらは Issue #640 で決める
  - CI で使う道具のうち、Node.js、Trivy、Codex CLI、Terraform のほかの道具の版の扱い
  - 開発のときだけ使う部品の扱い
  - 開発環境の Docker イメージの扱いと、本番のコンテナイメージの土台の版の扱い
  - 変更を作ったときに、すべての部品の版が公開から72時間経っている変更の扱い。こうした変更は、今と同じ検査を受ける。この spec は、こうした変更に、悪意のある部品の一覧に照らす確認と、署名した者の確認を足さない。所有者の承認を待つあいだにすべての部品の版が72時間経った変更は、この項目に当たらない。
- この spec が前提にしていること: この spec は、次の3つを前提にする。
  - GitHub が、このリポジトリが使っている部品の脆弱性の警告を出すこと。警告には、部品の名前と、深刻度と、最初の修正版と、その部品が本番で動くか開発のときだけ使うかが載る。ただし、本番で動くか開発のときだけ使うかが載らない警告もある
  - 72時間の待ちが、今、frontend と backend の部品に効いていること
  - CI の道具の版を変える変更は、所有者が承認しないとマージされないこと

## 要件

### 要件1 本番で動く部品の深刻度の高い脆弱性を直した版は、72時間待たずに入る

脆弱性を直した版が公開されても、72時間の待ちのあいだ、本番は脆弱性を抱えたまま動く。深刻度が high か critical の脆弱性は、攻撃されたときの被害が大きい。そこで、所有者は、直した版をすぐに入れたい。ただし、72時間待たずに入れる版には、悪意のある版を誰かが見つけるまでの時間が無い。そのため、所有者は、72時間待たずに入れる変更を、自分で読んで承認してからマージしたい。

1. 脆弱性の警告が示す最初の修正版は、次の3つがすべてそろえば、公開から72時間経っていなくても入る。
   - 警告が、このリポジトリが今使っている版に出ている
   - 警告が出た部品が、本番で動く frontend か backend の部品である
   - 警告の深刻度が high か critical である
2. 最初の修正版を72時間待たずに入れる変更は、frontend の部品の変更でも backend の部品の変更でも、所有者が承認するまでマージされない。変更の PR が自動で作られたときも、所有者が承認するまでマージされない。所有者は、承認するときに、その PR で、72時間待たずに入れる版と、理由になった警告を読める。所有者の承認を待つあいだに、変更で新しく入るか版が変わるすべての部品の版が、公開から72時間経つことがある。そのときも、その変更は、frontend の部品の変更でも backend の部品の変更でも、所有者が承認するまでマージされない。
3. 1つの部品に、深刻度が high か critical の警告が2つ以上出ているときは、どの警告が示す最初の修正版も、72時間待たずに入る。
4. 警告の深刻度が high でも critical でもなければ、その警告が示す最初の修正版は、今と同じく、公開から72時間経つまで入らない。
5. 警告が出た部品が開発のときだけ使う部品であれば、その警告が示す最初の修正版は、今と同じく、公開から72時間経つまで入らない。
6. 警告に、その部品が本番で動くか開発のときだけ使うかが載っていなければ、その警告が示す最初の修正版は、公開から72時間経つまで入らない。
7. 最初の修正版に上げる変更は、誰が作ったかによらず、この要件の決まりで入るかどうかが決まる。
8. 72時間待たずに入った版は、マージのあとに警告が閉じても、入ったままである。CI と開発者の環境と本番の配布物の組み立ては、その版の公開から72時間経つ前でも、その版を入れられる。

### 要件2 72時間待たずに入るのは、警告が示す最初の修正版だけにする

72時間待たずに入る版が増えるほど、公開から間もない悪意のある版が入るおそれが増える。脆弱性を直すために要るのは、警告が示す最初の修正版だけである。そこで、所有者は、72時間待たずに入る版を、最初の修正版だけに絞りたい。

1. 警告が示す最初の修正版より新しい版に上げる変更は、今と同じく、その新しい版の公開から72時間経つまで入らない。
2. 最初の修正版に上げる変更で、ほかの部品が新しく入るか、ほかの部品の版が変わるときは、ほかの部品のその版は、今と同じく、公開から72時間経つまで入らない。その変更は、ほかの部品のすべての版が公開から72時間経つまで入らない。

### 要件3 悪意のある部品として公表されている部品を含む変更は、72時間待たずには入らない

72時間の待ちは、公開から間もない悪意のある版を、誰かが見つけて公表するまでの時間をとるためにある。72時間待たずに入れる版には、この時間が無い。そこで、所有者は、すでに公表されている悪意のある部品の一覧に照らしてから、最初の修正版を入れたい。

1. 最初の修正版を72時間待たずに入れる変更は、変更で新しく入るか版が変わるすべての部品が、悪意のある部品として公表された部品の一覧に載っていないと確かめられたときだけ入る。一覧に照らす部品には、72時間待たずに入れる最初の修正版も含まれる。
2. 一覧に照らせなかったときも、その変更は72時間待たずには入らない。一覧に照らせなかったときとは、一覧を取りに行けなかったときや、一覧から答えを得られなかったときを指す。その変更は、今と同じく、変更で新しく入るか版が変わるすべての部品の版が公開から72時間経てば入る。

### 要件4 署名した者が前の版と違う最初の修正版は、72時間待たずには入らない

公開元を乗っ取った者は、本来の公開元として署名できないまま、版を公開することがある。署名した者が前の版から変わったことは、公開元が乗っ取られたことを疑う手がかりになる。そこで、所有者は、署名した者が前の版と同じことを確かめてから、最初の修正版を72時間待たずに入れたい。この要件の「前の版」は、最初の修正版に上げる前に、このリポジトリが使っている版を指す。

1. 前の版に署名があれば、最初の修正版は、署名した者が前の版と同じだと確かめられたときだけ、72時間待たずに入る。最初の修正版を署名した者が前の版と違うときと、最初の修正版に署名が無いときは、最初の修正版は、公開から72時間経つまで入らない。
2. 署名した者とは、署名から分かる、その版を公開した者の身元を指す。署名に使った鍵がその公開元だけのものなら、鍵が身元になる。署名のたびに鍵が作り直される署名なら、署名に記された公開元の身元が身元になる。
3. 公開元を見分けられない署名は、署名した者を比べる材料にならない。どの部品にも同じ鍵で付く署名は、公開元を見分けられない署名に当たる。前の版と最初の修正版に、公開元を見分けられる署名が無ければ、その版には署名が無いものとして扱う。
4. 前の版に署名が無ければ、署名した者を比べることは、最初の修正版を止める理由にならない。ほかの要件の確認が通れば、最初の修正版は72時間待たずに入る。
5. 前の版と最初の修正版のどちらかの署名を調べられなかったときは、最初の修正版は、公開から72時間経つまで入らない。署名を調べられなかったときとは、署名を取りに行けなかったときや、署名があるかどうかを判定できなかったときを指す。

### 要件5 72時間待たずに入れた版は記録に残り、今ある週次監査が、その版の一覧を報告する

72時間待たずに入れた版は、悪意のある版であっても、まだ誰も気づいていないうちに本番に入るおそれがある。そこで、所有者は、何が72時間待たずに入ったかを、あとから確かめられるようにしたい。また、所有者は、今ある週次監査の報告で、その週に72時間待たずに入った版の一覧を読みたい。この要件は、新しい監査を作らない。この要件は、今ある週次監査に、72時間待たずに入った版を報告する項目を1つ足す。

1. frontend か backend の部品の版が72時間待たずに入ったら、その版の記録が残る。記録には、部品の名前と、版と、版の公開日時と、72時間待たずに入れる理由になった警告と、その版を入れた PR と、その PR がマージされた日時が載る。
2. frontend か backend の部品の版は、その版の記録が残るときだけ、72時間待たずに入る。
3. Claude は、CI の道具の版を72時間待たずに変えるときは、その版に変える PR で、その版の記録を残す。記録には、道具の名前と、版と、版の公開日時と、所有者が指示したことと、署名を確かめた結果と、その版に変えた PR が載る。CI の道具の版を変える PR は所有者が承認してからマージされるので、所有者は、承認するときに、その PR に記録があるかを確かめられる。
4. 記録は、版の公開から72時間経ったあとも残る。
5. 最初の修正版が、変更のときにすでに公開から72時間経っていれば、その版は今と同じ決まりで入る。この版は、72時間待たずに入れた版の記録に載らない。
6. 週次監査は、前の回の週次監査からその回の週次監査までのあいだに72時間待たずに入った frontend か backend の部品の版と、同じあいだに72時間待たずに変えた CI の道具の版の一覧を、報告に載せる。週次監査は、この一覧を、今の判定の項目の結果と同じく、所有者を担当者にした Issue で所有者に届ける。週次監査がこの一覧を載せるのは、一覧に載せる版が1つでもあるときである。週次監査は、一覧に、frontend か backend の部品の版が72時間待たずに入ったときに残る記録の版と、Claude が CI の道具の版を72時間待たずに変えたときに PR で残す記録の版の両方を載せる。週次監査は、一覧の版ごとに、記録に載っていることをすべて載せる。CI の道具の版がどの回の週次監査の一覧に載るかは、その版に変えた PR がマージされた日時で決まる。
7. 週次監査は、72時間待たずに入った版が無い回には、この項目のために Issue を作らない。72時間待たずに入った版が無い回とは、前の回の週次監査からその回の週次監査までのあいだに、72時間待たずに入った frontend か backend の部品の版も、72時間待たずに変えた CI の道具の版も、1つも無い回を指す。
8. 週次監査が記録を読めなかったときは、週次監査は、今の判定の項目を判定できなかったときと同じく、記録を読めなかったことを、所有者を担当者にした Issue に書く。

### 要件6 CI の道具は、所有者が指示したときだけ、署名を確かめてから72時間待たずに変える

CI は、本番の配布物を組み立て、秘密の値を扱う。CI の道具に悪意のある版が入ると、被害は本番と秘密の値に及ぶ。そこで、所有者は、CI の道具の脆弱性を直した版を72時間待たずに入れるかどうかを、自分で決めたい。また、所有者は、72時間待たずに入れるときは、その版が配布元の出したとおりのものだと Claude が確かめてから、その版を入れるようにしたい。

1. 所有者が指示したときだけ、Claude は、CI の Node.js、Trivy、Codex CLI、Terraform の版を、公開から72時間経っていない版に変える。
2. 所有者の指示が無いときは、Claude は、CI の道具の版を、公開から72時間経っていない版に変えない。
3. 公開から72時間経っていない版に変える前に、Claude は、配布元の署名で、その版の中身が配布元の出したものと同じことを確かめる。
4. 署名で確かめられなかったときは、Claude は、その版に変えない。署名で確かめられなかったときとは、配布元が署名を出していないときや、署名が中身と合わないときや、署名を取りに行けなかったときを指す。Claude は、その版に変えなかったことと、署名で確かめられなかった理由を、所有者への返事に書く。
5. Claude は、署名を確かめた結果を、その版に変える PR の本文に書く。

### 要件7 最初の修正版を72時間待たずに入れられないときは、PR の検査の結果に、理由と、入るようになる時刻が出る

最初の修正版を72時間待たずに入れられないとき、変更を作った人は、理由が分からなければ、手で調べ直すことになる。また、変更を作った人は、あと何時間待てば入るかが分からなければ、いつ変更をやり直せばよいかが分からない。そこで、所有者は、止めた理由と、入るようになる時刻を、変更の PR の検査の結果で読めるようにしたい。

1. 最初の修正版に上げる変更が72時間待たずには入らないときは、その変更の PR の検査の結果に、止めた部品の名前と版と、止めた理由が出る。
2. 止めた理由が悪意のある部品の一覧に載っていたことでなければ、検査の結果に、止めた部品のその版が入るようになる時刻も出る。その時刻は、その版の公開から72時間経つ時刻である。
3. 止めた理由が悪意のある部品の一覧に載っていたことであれば、検査の結果に、一覧に載っていた部品の名前と版と、その部品を悪意のある部品として公表した記載が出る。
4. 1つの変更で2つ以上の部品を止めたときは、検査の結果に、止めたすべての部品が出る。
