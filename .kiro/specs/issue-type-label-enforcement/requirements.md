# 要件

## 元の要望
Issue #500: AI が起票する Issue に種類のラベルを必ず付け、ラベルの一覧をファイルで管理する

### きっかけ

AI が #490〜#499 をラベル無しで起票したことについて、所有者が「bugのラベル付けるべきではないですか」と指摘した。
「Issue起票時に適切なLabel付与するのを強制にしたい」(所有者、2026-10-06)

### やりたいこと

- Issue を起票するときに、適切なラベルを付けることを強制する。ラベルが適切かどうかは、AI が自分で判断する
- 強制するのは、AI の起票(file-issue・/request・分けた部分の Issue)と、振り返りの Issue(AIの提案を了承)
- ラベルの一覧を、リポジトリの中のファイルで管理する(AIの提案を了承)
- 種類のラベルに「保守」(依存やツールの版上げなど、不具合でも新機能でもないもの)を足す(AIの提案を了承)
- 一度も使われていないラベル duplicate・invalid・wontfix・good first issue・help wanted を消す(AIの提案を了承)

### どうなれば解決か

- 起票した Issue には、種類のラベル(bug・enhancement のように、何の Issue かを表すもの)が必ず1つ付いている(AIの提案を了承)
- 種類のラベルを付けずに起票しようとすると、起票できない(AIの提案を了承)

### やらないこと

- 定期実行が作る Issue、所有者が GitHub の画面で手で作る Issue、PR には、ラベルを強制しない(AIの提案を了承)

### 決めた方式

- ラベルの名前は英語にそろえ、種類のラベルの名前は `kind/`、変える場所のラベルの名前は `area/` で始める
- 種類のラベルは `kind/bug`・`kind/feature`・`kind/enhancement`・`kind/cleanup`・`kind/dependency`・`kind/documentation` の6つにする。「保守」は、作りの整理(`kind/cleanup`)と、依存やツールの版上げ(`kind/dependency`)の2つに分ける
- `kind/documentation` は、人が読む文書(README と `doc/`)だけを変える Issue に付ける。CLAUDE.md、スキル、spec など AI が読む文書の変更には付けない
- AI は、種類のラベルに加えて、変える場所のラベル(`area/app`・`area/infra`・`area/dev-platform`。2つ以上の場所を変えるときは、当たるものをすべて)を必ず付ける。場所のラベルが無い起票も止める(場所のラベルが要らない種類のラベルを除く)
- 消すラベルに `question` も加える
- ラベルの一覧のファイルを書き換えたPRが main に入ると、ワークフローが GitHub のラベルをファイルのとおりに変える。ファイルに無いラベルは、所有者が画面で手で足したものも消す(AIの提案を了承)
- 振り返りの Issue に付ける `retrospective` は、種類のラベルの1つにする。振り返りの Issue には、場所のラベルを付けない
- ラベルの一覧のファイルには、種類のラベルごとに、場所のラベルが要るかどうかと、AI がそのラベルを選ぶときの決まりを書く。場所のラベルが要らない種類を足すときや、選ぶときの決まりを変えるときは、ファイルだけを書き換える

## はじめに

Claude は、これまで Issue をラベル無しで起票することがあった。そこで、Claude が起票する Issue に、種類を表すラベルと、種類によっては変える場所を表すラベルを必ず付けさせる。

Claude は、要件を決める会話(2026-10-13)で所有者が決めたことを、所有者の了承を得て、Issue の本文の「決めた方式」の節に書き足した。Issue の本文の「決めた方式」の節は、「やりたいこと」の節に書かれた「保守」のラベルと、消すラベルの一覧を改めている。種類のラベルの名前の付け方は、所有者が Kubernetes の付け方(種類のラベルに `kind/`、場所のラベルに `area/` を付ける)を調べた結果を見て選んだ。

## 範囲

- この spec で決めること: ラベルの一覧のファイルに書くラベルと、その意味。ファイルを書き換えたときに GitHub のラベルが変わる動き。Claude が起票のときにラベルを選ぶ決まり。ラベルが足りない起票を止める動き
- この spec で決めないこと: 今ある Issue に、ラベルを付け直すこと。たとえば、今ラベルの付いていない Issue に種類と場所のラベルを付けることと、今 `enhancement` が付いている Issue のうち新しい機能の Issue を `kind/feature` に付け替えることは、この spec では行わない。PR に付くラベルの意味と、PR にラベルを付ける仕組み(Dependabot、ワークフロー、`/review-loop`)の動き。ラベルの色
- この spec が前提にしていること: GitHub のラベルは、Issue と PR で共通の1つの一覧である。そのため、PR に付くラベルも、ラベルの一覧のファイルに書く

## 要件

### 要件1 ラベルの一覧を1つのファイルに書く

所有者は、ラベルの決め方を、これからも何度も変えていくと考えている。ラベルが GitHub の画面とスキルの文書に散らばっていると、変えるたびにいくつもの場所を直すことになる。そこで、ラベルの一覧をリポジトリの中の1つのファイルに書き、そのファイルを、どのラベルがあるかの唯一の基準にする。

1. GitHub のラベルは、すべてリポジトリの中のファイル1つに書かれている。ファイルには、ラベルごとに、名前と、GitHub の画面に出す説明と、色と、そのラベルがどの組に入るかが書かれている。組は、種類のラベル、場所のラベル、そのほかのラベルの3つである。ラベルには、Claude がそのラベルを選ぶときの決まりを書ける。種類のラベルには、加えて、そのラベルを付ける Issue に場所のラベルが要るかどうかが書かれている。
2. ファイルに最初に書く種類のラベルは、次の7つとする。それぞれのラベルの説明の欄には、表の意味の列の文が書かれる。場所のラベルの列は、そのラベルを付ける Issue に場所のラベルが要るかどうかである。選ぶときの決まりの列が空のラベルには、選ぶときの決まりが書かれない。

   | ラベル | 意味 | 場所のラベル | 選ぶときの決まり |
   |---|---|---|---|
   | `kind/bug` | 今ある機能が本来の動きをしていないので、本来の動きに直す | 要る | |
   | `kind/feature` | 利用者や所有者が、今はできないことをできるようになる | 要る | |
   | `kind/enhancement` | 今ある機能の動きや見た目を、意図して変えてよくする | 要る | |
   | `kind/cleanup` | 見える動きを変えずに、作りを整理する、または使っていないものを消す | 要る | |
   | `kind/dependency` | 依存やツールの版を上げる | 要る | |
   | `kind/documentation` | 人が読む文書(README と `doc/` の下の文書)だけを変える | 要る | README と `doc/` の下の文書だけを変える Issue に付ける。コードや仕組みの変更に合わせて文書も直す Issue と、CLAUDE.md・スキル・steering・spec のように Claude が読んで動きを決める文書を変える Issue には付けない |
   | `retrospective` | ゲートすり抜けの振り返り(月次監査の棚卸し対象) | 要らない | 振り返りの手順(`/retrospective`)で起票する Issue にだけ付ける |

   `retrospective` の説明は、Claude が今の振り返りの手順に従ってラベルを作るときに付ける説明と同じである。

3. ファイルに最初に書く場所のラベルは、次の3つとする。それぞれのラベルの説明の欄には、表の意味の列の文が書かれる。

   | ラベル | 意味 |
   |---|---|
   | `area/app` | 利用者が使う画面・API・データベースの中身 |
   | `area/infra` | アプリを動かす本番の AWS の環境 |
   | `area/dev-platform` | Claude が開発を進めるための手順・品質チェック・CI・監査と、開発環境 |

4. ファイルに最初に書くそのほかのラベルは、今の GitHub にある `blocked`、`audit`、`container-vuln`、`canary`、`pre-merge-check`、`migration`、`codex-overruled`、`dependencies`、`java`、`javascript`、`python`、`docker`、`github_actions` とする。これらのラベルの説明は、今の GitHub の説明と同じである。
5. 今の GitHub にある `bug`、`enhancement`、`documentation` は、ファイルではそれぞれ `kind/bug`、`kind/enhancement`、`kind/documentation` に名前を変えたラベルとして書かれる。
6. 今の GitHub にある `duplicate`、`invalid`、`wontfix`、`good first issue`、`help wanted`、`question` は、ファイルに書かれない。

### 要件2 ファイルを書き換えると GitHub のラベルがファイルのとおりになる

所有者は、ラベルを変えたいときにすることを、ファイルを書き換えることだけにしたい。所有者が GitHub の画面でラベルを1つずつ作ったり消したりする手間を無くすため、ファイルの変更が main に入ったら、ワークフローが GitHub のラベルを自動でファイルのとおりにする。

1. ラベルの一覧のファイルを書き換えたPRが main に入ったら、ワークフローは、GitHub のラベルをファイルのとおりにする。ワークフローは、ファイルにあって GitHub に無いラベルを作り、説明か色がファイルと違うラベルを直し、GitHub にあってファイルに無いラベルを消す。
2. ワークフローは、所有者が GitHub の画面で手で足したラベルも、ファイルに書かれていなければ消す。
3. 所有者か Claude がファイルで、あるラベルの古い名前と新しい名前を書いたときは、GitHub に古い名前のラベルが残っている限り、ワークフローはどの実行でも、そのラベルを消して作り直さずに、名前だけを変える。ワークフローは、古い名前のラベルを、ファイルに無いラベルとして消さない。main に入ったときの実行が失敗し、あとで所有者が手で動かした実行でも、ワークフローは同じく名前だけを変える。名前を変えたラベルは、付いていた Issue と PR に付いたまま残る。たとえば、今 `bug` が付いている Issue には、名前が変わったあとも `kind/bug` が付いている。
4. ワークフローが消したラベルは、付いていた Issue と PR からも外れる。たとえば、今 `question` が付いている #409 と #410 からは、`question` が外れる。
5. ワークフローがファイルを読めないとき、またはファイルにラベルが1つも書かれていないときは、ワークフローは GitHub のラベルを1つも変えずに失敗として終わる。ファイルの誤りで GitHub のラベルがすべて消えることを防ぐためである。
6. ワークフローが失敗として終わったら、所有者は GitHub の Actions の画面で失敗を見られる。
7. 所有者は、ファイルを書き換えなくても、ワークフローを手で動かして、GitHub のラベルをファイルのとおりにし直せる。

### 要件3 Claude は起票する Issue に種類のラベルと場所のラベルを付ける

所有者は、GitHub の Issue の一覧で、種類のラベルと場所のラベルを組み合わせて絞り込み、たとえば「アプリの不具合」や「開発の仕組みの新しい機能」だけを見たい。そのため、Claude は、起票する Issue に種類のラベルを1つ付け、その種類のラベルが場所のラベルを要るときは、場所のラベルを1つ以上付ける。どのラベルが適切かは、Claude がラベルの一覧のファイルの説明と選ぶときの決まりを読んで判断する。

1. Claude が Issue を起票するときは、Claude は、ラベルの一覧のファイルにある種類のラベルの中から1つだけを選んで付ける。
2. Issue が2つ以上の種類に当てはまりそうなときは、Claude は、本文の「どうなれば解決か」に書かれた一番の目的に合う種類のラベルを1つ選ぶ。本文に「どうなれば解決か」の節が無いときは、Claude は「やりたいこと」の節に書かれた一番の目的で選ぶ。たとえば、新しい仕組みを足すことと、本来の動きをしていないものを直すことの両方を含み、きっかけが本来の動きをしていないことである Issue には、Claude は `kind/bug` を選ぶ。
3. ラベルの一覧のファイルで、ラベルに選ぶときの決まりが書かれているときは、Claude はその決まりに従ってそのラベルを付けるかどうかを決める。Claude の起票の手順(スキル)には、ラベルごとの選ぶときの決まりを書かない。Claude は、選ぶときの決まりを、起票のたびにラベルの一覧のファイルから読む。
4. 選んだ種類のラベルが場所のラベルを要るときは、Claude は、ラベルの一覧のファイルにある場所のラベルの中から、Issue が変える場所に当たるものを付ける。選んだ種類のラベルが場所のラベルを要らないときは、Claude は場所のラベルを付けない。Issue が2つ以上の場所を変えるときは、Claude は、当たる場所のラベルをすべて付ける。たとえば、本番の AWS の環境と画面の両方を変える Issue には、Claude は `area/infra` と `area/app` の2つを付ける。
5. 次の起票のどれでも、Claude は、1から4と同じく、ラベルの一覧のファイルから種類のラベルを1つ選び、その種類のラベルが場所のラベルを要るときは場所のラベルも選んで付ける。
   - Claude が起票の決まり(`file-issue`)に従って起票するとき。この起票には、`/request` の最後の起票も含まれる
   - Claude が1つの Issue を分けて、分けた部分の Issue を起票するとき。この起票には、所有者が了承した分け方で分けるときと、実装の途中で小さく分けるときの両方が含まれる
   - Claude が振り返りの手順(`/retrospective`)で起票するとき。このとき、Claude は種類のラベルとして `retrospective` を付ける
6. Claude は、起票の前に所有者に起票の案を見せるときに、題名と本文とあわせて、付けるラベルを見せる。所有者がラベルを直すよう言ったら、Claude は、所有者が言ったラベルに直してから起票する。
7. 所有者に案を見せずに起票するとき(実装の途中で小さく分けるとき)は、Claude は、起票したあとに所有者に示す Issue の番号と題名とあわせて、付けたラベルを示す。

### 要件4 ラベルが足りない起票は止まる

Claude がラベルを付け忘れても、その起票が行われる前に止まらなければ、ラベルの無い Issue が残る。Claude が決まりを読み飛ばしても決まりが守られるように、ラベルが足りない起票は、Claude の判断によらず止まる。

1. Claude が種類のラベルを付けずに Issue を起票しようとしたら、起票は行われない。Claude には、起票を止めた理由と、ラベルの一覧のファイルにある種類のラベルの一覧が示される。
2. Claude が種類のラベルを2つ以上付けて Issue を起票しようとしたときも、1と同じく起票は行われない。
3. Claude が、場所のラベルを要る種類のラベルを付けて、場所のラベルを付けずに Issue を起票しようとしたら、起票は行われない。場所のラベルを要らない種類のラベルを付けた起票は、場所のラベルが無くても止まらない。Claude には、起票を止めた理由と、ラベルの一覧のファイルにある場所のラベルの一覧が示される。
4. 起票を止めるかどうかは、そのときのラベルの一覧のファイルに書かれた種類のラベルと場所のラベルと、種類のラベルごとの場所のラベルが要るかどうかで決まる。所有者か Claude がファイルで種類や場所のラベルを足したり、名前を変えたり、消したり、場所のラベルが要るかどうかを変えたり、選ぶときの決まりを書いたり変えたり消したりしたら、Claude が選べるラベルと、Claude がラベルを選ぶときの決まりと、起票を止めるときの判定も、ファイルのとおりに変わる。そのために、所有者と Claude がラベルの一覧のファイルのほかに直すファイルは無い。
5. 起票しようとしたときにラベルの一覧のファイルを読めなければ、起票は行われない。Claude には、ファイルを読めないので起票を止めたことが示される。
6. 次の Issue と PR は、起票を止める対象にしない。
   - 定期実行のワークフローが作る Issue
   - 所有者が GitHub の画面か所有者自身の端末で作る Issue
   - PR
7. すでにある Issue のラベルを付け替えることは、起票を止める対象にしない。
