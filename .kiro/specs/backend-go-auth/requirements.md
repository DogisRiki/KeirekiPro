## はじめに

Issue #445 で、所有者は、backend を Java と Spring Boot から Go に置き換えると決めた。置き換えの進め方と、Go 版が守ることは、spec `backend-go-replacement` が決めている。この spec では、spec `backend-go-replacement` を「置き換えの spec」と呼ぶ。置き換えの spec は、機能のまとまりごとの Go 版を、まとまりごとの別の spec で作ると決めた。この spec は、そのうち認証のまとまりを受け持ち、Issue #770 の「やりたいこと」に挙げた13の操作の Go 版を作る。この spec では、この13の操作を「認証の操作」と呼ぶ。

Claude は、5つのまとまりの中で、認証のまとまりの Go 版を最初に作る。利用者、マスタと経歴書、出力、バックアップのまとまりの操作は、どれもログインした利用者だけが使える。そのため、ほかのまとまりの Go 版は、この spec で作るログインの状態の検査が無いと、Java 版と同じ答えを返せない。

この spec の「所有者」「Java 版」「Go 版」「利用者」「画面」「切り替え」は、置き換えの spec と同じものを指す。「ログインの状態」は、ログインした利用者のブラウザが Cookie に持ち、要求ごとに backend に送る値を指す。「筋書き」は、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査が、版に送る要求の並びと、期待する答えを書いたものを指す。

Issue #770 の「どうなれば解決か」は、認証の操作について、置き換えの spec の22の受入基準を満たすことを求めている。置き換えの spec は、まとまりごとの spec に置き換えの spec の要件を書き写さず、当てはまる要件を指すと決めている。そこで、この spec は、22の受入基準のそれぞれを、次の表のとおりに受け持つ。表で「置き換えの spec のとおり」とした受入基準は、認証の操作に固有の決めごとが無い。Claude は、その受入基準を、置き換えの spec の文のとおりに認証の操作に当てはめる。

## 範囲

- この spec で決めること: この spec では、次の3つを決める。
  - 認証の操作の Go 版。認証の操作には、新規の登録、メールアドレスの確認、ログイン、2段階認証、ログインを続けるための作り直し、ログアウト、パスワードの再設定、Google か GitHub のアカウントでのログインがある
  - ほかのまとまりの操作のうちログインの要る操作について、Go 版が、操作の前にログインの状態を確かめる検査
  - 認証の操作について、Java 版と Go 版を比べる検査と、版をまたいで確かめる検査に足す筋書き
- この spec で決めないこと: この spec では、次の4つを決めない。
  - ほかのまとまりの操作の Go 版。たとえば、Claude は、ログインしたあとのメールアドレスの変更、パスワードの変更、退会、Google か GitHub のアカウントのつなぎの解除の Go 版を、利用者のまとまりの spec で作る
  - ほかのサイトから送られた偽の要求を断る検査。この検査は、置き換えの spec で作ってある
  - 認証の機能を足すことと、認証の仕様を変えること。Issue #445 の「やらないこと」で、所有者が、置き換えでは機能を足さず、仕様も変えないと決めたためである
  - 本番の切り替え。本番の切り替えは、置き換えの spec が受け持つ
- この spec が前提にしていること: この spec は、次の3つを前提にする。
  - 次の5つは、置き換えの spec の段階2で作られ、main に入っている。Go 版の土台、Java 版と Go 版を比べる検査、版をまたいで確かめる検査、検査で本物の Google と GitHub の代わりに使う偽のログインのサービス、検査で AWS の代わりに使う偽のサービスである
  - 認証の操作の API の仕様書は、置き換えの spec で、今の Java 版から作られ、main に入っている
  - Claude は、置き換えの spec の設計を書く前に、次の7つの動きを試しに作り、Java 版と Go 版のどちらの向きでも同じになることを確かめた。
    - 保存されたパスワードの照合
    - ログインの状態の値
    - メールアドレスの確認のリンクの値
    - Cookie の書き方
    - 偽の要求を見分ける値
    - ログインを続けるための値とログアウト
    - 2段階認証の途中の記録
  - 一方で、Claude は、置き換えの spec の設計を書く前には、次の4つを試しに作っていない。
    - Google か GitHub のアカウントでのログインの一連の手順
    - パスワードの再設定
    - 確認のメールを送り直せる間隔の制限
    - メールの件名と本文

## 要件

### 要件1 認証の操作を、今の画面を直さずに Go 版で使えるようにする

切り替えのあとも、利用者は、今の画面で登録し、ログインする。Go 版の答えが Java 版と少しでも違うと、画面はエラーを出すか、利用者をログインさせられない。たとえば、Cookie の名前か性質が1つ違うだけで、ブラウザはログインの状態を送らなくなり、利用者はログインできなくなる。そこで、Go 版は、認証の操作に、Java 版と同じ答えを返す。

1. Go 版は、認証の操作の要求に、Java 版と同じ HTTP の状態の番号、同じ本文、同じ Cookie の名前と性質で答える。同じかどうかの正解は、今の Java 版が実際に返す答えとする。
2. 利用者は、今の画面で、Go 版を相手に、新規の登録、メールアドレスの確認、ログイン、2段階認証、ログアウトを終えられる。パスワードを忘れた利用者は、今の画面で、Go 版からパスワードの再設定のメールを受け取り、新しいパスワードを設定してログインできる。
3. 利用者は、今の画面から、Google か GitHub のアカウントで Go 版にログインできる。ログインが終わったときと、ログインに失敗したときに、ブラウザは、Java 版と同じ画面に移り、Java 版と同じ文言を見せる。
4. Go 版は、認証の操作で、入力の誤りとして断る条件と、画面に出るエラーの文言を、Java 版と同じにする。
5. Go 版は、認証の操作で送るメールの件名と本文を、Java 版と同じにする。認証の操作が送るメールは、メールアドレスの確認、パスワードの再設定、2段階認証の確認のコード、新規の登録の完了の4種類である。

### 要件2 ほかのまとまりの操作の前で、ログインの状態を Java 版と同じに確かめる

ほかのまとまりの操作は、ログインした利用者だけが使える。Claude は、ほかのまとまりの spec で Go 版を作るときに、この spec で作るログインの状態の検査を使う。この検査の答えが Java 版と違うと、画面は、ログインの状態が切れた利用者のログインを続けられないか、利用者をログインの画面に戻せない。また、この検査が Java 版より緩いと、ログアウトした利用者のログインの状態で、ほかの人が操作できてしまう。

1. ログインの要る操作に、ログインの状態を持たない要求が届いたら、Go 版は、その要求を Java 版と同じ答えで断る。ログインの要る操作とは、API の仕様書の操作のうち、経路が `/api/auth` の下に無いものである。Go 版は、Java 版と同じく、生きているかの確認の要求と、ブラウザが本来の要求の前に送る `OPTIONS` の要求には、ログインの状態を求めない。
2. ログインの要る操作に、次の3つのどれかの要求が届いたときも、Go 版は、その要求を Java 版と同じ答えで断る。断るときに Java 版が Cookie を消すなら、Go 版も同じ Cookie を消す。
   - ログインの状態の有効な時間が過ぎた要求
   - ログインの状態の値を書き換えた要求
   - ログアウトか、パスワードの再設定によって使えなくなったログインの状態を持つ要求
3. Go 版のログインの状態の検査は、Java 版と同じく、要求を送った利用者がまだ居るかを確かめない。Java 版では、退会した利用者の要求は、ログインの状態の検査を通り、その先の操作ごとの処理で断られる。そのため、Claude は、すでに居ない利用者の要求を断る答えを、その操作を作るまとまりの spec で、Java 版と同じにする。
4. Claude は、ほかのまとまりの spec で Go 版を作るときに、ログインの状態の検査を作り直さず、この spec で作った検査をそのまま使う。

### 要件3 今あるセキュリティの対策を弱めない

認証の操作は、利用者のアカウントを守る。Go 版で今あるセキュリティの対策が弱まると、ほかの人が利用者のアカウントに入れるおそれがある。しかも、利用者は、今あるセキュリティの対策が弱まったことに画面で気づけない。そこで、Go 版は、今あるセキュリティの対策を、Java 版と同じに守る。

1. Go 版は、ログインの状態の有効な時間と、ログインし直さずに使い続けられる時間を、Java 版と同じにする。
2. 2段階認証を有効にした利用者を、Go 版は、メールで届いた確認のコードを入れるまでログインさせない。Go 版は、確認のコードの有効な時間と、誤ったコードを入れられる回数の上限を、Java 版と同じにする。
3. Go 版は、パスワードの再設定のリンクとメールアドレスの確認のリンクについて、有効な時間と、1回しか使えないことを、Java 版と同じに守る。新しい確認のリンクを送ると前の確認のリンクが使えなくなることも、Go 版は Java 版と同じに守る。
4. Go 版は、同じメールアドレスに確認のメールを送り直せる間隔の制限を、Java 版と同じに守る。
5. 利用者がログアウトしたときと、パスワードを再設定したときに、Go 版は、Java 版と同じく、その利用者のほかの端末のログインの状態も使えなくする。
6. ログインに失敗したときに、Go 版は、Java 版と同じく、アカウントが無いのかパスワードが違うのかを答えから見分けられないようにする。パスワードの再設定を求められたときも、Go 版は、Java 版と同じく、そのメールアドレスのアカウントがあるかを答えから見分けられないようにする。
7. Google か GitHub のアカウントでログインするときに、Go 版は、Java 版と同じく、Google か GitHub が確認済みとしたメールアドレスだけを使う。Go 版は、Google か GitHub から戻ってきた要求が、同じブラウザが始めたログインと組になっていることを、Java 版と同じに確かめる。

### 要件4 ログインの状態と途中の手順の記録を版の間で引き継ぎ、版をまたいでも操作を終えられる

切り替えの出荷の途中では、Java 版と Go 版の両方が利用者の操作を受けるので、同じ利用者の続けた要求が、別々の版に届くことがある。一方の版の記録をもう一方の版が読めないと、利用者は、ログインし直すことになるか、登録やパスワードの再設定を途中からやり直すことになる。そこで、Go 版は、ログインの状態と途中の手順の記録を、Java 版と互いに読めるようにする。

1. 一方の版でログインした利用者は、もう一方の版でも、ログインし直さずに使い続けられる。ログインを続けるための作り直しも、どちらの版で受けても成功する。一方の版でログアウトした利用者のログインの状態は、もう一方の版でも使えない。
2. 利用者は、次の5つの操作を、1つ目の要求と2つ目からの要求が別々の版に届いても、最後まで終えられる。どちらの版に届いた登録も、切り替えのあとに残っている。
   - 2段階認証の、ログインと、確認のコードの入力
   - 新規の登録の、登録と、メールアドレスの確認
   - 確認のメールの送り直しと、送り直したリンクでのメールアドレスの確認
   - パスワードの再設定の、再設定の申し込み、リンクの確認、新しいパスワードの設定
   - Google か GitHub のアカウントでのログインの、ログインの開始と、Google か GitHub から戻ったあとの処理
3. Claude は、途中の手順をまたぐ5つの操作と、ログインしたままの利用者の操作のそれぞれについて、Java 版から Go 版への向きと、Go 版から Java 版への向きの両方の筋書きを、版をまたいで確かめる検査に足す。この検査は CI で動く。この検査が通らない PR は、main に入らない。

### 要件5 Java 版と Go 版を比べる検査で、認証の操作の答えと残したものが同じことを確かめる

人はコードを読まないので、Claude は、Go 版が Java 版と同じかを、機械で確かめる。認証の操作は、答えのほかに、Cookie、データベース、ログインの状態の保存先、送ったメールに結果を残す。答えだけを比べると、Claude は、保存したものの違いやメールの違いを見落とす。そこで、Claude は、Java 版と Go 版に同じ要求を送り、答えと残したものの両方を比べる。

1. Claude は、認証の操作のすべてについて、Java 版と Go 版を比べる検査の筋書きを書く。筋書きには、画面が送る正しい要求に加えて、次の要求を含める。
   - 入力に誤りのある要求
   - 期限の切れたリンクと、使い終わったリンクの要求
   - 2段階認証の誤ったコードの要求と、誤りの回数が上限に達する要求
   - 確認のメールを送り直せる間隔の制限に当たる要求
   - ログインの状態が切れたあとの要求と、ログアウトしたあとの要求
   - 偽の要求を見分けるヘッダを付けない要求
2. Java 版と Go 版を比べる検査は、答えに加えて、データベースとログインの状態の保存先に残ったものと、送ったメールの宛先と件名と本文を比べる。
3. Claude は、Google か GitHub のアカウントでのログインを、偽のログインのサービスを使って比べる。比べる場面には、次の4つを含める。
   - 初めてログインする利用者がログインするとき
   - 登録済みのアカウントに Google か GitHub のアカウントをつなぐ利用者がログインするとき
   - 確認の済んでいないメールアドレスを持つアカウントでログインするとき
   - Google か GitHub がログインを断ったとき

   Google と GitHub は利用者のメールアドレスを別々のやり方で返すので、Claude は、Google と GitHub の両方を比べる。
4. 確認のコード、リンクの値、ログインの状態の値のように、要求のたびに違う値になるものについて、Java 版と Go 版を比べる検査は、値が違うことでは PR を止めない。Java 版と Go 版を比べる検査は、その値の形が Java 版と同じかを確かめる。
5. 認証の操作には、Java 版がサーバの誤りとして状態の番号 500 で答えている、形の誤った要求がある。Go 版は、このような要求に、要求の誤りとして状態の番号 400 で答える。たとえば、Google と GitHub のどちらでログインするかの指定が無い要求がある。画面はこのような要求を送らないので、この違いは利用者の目に触れない。Claude は、答えを変えた要求を、変えた動きの一覧に1つずつ載せる。
6. 置き換えの spec は、主な操作の応答にかかる時間を Java 版と Go 版で測って比べると決めている。Claude は、認証の操作では、ログイン、2段階認証の確認のコードの入力、ログインを続けるための作り直し、新規の登録の4つを、主な操作として測る。

### 要件6 API の説明画面からログインして、ログインの要る API を試せる

開発者は、開発環境の API の説明画面の「Try it out」で、Go 版に要求を送って答えを確かめる。ログインの要る API を試すには、開発者は、先に説明画面でログインしなければならない。置き換えの spec では、Go 版のログインの API が未実装の答えを返していたので、Claude は、説明画面でログインできることを確かめられなかった。そこで、この spec で、説明画面でのログインを確かめる。

1. 開発者は、開発環境の API の説明画面の「Try it out」で、Go 版のログインの API を呼び、ログインできる。
2. ログインした開発者が「Try it out」でログインの要る API に要求を送ると、Go 版は、その要求をログインの状態の検査で断らず、その操作の処理に渡す。この spec が main に入る時点では、ほかのまとまりの操作の Go 版はまだ無い。そのため、Go 版は、ほかのまとまりの操作に「未実装です。」の答えを返す。そこで、Claude は、開発者がログインする前は、Go 版がログインが要ることを示す答えで要求を断ることを確かめる。Claude は、開発者がログインしたあとは、Go 版の答えが「未実装です。」に変わることで、ログインした開発者の要求が操作の処理まで届いたことを確かめる。
3. Claude は、ログインした開発者の要求に Go 版がログインした開発者への答えを返すことを、利用者のまとまりの spec で確かめる。置き換えの spec の進み具合の表の下には、この確認を認証のまとまりの spec で行うという決まりがある。Claude は、その決まりを、ログインの状態の検査を通ることはこの spec で確かめ、ログインした開発者への答えは利用者のまとまりの spec で確かめる、と書き直す。

### 要件7 Java 版と同じにできるかを設計の前に試し、進み具合を表に書く

Claude が、設計を書いたあとや作り終えたあとに、Go 版の動きを Java 版と同じにできないと分かると、所有者は spec を承認し直すことになる。そこで、Claude は、確かめていない動きを設計の前に試し、Java 版と同じにできないと分かったら止まって所有者に報告する。

1. Claude は、この spec の設計を書く前に、Claude が置き換えの spec でまだ試しに作っていない認証の動きを試しに作り、Java 版と同じになるかを確かめる。試しに作る動きには、少なくとも、Google か GitHub のアカウントでのログインの一連の手順、パスワードの再設定、確認のメールを送り直せる間隔の制限、4種類のメールの件名と本文を含める。Claude は、試しに作った方法と結果を、この spec の research.md に書く。
2. 試しに作った結果、Java 版と同じにできない動きが見つかったら、Claude は、設計を書く前に止まる。Claude は、何が同じにならないかと、その違いが利用者に何をもたらすかを、所有者に報告する。
3. Claude は、置き換えの spec の進み具合の表の、認証のまとまりの行に、この spec の場所と、まとまりの状態を書く。Claude は、状態を、作り終えたら「作り終えた」にし、Java 版と Go 版を比べる検査に通ったら「比べる検査に通った」にする。
