# 調査と設計の判断の記録

## まとめ

- 機能: `email-ownership-verification`
- 調べた範囲: 今の仕組みを広げる変更(Complex Integration)。登録、ログイン、パスワードの再設定、外部連携、ユーザー設定、メールの送信、DB と Redis にまたがる
- 設計を決めた主な事実:
  - 確認前の登録は、アカウントができる前のデータで、期限が来たら消える。Redis の有効期限で持てば、定期実行の仕組みを足さずに消せる。backend には今、定期実行(`@Scheduled`)の仕組みが無い
  - 確認のリンクは、期限が切れたあとも、どのメールアドレスへの、どの種類のリンクだったかを読めないと、送り直すボタンと、確認が済んでいることの表示を出し分けられない。署名付きのトークンに中身を持たせれば、保存した記録の消える時期に縛られない
  - ブラウザは、URL の fragment(`#` より後ろ)を、サーバーへの要求にも Referer にも載せない。確認のリンクのトークンを fragment に置けば、トークンは、利用者のブラウザと確認の API のほかに渡らない

## 調べたこと

### Google が返すメールアドレス

- きっかけ: 要件7は、Google が持ち主を確かめたメールアドレスだけを受け取ると決めている
- 調べた資料: Google の OpenID Connect の文書(下の参考資料)
- 分かったこと:
  - ID トークンの `email_verified` は、Google がそのメールアドレスを確かめたときに true になる
  - Google は、利用者を見分ける値に `email` ではなく `sub` を使うよう求めている
  - `backend/.../infrastructure/auth/oidc/provider/GoogleOidcProvider.java` は、`email_verified` が true でないときに email を null にして返す
- 設計への影響: Google の側は変えない。外部連携と利用者の対応は、今と同じく `sub`(`provider_user_id`)で探す

### GitHub が返すメールアドレス

- きっかけ: 要件7.4 は、持ち主を確かめていないメールアドレスを受け取らないと決めている
- 調べた資料: GitHub の REST API の文書 `GET /user/emails`(下の参考資料)
- 分かったこと:
  - `GET /user/emails` は、要素ごとに `email` `primary` `verified` `visibility` を返す
  - OAuth アプリのトークンでこの API を呼ぶには、`user:email` の scope が要る。今の scope は `read:user user:email` で、足りている
  - `GET /user` の `email` は、利用者がプロフィールに公開したメールアドレスで、`verified` を持たない
- 設計への影響: `GithubOidcProvider` は、いつも `GET /user/emails` を呼び、`primary` と `verified` がどちらも true の要素の `email` だけを返す。該当する要素が無ければ email を null にする

### 今の登録とログインの流れ

- きっかけ: 登録を「確認を済ませてからアカウントを作る」形に変えるため、今の流れのどこを差し替えるかを確かめた
- 調べたファイル: `UserRegistrationUseCase` `UserRegisteredEventListener` `LoginUseCase` `LoginController` `RequestPasswordResetUseCase` `ResetPasswordUseCase` `SetEmailAndPasswordUseCase` `OidcLoginUseCase` `HandleOidcCallbackUseCase` `OidcCallbackController` `User`
- 分かったこと:
  - 登録は1つのトランザクションでユーザーを保存し、同期のイベントのリスナーが登録完了のメールを送る。メールの送信に失敗すると、登録も取り消される
  - ログインは Spring Security の認証の仕組みを使わず、`LoginUseCase` がパスワードを照らす。2段階認証が有効なら 202 を返す
  - パスワードの再設定のトークンは、32バイトの乱数を Base64URL にした文字列で、Redis の `password-reset:{token}` に10分の有効期限で置く。確かめる API はトークンを消さず、再設定の API が消す
  - `User.reconstruct` は、2段階認証が有効なのにメールアドレスかパスワードが無いアカウントを読み込みで断る
  - 外部連携の戻り先は、失敗したときに `{frontend}/login?error=<文>` へ送る。frontend のログインの画面は、今は `error` のクエリを読まない
- 設計への影響:
  - 確認前の登録は users の表に入れず、Redis に置く。アカウントは確認を済ませた時点で作る
  - `User.reconstruct` の条件は強めない。前からあるアカウントは確認前になるので、条件を「確認済みのメールアドレス」に強めると、2段階認証が有効なアカウントを読み込めなくなる
  - ログインの画面は、`error` のクエリの決まった符号だけを読み、符号ごとに決まった文を出す。クエリの文をそのまま画面に出すと、他人が作ったリンクで任意の文を出せてしまう

### frontend の受け方

- きっかけ: 確認前の人のログインに、どの応答を返すかを決めるため
- 調べたファイル: `frontend/src/lib/axiosInterceptors.ts` `features/auth/hooks/useLogin.ts` `routes/AppRouter.tsx` `config/paths.ts`
- 分かったこと:
  - 共通のインターセプタは、400 と 404 を画面の上の帯(ErrorBanner)に出し、403 で強制的にログアウトさせ、500 でトーストを出す。それ以外の状態の番号は、呼んだフックにそのまま渡す
  - `PublicLoader` の下の画面は、ログインしていると職務経歴書の一覧へ移る
- 設計への影響:
  - 確認前の人のログインには 409 を返す。403 を使うと強制のログアウトが走る。400 にすると帯に文が出るだけで、ボタンを出す分け方ができない
  - 確認のリンクの画面は、利用規約の画面と同じく、loader の無い経路に置く。ログインしたままの人がリンクを押しても、確認の画面が出るようにするためである

### java-jwt の署名と検証

- きっかけ: 確認のリンクのトークンを、すでに使っている java-jwt(版 4.6.2)で作れるかを確かめた
- 調べた資料: java-jwt の文書(下の参考資料)
- 分かったこと:
  - `JWT.create()` で `aud` `jti` `sub` と任意の claim を付けて `Algorithm.HMAC256` で署名できる
  - `JWT.require(alg).withAudience(...).build().verify(token)` は、`exp` `nbf` `iat` の検査を、その claim があるときだけ行う
- 設計への影響: トークンに `exp` を付けず、リンクの期限を独自の claim に入れる。期限が切れたトークンでも、署名を確かめたうえで中身を読める。アクセストークンと同じ鍵で署名すると、確認のトークンをアクセストークンとして出されたときに受け付けてしまうおそれがあるので、`jwt.secret` から用途ごとの鍵を導いて使う

## 比べた方式

| 方式 | 中身 | 良い点 | 弱い点 | 判断 |
|---|---|---|---|---|
| 確認前の登録を DB の表に置く | `pending_registrations` の表を足す | 再起動で消えない | 期限で消すために定期実行の仕組みが要る。表の追加でマイグレーションが増える | 採らない |
| 確認前の登録を Redis に置く | 登録ごとのキーに有効期限を付ける | 期限で自然に消える。パスワードの再設定のトークンと同じ置き場所 | Redis を作り直すと、確認前の登録が消える | 採る |
| リンクのトークンを乱数にし、記録を Redis に置く | 今のパスワードの再設定と同じ形 | 今の作りと同じ | 記録の有効期限を過ぎると、どのメールアドレスへの、どの種類のリンクだったかが分からない。送り直すボタンと、確認が済んでいる表示を出し分けられない | 採らない |
| リンクのトークンを署名付きにする | 種類、対象、メールアドレス、期限をトークンに持たせる | 期限が切れたあとも中身を読める。新しいリンクで前のリンクを使えなくするための記録だけを Redis に置けばよい | 署名の鍵を扱う部品が1つ増える | 採る |

## 設計の判断

### 判断: 確認前の登録を Redis に置く

- きっかけ: 要件1.1、1.4、1.6
- 比べた案:
  1. DB の表に置く
  2. Redis に有効期限付きで置く
- 選んだ案: Redis の `pending-registration:{id}` に、メールアドレス、パスワードのハッシュ、ユーザー名、作った日時を JSON で置く。有効期限は、最後に送ったリンクの期限までとし、メールを送らずに受け付けたときは24時間とする。メールアドレスごとの登録の一覧を `pending-registration:email:{email}` の集合で持つ
- 理由: 期限で消すことを Redis の有効期限に任せられ、定期実行の仕組みを足さずに済む
- 引き換え: Redis が作り直されると、確認前の登録が消える。消えた人は、もう一度登録すれば済む
- 実装で確かめること: 集合に残った、消えた登録の ID を、読むときに取り除く

### 判断: 確認のリンクのトークンを署名付きにする

- きっかけ: 要件2.2、2.3、2.4、2.5
- 比べた案:
  1. 乱数のトークンと Redis の記録
  2. 署名付きのトークン(JWT)と、最新のリンクの ID だけを Redis に置く形
- 選んだ案: トークンは JWT で、`aud` に `keirekipro-email-verification`、`jti` に乱数の ID、`sub` に対象の ID(確認前の登録の ID か、アカウントの ID)を入れる。独自の claim に、種類(`purpose`)、メールアドレス(`email`)、リンクの期限(`lexp`、UNIX 秒)を入れる。対象ごとに最新のリンクの `jti` を Redis の `email-verification:current:{subjectId}` に置き、ほかの `jti` のリンクは新しいリンクで使えなくなったものとして扱う
- 理由: 期限が切れたあとも、種類とメールアドレスを読めるので、要件2.4 と 2.5 の出し分けがいつまでも成り立つ。使ったかどうかは、対象のアカウントのメールアドレスが確認済みかどうかで判断できるので、使ったことを別に記録しなくてよい
- 引き換え: 鍵を扱う部品が増える。鍵は `jwt.secret` から導くので、新しい秘密の値と基盤の設定は要らない。`jwt.secret` を替えると、送ったリンクはすべて使えなくなる
- 実装で確かめること: 確認前の登録から作るアカウントの ID を、登録の ID と同じにする。こうすると、登録のリンクが使われたかを、`sub` の ID のアカウントがそのメールアドレスを確認済みで持つかで判断できる

### 判断: パスワードの再設定に続く確認のあとの、再設定のトークンの期限(要件の審査で持ち越した R2-1-2)

- きっかけ: 要件2.1、9.2
- 比べた案:
  1. 再設定のトークンの期限を、確認のリンクの期限までの残りの時間にする
  2. 確認を受け付けた時点から新たに10分にする
- 選んだ案: 案1。確認を受け付けたら、`PasswordResetTokenStore.store(token, userId, リンクの期限 - 今)` で再設定のトークンを置く
- 理由: 今のパスワードの再設定は、メールを送ってから10分のうちに新しいパスワードを送れば済む。案1なら、メールを送ってから新しいパスワードを送るまでの時間が、今と同じく10分に収まる。案2では、確認のあとにさらに10分使えるので、メールを送ってから最大20分になる
- 引き換え: 期限の間際にリンクを押した人は、新しいパスワードを打つ時間が短い。今のパスワードの再設定のリンクを間際に押したときと同じである

### 判断: 送り直したリンクの種類を引き継ぐ(要件の審査で持ち越した R2-2-1)

- きっかけ: 要件2.4
- 選んだ案: 送り直すときは、押されたリンクのトークンの `purpose` をそのまま新しいトークンに入れる。リンクの期限は `purpose` ごとに決める(パスワードの再設定に続く確認は10分、ほかは24時間)。送り直したリンクをもう一度送り直しても、種類は変わらない
- 理由: 種類をトークンに持たせているので、送り直しの回数に関わらず同じ種類のリンクになる

### 判断: 同じメールアドレスへの送信を1分に1回に抑える

- きっかけ: 要件2.6、2.7、4.6、9.5
- 選んだ案: Redis の `email-verification:rate:{email}` を `SET NX EX 60` で置けたときだけ送る。置けなかったら送らない
- 理由: 1つの命令で「1分のうちに送ったか」の判定と記録ができ、複数のサーバーが同時に動いても1通に収まる

### 判断: users の表に足す列

- きっかけ: 要件4.1、5.1
- 選んだ案: `email_verified_at TIMESTAMP NULL`(NULL なら確認前)と `pending_email VARCHAR(255) NULL`(UNIQUE にしない)を足す
- 理由: 今ある行は `email_verified_at` が NULL になるので、マイグレーションの中でデータを書き換えずに要件5.1 が成り立つ。設定待ちのメールアドレスは、ほかのアカウントの設定待ちと同じでもよいので、一意の制約を付けない。確かめるときにアカウントの `email` の一意の制約で重複を止める

### 判断: 確認前の人のログインの応答

- きっかけ: 要件3.1、3.2、3.3
- 選んだ案: パスワードが合ったときだけ、409 と `{message, kind}` を返す。`kind` は、確認前の登録なら `PENDING_REGISTRATION`、確認前のメールアドレスを持つアカウントなら `UNVERIFIED_ACCOUNT_EMAIL` にする
- 理由: 共通のインターセプタが 409 を扱わないので、ログインのフックが自分で文とボタンを出せる

### 判断: 確認のあとに続けてパスワードの再設定の画面を出す方法

- きっかけ: 要件9.2
- 選んだ案: 確認の API が再設定のトークンを応答で返し、確認のリンクの画面が、同じ画面の中に今の `ResetPasswordForm` を出す。新しいパスワードは今の `POST /api/auth/password/reset` に送る
- 理由: 再設定のトークンを URL に載せずに済み、今の再設定の API と画面の部品をそのまま使える

### 判断: 外部連携のログインで、設定待ちのメールアドレスを確認済みに移す(design の審査で差し戻した D1-1-4)

- きっかけ: 要件7.2
- 選んだ案: `OidcLoginUseCase` が、結び付いたアカウントの `pendingEmail` と外部連携が返した `email` が同じなら、`findByEmail` でほかのアカウントが持っていないことを確かめてから `promotePendingEmail` を呼ぶ。ほかのアカウントが持っていれば、設定待ちのまま残す
- 理由: 確認のリンクを押したときと同じく、users の `email` の一意の制約の前に、ほかのアカウントが持っているかを見る。確かめたあとにほかのアカウントが同じメールアドレスを確認済みにすると、ログインが一度失敗するが、利用者がもう一度ログインすれば設定待ちのまま残してログインできる。この重なりはまれなので、ログインのトランザクションを分ける仕組みは作らない

### 一般化、採り入れ、簡単にすること

- 一般化: 確認のメールを送る4つの場面(登録、前からあるアカウント、設定待ち、パスワードの再設定に続く確認)を、`purpose` の違いだけで1つの送る部品と1つの確かめる API にまとめた
- 採り入れ: トークンの署名は、すでに使っている java-jwt を使う。1分の制限は Redis の `SET NX EX` を使う。新しいライブラリは足さない
- 簡単にすること: 確認前の登録を消す定期実行は作らない。使ったリンクの記録は作らない。設定待ちのメールアドレスの索引は作らない(設定待ちのメールアドレスで探す処理が無いため)

## 危ないことと対処

- 同じメールアドレスの確認前の登録を他人が大量に作ると、ログインで照らすパスワードのハッシュが増え、ログインが遅くなる。対処: ログインで照らすのは、そのメールアドレスの新しい順に5件までにする
- 2つの確認が同じメールアドレスで同時に通ると、2つのアカウントが同じメールアドレスを持とうとする。対処: users の `email` の一意の制約で2つ目の保存を断り、断った側には、そのメールアドレスをほかのアカウントが持つときの文を出す
- Redis が容量の上限に達して有効期限付きのキーを消すと、確認前の登録が早く消える。対処: 消えた登録のリンクを押した人には、もう一度登録するよう案内する文を出す。要件2.4 の、登録が消えていたときの扱いと同じになる
- 確認のメールの送信に失敗すると、確認前の登録だけが残る。対処: 送信に失敗したら、その登録と1分の記録を消し、500 を返す
