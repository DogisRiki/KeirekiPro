### 申告

**1. 確認を済ませるまでアカウントを作らない(確認前の登録はアカウントではない)** — はじめに(言葉の定義)、要件1

- Issue の記載: あり。「利用者がメールの中の確認の操作を済ませてから、そのメールアドレスをアカウントのメールアドレスとして扱う」(AIの提案を了承)。アカウントをいつ作るかは書かれていない
- 決めたこと: 確認前は「確認前の登録」として置き、確認を済ませたときにはじめてアカウントを作る。期限が切れたら登録を消す(要件1の1・2・6)
- 他にありえた選択肢: 登録の時点でアカウントを作り、メールアドレスを「確認前」の印付きで持たせる(前からあるアカウントに対する要件5と同じ形)
- 外れていた場合: 確認前の登録を保存する仕組み、期限切れで消す仕組み、ログインと再設定の分岐(要件3の1、要件9の3)が丸ごと作り直しになる

**2. 確認前の利用者をメールアドレスとパスワードでログインさせない** — 要件3

- Issue の記載: あり。「確認の操作を済ませていないメールアドレスは、どの機能でも、アカウントのメールアドレスとして扱われない」。ログインを断るとは書かれていない
- 決めたこと: 確認前の登録も、前からあるアカウントの確認前のメールアドレスも、ログインさせない。ログインの画面から確認のメールを受け取れるようにする
- 他にありえた選択肢: ログインは通し、ログイン後の画面で確認待ちを見せて確認を促す(メールアドレスを識別にだけ使い、ほかの機能では使わない)
- 外れていた場合: 要件3の全部と、それを前提にした要件6(ログイン後に確認のメールを受け取る手段)・要件9(ログインできない利用者の再設定)の組み立てが変わる。前からあるアカウントの利用者が本番の切り替え直後にログインできなくなる動きも変わる

**3. Google と GitHub が確かめたメールアドレスは、アプリの確認のメール無しで確認済みとして扱う** — 要件7

- Issue の記載: なし
- 決めたこと: Google か GitHub が持ち主を確かめたと返したメールアドレスは、アプリの確認を省く。前からあるアカウントの確認前のメールアドレスも、同じメールアドレスを Google か GitHub が確かめたと返せば確認済みにする(要件7の3)
- 他にありえた選択肢: Google と GitHub のメールアドレスにも、アプリの確認のメールを必ず送る
- 外れていた場合: Google と GitHub でログインした利用者の全員に確認の流れが要ることになり、要件7と要件8の動きと、ログイン後の画面の作りが変わる

**4. 確認前のメールアドレスでパスワードの再設定を求めたら、確認と再設定を1通のメールで続けて行う** — 要件9

- Issue の記載: なし
- 決めたこと: 再設定のメールの代わりに確認のメールを送り、確認を済ませたら続けて再設定の画面を出す
- 他にありえた選択肢: 確認前のメールアドレスには再設定のメールも送らず、先に確認を済ませるよう案内する。または、確認を済ませてから別に再設定のメールを送る
- 外れていた場合: 確認のリンクの受け付けと再設定の画面のつなぎ(確認のリンクに再設定の役目を持たせる作り)を作り直す

**5. 前からあるアカウントの利用者に、切り替えを前もって知らせるメールを送らない** — 要件10の1

- Issue の記載: なし
- 決めたこと: 前からあるアカウントのメールアドレスは確認前なので、前もって知らせるメールも送らない
- 他にありえた選択肢: 本番に入れる前に、前からあるアカウントのメールアドレスへ1回だけ知らせを送る(入れる前なら、そのメールアドレスはまだ確認前ではない)
- 外れていた場合: 利用者は、次にログインしようとしたときにはじめて確認を求められる。知らせを足すなら、本番に入れる前の1回きりの作業が要る

**6. 同じメールアドレスの確認前の登録を複数受け付ける** — 要件1の4

- Issue の記載: なし
- 決めたこと: 同じメールアドレスの確認前の登録があっても別の登録を受け付け、先に確認を済ませた登録だけからアカウントを作る
- 他にありえた選択肢: 確認前の登録があるメールアドレスの登録を断る。または、新しい登録で前の登録を置き換える
- 外れていた場合: 確認前の登録の重複の扱い(要件1の4・5、要件3の1)と、確認のリンクの無効化(要件2の3)の決めごとが変わる

**7. 確認のリンクの期限は24時間、1回だけ使える、送り直しは1分に1回** — 要件2の1・2・6

- Issue の記載: なし
- 決めたこと: 上の3つの値
- 他にありえた選択肢: ほかの時間(たとえば1時間、72時間)、送り直しの間隔を設けない、または1日の回数で制限する
- 外れていた場合: 値の変更で済み、手戻りは小さい。ただし、はじめにに「所有者が決めた」と書かれており、その根拠が Issue 本文に無い(指摘 R1-1-7)

**1. 結び付いたアカウントがあるときは、Google か GitHub が返したメールアドレスをそのアカウントに付けない** — 要件7の1

- Issue の記載: なし
- 決めたこと: 結び付いたアカウントにログインさせるときは、今と同じく、返ったメールアドレスをそのアカウントに付けない(確認前のメールアドレスと同じなら確認済みにするだけ。7の2)
- 他にありえた選択肢: 結び付いたアカウントがメールアドレスを持たないときは、Google か GitHub が確かめたと返したメールアドレスを、確認を済ませたメールアドレスとしてそのアカウントに付ける
- 外れていた場合: メールアドレスを持たない Google・GitHub の利用者は、要件4の設定の画面から確認のメールを受け取る流れを通ることになる。選択肢をとるなら、要件7の1と要件4の1(すでにほかのアカウントが持っているメールアドレスのときの扱い)を書き直す

**2. 設定待ちのメールアドレスとパスワードでは、アカウントが無いときと同じ文を出す** — 要件3の5

- Issue の記載: なし
- 決めたこと: 設定待ちのメールアドレスはアカウントのメールアドレスではないので、ログインの画面では「確認がまだ」と出さず、送るボタンも出さない

- 外れていた場合: ログインの画面の分岐が1つ増える。設定待ちのメールアドレスを持つ利用者が Google か GitHub を使えなくなったとき(連携の解除や外部の都合)に、ログインの画面からは確認を済ませられない

**3. 1分たつ前の登録は受け付けて、確認のメールを送らずに、いつもの文を出す** — 要件2の7

- Issue の記載: なし
- 決めたこと: 登録を受け付け、確認のメールを送らず、送ったときと同じ文を出す。利用者は1分たったあとにログインの画面から送り直す
- 他にありえた選択肢: 登録を断る。または、少し待ってから求め直すよう案内する(他人に直前の送信を知られる)
- 外れていた場合: 登録の画面の文と、確認前の登録の保存の仕方(メールを送っていない登録を持つかどうか)が変わる

**4. 設定待ちのメールアドレスでパスワードの再設定を求められても、メールを送らない** — 要件9の3

- Issue の記載: なし

- 他にありえた選択肢: 設定待ちのメールアドレスを持つアカウントはパスワードも持っている(要件4の1)ので、確認前のメールアドレスと同じく確認のメールを送り、確認と再設定を続けて行う(9の1・2)
- 外れていた場合: 要件9の1・2の対象が広がる。パスワードを忘れた Google・GitHub の利用者の再設定の経路が変わる
