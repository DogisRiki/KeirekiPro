# 要件

## 元の要望
Issue #640: ワークフローの中に直接書いた Node.js、Trivy、Codex CLI、Terraform の版を、自動で上がるようにする

### きっかけ

#625 で、CI の Node.js の版を、脆弱性を直すために手で上げた。そのあと、所有者が、CI の中で使う版も自動で上がるようにしたいと求めた。

### やりたいこと

- ワークフローの中に直接書いた Node.js、Trivy、Codex CLI、Terraform(本番の適用に使う版)の版を、すべて自動で上がるようにする。
- 4つの道具の新しい版が出ると、版を書き換えた更新の PR が自動で届くようにする。(AIの提案を了承)

### どうなれば解決か

- 4つの道具のどれかにパッチ版かマイナー版の新しい版が出ると、所有者も AI も作業を始めていなくても、版を書き換えた更新の PR が届く。(AIの提案を了承)
- 更新の PR は週1回届く。(AIの提案を了承)
- 更新の PR は、新しい版が公開されてから72時間経ったあとに届く。脆弱性を直した版も、ほかの版と同じく72時間経ってから届く。(AIの提案を了承)
- Node.js と Terraform は、開発環境と CI の版が揃って上がる。(AIの提案を了承)
- 更新の PR は、所有者が承認してからマージされる。(AIの提案を了承)
- 今後ワークフローに新しく書いた道具の版が、自動で上がる対象に入っていないとき、そのことに気づける。(AIの提案を了承)
- #420 の棚卸しの表は今のまま残り、自動で上がるようになった版も表に載り続ける。(AIの提案を了承)

### やらないこと

- メジャー版の更新の PR を自動で届けること。メジャー版は、今と同じく棚卸しの表で新しい版を知り、所有者が起票して個別に上げる。(AIの提案を了承)


## はじめに

CI のワークフローは、Node.js、Trivy、Codex CLI、Terraform の4つの道具を、ワークフローの中に直接書いた版で入れる。Dependabot は、ワークフローの中に直接書いたこれらの版を上げない。そのため、新しい版が出ても、所有者か Claude が気づいて手で書き換えるまで、CI は古い版のまま動く。また、開発環境の Node.js と Terraform の版は、Dependabot が CI の版とは別に上げるので、CI の版とずれる。

この spec は、4つの道具の版が、所有者や Claude が気づかなくても、新しい版に上がるようにする。

この spec では、次の言葉を次の意味で使う。

- 4つの道具: CI で使う Node.js、Trivy、Codex CLI、Terraform。Terraform は、本番に適用するワークフロー `terraform-apply.yaml` が使う版を指す
- CI の版: ワークフローの中に直接書いた、4つの道具の版
- 開発環境の版: 開発者が Docker の開発環境で使う Node.js と Terraform の版。開発環境のイメージを作るファイル(`docker/frontend/Dockerfile` と `docker/terraform/Dockerfile`)の `FROM` の行に書いてある
- 72時間の待ち: 版が配布元で公開されてから72時間経つまで、その版を入れないこと
- 公開からの時間の検査: 4つの道具の版を変える PR が受ける、変えた先の版が配布元で公開されてから72時間経っているかの検査
- 版の書き場所の検査: PR が受ける、ワークフローに直接書いた道具の版が、自動で上がる対象か対象外の一覧に入っているかの検査
- 同じメジャー版: 版の番号の最初の数字が同じ版。Trivy と Codex CLI のように 0 で始まる版も、最初の数字が 0 のあいだは同じメジャー版とする。たとえば、Trivy の 0.74.0 から 0.75.0 への更新は、マイナー版の更新として届く

## 範囲

- この spec で決めること:
  - 4つの道具の、パッチ版とマイナー版の更新の PR が届く時期と、PR の中身
  - 更新の PR をマージするまでの扱い
  - Node.js と Terraform の開発環境の版を、CI の版とそろえること
  - 4つの道具の版を変える PR に、72時間の待ちを機械で効かせること
  - ワークフローに直接書いた道具の版が自動で上がる対象から漏れたことを、版の書き場所の検査で知らせること
  - 棚卸しの表に、4つの道具が載ること
  - 週1回の実行に失敗したときの知らせ
- この spec で決めないこと:
  - メジャー版の更新の PR を自動で届けること。所有者は、今と同じく、棚卸しの表でメジャー版の新しい版を知り、起票して個別に上げる
  - 所有者の指示で、脆弱性を直した版を72時間待たずに CI に入れる手順。この手順は、spec `security-fix-cooldown-exception`(Issue #641)が決めている。この spec は、その手順で入れた版を、公開からの時間の検査で止めないことだけを決める
  - CI の Java の版。ワークフローには、Java のメジャー版だけが書いてある。CI は、動くたびに、そのメジャー版の最新のパッチ版を入れる。そのため、Java には更新の PR が要らない
  - ワークフローが参照するアクションの版(`uses:` の行)と、frontend と backend の部品の版。これらは、今と同じく Dependabot が上げる
  - 開発環境のイメージの、版を変えずに中身だけを新しくする更新。この更新は、今と同じく Dependabot が届ける
  - 週1回の実行が、GitHub の都合で起動されなかったことに気づく仕組み。これは Issue #482 で扱う
- この spec が前提にしていること:
  - CI は、4つの道具を入れるときに、配布元の署名で中身を確かめる(Issue #644)。署名で確かめられなければ、CI は失敗する
  - `.github/` の下のファイルを変える PR は、所有者が承認しないとマージされない
  - frontend と backend の部品の版には、72時間の待ちが今も機械で効いている
  - 棚卸しの表(Issue #420)は月1回届き、対象ごとに、使っている版と最新の版を載せる

## 要件

### 要件1 4つの道具の新しい版に書き換えた更新の PR が、週1回届く

新しい版が出ても、誰かが気づいて手で書き換えるまで、CI は古い版のまま動く。Issue #625 では、脆弱性を直した Node.js の版に、Claude が手で書き換えた。所有者は、開発者も Claude も作業を始めていなくても、新しい版に書き換えた PR が届くようにしたい。届くのが週1回なら、所有者が更新の PR を承認する回数は、道具ごとに週に多くて1回で済む。

1. 日本時間の毎週月曜日の9時ごろに、4つの道具のそれぞれについて、上げる先の版があれば、その版に書き換えた更新の PR が届く。開発者も Claude も作業を始めていなくても、更新の PR は届く。
2. 上げる先の版は、次の3つをすべて満たす版のうち、最も新しい版である。
   - 今の CI の版と同じメジャー版である
   - 今の CI の版より新しい
   - 配布元で公開されてから72時間経っている
3. 脆弱性を直した版も、ほかの版と同じく、公開から72時間経ってから届く。
4. 更新の PR は、道具ごとに1つずつ届く。同じ週に2つの道具に上げる先の版があれば、更新の PR が2つ届く。そのため、1つの道具の PR の検査が失敗しても、所有者は、ほかの道具の PR をマージできる。
5. 上げる先の版が無い道具の更新の PR は届かない。今の CI の版より新しい版に、メジャー版の違う版しか無いときも、更新の PR は届かない。
6. 同じ道具の更新の PR がまだ開いているときは、新しい PR は届かない。その週に上げる先の版が、開いている PR の版より新しければ、開いている PR の版が、その版に書き換わる。
7. 所有者が更新の PR をマージせずに閉じても、翌週に上げる先の版があれば、更新の PR が改めて届く。
8. リポジトリに書き込める開発者は、GitHub の画面から、週1回の実行を、月曜日を待たずに起動できる。手で起動したときの動きは、月曜日の実行と同じである。

### 要件2 所有者は、更新の PR を読めば、何を承認するのかが分かる

所有者は、更新の PR を自分で読んで承認したい。所有者は、承認するときに、どの道具の版をどの版に上げるのかと、上げる先の版がいつ公開されたのかと、上げる先の版で道具の何が変わったのかが分からなければ、承認してよいかを判断できない。

1. 更新の PR の題名には、道具の名前と、上げる先の版が書いてある。
2. 更新の PR の本文には、今の CI の版、上げる先の版、上げる先の版が配布元で公開された日時、配布元が出したその版の変更点の文書へのリンクが書いてある。Node.js と Terraform の更新の PR の本文には、今の開発環境の版も書いてある。
3. 今の版と上げる先の版のあいだに、ほかの版がいくつか出ているときは、更新の PR の本文には、あいだの版ごとの変更点の文書へのリンクも書いてある。
4. Terraform の更新の PR の本文には、本番に適用するときの Terraform の版が変わることが書いてある。あわせて、本文には、新しい版が本番に使われるのは、マージのあとに誰かが本番に適用するワークフローを動かしたときであることが書いてある。

### 要件3 更新の PR は、所有者が承認してからマージされる

CI は、本番に配る frontend のファイルを組み立て、秘密の値を扱う。CI の道具に悪意のある版が入ると、被害は本番と秘密の値に及ぶ。そこで、所有者は、CI の道具の版が変わる変更を、自分で読んで承認してからマージしたい。

1. 更新の PR は、ほかの PR と同じ検査をすべて受ける。検査には、上げる先の版の、配布元の署名の確認も含まれる。
2. 更新の PR は、検査がすべて通っても、所有者が承認するまでマージされない。
3. 所有者が承認し、検査がすべて通ったら、更新の PR は、ほかの PR と同じく自動でマージされる。
4. 更新の PR の検査が失敗したら、更新の PR はマージされず、開いたまま残る。

### 要件4 Node.js と Terraform は、開発環境と CI の版がそろって上がる

開発環境と CI で道具の版が違うと、開発者が開発環境で通した確認を、CI は別の版の道具で動かす。そのため、開発者は、CI で失敗したときに、開発環境で同じ失敗を再現できないことがある。所有者は、Node.js と Terraform について、開発環境と CI で同じ版を使いたい。

1. Node.js と Terraform の更新の PR は、CI の版と開発環境の版を、同じ版に書き換える。
2. Node.js と Terraform の上げる先の版は、要件1の上げる先の版の3つの条件に加えて、もう1つの条件も満たす版に限る。3つの条件とは、今の CI の版と同じメジャー版であること、今の CI の版より新しいこと、配布元で公開されてから72時間経っていることである。もう1つの条件とは、その版を入れた配布元のイメージも、配布元で公開されてから72時間経っていることである。配布元のイメージとは、開発環境の `FROM` の行に書くイメージである。
3. 更新の PR は、CI の版も開発環境の版も下げない。
4. 上げる先の版が無い週にも、次の2つをどちらも満たすときは、更新の PR が届く。1つ目は、開発環境の版と CI の版が違うことである。2つ目は、2つの版のうち新しいほうの版を入れた配布元のイメージが、配布元で公開されてから72時間経っていることである。この更新の PR は、古いほうの版を、新しいほうの版にそろえる。たとえば、所有者の指示で、CI の版だけを72時間待たずに上げたとする。このときは、更新の PR が、その版を入れた配布元のイメージが公開から72時間経った週に、開発環境の版をその版にそろえる。
5. 開発環境の Node.js と Terraform の版を、CI の版とは別に上げる PR は届かない。版を変えずに開発環境のイメージの中身だけを新しくする PR は、今と同じく届く。

### 要件5 4つの道具の版を変える PR は、公開から72時間経っていない版なら、公開からの時間の検査が失敗する

所有者は、4つの道具の版にも、frontend と backend の部品と同じく、72時間の待ちを機械で効かせたい。72時間の待ちがあるのは、公開から間もない版が、配布元を乗っ取った者の出した悪意のある版であっても、まだ誰も気づいていないことがあるためである。そこで、所有者は、版が更新の PR で変わるときも、開発者や Claude が手で書き換えるときも、同じ待ちが効くようにしたい。

1. 4つの道具の CI の版か、Node.js と Terraform の開発環境の版を変える PR は、変えた先の版が配布元で公開されてから72時間経っていなければ、公開からの時間の検査が失敗し、マージされない。開発環境の版を変える PR では、変えた先の版を入れた配布元のイメージが配布元で公開されてから72時間経っていないときも、公開からの時間の検査が失敗する。更新の PR も、開発者や Claude が手で版を書き換えた PR も、同じ扱いになる。
2. 公開からの時間の検査が失敗したときは、検査の結果に、止めた道具と版、その版か配布元のイメージが配布元で公開された日時、検査が通るようになる日時が書いてある。開発者が、検査が通るようになる日時を過ぎてから公開からの時間の検査をやり直すと、その検査は通る。
3. 公開からの時間の検査は、変えた先の版か、その版を入れた配布元のイメージが配布元で公開された日時を取れなかったときも、失敗する。検査の結果には、日時を取れなかった道具と版と、取れなかった理由が書いてある。
4. 例外として、所有者の指示で、脆弱性を直した版を72時間待たずに CI に入れる PR は、記録に書かれた道具の CI の版を、記録に書かれた版に変えた箇所だけ、公開からの時間の検査が通る。記録とは、spec `security-fix-cooldown-exception` が決めた、PR の本文に書く記録で、所有者の指示で、配布元の署名を確かめてからその版を入れたことの記録である。同じ PR の中でも、ほかの道具の版の変更と、開発環境の版の変更は、この例外に当たらない。公開からの時間の検査は、これらの変更を、例外に当たらない PR の版の変更と同じく検査する。
5. 4つの道具の版を変えない PR は、公開からの時間の検査で止まらない。

### 要件6 ワークフローに直接書いた道具の版が、自動で上がる対象から漏れたら、版の書き場所の検査が失敗する

今後、ワークフローに新しく道具を足すと、その道具は、版が自動で上がる対象に入らないまま、古い版で動き続けるおそれがある。また、4つの道具の版を新しいワークフローに書いても、その場所が自動で上がる対象に入っていなければ、その場所だけが古い版のまま残る。所有者は、こうした漏れに、マージの前に気づきたい。

1. 版の書き場所の検査は、ワークフローと、ワークフローが使うこのリポジトリの中のアクションに直接書いた道具の版を、すべて調べる。道具の版とは、ワークフローが道具を入れるときに入れる版を、数字で書いたものである。たとえば、道具を入れるアクションに渡す版や、版を入れた環境変数や、道具を入れるコマンドに書いた版や、`docker run` で動かすイメージのタグに書いた版が、道具の版に当たる。ワークフローが参照するアクションの版(`uses:` の行)と、frontend と backend の部品の版は、版の書き場所の検査は調べない。
2. 調べた道具の版が、自動で上がる対象にも、対象外の一覧にも入っていなければ、版の書き場所の検査は失敗する。検査の結果には、その版が書いてあるファイルと行と、その版を自動で上がる対象か対象外の一覧のどちらかに入れる必要があることが書いてある。
3. 4つの道具の版を、自動で上がる対象に入っていない場所に書いたときも、版の書き場所の検査は失敗する。
4. 同じ道具の CI の版が、書いてある場所によって違うときは、版の書き場所の検査は失敗する。検査の結果には、版の違う場所が書いてある。
5. 対象外の一覧には、版ごとに、自動で上げない理由が書いてある。所有者は、この一覧を読めば、どの道具の版が自動で上がらないのかと、その理由が分かる。
6. この spec が main に入った時点でワークフローに直接書いてある道具の版のうち、4つの道具の版は、どの場所の版も、自動で上がる対象に入っている。4つの道具のほかの道具の版は、どれも対象外の一覧に入っている。たとえば、CI の Java の版と、`guardrails.yaml` が `docker run` で動かす actionlint と shellcheck の版が、対象外の一覧に入っている。そのため、この spec が main に入った直後の PR では、版の書き場所の検査は、次の2つのどちらの理由でも失敗しない。1つ目は、道具の版が自動で上がる対象にも対象外の一覧にも入っていないことである。2つ目は、4つの道具の版が自動で上がる対象に入っていない場所に書いてあることである。

### 要件7 棚卸しの表に、4つの道具が載り続ける

メジャー版の更新の PR は届かないので、所有者は、4つの道具のメジャー版が出たことを、月1回届く棚卸しの表で知る。所有者は、表に載っていない道具の新しいメジャー版が出ても、そのことに気づけない。今の棚卸しの表には、Codex CLI が載っていない。

1. 棚卸しの表は、今と同じく月1回届き、4つの道具のそれぞれについて、使っている版と、書いてある場所と、最新の版を載せる。
2. 更新の PR がマージされたあとに届く棚卸しの表は、マージされた新しい版を、使っている版として載せる。
3. Node.js と Terraform については、棚卸しの表は、CI の版と開発環境の版を、今と同じく両方とも載せる。

### 要件8 週1回の実行に失敗したら、所有者に知らせが届く

週1回の実行が失敗したまま誰も気づかなければ、4つの道具の版は上がらず、所有者は版が上がらない理由も分からない。所有者は、週1回の実行に失敗したことを、知らせで知りたい。

1. 所有者には、週1回の実行が失敗したときに知らせが届く。ここでの失敗とは、週1回の実行が、ある道具の新しい版を調べられなかったこと、更新の PR を作れなかったこと、更新の PR を書き換えられなかったことの3つである。知らせは、ほかの監査の知らせと同じ形で届く。
2. 知らせには、どの道具の何に失敗したかと、失敗した実行へのリンクが書いてある。
3. 1つの道具で失敗しても、週1回の実行は、ほかの道具の更新の PR を作り続ける。
