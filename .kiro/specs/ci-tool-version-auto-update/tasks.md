## 実装のメモ

- 置き場所: design.md の移行の節は、完成品を scratchpad で作ると書く。Claude は、scratchpad の代わりに、作業フォルダの中の `.claude/.state/ci-tool-version-auto-update/place-1/` を置き場所にする。scratchpad は会話ごとに別のフォルダなので、所有者がファイルを置くのを待つあいだに会話を開き直すと、置く前のファイルが失われるためである。このことは、spec `security-fix-cooldown-exception` の実装で分かった。このフォルダは `.gitignore` の `.claude/.state/` に当たるので、コミットされない
- Claude は、`.github/` の下に置くファイルを、置き場所の `dot-github/` に、`.github/` と同じ並びで作る。`settings.json` の `deny` の `.github/**` が、置き場所の中の `.github/` にも当たるためである。Claude は、`.claude/` の下に置くファイルを、design.md の移行の節のとおり所有者に置いてもらう。そのため、Claude は、これらのファイルを、置き場所の `dot-claude/` に、`.claude/` と同じ並びで作る。今あるファイルを変えるときは、Claude は、今の版を Read で読み、Write で置き場所に写してから変える
- `README.md` と `doc/` の下の文書は、Claude が本来の場所に書く
- テストを流す環境: `.github/scripts/` のテストは `jq` を使う。この PC の Git Bash には `jq` が無い。そのため、この spec の `.github/scripts/tests/` のテストでは、`/kiro-impl` が言う「実装する PC のシェル」を、Git Bash ではなく Linux のコンテナとする。Claude は、このテストを、品質チェックのコマンドとしてではなく、タスクで変えたファイルを使うテストのコマンドとして、どのタスクでも、実装と修正のあいだと確認役の確かめで流す。Claude は、テストを、`.github/CLAUDE.md` の形の alpine のコンテナに `bash` `jq` `curl` `git` を入れて流す。`git` を入れるのは、週1回の実行の結合テストと公開からの時間の検査のテストが、一時のフォルダに Git のリポジトリを作るためである。Claude は、リポジトリの写しを scratchpad に作り、置き場所のファイルを重ねてから、その写しに `chmod -R a-x` をかけてコンテナに読ませる
- テストのほかに道具が要るタスク: Claude は、`dependabot.yml` を読むタスク 4.4 では、コンテナに `python3` と `py3-yaml` を足す。Claude は、署名を確かめるステップを動かすタスク 4.6 では、`install-verified-terraform.sh` が使う `gnupg` と `unzip` をコンテナに足し、配布元に届くネットワークのあるコンテナで流す
- Claude は、完了条件の4つ目の、テストの対象のコードを壊した写しで流すテストも、Linux のコンテナで流す。Claude は、`run-copies.pl` に渡す一覧の写しごとのコマンドを、その写しをつないだ alpine のコンテナでテストを流す `docker run` の形にする。Claude は、壊す前の写しでテストが通ることも、同じ形で確かめる。壊さなくても失敗するテストを、壊したから失敗したと読み違えないためである
- shellcheck: Claude は、shellcheck を品質チェックのコマンドとして扱い、大きなまとまりの最後のタスクの確認で1回流す。Claude は、置き場所のファイルを重ねたリポジトリの写しのすべての `.sh` に、`guardrails.yaml` と同じ `koalaman/shellcheck:v0.11.0` を、`.github/CLAUDE.md` の形で流し、指摘が0件であることを確かめる。すべての `.sh` を一度に渡すのは、`. "$LIB"` で読み込むライブラリまでたどらせ、CI と同じ結果にするためである
- テストのスタブが返す配布元の JSON は、Claude が実際の配布元から1回取った答えの形をもとにする。テストはネットワークを使わない
- PR の検査で流すテスト: ジョブ `cooldown` に足すテストを決めるタスク 4.6 と、ジョブ `escape-hatch` に足すテストを決めるタスク 4.7 の割り当てで、この spec で作る5本のテストが、どれもいずれかの PR の検査で流れる
- 公開からの時間の検査は、分かれ目と head の版を、行番号ではなく、ファイルと名前の組ごとの版の集まりで比べる。版の行より上に行を足しただけの PR で、変わっていない版を変更と読まないためである
- `lib-ci-tool-releases.sh` の版の一覧を取る関数は、Trivy のリリースの一覧を、今の版より古い版に届くまでページをたどって取る。今の版から30件より多く離れたときに、あいだの版の変更点の文書のリンクが欠けないようにするためである
- 所有者への依頼は、親のセッションが行う。実装役のサブエージェントは、所有者に依頼する手前で止まり、用意したファイルの置き場所のパスを親のセッションに返す。確認役は、置く前の成果を置き場所のパスで確かめる
- この spec は frontend と backend と terraform のコードを変えないので、共通の完了条件の2つ目の verify のスキルは、どのタスクにも当てはまらない。代わりに、Claude は、上の shellcheck の箇条のとおりに shellcheck を流し、ワークフローを変えるタスクで actionlint を流す
- 共通の完了条件の1つ目(確かめるテストの無い受入基準を残さない)には、2つの例外がある。1つ目は、ワークフローの起動と権限とステップの条件を変えるタスク 4.5 から 4.7 である。これらのタスクは、actionlint と照合と、実装の PR の検査の結果で実際の環境を確かめるタスク 6.2 で確かめる。2つ目は、手順の文書を書くタスク 4.3 と 5 である。これらのタスクは、照合で確かめる
- マージのあとの確かめ方: Claude は、出荷の PR の本文に、design.md の移行の節のとおり、最初の実行で届く見込みの更新の PR と、Terraform の更新の PR を承認する前に所有者が確かめることを書く
- Claude は、出荷の PR の本文に、CI の道具の記録の目印(`<!-- ci-tool-cooldown-exception`)の文字列を書かない。公開からの時間の検査と週次監査が、PR の本文の目印を読むためである
- `civ_rewrite_ci` は、組の行の古い版を、渡された版で丸ごと置き換える。古い版の先頭に `v` が付く行では、書き換えたあとの版から `v` が落ちる。今のデータのファイルの ci の組は、どれも先頭に `v` の付かない `名前: 値` の行である。先頭に `v` の付く書き場所を ci の組に足すときは、書き換えの関数に `v` を残す処理を先に足す
- `test-check-ci-tool-placement.sh` の場合 main_snapshot は、本物の `inventory-targets.json` に Codex CLI の対象が無いときだけ、テストの中で対象を足してから流す。Claude は、タスク 4.2 で本物に Codex CLI の対象を足したら、この分岐を消し、本物をそのまま使う形にする。分岐を残すと、Codex CLI の対象が本物から消えても、このテストが気づかないためである
- 公開からの時間の検査は、変わった版をまとめて判定する関数が失敗を返したのに結果の行を1行も出さなかったとき、その変更を止めずに通す。Claude は、このスクリプトを変えるタスク 4.6 で、この場合も止める形に直し、テストを足す。検査が失敗したときは止める側に倒すためである。このことは、タスク 2.2 の審査で分かった
- 更新の PR の本文は、開発環境の版だけを変える PR で、design.md の題名と本文の箇条の文と2か所違う。1つ目に、Terraform の本番に適用する版の節には、本番に適用する版が変わらないことを書く。2つ目に、承認の節には、`.github/` を変えることではなく、dependency-gate の検査が所有者の承認を求めることを書く。開発環境の版だけを変える PR は `.github/` を変えないので、design の文のとおりに書くと、事実と違う文になるためである。このことは、タスク 3.2 で分かった。Claude は、出荷の PR の本文にも、この違いを書く
- テストで、`set -o pipefail` の下で `printf '%s\n' "$大きな値" | grep -q …` と書かない。`grep -q` が一致で先に終わると `printf` が SIGPIPE で止まり、一致していてもパイプ全体が失敗になるためである。Claude は、`grep -q … <<<"$大きな値"` と書く。このことは、タスク 4.2 で `test-collect-inventory.sh` が1回だけ落ちたことで分かった
- Dependabot は、node の digest だけが変わった PR(#550)の本文の `update-type` に `version-update:semver-patch` と書いた。dependabot-core の除外は、本文のこの欄ではなく、今の版を含まない版の範囲で判定するので、タスク 4.4 の除外は digest だけが変わる PR を止めないと判断した。この判断は動かして確かめていないので、Claude は、出荷の PR の本文のマージのあとの確かめ方に、digest だけが変わる node と hashicorp/terraform の PR が届き続けることを確かめる手順を書く。このことは、タスク 4.4 の審査で分かった
- 週1回の実行のワークフローは、design.md の文に2つを足した。1つ目に、checkout に `ref: main` を書き、別のブランチから手で起動したときも main のスクリプトを流す。2つ目に、テストは通ったのに週1回の実行のスクリプトが報告を書かずに失敗したときも、知らせのステップが報告のファイルに1行を書く。書かないと `audit-issue.sh` が報告のファイルが無いことで止まり、知らせの Issue が作られないためである。Claude は、この2つを、出荷の PR の本文に design.md と違えた箇所として書く

## 完了条件(全タスク共通)

Claude は、どのタスクでも、タスクの箇条書きの欄を書いたうえで、次の4つを満たしたときにタスクを完了とする。

1. Claude は、タスクが満たす requirements.md の受入基準(要件の番号付きの項目)ごとに、それを確かめるテストのファイル名とテスト名を「受入基準とテストの対応」の行に書く。Claude は、確かめるテストの無い受入基準を残さない。
2. タスクで変えたファイルを使うテストが、すべて成功している。`1.` や `2.` の見出しのタスクを大きなまとまりと呼ぶ。大きなまとまりの最後のタスクでは、加えて、そのまとまりのタスクで変えた領域の verify のスキル(`/verify-frontend` `/verify-backend` `/verify-terraform`)が、すべて成功している。
3. Claude は、テストを飛ばす設定、アサーションの削除、カバレッジや lint の対象からの除外を足して、完了条件を満たしたように見せない。CI の escape-hatch の検査が、これらの追加を機械で見つける。
4. Claude は、新しく書いたテストについて、テストの対象のコードを一時的に壊してテストが失敗することを確かめる。Claude は、新しいテスト1件につき1か所だけを、作業フォルダの外の写しで壊し、そのテストだけを流す。壊した写しの作り方と流し方は、`.kiro/steering/tech.md` の「テストの完全性」に従う。
