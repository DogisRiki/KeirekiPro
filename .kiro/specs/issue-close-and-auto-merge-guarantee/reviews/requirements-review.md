### 申告

**1. 所有者が手で予約を外しても付け直す。止める手段はラベルと下書きだけになる** — requirements.md 要件4-1、Boundary Context の Adjacent expectations

- Issue の記載: あり。「予約が外れると、誰が外したかに関係なく予約が付け直される(AIの提案を了承)」。所有者が外した場合を含むことは「誰が外したかに関係なく」から読めるが、止める手段には触れていない
- 決めたこと: 所有者が外した場合も付け直す。マージを保留する手段は `pre-merge-check` ラベル(と下書き)に限る。現行の `rearm-auto-merge.yaml` は「所有者が手で外した場合など、ほかの理由では何もしない」で、これを逆にする
- 他にありえた選択肢: 所有者(人間のアカウント)が外した場合だけは付け直さない。または、付け直しを止める専用のラベルを設ける
- 外れていた場合: 所有者が画面で予約を外しても、付け直されてチェックが緑になった時点でマージされる。同じコミットで4回外すと止まる(要件4-3)が、それまでは外す操作が効かない

**2. 「対応するIssue」を、PR本文の `Closes #<番号>` に書かれたものだけにした** — requirements.md 要件1-1

- Issue の記載: なし。「対応する Issue」としか書かれていない
- 決めたこと: PR本文の `Closes #<番号>` だけを見る。`Fixes` `Resolves` など GitHub が認めるほかの語、コミット本文の記載、画面で手で紐づけたIssueは対象にしない。大文字小文字や `Closes: #<番号>` のような表記ゆれの扱いは書かれていない
- 他にありえた選択肢: GitHub が認める閉じる語をすべて対象にする。GitHub が紐づけたIssue(画面で紐づけたものを含む)も対象にする
- 外れていた場合: 所有者のアカウントで作ったPRに `Fixes #12` と書いた場合、GitHub が紐づけに失敗するとIssueは開いたままになり、知らせも出ない(`Refs:` も無ければ要件2-2 にも掛からない)

**3. 仕組みそのものが動かなかったときは、知らせが出ない** — requirements.md 要件2-1、2-4、5-1、Adjacent expectations

- Issue の記載: あり。「Issue が閉じなかったときは、所有者に知らせが届く」「予約に失敗したときは、所有者に知らせが届く」
- 決めたこと: 知らせは仕組み自身が出す。ワークフローの失敗に対する GitHub 既定の通知には頼らない。仕組みが起動しない・権限(botのトークン)が切れているときに、別の経路で気づく要件は置いていない
- 他にありえた選択肢: 週次監査に「マージ済みPRの `Closes` のIssueが開いたまま」「開いているPRに予約が無い」の確認を足す
- 外れていた場合: トークンの期限切れなどで閉じる操作も知らせも両方失敗すると、#448 と同じく誰も気づかないまま開いたIssueと止まったPRが残る

**4. `Refs:` だけに書かれたIssueは閉じず、知らせるだけにした** — requirements.md 要件2-2

- Issue の記載: なし
- 決めたこと: `Closes` に無く `Refs:` にだけあるIssueが開いていたら、閉じずに所有者へ知らせる
- 他にありえた選択肢: `Refs:` のIssueも閉じる(出荷手順は `Closes` を例外なく必須としているため、書き漏れとみなす)。または何もしない
- 外れていた場合: 1つのIssueを複数のPRに分けて進める運用をしたとき、途中のPRがマージされるたびに知らせが届く。逆に書き漏れのときは、所有者が手で閉じる作業が残る

**5. 予約しないPRを Dependabot・カナリア・fork・下書きに決めた** — requirements.md 要件3-4、3-6、Out of scope

- Issue の記載: あり。「仕組みが必ず付ける」「所有者のアカウントで作った PR にも予約が付く」。除外には触れていない
- 決めたこと: 上の4種には予約しない。それ以外の main 向けPRには、作成・下書き解除・開き直しの時点で必ず予約する
- 他にありえた選択肢: 予約しない印(ラベルなど)を設けて、所有者が個別に外せるようにする
- 外れていた場合: 所有者が試しに作ったPR(マージするつもりの無いもの)も、下書きにしない限りチェックが緑になった時点でマージされる

**6. 待ち時間を1時間、付け直しの上限を3回にした** — requirements.md 要件2-4、4-2、4-3

- Issue の記載: なし
- 決めたこと: Issueが開いたままの見直しと、予約が無い状態の見直しをどちらも1時間。同じコミットで3回を超えて外れたら止める(3回は現行の `rearm-auto-merge.yaml` と同じ。ただし現行はルール違反の理由だけを数え、本specは理由を問わず数える)
- 他にありえた選択肢: 見直しを1日1回にする(`dependabot-auto-merge.yaml` の毎日の見直しと同じ)。上限の回数を理由ごとに分ける
- 外れていた場合: 1時間は、起点のイベントを取り逃したPRが最長1時間止まることを意味する。短くすると定期実行の回数が増える

**7. 閉じたIssueに「どのPRで閉じたか」を書き込む** — requirements.md 要件1-3

- Issue の記載: なし
- 決めたこと: 仕組みが閉じたIssueに記録を残す。すでに閉じていたら何も書かない(要件1-4)
- 他にありえた選択肢: 記録を残さず閉じるだけにする
- 外れていた場合: 影響は小さい。GitHub 自身の紐づけが遅れただけのときも仕組みが先に閉じると、ほとんどのIssueに記録が付く

**1. 導入後に人間が確認する手順の置き場所を、導入のPRの本文にした** — requirements.md 要件7-5

- Issue の記載: なし。対応記録にある所有者の指示は「運用文書に1回きりの作業を書かない」で、代わりの置き場所までは決めていない

- 外れていた場合: PRの本文は出荷のとき(`/ship`)に AI が書くもので、実装のタスクが終わった後に作られる。用意した文面が本文に入らなかった場合、所有者は確認の手順を受け取れない。確認の4項目には、仕組みが予約したPRのマージ後に後続の処理が動くこと(#326 の再発が無いこと)が含まれる。また、PRの本文は後から誰でも書き換えられ、変更の履歴がリポジトリに残らない

**2. 運用文書に書かない範囲を「導入のときに1回だけ行う作業の手順」と定めた** — requirements.md 要件7-6

- Issue の記載: なし。対応記録にある所有者の指示(運用文書に1回きりの作業を書かない)を要件にしたもの

- 他にありえた選択肢: 対象を README や CLAUDE.md、出荷手順まで含めて「リポジトリの文書すべて」にする
- 外れていた場合: 影響は小さい。README や CLAUDE.md に1回きりの作業が書かれても、この要件では止まらない
