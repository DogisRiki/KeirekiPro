# 要件

## 元の要望
Issue #455: PR がマージされたら Issue が必ず閉じ、自動マージの予約も仕組みが付けるようにする

### きっかけ

> さっきPR mergeされたのにissue閉じなかったってのがきっかけ

(#450 のマージ後も #448 が開いたままだった)

### やりたいこと

- PR がマージされたら、対応する Issue が必ず閉じるようにする
- PR の自動マージの予約を、AI の手順に任せず、仕組みが必ず付けるようにする(AIの提案を了承)

### どうなれば解決か

- PR がマージされると、対応する Issue が閉じている
- Issue が閉じなかったときは、所有者に知らせが届く(AIの提案を了承)
- AI が予約の操作をしなくても、PR に自動マージの予約が付いている(AIの提案を了承)
- 所有者のアカウントで作った PR にも予約が付く
- 予約が外れると、誰が外したかに関係なく予約が付け直される(AIの提案を了承)
- 予約に失敗したときは、所有者に知らせが届く(AIの提案を了承)

## はじめに

この spec は、2つの問題を、AIの手順ではなく仕組みの側で解消する。1つ目は、PRがマージされたあと、対応するIssueが開いたまま残ることである。2つ目は、自動マージの予約がAIの手順(`/ship`)に依存していることである。

今は、Issueが閉じるかどうかは、GitHubがPR本文の `Closes #<番号>` を紐づけるかどうかに任されている。GitHubが紐づけなかったときに、所有者がそれに気づく手段は無い。自動マージの予約は、`/ship` の中でAIが操作しており、所有者のアカウントで作ったPRには付かない。予約が外れたときの付け直しは、外れた理由がルール違反のときに限られている。

この spec は、マージ後のIssueのクローズと、自動マージの予約・付け直しを、AIの操作にもPRの作成者にも依らず、GitHub Actions のワークフローが行うようにする。ワークフローがこれらを果たせなかったときは、ワークフローが所有者に知らせる。この spec では、マージされたPRに対応するIssueを閉じるワークフローを「クローズのワークフロー」と呼び、PRに自動マージを予約して付け直すワークフローを「予約のワークフロー」と呼ぶ。

## 範囲

- この spec で決めること: マージされたPRに対応するIssueのクローズの保証、Issueを閉じられなかったときの所有者への知らせ、PRへの自動マージの予約の自動付与(作成者を問わない)、予約が外れたときの付け直し(外した者と理由を問わない)、予約に失敗したときの所有者への知らせ、出荷手順・README・運用文書の記述をこの仕組みに合わせる変更
- この spec で決めないこと:
  - Dependabot のPRの予約。既存の仕組みが、公開から72時間の待ち期間を含めて、Dependabot のPRの予約の時期を決めている。この spec のワークフローは、Dependabot のPRに予約を付けず、外れた予約も付け直さない
  - カナリアPR(マージしてはならないPR)。この spec のワークフローは、カナリアPRに予約を付けない
  - リポジトリの外(fork)から出されたPR
  - PR本文に `Closes #<番号>` が書かれているかどうかの検査。`Closes #<番号>` を書くことは、既存の出荷手順が定めている
  - GitHubがPR本文の `Closes` を紐づけなかった原因の究明と解消。これはGitHub側の事象である
  - マージの条件そのもの(必須チェック・承認の要否)の変更
- この spec が前提にしていること:
  - 所有者は、マージを保留したいときに、予約を外すのではなく、既存の `pre-merge-check` ラベルを使う。この spec の導入後は、所有者が予約を手で外しても、予約のワークフローが予約を付け直す
  - 予約が付いても、必須チェックと必要な承認が揃うまで、GitHubはPRをマージしない。既存のゲートは、この spec の導入後もそのまま働く
  - ワークフローは、所有者への知らせを、GitHubの通知として所有者に届く形で出す。ワークフローは、ワークフローの失敗に対するGitHub既定の通知には頼らない。botが書いたワークフローの定期実行が失敗しても、その通知が所有者に届かないことは、audit-notification spec で確認済みである

## 要件

### 要件1 マージ後のIssueのクローズ

所有者は、PRがマージされたら、対応するIssueが必ず閉じていてほしい。開いたままのIssueが残ると、所有者は、終わった作業と残っている作業を見分けられなくなるからである。

1. PRがmainブランチへマージされたら、クローズのワークフローは、そのPRの本文に `Closes #<番号>` で書かれたIssueを、対応するIssueとして扱う。
2. PRがマージされ、対応するIssueが開いたままなら、クローズのワークフローは、そのIssueを閉じる。
3. クローズのワークフローがIssueを閉じたら、クローズのワークフローは、どのPRのマージによって閉じたかをそのIssueに記録する。
4. PRがマージされ、対応するIssueがすでに閉じていれば、クローズのワークフローは、そのIssueに何も書き込まない。
5. PRの本文に対応するIssueが複数書かれていれば、クローズのワークフローは、そのすべてを閉じる。
6. クローズのワークフローは、マージの方法(自動マージか、所有者による手動のマージか)とPRの作成者に依らず動く。
7. PRがマージされずに閉じられたら、クローズのワークフローは、対応するIssueを閉じない。

### 要件2 Issueが閉じなかったときの知らせ

所有者は、マージ後にIssueが閉じなかったときは知らせてほしい。#448 は、誰も気づかないまま開いたままになっていたからである。

1. 対応するIssueを閉じる操作に失敗したら、クローズのワークフローは、所有者に知らせる。
2. マージされたPRの本文に `Refs: #<番号>` で書かれたIssueが、`Closes` に書かれておらず開いたままなら、クローズのワークフローは、そのIssueを閉じず、そのIssueが開いたままであることを所有者に知らせる。
3. クローズのワークフローは、知らせに、対象のPR番号とIssue番号、何が起きたか、所有者にしてほしいことを書く。
4. PRのマージから1時間が経っても、対応するIssueがマージの後に一度も閉じられておらず開いたままなら、クローズのワークフローは、マージの時点の処理が動いたかどうかに依らず、そのIssueを閉じる。そのIssueを閉じる操作に失敗したときは、クローズのワークフローは、閉じる操作に失敗したときと同じく所有者に知らせる。
5. `Refs: #<番号>` にだけ書かれて開いたままのIssueについて、PRのマージから1時間が経っても知らせが出ていなければ、クローズのワークフローは、マージの時点の処理が動いたかどうかに依らず、そのIssueが開いたままであることを所有者に知らせる。
6. クローズのワークフローは、マージの後に一度でも閉じられたIssueを、その後に開き直されていても閉じず、そのIssueについて知らせも出さない。
7. クローズのワークフローは、マージから1時間が経ったあとの見直し(開いたままのIssueを閉じることと、出ていない知らせを出すこと)の対象を、マージから7日以内のPRに限る。
8. クローズのワークフローは、同じPRとIssueの組について、同じ内容の知らせを繰り返し出さない。

### 要件3 自動マージの予約の自動付与

所有者は、自動マージの予約が、AIの操作やPRの作成者に依らず付いていてほしい。予約がAIの手順に依存していると、手順が抜けたときや、所有者のアカウントでPRを作ったときに予約が付かず、PRが止まるからである。

1. mainブランチ向けのPRが作成されたら、予約のワークフローは、そのPRに自動マージを予約する。
2. 下書きのPRがレビュー可能な状態に変えられたら、予約のワークフローは、そのPRに自動マージを予約する。
3. 閉じられていたPRが開き直されたら、予約のワークフローは、そのPRに自動マージを予約する。
4. PRが下書きの状態である間は、予約のワークフローは、そのPRに自動マージを予約しない。
5. 予約のワークフローは、PRの作成者がAI(bot)か所有者かに依らず予約する。
6. 予約のワークフローは、Dependabot のPR、カナリアPR、リポジトリの外(fork)から出されたPRに予約しない。
7. 予約のワークフローは、既存のマージ方式(squash)で予約する。
8. PRにすでに自動マージが予約されていれば、予約のワークフローは、その予約をそのままにし、失敗として扱わない。

### 要件4 外れた予約の付け直し

所有者は、予約が外れたら、誰が外したかに関係なく付け直してほしい。予約が外れたままだと、チェックが緑でも、誰かが気づくまでPRが止まるからである。

1. 対象のPRの自動マージの予約が外れたら、予約のワークフローは、外した者と外れた理由に依らず、予約を付け直す。
2. 開いていて下書きでない対象のPRに、予約が付いていない状態が1時間続いたら、予約のワークフローは、予約が外れたことの知らせを受け取っていなくても、予約を付け直す。
3. 同じコミットで予約が3回を超えて外れたら、予約のワークフローは、そのコミットではそれ以上付け直さず、所有者に知らせる。
4. 付け直しを止めたPRに新しいコミットが積まれたら、予約のワークフローは、そのPRへの予約を再開する。
5. PRが閉じられたか、マージされたら、予約のワークフローは、そのPRに予約を付け直さない。

### 要件5 予約に失敗したときの知らせ

所有者は、予約を付けられなかったときは知らせてほしい。予約が付いていないことに気づけないと、所有者は、PRが止まっていることにも気づけないからである。

1. 自動マージの予約または付け直しに失敗したら、予約のワークフローは、所有者に知らせる。
2. 予約のワークフローは、知らせに、対象のPR番号、失敗した操作、所有者にしてほしいことを書く。
3. 予約のワークフローは、同じPRの同じコミットについて、同じ内容の知らせを繰り返し出さない。
4. 知らせを出したPRに予約が付いたら、予約のワークフローは、所有者がそのPRに対して何もしなくてよい状態になったことを、知らせを出した場所で分かるようにする。

### 要件6 既存のゲートと運用の維持

所有者は、予約とクローズを仕組みに任せても、今の安全性が下がらないようにしたい。

1. 予約のワークフローは、必須チェックと必要な承認を迂回する権限を使わず、マージの可否を既存のゲートの判定に任せる。
2. 予約のワークフローは、PRが書き換えた内容を、書き込みの権限を持たせて実行しない。
3. 予約のワークフローは、マージを起点とする既存の後続の処理(依存関係の記録など)が起動する方法で予約する。
4. 予約のワークフローは、`pre-merge-check` ラベルによる保留の判定を変えず、ラベルの有無に依らず予約する。保留は、既存の必須チェックが行う。
5. クローズのワークフローは、書き込みを、対応するIssueのクローズと記録、および所有者への知らせに限る。
6. 予約のワークフローとクローズのワークフローは、判定の部分を、自動テストで検証できる形で持つ。

### 要件7 手順と文書の整合

所有者は、文書に書かれた手順が実際の仕組みと一致していてほしい。AIが古い手順どおりに予約を操作し続けると、AIの操作と仕組みが二重になり、どちらが働いたのか分からなくなるからである。

1. Claude は、出荷手順(`/ship`)とCLAUDE.md で、自動マージの予約をAIの操作として求めず、仕組みが予約することを書く。
2. Claude は、出荷手順(`/ship`)の、PR本文に `Closes #<番号>` と `Refs: #<番号>` を書く決まりを残す。
3. Claude は、READMEのワークフロー一覧表とMermaid図を、追加・変更したワークフローの内容と一致させる。
4. Claude は、運用文書に、予約を手で外しても付け直されること、マージを保留するには `pre-merge-check` ラベルを使うこと、知らせを受け取ったときの対処を書く。
5. Claude は、導入のPRの本文に、人間が導入後に確認する手順を書く。人間が確認することは、所有者のアカウントで作ったPRに予約が付くこと、知らせが所有者に届くこと、仕組みが予約したPRのマージ後に既存の後続の処理(依存関係の記録など)が動いたこと、`pre-merge-check` ラベルを付けたPRが所有者の承認までマージされないことである。
6. Claude は、運用文書に、導入のときに1回だけ行う作業の手順を書かない。
