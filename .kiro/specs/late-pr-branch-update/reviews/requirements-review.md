### 申告

**1. ワークフローがブランチを合わせられなかったPR(衝突など)は、出した Claude が直し、所有者には知らせない** — 範囲「決めないこと」の「所有者への知らせを足すこと」、要件2の1〜3

- Issue の記載: なし。Issue は「人が手でブランチを更新しなくても、main の最新に合わせられてマージまで進む」とだけ書き、衝突などで合わせられなかったときの扱いには触れていない
- 決めたこと: ワークフローは実行ログに残すだけで所有者に知らせない。`/ship` で出したPRは、Claude が main を取り込み、衝突を直して push し直す
- 他にありえた選択肢: ワークフローがPRへのコメントで所有者に知らせる(`auto-merge.yaml` が予約に失敗したときと同じ経路)。または、今のまま(ログに残すだけで、Claude の見届けも足さない)
- 外れていた場合: `/ship` のセッションが終わったあとに衝突したPR、`/ship` 以外で出されたPR(所有者のPR、Dependabot のPR)は、誰にも知らされずに止まる。Issue の「所有者が気づいて声をかけるまで、PRが止まったままになる」が、衝突の場合に残る

**2. PRを出したときにブランチを合わせる役を、ワークフローにした** — 要件1の1〜3

- Issue の記載: 「人が手でブランチを更新しなくても、main の最新に合わせられてマージまで進む」(AIの提案を了承)。誰が合わせるかは書いていない
- 決めたこと: `update-pr-branches.yaml` の起点に、PRを出したときを足す(ワークフローが合わせる)
- 他にありえた選択肢: `/ship` の手順で、PRを出す前に Claude が `git merge origin/main` を行うか、PRを出した直後に `gh pr update-branch` を打つ(ワークフローは変えない)
- 外れていた場合: ワークフローの変更は `.github/` 配下のため、Claude は書き込めず、所有者がファイルを置き、CODEOWNERS の承認を行うことになる。逆に `/ship` だけで済ませると、`/ship` を通らないPR(所有者が出すPR、下書きを解除したPR)は対象にならない。前者は手間、後者は対象の範囲の違いであり、どちらを取るかは所有者の判断になる

**3. Claude は、`/ship` で出したPRがマージされるまで見届けを終えない** — 要件2の3

- Issue の記載: 「所有者が気づいて声をかけるまで、PRが止まったままになる」(困っていること)
- 決めたこと: Claude がマージを確かめるまで見届けを続ける。承認待ちのときだけ報告して終える
- 他にありえた選択肢: 今の `/ship` のまま(必須の検査の結果を見届けて終える。out-of-date の対処は書いてあるが、マージまでは見届けない)。または、ワークフロー側に定期の見直しを足して、Claude の見届けに頼らない
- 外れていた場合: 必須の検査(container-scan は本番イメージの組み立てを含む)が終わってからマージされるまで、Claude のセッションが長く占有される。セッションが途中で終われば、見届けは成立しない

**4. PRを出したときに加えて、下書きの解除と開き直しのときも合わせる** — 要件1の2

- Issue の記載: なし
- 決めたこと: 下書きでなくしたとき、閉じたPRを開き直したときも、PRを出したときと同じく合わせる
- 他にありえた選択肢: PRを出したときだけにする
- 外れていた場合: PRを出したときだけにすると、下書きのまま main が進んだPR(下書きは今のワークフローの対象外)は、下書きを解除しても次の main への push まで止まる。影響は小さい

### 申告

**6. 衝突しているPRは、PRを出したあとに Claude が検査を待たずに直す(PRを出す前に main を取り込んでおく形にはしない)** — 要件2の3

- Issue の記載: なし。Issue は「人が手でブランチを更新しなくても、main の最新に合わせられてマージまで進む」とだけ書く
- 決めたこと: `/ship` で出したPRが main と衝突しているときは、Claude は必須の検査の結果を待たずに main を取り込んで衝突を直す
- 他にありえた選択肢: `/ship` の push の前(手順4の前)に Claude が `origin/main` を取り込み、衝突があればその場で直してからPRを出す。こうすると、衝突したままのPRは開かれず、PRを出したときのワークフロー(要件1の1)と必須の検査が最初から動く。または、衝突したPRは Claude が直さず所有者に報告して終える
- 外れていた場合: 選んだ形では、衝突したPRがいったん開かれ、検査もワークフローも自動マージの予約も動かない状態になる。Claude はPRを出した直後に衝突の有無を読む必要があり(GitHub が衝突の判定を終える前は値が定まらないため、design で待ち方を決める)、そのあとに手元での取り込みと品質チェックと push が入る。マージまでの時間は、PRを出す前に取り込む形と変わらないが、design の `/ship` の手順7に場合分けが1つ増える。逆にPRを出す前に取り込む形だと、PRを開いたあとに main が進んで衝突した場合は救えないので、要件2の2の取り込みはどちらにしても要る

**7. 必須の検査がすべて通ったのに自動マージの予約が付いていないときは、Claude が見届けを終える** — 要件2の4

- Issue の記載: なし
- 決めたこと: Claude は自分で予約を付けず、その状態を所有者に報告して見届けを終える
- 他にありえた選択肢: `auto-merge.yaml` の見直し(30分ごとの `sweep`)が予約を付け直すのを Claude が待つ。または、予約が付いていないことを報告したうえで、見届けは続ける(今の `/ship` の手順6はこの形)
- 外れていた場合: 見届けを終えたあとに `sweep` が予約を付けてマージされるときは、所有者への報告が空振りになるだけで困らない。予約が付かない原因が `reserve-auto-merge.sh` の判定(カナリア、fork など)にあるときは、見届けを続けても変わらないので、終える判断で正しい。影響は小さい
