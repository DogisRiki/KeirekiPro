### 申告

**1. 要件1の中心の動き(main より古いPRを出したときにワークフローが合わせ、検査がやり直されてマージされる)は、実装のPR自身では確かめず、マージのあとの実際の作業のPRで確かめる** — タスク3.1の説明の文と完了の確かめ方、`## 実装のメモ`

- Issue の記載: 「main に最後に push されたあとに出したPRも、人が手でブランチを更新しなくても、main の最新に合わせられてマージまで進む」
- 決めたこと: Claude は `/ship` の直前に `git fetch origin` と `git merge origin/main` でブランチを最新の main に合わせてから実装のPRを出す。そのため、実装のPRで確かめられるのは「すでに最新です」の経路(要件1の4)が主で、「最新化しました」の経路(要件1の1と5)は、PRを出すまでに main が進んだときにだけ確かめられる。要件1の1・2・5と要件2の1・3は、PR本文に書く「導入のあとの実地の確かめ」として、マージのあとの実際の作業のPRで確かめる(design の `## テストの方針` が「確かめのためだけのPRを作らない」と決めたことに沿う)。テストの省略可能な印(`- [ ]*`)は使っていない
- 他にありえた選択肢: `/ship` の直前に main を取り込まず、ブランチが main より古いまま実装のPRを出し、PRの起点の実行が update-branch を呼んで検査がやり直されることを実装のPR自身で確かめる(ワークフローの定義はPRのブランチのものが使われるので、この経路も実装のPRで動く)。または、基盤構築手順の8と同じ検証用のPRを作る
- 外れていた場合: PRの起点の処理に誤り(PR1件の取り直しに `TARGET_FILTER` を当てる形、compare の API の呼び方、`behind_by` が1以上のときの update-branch の呼び方など)があっても、実装のPRでは「すでに最新です」までしか動かないので、所有者が承認してマージしたあとに次の古いPRが出るまで見つからない。見つかるときの症状は、Issue #511 と同じ「PRが out-of-date のまま止まる」になる

**2. design.md の手順7の記述を直さず、タスク2.1の文で置き換える(タスクの文が design.md より優先する)** — タスク2.1の説明の文とその下の4つの項
