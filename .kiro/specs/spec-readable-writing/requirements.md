# 要件

## 元の要望(Issue #474 の本文)

Issue #474: AIが書く spec を、所有者が読んで分かる書き方にする


### きっかけ

> AIエージェントが作成するrequirements.mdなどのspecファイルが人間が理解しずらい内容になる。要件はさすがにレビューしているので見ているのだが毎回理解に苦しむ。

### 困っていること

- AIが書く spec(requirements.md・design.md・tasks.md)の文章が分かりにくく、所有者は requirements を読むたびに理解に苦しむ
- 分かりにくいのは、次のような書き方である
  - 「The 着手の手順 shall …」のような、英語と日本語が混ざった定型文(AIの提案を了承)
  - 「要件9に従って」「受入基準4で」のような、番号で別の箇所を指す書き方(AIの提案を了承)
  - 「着手の手順」「起票の決まり」のような抽象的な言葉を主語にした言い回し(AIの提案を了承)
  - 目的語が抜けていて、何を直すのか、何を決めるのかが書かれておらず、文がぼやけている
- 同じことが何度も書かれている。文書が長いこと自体はかまわないが、同じことの繰り返しに見える

### やりたいこと

- 対象は、これから作る spec の requirements.md・design.md・tasks.md とする(AIの提案を了承)
- それらを、下の「どうなれば解決か」に載せた見本と同じ書き方で書く
- 文体は常体(だ・である調)にそろえる。敬語(です・ます調)と混ぜない
- design.md は、技術の中身を削らず、設計として成り立たせたまま、書き方だけを分かりやすくする
- 同じことの繰り返しを減らす。所有者は、繰り返しを減らせば結果として文書は短くなるのではないかと考えている

### どうなれば解決か

- これから作る spec の requirements.md・design.md・tasks.md が、次の見本と同じ書き方で書かれている。見本は、既存の spec の一部を所有者との壁打ちで書き直し、所有者が合格とした文章である
- AIが書いた spec に、この書き方から外れた文が残っていたら、所有者が承認のために読む前に、AIが見つけて直している(AIの提案を了承)

#### 見本1: requirements.md の要件1つ

元の文章: `.kiro/specs/memory-contamination-check/requirements.md` の Requirement 5

> #### 要件5 メモリを直すかどうかは所有者が決める
>
> メモリの多くは、所有者の指摘を Claude が書き留めたものである。Claude が自分の判断でメモリを書き換えると、その書き換えが新しい誤りになるおそれがある。そこで、メモリを直すかどうかは原則として所有者が決める。
>
> 1. 点検でメモリの記述に誤りの疑いを見つけたら、Claude は、どのメモリファイルのどの記述が疑わしいかと、その記述の直し方の案を所有者に見せる。誤りの疑いとは、古くなった事実、一度の出来事を一般の決まりとして書いたもの、根拠の書かれていない主張などを指す。所有者がその記述を直すかどうかを答えるまで、Claude はそのメモリファイルを書き換えない。
> 2. 所有者がその記述を直すと答えたら、Claude は、所有者が決めた直し方のとおりにその記述を書き換える。
> 3. 所有者がその記述を直さないと答えたら、Claude は「この記述は直さない」という所有者の答えを点検の記録に残す。そのあとの点検では、その記述の文面が変わらない限り、Claude は同じ記述を誤りの疑いとして挙げない。
> 4. Claude が所有者に見せた誤りの疑いのうち、所有者が直すか直さないかをまだ答えていないものは、次の点検の結果にも「所有者の答え待ち」として載せ続ける。
> 5. 例外として、目次(MEMORY.md)とメモリファイルが対応していないだけのときは、Claude が所有者に尋ねずに目次を直す。対応していないとは、目次に行があるのにメモリファイルが無いこと、またはメモリファイルがあるのに目次に行が無いことを指す。Claude は目次の行を足すか消して、実際のファイルに合わせる。メモリファイルの中身は書き換えない。目次を直したことは点検の結果に書く。ただし、そのメモリファイルに誤りの疑いや、誰かが会話の外で直接書き換えた疑いもあるときは、Claude は目次も直さず、1と同じく所有者に見せる。

#### 見本2: design.md の1節

元の文章: `.kiro/specs/issue-close-and-auto-merge-guarantee/design.md` の「auto-merge.yaml」の節

> ##### auto-merge.yaml(PRに自動マージの予約を付けるワークフロー)
>
> 対応する要件: 3.1, 3.2, 3.3, 3.5, 3.6, 4.1, 4.2, 4.4, 6.2, 6.3
>
> **役割**: このワークフローは、PRのイベントと定期実行で起動し、PRごとにスクリプト `reserve-auto-merge.sh` を呼び出す。予約を付けるかどうかはスクリプトが判定し、ワークフローは判定しない。
>
> **権限**: ワークフローに与える権限は、`contents: read`(コードを checkout するため)と `pull-requests: write`(PRに知らせのコメントを書くため)の2つに限る。予約の操作には、ボットのトークン `secrets.BOT_GITHUB_TOKEN` を使う。ワークフローはPRの変更内容を checkout しない。
>
> **PRのイベントで起動するとき(ジョブ `reserve`)**
> - 起動するイベント: main に向けた `pull_request` の `opened` `reopened` `ready_for_review` `synchronize` `auto_merge_disabled`
> - 動かす条件: PRが同じリポジトリのブランチから出されていて、作成者が `dependabot[bot]` でないこと。fork と Dependabot のイベントにはシークレットが渡されないので、スクリプトを呼ぶ前に、ジョブの条件で外す
> - 手順: ワークフローはPRの base のコミット(`github.event.pull_request.base.sha`)を、認証情報を残さない設定(`persist-credentials: false`)で checkout する。次に、スクリプトのテスト3本のうち予約に関わる2本を流す。最後に `reserve-auto-merge.sh <PR番号>` を呼ぶ
> - 同時実行: 同じPRのジョブは、`auto-merge-<PR番号>` の組で1つずつ動かす。あとから起動したジョブは、先に動いているジョブを止めずに、終わるのを待つ(`cancel-in-progress: false`)
>
> **定期実行で起動するとき(ジョブ `sweep`)**
> - 起動: 30分ごと(cron `7,37 * * * *`)と、手での起動(`workflow_dispatch`)
> - 手順: ワークフローは既定のブランチを checkout し、スクリプトのテストを流してから、`reserve-auto-merge.sh --sweep` を1回呼ぶ。対象のPRの一覧はスクリプトが取り、ワークフローはPRを選ばない
> - 失敗したとき: スクリプトは、同じPRに何度呼ばれても結果が変わらないように作る。スクリプトは1件の失敗では止まらずに残りのPRを続け、最後に1件でも失敗があればジョブを失敗にする。ワークフローは、PR1件ごとの呼び出しを120秒で打ち切る
> - 同時実行: `auto-merge-sweep` の組で1つずつ動かす(`cancel-in-progress: false`)。ジョブ全体は30分で打ち切る

### やらないこと

- いま作っている途中の spec(spec-need-triage、memory-contamination-check)と、出荷済みの spec は書き直さない。途中の spec は今の書き方のまま進める(AIの提案を了承)



## はじめに

Claude が書く spec(requirements.md・design.md・tasks.md)は、所有者が読んでも意味を取りにくい。英語と日本語が混ざった定型文、番号だけで別の箇所を指す書き方、まだ存在しない手順の名前を主語にした文、目的語の抜けた文が多く、同じ決めごとが何度も書かれている。所有者は承認のたびに requirements を読むが、毎回理解に苦しんでいる。

この spec では、Claude がこれから書く spec を、#474 に載せた見本1と見本2と同じ書き方で書くようにする。あわせて、書き方から外れた文が残っていたら、所有者が承認のために読む前に Claude が見つけて直すようにする。

## 範囲

この spec で決めることは、次のとおりである。

- Claude がこれから書く spec の requirements.md・design.md・tasks.md の書き方
- Claude が書いた spec から、書き方に外れた文を所有者が読む前に見つけて直すこと
- Claude が spec を書くときに従う決まりと雛形を、この書き方に合わせること

この spec で決めないことは、次のとおりである。

- requirements.md・design.md・tasks.md 以外の文書の書き方。#474 が対象にしたのはこの3つの文書であり、審査の記録(reviews/ の下のファイル)、research.md、Issue本文、PR本文、Claude から所有者への報告は含まない

この spec が前提にしていることは、次のとおりである。

- Claude が spec を書くときに従う決まりと雛形は `.claude/` と `.kiro/settings/` の下にある。`.claude/` の下を変える PR は、今の決まりにより、所有者が承認するまでマージされない

## 要件

### 要件1 新しい書き方を当てはめる spec

この要件は、新しい書き方をどの spec に当てはめるかを決める。

1. この spec の変更が main に入ったあとに作られた spec では、Claude は requirements.md・design.md・tasks.md のすべてを、この spec で決める書き方で書く。
2. この spec の変更が main に入った時点ですでに作られていた spec では、作っている途中のものも出荷済みのものも、Claude は、そのあとに書く段階を含めて今の書き方のまま書く。Claude は、それらの spec の本文を新しい書き方に書き直さず、書き方の点検の対象にもしない。

### 要件2 文の書き方

所有者が spec の文を一度読めば、誰が何をするのかが分かるようにする。この要件は、requirements.md・design.md・tasks.md のすべてに当てはまる。ただし、Issue本文や既存の文書から引用した部分は、引用元のまま残す。

1. Claude は、spec の本文を常体(だ・である調)で書く。敬語(です・ます調)を混ぜない。
2. Claude は、文ごとに、動作をする人や物(主語)と、動作の対象(目的語)を書く。主語を省くのは、同じ段落の直前の文と主語が同じときに限る。例外として、「起動: 30分ごと」のように「ラベル: 内容」の形で書く箇条書きでは、ラベルが主語や条件を示すので、内容の文で主語を省いてよい。
3. Claude は、主語を、実際に動く人や物(所有者、Claude、ワークフロー、スクリプトなど)にする。Claude は、まだ存在しない手順や仕組みに「〜の手順」「〜の仕組み」のような名前を付けて、それを主語にしない。
4. Claude は、「問題」「点」「対応」のように、何を指すかが文脈から決まらない言葉で文を済ませない。Claude は、指すものをその文の中で言い切る。たとえば、「問題を見つけたら」とは書かず、「メモリの記述に誤りの疑いを見つけたら」と書く。
5. Claude は、「The ○○ shall …」「When …, the ○○ shall …」のような、英語と日本語を混ぜた定型文を使わない。Claude は、見出しと欄の名前を日本語で書く。ただし、ファイル名、コマンド、設定の名前、イベント名のように、書き換えると指すものが変わる名前は、元の綴りのまま書く。
6. Claude は、文の中で別の要件や受入基準に触れるときに、番号だけで指さない。Claude は、触れる先の中身を同じ文の中で言葉にする。たとえば、「5-2 に従う」とは書かず、「1と同じく所有者に見せる」と書く。
7. 例外として、design.md の「対応する要件」の行と、tasks.md でタスクと要件の対応を示す行は、要件の番号だけで書く。これらの行は、文ではなく、どの要件を満たすかの対応表として使う。
8. Claude は、1つの文に、条件と例外と別の箇所への参照を重ねない。Claude は、原則を先に書き、例外はそのあとに別の文で書く。

### 要件3 文書の組み立て

文の書き方だけを直しても、英語の雛形の組み立てが残ると、文書は読みにくいままになる。そこで、文書の組み立ても見本1と見本2に合わせる。

1. Claude は、requirements.md の各要件を、「要件1 題名」のような番号と題名の見出し、所有者がなぜそれを望むのかを書いた段落、番号付きの項目の順で書く。Claude は、「所有者として、…したい」のような利用者の立場を名乗る行と、「受入基準」の小見出しを書かない。
2. Claude は、design.md の部品ごとの節を、部品の名前とその部品が何かを括弧で添えた見出し、対応する要件の行、「役割」「権限」のような日本語の欄の順で書く。
3. tasks.md には、#474 の見本が無い。Claude は、この spec の design.md に tasks.md の見本をタスク1つ分載せる。所有者がこの spec の design を承認したら、Claude はその見本を tasks.md の書き方の基準として使う。

### 要件4 design.md の書き方

design.md は、設計として成り立ったまま、所有者が読んで分かるものでなければならない。#474 の壁打ちで、所有者は、技術の中身を削って平易にした書き直しを「設計になっていない」と退けた。

1. Claude は、design.md を分かりやすくするために、技術の中身を削らない。Claude は、イベント名、権限、設定の値、時間の上限、コマンドの引数のように、実装に要る情報を design.md に残す。
2. Claude は、design.md の部品ごとに、その部品が何をして何をしないのかを、主語と目的語のある文で書く。
3. Claude は、専門用語(冪等など)を使うときは、その語が何を意味するかを同じ文か直後の文に書く。

### 要件5 同じことの繰り返し

同じ決めごとが何度も書かれていると、所有者は同じ内容を繰り返し読むことになる。文書が長いこと自体はかまわない。所有者は、繰り返しを減らせば、結果として文書は短くなるのではないかと考えている。

1. Claude は、1つの文書の中で、同じ決めごとを言い換えて複数の節に書かない。
2. Claude は、design.md と tasks.md に、requirements.md に書いた決めごとを書き写さない。design.md には、requirements.md の決めごとをどう実現するかを書く。tasks.md には、どの順番で何を作るかを書く。
3. 例外として、tasks.md で、受入基準とそれを確かめるテストの対応を示すために受入基準を引くことは、書き写しに当たらない。

### 要件6 書き方から外れた文の点検

所有者が承認のために spec を読む時点では、書き方から外れた文が残っていないようにする。

1. Claude は、新しい書き方で書く spec について、各段階の本文を書いたあと、所有者に承認を求める前に、その本文の全体がこの spec で決めた書き方に沿っているかを点検する。この spec で決めた書き方とは、文の書き方、文書の組み立て、design.md の書き方、同じことの繰り返しの扱いを指す。
2. Claude は、spec の審査(`/spec-review`)の指摘を受けて本文を直したときも、所有者に承認を求める前に、直したあとの本文を同じく点検する。
3. 点検で書き方から外れた文を見つけたら、Claude は、所有者に承認を求める前にその文を書き直す。Claude は、書き直すときに、文が述べている決めごとの中身を変えない。
4. 書き方に沿うように書き直すと決めごとの中身が変わってしまう文があったら、Claude はその文を書き直さない。Claude は、所有者に承認を求めるときに、その文と、書き直さなかった理由を所有者に示す。
5. Claude は、点検した日時と、書き直した文の数と、書き直さなかった文を、spec のディレクトリに記録として残す。この記録は所有者が読むためのものではない。Claude が点検をしたかどうかを、機械で確かめるために使う。
6. 本文を最後に書き直したあとの点検の記録が無いまま、Claude が所有者に承認を求めようとしたら、Claude の作業はそこで止まる。審査の指摘を受けて本文を直したあとに点検し直していない場合も、記録が無い場合と同じく作業は止まる。

### 要件7 Claude が従う決まりと雛形

Claude が spec を書くときに従う決まりが新しい書き方と食い違っていると、Claude は古い書き方に戻ってしまう。そこで、決まりと雛形を新しい書き方に合わせる。

1. Claude は、spec を書くときに従う決まりと雛形から、この spec で決めた書き方と食い違う指示を取り除く。たとえば、英語の定型文を残す指示や、英語の見出しを使う雛形を取り除く。
2. Claude は、spec を書くときに、#474 の見本1(requirements.md の要件1つ)と見本2(design.md の1節)、それにこの spec の design.md に載せる tasks.md の見本を、書き方の基準として読める。
3. Claude は、見出しや欄の名前を日本語に変えたあとも、spec を読んで動く手順と検査が、変える前と同じように spec を読み取って動くようにする。spec を読んで動く手順と検査とは、実装の `/kiro-impl`、検証の `/kiro-validate-impl`、審査の `/spec-review`、PR に spec が付いているかを確かめる検査(`check-spec-backing.sh`)を指す。たとえば、`/kiro-impl` は tasks.md のタスクの箱(`- [ ]`)、タスク番号、依存や中断の注記を読んでタスクの順番を決めるので、新しい書き方の tasks.md でも同じ判定ができるようにする。
