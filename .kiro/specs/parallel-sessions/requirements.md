# 要件

## 元の要望
Issue #481: 複数のセッションで別々のIssueを並行して進められるようにする

### きっかけ

2つのセッションで別々の spec を同時に進めようとしたとき、worktree で開いたセッションでは品質チェックが本体フォルダを検査すると分かった(2026-10-03)。
「そもそもこのissueは複数セッションでworktreeなどで並列で動かした場合を考慮されていないことを言っています」(所有者、2026-10-04)

### 困っていること

開発の仕組みが、複数のセッションを並行して動かすことを考えて作られていない。
例えば、worktree で開いたセッションで品質チェックを走らせると、そのセッションの変更ではなく本体フォルダのファイルが検査され、合格と出る。

### やりたいこと

複数のセッションで別々のIssueを並行して進めたい。

spec で進めるIssueも、spec 無しで進めるIssueも対象にする。(AIの提案を了承)

所有者は各セッションで `/start #N` を打つ以外に、セッションどうしの使い分けや準備を意識しなくて済むようにする。(AIの提案を了承)

### どうなれば解決か

- 同時に動かせるセッションの数は、所有者が設定で変えられる。作業PCのメモリを増やしたときに、数を増やせるようにするため。
- 設定の初期値は1とする。(AIの提案を了承)
- 設定した数までのセッションで別々のIssueを同時に進め、どのセッションも `/start` から `/ship`(PRに自動マージの予約が付くところ)までを、ほかのセッションを止めたり、ほかのセッションが作業中のファイル・ブランチ・PRを変えたりせずに終えられる。確かめ方: 2つのセッションを同時に動かして確かめる。(AIの提案を了承)
- 各セッションの品質チェックと画面確認(`/verify-ui`)の結果は、そのセッションの変更だけを反映する。確かめ方: 1つのセッションでわざとテストを壊すと、壊した側だけが失敗し、ほかのセッションは合格する。(AIの提案を了承)
- 設定した数のセッションの品質チェックが走っているときに、別のセッションの品質チェックが走ろうとしたら、そのセッションを待たせてよい。設定した数までのセッションの品質チェックは、待たずに同時に走る。同時に走ったことが原因で失敗や合格が出ることは無い。待たされているときは、そのセッションにそのことが示される。(AIの提案を了承)
- セッションを開いたあと、所有者がセッションごとに手で行う準備は無い(最初に一度だけ行う準備は除く)。(AIの提案を了承)
- 同じIssueを別のセッションでも始めようとしたとき、後から始めたセッションがそれに気づいて止まる。(AIの提案を了承)

### やらないこと

- 同じ作業フォルダ(worktree を使わない1つのフォルダ)で、複数のセッションを同時に動かすこと。(AIの提案を了承)
- 設定した数を超えるセッションで、品質チェックと画面確認を同時に走らせること。(AIの提案を了承)

## はじめに

この spec でいうセッションは、所有者が Claude Code で開く会話の1つを指す。所有者は、セッションを開くときに worktree を選ぶと、そのセッション専用の作業フォルダ(本体フォルダとは別のフォルダ)を持たせられる。

今の開発の仕組みは、作業フォルダが1つで、セッションも1つだけ動くことを前提に作られている。そのため、所有者が別々のセッションで別々のIssueを同時に進めると、仕組みのいくつかが正しく動かない。たとえば、worktree で開いたセッションで品質チェックが走ると、品質チェックは、そのセッションの変更ではなく本体フォルダのファイルを検査し、合格と出す。

この spec は、所有者が複数のセッションで別々のIssueを並行して進められるようにする。あわせて、この spec は、同じIssueや同じ作業フォルダを2つのセッションで使おうとしたときに、Claude がどうするかを決める。

## 範囲

- この spec で決めること:
  - 複数のセッションが、それぞれ着手から出荷までを、ほかのセッションの作業を変えずに進めること
  - 各セッションの品質チェックと画面確認が、そのセッションの変更を検査すること
  - 品質チェックと画面確認を同時に走らせるセッションの数の設定と、数を超えたときの待ち方と知らせ方
  - 同じIssueを2つのセッションで始めようとしたときと、同じ作業フォルダで2つ目のセッションを始めようとしたときの、Claude の動き
  - 並行して進めるための所有者の準備と、その案内
- この spec で決めないこと:
  - 同じ作業フォルダの中で、複数のセッションを同時に動かせるようにすること。この spec は、そうなったときに Claude が気づいて止まるところまでを決める
  - PRで走るチェック(GitHub Actions)。PRのチェックは、今のまま、PRの変更を検査する
  - 定期実行のループ(`/loop`)の動き
  - クラウドで動くセッションとの並行。クラウドのセッションは作業PCの開発環境を使わないため、この spec の対象にしない
  - 3段階の承認、200行の検査(size-check)、出荷の手順そのもの(コミット・PR・自動マージの予約の決まり)の変更
- この spec が前提にしていること:
  - 所有者は、並行して進めるセッションを、worktree を選んで開く。worktree を選ばずに本体フォルダで開くセッションは、同時に1つまでとし、ほかの worktree のセッションと並行してよい
  - 1つのセッションの中では、Claude は今の決まりのとおり、品質チェックのコマンドを1つずつ順に走らせる
  - この spec の変更の多くは、所有者の承認が要るファイル(`.claude/` の下など)に及ぶ。そのため、この spec のPRは、所有者が承認するまで自動ではマージされない

## 要件

### 要件1 どのセッションも、ほかのセッションの作業を変えずに着手から出荷まで進める

所有者が別々のセッションで別々のIssueを進めているときに、片方のセッションの作業がもう片方のファイルやブランチを書き換えると、所有者が気づかないうちに作業が混ざる。そこで、どのセッションも、自分の作業フォルダ・ブランチ・PRの中だけで着手から出荷までを進める。

1. 所有者が別々のセッションで別々のIssueに `/start` を打ったら、Claude は、セッションごとに、そのセッションの作業フォルダの中だけで spec・変更・コミットを作る。Claude は、ほかのセッションの作業フォルダのファイルを書き換えない。ただし、同じIssueを別のセッションで始めようとしたときに、Claude が所有者の答えを受けて同じIssueの作りかけを引き継ぐ場合に限り、Claude は前のセッションの作業フォルダの作りかけの spec と変更を扱ってよい。所有者の答えが「前のセッションはやめた」でも「続きから進める」でも、引き継ぐときはこの例外に当たる。
2. Claude は、セッションごとに、そのセッションのIssueのためのブランチで作業する。Claude は、ほかのセッションのブランチに切り替えず、ほかのセッションのブランチにコミットしない。
3. Claude は、そのセッションの変更を、ほかのセッションの変更を含めずに `/ship` で出荷する。`/ship` は、worktree の作業フォルダでも本体フォルダでも、コミットからPRの作成、自動マージの予約の確認、CIの見届けまでを同じように終える。
4. CIの見届けと、Codex のレビューの指摘への対応(`/review-loop`)では、Claude は、そのセッションで出したPRだけを扱う。Claude は、ほかのセッションが出したPRを直さない。
5. Claude は、開発サーバの起動や停止をするときに、ほかのセッションが走らせている品質チェック・テスト・開発サーバを止めない。

### 要件2 品質チェックと画面確認は、そのセッションの変更を検査する

品質チェックが別のフォルダのファイルを検査して合格と出ると、Claude は検査していない変更を合格として所有者に報告してしまう。PRのチェックが最後にその変更を止めるとしても、所有者に届く報告は誤りになり、直しの往復も増える。そこで、各セッションの品質チェックと画面確認は、そのセッションの変更を検査する。

1. Claude があるセッションで品質チェック(`/verify-frontend` `/verify-backend` `/verify-terraform`、およびそれらをまとめて走らせる `/verify-all`)を走らせたら、品質チェックは、そのセッションの作業フォルダのファイルを検査する。
2. Claude があるセッションで画面確認(`/verify-ui`)を走らせたら、画面確認の画面には、そのセッションの作業フォルダの変更が表示される。
3. 2つのセッションが並行しているときに、所有者または Claude が片方のセッションでわざとテストを壊して品質チェックを走らせると、壊した側のセッションの品質チェックだけが失敗し、もう片方のセッションの品質チェックは合格する。
4. 品質チェックがそのセッションの作業フォルダのファイルを検査できないとき(検査のための環境が用意できないときなど)は、Claude は品質チェックを合格として扱わない。Claude は、検査できなかったことと、その理由を所有者に報告する。
5. Claude が作業を終える前に品質チェックを済ませたかどうかを判定するときは、そのセッションの変更に対して走らせた品質チェックだけを数える。Claude は、ほかのセッションが走らせた品質チェックを、このセッションの品質チェックとして数えない。
6. 品質チェックが出すテストの結果やカバレッジの結果は、セッションごとに分かれる。あるセッションの品質チェックは、ほかのセッションの品質チェックの結果を上書きしない。

### 要件3 同時に走らせる数を所有者が設定で変えられ、数を超えたら待つ

品質チェックと画面確認は作業PCのメモリを多く使う。同時に走る数が多すぎると、テストがメモリ不足で落ち、同時に走らせたことが原因の失敗が出る。一方で、作業PCのメモリを増やせば、同時に走らせられる数は増やせる。そこで、同時に走らせる数は、所有者が設定で変えられるものとする。数を超えたセッションのチェックは、番が来るまで待つ。所有者は、待ちが起きそうなことを着手のときに知りたい。

1. 所有者は、品質チェックと画面確認を同時に走らせられるセッションの数を、1か所の設定で変えられる。設定の初期値は1とする。所有者が数を変えるときに、設定のほかに書き換えるファイルは無い。
2. 設定の数のセッションが品質チェックまたは画面確認を走らせているときに、別のセッションで Claude が品質チェックまたは画面確認を始めようとしたら、そのセッションの品質チェックまたは画面確認は、走っているものが1つ終わるまで待ってから始まる。品質チェックまたは画面確認を走らせているセッションの数が設定の数に達していないときは、Claude は、そのセッションの品質チェックまたは画面確認を、待たずにすぐ始める。品質チェックを走らせている間とは、品質チェックのコマンドが始まってから終わるまでを指す。画面確認を走らせている間とは、`/verify-ui` の手順が始まってから、Claude が画面の確認を終えるまでを指す。画面の確認を終えたあとも動き続けている開発サーバは、この数に入らない。
3. あるセッションの品質チェックまたは画面確認が待っている間は、Claude は、そのセッションで、待っていることと、どのセッションのIssueのチェックを待っているかを所有者に示す。
4. 複数のセッションの品質チェックと画面確認が同時に走っても、同時に走ったことが原因で失敗や合格が出ることは無い。
5. 決めた時間を待っても番が来なければ、Claude はそのセッションでの待ちをやめ、どのセッションのIssueのチェックを待っていたかを所有者に報告する。このとき、Claude は品質チェックを合格として扱わない。Claude は、品質チェックと画面確認に実際にかかる時間を測ったうえで、待つ時間の長さを設計の段階で決める。
6. 所有者があるセッションで `/start` を打ったときに、ほかに作業中のセッションの数がすでに設定の数に達していたら、Claude は着手を続けたうえで、セッションが埋まっていることを所有者に報告する。報告には、作業中のセッションのIssueの番号と、このセッションの品質チェックと画面確認が順番待ちになることがあることを含める。作業中のセッションとは、所有者が開いたままにしていて、`/start` で着手したIssueの作業を続けているセッションを指す。Issueが開いたままでも、所有者が閉じたセッションや、所有者が「やめた」と答えたセッションは、作業中のセッションに当たらない。同じIssueの作りかけが残っている作業フォルダで作業中のセッションがあるかどうかと、同じ作業フォルダで作業中の別のセッションがあるかどうかを Claude が見分けるときも、作業中かどうかをこの意味で判定する。

### 要件4 同じIssueを2つのセッションで始めようとしたら、あとのセッションが止まる

同じIssueを2つのセッションで進めると、同じIssueの spec やブランチが二重にでき、どちらが正しいか分からなくなる。今は、Claude が自分の作業フォルダの中しか探さないため、ほかのセッションで作りかけの spec に気づかない。一方で、所有者は、途中でやめたセッションのIssueに、別のセッションで続きから着手できなければならない。

1. 所有者があるセッションで `/start #N` を打ったときに、いずれかの作業フォルダにIssue #N の作りかけが残っていたら、Claude は着手せずに止まる。いずれかの作業フォルダには、このセッションの作業フォルダも含む。作りかけがこのセッションの作業フォルダに残っているときは、Claude は、その作業フォルダで作業中のセッションが無いときと同じく、続きから進めるかどうかを所有者に尋ねる。Issue #N の作りかけとは、Issue #N の spec、Issue #N のためのブランチ、Issue #N のためのまだコミットしていない変更のどれかを指す。Claude は、作りかけが残っている作業フォルダの場所と、その作業フォルダで作業中のセッションがあるかどうかを所有者に知らせる。止まるまでの間に、Claude は spec もブランチも作らない。
2. Issue #N の作りかけが残っているかどうかを調べるときは、Claude は、作業フォルダごとに、その作業フォルダのセッションが開いているかどうかを問わずに調べる。spec の無いIssueの作りかけも、Claude はIssueの番号で見分ける。
3. 作りかけが残っている作業フォルダで作業中のセッションがあるときは、Claude は、所有者に前のセッションをやめたかどうかを尋ねる。所有者が「前のセッションはまだ進めている」と答えたら、Claude は、このセッションではIssue #N の作業をしない。所有者が「前のセッションはやめた」と答えたら、Claude は、作りかけを引き継ぐ。
4. 作りかけが残っている作業フォルダで作業中のセッションが無いときは、Claude は、所有者に前のセッションの続きから進めるかどうかを尋ねる。所有者が「続きから進める」と答えたら、Claude は、作りかけを引き継ぐ。所有者が「続きから進めない」と答えたら、Claude は、このセッションではIssue #N の作業をせず、作りかけが残っている作業フォルダの場所を所有者に示す。
5. Issue #N のためのブランチが残っていて、そのブランチがどの作業フォルダでも開かれていないときも、Claude は着手せずに止まる。この状態は、たとえば、Claude が200行の検査で止まったPRを閉じてブランチを残し、そのあとで所有者がそのセッションと作業フォルダを閉じたときに起きる。Claude は、残っているブランチの名前を所有者に示し、そのブランチの続きから進めるかどうかを尋ねる。所有者が「続きから進める」と答えたら、Claude は、そのブランチを作りかけとして引き継ぐ。所有者が「続きから進めない」と答えたら、Claude は、このセッションではIssue #N の作業をせず、残っているブランチの名前を所有者に示す。
6. Claude が作りかけを引き継ぐときは、前のセッションの作りかけの spec と変更を失わずに、このセッションでIssue #N を続ける。引き継いだあと、Claude は、spec の進み具合と次の手順を所有者に示す。引き継いだあとは、Claude は、Issue #N を進めているセッションをこのセッションだけとして扱う。そのため、所有者がさらに別のセッションで `/start #N` を打つと、Claude は、作りかけを引き継いだセッションがIssue #N を進めていると知らせて止まる。前のセッションの作業フォルダに作りかけが残っていても、Claude はそれを、Issue #N を進めている作りかけとして数えない。

### 要件5 同じ作業フォルダで2つ目のセッションを始めようとしたら、あとのセッションが止まる

同じ作業フォルダで2つのセッションが進むと、片方がブランチを切り替えたときに、もう片方の作業が気づかないうちに別のブランチに入る。所有者は、worktree を選び忘れたときにも、選び忘れたことに気づきたい。

1. ほかのセッションが作業中の作業フォルダで、所有者が別のセッションを開いて `/start` を打ったら、Claude は、ファイルもブランチも変えずに止まる。Claude は、同じ作業フォルダで別のセッションが作業中であることと、worktree を選んでセッションを開き直すよう所有者に知らせる。
2. 所有者が「前のセッションはやめた」と答えたら、Claude は、あとから開いたセッションで `/start` の手順を続ける。

### 要件6 所有者は、セッションを開いて `/start` を打つだけで並行して進められる

所有者は、セッションごとの準備や、どのセッションで何をしてよいかの使い分けを意識したくない。そこで、所有者がセッションごとにする操作は、セッションを開くことと `/start` を打つことに限る。最初に一度だけ要る準備は、Claude が運用の文書に手順を残す。

1. 所有者が worktree を選んでセッションを開き、`/start #N` を打ったら、Claude は、そのセッションで品質チェックと画面確認を走らせるための準備を、所有者に頼まずに済ませる。所有者は、セッションごとに、ファイルを写したり、検査の環境を起動したり、設定を書き換えたりしない。
2. 作業PCごとに最初に一度だけ所有者が行う準備があるときは、Claude は、その準備の手順を運用の文書に書く。
3. Claude は、並行して進めるときの所有者の操作(worktree を選んでセッションを開くこと、同時に走らせる数の設定の変え方)を、運用の文書に書く。
4. Claude は、CLAUDE.md・スコープ別の CLAUDE.md・steering のうち、作業フォルダが1つでセッションも1つだけ動くことを前提にした記述を、並行して進めることに合わせて書き直す。
