# 要件

## 元の要望

監査の自動化(#310)。週次・月次の定期監査のうち自動化対象を3本のワークフローに置き換える。

対象範囲(Issue #310 の段階1〜3のみ。段階4=文書削減の残り・段階5=メトリクス記録は本specの対象外):

1. `audit-weekly.yaml`: 週次8(定期スキャンの稼働確認。前回成功から8日で赤)と週次6(赤で止まっているDependabot PRの検知)、必須チェックがスキップで通ったPRの検知。AI呼び出し0回・履歴保存なし・外部問い合わせなし
2. `ci.yaml` への死活1ステップ: 直近の監査ワークフローの成功が10日以内に無ければ赤(API 1リクエスト)。段階1と同一PRとする
3. `canary-verify.yaml`: 月初3日後に発火し、カナリアPR6件の結論を期待値と3値判定で照合する(`failure`=正常 / `success`=判定側の故障 / `skipped`=実行されていない)。カナリアPRのcloseはしない

決定済みの制約(Issue #310 の「採らないと決めたこと」と判定表に従う。要件生成で再検討しない):

- 逸脱はワークフローを赤で終わらせるだけとし、修正PRの自動作成はしない(監査が直す対象はゲート自身であり、自己検査の循環を作らないため)
- AIに判定させない(費用と、事実の基点が無い構造のため)
- Dependabotへの操作(`@dependabot recreate` 等)は自動化しない(1回の誤判断で復旧経路が無くなるため)
- 外部の死活監視サービスは使わない(リポジトリ外部へのデータ送信に該当するため)
- 廃止・凍結が確定した6項目(週次2・3・4・5・7、月次3)は対象外(PR #330 で文書反映済み)

背景(2026-09-03 の実測。本specの動機):

- codex-review は `vars.CODEX_REVIEW_ENABLED` 未設定により全実行が skipped だが、必須チェックのスキップは成功として扱われるため、既存の16項目のどれも検知しなかった
- 必須チェックの一覧はGitHubのruleset側にしか存在せず、リポジトリのファイルに無い
- 2026-09-01 生成のカナリア点検で、known-bug の codex-review が skipped のまま起票されなかった(スキップ=検出漏れの実例)

## はじめに

人間は、これまで定期的に画面を開いて監査項目を確かめてきた。この spec は、そのうち機械で判定できる3つの領域(定期スキャンの稼働確認、Dependabot PRの滞留検知、カナリア点検)と、新しい1つの領域(必須チェックのスキップ検知)を、リポジトリ内のワークフローによる自動の監査へ置き換える。監査のワークフローは、逸脱の通知に、GitHub既定の「ワークフロー失敗の通知」だけを使う。監査自体が止まったことは、通常のPRのCIが検知する。

## 範囲

- この spec で決めること: Issue #310 の段階1(週次監査ワークフロー)、段階2(CIによる監査の死活検知。段階1と同一PR)、段階3(カナリア照合ワークフロー)
- この spec で決めないこと: 段階4の残り(自動化が引き受けた節の文書削除)、段階5(メトリクス記録)、廃止・凍結済みの6項目、カナリアPRのclose(翌月の生成側が行う)、逸脱の自動修正、Dependabotへの操作、外部サービスの利用。この spec は、**チェック失敗以外のPR滞留**(mainより遅れたまま緑で停止・ブランチ自動更新の失敗・マージ衝突・アラートがあるのにPRが作られない)の検知を自動化しない。この滞留の検知は、既存の失敗通知と、監査手順に残す人間向けの対処手順(現行の週次6のサブ手順。段階4の削除対象から除外する)に委ねる。**月次3の残骸**(ワークフローとスクリプトのコメント内に残るretrospective参照2箇所)は実害が無いため、この spec では触れず、段階4で扱う
- この spec が前提にしていること: カナリアPR6件は、既存の生成側(毎月1日に自動生成)が作る。必須チェックの構成は、GitHubのruleset側に定義がある。逸脱時の人間への通知は、GitHubの既定機能(失敗したワークフローの通知)に乗る。この spec は、新しい通知経路を作らない。導入時点ではcodex-reviewが停止中(#166)のため、期待一覧の初期値はcodex-reviewを「停止中(参照: #166)」として記録する。この記録により、codex-reviewを止めたままこの spec を導入しても、週次監査・死活・カナリア照合が誤って赤になり続けない。この記録は、Issue #310の「codex-reviewを止めたまま進められる」という依存関係の宣言と整合させるためのものである

## 要件

### 要件1 定期スキャンの稼働確認(週次8の置き換え)

運用者は、稼働中イメージの脆弱性監視が動き続けていることを、画面を開かずに保証したい。「起きなかったこと」には、人間が気づけないからである。

1. 週次監査が実行されたら、週次監査は、稼働中イメージの定期脆弱性スキャンの直近の成功実行を確認する。
2. 定期スキャンの直近の成功から8日以上経過していたら、週次監査は失敗として終了し、最後に成功した日時を報告に含める。
3. 定期スキャンの成功実行が一度も存在しなければ、週次監査は失敗として終了し、成功実行が一度も存在しない旨を報告に含める。
4. 定期スキャンの直近の成功からの経過が8日未満なら、週次監査は、定期スキャンの稼働確認の項目を成功として扱う。

### 要件2 滞留しているDependabot PRの検知(週次6の置き換え)

運用者は、Dependabotの更新PRが赤のまま止まっていることを、一覧画面を開かずに知りたい。dockerレーンの滞留は、そのままイメージの更新停止を意味するからである。

1. 週次監査が実行されたら、週次監査は、openのDependabot PRそれぞれについて、必須チェックの失敗の有無を確認する。
2. 必須チェックの失敗で止まっているDependabot PRが1件以上あれば、週次監査は失敗として終了し、対象のPR番号と失敗しているチェック名を報告に含める。
3. 必須チェックの失敗で止まっているDependabot PRが1件も無ければ、週次監査は、Dependabot PRの滞留検知の項目を成功として扱う。週次監査は、チェック実行中のPR、チェックがすべて緑のPR、所有者の承認待ちのみで停止しているPRを、異常として扱わない。
4. 週次監査は、滞留の件数にしきい値を設けず、失敗で止まっているPRの有無だけで判定する。
5. 週次監査は、チェック失敗以外の滞留(mainより遅れたまま緑で停止・ブランチ自動更新の失敗・マージ衝突・アラートがあるのにPRが作られない)を判定の対象にしない。週次監査は、これらの滞留を、既存の失敗通知と、監査手順に残す人間向けの対処手順に委ねる。

### 要件3 必須チェックがスキップで通ったPRの検知(新規)

運用者は、必須チェックがスキップのままマージされたPRを検知したい。スキップは成功として扱われるため、意図的に止めたチェックと事故で止まったチェックが同じに見えるからである。

1. リポジトリは、必須チェックの期待一覧を、リポジトリ内のファイルとして保持する。
2. 期待一覧は、チェックごとに「稼働中」または「停止中(停止の理由と参照Issueを添える)」の状態を記録できる。
3. リポジトリは、停止中の記録の追加と変更に、所有者の承認を要する。停止中の記録の追加と変更は、一覧ファイルの変更として承認ゲートを通る。
4. 週次監査が実行されたら、週次監査は、リポジトリ内の期待一覧とGitHub側の必須チェック設定を照合する。不一致があれば、週次監査は失敗として終了し、差分を報告に含める。週次監査は、この照合をチェック名の集合で行う。週次監査は、稼働中と停止中の状態をこの照合には用いず、スキップのままマージされたPRを失敗とするか、停止中として報告するかの判定(この要件の項目6と項目7)にだけ用いる。
5. 週次監査が実行されたら、週次監査は、前回の週次監査の実行以降にマージされたPRについて、変更内容から実行されるべきだった必須チェックがスキップのまま通っていないかを確認する。前回の実行が存在しない初回は、週次監査は直近7日間を対象とする。
6. 実行されるべきだった必須チェックがスキップのままマージされたPRがあり、そのチェックが期待一覧で「稼働中」なら、週次監査は失敗として終了し、対象のPR番号とチェック名を報告に含める。
7. スキップされたチェックが期待一覧で「停止中」と記録されていれば、週次監査はそのスキップを失敗とせず、停止中である旨と参照Issueを報告に明示する。週次監査は、記録された停止と事故による停止を、記録の有無で見分けられるようにする。
8. スキップが、変更内容の検知によって対象外と判定されたことによるもの(例: backend変更の無いPRのbackendテスト)なら、週次監査はそのスキップを異常として扱わない。

### 要件4 監査自体の死活検知(段階2)

運用者は、監査ワークフロー自体が止まったことを、番人の連鎖を作らずに知りたい。監査を監視する専用の仕組みを作ると、「それを誰が監視するか」の入れ子になるからである。

1. PRのCIが実行されたら、CIは、週次監査の直近の成功実行を確認する。
2. 週次監査の成功が10日以上無ければ、CIはそのPRのCIを失敗として終了し、監査が止まっている旨を報告に含める。
3. 週次監査がまだ一度も実行されていない期間(導入直後)なら、CIはこの確認を失敗として扱わない。
4. 死活確認は、PRが1本も作られない期間には作動しない。その期間は監査が止まっていても出荷が無いため、論理的に許容する。

> 注記(2026-09-25): 本要件は audit-notification spec(#347)の要件4で置き換えた。死活確認は週次監査の「成功」ではなく「完了」(結論を問わない)を見て、完了した実行が10日以上無い場合に失敗とする。理由: 週次監査は逸脱ありでも成功で終わるように改めたが、成功だけを数えると、逸脱が続く限りPRのCIが止まり、逸脱を直すPRもマージできなくなるため。本文は監査証跡として当時のまま残す。

### 要件5 カナリア点検の照合(月次1の置き換え・判定まで)

運用者は、毎月のカナリアPR6件が期待どおりのチェックで赤になっていることを、PRを1件ずつ開かずに確認したい。カナリア点検には、唯一の実施回で検出漏れを見逃した実績があるからである。

1. 毎月の照合の実行時(カナリア生成の3日後)に、カナリア照合は、当月のカナリアPR6件それぞれについて、種別ごとに定義された期待チェックの結論を取得する。
2. 期待チェックの結論が failure なら、カナリア照合は、その種別を正常(検査が問題を検知した)と判定する。
3. 期待チェックの結論が success なら、カナリア照合は、その種別を「実行されたが検知しなかった(判定側の故障)」として失敗と判定する。カナリア照合は、結論だけで分類する。実行内部の状態の切り分けと原因の調査は、人間が行う。
4. 期待チェックの結論が skipped か、期待チェックの実行が存在しなければ、カナリア照合は、その種別を「検査が実行されていない」として失敗と判定し、判定側の故障とは区別して報告する。
5. 当月のカナリアPRが6件揃っていなければ、カナリア照合は失敗として終了し、生成側の異常である旨を報告に含める。
6. いずれかの種別が失敗判定なら、カナリア照合はワークフロー全体を失敗として終了し、種別ごとの判定結果の一覧を報告に含める。
7. カナリア照合は、カナリアPRのclose・コメント・その他の書き込み操作を行わない。
8. 期待チェックが、必須チェックがスキップで通ったPRの検知(要件3)の期待一覧で「停止中」と記録されていれば、カナリア照合は、その種別を失敗と区別して「停止中(記録済み)」として報告する。記録の無い停止は、期待チェックの結論が skipped か実行が存在しないときと同じく、「検査が実行されていない」として失敗とする。意図的な停止は承認された記録によって、事故による停止は赤によって、それぞれ見え続ける。

### 要件6 運用特性(共通制約)

所有者は、監査の自動化によって、費用・攻撃面・保守負担が増えないことを保証したい。

1. 監査ワークフロー群は、AIの呼び出しを行わない。
2. 監査ワークフロー群は、GitHubのAPI以外の外部サービスへ問い合わせを行わない。

   > 注記(2026-09-29): 本項は audit-inventory-metrics spec(#415)の要件6-1・6-6で、棚卸し(audit-inventory.yaml)に限って改めた。棚卸しは GitHub 以外の公開情報(endoflife.date・PyPI・Docker Hub)を読み取りで問い合わせ、送るのは製品やパッケージの名前だけで、リポジトリの内容や認証情報を送らない。週次監査とカナリア照合については本項の禁止を維持する。理由: 本項の元の理由は「外部の死活監視サービスへのリポジトリの情報の送信」であり、製品名を送って公開情報を受け取る問い合わせは想定していなかった(所有者了承 2026-09-28)。本文は監査証跡として当時のまま残す。

3. 監査ワークフロー群は、実行履歴以外の状態(台帳・スナップショット等)を保存しない。
4. 監査ワークフロー群は、リポジトリへの書き込み・PRやIssueの作成・Dependabotへの操作を行わない。監査ワークフロー群が行うのは、判定と報告だけである。

   > 注記(2026-09-25): 本項は audit-notification spec(#347)の要件6-2で置き換えた。書き込みはIssueの作成・追記・クローズと担当者の割り当てに限って認め、リポジトリの内容・PR・Dependabotへの書き込みは引き続き行わない。理由: 定期実行の失敗通知は cron を最後に書き換えた利用者にしか届かず、botが書いた監査ワークフローの赤は所有者に届いていなかったため、Issueで知らせる必要がある。本文は監査証跡として当時のまま残す。

5. 逸脱を検知したら、監査ワークフロー群は、ワークフローを失敗として終了する以外の対処を行わない。逸脱の通知は、GitHub既定の失敗通知に乗る。

   > 注記(2026-09-25): 本項は audit-notification spec(#347)で置き換えた。逸脱は固定タイトルのIssue(「週次監査: 逸脱あり」「カナリア照合: 逸脱あり」)で知らせ、ワークフローは成功で終わる。ワークフローが失敗で終わるのは、判定不能のときとIssueへの反映に失敗したときに限る。理由: 定期実行の失敗通知は cron を最後に書き換えた利用者にしか届かず(https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、「GitHub既定の失敗通知に乗る」という前提が誤っていたため。本文は監査証跡として当時のまま残す。

6. 監査ワークフロー群は、判定ロジックをテスト可能な形で持ち、検査スクリプトと同等の自動テストを備える。
