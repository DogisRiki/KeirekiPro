# 所有者に送る文の書き方

このファイルは、Claude が所有者に送る文の書き方の決まりを定める。所有者に送る文は、次の4つである。

- チャットの報告と問い: Claude が1回の返事の終わりに書く本文と、返事の最後に出る、まとめの文とボタン付きの質問
- spec の本文: requirements.md、design.md、tasks.md
- Issue の本文: Claude が起票するときの本文と、Claude が本文に書き足すときの文
- PR の本文: Claude が PR を作るときの本文と、Claude が本文を書き換えるときの文

Claude は、この4つのどれを書くときも、書く前にこのファイルを読む。spec の本文には、このファイルの決まりに加えて、`.kiro/settings/rules/spec-writing.md` の決まりも当てはまる。Claude が作業の途中に書く一言も、このファイルの決まりに沿って書く。ただし、Claude は、作業の途中に書く一言を、下の読み直しの対象にしない。

## 送る前の読み直し

Claude は、次の3つの文を、送る前に、このファイルの `## 決まり` の節の決まりと照らして自分で読み直す。Claude は、決まりから外れていると気づいた文を、すべて書き直してから送る。

- チャットの報告と問い: Claude は、所有者に見せる前に読み直す
- Issue の本文: Claude は、起票する本文の案を所有者に見せる前と、Issue を起票する前と、Issue の本文に書き足す前に読み直す
- PR の本文: Claude は、PR を作る前と、PR の本文を書き換える前に読み直す

spec の本文は、`/spec-review` の中で点検役 `spec-style-checker` が点検する。そのため、Claude は、spec の本文を、この読み直しの対象にしない。

Claude は、文を読み直すために、別のエージェントを動かさない。別のエージェントを動かすと、費用がかかり、所有者への返事も遅くなるためである。Claude は、文を読み直したことを、そのたびに所有者に報告しない。所有者に送る文が、読み直しの話で長くならないようにするためである。

## 決まりの例外

Claude は、次のものを、決まりに合わせて書き換えなくてよい。

- 所有者が画面で目にする名前: Claude は、GitHub の「Re-run」のような名前を、画面と同じ綴りのまま書いてよい
- ファイル名、コマンド、設定の名前、イベント名: Claude は、これらを元の綴りのまま書いてよい。書き換えると、指すものが変わるためである
- 引用した部分: Claude は、所有者の言葉、Issue の本文、例の一覧から引用した部分を、引用元のまま書く。Claude は、引用した部分を決まりに合わせて書き直さない
- 図の中の矢印: Claude は、Mermaid などの図の中では、矢印で流れを示してよい。図の矢印は、文と文をつなぐものではないためである
- 「ラベル: 内容」の形の箇条書き: 「起動: 30分ごと」のような箇条書きでは、ラベルが主語や条件を示す。そのため、Claude は、この形の箇条書きでは、内容の文の主語を省いてよい

## 例に書かないもの

このリポジトリは公開されている。Claude は、このファイルと例の一覧 `.kiro/settings/rules/owner-writing-examples.md` に、まだ直していないセキュリティの穴の中身と、秘密の値(パスワード、トークンなど)を書かない。

## 例の読み方

決まりごとの「外れた文の例」は、決まりから外れた書き方をわざと示す。Claude は、外れた文の例を書き方の手本にしない。所有者が実際に差し戻した文を使った例には、例の一覧の組の番号を書き添える。例の一覧に無く、メモリのファイルに残っていた文を使った例には、そのメモリのファイルの名前を書き添える。Claude が作った例には、そのことを書き添える。

## 決まり

### 文ごとに主語と目的語を書く

Claude は、文ごとに、主語と目的語を書く。主語は動作をする人や物で、目的語は動作の対象である。Claude が主語を省いてよいのは、同じ段落の直前の文と主語が同じときに限る。

**外れた文の例**(例の一覧の組40)

> ただ、別の Claude は次のように動くこともあり、そのときの決め方が要件に書かれていません。
>
> - 表を出さず、「実装します」の1文だけで止まった
> - 表の半分だけ出して、ファイルを書き換え始めた

**直した文の例**

> ただし、別の Claude が次のように動いたときに、私がフックを残すのか消すのかが、要件に書かれていません。
>
> - 別の Claude が、「spec を作るかどうかの判断と、その理由」の報告を出さずに、「実装します」とだけ書いて止まった
> - 別の Claude が、判断の報告を途中まで書いたところで、ファイルを書き換え始めた

**外れた文の例**(Claude が作った例)

> 承認の前に確かめ、必要なら直す。

誰が何を確かめ、何を直すのかが書かれていない。

**直した文の例**

> Claude は、所有者に承認を求める前に本文の全体を点検し、書き方から外れた文を直す。

### 実際に動く人や物を主語にする

Claude は、主語を、実際に動く人や物にする。実際に動く人や物とは、所有者、Claude、ワークフロー、スクリプトなどである。Claude は、まだ存在しない手順や仕組みに「〜の手順」「〜の仕組み」のような名前を付けて、それを主語にしない。

**外れた文の例**(例の一覧の組47)

> 作業を止める検査は、Claude が書き込めない場所(.claude/hooks/)に置くので、所有者に手で置いてもらう手順が要ります

**直した文の例**

> 実装が終わったら、あなたに、私が用意したファイルを `.claude/hooks/` に写すコマンドを打ってもらうことになります。

**外れた文の例**(Claude が作った例)

> 着手の手順は、Issue の本文を読んで spec の要否を判断する。

**直した文の例**

> Claude は、`/start` を実行したときに Issue の本文を読み、spec が要るかどうかを判断する。

### 作業の中だけで使う呼び名を使わない

Claude は、作業の中だけで使っている呼び名を、所有者に送る文に使わない。Claude は、その呼び名が指すものを、所有者が知っている言葉で書く。spec の本文で使っている呼び名も、Claude は、報告や問いにそのまま持ち込まない。

**外れた文の例**(例の一覧の組37)

> ## 審査役が挙げた、AIが決めたこと(6件)
> 承認の前に、次の6つがあなたの考えと合っているかを見てください。
> 1. 控えは、作業フォルダの中の、リポジトリに残らない場所に置きます。別の作業フォルダで続きを進めると控えが無いので、そのときは本文の全体を審査します
> 2. 上限に達したかどうかは、エラーの文面だけで見分けます。文面の形が変わったときは、上限ではない失敗として扱い、止まってあなたに知らせます

**直した文の例**

> ## spec を審査したエージェントが挙げた、私があなたに確かめずに決めたこと
> 承認の前に、次の6つがあなたの考えと合っているかを見てください。
> 1. 私は、前回 spec を審査するエージェントを動かしたときの本文を写したファイルを、作業フォルダの中の、リポジトリに入らない場所に置きます。本文を直したあとの審査では、私は、このファイルと今の本文とで違うところを、エージェントに渡します。あなたが別の作業フォルダで続きを進めると、その作業フォルダには写したファイルが無いので、私はエージェントに本文の全体を審査させます
> 2. 審査するエージェントが使える量の上限に達して止まったかどうかは、私が、エージェントが返したエラーの文面だけを見て判断します。文面の形が変わったときは、私は、上限ではない理由で止まったとみなし、作業を止めてあなたに知らせます

### 造語を使わない

Claude は、造語を、所有者に送る文に使わない。造語とは、Claude が自分で作った言葉である。Claude は、造語で済ませずに、何をすることか、何のことかを普通の文で書く。

**外れた文の例**(例の一覧の組64)

> 1. あなたは「文の読み直しに、別のAIを使うな」と言いました。私はこれを「別のAIを一切使うな」と取り違えました。

**直した文の例**

> 1. あなたは、私があなたに送る文がわかりにくいかどうかを、別のAIに確かめさせないように、と言いました。私はこれを、実装のチェックにも別のAIを使ってはいけない、という意味に取り違えました。

英語の見出しを日本語に置き換えるときも、Claude は、直訳や名詞の組み合わせで新しい言葉を作らない。

**外れた文の例**(例の一覧の組43)

> 決まりとの照合

> 受け持つ範囲

> 頼りにするもの

**直した文の例**

> プロジェクトの決まりを守っているか

> 作るものと作らないもの

> 使う既存の仕組み

Claude は、動詞の「確かめる」を名詞にした「確かめ」を使わない。名詞が要るときは、Claude は「確認」と書く。

**外れた文の例**(例の一覧の組62)

> ## 7. 本番に入れたあとの確かめ
> (中略)
> - 確かめは4つです

**直した文の例**

> ## 7. 本番に入れたあとに確認すること
> (中略)
> - 確認することは4つです

### 種類の違うものを1つの言葉でまとめない

Claude は、種類の違うものを、1つの言葉でまとめて呼ばない。Claude は、種類ごとに分けて、それぞれが何かを書く。

**外れた文の例**(例の一覧の組35)

> この案で残る弱点は2つです。
>
> - 見逃す側: main が、同じファイルの中で、たまたま同じ中身の行を別に消すか足していると見逃します。空行などで起こりえますが、まれです。
> - 止まりすぎる側: マージのあと、main がその行をさらに書き換えていると「直している」とみなして止まります。このときは、あなたが「やめた」と答えれば進みます。

**直した文の例**

> この手順に変えても、次の2つの場面が残ります。
>
> 1. ほかのセッションの変更が main に入っていないのに、入っているとみなして、止まらずに進む場面: main の同じファイルで、たまたま同じ中身の行が別の場所で消されたか足されたときに起きます。空行などで起こりえますが、まれです。この場面は、私が直すべき誤りです。
> 2. ほかのセッションの変更がマージされたあとに、main がその行をさらに書き換えたときに、止まってあなたに尋ねる場面: これは誤りではなく、要件で決めた動きです。あなたが「やめた」と答えれば、作業は進みます。

### 名詞を並べただけで済ませない

Claude は、名詞を「・」や読点で並べただけの文で済ませない。Claude は、それぞれの名詞が何かと、何が起きるのかを、主語と述語のある文で書く。

**外れた文の例**(例の一覧の組24)

> パッケージの取得元設定・インストール時に実行されるスクリプト・供給網対策の設定・backendのビルドスクリプトの変更を検知し、リポジトリ所有者が承認するまでマージを保留。依存のバージョン宣言そのものは対象外(機械の検査が担う)

**直した文の例**

> 次のどれかを変えたプルリクエストは、所有者が承認するまでマージされない。変えるとマージが止まるものは、ライブラリをどこから入手するかの設定、ライブラリを入れるときに動くプログラムの設定、悪意のあるライブラリを入れないための設定、backend のビルドの手順を書いたファイルの4つである。ライブラリの版を上げるだけの変更は、承認がなくてもマージされる。版を上げるだけの変更に承認が要らないのは、機械の検査が、脆弱性と公開からの日数を調べるためである。

### 括弧に補足を詰め込まない

Claude は、文の補足を括弧の中に詰め込まない。Claude は、要る補足を別の文で書き、要らない補足は書かない。

**外れた文の例**(例の一覧の組45)

メモリに残っていたのは、括弧の部分だけである。

> (時刻は、5分ごとの確認で起動を検知した時刻です)

**直した文の例**

この断り書きは書かない。読む人がすることは、断り書きがあっても無くても変わらないためである。

Claude は、数を括弧に入れて言葉に添えない。

**外れた文の例**(例の一覧の組19)

> ## 人間の役割(5つだけ)

**直した文の例**

> ## 人間が行うこと
>
> 人間が行うのは、次の5つに限る。

### 矢印でつながない

Claude は、手順や流れを、矢印でつないで書かない。Claude は、手順や流れを1つずつに分け、それぞれで誰が何をするかを文で書く。

**外れた文の例**(例の一覧の組52)

> 流れ: さっきの文を貼る → AIが要件文書の「やらないこと」一覧にその1行を書き足す → 直した文書をあなたに見せてくる → 読んでOKなら `/kiro-spec-design machine-gated-dependency-updates` を打つ。

**直した文の例**

> 1. あなたが、さっきの文を、もう1つのセッションに貼ります。
> 2. もう1つのセッションの Claude が、要件の文書の「やらないこと」の一覧に、その1行を書き足します。
> 3. その Claude が、直した要件の文書をあなたに見せます。
> 4. あなたが読んで問題が無ければ、`/kiro-spec-design machine-gated-dependency-updates` を打ちます。

### 別々のことを1つの行や段落に詰め込まない

Claude は、別々のことを、1つの行や段落にいくつも詰め込まない。Claude は、1つのことを1つの項目に書き、項目がいくつあるかを先に書く。

**外れた文の例**(例の一覧の組1)

> - この spec で決めないこと: 自動レビューを止めている今の状態を再開するかどうか(所有者が決める。この spec は自動レビューを再開しない)。PR本文に `Spec:` を書いて spec を判定の基準にするPRの判定。Issue本文の「決めた方式」の書き方(起票の決まりのまま)。自動レビューの往復の上限と、上限に達したときの扱い。「決めた方式」どおりに作れないと分かったときの Claude の動き(今の `/start` の決まりのまま)

**直した文の例**

> この spec では、次の5つを決めない。
> - 止めている自動レビューを、また動かすかどうか。これは所有者が決める。この spec では、自動レビューを動かし直さない
> - PR本文に `Spec:` を書いたPRを、自動レビューがどう判定するか
> - Issue本文の「決めた方式」をどう書くか。この spec では、今の起票の決まりのままにする
> - 自動レビューと Claude のやりとりを何回までにするか。その回数に達したらどうするか
> - 「決めた方式」のとおりに作れないと分かったとき、Claude がどう動くか。この spec では、今の `/start` の決まりのままにする

### 長い条件を文の前に置かない

Claude は、長い条件を文の前に置いて、誰が何をするのかが文の最後まで分からない文を書かない。Claude は、条件を先に別の文で書くか、誰が何をするのかを先に書く。

**外れた文の例**(例の一覧の組2)

> 7. 「決めた方式」の項目が、作業の順番や所有者の操作のように、PRの変更からは沿っているかどうかを判定できないことを書いているときは、自動レビューは、その項目を「このPRの変更からは判定できない」と示す。自動レビューは、「このPRの変更からは判定できない」項目だけを理由に、spec適合の判定を「直す必要あり」にしない。Claude がPRを直しても、その項目の判定は変わらないからである。

**直した文の例**

> 7. 「決めた方式」の項目の中には、PRの変更を見ても、守られたかどうかが分からないものがある。たとえば、作業の順番を書いた項目や、所有者が行う操作を書いた項目である。自動レビューは、こうした項目に「このPRの変更からは判定できない」と書く。自動レビューは、こうした項目だけを理由に、PRを「直す必要あり」とは判定しない。Claude がPRを直しても、こうした項目の判定は変わらないからである。

### 専門用語の意味を書き添える

Claude は、冪等のような専門用語を使うときは、その語が何を意味するかを同じ文か直後の文に書く。Claude は、専門用語を消さずに残し、それが何かを書き添える。

**外れた文の例**(例の一覧の組3)

> - この機能の検査対象は、イメージのOS層と同梱アーティファクト(jar)の双方であり、この機能は既存の依存に対しても脆弱性を検出する。

**直した文の例**

> - この機能は、本番のイメージの2か所を調べる。イメージとは、本番で動かすプログラムと、プログラムを動かす土台をまとめたものである。この機能が調べる1か所目は土台の OS の部分で、2か所目はイメージに入れた backend のプログラムである jar のファイルである。この機能は、前から使っている部品の脆弱性も見つける。

**外れた文の例**(Claude が作った例)

> スクリプトは冪等に作る。

**直した文の例**

> スクリプトは冪等に作る。冪等とは、同じPRに何度呼ばれても結果が変わらないことを指す。

### 番号だけで別の箇所を指さない

Claude は、文の中で別の箇所に触れるときに、番号だけで指さない。Claude は、触れる先の中身を同じ文の中で言葉にする。

**外れた文の例**(例の一覧の組4)

> - 推奨: B。A は今のやり方で、上の2のとおり誤りが止まっていないため。

**直した文の例**

> - 推奨: B の、送る前に別のエージェントが読むやり方。A の、書くときに決まりを読んで守るやり方は、今のやり方と同じです。メモリに決まりを書いたあとも、あなたは私が書いた同じ種類の文を差し戻し続けているので、A のやり方では誤りが止まりません。

**外れた文の例**(Claude が作った例)

> そのときは、Claude は 5-2 に従う。

**直した文の例**

> そのときは、Claude は目次も直さず、1と同じく所有者に見せる。

### 指すものを文の中で言い切る

Claude は、「問題」「点」「対応」「どちらでもない動き」のように、何を指すかが文の前後から決まらない言葉で文を済ませない。Claude は、指すものをその文の中で言い切る。

**外れた文の例**(例の一覧の組41)

> **要件に足りないこと**
> 別の Claude がどちらでもない動きをしたときに、フックを残すのか消すのかが、要件に書いてありません。たとえば、判断の報告を出さずにそのまま止まったときです。

**直した文の例**

> **要件に足りないこと**
> 別の Claude が、判断の報告を出して止まることも、報告の前にファイルを書き換えることもしなかったときに、私がフックを残すのか消すのかが、要件に書いてありません。たとえば、別の Claude が判断の報告を出さずにそのまま止まったときです。

**外れた文の例**(Claude が作った例)

> 問題を見つけたら、Claude は対応を所有者に見せる。

**直した文の例**

> メモリの記述に誤りの疑いを見つけたら、Claude は、その記述の直し方の案を所有者に見せる。

### 英語の定型文を使わず、見出しと欄を日本語で書く

Claude は、「The ○○ shall …」「When …, the ○○ shall …」のような、英語と日本語を混ぜた定型文を使わない。Claude は、見出しと欄の名前を日本語で書く。

**外れた文の例**(例の一覧の組56)

> ### Allowed Dependencies
>
> - Claude Code のフック機構(`UserPromptExpansion` / `UserPromptSubmit` / `SubagentStop` / `PostToolUse` / `Stop`)
> - Agent ツールによるサブエージェントの起動とモデル指定
>
> (以下略)

**直した文の例**

> ### この spec の仕組みが使う、すでにある道具
>
> - Claude Code のフック。使うのは `UserPromptExpansion`、`UserPromptSubmit`、`SubagentStop`、`PostToolUse`、`Stop` の5つである
> - Claude が別のエージェントを起動する Agent ツール。起動するときに、Claude はそのエージェントのモデルを決める
>
> (以下略)

**外れた文の例**(Claude が作った例)

**外れた文の例**(メモリの owner-steps-concrete-clicks.md に残っていた、差し戻された文)

> 権限に events:* と sqs:* を足す

> apply を 7:45〜7:55 を避けて実行

> 1. AWS マネジメントコンソールで「IAM」を開き、左の「ロール」を押します。

> 4. 次のコマンドを打ちます。ただし、7:45 から 7:55 のあいだは避けてください。この時間は、データベースを起動する予定が動くためです。

> ```bash
> terraform apply
> ```
>
> 5. 最後に `Apply complete!` と出れば終わりです。エラーが出たときは、出た文をそのまま私に送ってください。

**外れた文の例**(例の一覧の組70)

**直した文の例**

> 1. Git Bash を開き、次のコマンドを貼り付けて、Enter キーを押してください。

### 場面は、所有者がしたことと起きた出来事で書く

Claude は、所有者に判断してもらう場面を、「止まっている状態」のような仕組みの側から見た状態で書かない。Claude は、所有者がしたことや起きた出来事を並べて書き、そのとき仕組みが何をして、所有者に何が起きるかを順に書く。

**外れた文の例**(例の一覧の組48)

> Docker Desktop が止まっている状態で /start を打ったとします

**直した文の例**

> PC を起動して、Docker Desktop をまだ起動していないうちに、あなたが `/start` を打ったとします。

### 問いには、誰の、何についての問いかを書き、似たものを1つの問いに混ぜない

Claude は、問いと選択肢に、誰が、何について決めるのかを書く。似たものが複数あるときは、Claude は、1つの問いに混ぜず、どちらの話かを文の頭に書く。

**外れた文の例**(例の一覧の組46)

Claude は、メールとアプリ内のお知らせの両方を決める問いで、送り先の絞り込みの条件として、次の2つを書いた。

> メールアドレスがあるか無いか

> ログインしていない人にも見せるか

**直した文の例**

> アプリは、メールアドレスを登録しているユーザーにだけ、メールを送りますか。

> アプリは、アプリ内のお知らせを、ログインしていない人にも画面で見せますか。

### 決まりと普通の判断で答えが決まることを、所有者に尋ねない

Claude は、CLAUDE.md や steering に書いたリポジトリの決まりと、普通の判断で答えが1つに決まることを、所有者に尋ねない。Claude は、そう決めたことと、その根拠を、本文に書く。

**外れた文の例**(例の一覧の組51)

> - 「言語に依存しない書き方をワークフローにも当てはめるか」「過去のspecも書き換えるか」

**直した文の例**

Claude は、これを問いにせず、報告の本文に次のように書く。

> - 私は、ワークフローには、言語に依存しない書き方を当てはめません。ワークフローのように実際に動かすファイルは、言語を名指ししないと動かないためです。
> - 過去の spec は、監査の証跡としてコミットしたものなので、私は書き換えません。

### 考えを求められたら、結論と推奨を本文に書く

Claude は、所有者に「まず考えて」と頼まれたら、調べた結果をもとにした結論と推奨を、返事の本文に書く。Claude は、考えを書く前に、所有者に選択肢を選ばせない。

**外れた文の例**(Claude が作った例)

Claude は、調べた結果を書かずに、ボタン付きの質問だけを出した。

> どこまで作りますか。

**直した文の例**

> 私は、まず月に1回の点検だけを作るのがよいと考えます。点検で見つけたことが、次に何を作るかを決める材料になるためです。毎週の点検は、月に1回の点検で見つけることが多かったときに足します。

### 調べた結果は、すぐする対処と、長く続ける対処と、採らなかった案を一度に書く

Claude は、調べた結果や、別のAIと話し合った結果を所有者に書くとき、すぐする対処、長く続ける対処、採らなかった案とその理由を、一度に書く。所有者が驚いたり疑ったりしても、Claude は、新しい事実が無ければ推奨を変えず、元の推奨の根拠を書く。推奨を変えるときは、Claude は、何が変わったのかを書く。

**外れた文の例**(Claude が作った例)

> 当面は、検査で見つかった脆弱性を、期限を付けて抑えます。

所有者は、これに「そんな方法なの?」と返した。Claude は、新しい事実が無いまま、次のように推奨を替えた。

> では、版を固定する案にします。

**直した文の例**

> すぐする対処として、検査で見つかった脆弱性を、期限を付けて抑えます。長く続ける対処として、PR の検査と定期の検査の役割を分けます。版を固定する案は採りません。版を固定すると、直った版にも上がらなくなるためです。

### 確かめていないことを、確かめたように書かない

Claude は、確かめていない主張を報告に書かない。Claude は、確かめてから書くか、確かめられない理由と、所有者がする確認の手順を書く。

**外れた文の例**(メモリの no-unverified-claims-in-reports.md に残っていた、差し戻された文)

> pnpmは歴史的にpackage.jsonのpnpmキーでoverridesを書ける版が存在する。現行版で有効かは未確認

**直した文の例**(Claude が作った例)

> 今の pnpm 11 は、`package.json` の `pnpm` キーに書いた overrides を読まず、警告を出します。コンテナの中で `pnpm install --lockfile-only` を1回動かして確かめました。

### 割り込みの質問には、その質問にだけ答える

Claude は、所有者が途中で別の質問をしたら、その質問にだけ答える。Claude は、前に出した問いへの答えを催促しない。前に出した問いが、所有者が戻ってきたときにまだ要るなら、Claude は、短く1回だけ触れる。

**外れた文の例**(Claude が作った例)

> spec は要ります。理由は次のとおりです。(中略)ところで、前にお聞きしたブランチを引き継ぐかどうかに答えてください。

**直した文の例**

> spec は要ります。この変更で、Issue の作り方の決まりが変わるためです。

### 読んで決めてもらう中身は、ボタン付きの質問ではなく、返事の本文に全部書く

Claude は、起票の案や手順や比べる材料のように、所有者に読んで決めてもらう中身があるときは、それを返事の最後のボタン付きの質問に頼らず、返事の本文に全部書いてから、本文の最後で尋ねる。ボタン付きの質問を出すと、所有者の画面では、その前の本文が見えなくなるためである。

**外れた文の例**(メモリの askuserquestion-hides-content.md に残っていた、差し戻された文)

Claude は、案の中身を本文に書かずに、ボタン付きの質問だけで尋ねた。

> A・B・C のどれにしますか

**直した文の例**(Claude が作った例)

> A は、毎朝7:30にデータベースを起動する案です。B は、あなたが画面を開いたときに起動する案です。C は、起動したままにする案です。私は A がよいと考えます。どれにするかを返してください。

### Issue に、所有者の話し言葉をそのまま引かない

Claude は、Issue の本文に、所有者がチャットで書いた話し言葉をそのまま引かない。Claude は、所有者が何を求めたのかを、書き言葉の文で書く。所有者の言葉が書き言葉で短いときだけ、Claude はそのまま引く。

**外れた文の例**(Claude が作った例)

> ## きっかけ
>
> 所有者が「通知がメールで来ないと気づけないよね」と言った。

**直した文の例**

> ## きっかけ
>

### 文の書き方を示すときは、原文のまとまりと書き直しを並べる

Claude は、文の書き方について所有者と考えを合わせるとき、1行を抜き出して示さない。Claude は、要件の1つや設計の1節のような原文のまとまりと、同じ範囲を書き直した文を並べ、所有者に自由に答えてもらう。

**外れた文の例**(Claude が作った例)

> わかりにくい文の例: 「双方を検査する」
>
> A. 直す B. 直さない

**直した文の例**

> 次は、今の要件3の全文です。
>
> > (要件3の段落と受入基準の全文)
>
> 次は、同じ範囲を書き直した文です。
>
> > (書き直した段落と受入基準の全文)
>
> 書き直した文で伝わるかどうかと、まだわかりにくいところを、自由に書いて返してください。

### 形が答えになることは、たたき台の全体を見せる

Claude は、集計の表や一覧のように、出来上がりの形が答えになる決めごとでは、選択肢の問いを重ねない。Claude は、見本の数字を入れたたたき台を、途中を省かずに全体で見せ、行と列の言葉の意味を下に書く。

**外れた文の例**(Claude が作った例)

> 時間の数え方を決めます。次のどちらにしますか。
>
> A. PR を作ってからマージするまで
> B. Issue に着手してからマージするまで

**直した文の例**

> 集計の表の案です。数字は見本です。
>
> | Issue | 着手からマージまで | 所有者が答えるのを待った時間 |
> |---|---|---|
> | #500 | 6時間 | 2時間 |

> - 所有者が答えるのを待った時間: Claude が問いを出してから、あなたが答えるまでの時間の合計

### 出荷の報告に、アプリの機能の案内を書かない

Claude は、PR を作ったあとの報告に、デスクトップアプリの機能の案内を書かない。Claude は、出荷の報告に、所有者にしてほしいことと結果だけを書く。

> CIが赤になったときにこのアプリが自動で修正を試みる設定(Auto-fix)も有効にできます。必要なら言ってください。

### spec に、手元にしかない情報と、この spec 自身の作り方を書かない

Claude は、spec の要件に、まだコミットしていないフォルダや進めている途中の別の spec のような作業中の手元の状態と、この spec 自身をどう書くかを書かない。Claude は、要件の境目を、「main に入った時点ですでに作られていたもの」のような、あとから読んでも変わらない条件で書く。Claude は、要件の前置きの段落に、その要件がなぜ要るのかを書き、「所有者は〜を読みたい」のような願望の文だけで済ませない。

**外れた文の例**(例の一覧の組50)

> spec-need-triage と memory-contamination-check を含む

> この spec(spec-readable-writing)は例外として新しい書き方で書く

**直した文の例**

> Claude は、この spec が main に入った時点ですでに作られていた spec を、新しい書き方に書き直さない。

### 自分の誤りの原因を、出どころを挙げて言い訳せずに書く

Claude は、「なぜそうなったのか」と問われたら、自分の誤りとして原因を書く。Claude は、「誰が決めたか」や「私が足したのではない」を書かない。前の会話の Claude がしたことも、Claude の誤りとして書く。原因が GitHub の不具合のように Claude の外にあるときは、Claude は、それを事実として書き、自分の側で防げたことを分けて書く。

**外れた文の例**(メモリの own-past-work-no-blame.md に残っていた、差し戻された文)

> 私が勝手に足したのではない。file-issue の決まりにあった。決めたのはAI(Fableとの壁打ち)

**直した文の例**(メモリの own-past-work-no-blame.md に残っていた、直した文)

> 私が決まりを作ったときに、要望の段階で設計を書かないという考えが抜けていた

### 作業の終わりに、自分が作った物の穴を並べて所有者に投げない

Claude は、作業の終わりに、自分がこの作業で作った物の穴を並べて、所有者に判断を求めない。Claude は、穴を同じ PR の中で直すか、実害が小さいものは直さないと自分で決めて、報告に書かない。本当に依頼の範囲の外にあり、実害が大きいものだけを、Claude は1行で報告する。

**外れた文の例**(Claude が作った例)

> 設計に無かった場面が2つあります。1つ目は、PR を作っている途中で PC を落としたときです。2つ目は、(中略)。直すなら、起票の案を作ります。

**直した文の例**

> PR #600 を作りました。PR を作っている途中で PC を落としたときに、作りかけの PR が残る穴があったので、同じ PR の中で直しました。

### 公開される文に、まだ直していないセキュリティの穴を書かない

Claude は、Issue の本文と PR の本文に、まだ直していないセキュリティの穴を書かない。穴を直す Issue では、Claude は、穴とは書かず、作る動きとして書く。このリポジトリは公開されていて、直す前に穴を書くと、攻撃の手引きになるためである。

**外れた文の例**(Claude が作った例)

> ○○の画面で、△△を確かめていない穴を直す

**直した文の例**

> ○○の画面で、△△を確かめるようにする

### 見出しに、かぎ括弧の標語を付けない

Claude は、見出しに「」で囲んだ標語を付け足さない。Claude は、見出しを、その節に何が書いてあるかが分かる普通の言葉で書く。

**外れた文の例**(例の一覧の組20)

> ### ガードレール(「読まない」を成立させる多層防御)

**直した文の例**

> ### 品質を担保する仕組み

### 報告に仕組みの中の言葉を出さず、どれの話かを指す番号と名前は残す

Claude は、所有者への報告に、終了コード、正規表現、関数名、ツールの中の動き、脆弱性の番号のような、仕組みの中の言葉を出さない。Claude は、どれの話かを指す、タスクの番号、Issue の番号、ワークフローの名前、ファイルのパスは残す。

**外れた文の例**(Claude が作った例)

> `check-spec` が終了コード69で落ちました。jq の式が空の配列を返したためです。

> 検査が失敗したので直しました。

**直した文の例**

> `/kiro-spec-init` の途中で、ほかのセッションが同じ spec を直していないかを調べる処理が、最後まで動きませんでした。#507 のタスク2.1 で直します。

### 選択肢の名前は、選んだときに何が起きるかで書く

Claude は、選択肢の名前を「案1」「A」だけにしない。Claude は、選択肢の名前に、それを選んだときに何が起きるかを書く。

**外れた文の例**(Claude が作った例)

> A. 案1
>
> B. 案2

**直した文の例**(Claude が作った例)

> A. 検査の仕組みはこの PR で入れ、検査が PR を止めるようにするのは次の PR にする
>
> B. 検査の仕組みを入れ、検査が PR を止めるようにするところまで、この PR でする

### 選択肢を減らすときは、減らした理由を1つずつ書く

Claude は、所有者に示す選択肢を減らすとき、減らした選択肢ごとに、なぜ減らしたのかを書く。所有者が決めた方針より範囲を絞る推奨を出すときは、Claude は、その方針とどう両立するのかを書く。

**外れた文の例**(Claude が作った例)

> 4つの案のうち、残すのは A と B の2つです。

**直した文の例**

> 4つの案のうち、A と B の2つを残します。C は、毎月あなたに手で設定を直してもらう必要があるので外しました。D は、今の検査の道具では動かないので外しました。

### 自分の文がおかしくて書き直したときは、「書き直した」と書く

Claude は、自分の文がわかりにくくて書き直したときに、「言葉を補った」と書かない。Claude は、「書き直した」と書く。元の文がおかしかったときは、言葉を足しただけでは直らないためである。

**外れた文の例**(Claude が作った例)

> 言葉を補って、もう一度書きます。

**直した文の例**

> 前の文がわかりにくかったので、書き直しました。

### 返事の形は、場面ごとに決める

Claude は、返事を書く前に、今どの場面かを決め、その場面の決まりを先に守る。場面と、先に守る決まりは次のとおりである。

- 「なぜ」「どうなっている」への答え: 「問われたことには、まず短く結論だけを答える」を先に守る
- 頼まれた調査や話し合いの結果の報告: 「調べた結果は、すぐする対処と、長く続ける対処と、採らなかった案を一度に書く」を先に守る。それぞれの対処は1行か2行で書く
- 「考えて」と頼まれたとき: 「考えを求められたら、結論と推奨を本文に書く」を先に守る
- 所有者にしか決められないことを尋ねるとき: 選択肢だけで決められる短い問いは、ボタン付きの質問で尋ね、1回の返事に2つまでにし、推奨を最初に置く。読んで決めてもらう中身があるときは、「読んで決めてもらう中身は、ボタン付きの質問ではなく、返事の本文に全部書く」を先に守る
- 作業を頼むとき: 「依頼は1回の返事に1つだけ書く」を先に守る
- `/request` の壁打ちで問いを出すとき: 互いに関わらない問いを、番号を付け、推奨を添えて、1回の返事にまとめて出す。答えで Issue の本文が変わらない問いは出さない

どの場面でも、Claude は、この節のほかの決まりを守る。

**外れた文の例**(Claude が作った例)

所有者は、「なぜ予約が付かないの?」と尋ねた。Claude は、調査の報告の形で、すぐする対処と長く続ける対処と採らなかった案を、見出しを付けて長く書いた。

**直した文の例**

> 予約が付かなかったのは、PR を作ったのがあなたのアカウントだったためです。

## 決まりに入れない書き方

所有者は、次の4つの書き方を、わかりにくい文に入れないと決めた。Claude は、この4つを `## 決まり` の節に入れない。点検役 `spec-style-checker` も、この4つを決まりから外れた書き方として挙げない。

- 「双方」「〜に限られる」「代替ではなく補完の関係にある」「失敗しうる」のような硬い言い回し
- 1つの段落の中で太字をいくつも使うこと
- 書いていないことまで読み取れてしまう文
- 順番にすることに番号を振らない書き方

## 決まりと例を足すとき

### 所有者がわかりにくいと指摘したとき

所有者が、Claude が送った文をわかりにくいと指摘したら、Claude は次の順に進める。

1. Claude は、指摘された文を書き直して、所有者に送り直す。
2. Claude は、`git fetch origin` のあと、`git worktree add <scratchpad のフォルダ> -b docs/<短い説明> origin/main` で、そのとき進めている作業のブランチとは別のブランチと作業フォルダを作る。ブランチ名は `.branch_name_template` に従う。
3. Claude は、その作業フォルダで、指摘された文と書き直した文を、このファイルの当たる決まりの例と、例の一覧 `owner-writing-examples.md` に足す。指摘された文がどの決まりにも当たらないときは、Claude は、その種類の文を差し戻す決まりを、新しい `### ` の見出しで足す。指摘された文が今ある決まりに当たるときは、Claude は、その決まりに例だけを足す。
4. Claude は、下の「決まりを変える PR で確認すること」をやり直し、結果を PR の本文に書く。
5. Claude は、`.commit_template` に従ってコミットし、push し、`gh pr create` で PR を作る。Claude は、PR を作ったことを、PR の番号を添えて、チャットで所有者に1文で知らせる。そのあと、Claude は `git worktree remove` で作業フォルダを消す。

Claude は、この PR を、そのとき進めている作業の PR に混ぜない。このファイルと例の一覧は、所有者の承認が要る場所(`.github/CODEOWNERS` に書かれた場所)の外にある。そのため、この PR は、品質のチェックを通れば、所有者の承認を待たずに自動でマージされる。Claude は、決まりと例を、エージェントの定義とスキルの手順に写さない。写すと、例を足す PR が、所有者の承認が要る場所を直すことになるためである。

### 決まりを変える PR で確認すること

Claude は、このファイルの決まりを変える PR を作る前に、例の一覧のすべての組で、次の順に確かめる。

1. Claude は、組ごとに、差し戻された文を、引用ではなく自分が送る文として読み、このファイルのどの決まりから外れるかを、例の一覧の「当たる決まり」の欄に書く。
2. Claude は、組ごとに、書き直した文が、どの決まりからも外れないことを確かめる。
3. 外れる決まりを挙げられない差し戻された文か、決まりから外れる書き直した文があれば、Claude は、このファイルの決まりと例を直し、1から確かめ直す。同じ文で3回直しても外れる決まりを挙げられないときは、Claude は止まって所有者に知らせる。
4. Claude は、組ごとの結果を、PR の本文の表に書く。表には、組の番号、差し戻された文が外れる決まりの名前、書き直した文が外れないことを書く。

Claude は、この確認のために、別のエージェントを動かさない。
