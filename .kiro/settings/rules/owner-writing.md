# 所有者に送る文の書き方

このファイルは、Claude が所有者に送る文の書き方の決まりを定める。所有者に送る文は、次の4つである。

- チャットの報告と問い: Claude が1回の返事の終わりに書く本文と、返事の最後に出る、まとめの文とボタン付きの質問
- spec の本文: requirements.md、design.md、tasks.md
- Issue の本文: Claude が起票するときの本文と、Claude が本文に書き足すときの文
- PR の本文: Claude が PR を作るときの本文と、Claude が本文を書き換えるときの文

Claude は、この4つのどれを書くときも、書く前にこのファイルを読む。spec の本文には、このファイルの決まりに加えて、`.kiro/settings/rules/spec-writing.md` の決まりも当てはまる。Claude が作業の途中に書く一言も、このファイルの決まりに沿って書く。ただし、Claude は、作業の途中に書く一言を、下の読み直しの対象にしない。

## 送る前の読み直し

Claude は、次の3つの文を、送る前に、このファイルの `## 決まり` の節の決まりと照らして自分で読み直す。Claude は、決まりから外れていると気づいた文を、すべて書き直してから送る。

- チャットの報告と問い: Claude は、所有者に見せる前に読み直す
- Issue の本文: Claude は、起票する本文の案を所有者に見せる前と、Issue を起票する前と、Issue の本文に書き足す前に読み直す
- PR の本文: Claude は、PR を作る前と、PR の本文を書き換える前に読み直す

spec の本文は、`/spec-review` の中で点検役 `spec-style-checker` が点検する。そのため、Claude は、spec の本文を、この読み直しの対象にしない。

Claude は、文を読み直すために、別のエージェントを動かさない。別のエージェントを動かすと、費用がかかり、所有者への返事も遅くなるためである。Claude は、文を読み直したことを、そのたびに所有者に報告しない。所有者に送る文が、読み直しの話で長くならないようにするためである。

## 決まりの例外

Claude は、次のものを、決まりに合わせて書き換えなくてよい。

- 所有者が画面で目にする名前: Claude は、GitHub の「Re-run」のような名前を、画面と同じ綴りのまま書いてよい
- ファイル名、コマンド、設定の名前、イベント名: Claude は、これらを元の綴りのまま書いてよい。書き換えると、指すものが変わるためである
- 引用した部分: Claude は、所有者の言葉、Issue の本文、例の一覧から引用した部分を、引用元のまま書く。Claude は、引用した部分を決まりに合わせて書き直さない
- 「ラベル: 内容」の形の箇条書き: 「起動: 30分ごと」のような箇条書きでは、ラベルが主語や条件を示す。そのため、Claude は、この形の箇条書きでは、内容の文の主語を省いてよい

## 例に書かないもの

このリポジトリは公開されている。Claude は、このファイルと例の一覧 `.kiro/settings/rules/owner-writing-examples.md` に、まだ直していないセキュリティの穴の中身と、秘密の値(パスワード、トークンなど)を書かない。

## 例の読み方

決まりごとの「外れた文の例」は、決まりから外れた書き方をわざと示す。Claude は、外れた文の例を書き方の手本にしない。所有者が実際に差し戻した文を使った例には、例の一覧の組の番号を書き添える。Claude が作った例には、そのことを書き添える。

## 決まり

### 文ごとに主語と目的語を書く

Claude は、文ごとに、主語と目的語を書く。主語は動作をする人や物で、目的語は動作の対象である。Claude が主語を省いてよいのは、同じ段落の直前の文と主語が同じときに限る。

**外れた文の例**(例の一覧の組40)

> ただ、別の Claude は次のように動くこともあり、そのときの決め方が要件に書かれていません。
>
> - 表を出さず、「実装します」の1文だけで止まった
> - 表の半分だけ出して、ファイルを書き換え始めた

**直した文の例**

> ただし、別の Claude が次のように動いたときに、私がフックを残すのか消すのかが、要件に書かれていません。
>
> - 別の Claude が、「spec を作るかどうかの判断と、その理由」の報告を出さずに、「実装します」とだけ書いて止まった
> - 別の Claude が、判断の報告を途中まで書いたところで、ファイルを書き換え始めた

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> 承認の前に確かめ、必要なら直す。

誰が何を確かめ、何を直すのかが書かれていない。

**直した文の例**

> Claude は、所有者に承認を求める前に本文の全体を点検し、書き方から外れた文を直す。

### 実際に動く人や物を主語にする

Claude は、主語を、実際に動く人や物にする。実際に動く人や物とは、所有者、Claude、ワークフロー、スクリプトなどである。Claude は、まだ存在しない手順や仕組みに「〜の手順」「〜の仕組み」のような名前を付けて、それを主語にしない。

**外れた文の例**(例の一覧の組47)

> 作業を止める検査は、Claude が書き込めない場所(.claude/hooks/)に置くので、所有者に手で置いてもらう手順が要ります

**直した文の例**

> 実装が終わったら、あなたに、私が用意したファイルを `.claude/hooks/` に写すコマンドを打ってもらうことになります。

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> 着手の手順は、Issue の本文を読んで spec の要否を判断する。

**直した文の例**

> Claude は、`/start` を実行したときに Issue の本文を読み、spec が要るかどうかを判断する。

### 作業の中だけで使う呼び名を使わない

Claude は、作業の中だけで使っている呼び名を、所有者に送る文に使わない。Claude は、その呼び名が指すものを、所有者が知っている言葉で書く。

**外れた文の例**(例の一覧の組37)

> ## 審査役が挙げた、AIが決めたこと(6件)
> 承認の前に、次の6つがあなたの考えと合っているかを見てください。
> 1. 控えは、作業フォルダの中の、リポジトリに残らない場所に置きます。別の作業フォルダで続きを進めると控えが無いので、そのときは本文の全体を審査します
> 2. 上限に達したかどうかは、エラーの文面だけで見分けます。文面の形が変わったときは、上限ではない失敗として扱い、止まってあなたに知らせます

**直した文の例**

> ## spec を審査したエージェントが挙げた、私があなたに確かめずに決めたこと(6件)
> 承認の前に、次の6つがあなたの考えと合っているかを見てください。
> 1. 私は、前回 spec を審査するエージェントを動かしたときの本文を写したファイルを、作業フォルダの中の、リポジトリに入らない場所に置きます。本文を直したあとの審査では、私は、このファイルと今の本文とで違うところを、エージェントに渡します。あなたが別の作業フォルダで続きを進めると、その作業フォルダには写したファイルが無いので、私はエージェントに本文の全体を審査させます
> 2. 審査するエージェントが使える量の上限に達して止まったかどうかは、私が、エージェントが返したエラーの文面だけを見て判断します。文面の形が変わったときは、私は、上限ではない理由で止まったとみなし、作業を止めてあなたに知らせます

### 造語を使わない

Claude は、造語を、所有者に送る文に使わない。造語とは、Claude が自分で作った言葉である。Claude は、造語で済ませずに、何をすることか、何のことかを普通の文で書く。

**外れた文の例**(例の一覧の組64)

> 1. あなたは「文の読み直しに、別のAIを使うな」と言いました。私はこれを「別のAIを一切使うな」と取り違えました。

**直した文の例**

> 1. あなたは、「私があなたに送る文がわかりにくいかどうかを、別のAIに確かめさせるな」と言いました。私はこれを、「実装のチェックにも別のAIを使うな」という意味に取り違えました。

### 種類の違うものを1つの言葉でまとめない

Claude は、種類の違うものを、1つの言葉でまとめて呼ばない。Claude は、種類ごとに分けて、それぞれが何かを書く。

**外れた文の例**(例の一覧の組35)

> この案で残る弱点は2つです。
>
> - 見逃す側: main が、同じファイルの中で、たまたま同じ中身の行を別に消すか足していると見逃します。空行などで起こりえますが、まれです。
> - 止まりすぎる側: マージのあと、main がその行をさらに書き換えていると「直している」とみなして止まります。このときは、あなたが「やめた」と答えれば進みます。

**直した文の例**

> この手順に変えても、次の2つの場面が残ります。
>
> 1. ほかのセッションの変更が main に入っていないのに、入っているとみなして、止まらずに進む場面: main の同じファイルで、たまたま同じ中身の行が別の場所で消されたか足されたときに起きます。空行などで起こりえますが、まれです。この場面は、ふさぐべき穴です。
> 2. ほかのセッションの変更がマージされたあとに、main がその行をさらに書き換えたときに、止まってあなたに尋ねる場面: これは穴ではなく、要件で決めた動きです。あなたが「やめた」と答えれば、作業は進みます。

### 名詞を並べただけで済ませない

Claude は、名詞を「・」や読点で並べただけの文で済ませない。Claude は、それぞれの名詞が何かと、何が起きるのかを、主語と述語のある文で書く。

**外れた文の例**(例の一覧の組24)

> パッケージの取得元設定・インストール時に実行されるスクリプト・供給網対策の設定・backendのビルドスクリプトの変更を検知し、リポジトリ所有者が承認するまでマージを保留。依存のバージョン宣言そのものは対象外(機械の検査が担う)

**直した文の例**

> 次のどれかを変えたプルリクエストは、リポジトリ所有者が承認するまでマージされない。ライブラリをどこから入手するかの設定、ライブラリを入れるときに動くプログラムの設定、悪意のあるライブラリを入れないための設定、backend のビルドの手順を書いたファイルの4つである。ライブラリの版を上げるだけの変更は、承認がなくてもマージされる。

### 括弧に補足を詰め込まない

Claude は、文の補足を括弧の中に詰め込まない。Claude は、要る補足を別の文で書き、要らない補足は書かない。

**外れた文の例**(例の一覧の組45)

メモリに残っていたのは、括弧の部分だけである。

> (時刻は、5分ごとの確認で起動を検知した時刻です)

**直した文の例**

この断り書きは書かない。読む人がすることは、断り書きがあっても無くても変わらないためである。

### 矢印でつながない

Claude は、手順や流れを、矢印でつないで書かない。Claude は、手順や流れを1つずつに分け、それぞれで誰が何をするかを文で書く。

**外れた文の例**(例の一覧の組52)

> 流れ: さっきの文を貼る → AIが要件文書の「やらないこと」一覧にその1行を書き足す → 直した文書をあなたに見せてくる → 読んでOKなら `/kiro-spec-design machine-gated-dependency-updates` を打つ。

**直した文の例**

> 1. あなたが、さっきの文を、もう1つのセッションに貼ります。
> 2. もう1つのセッションの AI が、要件の文書の「やらないこと」の一覧に、その1行を書き足します。
> 3. その AI が、直した要件の文書をあなたに見せます。
> 4. あなたが読んで問題が無ければ、`/kiro-spec-design machine-gated-dependency-updates` を打ちます。

### 別々のことを1つの行や段落に詰め込まない

Claude は、別々のことを、1つの行や段落にいくつも詰め込まない。Claude は、1つのことを1つの項目に書き、項目がいくつあるかを先に書く。

**外れた文の例**(例の一覧の組1)

> - この spec で決めないこと: 自動レビューを止めている今の状態を再開するかどうか(所有者が決める。この spec は自動レビューを再開しない)。PR本文に `Spec:` を書いて spec を判定の基準にするPRの判定。Issue本文の「決めた方式」の書き方(起票の決まりのまま)。自動レビューの往復の上限と、上限に達したときの扱い。「決めた方式」どおりに作れないと分かったときの Claude の動き(今の `/start` の決まりのまま)

**直した文の例**

> この spec では、次の5つを決めない。
> - 止めている自動レビューを、また動かすかどうか。これは所有者が決める。この spec では、自動レビューを動かし直さない
> - PR本文に `Spec:` を書いたPRを、自動レビューがどう判定するか
> - Issue本文の「決めた方式」をどう書くか。今の起票の決まりのままにする
> - 自動レビューとAIのやりとりを何回までにするか。その回数に達したらどうするか
> - 「決めた方式」のとおりに作れないと分かったとき、Claude がどう動くか。今の `/start` の決まりのままにする

### 長い条件を文の前に置かない

Claude は、長い条件を文の前に置いて、誰が何をするのかが文の最後まで分からない文を書かない。Claude は、条件を先に別の文で書くか、誰が何をするのかを先に書く。

**外れた文の例**(例の一覧の組2)

> 7. 「決めた方式」の項目が、作業の順番や所有者の操作のように、PRの変更からは沿っているかどうかを判定できないことを書いているときは、自動レビューは、その項目を「このPRの変更からは判定できない」と示す。自動レビューは、「このPRの変更からは判定できない」項目だけを理由に、spec適合の判定を「直す必要あり」にしない。Claude がPRを直しても、その項目の判定は変わらないからである。

**直した文の例**

> 7. 「決めた方式」の項目の中には、PRの変更を見ても、守られたかどうかが分からないものがある。たとえば、作業の順番を書いた項目や、所有者が行う操作を書いた項目である。自動レビューは、こうした項目に「このPRの変更からは判定できない」と書く。自動レビューは、こうした項目だけを理由に、PRを「直す必要あり」とは判定しない。Claude がPRを直しても、こうした項目の判定は変わらないからである。

### 専門用語の意味を書き添える

Claude は、冪等のような専門用語を使うときは、その語が何を意味するかを同じ文か直後の文に書く。Claude は、専門用語を消さずに残し、それが何かを書き添える。

**外れた文の例**(例の一覧の組3)

> - この機能の検査対象は、イメージのOS層と同梱アーティファクト(jar)の双方であり、この機能は既存の依存に対しても脆弱性を検出する。

**直した文の例**

> - この機能は、本番のイメージの2か所を調べる。イメージとは、本番で動かすプログラムと、プログラムを動かす土台をまとめたものである。この機能が調べる1か所目は土台の OS の部分で、2か所目はイメージに入れた backend のプログラムである jar のファイルである。この機能は、前から使っている部品の脆弱性も見つける。

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> スクリプトは冪等に作る。

**直した文の例**

> スクリプトは冪等に作る。冪等とは、同じPRに何度呼ばれても結果が変わらないことを指す。

### 番号だけで別の箇所を指さない

Claude は、文の中で別の箇所に触れるときに、番号だけで指さない。Claude は、触れる先の中身を同じ文の中で言葉にする。

**外れた文の例**(例の一覧の組4)

> - 推奨: B。A は今のやり方で、上の2のとおり誤りが止まっていないため。

**直した文の例**

> - 推奨: B。A は今のやり方で、メモリに決まりを書いたあとも、AIが同じ種類の文をあなたに差し戻され続けているため。

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> そのときは、Claude は 5-2 に従う。

**直した文の例**

> そのときは、Claude は目次も直さず、1と同じく所有者に見せる。

### 指すものを文の中で言い切る

Claude は、「問題」「点」「対応」「どちらでもない動き」のように、何を指すかが文の前後から決まらない言葉で文を済ませない。Claude は、指すものをその文の中で言い切る。

**外れた文の例**(例の一覧の組41)

> **要件に足りないこと**
> 別の Claude がどちらでもない動きをしたときに、フックを残すのか消すのかが、要件に書いてありません。たとえば、判断の報告を出さずにそのまま止まったときです。

**直した文の例**

> **要件に足りないこと**
> 別の Claude が、判断の報告を出して止まることも、報告の前にファイルを書き換えることもしなかったときに、私がフックを残すのか消すのかが、要件に書いてありません。たとえば、別の Claude が判断の報告を出さずにそのまま止まったときです。

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> 問題を見つけたら、Claude は対応を所有者に見せる。

**直した文の例**

> メモリの記述に誤りの疑いを見つけたら、Claude は、その記述の直し方の案を所有者に見せる。

### 英語の定型文を使わず、見出しと欄を日本語で書く

Claude は、「The ○○ shall …」「When …, the ○○ shall …」のような、英語と日本語を混ぜた定型文を使わない。Claude は、見出しと欄の名前を日本語で書く。

**外れた文の例**(例の一覧の組56)

> ### Allowed Dependencies
>
> - Claude Code のフック機構(`UserPromptExpansion` / `UserPromptSubmit` / `SubagentStop` / `PostToolUse` / `Stop`)
> - Agent ツールによるサブエージェントの起動とモデル指定
>
> (以下略)

**直した文の例**

> ### この spec の仕組みが使う、すでにある道具
>
> - Claude Code のフック。使うのは `UserPromptExpansion`、`UserPromptSubmit`、`SubagentStop`、`PostToolUse`、`Stop` の5つである
> - Claude が別のAIを起動する Agent ツール。起動するときに、別のAIのモデルを決める
>
> (以下略)

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

> When 所有者が tasks を承認する, the 承認の手順 shall record the approver in spec.json.

**直した文の例**

> 所有者が tasks を承認したら、Claude は spec.json の `approved_by` に承認者の名前を書く。

### 日本語で言える英語を混ぜない

Claude は、日本語で言える意味の英語を、そのまま文に混ぜない。所有者が画面で目にする名前は、この決まりの例外である。

**外れた文の例**(例の一覧の組6)

> - **死活ステップの判定不能**: 死活ステップも、判定不能のときは同様にステップを失敗とする。死活ステップは全PRの hot path にあるが、判定はAPIの1リクエストで、再実行が安価である。この設計は、fail-closed を優先する(素通りは「監査停止の見逃し」そのものだからである)

**直した文の例**

> - **監査が動いているかを確かめるステップが、判定できないとき**: このステップも、判定できないときは失敗にする。このステップはすべてのPRで動くので、失敗するとすべてのPRが止まる。それでも、判定は API への1回の問い合わせで済み、やり直しても手間はかからない。そこで、この設計は、判定できないときはPRを通さずに止めるほうを選ぶ。通してしまうと、監査が止まっていることを見逃すからである。

### 同じものは同じ名前で呼び、違うものは違う名前で呼ぶ

Claude は、1つの文書の中で、同じものを別々の名前で呼ばず、違うものを同じ名前で呼ばない。

**外れた文の例**(例の一覧の組5)

次の2つは、spec を審査するエージェントを「レビュー役」とも「審査役」とも呼び、タスクの実装を審査するエージェントも「レビュー役」と呼んでいた文書の文である。

> - レビュー役の定義と、その制約(`spec-reviewer` エージェント)

> - 選んだ型: この設計は、実装役とレビュー役を別のサブエージェントに分ける。フックがレビューの実施の事実を記録し、別のフックがその事実を検査する。この設計は、`kiro-impl` の実装役・レビュー役・デバッグ役の往復と、`record-gate-run.sh` と `check-verify-before-stop.sh` の記録と検査の組み合わせを、spec の段階へ持ち込む

**直した文の例**

> - spec を審査するエージェント `spec-reviewer` の定義と、その制約

> - 選んだ型: この設計は、spec を書くエージェントと spec を審査するエージェントを、別のサブエージェントに分ける。フックがレビューの実施の事実を記録し、別のフックがその事実を検査する。この設計は、`kiro-impl` での、タスクを実装するエージェントと、実装を審査するエージェントと、失敗の原因を調べるエージェントの往復と、`record-gate-run.sh` と `check-verify-before-stop.sh` の記録と検査の組み合わせを、spec の段階へ持ち込む

### 1つの文書で同じ決めごとを繰り返さない

Claude は、1つの文書の中で、同じ決めごとを言い換えて複数の節に書かない。

**外れた文の例**(例の一覧の組7)

同じ文書の「作るもの」の節にも、次の文と同じ4つのことが書かれていた。

> Issue #559 のために、この設計は、次の4つを足す。1つ目に、実装セッションは、所有者が選び、実装セッションが spec.json に記録したモデルでレビュー役を起動する。2つ目に、Fable 5.1 が上限に達してレビュー役が動かないときは、実装セッションは Opus 5.5 でレビュー役を起動し直す。3つ目に、実装セッションは、前回レビュー役を起動したときの本文を控えておき、本文を直したあとのレビューでは、控えとの差分をレビュー役に渡す。4つ目に、実装セッションは、往復ごとのレビュー役のモデルと使った量を response のファイルに書く。(#559)

**直した文の例**

> Issue #559 のために、この設計は、「作るもの」の節で「(#559)」の印を付けたものを足す。

**外れた文の例**(Claude が作った例。spec-writing.md から移した)

design.md の概要の節に「点検の記録が本文より古ければ、Stop フックが Claude の作業を止める。」と書き、部品の節にも「本文を直したあとに点検し直していなければ、Claude は承認に進めない。」と書く。

**直した文の例**

Claude は、止まる条件を `spec-review-scan.sh` の部品の節にだけ書き、概要の節には「Claude は、判定のスクリプト `spec-review-scan.sh` に、点検の記録が本文より古いかどうかの判定を足す。」とだけ書く。

### 何が起きればよいのかを具体的に書く

Claude は、何が起きればよいのかを書かずに、抽象的な言葉で文を済ませない。Claude は、誰が何をすれば、または何が起きれば、その文の言うとおりになるのかを書く。

**外れた文の例**(例の一覧の組8)

> ### 要件4 依存の検査の保証の水準を保つ
>
> 所有者は、切り替えによって、依存の脆弱性とクールダウンの担保が弱まらないようにしてほしい。

**直した文の例**

> ### 要件4 マージの仕方を切り替えたあとも、脆弱性のある依存と、公開から72時間たっていない依存を、今と同じく止める
>
> 所有者は、マージの仕方を切り替えたあとも、脆弱性のある依存か、公開から72時間たっていない依存が入ったPRを、今と同じくマージさせたくない。

### 1つの文の途中で話の中心を替えない

Claude は、1つの文の途中で話の中心を替えない。話の中心が替わるところで、Claude は文を分け、後半の文にも主語を書く。

**外れた文の例**(例の一覧の組9)

> backend の依存は Gradle の解決の結果に依存し、変更を重ね合わせると解決の結果が変わりうるからである。

**直した文の例**

> backend が使う依存の版は、Gradle が組み合わせを計算して決める。そのため、複数のPRの変更を重ねると、Gradle が選ぶ版が変わることがある。

### 表のマスには短い言葉だけを書く

Claude は、表の1つのマスに、いくつもの文や括弧書きを詰め込まない。Claude は、表を、短い言葉を並べて見比べるときにだけ使い、理由は表の下に文で書く。

**外れた文の例**(例の一覧の組10)

> | 観点 | 当たるか | 根拠 |
> |---|---|---|
> | 作り方を選ぶ必要があるか | 当たる | 作り方によって、マージしたあとにあなたが受け取るものが変わります。たとえば「決まりの文を足すだけ(今と同じく、守られなかったらあなたが気づいて指摘する)」と「AIが報告を送る前に別の役が読み直して止める(わかりにくい文があなたに届く前に直る)」です。本文にも既存の文書にも、どちらにするかを決める材料がありません。あなたも壁打ちが要ると言っているので、1回の問いでは決まりません |

**直した文の例**

> | 観点 | 当たるか |
> |---|---|
> | 作り方を選ぶ必要があるか | 当たる |
>
> **作り方を選ぶ必要があるか**: 当たります。作り方によって、マージしたあとにあなたが受け取るものが変わるためです。
> - 決まりの文を足すだけにすると、今と同じく、守られなかった文があなたに届き、あなたが指摘します。
> - AIが報告を送る前に別のエージェントが読み直すようにすると、わかりにくい文は、あなたに届く前に直ります。
>
> Issue の本文にも既存の文書にも、どちらにするかを決める材料がありません。あなたも壁打ちが要ると言っているので、1回の問いでは決まりません。

### 所有者が知っている正式な名前を使う

Claude は、所有者が知っている正式な名前を、別の言い方に置き換えない。

**外れた文の例**(例の一覧の組11)

> **AWS の画面(ブラウザで開く管理画面)で設定を変えるときに、ひと手間増えてもよいですか。**

**直した文の例**

> **AWS マネジメントコンソールで設定を変えるときに、ひと手間増えてもよいですか。**

### 動詞を本来の意味で使い、たとえの言葉を使わない

Claude は、動詞を本来とは違う意味で使わず、たとえの言葉も使わない。

**外れた文の例**(例の一覧の組12)

> 3つ目の「他にありえた選択肢」が肝だと思っています。**ここが書けないものは、申告する必要がありません。** リポジトリの既存のやり方に従っただけで他に選びようがないものは、あなたが判断する余地が無いからです。前に話した絞り込みの基準が、この項目に落ちています。
>
> 並び順は「外れていた場合」の影響が大きいものから上にします。上から読んで、途中で「ここまでは全部妥当」と思ったら止められます。

**直した文の例**

> 4つの中で一番大事なのは、3つ目の「ほかにどんな選び方があったか」です。ほかの選び方を書けないものは、申告しなくてよいことにします。リポジトリの今のやり方に従っただけで、ほかに選びようがないものは、あなたが判断することが無いからです。前に話した、申告するものを絞り込む基準は、この3つ目を書けるかどうかで決まります。
>
> 申告は、外れていたときの影響が大きいものから順に、上に並べます。あなたは上から読み、途中で「ここまでは全部妥当」と思ったら、そこで読むのをやめてかまいません。

### どうやってするのかが分かる動詞を使う

Claude は、「伝える」「提出する」「知らせる」のように、どうやってするのかが分からない動詞で文を済ませない。Claude は、どこで、何を使って、何をするのかを書く。

**外れた文の例**(例の一覧の組13)

次の2つは、README の図の矢印に書いた文である。

> Human->>Claude: 【人間】Issueを起票し、作りたいもの・直したいものを伝える

> Claude->>Human: 要件・設計・タスクの仕様書を作成して提出する

**直した文の例**

> Human->>Claude: GitHub で Issue を作り、作りたいものか直したいものを本文に書く

> Claude->>Human: .kiro/specs/ に要件・設計・タスクの文書を作り、チャットで承認を頼む

### なぜ困るのか、なぜ問題ないのかを書く

Claude は、何が起きるかだけを書いて文を終えない。Claude は、それが起きるとなぜ困るのか、または、なぜ問題ないのかを書く。

**外れた文の例**(例の一覧の組14)

> **tflint と checkov の更新 PR が、人の目を通らずにマージされる。** 今の設定では、Dependabot の PR はすべて自動マージが予約されます。また、`docker/terraform/` はあなたの承認が要る場所に入っていません。そのため、terraform の検査が通る版の更新は、そのまま main に入ります。新しいルールが増えた版は検査が赤になるので止まります。
>
> (中略)
>
> 残りの 6 件は、そのままで問題ないと判断しています。
>
> - 棚卸しが止まったとみなす日数を 35 日にしたこと
> - カバレッジは main の直近の値を使うこと
>
> (以下略)

**直した文の例**

> **tflint と checkov の新しい版を入れる PR は、あなたの承認を待たずにマージされます。** 困るのは、新しい版で検査のルールが減ったり、見逃しが増えたりしたときです。そのときも検査は緑のままなので、誰も気づけません。ただし、ESLint など、ほかの検査の道具の新しい版も、同じく承認を待たずにマージされています。tflint と checkov だけを別に扱う理由が無いので、私は今のままでよいと考えています。
>
> 残りの6件は、要件を書いた私が、あなたに確かめずに決めたことです。理由を1件ずつ書きます。
>
> 1. 棚卸しが止まったとみなす日数を35日にしました。棚卸しは月に1回動くので、1回分の遅れを見込んだ日数です。
> 2. カバレッジは、main の CI の直近の結果から取ります。棚卸しのために、テストをもう一度流す手間をかけないためです。
>
> (以下略)

### 「〜せず」「〜ずに」を重ねない

Claude は、「〜せず」「〜ずに」を1つの文に重ねない。Claude は、何をしないかではなく、何が起きるのかを書く。

**外れた文の例**(例の一覧の組15)

> **推奨**: `run-check.sh` が、terraform の `apply` と `destroy` を受け付けず、品質チェックを動かさずに止まるようにします。

**直した文の例**

> **推奨**: 私が `terraform apply` か `terraform destroy` を `run-check.sh` で動かそうとしたら、`run-check.sh` はそのコマンドを動かさずに、エラーを出して終わるようにします。

### 仕組みを知らない人にも中身が分かる見出しにする

Claude は、仕組みを知らない人には中身が分からない見出しを書かない。Claude は、その節で何をするのか、何のことかが分かる言葉で見出しを書く。

**外れた文の例**(例の一覧の組16)

> ### 3. 退けた指摘のサンプリング

**直した文の例**

> ### 1. Claude Code の利用量の確認

> ### 3. AIレビューの指摘を、AIが正しい理由なく退けていないかの抜き取り確認

## 決まりに入れない書き方

所有者は、次の4つの書き方を、わかりにくい文に入れないと決めた。Claude は、この4つを `## 決まり` の節に入れない。点検役 `spec-style-checker` も、この4つを決まりから外れた書き方として挙げない。

- 「双方」「〜に限られる」「代替ではなく補完の関係にある」「失敗しうる」のような硬い言い回し
- 1つの段落の中で太字をいくつも使うこと
- 書いていないことまで読み取れてしまう文
- 順番にすることに番号を振らない書き方

## 決まりと例を足すとき

### 所有者がわかりにくいと指摘したとき

所有者が、Claude が送った文をわかりにくいと指摘したら、Claude は次の順に進める。

1. Claude は、指摘された文を書き直して、所有者に送り直す。
2. Claude は、`git fetch origin` のあと、`git worktree add <scratchpad のフォルダ> -b docs/<短い説明> origin/main` で、そのとき進めている作業のブランチとは別のブランチと作業フォルダを作る。ブランチ名は `.branch_name_template` に従う。
3. Claude は、その作業フォルダで、指摘された文と書き直した文を、このファイルの当たる決まりの例と、例の一覧 `owner-writing-examples.md` に足す。指摘された文がどの決まりにも当たらないときは、Claude は、その種類の文を差し戻す決まりを、新しい `### ` の見出しで足す。指摘された文が今ある決まりに当たるときは、Claude は、その決まりに例だけを足す。
4. Claude は、下の「決まりを変える PR での確かめ」をやり直し、結果を PR の本文に書く。
5. Claude は、`.commit_template` に従ってコミットし、push し、`gh pr create` で PR を作る。Claude は、PR を作ったことを、PR の番号を添えて、チャットで所有者に1文で知らせる。そのあと、Claude は `git worktree remove` で作業フォルダを消す。

Claude は、この PR を、そのとき進めている作業の PR に混ぜない。このファイルと例の一覧は、所有者の承認が要る場所(`.github/CODEOWNERS` に書かれた場所)の外にある。そのため、この PR は、品質のチェックを通れば、所有者の承認を待たずに自動でマージされる。Claude は、決まりと例を、エージェントの定義とスキルの手順に写さない。写すと、例を足す PR が、所有者の承認が要る場所を直すことになるためである。

### 決まりを変える PR での確かめ

Claude は、このファイルの決まりを変える PR を作る前に、例の一覧のすべての組で、次の順に確かめる。

1. Claude は、組ごとに、差し戻された文を、引用ではなく自分が送る文として読み、このファイルのどの決まりから外れるかを、例の一覧の「当たる決まり」の欄に書く。
2. Claude は、組ごとに、書き直した文が、どの決まりからも外れないことを確かめる。
3. 外れる決まりを挙げられない差し戻された文か、決まりから外れる書き直した文があれば、Claude は、このファイルの決まりと例を直し、1から確かめ直す。同じ文で3回直しても外れる決まりを挙げられないときは、Claude は止まって所有者に知らせる。
4. Claude は、組ごとの結果を、PR の本文の表に書く。表には、組の番号、差し戻された文が外れる決まりの名前、書き直した文が外れないことを書く。

Claude は、この確かめのために、別のエージェントを動かさない。
