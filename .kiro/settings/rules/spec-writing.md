# spec の書き方

このファイルは、Claude が spec の requirements.md・design.md・tasks.md を書くときと、書いた本文を点検するときに従う書き方の決まりを定める。このファイルの決まりは、すべての spec に当てはまる。

spec の本文には、所有者に送る文の書き方の決まり `.kiro/settings/rules/owner-writing.md` の `## 決まり` の節の決まりも当てはまる。Claude は、spec を書くときと点検するときに、このファイルより先に `owner-writing.md` を読む。このファイルには、spec の本文にだけ当てはまる決まりを書く。

spec を書くスキル(`/kiro-spec-init` `/kiro-spec-requirements` `/kiro-spec-design` `/kiro-spec-tasks`)、点検役 `spec-style-checker`、spec を読むスキル(`/kiro-impl` など)は、spec を扱うときにこのファイルを読む。所有者は、Claude が書いた spec の書き方を確かめるときに、このファイルを基準にできる。

Claude は、Issue本文や既存の文書から引用した部分を、このファイルの決まりに合わせて書き直さない。Claude は、引用した部分を引用元のまま残す。

決まりごとの「外れた文の例」は、決まりから外れた書き方をわざと示す。Claude は、外れた文の例を spec の書き方の手本にしない。

## 文の書き方

この節の決まりは、requirements.md・design.md・tasks.md のすべてに当てはまる。所有者が spec の文を一度読めば、誰が何をするのかが分かるようにするためである。

### 常体で書く

Claude は、spec の本文を常体(だ・である調)で書く。Claude は、敬語(です・ます調)を混ぜない。

- 外れた文の例: 「Claude は、点検の記録を spec のディレクトリに残します。」
- 直した文の例: 「Claude は、点検の記録を spec のディレクトリに残す。」

### 対応の行だけは要件の番号で書く

Claude は、design.md の「対応する要件」の行と、tasks.md でタスクと要件の対応を示す行(`_要件:_` の行)を、要件の番号だけで書く。これは、`owner-writing.md` の決まり「番号だけで別の箇所を指さない」の例外である。これらの行は、文ではなく、どの要件を満たすかの対応表として使うからである。

- 外れた文の例: 「対応する要件: 点検の記録を残すこと、点検の記録が古いまま承認を求めると止まること」
- 直した文の例: 「対応する要件: 6.5, 6.6」

### 原則を先に書き、例外はあとに別の文で書く

Claude は、1つの文に、条件と例外と別の箇所への参照を重ねない。Claude は、原則を先に書き、例外はそのあとに別の文で書く。

- 外れた文の例: 「目次とメモリファイルが対応していないときは、そのメモリファイルに誤りの疑いが無い限り、5-1 によらず Claude が目次を直す。」
- 直した文の例: 「目次とメモリファイルが対応していないだけのときは、Claude が所有者に尋ねずに目次を直す。ただし、そのメモリファイルに誤りの疑いもあるときは、Claude は目次も直さず、1と同じく所有者に見せる。」

## 文書の組み立て

文の書き方だけを直しても、英語の雛形の組み立てが残ると、文書は読みにくいままになる。そこで、Claude は文書の組み立ても見本1と見本2に合わせる。

### requirements.md の要件の組み立て

Claude は、requirements.md の各要件を、次の順で書く。

1. 「要件1 題名」のような番号と題名の見出し(`### 要件N 題名`)
2. 所有者がなぜそれを望むのかを書いた段落
3. 番号付きの項目

Claude は、「所有者として、…したい」のような利用者の立場を名乗る行と、「受入基準」の小見出しを書かない。

- 外れた文の例:

  ```markdown
  ### Requirement 5: メモリの修正の判断
  **Objective:** As a 所有者, I want メモリの修正を自分で決めたい, so that 誤りが増えない
  #### Acceptance Criteria
  1. When 点検で誤りの疑いを見つけた, the 点検の手順 shall 所有者に案を見せる.
  ```

- 直した文の例:

  ```markdown
  ### 要件5 メモリを直すかどうかは所有者が決める

  Claude が自分の判断でメモリを書き換えると、その書き換えが新しい誤りになるおそれがある。そこで、メモリを直すかどうかは原則として所有者が決める。

  1. 点検でメモリの記述に誤りの疑いを見つけたら、Claude は、その記述の直し方の案を所有者に見せる。
  ```

### design.md の部品の節の組み立て

Claude は、design.md の部品ごとの節を、次の順で書く。

1. 部品の名前と、その部品が何かを括弧で添えた見出し
2. 対応する要件の行
3. 「役割」「権限」のような日本語の欄

- 外れた文の例:

  ```markdown
  #### ReserveAutoMerge

  | Field | Detail |
  |---|---|
  | Intent | PRに予約を付ける |
  | Requirements | 3.1, 3.2 |

  **Responsibilities & Constraints**
  - The workflow shall call reserve-auto-merge.sh.
  ```

- 直した文の例:

  ```markdown
  ### auto-merge.yaml(PRに自動マージの予約を付けるワークフロー)

  対応する要件: 3.1, 3.2

  **役割**: このワークフローは、PRごとにスクリプト `reserve-auto-merge.sh` を呼び出す。予約を付けるかどうかはスクリプトが判定し、ワークフローは判定しない。
  ```

## design.md の書き方

design.md は、設計として成り立ったまま、所有者が読んで分かるものでなければならない。Issue #474 の壁打ちで、所有者は、技術の中身を削って平易にした書き直しを「設計になっていない」と退けた。

### 技術の中身を削らない

Claude は、design.md を分かりやすくするために、技術の中身を削らない。Claude は、イベント名、権限、設定の値、時間の上限、コマンドの引数のように、実装に要る情報を design.md に残す。

- 外れた文の例: 「このワークフローは、必要なときに起動し、適切な権限で予約を付ける。」
- 直した文の例: 「このワークフローは、main に向けた `pull_request` の `opened` と `synchronize` で起動する。ワークフローに与える権限は、`contents: read` と `pull-requests: write` の2つに限る。」

### 部品が何をして何をしないかを書く

Claude は、design.md の部品ごとに、その部品が何をして何をしないのかを、主語と目的語のある文で書く。

- 外れた文の例: 「**役割**: 予約の判定と、その呼び出し。」
- 直した文の例: 「**役割**: このワークフローは、PRごとにスクリプト `reserve-auto-merge.sh` を呼び出す。予約を付けるかどうかはスクリプトが判定し、ワークフローは判定しない。」

## 繰り返しの扱い

同じ決めごとが何度も書かれていると、所有者は同じ内容を繰り返し読むことになる。文書が長いこと自体はかまわない。

### design.md と tasks.md に requirements.md の決めごとを書き写さない

Claude は、design.md と tasks.md に、requirements.md に書いた決めごとを書き写さない。Claude は、design.md には、requirements.md の決めごとをどう実現するかを書く。Claude は、tasks.md には、どの順番で何を作るかを書く。

- 外れた文の例: design.md の部品の節に「Claude は、所有者に承認を求める前に、本文の全体が書き方に沿っているかを点検する。」と書く(requirements.md の決めごとの書き写し)。
- 直した文の例: design.md の部品の節に「`/spec-review` は、Step 1 と Step 2 の間に点検の工程を置き、審査役を起動する前に点検役に本文を点検させる。」と書く。

### tasks.md で受入基準を引くことは書き写しに当たらない

例外として、Claude が tasks.md で、受入基準とそれを確かめるテストの対応を示すために受入基準を引くことは、書き写しに当たらない。Claude は、受入基準を、タスクの説明の文ではなく、「受入基準とテストの対応」の行で引く。

- 外れた文の例: タスクの説明の文に「Claude は、本文を最後に直したあとの点検の記録が無いまま承認を求めると作業が止まるようにする。」と書く。
- 直した文の例: タスクの説明の文に「Claude は、変更後の `spec-review-scan.sh` を scratchpad に用意する。」と書き、その下の箇条書きに「受入基準とテストの対応: 要件6の受入基準6(本文を直したあとの点検の記録が無いまま承認を求めると止まる)は、テストの「本文が点検の記録より新しければ理由を出す」で確かめる」と書く。

## Issueの印

既存の spec を新しいIssueのために直したとき(`/kiro-spec-init #N <feature>` で開き直し、spec.json に `additional_issues` があるとき)は、
要件・受入基準・設計の節・タスクがどのIssueに対するものかを、次の印で本文の中に示す。

- 追加のIssue #N のために足した項目は、末尾に `(#N)` を付ける。設計の節を足したときは、節の見出しの末尾に付ける
- 既存の項目を直したときは、直した項目の末尾に `(#N で変更)` を付ける
- 既存の項目を取りやめるときは、本文を消さず、先頭に `(#N で取りやめ)` を付ける
- 印の無い項目は、spec.json の `issue`(元のIssue)に対するものとする
- spec 無しのPRで変わった動きを、spec を更新するときに反映した項目は、末尾に `(PR #<番号> で変更済み)` を付ける。この項目の動きは、そのPRで実装済みである
- 既存の要件・受入基準・タスクの番号は変えない。新しい要件は既存の最後の番号の次から足す(実装済みのタスクの `_要件:_` が指す番号をずらさないため)
- tasks.md では、`(#N)` をタスクの題名の末尾に置き、題名に `(並行可)` があるときはそのあとに置く。`_要件:_` の行には付けない
- 実装済みのタスクの完了の印(`[x]`)は外さない

審査役と点検役は、追加のIssueのために足した要件・設計の節・タスクのそれぞれに `(#N)` があるかを確かめる。印の無い項目は元のIssueに対するものと読まれるので、印の抜けは、印の置き場所の誤りと同じく誤りである。

## 見本

Claude は、次の3つの見本を、spec の書き方の基準として読む。見本1は requirements.md の要件1つ、見本2は design.md の1節、3つ目は tasks.md のタスク1つの基準である。Claude は、tasks.md を、3つ目の見本と同じ組み立てで書く。

見本1と見本2は、既存の spec の一部を所有者との壁打ちで書き直し、所有者が合格とした文章である。Claude は、見本1と見本2を Issue #474 の本文から文字を変えずに写した。Claude は、見本に手を入れない。

### 見本1: requirements.md の要件1つ

元の文章: `.kiro/specs/memory-contamination-check/requirements.md` の Requirement 5

> ### 要件5 メモリを直すかどうかは所有者が決める
>
> メモリの多くは、所有者の指摘を Claude が書き留めたものである。Claude が自分の判断でメモリを書き換えると、その書き換えが新しい誤りになるおそれがある。そこで、メモリを直すかどうかは原則として所有者が決める。
>
> 1. 点検でメモリの記述に誤りの疑いを見つけたら、Claude は、どのメモリファイルのどの記述が疑わしいかと、その記述の直し方の案を所有者に見せる。誤りの疑いとは、古くなった事実、一度の出来事を一般の決まりとして書いたもの、根拠の書かれていない主張などを指す。所有者がその記述を直すかどうかを答えるまで、Claude はそのメモリファイルを書き換えない。
> 2. 所有者がその記述を直すと答えたら、Claude は、所有者が決めた直し方のとおりにその記述を書き換える。
> 3. 所有者がその記述を直さないと答えたら、Claude は「この記述は直さない」という所有者の答えを点検の記録に残す。そのあとの点検では、その記述の文面が変わらない限り、Claude は同じ記述を誤りの疑いとして挙げない。
> 4. Claude が所有者に見せた誤りの疑いのうち、所有者が直すか直さないかをまだ答えていないものは、次の点検の結果にも「所有者の答え待ち」として載せ続ける。
> 5. 例外として、目次(MEMORY.md)とメモリファイルが対応していないだけのときは、Claude が所有者に尋ねずに目次を直す。対応していないとは、目次に行があるのにメモリファイルが無いこと、またはメモリファイルがあるのに目次に行が無いことを指す。Claude は目次の行を足すか消して、実際のファイルに合わせる。メモリファイルの中身は書き換えない。目次を直したことは点検の結果に書く。ただし、そのメモリファイルに誤りの疑いや、誰かが会話の外で直接書き換えた疑いもあるときは、Claude は目次も直さず、1と同じく所有者に見せる。

### 見本2: design.md の1節

元の文章: `.kiro/specs/issue-close-and-auto-merge-guarantee/design.md` の「auto-merge.yaml」の節

> #### auto-merge.yaml(PRに自動マージの予約を付けるワークフロー)
>
> 対応する要件: 3.1, 3.2, 3.3, 3.5, 3.6, 4.1, 4.2, 4.4, 6.2, 6.3
>
> **役割**: このワークフローは、PRのイベントと定期実行で起動し、PRごとにスクリプト `reserve-auto-merge.sh` を呼び出す。予約を付けるかどうかはスクリプトが判定し、ワークフローは判定しない。
>
> **権限**: ワークフローに与える権限は、`contents: read`(コードを checkout するため)と `pull-requests: write`(PRに知らせのコメントを書くため)の2つに限る。予約の操作には、ボットのトークン `secrets.BOT_GITHUB_TOKEN` を使う。ワークフローはPRの変更内容を checkout しない。
>
> **PRのイベントで起動するとき(ジョブ `reserve`)**
> - 起動するイベント: main に向けた `pull_request` の `opened` `reopened` `ready_for_review` `synchronize` `auto_merge_disabled`
> - 動かす条件: PRが同じリポジトリのブランチから出されていて、作成者が `dependabot[bot]` でないこと。fork と Dependabot のイベントにはシークレットが渡されないので、スクリプトを呼ぶ前に、ジョブの条件で外す
> - 手順: ワークフローはPRの base のコミット(`github.event.pull_request.base.sha`)を、認証情報を残さない設定(`persist-credentials: false`)で checkout する。次に、スクリプトのテスト3本のうち予約に関わる2本を流す。最後に `reserve-auto-merge.sh <PR番号>` を呼ぶ
> - 同時実行: 同じPRのジョブは、`auto-merge-<PR番号>` の組で1つずつ動かす。あとから起動したジョブは、先に動いているジョブを止めずに、終わるのを待つ(`cancel-in-progress: false`)
>
> **定期実行で起動するとき(ジョブ `sweep`)**
> - 起動: 30分ごと(cron `7,37 * * * *`)と、手での起動(`workflow_dispatch`)
> - 手順: ワークフローは既定のブランチを checkout し、スクリプトのテストを流してから、`reserve-auto-merge.sh --sweep` を1回呼ぶ。対象のPRの一覧はスクリプトが取り、ワークフローはPRを選ばない
> - 失敗したとき: スクリプトは、同じPRに何度呼ばれても結果が変わらないように作る。スクリプトは1件の失敗では止まらずに残りのPRを続け、最後に1件でも失敗があればジョブを失敗にする。ワークフローは、PR1件ごとの呼び出しを120秒で打ち切る
> - 同時実行: `auto-merge-sweep` の組で1つずつ動かす(`cancel-in-progress: false`)。ジョブ全体は30分で打ち切る

### tasks.md の見本

この見本は、tasks.md の書き方の基準である。

```markdown
- [ ] 3. 点検の記録が古いまま承認に進めないようにする
- [ ] 3.1 点検の記録の判定を scan に足す (並行可)

  Claude は、変更後の `spec-review-scan.sh` を scratchpad に用意する。この scan は、点検の記録が無いときと、本文が点検の記録より新しいときに、理由を出す。
  - 完了の確かめ方: テスト `test-spec-review-scan.sh` の場合がすべて通る
  - 受入基準とテストの対応: 要件6の受入基準6(本文を直したあとの点検の記録が無いまま承認を求めると止まる)は、テストの「本文が点検の記録より新しければ理由を出す」で確かめる
  - _要件: 1.2, 6.6_
  - _対象の部品: spec-review-scan.sh_
  - _依存: 1.1_
```

Claude は、大タスクと小タスクの最初の行を、どちらもタスクの箱と番号と題名にする。Claude は、ほかのタスクと並行に進められる小タスクの題名の末尾に、`(並行可)` を付ける。Claude は、既存の spec に追加の Issue #N のためにタスクを足したとき、そのタスクの題名の末尾に印 `(#N)` を置く。題名に `(並行可)` があるときは、Claude は `(#N)` を `(並行可)` のあとに置く。Claude は、小タスクの題名の行のあとに空行を1つ置き、その次の行に、誰が何を作るかを主語と目的語のある文で書く。大タスクに説明の文を書くときも、Claude は同じ形にする。空行を置くのは、tasks.md を Markdown として表示したときに、説明の文が題名と同じ段落につながらないようにするためである。Claude は、その下の箇条書きに、完了の確かめ方、受入基準とテストの対応、`_要件:_`・`_対象の部品:_`・`_依存:_` の目印を書く。
