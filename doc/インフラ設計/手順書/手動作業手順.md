# KeirekiPro インフラ構築 手動作業手順書

本手順書は、Terraform実行前に手動で実施する必要がある作業をまとめたものである。
すべての作業を完了してからTerraformを実行すること。

## 作業の順番

所有者は、次の順で作業する。

1. 所有者は、AWS のルートユーザーで、IAM ユーザー `keirekipro` とその MFA、変更用ロール `keirekipro-ops` を作る(1.2.1)
2. 所有者は、自分のPCで、`keirekipro` で `aws login` する(1.2.2)。このログインは読み取り専用である
3. 所有者は、[参加者セットアップ手順](../../開発フロー/参加者セットアップ手順.md) の「5. 本番を変えるターミナル(ops-shell)の設置」のとおりに、ops-shell を置く
4. 所有者は、ops-shell とマネジメントコンソールで、変更用ロールに切り替えられることを確かめる(1.3)
5. 所有者は、「2. SES設定」を、マネジメントコンソールで変更用ロールに切り替えて行う
6. 所有者は、「3. Terraformバックエンド用リソース作成」を、ops-shell で行う
7. 所有者は、「4. GitHub Actions用OIDC設定」を、AWS のルートユーザーで行う
8. 所有者は、[基盤構築手順](../../開発フロー/基盤構築手順.md) の「1. botアカウント・GitHub App・所有者の gh の鍵の準備」のとおりに、GitHub の準備をする
9. 所有者は、「5. Google OAuth認証情報の取得」から「9. Terraform実行後の作業」までを順に行う

## 1. 事前準備

### 1.1 必要なツールのインストール

以下のツールがインストールされていることを確認する。

```bash
# AWS CLIのバージョン確認(2.32.0 以上が必要。1.2 の aws login を使うため)
aws --version
# 出力例: aws-cli/2.x.x Python/3.x.x ...

# AWS CLIが未インストールの場合
# macOS
brew install awscli

# Linux
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install

# Windows
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi
```

### 1.2 AWS CLIの認証設定

アクセスキーは作らない。コンソールのログイン(MFA込み)で一時的な認証情報を得る `aws login` を使う。

普段のログイン(IAMユーザー `keirekipro` の `aws login` とマネジメントコンソール)は読み取り専用である。
所有者と Claude は AWS の状態を読めるが、AWS を変える操作と、秘密の値と Terraform の状態ファイルの中身を読む操作は、AWS が拒む。
所有者は、AWS を変えるときは、変更用ロール `keirekipro-ops` に切り替える(1.3)。

#### 1.2.1 IAMユーザーと変更用ロールの作成(ルートユーザー)

所有者は、AWS のルートユーザーで、IAM ユーザー `keirekipro` とその MFA、変更用ロール `keirekipro-ops` を作る。
`keirekipro` と `keirekipro-ops` は IAM を変えられないため、ルートユーザーで作る。
権限の一覧は `doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md` の 6 と 7 にある。

1. 所有者は、ルートユーザー(AWS アカウントを作ったメールアドレス)でマネジメントコンソールにサインインし、
   リージョンを東京(ap-northeast-1)にして、上のバーの CloudShell のアイコンを押す。以降のコマンドは CloudShell で打つ

2. 所有者は、アカウントの番号を取る。2つ目のコマンドで `OK` が出ればよい:

```bash
export AWS_PAGER=""
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
```

```bash
[[ "$ACCOUNT_ID" =~ ^[0-9]{12}$ ]] && echo OK
```

3. 所有者は、リポジトリからポリシーの JSON を取り出し、その場所に移る:

```bash
git clone --depth 1 https://github.com/DogisRiki/KeirekiPro.git
cd "KeirekiPro/doc/インフラ設計/AWS設計/運用者の権限"
```

4. 所有者は、`keirekipro` のコンソールの初回のパスワードを入れる(画面に出ない)。
   所有者は、1.2.2 で初めてサインインしたときに、新しいパスワードを決める:

```bash
read -rsp 'Initial password: ' KP_PASSWORD; echo
```

5. 所有者は、`keirekipro` を作り、`ReadOnlyAccess` と `SignInLocalDevelopmentAccess` と `keirekipro-readonly-guard` を付ける。
   `keirekipro-readonly-guard` は、`<ACCOUNT_ID>` にアカウントの番号を入れて渡す:

```bash
aws iam create-user --user-name keirekipro
aws iam create-login-profile --user-name keirekipro --password "$KP_PASSWORD" --password-reset-required
unset KP_PASSWORD
aws iam attach-user-policy --user-name keirekipro --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess
aws iam attach-user-policy --user-name keirekipro --policy-arn arn:aws:iam::aws:policy/SignInLocalDevelopmentAccess
aws iam put-user-policy --user-name keirekipro --policy-name keirekipro-readonly-guard \
  --policy-document "$(sed "s/<ACCOUNT_ID>/$ACCOUNT_ID/g" keirekipro-readonly-guard.json)"
```

6. 所有者は、同じ画面の IAM コンソールで、`keirekipro` に認証アプリの MFA を登録する。
   1. 左側メニューの「ユーザー」→ `keirekipro` →「セキュリティ認証情報」タブ →「MFA デバイスの割り当て」をクリック
   2. デバイス名に `authenticator-app` と入力し、「認証アプリケーション」を選んで「次へ」をクリック。
      ops-shell がこの名前を使うので、名前を変えない
   3. 「QR コードを表示」をクリックし、スマホの認証アプリで読み取る
   4. 認証アプリに続けて出た2つのコードを「MFA コード 1」と「MFA コード 2」に入力し、「MFA を追加」をクリック

7. 所有者は、CloudShell に戻り、変更用ロール `keirekipro-ops` を作る。最大のセッションの長さは3600秒にし、
   `PowerUserAccess` と `keirekipro-ops-guard` を付ける。信頼ポリシーは、`<ACCOUNT_ID>` にアカウントの番号を入れて渡す:

```bash
aws iam create-role --role-name keirekipro-ops --max-session-duration 3600 \
  --assume-role-policy-document "$(sed "s/<ACCOUNT_ID>/$ACCOUNT_ID/g" keirekipro-ops-trust.json)"
aws iam attach-role-policy --role-name keirekipro-ops --policy-arn arn:aws:iam::aws:policy/PowerUserAccess
aws iam put-role-policy --role-name keirekipro-ops --policy-name keirekipro-ops-guard \
  --policy-document file://keirekipro-ops-guard.json
```

8. 所有者は、次のコマンドを1つずつ打ち、右に書いた出力になることを確かめる:

| コマンド | 出力 |
|---|---|
| `aws iam list-attached-user-policies --user-name keirekipro --query 'AttachedPolicies[].PolicyName' --output text` | `ReadOnlyAccess` と `SignInLocalDevelopmentAccess` の2つだけ |
| `aws iam list-user-policies --user-name keirekipro --query 'PolicyNames' --output text` | `keirekipro-readonly-guard` だけ |
| `aws iam list-mfa-devices --user-name keirekipro --query 'MFADevices[].SerialNumber' --output text` | `:mfa/authenticator-app` で終わる1行 |
| `aws iam list-attached-role-policies --role-name keirekipro-ops --query 'AttachedPolicies[].PolicyName' --output text` | `PowerUserAccess` だけ |
| `aws iam list-role-policies --role-name keirekipro-ops --query 'PolicyNames' --output text` | `keirekipro-ops-guard` だけ |
| `aws iam get-role --role-name keirekipro-ops --query 'Role.MaxSessionDuration' --output text` | `3600` |

9. 所有者は、次を打ち、出たアカウントの番号を控える。1.2.2 で `keirekipro` でサインインするときに使う。
   控えた番号は、リポジトリのファイル、Issue、PR に書かない(リポジトリは公開されている):

```bash
echo "$ACCOUNT_ID"
```

10. 所有者は、CloudShell を閉じ、ルートユーザーからサインアウトする

#### 1.2.2 aws login

所有者は、自分のPCの普段のターミナルで、`keirekipro` でログインする。
サインインの画面では「IAM ユーザー」を選び、1.2.1 の 9 で控えたアカウントの番号、ユーザー名 `keirekipro`、パスワード、認証アプリの6桁を入れる。
初めてサインインするときは、パスワードに 1.2.1 の初回のパスワードを入れ、続けて新しいパスワードを決める。

```bash
# ログイン(ブラウザが開くので、IAMユーザー keirekipro でコンソールにログインする)
aws login

# リージョンを聞かれたら以下を入力
# AWS Region: ap-northeast-1

# 設定確認(Arn が :user/keirekipro で終わればよい)
aws sts get-caller-identity

# 作業が終わったらログアウトする
aws logout
```

- `aws login` には `SignInLocalDevelopmentAccess` ポリシーが要る。`keirekipro` には 1.2.1 で付けてある
- ログインのときに Windows のファイアウォールが aws.exe の通信の許可を求めたら「キャンセル」を選ぶ(許可しなくてもログインできる)

### 1.3 変更用ロールへの切り替えの確認

> 前提: 所有者が [参加者セットアップ手順](../../開発フロー/参加者セットアップ手順.md) の「5. 本番を変えるターミナル(ops-shell)の設置」を済ませ、
> 普段のターミナルで `aws login` していること。

所有者は、ops-shell とマネジメントコンソールの両方で、変更用ロール `keirekipro-ops` に切り替えられることを確かめる。

**ops-shell**

1. 所有者は、スタートメニューの「KeirekiPro ops」を開き、Windows の確認の画面(ユーザーアカウント制御)で「はい」を押す
2. 所有者は、`Enter the 6-digit code from the authenticator app` と出たら、認証アプリの `keirekipro` の6桁を入れる
3. 所有者は、`This window now uses the role keirekipro-ops` と出ることを確かめ、次を打つ。出力が `assumed-role/keirekipro-ops/` を含めばよい

```powershell
aws sts get-caller-identity --query Arn --output text
```

4. 所有者は、ウィンドウを閉じる

**マネジメントコンソール**

1. 所有者は、普段のターミナルで次を打ち、出たアカウントの番号を控える

```bash
aws sts get-caller-identity --query Account --output text
```

2. 所有者は、マネジメントコンソールにサインインしていればサインアウトし、`keirekipro` でサインインし直す(認証アプリの6桁を入れる)
3. 所有者は、サインインしてから1分以内に、右上のユーザー名 →「ロールの切り替え」をクリックし、
   アカウント ID に 1 で控えた番号、IAM ロール名に `keirekipro-ops` を入力して「ロールの切り替え」をクリックする
4. 所有者は、右上に `keirekipro-ops` が出ることを確かめる。1分を過ぎて拒まれたら、2 からやり直す
5. 所有者は、サインアウトする

## 2. SES設定（Route 53・ドメイン検証）

### 前提条件

- keirekipro.click をNamecheapで購入済み
- マネジメントコンソールで、1.3 の手順で変更用ロール `keirekipro-ops` に切り替え済み
- リージョン：東京（ap-northeast-1）

### 2.1 Route 53でホストゾーン作成

1. AWSコンソールで「Route 53」を検索して開く
2. 左メニューの「ホストゾーン」をクリック
3. 「ホストゾーンの作成」ボタンをクリック
4. 以下を入力：
   - ドメイン名：`keirekipro.click`
   - タイプ：「パブリックホストゾーン」
   - コメント：`KeirekiPro production domain`
5. 「ホストゾーンの作成」をクリック
6. 作成後、NSレコードに4つのネームサーバーが表示される。これをメモする

### 2.2 Namecheapでネームサーバー変更

1. Namecheapにログイン
2. 「Domain List」→ keirekipro.click の「Manage」をクリック
3. 「Nameservers」セクションを探す
4. 「Namecheap BasicDNS」から「Custom DNS」に変更
5. 2.1でメモした4つのネームサーバーを入力（末尾のドット「.」は不要）
6. 保存
7. 反映まで数分〜最大48時間待つ

#### 確認方法（ターミナルで実行）

```bash
nslookup -type=NS keirekipro.click
```

awsdns のネームサーバーが表示されればOK

### 2.3 SESでドメイン検証（IDの作成）

1. AWSコンソールで「Amazon SES」を検索して開く（リージョン：東京）
2. 左メニューの「設定」→「ID」をクリック
3. 「IDの作成」ボタンをクリック
4. 以下を設定：
   - IDタイプ：「ドメイン」を選択
   - ドメイン：`keirekipro.click` を入力
5. 「詳細設定」を開く
   - 「Easy DKIM」を選択
   - 「DKIM署名キー長」：2048ビット
   - 「Route 53でDKIMレコードを発行」にチェック
6. 「カスタムMAIL FROMドメインの使用」を開く
   - チェックを入れる
   - MAIL FROMドメイン：`mail`（※ `mail.keirekipro.click` ではなく `mail` のみ入力）
   - MX障害時の動作：「デフォルトのMAIL FROMドメインを使用」
   - 「Route 53でMXレコードを発行」にチェック
7. 「IDの作成」をクリック
8. ステータスが「検証済み」になるまで待つ（数分〜数時間）

#### 自動作成されるレコード

以下のレコードはSESがRoute 53に自動作成する：

| レコード名 | タイプ | 用途 |
|-----------|--------|------|
| {selector1}._domainkey.keirekipro.click | CNAME | DKIM |
| {selector2}._domainkey.keirekipro.click | CNAME | DKIM |
| {selector3}._domainkey.keirekipro.click | CNAME | DKIM |
| mail.keirekipro.click | MX | カスタムMAIL FROM |
| mail.keirekipro.click | TXT | MAIL FROM用SPF |

### 2.4 SPFレコード追加（手動）

Route 53に以下のTXTレコードを手動で追加する。

1. Route 53 → ホストゾーン → keirekipro.click を開く
2. 「レコードを作成」をクリック
3. 以下を入力：
   - レコード名：（空欄のまま = keirekipro.click）
   - レコードタイプ：TXT
   - 値：`"v=spf1 include:amazonses.com ~all"`
   - TTL：300
4. 「レコードを作成」をクリック

### 2.5 DMARCレコード追加（手動）

1. 「レコードを作成」をクリック
2. 以下を入力：
   - レコード名：`_dmarc`
   - レコードタイプ：TXT
   - 値：`"v=DMARC1; p=quarantine; rua=mailto:dmarc@keirekipro.click"`
   - TTL：300
3. 「レコードを作成」をクリック

### 2.6 SESでドメイン検証完了を確認

1. SESコンソール → 設定 → ID → keirekipro.click を開く
2. 以下がすべて「検証済み」または「成功」になっていることを確認：
   - IDステータス：検証済み
   - DKIMの設定：成功
   - カスタムMAIL FROMドメイン：成功

### 最終確認：Route 53レコード一覧

設定完了後、以下の9レコードが存在することを確認：

| レコード名 | タイプ | 用途 | 作成方法 |
|-----------|--------|------|----------|
| keirekipro.click | NS | ドメイン委任 | 自動生成 |
| keirekipro.click | SOA | 権威情報 | 自動生成 |
| keirekipro.click | TXT | SPF | 手動 |
| _dmarc.keirekipro.click | TXT | DMARC | 手動 |
| {selector1}._domainkey.keirekipro.click | CNAME | DKIM | SES自動 |
| {selector2}._domainkey.keirekipro.click | CNAME | DKIM | SES自動 |
| {selector3}._domainkey.keirekipro.click | CNAME | DKIM | SES自動 |
| mail.keirekipro.click | MX | カスタムMAIL FROM | SES自動 |
| mail.keirekipro.click | TXT | MAIL FROM用SPF | SES自動 |

### 注意事項

#### MAIL FROMドメイン入力時の注意

SESでカスタムMAIL FROMドメインを設定する際、入力欄には `mail` のみを入力する。`mail.keirekipro.click` とフルで入力すると、レコード名が `mail.keirekipro.click.keirekipro.click` になってしまう。

#### 誤って別リージョンでIDを作成した場合

別リージョン（例：バージニア北部）で誤ってIDを作成し削除した場合、Route 53に作成されたDKIMレコード（CNAMEレコード3個）は自動削除されない。不要なレコードは手動で削除する必要がある。

## 3. Terraformバックエンド用リソース作成

TerraformはS3バケットとDynamoDBテーブルを状態管理に使用する。
これらはTerraform自身で作成できないため、事前に手動で作成する。

所有者は、この章のコマンドを、スタートメニューの「KeirekiPro ops」で開いた ops-shell(1.3)で打つ。
普段のログインでは作れないためである。ops-shell は PowerShell なので、コマンドは PowerShell の書き方にしてある。
所有者は、15分を過ぎて `ExpiredToken` が出たら、`ops-renew` を打って6桁を入れ直し、失敗したコマンドから続ける。

### 3.1 S3バケットの作成

```powershell
# 変数設定
$BUCKET_NAME = "keirekipro-terraform-state"
$REGION = "ap-northeast-1"

# S3バケット作成
aws s3api create-bucket --bucket $BUCKET_NAME --region $REGION --create-bucket-configuration "LocationConstraint=$REGION"

# バージョニング有効化
aws s3api put-bucket-versioning --bucket $BUCKET_NAME --versioning-configuration Status=Enabled

# サーバーサイド暗号化の設定（SSE-S3）
aws s3api put-bucket-encryption --bucket $BUCKET_NAME --server-side-encryption-configuration '{\"Rules\":[{\"ApplyServerSideEncryptionByDefault\":{\"SSEAlgorithm\":\"AES256\"},\"BucketKeyEnabled\":true}]}'

# パブリックアクセスブロック設定
aws s3api put-public-access-block --bucket $BUCKET_NAME --public-access-block-configuration "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

# 作成確認
aws s3api head-bucket --bucket $BUCKET_NAME
echo "S3バケット $BUCKET_NAME の作成が完了した"
```

### 3.2 DynamoDBテーブルの作成

```powershell
# 変数設定
$TABLE_NAME = "keirekipro-terraform-lock"
$REGION = "ap-northeast-1"

# DynamoDBテーブル作成
aws dynamodb create-table --table-name $TABLE_NAME --attribute-definitions AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST --region $REGION

# テーブル作成完了を待機
aws dynamodb wait table-exists --table-name $TABLE_NAME --region $REGION

# 作成確認
aws dynamodb describe-table --table-name $TABLE_NAME --region $REGION --query 'Table.TableStatus'
echo "DynamoDBテーブル $TABLE_NAME の作成が完了した"
```

### 3.3 作成結果の確認

```powershell
# S3バケット確認
echo "=== S3バケット ==="
aws s3api get-bucket-versioning --bucket keirekipro-terraform-state
aws s3api get-bucket-encryption --bucket keirekipro-terraform-state

# DynamoDBテーブル確認
echo "=== DynamoDBテーブル ==="
aws dynamodb describe-table --table-name keirekipro-terraform-lock --query 'Table.{Name:TableName,Status:TableStatus,KeySchema:KeySchema}'
```

## 4. GitHub Actions用OIDC設定

GitHub ActionsからAWSにアクセスするため、OIDCプロバイダーとIAMロールを作成する。
これにより、GitHub ActionsのワークフローがアクセスキーなしでセキュアにAWSリソースを操作できるようになる。

所有者は、この章の AWS の作業を、AWS のルートユーザーで行う。普段の `keirekipro` と変更用ロール `keirekipro-ops` は IAM を変えられないためである。
所有者は、ルートユーザーでマネジメントコンソールにサインインして 4.1〜4.4 と 4.6 を行い、CLI のコマンド(4.6、4.7)は、同じ画面の CloudShell で打つ。
4.5 は GitHub の画面で行う。

### 4.1 OIDCプロバイダーの作成

1. AWSコンソールで「IAM」を検索して開く
2. 左側メニューの「IDプロバイダ」をクリック

### 4.4 信頼ポリシーの差し替え

作成直後の信頼ポリシーは全ブランチからの引き受けを許可している。用途ごとに条件を絞ったものへ差し替える。

**`pull_request` を条件に含めてはいけない。** `pull_request` イベントの `sub` にはブランチ名が入らないため、この条件を付けると「リポジトリにブランチをpushできる者」が構築権限を持つジョブを動かせる。PRでのPlanは 4.6 で作る参照専用のロールが担う。

1. IAMコンソールの「ロール」から `keirekipro-github-actions-role` をクリック
2. 「信頼関係」タブ →「信頼ポリシーを編集」をクリック
3. 内容を次で置き換える。`<AWSアカウントID>` と `<GitHubユーザー名>` は実際の値にする
4. 「ポリシーを更新」をクリック

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DeployFromMainProductionEnvironment",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<AWSアカウントID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:<GitHubユーザー名>/KeirekiPro:environment:production",
          "token.actions.githubusercontent.com:ref": "refs/heads/main"
        }
      }
    },
    {
      "Sid": "TerraformPlanOnPullRequest",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<AWSアカウントID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:<GitHubユーザー名>/KeirekiPro:pull_request"
        }
      }
    },
    {
      "Sid": "TerraformApplyFromMain",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<AWSアカウントID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:<GitHubユーザー名>/KeirekiPro:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

1つ目のStatementで、本番デプロイの認証情報はmainブランチかつproduction環境を経由するジョブしか
取得できなくなる。ワークフローから `environment: production` の行を消した実行は `sub` が
`repo:<GitHubユーザー名>/KeirekiPro:ref:refs/heads/main` になり、このStatementに一致しない。

> 注意: 各Statementに `sub` を必ず入れる。GitHubのOIDCプロバイダーを信頼するロールでは、
> IAMが保存時に `sub` の存在を検査し、無い場合やワイルドカードだけの場合は保存が失敗する。

差し替え後、次を確認する。

- 「ポリシーを更新」がエラーなく完了する
- PRを1つ作り、`terraform-plan` が成功する(Statement 2の確認)

> 注意: `terraform-apply.yaml` と `frontend-rollback.yaml` をmain以外のブランチから起動すると、
> どのStatementにも一致せず `Configure AWS credentials` のステップでSTSのエラーになる。
> 意図した制限だが、エラーメッセージからは理由が読み取れない。この2つはmainから起動する。

### 4.5 production環境のブランチ制限

信頼ポリシーの environment 条件と対になる設定。**リポジトリの** Settings → Environments を開く。
`production` が一覧に無い場合は「New environment」で作成する(environmentは、それを参照する
デプロイジョブが初めて実行されるまで存在しない)。`production` を開き、次を設定する。

| 設定 | 値 |
|---|---|
| Deployment branches and tags | `Selected branches and tags` |
| 追加するルール | `main`(Ref type: Branch) |
| Required reviewers | 所有者を登録する |
| Prevent self-review | **有効にしない** |

この制限は実行のGITHUB_REFに対して照合される。mainブランチ以外から起動したデプロイは、
ジョブが開始する前に止まる。

**Required reviewers を登録すると、この環境を使うジョブは開始前に止まり、承認されるまで
進まない。** 止まるのはジョブが開始する前なので、AWSの認証情報はまだ発行されていない。
対象は `backend-deploy.yaml` / `frontend-deploy.yaml`(`release.yaml` と
`frontend-rollback.yaml` から呼ばれる)と `terraform-apply.yaml` の3本。

**Prevent self-review を有効にしてはいけない。** 実質1人運用のため、有効にすると
起動した本人が承認できず、誰も承認できなくなる。目的は職務分離ではなく
「自動で進まないようにすること」であり、無効のままで達せられる。

これは手元の禁止設定(`.claude/settings.json` の deny)と役割が違う。あちらは
Claude Code 側の仕組みで打ち方によっては素通りしうるが、**こちらは GitHub 側で
強制されるため、誰がどう起動しても承認を挟む。**

### 4.6 参照専用ロールの作成

構築権限を持たない2本を作る。**コンソールではなくCLIで作る。** 信頼ポリシーの条件を1文字でも間違えると、引き受けられる範囲が意図せず広がるため。

| ロール名 | 用途 | 引き受けの条件 | 権限 |
|---|---|---|---|
| keirekipro-github-actions-plan-role | PRでのTerraform Plan | `repo:<ORG>/<REPO>:pull_request` | `ReadOnlyAccess` + インライン(状態ロックと `keirekipro/*` の秘密の読み取り) |
| keirekipro-github-actions-scan-role | 週次のコンテナ監視 | `repo:<ORG>/<REPO>:ref:refs/heads/main` | インライン(ECSの参照とECRからの取得のみ) |

ポリシーの中身は `doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md` の 3.2 に書いてある。作成後、**書き換えができないことを必ず確認する。**

```bash
aws iam simulate-principal-policy   --policy-source-arn "arn:aws:iam::<AWSアカウントID>:role/keirekipro-github-actions-plan-role"   --action-names iam:CreateUser ec2:TerminateInstances ecs:UpdateService s3:DeleteObject   --query 'EvaluationResults[].{action:EvalActionName,decision:EvalDecision}' --output table
```

4つとも `implicitDeny` になれば正しい。1つでも `allowed` なら、付けたポリシーを見直す。

### 4.7 作成結果の確認

```bash
# OIDCプロバイダーの確認
aws iam list-open-id-connect-providers

# IAMロールの確認(3本とも)
for r in keirekipro-github-actions-role          keirekipro-github-actions-plan-role          keirekipro-github-actions-scan-role; do
  aws iam get-role --role-name "$r" --query 'Role.Arn' --output text
done

# 構築権限を持つロールが pull_request を信頼していないことの確認
aws iam get-role --role-name keirekipro-github-actions-role   --query 'Role.AssumeRolePolicyDocument.Statement[].Sid' --output table
```

出力例：
```
arn:aws:iam::123456789012:role/keirekipro-github-actions-role
arn:aws:iam::123456789012:role/keirekipro-github-actions-plan-role
arn:aws:iam::123456789012:role/keirekipro-github-actions-scan-role
```

**Sid の一覧に `TerraformPlanOnPullRequest` が出てはいけない。** 出た場合は 4.4 の信頼ポリシーを見直す。

## 9. Terraform実行後の作業

Terraform適用後に実施する作業である。

### 9.1 SNS Emailサブスクリプションの確認

Terraform適用後、CloudWatchアラート通知用のメールサブスクリプション確認が必要である。

1. `TF_VAR_alert_email_address` に登録したメールアドレスの受信トレイを確認
2. 「AWS Notification - Subscription Confirmation」という件名のメールを開く
3. メール本文内の「Confirm subscription」リンクをクリック
4. ブラウザに「Subscription confirmed!」と表示されれば完了

**注意**: 確認が完了するまでCloudWatchアラームの通知は届かない。

### 9.2 Amazon SESサンドボックス解除申請

アプリケーションがデプロイされ、`https://app.keirekipro.click` にアクセスできるようになってから実施する。
所有者は、1.3 の手順でマネジメントコンソールを変更用ロール `keirekipro-ops` に切り替えてから行う。

1. AWSコンソールで「Amazon SES」を開く（リージョン：東京）
2. 左メニューの「アカウントダッシュボード」をクリック
3. 「Amazon SESアカウントは以下のサンドボックスにあります」の警告ボックス内にある「本稼働アクセスのリクエスト」をクリック
4. 以下を入力：
   - メールタイプ：トランザクション
   - ウェブサイトのURL：`https://app.keirekipro.click`
   - ユースケースの説明：以下の内容を入力

```
【サービス概要】
エンジニア向けの職務経歴書作成Webアプリケーション（ポートフォリオプロジェクト）

【メール送信用途】
- ユーザー登録時のメールアドレス確認
- パスワードリセット
- 二要素認証コードの送信

【送信元アドレス】
info@keirekipro.click

【想定送信量】
1日あたり10通以下（ポートフォリオ用途のため利用者は限定的）

【オプトイン】
ユーザー自身がアカウント登録フォームからメールアドレスを入力して登録する形式である。マーケティングメールや一方的な送信は行わない。

【バウンス・苦情対策】
- トランザクションメールのみ送信（登録確認、パスワードリセット、二要素認証）
- ユーザーが自ら登録したアドレスにのみ送信
- バウンスが発生した場合は該当アドレスへの送信を停止

【設定済み項目】
- ドメイン検証：完了
- DKIM：有効（2048ビット）
- SPF：設定済み
- DMARC：設定済み（p=quarantine）
- カスタムMAIL FROMドメイン：設定済み
```

5. 「リクエストを送信」をクリック

### 9.3 サンドボックス解除の承認を待つ

- 最大24時間以内に返答がある
- 承認されると、サンドボックスが解除される

### 9.4 サンドボックス解除確認

1. SESコンソールの「アカウントダッシュボード」を開く
2. 「サンドボックス」の表示が消えていることを確認
