# GitHub Actions CI/CD設計書

## 1. ワークフロー設計

### 1.1 ワークフロー一覧

| ワークフロー名 | ファイル名 | トリガー | 依存関係 | 用途 |
|--------------|-----------|---------|---------|------|
| CI Workflow | ci.yaml | push（main）、PR（main） | なし | 変更領域の検証、frontend本番ビルド、本番アプリ配布の起動 |
| Frontend Deploy | frontend-deploy.yaml | CI WorkflowまたはFrontend Rollbackから呼び出し | CI検証済みartifact | `frontend-dist` のS3配布・CloudFrontキャッシュ無効化 |
| Frontend Rollback | frontend-rollback.yaml | 手動 | 成功済みCI Workflow run | 保存済み`frontend-dist`を本番へ再配布 |
| Backend Deploy | backend-deploy.yaml | CI Workflowから呼び出し | deploy gate、必要時はfrontend検証 | DockerイメージのECR push・ECSデプロイ |
| Terraform | terraform-plan.yaml | PR（main） | なし | 静的検査（fmt・validate・tflint・checkov）とTerraformプラン実行・PRへのコメント。terraform/**、docker/terraform/**、自身の変更が無いPRでは各ジョブをスキップする |
| Terraform Apply | terraform-apply.yaml | push（main、terraform/**変更時）、手動 | なし | Terraformアプライ実行 |

### 1.2 ワークフロー実行フロー

#### 1.2.1 Pull Request作成時
```
PRを作成
    │
    ├─── frontend/**変更あり ──→ CI Workflow（format・lint・test・coverage・production build）
    │
    ├─── backend/**変更あり ───→ CI Workflow（バックエンドのテスト・リント）
    │
    └─── terraform/**変更あり ─→ Terraform Plan（plan結果をPRにコメント）

    ↓
レビュー・承認
    ↓
mainにマージ
```

#### 1.2.2 アプリケーションデプロイ時（mainへのマージ）

backend/、frontend/の両方に変更がある状態。
```
mainにマージ
    │
    ▼
┌────────────────────────────────────────────────────────────────────┐
│ Step 1: ci.yaml                                                     │
│ - frontend: format・lint・test・coverage・production build           │
│ - backend: ./gradlew check                                          │
│ - frontend build成功時: frontend-dist artifactを90日保持             │
└────────────────────────────────────────────────────────────────────┘
    │
    │ 変更対象の検証がすべて成功した場合のみ
    ▼
┌─────────────────────────────────┐
│ Step 2: backend-deploy.yaml     │
│ - Dockerイメージをビルド         │
│ - ECRにプッシュ                  │
│ - ECSへデプロイして安定化を待機   │
└─────────────────────────────────┘
    │
    │ backendデプロイ成功後
    ▼
┌─────────────────────────────────┐
│ Step 3: frontend-deploy.yaml    │
│ - frontend-distをダウンロード    │
│ - S3へ順次アップロード           │
│ - CloudFrontキャッシュ無効化     │
└─────────────────────────────────┘
```

#### 1.2.3 通常運用時（2回目以降、mainへのマージ）

変更されたアプリケーション領域に応じて必要な配布のみ実行する。
```
mainにマージ
    │
    ├─── backend/**のみ変更 ───→ backend-deploy.yamlのみ実行
    │
    └─── frontend/**のみ変更 ──→ frontend-deploy.yamlのみ実行
```

frontend/**とbackend/**の両方に変更がある場合、両方のCIが成功した後、backend、frontendの順にデプロイする。backendのCIまたはデプロイが失敗した場合はfrontendを公開しない。

terraform/**の変更は`terraform-apply.yaml`が独立して処理する。Terraform applyとアプリケーション配布の間に自動的な依存関係は設けていないため、新規環境作成やアプリ配布先を変更するインフラ更新では、必要なインフラ反映後にアプリケーション変更を反映する。

#### 1.2.4 フロントエンドロールバック時

```
Frontend Rollbackを手動実行（成功済みCI Workflow run_idを入力）
    │
    ▼
CI Workflowがmainへのpushで成功済みかつfrontend-distが利用可能であることを確認
    │
    ▼
保存済みfrontend-distをS3へ再配布し、CloudFrontキャッシュを無効化
```

### 1.4 OIDC連携

GitHub ActionsからAWSへの認証はOIDC連携を使用する。IAMロールは用途ごとに3本に分かれている。`keirekipro-github-actions-role`が本番デプロイとTerraform Apply、`keirekipro-github-actions-plan-role`がPRでのTerraform Plan、`keirekipro-github-actions-scan-role`が週次のコンテナイメージ監視を担う。構築権限を持つのは1本目だけで、mainブランチからしか引き受けられない。PRから引き受けられるのは参照専用の2本目のみ。設定内容と分割の理由は`doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md`の3.1と3.5を参照する。

### 1.5 デプロイ戦略

| 対象 | 戦略 |
|------|------|
| フロントエンド | CIで一度だけbuildしたartifactをS3へ配布 + CloudFrontキャッシュ無効化。旧assetは保持し、成功済みartifactの再配布でrollback |
| バックエンド | ECSローリングアップデート（最小ヘルス率100%、最大率200%、回路ブレーカーによる自動rollback有効） |

frontendとbackendの同時変更では、APIの前後互換性を維持し、backendを先に公開する。frontendの配布が失敗しても、正常に稼働しているbackendを連動して自動rollbackしない。

### 1.6 Terraform Plan PRコメント

terraform-plan.yamlでPRにplan結果をコメントする際は、hashicorp/setup-terraform + github-scriptを使用する。

| ツール/Action | 説明 |
|--------------|------|
| hashicorp/setup-terraform | Terraform公式Action |
| actions/github-script | `terraform show`の出力をPRにコメント |

### 1.7 承認プロセス

terraform-apply.yaml実行前の承認プロセスは設定しない（ポートフォリオ用途のため）。frontendの通常デプロイとrollbackはGitHubの`production` environmentを使用して履歴を残すが、承認は必須化しない。

本番運用で承認プロセスが必要な場合は、GitHubの「Environment protection rules」を使用して、特定ユーザーの承認を必須にできる。

### 1.8 frontend-deploy.yaml 詳細設定

| 項目 | 設定値 |
|------|--------|
| ビルド実行箇所 | `ci.yaml`のfrontend検証job（`pnpm run build`） |
| 配布artifact | `frontend-dist`（main pushの成功候補を90日保持） |
| 配布方式 | immutable assetを先にS3へ配置し、短期キャッシュ対象JSON、`index.html`の順に公開 |
| 旧asset | rollbackと既存クライアント参照を保護するため通常配布では削除しない |
| Rollback | `frontend-rollback.yaml`に成功済みCI Workflowの`source_run_id`を指定してartifactを再配布 |

### 1.9 backend-deploy.yaml 詳細設定

| 項目 | 設定値 |
|------|--------|
| Dockerイメージのタグ付け | コミットハッシュ（`${{ github.sha }}`）を使用 |
| ECSデプロイ完了の待機処理 | あり（`aws ecs wait services-stable`を使用） |
| ロールバック | ECS deployment circuit breakerによるbackendデプロイ失敗時の自動rollback |

## 2. 自動チェックと受容した残余リスク

人間が定期的に点検する手順は [監査手順](../../開発フロー/監査手順.md) にある。

### 2.1 自動チェックの一覧

監査で見るべき自動チェックの全体像。どれかが機能しなくなっていないかをカナリア結果・すり抜け実績から確認する。

| 種類 | 実体 | 何を防ぐか |
|---|---|---|
| テストとカバレッジ基準 | Vitest / JUnit(Testcontainers)、カバレッジ基準値(vite.config.ts / quality.gradle) | ロジックの破壊、テストの薄い変更 |
| 静的解析 | ESLint(境界ルールとsonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | アーキテクチャ境界の違反、アサーションの無いテスト、型の逸脱 |
| 検査回避の検知 | escape-hatchチェック(guardrails.yaml) | テストのskip化、@Disabledや@ts-ignoreの追加、インラインでのlint無効化、アサーションの削除、品質チェック配線の改変 |
| 差分サイズの検査 | size-check(guardrails.yaml) | 仕様書の裏付けなしにコード差分200行を超える変更が入ること(注1) |
| 依存の脆弱性検査 | dependency-review(dependency-review.yaml) | そのPRで新しく増えた、moderate以上の既知の脆弱性。開発依存も対象で、既存の依存では赤にならない(注2) |
| 依存グラフの空洞化の検知 | check-dependency-snapshot(dependency-review.yaml / dependency-graph.yaml) | 依存解決が空のまま送信されること。空のスナップショットが送られると、脆弱性とクールダウンの検査が「追加0件」と判定して緑になり、backendのDependabotアラートも出なくなる。捉えるのは「空」までで、部分的に欠けたグラフと、送信より後の区間は月次のカナリア(vulnerable-dep)が受け持つ |
| 公開直後の版の遮断(backend) | dependency-cooldown(dependency-review.yaml) | 公開から72時間を経過していないライブラリ。そのPRで新しく追加されたものを、推移的依存とGradleプラグインまで含めて見る(注3) |
| Gradle本体の検証 | gradle-wrapper(guardrails.yaml) | ビルドが取得するGradle本体が公式のものでなくなること。配布元ホストが `services.gradle.org` であること、チェックサムと `gradle-wrapper.jar` が公式リリースと一致することを見る。wrapper関連の変更が無いPRでは外部への問い合わせを行わず通す |
| 入手先と防御設定の検査 | dependency-gate | ライブラリの入手先(`.npmrc`)、インストール時に実行されるコード(`.pnpmfile.*`)、差し替えと待機期間の設定(`pnpm-workspace.yaml`)、backendのビルドスクリプト(`*.gradle` `*.gradle.kts`)が承認なしに変更されること。中身は解析せず変更の有無で判定する。バージョン宣言そのものは対象外で、上の3つの検査が代わりを務める |
| コンテナイメージのビルド確認 | docker-smoke(ci.yaml) | ベースイメージの更新でDockerfileがビルドできなくなること。Dockerfileの変更だけではテスト系のジョブが動かないため、変更されたDockerfileを実際にビルドして確認する。検証はamd64で行い、arm64に固有の破綻はリリース時のビルドで検知する |
| コンテナイメージの脆弱性検査 | container-scan(container-scan.yaml) | 本番イメージのOS層と同梱 fat jar に、修正版のある CRITICAL/HIGH の脆弱性を持ち込む変更がマージされること。既存の依存も対象で、`dependency-review`(そのPRで新しく増えた分だけを見る)とは補完の関係にある |
| 週次の自動監査 | audit-weekly(audit-weekly.yaml) | 定期スキャンの停止(成功から8日)、棚卸しの停止(成功から35日)、Dependabot PRの滞留(failure/cancelled/timed_out/action_required)、必須チェックがスキップのままマージされたPR、期待一覧(`.github/audit/required-checks.json`)とrulesetのずれ、PRの検査と定期検査の `TRIVY_VERSION` の食い違い。逸脱は `週次監査: 逸脱あり`、監査の故障は `週次監査: 判定不能` のIssueで所有者に知らせる(ラベル `audit`)。逸脱ありでも実行は緑で終わる。赤になるのは、判定不能のときと、Issueへの反映が失敗したとき |
| 監査自体の死活 | ci.yaml の audit-liveness ステップ | 週次監査が止まったこと(完了した実行が10日無ければPRのCIが赤。結果が逸脱ありでも判定不能でも完了として数える)。番人の連鎖を作らず、PRが無い期間は問わない |
| カナリアの自動照合 | canary-verify(canary-verify.yaml) | 毎月のカナリア6件が期待チェックで赤になっていること(3値判定。判定側の故障と実行漏れを区別)。逸脱は `カナリア照合: 逸脱あり`、照合の故障は `カナリア照合: 判定不能` のIssueで知らせる。逸脱ありでも実行は緑で終わる。赤になるのは、判定不能のときと、Issueへの反映が失敗したとき。カナリアPRのcloseは行わない |
| 版とサポート期限の棚卸し | audit-inventory(audit-inventory.yaml、毎月2日) | Dependabot が扱わない版(メジャー版の更新と、Dockerfile の `FROM` 以外の行・ワークフロー・terraform に書いた版)の遅れやサポート期限切れが、誰にも気づかれないまま残ること。判定はせず、使っている版・最新のリリース・サポート期限の表を `棚卸し台帳: 版とサポート期限` のIssue(ラベル `audit`)に所有者へのメンションつきでコメントする。外部の取得元から取れなかった欄があっても実行は緑で終わる。赤になるのは、スクリプトの自己テストの失敗と、台帳に書けなかったとき。止まったことは週次監査が知らせる |
| 稼働中イメージの脆弱性監視 | container-scan-scheduled.yaml(週次) | マージ後に公表された脆弱性が、稼働中のイメージについて誰にも気づかれないまま残ること |
| IaCの静的検査 | terraform-static(terraform-plan.yaml) | フォーマット崩れ・構文と参照の誤り・tflintの指摘・checkovの新規指摘(注4) |
| アクション参照の固定 | check-action-pinning(guardrails.yaml) | `uses: owner/repo@<40桁のSHA> # vX.Y.Z` 以外の形式のアクション参照。タグは上流で差し替え可能で、こちらを変更しなくても実行内容が変わり得るため |
| 公開直後の版の遮断(frontend) | pnpm の minimumReleaseAge(72時間) | 公開から72時間以内のパッケージのインストール。悪意ある版は数時間で削除されるため、寝かせることで大半を避ける。ただし公開日時のメタデータが無いパッケージは素通りする(`minimumReleaseAgeIgnoreMissingTime` の既定が true のため) |
| 公開直後の版の遮断(tflint) | check-release-age.sh(dependabot-auto-merge.yaml の auto-merge と recheck) | 公開から72時間以内の tflint が自動でマージされること。tflint のイメージの置き場(ghcr.io)には Dependabot の既定の待ち期間が効かないため、GitHub のリリースの公開日時(`published_at`)から72時間経つまで、更新PRの自動マージを予約しない。PRのイベントと毎日1回(10:37 JST)の見直しで判定する。公開日時を取れないときと、版が同じで中身(digest)だけが変わったときは予約せず、PRにコメントして所有者に知らせる。tflint 以外の Dependabot のPRは今までどおり予約する |
| DBマイグレーションの承認 | CODEOWNERS(migrationディレクトリ) | スキーマ変更が人間の確認なしにマージされること |
| チェック設定の保護 | CODEOWNERS + settings.jsonの編集拒否 | 品質チェックの設定がAIの判断で変更されること |
| シークレットスキャン | gitleaks | 認証情報などの混入 |
| 別AIによるレビュー | codex-review(判定はジョブの成否で行い、コメントの偽装は効かない) | バグ、セキュリティ問題、仕様との不一致、チェックを形だけ通す変更 |
| リリースの分離 | release.yaml(手動実行) | マージだけで本番に反映されること |
| 健全性の確認 | canary.yaml(月次) | チェックの仕組み自体が気づかないうちに壊れること |

- 注1: specの実在・必須4ファイル・プレースホルダ残存・spec.jsonの3段階承認フラグを検証する。承認フラグはAIの自己申告であり、人間が承認した証明にはならない(受容済みリスク: #177)
- 注2: baseとheadの依存グラフを比較する。backendの基準は、mainへのpushで dependency-graph.yaml が送信したスナップショット。required status check には generate / submit / review の3つすべてを指定すること。1つでも外すと、そのジョブが失敗したときに後続がスキップ(Success扱い)になり、検査されないままマージされる。フォークPRでは送信ジョブがスキップされ、Gradleの差分は未検査になる(受容済み)
- 注3: Dependabotが作成したPRは対象外(自動化側の待機期間が効いており、脆弱性対応の更新を遅らせないため)。フォークPRも対象外(スナップショットが送られず追加を特定できない)。公開時刻を取得できない場合、スナップショットが揃っていない場合、比較APIが失敗した場合はいずれも赤になる
- 注4: checkovの既存67件は `terraform/.checkov.baseline` で凍結してあり、baselineに無い指摘が出れば赤になる。checkovは `docker/terraform/requirements.txt` で、tflintは `docker/terraform/Dockerfile` の `FROM` で版を固定しており、更新は Dependabot のPR(checkov は pip、tflint は docker)で届く。新しい版で指摘が増えるとそのPRの terraform-static が赤になり、自動ではマージされない。baselineを作り直すときは `.checkov.yaml` の `baseline:` 行を一時的に外してから実行する(有効なまま `--create-baseline` するとbaselineが空になる)

### 2.2 受容した残余リスク

機械の検査で守れないと分かったうえで受け入れているもの。半期に一度、増えていないかを見る。増えている場合は、検査の追加で埋められないかを検討する。

#### 1. Gradle本体の検証は信頼の根が1つしかない

gradle-wrapper は配布元ホストを `services.gradle.org` に固定し、同じホストが公表するチェックサムと照合する。配布元が侵害されると配布物と公表値の両方が同時に偽装されるため、実質的に効いているのはホストの固定で、チェックサムの照合は手作業による書き換えとの不整合検知と位置づけている。あわせて、Gradle自身のチェックサム検証はダウンロード時にしか行われず、キャッシュ済みの環境では誤った値でも素通りする。ローカルで確認するときはキャッシュを削除してから実行する。

#### 2. プロジェクト自身の `package.json` に任意のコマンドを書ける

pnpm 10 以降、依存パッケージのインストール時スクリプトは既定で実行されないが、遮断されるのは依存パッケージのものだけで、`frontend/package.json` の `scripts` に書いたコマンドは実行される。`package.json` を承認の対象から外したため、この経路は機械の検査を通らない。エージェントが書いたコードがCIと開発環境で実行されることは既に受け入れている範囲であり(`src` のコードもテストも同じ)、新しい信頼水準を要求するものではないと判断した。

#### 3. フォークからのPRではbackendの依存が検査されない

フォークPRでは書き込み権限が得られず、依存グラフのスナップショットを送信できない。このため dependency-cooldown は対象外になり、dependency-review もfrontendしか見られない。このリポジトリのPRはすべて所有者のbotが同一リポジトリのブランチから作る運用であり、フォークPRは初回コントリビュータのワークフロー実行承認と人間のレビューを経る。

#### 4. PRで追加されたワークフローは、マージ前に実行される

`pull_request` で発火するワークフローは、**PRを出した時点で動く。** CODEOWNERS と `check-escape-hatches.sh` の承認ゲートはマージを止めるものであって、実行は止めない。したがって、PRに置かれたワークフローはリポジトリのシークレットに触れられる。

**機構では塞げない。** GitHubに、同一リポジトリのブランチから出たPRのワークフロー実行を承認制にする設定は無い(フォークPRにはある)。実行後に検知する検査を足しても、実行そのものは防げない。

受容の根拠は、ブランチをpushできるのが所有者とbotの2アカウントに限られること。**bot のアクセストークンは2要素認証の保護を受けない**ため、ここが実質的な信頼の根になる。

なお、AWSへの経路は 2026-08-21 に分離済みで、PRから引き受けられるのは参照専用のロールのみ(`doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md` の 3.5)。**残っているのはリポジトリのシークレットへの露出である。**

#### 5. `.github/` へのエージェントの書き込みは、ツールの禁止だけでは塞げない

`.claude/settings.json` は `Write` / `Edit` ツールによる `.github/**` の変更を拒否するが、**シェル経由の書き込み(`cp` / `sed -i` / リダイレクト / `python -c` など)は通る。** 書き方が無数にあり、コマンド文字列の照合で網羅できない。

**この禁止はうっかり編集の防止であって、安全対策ではない。** 本体はマージ前の所有者承認で、そちらは機械で強制されている。

**現在エージェントがこの経路で直接書いているのは、ゲート整備中の時限的な特例である**(#216)。ゲートそのものを作っている期間は、変更のほとんどが `.github/` 配下に集中し、1件ごとに人手で配置する手順が実務にならないため。**整備が一段落した時点で、本来の手順(エージェントが内容を用意し、人間が配置する)に戻す。** 判断と復帰の条件は #216 で追う。

塞ぐ機構を足すかどうかは、復帰時にあらためて決める。この受容は特例の期間に限る。

#### 6. 監査の通知そのものが失敗すると、通知は出ない

監査の結果をIssueに書き込む処理が失敗した場合(通知の処理の自己テストの失敗、Issueの作成・追記・クローズの失敗)は、
Issueは作られず、実行が赤で終わるだけになる。定期実行の失敗通知はcronを最後に書き換えた利用者(監査のワークフローではbot)にしか届かないため、この赤は所有者には届かない。
通知の失敗を別の仕組みで見張ると、その仕組みの失敗もまた見張る必要が出て切りがないため受け入れた。

あわせて、この赤の実行も週次監査の「前回の実行」として数えられ、スキップのままマージされたPRの確認期間の区切りになる。
このため、その実行が受け持つはずだった期間が確認されないまま残る。
気づいたときは、**その実行を Re-run で再実行すれば**、確認されない期間は埋まる。

#### 7. PRのCIの死活確認は、判定が行われたかどうかまでは見ない

PRのCIが確かめるのは、週次監査の実行が10日以内に完了しているかだけ。
手動でキャンセルされた実行や、通知の処理の自己テストで落ちた実行も「完了」に数える。
監査が実際に判定できたかどうかは、`週次監査: 判定不能` のIssueで見る。

#### 8. 担当者の割り当てとメンションの両方が届かないと、残る経路はWatchだけになる

監査のIssueは、所有者を担当者に割り当て、本文で所有者にメンションする。
どちらも届かなかった場合に所有者が気づく経路は、所有者がこのリポジトリをWatchしていることだけになる。
所有者がWatchを有効にしておくことは、[監査手順](../../開発フロー/監査手順.md)の「監査の通知Issueを受けたとき」に書いてある。

#### 9. 1日1回の見直しが止まると、保留した tflint の更新PRが開いたまま残る

tflint の更新PRは、公開から72時間経ったあとの見直し(`dependabot-auto-merge.yaml` の定期実行、毎日10:37 JST)で自動マージが予約される。
この見直しが止まると、保留したPRは予約されないまま開いて残る。PRのチェックは緑のため、週次監査のDependabot PRの滞留の検知には掛からない。
見張りを増やすと、その見張りの停止もまた見張る必要が出るため受け入れた。Dependabot が同じPRを更新すれば、PRのイベントで判定し直される。
予約されないまま72時間を大きく過ぎているPRに気づいたときの確かめ方は、[監査手順](../../開発フロー/監査手順.md)の「PRが止まったとき」に書いてある。

#### 10. tflint の72時間は、GitHub のリリースの公開日時で数える

Dependabot の既定の待ち期間は、置き場が付けた公開日時がある場合にしか効かない。今のところ使えるのは Docker Hub だけで、ghcr.io のイメージでは公開日時を取れず、待たずにPRが作られる([dependabot-core の docker/README.md](https://github.com/dependabot/dependabot-core/blob/main/docker/README.md) の Cooldown publication dates)。
そこで、tflint の72時間は GitHub のリリースの `published_at` で数える。GitHub が付ける値で、公開した側が後から書き換えられない。イメージの中の作成日時は公開した側が自由に付けられるため使わない。
数えているのはリリースの公開からの時間で、ghcr.io にイメージが置かれてからの時間ではない。リリースの無い版は公開日時を取れないとして予約せず、同じ版の名前のまま中身だけが差し替えられた更新も予約しない。どちらも所有者に知らせる。
配布元の GitHub のアカウントそのものが乗っ取られた場合は、リリースを作ってから72時間待たせる以上のことはできない。frontend と backend の待ち期間と同じ考え方として受け入れた。

#### 11. tflint の判定は、`BOT_GITHUB_TOKEN` が利用者のトークンであることに頼っている

公開日時を取れないときや中身だけの更新のときの知らせは、トークンの利用者(`gh api user`)を確かめ、その利用者が書いた目印のコメントで重複を避けている。毎日の見直しも、同じ確かめ方で中身だけの更新のPRを見分けている。
`BOT_GITHUB_TOKEN` を GitHub App のトークンに替えると利用者を確かめられなくなり、知らせのコメントを付けないまま判定できないとして赤で終わる。毎日の見直しは最初の確認で赤になって止まり、見直しでは1件も予約されなくなる(PRのイベントでの判定は、知らせが要らない場合は今までどおり動く)。
予約しない側に倒れるため、誤ってマージされることは無い。トークンの種類を替えるときは、この確かめ方も合わせて直す。
