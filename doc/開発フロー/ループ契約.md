# ループ契約(Loop Contract)

各ループの7要素(Trigger / Scope / Permission / Verification gate / Budget / Stop・Escalation / Reporting)を定義する。
ループを新設・変更するときは必ずこの表を更新する。

## 1. ターンベースループ(通常の対話作業)

| 要素 | 定義 |
|---|---|
| Trigger | 人間のプロンプト(Issue対応・小修正の依頼) |
| Scope | 依頼された変更範囲のみ。featureブランチ上 |
| Permission | 品質ゲート・git(feature)・gh(PR系)は自動。**DBスキーマ変更・依存パッケージ追加・外部送信・ゲート設定変更 = 人間承認必須** |
| Verification gate | verify Skill(format/lint/test/coverage/check)の全PASS + Stop hookの未実行検知 |
| Budget | 1セッション。同一の失敗3回で停止 |
| Stop/Escalation | タスク完了 or 情報不足で停止。範囲外の問題は報告のみ(勝手に直さない) |
| Reporting | 完了報告(Changed files / Commands PASS・FAIL / Notes / Commit message案) |

## 2. ゴールベースループ(/goal)

| 要素 | 定義 |
|---|---|
| Trigger | 人間または /kiro-impl が `/goal` を設定 |
| Scope | ゴール定義に書かれた対象のみ(1画面・1テストファイル・1タスク程度に絞る) |
| Permission | ターンベースと同じ。ループ中の commit/push は不可(出荷は /ship でのみ) |
| Verification gate | ゴール条件そのもの(定量・機械判定可能な条件のみ)+ ハック対策条項 |
| Budget | ゴール定義の最大ターン数(標準6〜15)。`doc/開発フロー/ゴールテンプレート.md` に準拠 |
| Stop/Escalation | 条件達成 or ターン上限で停止。上限到達時は原因を報告(上限を勝手に増やさない) |
| Reporting | 達成/未達成・ターン数・`/usage` のコスト概要 |

## 3. 時間ベースループ(/loop)

| 要素 | 定義 |
|---|---|
| Trigger | `/loop 30m`(作業中の定期メンテ = `.claude/loop.md`)/ `/loop 5m`(PR監視) |
| Scope | 未コミット変更のverify・図の乖離指摘・開いているPRのチェック監視のみ |
| Permission | 読み取り+verify+修正。**commit/pushはループから行わない** |
| Verification gate | verify Skillの全PASS / PRの必須チェック |
| Budget | ローカルセッション中のみ(セッション終了で消滅)。同一失敗3回で停止 |
| Stop/Escalation | 人間のEsc・`/loop` 停止。修正不能な失敗は報告して次周期をスキップ |
| Reporting | 各周期1行(正常時)/ 失敗時は要約と対応内容 |

## 4. プロアクティブループ(CI)

| 要素 | 定義 |
|---|---|
| Trigger | @claudeメンション(Issue/PR)/ 週次schedule(依存更新)/ 月次schedule(カナリア) |
| Scope | メンションされたIssue/PRの範囲 / 依存バージョン更新のみ(追加は不可) |
| Permission | CI内のbotアイデンティティ。mainへの直接push不可(ブランチ保護)。マージはゲート経由のみ |
| Verification gate | 全required checks(CI + guardrails + dependency-gate + codex-review) |
| Budget | GitHub Actionsのジョブタイムアウト。週次/月次の頻度固定 |
| Stop/Escalation | ゲート赤で自動停止(マージされない)。5往復超のレビュー対立はエスカレーション(下記) |
| Reporting | PRコメント・ジョブサマリ |

## エスカレーション手順(review-loop 5往復超過時)

人間が見る対象は次の**2つのみ**(コードは読まない):

1. **spec / Issue**(何を作るはずだったか)
2. **review-loopの往復ログ**(PRコメントの `## review-loop 往復<N>` 履歴。何が対立しているか)

取れる判断は次の**3択のみ**:

1. **spec差し戻し** — 要求・設計そのものを見直す(`/kiro-spec-requirements` からやり直し)
2. **タスク分割してIssue再起票** — 対立点を切り離して小さく作り直す
3. **PR破棄** — クローズして仕切り直す

## コスト監視

- `/usage` でスキル・サブエージェント・MCP別のトークン内訳を確認する(週次監査の項目)
- トークン消費が増え続ける場合は「ループ設計を小さく戻す」シグナルとして扱う
- 暴走時の停止手段: Esc(保留中の起動キャンセル)/ `/loop`(時間ループ停止)/ `/goal clear`(ゴール解除)
