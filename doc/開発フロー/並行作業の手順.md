# 並行作業の手順

所有者が、複数のセッションで別々のIssueを同時に進めるときの手順書。
所有者がすることは、最初に一度だけ行う準備と、セッションごとに worktree を選んでセッションを開き、`/start #N` を打つことである。
セッションごとの品質チェックと画面確認の準備は、Claude が所有者に頼まずに済ませる。

> 前提: [参加者セットアップ手順](参加者セットアップ手順.md) が完了していること。

## 1. 最初に一度だけ行う準備

作業PCごとに一度だけ行う。PCを再セットアップしたときも、最初からやり直す。

### 1-1. curl があることの確認

画面確認のスクリプト `ui.sh` は、backend の開発サーバが起動したかを `curl` で確かめる。
Windows では、`curl` は Git for Windows に同梱されているので、所有者が別に入れる必要は無い。macOS と Linux では標準で入っている。

所有者は、Git Bash(macOS と Linux ではターミナル)で次を打ち、版の番号が返ることを確かめる。
PowerShell では `curl` が別のコマンドを指すことがあるので、Git Bash で打つ。

```bash
curl --version
```

### 1-2. 共有のサービスの起動

どのセッションも、画面確認では `db` `redis` `localstack` `dind` を、backend の品質チェックでは `dind` を、本体フォルダの開発環境から共有して使う。
所有者は、本体フォルダ(worktree ではないリポジトリの最上位)で次を打ち、これらのサービスを起こしておく。

```bash
docker compose up -d
```

確かめる。各サービスの状態が `Up` になればよい:

```bash
docker compose ps
```

> 補足: PCの再起動などで共有のサービスが止まっていても、品質チェックと画面確認のスクリプトが、使うサービスを本体フォルダで起こし直す。
> 所有者がセッションのたびに起こす必要は無い。

## 2. 同時に走らせる数の設定

品質チェックと画面確認を同時に走らせられるセッションの数は、作業PCごとの設定 `keirekipro.parallelSlots` で決まる。
設定が無いときは1である。数を超えたセッションの品質チェックと画面確認は、前のものが終わるまで待つ。

### 2-1. 数の目安

同時に走らせる数の目安は、次の式で求める。

- 目安 = (Docker に割り当てたメモリ − 共有のサービスの分 約1GB)÷ backend の品質チェック1回分 約4.2GB
- 小数点以下は切り捨て、最小1とする

backend の品質チェック(`./gradlew check`)は、1回で約4.2GBのメモリを使う。目安より多くすると、品質チェックがメモリ不足で落ちることがある。

Docker に割り当てたメモリは、所有者が次を打つとバイトの単位で返る。1073741824 で割るとGBになる。

```bash
docker info --format '{{.MemTotal}}'
```

たとえば、割り当てが約7.6GBなら (7.6 − 1)÷ 4.2 = 1.57… なので目安は1、約16GBなら (16 − 1)÷ 4.2 = 3.57… なので目安は3である。

### 2-2. 数の変え方

所有者は、次のコマンドで数を変える。`<数>` は1以上の整数にする。本体フォルダで打っても worktree で打っても、同じ設定が変わる。
設定は git の管理外なので、コミットされず、ほかの作業PCには及ばない。ほかに書き換えるファイルは無い。

```bash
git config keirekipro.parallelSlots <数>
```

いまの値を確かめる。何も返らなければ、設定が無く数は1である:

```bash
git config --get keirekipro.parallelSlots
```

設定を消して1に戻す:

```bash
git config --unset keirekipro.parallelSlots
```

> 注意: 1以上の整数でない値(`0` や `abc` など)を設定すると、`/start` と品質チェックと画面確認は動かずに「keirekipro.parallelSlots の値 … は1以上の整数ではない」と出して止まる。
> そのときは、上のコマンドで正しい値に直す。

### 2-3. 数を超えたとき

設定の数のセッションが品質チェックか画面確認を走らせているときに、別のセッションで品質チェックか画面確認を始めようとすると、Claude は、そのセッションで順番待ちになったことと、どのIssueのチェックを待っているかを所有者に伝え、空くのを待つ。
30分待っても空かなければ、Claude は待ちをやめ、品質チェックを合格として扱わずに所有者に報告する。

`/start` を打ったときに、ほかに作業中のセッションの数がすでに設定の数に達していれば、Claude は着手を続けたうえで、そのことと、品質チェックと画面確認が順番待ちになることがあることを所有者に伝える。

## 3. セッションの開き方

並行して進めるセッションは、所有者が worktree を選んで開く。worktree を選ぶと、そのセッション専用の作業フォルダが本体フォルダとは別にできる。

- デスクトップアプリでは、所有者がセッションを始めるときに、ブランチ名の横の **worktree** の選択肢を選ぶ
- CLI では、所有者が本体フォルダで次を打つ。`<名前>` は作業フォルダの名前で、セッションごとに別の名前にする

```bash
claude --worktree <名前>
```

worktree の作業フォルダは、既定では本体フォルダの `.claude/worktrees/<名前>/` にできる(デスクトップアプリでは、設定の「Worktree location」で場所を変えられる)。
Claude Code が worktree を作るときに、本体フォルダの `.claude/settings.local.json`(ボットの資格情報の場所)と `docker/localstack/.env.local` が、worktree に自動で写される。
所有者がセッションごとにファイルを写したり、検査の環境を起動したり、設定を書き換えたりする必要は無い。

セッションを開いたら、所有者は `/start #N` を打つ。あとは1つのセッションで進めるときと同じである。

`/start #N` で Claude がIssueを分けたときは、Claude は分けた部分のIssueを一覧で示し、その会話ではどの部分にも着手しない。
所有者は、部分ごとに worktree を選んでセッションを開き、そのセッションで `/start #<部分の番号>` を打つ。部分のうち1つは、元の会話で打ってもよい。
実装の途中で Claude がIssueを分けたときは、Claude は最初の部分をその会話で続けるので、所有者は残りの部分ごとに同じように打つ。

> 注意: worktree を選ばずに本体フォルダで開くセッションは、同時に1つまでにする。
> 同じ作業フォルダで別のセッションが作業中のときに `/start` を打つと、Claude は止まり、前のセッションをやめたかを所有者に尋ねる。
> まだ進めているなら、所有者は worktree を選んでセッションを開き直す。

> 注意: `git worktree add` など、Claude Code 以外の方法で作った worktree には、上のファイルが写されない。
> worktree は、デスクトップアプリの選択肢か `claude --worktree` で作る。

> 補足: 同じIssueの作りかけ(spec、ブランチ、コミットしていない変更)がほかの作業フォルダに残っているときに `/start #N` を打つと、Claude は止まり、前のセッションをやめたか、続きから進めるかを所有者に尋ねる。
> 所有者が答えると、Claude は作りかけをいまのセッションの作業フォルダに引き継ぐ。

## 4. 残った枠やコンテナの片付け

セッションを閉じたり worktree を消したりすると、品質チェックと画面確認の順番の枠、画面確認のコンテナ、作業フォルダごとのボリュームと DB が残ることがある。
Claude は、`/start` のたびに、これらを自動で片付ける。所有者が手で片付けたいときは、先に Docker と共有のサービスを起こしておき(「1-2. 共有のサービスの起動」)、Git Bash(macOS と Linux ではターミナル)で、本体フォルダか worktree の最上位から次を打つ。

```bash
bash .claude/scripts/parallel/session.sh prune
```

このコマンドは、次のものを片付ける。記録とボリュームと DB を片付けたときと、消えた作業フォルダの枠を取り戻したときは、`[parallel] 片付け:` で始まる行が出る。それ以外の、持ち主が終わった枠を取り戻したときは、何も出ない。

- 作業フォルダが無くなったセッションとIssueの記録。Issueのブランチが残っていれば、Issueの記録は消さずに残す(次に `/start` を打ったときに、Claude がそのブランチの続きから進めるかを尋ねるため)
- 持ち主のセッションが終わった画面確認の枠とコンテナと、始めてから2分より長くたっていて動いているコンテナの無い品質チェックの枠
- 無くなった作業フォルダのボリューム(`kp-nm-<鍵>` `kp-gradle-project-<鍵>`)と DB(`kp_<鍵>`)

PCを起動して Docker Desktop をまだ起動していないとき、所有者が Docker Desktop を終了したとき、Docker Desktop が落ちたときに片付けが動くと、片付けはボリュームと DB を消さずに後回しにする。
本体フォルダの開発環境の DB が動いていないとき(本体フォルダで `docker compose down` や `docker compose stop` を打ったあと、まだ `docker compose up -d` を打っていないときや、Docker Desktop を起動した直後で DB がまだ立ち上がっていないときなど)は、DB を消さずに後回しにする。

後回しにしたときは、片付けは無くなった作業フォルダの記録を消さずに残す。
Docker Desktop と DB が動いているときに所有者が次に `/start` を打つか、`session.sh prune` を打つと、片付けは残した記録をもとに、後回しにしたボリュームと DB をもう一度消しにいく。所有者が手で消す必要は無い。

このときは、`[parallel] 消せなかった名前:` で始まる文が出る。`/start` のときの片付けでこの文が出たら、Claude はその文を所有者に伝えてから、着手を続ける。

ボリュームと DB は、記録に残っている作業フォルダの分だけを片付ける。`/start` を打たなかった worktree の分など、記録の無い作業フォルダのボリュームと DB は、片付けの対象にならずに残る。
所有者が手で消すのは、この記録の無い作業フォルダの分だけである。所有者は、Docker と共有のサービスを起こしてから(「1-2. 共有のサービスの起動」)、本体フォルダで次を打つ。

ボリュームを消す。`<名前>` は消すボリュームの名前(`kp-nm-<鍵>` か `kp-gradle-project-<鍵>`)にし、名前ごとに打つ:

```bash
docker volume rm <名前>
```

DB を消す。`<名前>` は消す DB の名前(`kp_<鍵>`)にし、名前ごとに打つ:

```bash
docker compose -p keirekipro exec -T db psql -U postgres -c "DROP DATABASE <名前>"
```

worktree そのものの消え方は、セッションの開き方で違う。

- CLI(`claude --worktree`)では、所有者がセッションを終えるときに、worktree に変更や新しいコミットが残っていれば、Claude Code が残すか消すかを尋ねる。何も残っていなければ、尋ねずに worktree とそのブランチを消すことがある
- デスクトップアプリでは、所有者がサイドバーでセッションを保管する(セッションにカーソルを合わせて保管のアイコンを押す)と、worktree が消える

作りかけを続けるときは、worktree を残す。作りかけを続けないなら、消してよい。
