# 開発基盤 初期セットアップ手順

人間にしか実行できない作業の手順書。上から順に実施する。

> 前提: 所有者1人 + bot1つの個人開発運用。メンバーが増える場合はCODEOWNERSと承認者の設計を見直す。

## 1. CLIのインストール(ホストOS)

### 1-1. GitHub CLI のインストールと所有者ログイン

Windows:

```bash
winget install --id GitHub.cli
```

macOS/Linux:

```bash
brew install gh
```

**所有者アカウント**でログインする:

```bash
gh auth login
```

### 1-2. Claude Code CLI のインストール

Windows:

```bash
winget install Anthropic.ClaudeCode
```

macOS/Linux:

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

ターミナルを開き直し、`claude --version` が返ることを確認する。

## 2. botアカウントの作成とPATの発行

1. エージェント専用の2つ目のGitHubアカウントを作成する(例: `DogisRiki-bot`)
2. **リポジトリの** Settings → Collaborators → Add people で botアカウントを招待し、
   botアカウント側で招待を承諾する
3. **botアカウントの** Settings → Developer settings → Personal access tokens →
   Tokens (classic) → Generate new token → Generate new token (classic) で
   classic PATを作成する
   - Note: 任意(例: `keirekipro-agent`)
   - Expiration: `Custom` を選び1年後
   - scopes: `repo`、`read:org`、`workflow`

> 注意: ブランチ保護(手順4)とCODEOWNERSは、botのWrite権限を抑える前提。設定を変えない。

## 3. コミット・PR作成・push名義の固定

### 3-1. コミット名義の固定(git config)

リポジトリルートで一度だけ実行する:

```bash
git config user.name "DogisRiki-bot"
```

```bash
git config user.email "<botアカウントのnoreplyメールアドレス>"
```

確認する。botのアカウント名が返ればよい:

```bash
git config user.name
```

### 3-2. PR作成名義の固定(bot専用のgh設定ディレクトリ)

bot専用のgh設定ディレクトリを作り、そこへbotアカウントでログインする。
PATはOSの資格情報ストアに入り、設定ファイルには残らない。

ホストOSのターミナルで、**その端末に限って** `GH_CONFIG_DIR` を設定する。

Windows(PowerShell):

```bash
mkdir "$env:USERPROFILE\.gh-bot" -Force
```

```bash
$env:GH_CONFIG_DIR = "$env:USERPROFILE\.gh-bot"
```

macOS/Linux:

```bash
mkdir -p "$HOME/.gh-bot"
```

```bash
export GH_CONFIG_DIR="$HOME/.gh-bot"
```

続けて、同じ端末で **botアカウント**としてログインする:

```bash
gh auth login
```

対話の答えは次のとおり。

| 質問 | 答え |
|---|---|
| Where do you use GitHub? | GitHub.com |
| What is your preferred protocol for Git operations on this host? | HTTPS |
| How would you like to authenticate GitHub CLI? | Paste an authentication token |
| Paste your authentication token | 手順2で発行したbotのPAT |

次に、リポジトリルートに `.claude/settings.local.json` を作成する。`<user>` は実際のユーザー名にし、
`$HOME` や `%USERPROFILE%` は使わず絶対パスで書く(環境変数は展開されない)。

Windows:

```json
{
    "env": {
        "GH_CONFIG_DIR": "C:\\Users\\<user>\\.gh-bot"
    }
}
```

macOS(Linuxでは `/home/<user>/.gh-bot`):

```json
{
    "env": {
        "GH_CONFIG_DIR": "/Users/<user>/.gh-bot"
    }
}
```

確認は4つとも行う。

1. ログインした端末で次を実行し、botのアカウント名が返ること

```bash
gh api user --jq .login
```

2. ログインした端末で次を実行し、何も出力されないこと(出力されたらPATが平文で保存されている)

Windows(PowerShell):

```bash
Select-String -Path "$env:USERPROFILE\.gh-bot\hosts.yml" -Pattern oauth_token
```

macOS/Linux:

```bash
grep oauth_token "$HOME/.gh-bot/hosts.yml"
```

出力された場合は次を実行してトークンを消し、OSの資格情報ストアが使える状態にしてから
(Linuxではgnome-keyring等のsecret-serviceを起動してから)ログインをやり直す。
平文のまま先へ進まない。

```bash
gh auth logout --hostname github.com
```

3. **新しく開いた**ターミナルで次を実行し、**所有者アカウント名**が返ること。
   返らない場合は、その端末で `gh auth login` をやり直して所有者アカウントに戻す

```bash
gh api user --jq .login
```

4. Claude Codeを再起動し、エージェントに「`gh api user --jq .login` を実行して結果を報告して」と
   依頼して `DogisRiki-bot` が返ること

> 注意: `GH_CONFIG_DIR` を常設の環境変数にしない。Windowsの `setx` も、macOS/Linuxの
> シェルのプロファイルへの追記も不可。人間のターミナルのghとgit pushまでbot名義になる。

> 注意: `.claude/settings.local.json` と `.gh-bot` ディレクトリは、どちらもgit管理外。
> PCの再セットアップ時は両方を作り直す。忘れるとPRが所有者名義になり、
> 保護パスを含むPRがマージ不能になる。

### 3-3. push名義の固定(HTTPS + gh の資格情報ヘルパー)

リモートをHTTPSにし、認証をghへ委ねる。リポジトリルートで一度だけ実行する:

```bash
git remote set-url origin https://github.com/DogisRiki/KeirekiPro.git
```

```bash
git config credential.https://github.com.helper ""
```

```bash
git config --add credential.https://github.com.helper "!gh auth git-credential"
```

2つ目は、グローバル設定のヘルパー(Git Credential Manager等)を打ち消すためのもの。
空を設定してからghのヘルパーを追加しないと、そちらが先に応答して所有者の資格情報が使われる。

確認は2つとも行う。

1. Claude Codeのセッションでpushし、成功すること(botのPATが使われる)
2. 人間がターミナルで次を実行し、成功すること(ghのkeyringの所有者アカウントが使われる)

```bash
git push --dry-run
```

> 注意: リモートをSSHにしない。SSH鍵はアカウントに紐づくため、セッション内のpushも
> 鍵の持ち主(所有者)名義になり、名義の分離が崩れる。

## 4. mainブランチの保護設定

**リポジトリの** Settings → Branches → Add branch protection rule で `main` に設定する。
**Required status checks のチェック名の指定はここでは行わない**(手順8で指定する)。

| 設定 | 値 |
|---|---|
| Require a pull request before merging | ✅ |
| └ Require approvals | ❌ |
| └ Require review from Code Owners | ✅ |
| └ Dismiss stale pull request approvals when new commits are pushed | ✅ |
| Require status checks to pass before merging | ✅ |
| └ Require branches to be up to date before merging | ✅ |
| Do not allow bypassing the above settings | ✅ |

> 注意: Require approvals にチェックを入れない。全PRが承認必須になり自律マージが止まる。

あわせて **リポジトリの** Settings → General → Pull Requests:

- Allow auto-merge: ✅
- Allow squash merging: ✅(それ以外は任意でオフ)

## 5. Secrets の登録

**リポジトリの** Settings → Secrets and variables → Actions に登録する。

| Secret | 値 | 失効したとき |
|---|---|---|
| `OPENAI_API_KEY` | OpenAIダッシュボードで発行したAPIキー | codex-reviewが失敗し全PRがマージ不能になる。再発行して差し替える |
| `BOT_GITHUB_TOKEN` | 手順2で作成したbotのclassic PAT | 月次のカナリア生成が失敗する。あわせて、bot専用のgh設定ディレクトリのトークンも同じPATのため、エージェントのgh操作(Issue読み取り・PR作成・push)が全て止まる。復旧は「botのPATが期限切れになったときの復旧」に従う |

> 注意: PATの有効期限をカレンダーに登録する。

## 6. Context7 MCP のAPIキーの環境変数設定(ホストOS)

Windows:

```bash
setx CONTEXT7_API_KEY "<Context7のAPIキー>"
```

macOS/Linux はシェルのプロファイル(`~/.zshrc` 等)に追記する:

```bash
export CONTEXT7_API_KEY="<Context7のAPIキー>"
```

## 7. 検証用PRで各ゲートが赤くなるかの確認

frontend・backendの両方に軽微な変更を含む検証用PRを作成し、各チェックを一度発火させる。
次を仕込み、対応するチェックが赤くなることを確認する。

| 仕込む内容 | 赤くなるチェック |
|---|---|
| frontendの既存モジュールに、テストが通らない分岐を足してカバレッジを閾値未満にする | `frontend-test` |
| テストに `.skip` を足す | `escape-hatch` |
| 依存パッケージを1つ追加する | `dependency-gate` |
| PRに `pre-merge-check` ラベルを付ける | `pre-merge-check` |

> 注意: `gitleaks` と `size-check` はこの手順では確認しない。

あわせて確認すること:

- 依存を足したPRで、所有者がApproveすると `dependency-gate` が緑に変わる
- `codex-review` のレビューコメントがPRに付き、VERDICTの判定どおりにチェックが緑/赤になる
- `codex-review` の実行ログで、モデルが `gpt-5.6-terra`、reasoning が `high` になっている
- ローカルで次を実行し、マイグレーションの一覧とStateが表示される

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```

> 注意: 検証用PRにauto-mergeを設定しない。確認後はクローズしてブランチを削除する。

## 8. Required status checks の指定

**リポジトリの** Settings → Branches → `main` の保護ルールを編集し、次を指定する。

- `frontend-test`
- `backend-test`
- `e2e-smoke`
- `escape-hatch`
- `size-check`
- `gitleaks`
- `dependency-gate`
- `pre-merge-check`
- `codex-review`

> 注意: ここに挙げたもの以外を追加しない。

指定後、もう一度小さな検証用PRを作り、必須チェックが効いた状態でauto-mergeまで通ることを確認する。

## 9. Dependabot の有効化

9-1 から順に実施する。

### 9-1. 依存グラフとアラートの有効化

**リポジトリの** Settings → Advanced Security で、この順に Enable にする。
すでに Enable 済みの項目は `Disable` ボタンが出ているので、その場合は何もしない。

1. **Dependency graph**
2. **Automatic Dependency Submission**
3. **Dependabot alerts**

Automatic Dependency Submission は有効化した時点で自動実行される。
Actions タブでその実行が完了したことを確認してから、
Insights タブ → Dependency graph → Dependencies を開き、
`backend/build.gradle` が一覧にあることを確認する。

以後は、依存マニフェスト(`backend/build.gradle` 等)を更新した main への push で再実行される。

> 注意: ここに `backend/build.gradle` が現れないと、backendの脆弱性が検知されない。
> また 1 と 3 は 9-4 の前提でもあり、無効のままだと security updates を有効にできない。

### 9-2. version updates が有効になっているかの確認

**リポジトリの** Settings → Advanced Security を開き、**Dependabot version updates** の項目を見る。

- ボタンが **Configure** になっていればよい(押すと `.github/dependabot.yml` が開く)
- ボタンが **Enable** の場合は押す

version updates で作成されるのは backend(Gradle)と GitHub Actions のアクションのPRのみ。
frontend(npm)は対象に含めていない。

> frontend の脆弱性修正のPRは、9-4 の security updates を有効にすると作成が試みられる。
> version updates の対象かどうかとは別に動く。
> 実際に作成されるかは、そのアラートが修正可能かによる。

### 9-3. DependabotのPRがチェックを通るかの確認

最初に作成されたPRで確認すること:

- 保留のまま止まる必須チェックが無い
- `codex-review` がスキップ扱いになっている
- 自動マージされず、所有者のマージ待ちで止まる

backend(Gradle)のPRは `dependency-gate` が赤になる。ビルド定義ファイルの変更は
中身によらず承認対象のため。内容を確認してApproveすると緑に変わり、マージできる。
frontend と GitHub Actions のPRは `dependency-gate` が緑のままになる。

確認できたらそのPRを手動でマージする。DependabotのPRは今後もこの運用になる。

### 9-4. security updates の有効化

**リポジトリの** Settings → Advanced Security で、この順に操作する。

1. **Dependabot security updates** を Enable にする
2. **Grouped security updates** を Enable にする

> 注意: Grouped security updates は、Dependabot security updates が有効でないと設定できない。
> 1と2の間に作成されたPRは個別に立つため、2は続けて操作する。

ここまで確認できれば、セットアップは完了。

## botのPATが期限切れになったときの復旧

セットアップ後の障害対応。上から順に実施する。

### 症状

- `gh auth status` で `The token in keyring is invalid` が出る
- エージェントのgh操作(Issue読み取り・PR作成・push)が全て失敗する

### 復旧手順

1. **botアカウントの** Settings → Developer settings → Personal access tokens →
   Tokens (classic) で該当トークンを `Regenerate` する
   - Expiration: `Custom` を選び1年後

2. ホストOSのターミナルで `GH_CONFIG_DIR` を設定し、`gh auth login` をやり直す
   (対話の答えは手順3-2の表と同じ)

   Windows(PowerShell):

```bash
$env:GH_CONFIG_DIR = "$env:USERPROFILE\.gh-bot"
```

   macOS/Linux:

```bash
export GH_CONFIG_DIR="$HOME/.gh-bot"
```

```bash
gh auth login
```

3. 同じ端末で次を実行し、botのアカウント名が返ること

```bash
gh api user --jq .login
```

4. **リポジトリの** Settings → Secrets and variables → Actions で
   `BOT_GITHUB_TOKEN` を新しい値に更新する

5. Claude Codeを再起動し、エージェントに「`gh api user --jq .login` を実行して結果を報告して」と
   依頼して `DogisRiki-bot` が返ること
