# 開発基盤 初期セットアップ手順(人間作業)

Claude Code自律開発パイプラインのうち、**人間にしか実行できない作業**の手順書。
上から順に実施する。ファイルベースの構築(CI・設定・Skills等)はリポジトリに反映済みのため、
ここにあるのはアカウント・権限・GitHub設定・Secretsのみ。

## 1. gh CLI のインストール(ホストOS)

```bash
winget install --id GitHub.cli
```

インストール後、所有者アカウントでログインする:

```bash
gh auth login
```

## 2. bot機械ユーザーの作成(エージェント用アイデンティティ)

エージェントのcommit/PR作成を所有者本人と分離する(本人名義だと自分のPRを自分で承認できず、
CODEOWNERS必須レビューが成立しないため)。

1. 新しいGitHubアカウント(機械ユーザー。例: `DogisRiki-bot`)を作成する
2. リポジトリの Settings → Collaborators で bot を **Write** 権限で招待し、botアカウントで承諾する
3. botアカウントで **Fine-grained PAT** を作成する
   - Repository access: `KeirekiPro` のみ
   - Permissions: Contents (Read and write) / Pull requests (Read and write) / Issues (Read and write) / Actions (Read) / Workflows (Read and write)
4. ホストOSで bot 用の gh プロファイルを追加する:

```bash
gh auth login
```

   (2アカウント目としてPATでログイン。`gh auth switch` で切り替え可能になる)

5. リポジトリローカルのgit識別子をbotにする場合(エージェント作業時):

```bash
git config user.name "DogisRiki-bot"
```

```bash
git config user.email "<botアカウントのnoreplyメールアドレス>"
```

> 運用: エージェントセッションでは bot プロファイル、人間の手作業では所有者プロファイルを使う。
> 切り替えは `gh auth switch --user <account>`。

## 3. ブランチ保護(Branch protection rule for `main`)

Settings → Branches → Add branch protection rule で `main` に対して以下を設定する:

| 設定 | 値 |
|---|---|
| Require a pull request before merging | ✅ |
| └ Require approvals | ❌(チェックしない。全PRに承認必須にすると自律マージが壊れる) |
| └ **Require review from Code Owners** | ✅(保護パスを含むPRのみ人間承認必須になる) |
| └ **Dismiss stale pull request approvals when new commits are pushed** | ✅(承認後のcommit追加による抜け道の封鎖) |
| **Require status checks to pass before merging** | ✅ |
| └ **Require branches to be up to date before merging** | ✅(マージの実質直列化) |
| └ Required checks | 下記リスト |
| Do not allow bypassing the above settings | ✅ 推奨 |

**Required status checks に指定するチェック名**(一度PRを作って実行されると候補に出る):

- `frontend-test`(ci.yaml / frontend変更時)
- `backend-test`(ci.yaml / backend変更時)
- `e2e-smoke`(ci.yaml / frontend変更時)
- `escape-hatch`(guardrails.yaml)
- `size-check`(guardrails.yaml)
- `gitleaks`(guardrails.yaml)
- `dependency-gate`(dependency-gate.yaml)
- `codex-review`(codex-review.yml ※Phase 3導入後)

> 注: paths-filterでskipされたジョブ(例: frontendのみのPRの `backend-test`)は成功扱いになる。

あわせて Settings → General → Pull Requests:

- **Allow auto-merge**: ✅
- Allow squash merging: ✅(それ以外は任意でオフ)

## 4. Secrets の登録

Settings → Secrets and variables → Actions:

| Secret | 用途 | 取得方法 |
|---|---|---|
| `OPENAI_API_KEY` | CodexクロスレビューCI | OpenAIダッシュボードで発行 |
| `CLAUDE_CODE_OAUTH_TOKEN` | @claudeメンションCI・週次依存更新 | ホストで `claude setup-token` を実行 |
| `BOT_GITHUB_TOKEN` | カナリアPR生成(月次) | 手順2で作成したbotのFine-grained PAT(デフォルトのGITHUB_TOKENではカナリアPRのCIが発火しないため) |

(既存の `AWS_ACCOUNT_ID` はそのまま)

## 5. MCP 用環境変数(ホストOS)

Context7 MCP用のAPIキーをOSユーザー環境変数に設定する(値はリポジトリに置かない):

```bash
setx CONTEXT7_API_KEY "<Context7のAPIキー>"
```

## 6. 動作確認

セットアップ完了後、検証用PR(意図的にカバレッジを下げる・`.skip`を足す・依存を足す等)で
各ゲートが赤くなること、所有者Approveで `dependency-gate` が緑に再評価されることを確認する。
検証手順の詳細は `doc/開発フロー/監査手順.md` を参照。
