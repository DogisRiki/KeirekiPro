# 開発基盤 初期セットアップ手順

Claude Code自律開発パイプラインのうち、**人間にしか実行できない作業**の手順書。
上から順に実施する。

> 本手順は**所有者1人+bot1つの個人開発運用**を前提とする。
> メンバーが増える場合は、CODEOWNERSと承認者の設計(所有者アカウント名での照合を含む)を見直すこと。

## 1. GitHub CLI と Claude Code CLI のインストール(ホストOS)

### 1-1. GitHub CLI

Windowsの場合:

```bash
winget install --id GitHub.cli
```

macOS/Linuxの場合は Homebrew 等でインストールする:

```bash
brew install gh
```

インストール後、**所有者アカウント**でログインする:

```bash
gh auth login
```

### 1-2. Claude Code CLI

Windowsの場合:

```bash
winget install Anthropic.ClaudeCode
```

macOS/Linuxの場合:

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

インストール後、ターミナルを開き直して `claude --version` が返ることを確認する。

## 2. botアカウントの作成(エージェント用アイデンティティ)

エージェントのcommit/PR作成を所有者本人と分離する(本人名義だと自分のPRを自分で承認できず、
CODEOWNERS必須レビューが成立しないため)。

> **安全の前提**: botはWrite権限を持つが、mainブランチへの直接pushはブランチ保護(手順4)で、
> ゲート設定ファイルの変更はCODEOWNERSの必須レビューで防がれている。この2つが安全の前提であり、
> ブランチ保護やCODEOWNERSの設定を変更するとこの前提が崩れる。

1. botアカウント(エージェント専用に使う2つ目のGitHubアカウント。例: `DogisRiki-bot`)を作成する
2. リポジトリの Settings → Collaborators → Add people で botアカウントを招待し、
   botアカウント側で届いた招待を承諾する(個人リポジトリでは権限を選ぶ操作は無く、
   承諾により読み書き可能なコラボレーターになる)
3. botアカウントで **classic PAT** を作成する
   (Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token → Generate new token(classic))
   - Note: (例: `keirekipro-agent`)
   - Expiration: `Custom` を選択して1年後を設定 ※更新は手順5を参照
   - scopes: `repo` と `workflow`

## 3. コミット・PR作成名義の固定(切り替え操作を無くす)

エージェント作業と人間作業の名義分離は、**切り替え操作を無くす方法**で行う。
手動切り替えは名義の混在事故を招くため採用しない。

### 3-1. コミット名義: リポジトリローカルのgit configをbotに固定する

リポジトリルートで一度だけ実行する(以後切り替えない):

```bash
git config user.name "DogisRiki-bot"
```

```bash
git config user.email "<botアカウントのnoreplyメールアドレス>"
```

この運用では人間がコードをコミットすることは無い(ゲート設定の変更もClaude Code経由のPRで行う)ため、
このリポジトリのコミット名義は常にbotでよい。

確認方法:

```bash
git config user.name
```

botのアカウント名が返ればよい。

### 3-2. PR作成名義: .claude/settings.local.json でClaude Codeセッションのghをbotにする

`.claude/settings.local.json` をリポジトリルートに作成し、手順2で作成したbotのPATを設定する:

```json
{
    "env": {
        "GH_TOKEN": "<botのclassic PAT>"
    }
}
```

- このファイルはgit管理外(gitignore済み)で、リポジトリには含まれない
- Claude Codeのセッション内で実行されるghコマンドだけが自動的にbot名義になる。
  人間が普段のターミナルで使うghは手順1の所有者ログインのまま

確認方法(両方確認する):

1. Claude Codeのセッション(利用しているインターフェースは問わない)で、エージェントに
   「`gh api user --jq .login` を実行して結果をそのまま報告して」と依頼し、
   報告された名前が `DogisRiki-bot` であることを確認する
2. 人間がターミナルで次を直接実行し、**所有者アカウント名**が返ることを確認する

```bash
gh api user --jq .login
```

> **警告**: PCを再セットアップしたときにこのファイルの再作成を忘れると、PR作成が所有者名義に戻り、
> CODEOWNERSの必須レビューが成立しなくなる(自分のPRは自分で承認できないため、
> 保護パスを含むPRがマージ不能になる)。再セットアップ時は必ずこの手順を再実施すること。

## 4. ブランチ保護(Branch protection rule for `main`)

Settings → Branches → Add branch protection rule で `main` に対して以下を設定する。
**Required status checks のチェック名の指定だけは、この時点では行わない**
(チェックが一度実行されるまで候補に出ないため、手順8の後に手順9で指定する)。

| 設定 | 値 |
|---|---|
| Require a pull request before merging | ✅ |
| └ Require approvals | ❌(チェックしない。全PRに承認必須にすると自律マージが壊れる) |
| └ **Require review from Code Owners** | ✅(保護パスを含むPRのみ人間承認必須になる) |
| └ **Dismiss stale pull request approvals when new commits are pushed** | ✅(承認後のcommit追加による抜け道の封鎖) |
| **Require status checks to pass before merging** | ✅(チェック名の指定は手順9で行う) |
| └ **Require branches to be up to date before merging** | ✅(マージの実質直列化) |
| Do not allow bypassing the above settings | ✅ 推奨 |

あわせて Settings → General → Pull Requests:

- **Allow auto-merge**: ✅
- Allow squash merging: ✅(それ以外は任意でオフ)

## 5. Secrets の登録

Settings → Secrets and variables → Actions:

| Secret | 用途 | 取得方法 | 有効期限と失効時の影響・更新方法 |
|---|---|---|---|
| `OPENAI_API_KEY` | CodexクロスレビューCI | OpenAIダッシュボードで発行 | 期限は無いが、失効・削除するとcodex-reviewが失敗し全PRがマージ不能になる。再発行してSecretsを差し替える |
| `CLAUDE_CODE_OAUTH_TOKEN` | @claudeメンションCI・週次依存更新 | **人間がターミナルで** `claude setup-token` を実行する。ブラウザが開くのでAnthropicアカウントで承認し、表示されたトークンをこのSecretに登録する。**エージェントに実行させないこと**(トークンが会話ログに残るため) | 1年間の有効期限あり。失効すると@claudeメンションと週次依存更新(claude.yml)が失敗する。人間が `claude setup-token` を再実行して差し替える |
| `BOT_GITHUB_TOKEN` | カナリアPR生成(月次) | 手順2で作成したbotのclassic PAT(デフォルトのGITHUB_TOKENではカナリアPRのCIが発火しないため) | classic PATは作成時に設定した有効期限(例: 1年)で失効する。失効すると月次のカナリア生成(canary.yaml)が認証エラーで失敗する。botアカウントでPATを再発行し、このSecretと **`.claude/settings.local.json` の `GH_TOKEN`(手順3-2)の両方**を差し替える |

- PATの有効期限はカレンダーに登録し、期限前に更新する

## 6. Claude GitHub App のインストール

@claudeメンションと週次依存更新(claude.yml)は Claude GitHub App が前提となる。
https://github.com/apps/claude を開き、`KeirekiPro` リポジトリへインストールする。
インストール後、Appの設定画面(Settings → Integrations → Applications)で Repository access に `KeirekiPro` が含まれていることを確認する。

## 7. MCP 用環境変数(ホストOS)

Context7 MCP用のAPIキーをOSユーザー環境変数に設定する(値はリポジトリに置かない)。

Windowsの場合:

```bash
setx CONTEXT7_API_KEY "<Context7のAPIキー>"
```

macOS/Linuxの場合はシェルのプロファイル(`~/.zshrc` 等)に追記する:

```bash
export CONTEXT7_API_KEY="<Context7のAPIキー>"
```

## 8. 検証用PRによる動作確認(チェックの発火)

frontend・backendの両方に軽微な変更を含む検証用PRを作成し、各チェックを一度発火させる。
このPRは手順9でRequired status checksの候補を出すためにも必要となる。

- 検証内容の例: 意図的にカバレッジを下げる・`.skip` を足す・依存パッケージを足す等で、
  各ゲートが赤くなることを確認する
- 依存を足したPRで、所有者がApproveすると `dependency-gate` が緑に再評価されることを確認する
- `codex-review` について、VERDICT(コード品質・spec適合の判定)を含むレビューコメントがPRに付き、
  **かつ codex-review チェックが判定どおりに緑/赤へ反映されること**まで確認する。
  失敗する場合は codex CLI のフラグ(`--sandbox` 等)が実態と合っていない可能性が高いため、
  実際のCLI仕様に合わせて `.github/workflows/codex-review.yml` を調整する想定でよい
- `codex-review` の実行ログで、使用モデル(gpt-5.6-terra)と reasoning 設定(high)が
  意図どおりに適用されていることを確認する。適用されていない場合は、
  CLIバージョンに合わせて設定キー(`model_reasoning_effort` / `--reasoning` 等)を
  実態に合わせて修正する
- ローカルで次を実行し、マイグレーションの適用状況(V1以降の一覧とState)が表示されることを確認する

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```
- Actionsタブから claude.yml の週次依存更新(workflow_dispatchで手動起動できる)を一度実行し、
  **作成されたPRで必須チェック(CI・guardrails等)が発火すること**を確認する。
  発火しない場合(チェックが1つも走らない場合)は、claude.yml の claude-code-action に
  `github_token: ${{ secrets.BOT_GITHUB_TOKEN }}` を渡す構成へ変更する
- 検証用PRには**auto-mergeを設定しない**。確認が済んだらクローズしてブランチを削除する
- 検証手順の詳細は `doc/開発フロー/監査手順.md` を参照

## 9. Required status checks の指定

手順8でチェックが実行されると、ブランチ保護の設定画面で候補に出るようになる。
Settings → Branches → `main` の保護ルールを編集し、以下を指定する:

- `frontend-test`(ci.yaml / frontend変更時)
- `backend-test`(ci.yaml / backend変更時)
- `e2e-smoke`(ci.yaml / frontend変更時)
- `escape-hatch`(guardrails.yaml)
- `size-check`(guardrails.yaml)
- `gitleaks`(guardrails.yaml)
- `dependency-gate`(dependency-gate.yaml)
- `pre-merge-check`(pre-merge-check.yaml)
- `codex-review`(codex-review.yml)

> 注: paths-filterでskipされたジョブ(例: frontendのみのPRの `backend-test`)は成功扱いになる。

指定後、もう一度小さな検証用PRを作り、必須チェックが効いた状態でauto-mergeまで通ることを
確認できれば、セットアップは完了。
