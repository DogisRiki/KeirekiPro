# 開発基盤 初期セットアップ手順

人間にしか実行できない作業の手順書。上から順に実施する。

> 前提: 所有者1人 + bot1つの個人開発運用。メンバーが増える場合はCODEOWNERSと承認者の設計を見直す。

## 1. CLIのインストール(ホストOS)

### 1-1. GitHub CLI のインストールと所有者ログイン

Windows:

```bash
winget install --id GitHub.cli
```

macOS/Linux:

```bash
brew install gh
```

**所有者アカウント**でログインする:

```bash
gh auth login
```

### 1-2. Claude Code CLI のインストール

Windows:

```bash
winget install Anthropic.ClaudeCode
```

macOS/Linux:

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

ターミナルを開き直し、`claude --version` が返ることを確認する。

## 2. botアカウントの作成とPATの発行

1. エージェント専用の2つ目のGitHubアカウントを作成する(例: `DogisRiki-bot`)
2. **リポジトリの** Settings → Collaborators → Add people で botアカウントを招待し、
   botアカウント側で招待を承諾する
3. **botアカウントの** Settings → Developer settings → Personal access tokens →
   Tokens (classic) → Generate new token → Generate new token (classic) で
   classic PATを作成する
   - Note: 任意(例: `keirekipro-agent`)
   - Expiration: `Custom` を選び1年後
   - scopes: `repo` と `workflow`

> 注意: ブランチ保護(手順4)とCODEOWNERSは、botのWrite権限を抑える前提。設定を変えない。

## 3. コミット・PR作成名義の固定

### 3-1. コミット名義の固定(git config)

リポジトリルートで一度だけ実行する:

```bash
git config user.name "DogisRiki-bot"
```

```bash
git config user.email "<botアカウントのnoreplyメールアドレス>"
```

確認する。botのアカウント名が返ればよい:

```bash
git config user.name
```

### 3-2. PR作成名義の固定(settings.local.json)

リポジトリルートに `.claude/settings.local.json` を作成し、手順2のPATを設定する:

```json
{
    "env": {
        "GH_TOKEN": "<botのclassic PAT>"
    }
}
```

確認は2つとも行う。

1. Claude Codeのセッションで、エージェントに「`gh api user --jq .login` を実行して結果を報告して」と
   依頼し、`DogisRiki-bot` が返ること
2. 人間がターミナルで次を実行し、**所有者アカウント名**が返ること

```bash
gh api user --jq .login
```

> 注意: このファイルはgit管理外。PCの再セットアップ時は必ず作り直す。忘れるとPRが所有者名義になり、
> 保護パスを含むPRがマージ不能になる。

## 4. mainブランチの保護設定

**リポジトリの** Settings → Branches → Add branch protection rule で `main` に設定する。
**Required status checks のチェック名の指定はここでは行わない**(手順8で指定する)。

| 設定 | 値 |
|---|---|
| Require a pull request before merging | ✅ |
| └ Require approvals | ❌ |
| └ Require review from Code Owners | ✅ |
| └ Dismiss stale pull request approvals when new commits are pushed | ✅ |
| Require status checks to pass before merging | ✅ |
| └ Require branches to be up to date before merging | ✅ |
| Do not allow bypassing the above settings | ✅ |

> 注意: Require approvals にチェックを入れない。全PRが承認必須になり自律マージが止まる。

あわせて **リポジトリの** Settings → General → Pull Requests:

- Allow auto-merge: ✅
- Allow squash merging: ✅(それ以外は任意でオフ)

## 5. Secrets の登録

**リポジトリの** Settings → Secrets and variables → Actions に登録する。

| Secret | 値 | 失効したとき |
|---|---|---|
| `OPENAI_API_KEY` | OpenAIダッシュボードで発行したAPIキー | codex-reviewが失敗し全PRがマージ不能になる。再発行して差し替える |
| `BOT_GITHUB_TOKEN` | 手順2で作成したbotのclassic PAT | 月次のカナリア生成が失敗する。PATを再発行し、このSecretと `.claude/settings.local.json` の `GH_TOKEN`(手順3-2)の**両方**を差し替える |

> 注意: PATの有効期限をカレンダーに登録する。

## 6. Context7 MCP のAPIキーの環境変数設定(ホストOS)

Windows:

```bash
setx CONTEXT7_API_KEY "<Context7のAPIキー>"
```

macOS/Linux はシェルのプロファイル(`~/.zshrc` 等)に追記する:

```bash
export CONTEXT7_API_KEY="<Context7のAPIキー>"
```

## 7. 検証用PRで各ゲートが赤くなるかの確認

frontend・backendの両方に軽微な変更を含む検証用PRを作成し、各チェックを一度発火させる。
意図的にカバレッジを下げる、`.skip` を足す、依存パッケージを足す、といった内容にする。

確認すること:

- 各ゲートが赤くなる
- 依存を足したPRで、所有者がApproveすると `dependency-gate` が緑に変わる
- `codex-review` のレビューコメントがPRに付き、VERDICTの判定どおりにチェックが緑/赤になる
- `codex-review` の実行ログで、モデルが `gpt-5.6-terra`、reasoning が `high` になっている
- ローカルで次を実行し、マイグレーションの一覧とStateが表示される

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```

> 注意: 検証用PRにauto-mergeを設定しない。確認後はクローズしてブランチを削除する。

## 8. Required status checks の指定

**リポジトリの** Settings → Branches → `main` の保護ルールを編集し、次を指定する。

- `frontend-test`
- `backend-test`
- `e2e-smoke`
- `escape-hatch`
- `size-check`
- `gitleaks`
- `dependency-gate`
- `pre-merge-check`
- `codex-review`

> 注意: ここに挙げたもの以外を追加しない。

指定後、もう一度小さな検証用PRを作り、必須チェックが効いた状態でauto-mergeまで通ることを確認する。

## 9. Dependabot の有効化

9-1 から順に実施する。

### 9-1. 依存グラフとアラートの有効化

**リポジトリの** Settings → Advanced Security で、この順に Enable にする。
すでに Enable 済みの項目は `Disable` ボタンが出ているので、その場合は何もしない。

1. **Dependency graph**
2. **Automatic Dependency Submission**
3. **Dependabot alerts**

有効化しただけでは依存グラフに反映されない。mainブランチへのpushをきっかけに更新される。
pushの数分後に Insights タブ → Dependency graph → Dependencies を開き、
`backend/build.gradle` が一覧にあることを確認する。無ければ数分待って再読み込みする。

> 注意: ここに `backend/build.gradle` が現れないと、backendの脆弱性が検知されない。
> また 1 と 3 は 9-4 の前提でもあり、無効のままだと security updates を有効にできない。

### 9-2. version updates が有効になっているかの確認

**リポジトリの** Settings → Advanced Security を開き、**Dependabot version updates** の項目を見る。

- ボタンが **Configure** になっていればよい(押すと `.github/dependabot.yml` が開く)
- ボタンが **Enable** の場合は押す

作成されるのは backend(Gradle)と GitHub Actions のアクションのPRのみ。frontend(npm)は対象外。

### 9-3. DependabotのPRがチェックを通るかの確認

最初に作成されたPRで確認すること:

- 必須チェックがすべて成功またはスキップ扱いになり、保留のまま止まるものが無い
- `codex-review` がスキップ扱いになっている
- `dependency-gate` が緑になっている
- すべて緑になっても自動マージされず、所有者のマージ待ちで止まる

確認できたらそのPRを手動でマージする。DependabotのPRは今後もこの運用になる。

### 9-4. security updates の有効化

**リポジトリの** Settings → Advanced Security で、この順に操作する。

1. **Dependabot security updates** を Enable にする
2. **Grouped security updates** を Enable にする

> 注意: Grouped security updates は、Dependabot security updates が有効でないと設定できない。
> 1と2の間に作成されたPRは個別に立つため、2は続けて操作する。

ここまで確認できれば、セットアップは完了。
