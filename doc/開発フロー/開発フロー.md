# 開発フロー

KeirekiProの開発は「**人間はコードを読まない**」前提の自律パイプラインで行う。
安全は人間のレビューではなく、多層の機械ゲート(テスト・カバレッジ閾値・ArchUnit/ESLint境界・
逃げ道封鎖CI・クロスAIレビュー・ブランチ保護)が担保する。

## 人間の役割(5つだけ)

| 役割 | 具体的行為 |
|---|---|
| **1. 意図の定義** | Issue起票(1〜2行でよい。詳細化はAIの仕事)。SDDのspec承認(要件・設計の意思決定。コードではなく仕様を判断する) |
| **2. ループの設計・監視・改善** | 週次・月次監査(`doc/開発フロー/監査手順.md`)。ゲートすり抜けを「ゲートの追加・強化」として還元 |
| **3. 体験検証** | **本番デプロイのトリガーを押す前に、ローカルでmainを起動して触って確認する**。マージのたびの確認は不要、デプロイしたいタイミングで1回触れば足りる |
| **4. 例外ゲートの承認** | DBマイグレーション・依存パッケージ追加・ゲート設定変更を含むPRのみ承認ボタンを押す。**DBマイグレーションPRは承認前にローカルDBで適用・巻き戻しを確認する**。**承認ボタンは、Codexレビューが両軸LGTMで収束しCI全グリーンになった後(=最後)に押す**(承認後のcommitでApproveが無効化されるため) |
| **5. リリース判断** | 本番デプロイの手動トリガー(Actions → Production Release)。マージには関与しない |

マージ判定は機械的: **Codexレビュー(コード品質・spec適合の両軸)LGTM + 必須チェック全グリーン → auto-merge**。

## 開発の起点

- **人間の意図**: 新機能・改善・バグ認知 → GitHub Issueを起票する
- **機械の検知**: CI失敗・依存脆弱性・レビュー指摘 → 自律ループが拾う

## Lane A: 新機能(spec駆動)

複数層にまたがる変更・新機能はspec駆動で行う。

```
人間: Issue起票
  ↓
/kiro-discovery "アイデア"          … spec化の要否・分割を判定
/kiro-spec-init → /kiro-spec-requirements → /kiro-spec-design → /kiro-spec-tasks
  ↓ (人間: requirements/designを承認 ← 仕様の判断。コードレビューではない)
/kiro-impl {feature} + /goal(SDDタスク消化ゴール)   … 自律実装
  ↓
/ship   … verify-all → commit → push → PR作成(本文に Spec: と Refs:)→ auto-merge予約
  ↓
Codexクロスレビュー ⇄ /review-loop(最大5往復)
  ↓ 両軸LGTM + CI全グリーン
自動squashマージ
  ↓ (任意のタイミングで)
人間: ローカルでmainを起動して確認 → Actions「Production Release」を手動トリガー
```

## Lane B: 小修正(spec不要)

バグ修正・小改善(コード差分200行以内)。

```
Issue → Claude Codeが直接実装 → /ship → (Lane Aと同じPRパイプライン)
```

- 200行(コード差分)を超えるとsize-checkが赤になりLane Aへ差し戻される
- マイグレーション・依存追加・ゲート設定変更を含む場合はサイズに関係なく人間承認ゲートにかかる

## Lane C: 自律メンテループ

| ループ | 起動 | 内容 |
|---|---|---|
| 作業中メンテ | `/loop 30m` | `.claude/loop.md`(verify+図の乖離確認+PR状態) |
| PR監視 | `/loop 5m check my PR` | CI赤の修復・Codex指摘対応(完了で自然停止) |
| メンション | Issue/PRで `@claude` | CI上で直接作業(所有者のコメントのみ発火) |
| 週次 | schedule(claude.yml) | 依存バージョン更新の自動レーン(追加は不可) |
| 週次 | schedule(mutation-report) | mutation testingレポート(Stryker/PIT) |
| 月次 | schedule(canary.yaml) | カナリアPR3種でゲートの健康診断 |

各ループの契約(Trigger/Scope/Permission/Verification gate/Budget/Stop・Escalation/Reporting)は
`doc/開発フロー/ループ契約.md` に定義。`/goal` の標準ゴールは `doc/開発フロー/ゴールテンプレート.md`。

## ガードレール一覧(何が機械強制されるか)

| 層 | ゲート | 検知対象 |
|---|---|---|
| テスト | Vitest / JUnit+Testcontainers + カバレッジ閾値(vite.config.ts / quality.gradle) | ロジック破壊・カバレッジ低下 |
| 静的解析 | ESLint(境界+sonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | 境界違反・アサーション無しテスト・型逸脱 |
| 逃げ道封鎖 | escape-hatch(guardrails.yaml) | skip/only/@Disabled・@ts-ignore・インラインeslint-disable・assert削除・ゲート配線破壊 |
| サイズ | size-check | コード差分200行超(spec裏付けなし) |
| 依存 | dependency-gate | 依存「追加」(所有者Approveで緑に再評価) |
| DB | CODEOWNERS(migrationディレクトリ) | マイグレーション変更(人間承認必須) |
| 設定保護 | CODEOWNERS + settings.json deny | ゲート設定ファイルの変更(人間承認必須) |
| 秘密情報 | gitleaks | シークレット混入 |
| クロスAI | codex-review(2軸VERDICT・fail-closed) | バグ・セキュリティ・spec不適合・ゴールハック |
| リリース | release.yaml(workflow_dispatch) | 本番反映は人間トリガーのみ |
| 健康診断 | canary.yaml(月次) | ゲート自体の検出能力低下 |

## エスカレーション(review-loop 5往復超過)

人間が見るのは「**spec/Issue**」「**review-loopの往復ログ(PRコメント)**」の2つのみ。
取れる判断は「**spec差し戻し**」「**タスク分割してIssue再起票**」「**PR破棄**」の3択。
コードを読む選択肢は無い。

## ロールバック

- frontend: Actions「Frontend Rollback」に過去の成功run IDを指定
- backend: ECSタスク定義を前リビジョンへ戻す(`doc/インフラ設計/手順書/手動作業手順.md`)
- DB: expand-contract規約(`backend/CLAUDE.md`)により、直前リリースとの互換が保たれている
