# 開発フロー

KeirekiProの開発は、人間がコードをレビューしないことを前提とした自律パイプラインで行う。
品質は人間のレビューではなく、テスト・カバレッジ基準・アーキテクチャ境界の機械検査・
検査回避の検知・別AIによるレビュー・ブランチ保護を重ねた自動チェックで担保する。

## 人間の役割

人間が行うのは次の5つに限る。

| 役割 | 具体的行為 |
|---|---|
| **1. 意図の定義** | Issueを起票する(1〜2行でよい。詳細化はAIの仕事)。spec駆動開発では要件・設計ドキュメントを承認する(コードではなく仕様を判断する) |
| **2. 仕組みの監視・改善** | 週次・月次の監査(`doc/開発フロー/監査手順.md`)。チェックをすり抜けた問題は、個別の修正で終わらせずチェックの追加・強化につなげる |
| **3. 体験の確認** | 本番デプロイを実行する前に、ローカルでmainブランチを起動して実際に触って確かめる。マージのたびに確認する必要はなく、デプロイしたいタイミングで1回確認すれば足りる |
| **4. 影響の大きい変更の承認** | DBマイグレーション・依存パッケージの追加・チェック設定の変更を含むPRに限り、承認ボタンを押す。DBマイグレーションのPRは、承認前にローカルDBで適用と巻き戻しを確認する。承認ボタンを押すのは、Codexレビューの指摘対応が終わりCIの必須チェックがすべて成功した、最後の段階にする(承認後にコミットが積まれると承認が無効化され、再承認が必要になるため) |
| **5. リリースの判断** | 本番デプロイを手動で実行する(Actionsの「Production Release」)。マージには関与しない |

プルリクエストのマージに人間は関与しない。Codexレビューがコード品質と仕様適合の両方を
問題なしと判定し、CIの必須チェックがすべて成功したときに、自動でマージされる。

## 開発の起点

- **人間の意図**: 新機能・改善・バグ認知 → GitHub Issueを起票する
- **機械の検知**: CI失敗・依存脆弱性・レビュー指摘 → 自律ループが拾う

## Lane A: 新機能(spec駆動)

複数層にまたがる変更・新機能はspec駆動で行う。

```
人間: Issue起票
  ↓
/kiro-discovery "アイデア"          … spec化の要否・分割を判定
/kiro-spec-init → /kiro-spec-requirements → /kiro-spec-design → /kiro-spec-tasks
  ↓ (人間: requirements/designを承認 ← 仕様の判断。コードレビューではない)
/kiro-impl {feature} + /goal(SDDタスク消化ゴール)   … 自律実装
  ↓
/ship   … verify-all → commit → push → PR作成(本文に Spec: と Refs:)→ auto-merge予約
  ↓
Codexレビュー と /review-loop での指摘対応(最大5往復)
  ↓ レビュー通過 + CI必須チェック成功
自動squashマージ
  ↓ (任意のタイミングで)
人間: ローカルでmainを起動して確認 → Actions「Production Release」を手動トリガー
```

## Lane B: 小修正(spec不要)

バグ修正・小改善(コード差分200行以内)。

```
Issue → Claude Codeが直接実装 → /ship → (Lane Aと同じPRパイプライン)
```

- 200行(コード差分)を超えるとsize-checkが赤になりLane Aへ差し戻される
- マイグレーション・依存追加・ゲート設定変更を含む場合はサイズに関係なく人間承認ゲートにかかる

## Lane C: 自律メンテループ

| ループ | 起動 | 内容 |
|---|---|---|
| 作業中メンテ | `/loop 30m` | `.claude/loop.md`(verify+図の乖離確認+PR状態) |
| PR監視 | `/loop 5m check my PR` | CI赤の修復・Codex指摘対応(完了で自然停止) |
| メンション | Issue/PRで `@claude` | CI上で直接作業(所有者のコメントのみ発火) |
| 週次 | schedule(claude.yml) | 依存バージョン更新の自動レーン(追加は不可) |
| 週次 | schedule(mutation-report) | mutation testingレポート(Stryker/PIT) |
| 月次 | schedule(canary.yaml) | カナリアPR3種でゲートの健康診断 |

各ループの契約(Trigger/Scope/Permission/Verification gate/Budget/Stop・Escalation/Reporting)は
`doc/開発フロー/ループ契約.md` に定義。`/goal` の標準ゴールは `doc/開発フロー/ゴールテンプレート.md`。

## 自動チェックの一覧

| 種類 | 実体 | 何を防ぐか |
|---|---|---|
| テストとカバレッジ基準 | Vitest / JUnit(Testcontainers)、カバレッジ閾値(vite.config.ts / quality.gradle) | ロジックの破壊、テストの薄い変更 |
| 静的解析 | ESLint(境界ルールとsonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | アーキテクチャ境界の違反、アサーションの無いテスト、型の逸脱 |
| 検査回避の検知 | escape-hatchチェック(guardrails.yaml) | テストのskip化、@Disabledや@ts-ignoreの追加、インラインでのlint無効化、アサーションの削除、品質チェック配線の改変 |
| 差分サイズの検査 | size-check(guardrails.yaml) | specの裏付けなしにコード差分200行を超える変更が入ること |
| 依存追加の検査 | dependency-gate | 依存パッケージが承認なしに追加されること(所有者が承認するとチェックが成功に変わり、マージが進む) |
| DBマイグレーションの承認 | CODEOWNERS(migrationディレクトリ) | スキーマ変更が人間の確認なしにマージされること |
| チェック設定の保護 | CODEOWNERS + settings.jsonの編集拒否 | 品質チェックの設定がAIの判断で変更されること |
| シークレットスキャン | gitleaks | 認証情報などの混入 |
| 別AIによるレビュー | codex-review(判定はジョブの成否で行い、コメントの偽装は効かない) | バグ、セキュリティ問題、仕様との不一致、チェックを形だけ通す変更 |
| リリースの分離 | release.yaml(手動実行) | マージだけで本番に反映されること |
| 健全性の確認 | canary.yaml(月次) | チェックの仕組み自体が気づかないうちに壊れること |

## レビューが収束しない場合の対応

Codexレビューとの指摘対応が5往復しても収束しない場合は、人間が判断する。
このとき人間が読むのはspec(またはIssue)と、PRコメントに残る指摘対応の履歴だけで、コードは読まない。
取れる判断は次の3つ。

1. specを差し戻し、要件・設計から見直す
2. タスクを分割してIssueを立て直す
3. PRを破棄する

## ロールバック

- frontend: Actions「Frontend Rollback」に過去の成功run IDを指定
- backend: ECSタスク定義を前リビジョンへ戻す(`doc/インフラ設計/手順書/手動作業手順.md`)
- DB: expand-contract規約(`backend/CLAUDE.md`)により、直前リリースとの互換が保たれている
