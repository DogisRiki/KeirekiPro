# /goal テンプレート集

ゴールベースループの標準ゴール定義。すべて「**定量条件 + 最大ターン + ハック対策**」の3点セットで書く。
評価は別モデル(Haiku)が行うため、機械的に判定できる条件のみを使うこと。

## 1. 実装完了ゴール(小修正・タスク実装の標準)

```
/goal verify-all(変更領域の format/lint/test/coverage または spotlessApply/check)の全コマンドが
exit 0 で PASS している。テストへの skip/only/@Disabled の追加、既存アサーションの削除、
カバレッジ・lint 除外設定の追加を行っていない。最大10ターンで停止。
```

## 2. テスト修復ゴール

```
/goal docker compose exec -u node -w /home/node/app frontend pnpm test が exit 0。
既存テストファイルの削除・skip化・アサーション削除を行っていない。最大8ターンで停止。
```

(backendの場合は `docker compose exec -w /home/spring/app backend ./gradlew test` に読み替え)

## 3. SDDタスク消化ゴール(/kiro-impl と併用)

```
/goal .kiro/specs/<feature>/tasks.md の未完了チェックボックスが0件で、各タスクの完了条件
(該当verifyのPASS・acceptance criteriaに対応するテストの存在)を満たしている。
テストskip・除外追加による見かけの完了を作っていない。最大15ターンで停止。
```

## 4. リファクタリングゴール

```
/goal docker compose exec -w /home/spring/app backend ./gradlew check が exit 0 で、
public メソッドのシグネチャ変更・APIレスポンス形式の変更・テストの削除を行っていない。
最大6ターンで停止。
```

## 運用ルール

- ゴールは1つに絞る(複数の関心事を1ゴールに詰めない)
- 開始前に対象を小さく切る(1画面・1テストファイル・1タスク程度)
- 終了後に `/usage` でコストを確認する。トークンが増え続ける場合はループ設計を小さく戻す
- ターン上限に達して未達成の場合は、原因を報告して人間の判断を仰ぐ(勝手に上限を増やして再実行しない)
