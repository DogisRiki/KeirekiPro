# 基盤構築手順

リポジトリに対して1回だけ行う作業の手順書。所有者が上から順に実施する。
開発に参加する人が各自行う作業は [参加者セットアップ手順](参加者セットアップ手順.md) に分けている。

> 前提: 所有者1人 + bot1つの個人開発運用。メンバーが増える場合はCODEOWNERSと承認者の設計を見直す。

手順2以降は、所有者自身の [参加者セットアップ手順](参加者セットアップ手順.md) が
完了していることを前提とする(手順1で作る GitHub App の秘密鍵と所有者の gh の鍵を
参加者セットアップで使うため、手順1だけを先に行う)。

## 1. botアカウント・GitHub App・所有者の gh の鍵の準備

### 1-1. botアカウントの作成と招待

1. エージェント専用の2つ目のGitHubアカウントを作成する(例: `DogisRiki-bot`)
2. **リポジトリの** Settings → Collaborators → Add people で botアカウントを招待し、
   botアカウント側で招待を承諾する

botアカウントの classic PAT は、手順3の冒頭で作る。

> 注意: ブランチ保護(手順2)とCODEOWNERSは、botのWrite権限を抑える前提。設定を変えない。

### 1-2. GitHub App を作ってインストールする

Claude の gh と git push は、この App のトークンで動く。

1. **自分のアカウントの** Settings → Developer settings → GitHub Apps → New GitHub App で App を作る

| 設定 | 値 |
|---|---|
| GitHub App name | 任意(例: `keirekipro-agent-dogisriki`。GitHub 全体で重ならない名前にする) |
| Homepage URL | `https://github.com/DogisRiki/KeirekiPro` |
| Webhook の Active | チェックを外す |
| Where can this GitHub App be installed? | `Only on this account` |

Permissions の Repository permissions は、次の表のとおりにする。

| 権限 | 値 |
|---|---|
| Contents | `Read & write` |
| Pull requests | `Read & write` |
| Issues | `Read & write` |
| Workflows | `Read & write` |
| Actions | `Read-only` |
| Checks | `Read-only` |
| Commit statuses | `Read-only` |
| Metadata | `Read-only` |

上の表に無い権限と、Account permissions は `No access` のままにする。

> 注意: Actions を `Read & write` にしない。Deployments、Environments、Administration、Secrets を付けない。

2. `Create GitHub App` を押す。開いた App の設定のページ(General)にある `Client ID` を控える
3. 同じページの左の Credentials → Key pairs で `New key` を押す。秘密鍵のファイル(`.pem`)が
   ダウンロードされる。このファイルは再ダウンロードできないので、参加者セットアップで移すまで消さない
4. 同じページの左の `Install App` を開き、自分のアカウントの `Install` を押す。
   `Only select repositories` を選び、Select repositories で `KeirekiPro` だけを選んで `Install` を押す
5. **自分のアカウントの** Settings → Applications → Installed GitHub Apps で、作った App の `Configure` を押す。
   開いたページのアドレス(`https://github.com/settings/installations/<数字>`)の末尾の数字を、
   インストールの番号として控える

控えた3つ(秘密鍵のファイル、`Client ID`、インストールの番号)は、[参加者セットアップ手順](参加者セットアップ手順.md) の
「2-2. PR作成名義の固定(bot専用のgh設定ディレクトリ)」で使う。

### 1-3. 所有者の gh の鍵(fine-grained PAT)の作成

所有者だけが、自分のWindowsのPCで行う。所有者の gh と git は、
ワークフローの起動と承認の権限が無い fine-grained PAT を使う。

gh が入っていなければ、先に [参加者セットアップ手順](参加者セットアップ手順.md) の
「1-1. GitHub CLI のインストールとログイン」のインストールのコマンドで入れる(`gh auth login` は打たない)。

1. **自分のアカウントの** Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → Generate new token で PAT を作る

| 設定 | 値 |
|---|---|
| Token name | 任意(例: `owner-gh`) |
| Expiration | 期限の日付が付くもののうち、選べる最も長いもの |
| Resource owner | 自分のアカウント |
| Repository access | `All repositories` |

Permissions の Repository permissions は、次の表のとおりにする。

| 権限 | 値 |
|---|---|
| Contents | `Read and write` |
| Issues | `Read and write` |
| Workflows | `Read and write` |
| Pull requests | `Read-only` |
| Actions | `Read-only` |
| Metadata | `Read-only` |

上の表に無い権限は付けない。

> 注意: Actions を `Read and write` にしない。Deployments、Environments、Administration、Secrets を付けない。
> Pull requests を `Read-only` から上げない。

2. `Generate token` を押し、表示された PAT をコピーする。コピーしたまま、PowerShell で次を実行して gh にログインする

```bash
Get-Clipboard | gh auth login --with-token
```

3. 次を実行し、`Logged in to github.com account <自分のアカウント名>` と、`github_pat_` で始まる Token が表示されること

```bash
gh auth status
```

4. Git Bash で次の2つを実行し、所有者がどのリポジトリで push しても git が gh の PAT を使うようにする

```bash
git config --global credential.https://github.com.helper ''
```

```bash
git config --global --add credential.https://github.com.helper '!gh auth git-credential'
```

確認は2つとも行う。

1. Git Bash で次を実行し、空の行と `!gh auth git-credential` の2行が出ること

```bash
git config --global --get-all credential.https://github.com.helper
```

2. 所有者が普段のターミナルで、KeirekiPro とほかの自分のリポジトリのそれぞれで次を実行し、成功すること

```bash
git push --dry-run
```

所有者は、PRの承認(Approve)と、本番のワークフローの起動と承認を GitHub の画面で行う。
この PAT は Pull requests が `Read-only` なので、`gh pr review --approve` は通らない。

GitHub から PAT の期限が近いことを知らせるメールが届いたら、所有者は、1 と同じ設定で PAT を作り直し、2 と 3 を行う。

### 1-4. 所有者のPCの前提

所有者は、次の3つを守る。

- 所有者は、Claude in Chrome で、github.com と AWS のコンソールに「常に許可」を出さない。
  Claude がこれらのサイトを操作するときは、1回の操作ごとに許可するかを決める
- 所有者は、Claude Desktop の中のブラウザで、GitHub と AWS にサインインしない
- 所有者は、Claude Desktop を管理者として起動しない

> 注意: この準備では、Claude がワークフローのファイルを足すか変えて push し、そのワークフローに本番のワークフローを
> 起動させる道と、ワークフローの中でリポジトリの秘密に触れる道は塞がない。この2つは #557 で扱う。

ここまで済んだら、[参加者セットアップ手順](参加者セットアップ手順.md) を実施してから
手順2へ進む。

## 2. mainブランチの保護設定

**リポジトリの** Settings → Rules → Rulesets → New ruleset → New branch ruleset で、
`main`(Default)を対象にしたルールセットを作る。

| 設定 | 値 |
|---|---|
| Enforcement status | Active |
| Bypass list | 空(誰も追加しない) |
| Restrict deletions | ✅ |
| Block force pushes | ✅ |
| Require linear history | ✅ |
| Require a pull request before merging | ✅ |
| └ Required approvals | `0` |
| └ Dismiss stale pull request approvals when new commits are pushed | ✅ |
| └ Require review from Code Owners | ✅ |
| Require status checks to pass | ✅ |
| └ Require branches to be up to date before merging | ✅ |

> 注意: Required approvals を `0` から上げない。全PRが承認必須になり自律マージが止まる。

> 注意: `Require branches to be up to date before merging` を有効にするのは、
> `update-pr-branches.yaml` が動く状態になってから。先に有効にすると、
> 先行のPRがマージされるたびに残りのPRが止まる。

あわせて **リポジトリの** Settings → General → Pull Requests:

- Allow auto-merge: ✅
- Allow squash merging: ✅(それ以外は任意でオフ)

## 3. Secrets の登録

最初に、`BOT_GITHUB_TOKEN` に登録するbotのclassic PATを作る。

1. **botアカウントの** Settings → Developer settings → Personal access tokens →
   Tokens (classic) → Generate new token → Generate new token (classic) で
   classic PATを作成する
   - Note: 任意(例: `keirekipro-agent`)
   - Expiration: `Custom` を選び1年後
   - scopes: `repo`、`read:org`、`workflow`

作ったら、画面を閉じずにそのまま 3-1 と 3-2 に登録する。値はどこにも控えない。
所有者は、このPATを `BOT_GITHUB_TOKEN` に登録することにだけ使い、gh のログイン、PCのファイル、環境変数には入れない。

Actions と Dependabot は保管庫が別で、Dependabotが起こしたワークフローからは Actions 側の
secrets を参照できない。3-1 と 3-2 の両方に登録する。

### 3-1. Actions secrets

**リポジトリの** Settings → Secrets and variables → Actions に登録する。

| Secret | 値 | 失効したとき |
|---|---|---|
| `OPENAI_API_KEY` | OpenAIダッシュボードで発行したAPIキー | codex-reviewが失敗し全PRがマージ不能になる。再発行して差し替える |
| `BOT_GITHUB_TOKEN` | 手順3の冒頭で作成したbotのclassic PAT | 月次のカナリア生成と、PRへの自動マージの予約が失敗する。復旧は「botのPATが期限切れになったときの復旧」に従う |

> 注意: PATの有効期限をカレンダーに登録する。

### 3-2. Dependabot secrets

**リポジトリの** Settings → Secrets and variables → Dependabot に登録する。
3-1 と同じ名前・同じ値を使う。

| Secret | 値 | 失効したとき |
|---|---|---|
| `BOT_GITHUB_TOKEN` | 手順3の冒頭で作成したbotのclassic PAT(3-1と同じ値) | PRのブランチが最新化されず、out-of-date のまま滞留する |

登録と確認は GitHub の画面で行う。所有者の gh の鍵(手順1-3)は Secrets の権限を持たないので、`gh secret set` では登録できない。

> 注意: 登録せずに `update-pr-branches.yaml` をマージすると、最新化が失敗しても
> DependabotのPRは赤にならず、静かに滞留する。鍵の登録 → ワークフローのマージ、の順で行う。

## 4. cc-sdd の導入

spec駆動開発のコマンド(`/kiro-*`)とテンプレートを生成する。リポジトリルートで実行する:

```bash
npx cc-sdd@latest --claude-skills --lang ja
```

生成物は `.claude/skills/kiro-*/` と `.kiro/settings/` に置かれる。これらはリポジトリに
コミットするため、参加者が各自インストールする必要は無い。

> 注意: このリポジトリの導入版には本家からの改造が入っている(`/kiro-spec-init` の引数を
> feature名でなく説明文にする等)。バージョンを更新するときは `--dry-run` で差分を確認し、
> 改造点を上書きしないこと。

## 5. steering の初期生成

steering(`.kiro/steering/`)は、spec作成時にAIが参照するプロジェクト知識。
無いままアプリ機能のspecを書くと、プロダクト知識の不足が要件の質に直結する。

Claude Code のセッションで次を実行する:

```
/kiro-steering
```

`.kiro/steering/` に `product.md`(プロダクト知識)・`tech.md`(技術スタック)・
`structure.md`(構成パターン)が生成される。内容がプロジェクトの実態と合っているかを
確認し、コミットする。

以降の更新も同じコマンドで行う(既存のsteeringがある状態では、コードとの差分を検出して
追記する同期モードで動く)。

## 6. 検証用PRで各ゲートが赤くなるかの確認

frontend・backendの両方に軽微な変更を含む検証用PRを**下書き(Draft)で**作成し、各チェックを一度発火させる。
次を仕込み、対応するチェックが赤くなることを確認する。

| 仕込む内容 | 赤くなるチェック |
|---|---|
| frontendの既存モジュールに、テストが通らない分岐を足してカバレッジを閾値未満にする | `frontend-test` |
| テストに `.skip` を足す | `escape-hatch` |
| 依存パッケージを1つ追加する | `dependency-gate` |
| PRに `pre-merge-check` ラベルを付ける | `pre-merge-check` |

> 注意: `gitleaks` と `size-check` はこの手順では確認しない。

あわせて確認すること:

- 依存を足したPRで、所有者がApproveすると `dependency-gate` が緑に変わる
- ローカルで次を実行し、マイグレーションの一覧とStateが表示される

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```

> 注意: 検証用PRは下書きのままにする。下書きでないPRには `auto-merge.yaml` が自動マージを予約し、
> マージできる状態になった時点でマージされる。確認後はクローズしてブランチを削除する。

> 注意: `codex-review` は下書きのPRでは動かない。`codex-review` の確認は、手順7の検証用PRで行う。

## 7. Required status checks の指定

**リポジトリの** Settings → Rules → Rulesets → `main` を開き、Require status checks to pass に
次の20本を指定する。

- `detect-changes`
- `frontend-test`
- `backend-test`
- `e2e-smoke`
- `docker-smoke`
- `detect-terraform-changes`
- `terraform-static`
- `gradle-wrapper`
- `escape-hatch`
- `size-check`
- `gitleaks`
- `dependency-gate`
- `pre-merge-check`
- `codex-review`
- `dependency-graph-generate`
- `dependency-graph-submit`
- `dependency-review`
- `dependency-cooldown`
- `container-scan-script-tests`
- `container-scan`

> 注意: ここに挙げたもの以外を追加しない。

指定後、次を実行して20本が揃っていることを確認する。

```bash
gh api repos/:owner/:repo/rules/branches/main \
  --jq '.[] | select(.type=="required_status_checks")
        | .parameters.required_status_checks[].context'
```

`dependency-graph-generate` `dependency-graph-submit` `dependency-review` `dependency-cooldown`
の4つは、mainへのpushで `dependency-graph-main` が1回成功したのを確認してから追加する。
一度も報告されていないチェック名を指定すると、Pending のまま残り全PRが保留になる。

`container-scan-script-tests` と `container-scan` は**登録の時期が異なる**。

- `container-scan-script-tests` は、PRで一度成功を報告したのを確認してから追加する。
  判定スクリプトの変更が単体テストを一度も通らずにmainへ入る経路を塞ぐためのもので、
  本番イメージの脆弱性の有無には左右されない
- `container-scan` は、**検出が0件になってから追加する。** 修正版のある CRITICAL / HIGH が
  イメージに残っている間に登録すると、本番イメージまたは backend を触る全PRが止まる。
  0件になったことを実際のPRの `container-scan` の実行結果で確認してから追加する。
  このリポジトリでは、2026-09-25 に PR #366 の実行結果(マージを止めるもの0件、抑制0件)を
  確認してから登録した(Issue #221)

指定後、もう一度小さな検証用PRを作り(こちらは下書きにしない)、必須チェックが効いた状態でマージまで通ることを確認する。
auto-merge は `auto-merge.yaml` が自動で予約する。人間は予約しない。

このPRで、あわせて次を確認する。

- `codex-review` のレビューコメントがPRに付き、VERDICTの判定どおりにチェックが緑/赤になる
- `codex-review` の実行ログで、モデルが `gpt-5.6-terra`、reasoning が `high` になっている

## 8. PRブランチの自動最新化の確認

`update-pr-branches.yaml` は mainへのpushと、main向けのPRを出したとき(`pull_request`)に発火し、PRのブランチを最新化する。
手順3-2で登録した `BOT_GITHUB_TOKEN` を使う。

検証用PRを2本作り(どちらも下書きにしない)、1本目がマージされてから次を確認する。
どちらのPRにも `auto-merge.yaml` が auto-merge を予約するため、人間は予約もマージもしない。

- 2本目のブランチが人間の操作なしに最新化される
- 最新化のあと必須チェックが再実行され、auto-mergeでマージされる

> 注意: `GITHUB_TOKEN` に切り替えない。`GITHUB_TOKEN` によるpushは後続のワークフローを
> 起動しないため、ブランチを最新化しても検査が再実行されず、必須チェックが古いSHAの
> ままになってマージできない。

最新化されないPRが残るときは [監査手順](監査手順.md) に従う。

## 9. Dependabot の有効化

9-1 から順に実施する。

### 9-1. 依存グラフとアラートの有効化

**リポジトリの** Settings → Advanced Security で、この順に Enable にする。
すでに Enable 済みの項目は `Disable` ボタンが出ているので、その場合は何もしない。

1. **Dependency graph**
2. **Automatic Dependency Submission**
3. **Dependabot alerts**

Automatic Dependency Submission は有効化した時点で自動実行される。
Actions タブでその実行が完了したことを確認してから、
Insights タブ → Dependency graph → Dependencies を開き、
`backend/build.gradle` が一覧にあることを確認する。

以後は、依存マニフェスト(`backend/build.gradle` 等)を更新した main への push で再実行される。

> 注意: ここに `backend/build.gradle` が現れないと、backendの脆弱性が検知されない。
> また 1 と 3 は 9-4 の前提でもあり、無効のままだと security updates を有効にできない。

### 9-2. version updates が有効になっているかの確認

**リポジトリの** Settings → Advanced Security を開き、**Dependabot version updates** の項目を見る。

- ボタンが **Configure** になっていればよい(押すと `.github/dependabot.yml` が開く)
- ボタンが **Enable** の場合は押す

version updates で作成されるのは backend(Gradle)・frontend(npm)・Dockerのベースイメージ・
GitHub Actions のアクションのPR。

> 脆弱性修正のPRは、9-4 の security updates を有効にすると作成が試みられる。
> version updates の対象かどうかとは別に動く。
> 実際に作成されるかは、そのアラートが修正可能かによる。

### 9-3. DependabotのPRがチェックを通るかの確認

最初に作成されたPRで確認すること:

- 保留のまま止まる必須チェックが無い
- `codex-review` がスキップ扱いになっている
- auto-merge が予約されている(`dependabot-auto-merge.yaml` が自動で予約する。人間は予約しない)

backend(Gradle)と frontend(npm)のPRは `dependency-gate` が赤になる。依存定義ファイルの
変更は中身によらず承認対象のため。内容を確認してApproveすると緑に変わる。
GitHub Actions のPRは `dependency-gate` が緑のままになるが、`.github/` の変更のため
Code Owners の承認までマージされない。

必要な承認が揃うと、人間の操作なしにマージされる。DependabotのPRは
今後もこの運用になる。

### 9-4. security updates の有効化

**リポジトリの** Settings → Advanced Security で、この順に操作する。

1. **Dependabot security updates** を Enable にする
2. **Grouped security updates** を Enable にする

> 注意: Grouped security updates は、Dependabot security updates が有効でないと設定できない。
> 1と2の間に作成されたPRは個別に立つため、2は続けて操作する。

ここまで確認できれば、基盤構築は完了。

## botのPATが期限切れになったときの復旧

セットアップ後の障害対応。上から順に実施する。

### 症状

- 月次のカナリア生成が失敗する
- PRに自動マージの予約が付かない
- PRのブランチが最新化されず、out-of-date のまま滞留する

### 復旧手順

1. **botアカウントの** Settings → Developer settings → Personal access tokens →
   Tokens (classic) で該当トークンを `Regenerate` する
   - Expiration: `Custom` を選び1年後

2. **リポジトリの** Settings → Secrets and variables で `BOT_GITHUB_TOKEN` を新しい値に
   更新する。**Actions と Dependabot の両方**(手順3-1・3-2)。Dependabot 側を忘れると、
   PRのブランチが最新化されず、out-of-date のまま滞留する

3. 所有者は、手順3の冒頭と同じく、PATの値を gh のログイン、PCのファイル、環境変数に入れず、どこにも控えない

4. 次に作られたPRに、自動マージの予約が付くこと

## App の秘密鍵を作り直すとき

セットアップ後の障害対応。上から順に実施する。
秘密鍵のファイルを失くしたとき、秘密鍵が漏れたおそれがあるとき、Claude の gh が App のトークンを入れられずに止まったときに行う。

### 症状

- Claude の gh が 401 で失敗し、トークンを入れ替えるフックが「GitHub App のトークンを入れ替えられなかった」と出す

### 復旧手順

1. **自分のアカウントの** Settings → Developer settings → GitHub Apps で、手順1-2で作った App の `Edit` を押す。
   左の Credentials → Key pairs で `New key` を押し、ダウンロードされた秘密鍵のファイル(`.pem`)を受け取る

2. ホストOSのターミナルで、ダウンロードしたファイルを `.gh-bot` の秘密鍵のファイルに上書きする。
   `<秘密鍵のファイル>` は、ダウンロードしたファイルのパスにする

   Windows(PowerShell):

```bash
Move-Item -Force "<秘密鍵のファイル>" "$env:USERPROFILE\.gh-bot\github-app.private-key.pem"
```

   macOS/Linux:

```bash
mv -f "<秘密鍵のファイル>" "$HOME/.gh-bot/github-app.private-key.pem"
```

3. 同じ端末に限って `GH_CONFIG_DIR` を設定し、リポジトリルートで App のトークンを入れる。何も出力されずに終わればよい

   Windows(PowerShell):

```bash
$env:GH_CONFIG_DIR = "$env:USERPROFILE\.gh-bot"
```

```bash
& "C:\Program Files\Git\bin\bash.exe" .claude/scripts/github-app/refresh-token.sh --force
```

   macOS/Linux:

```bash
export GH_CONFIG_DIR="$HOME/.gh-bot"
```

```bash
bash .claude/scripts/github-app/refresh-token.sh --force
```

4. 同じ端末で次を実行し、KeirekiPro のリポジトリの説明が表示されること

```bash
gh repo view DogisRiki/KeirekiPro
```

5. 1 の Key pairs で、古い鍵の右の `Delete` を押し、確認の画面でも `Delete` を押す

6. Claude Codeを再起動し、エージェントに「`gh repo view DogisRiki/KeirekiPro` を実行して結果を報告して」と
   依頼して、KeirekiPro のリポジトリの説明が返ること
