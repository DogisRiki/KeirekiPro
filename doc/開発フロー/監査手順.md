# 監査手順

人間がコードを読む代わりに行う、仕組みの点検のチェックリスト。
週次・月次・半期の各項目を上から順に実行する。

> 数値の目安のうち「初期値の提案」と付けたものは、運用実績に合わせて調整する。
> 変えた場合はこの文書を書き換えること。

## 用語

| 用語 | 意味 |
|---|---|
| review-loop | レビュー担当AI(Codex)の指摘にClaude Codeが対応する修正ループ。往復の記録はPRコメントに残る |
| codex-overruled | Codexの指摘をClaude Codeが誤検知と判定して退けたPRに付くラベル |
| guardrails | PRごとに検査回避・差分サイズ・シークレット混入などを検べるワークフロー(guardrails.yaml) |
| escape-hatch | テストの無効化などの検査回避を検知するCIチェック |
| dependency-gate | ライブラリの入手先や防御設定の変更を承認対象として止めるチェック。所有者がApproveすると成功に変わる |
| カナリアPR | 検査が検知できるはずの問題をわざと含めた健康診断用のPR。毎月1日に6件自動生成され、毎月4日に canary-verify.yaml が照合する(closeとブランチ削除は翌月の生成側が自動で行う) |
| mutation testing | わざとコードを壊してテストが失敗するかを見て、テストの実効性を測る仕組み。毎週土曜に自動実行される |
| retrospective | チェックをすり抜けた問題を仕組みの改善につなげる振り返りのIssue(同名のラベルが付く) |

## 監査の通知Issueを受けたとき

週次監査(`audit-weekly.yaml`)とカナリア照合(`canary-verify.yaml`)の結果は、Issueで届く。
監査が逸脱を見つけたときと、監査そのものが正しく動かなかったときの両方でIssueが作られ、
所有者が担当者に割り当てられ、本文の冒頭で所有者にメンションが付く。
定期的にActionsタブを開いて実行結果を見に行く必要は無い。

### なぜワークフローの失敗通知ではなくIssueで届けるのか

GitHubの定期実行(`schedule`)の失敗通知は、そのワークフローのcronの記述を最後に書き換えた利用者にしか届かない
(公式ドキュメント: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows )。
監査のワークフローを書いたのはbotのアカウントであり、実行が失敗しても所有者には何も届いていなかった。
2026-09 に週次監査が2回続けて失敗したまま約2週間誰も気づかなかったのはこのためで、
以後は結果をIssueで知らせる形に改めた(#347)。

### 届くIssueの種類

どのIssueにもラベル `audit` が付く。タイトルは次の4種類に決まっていて、同じタイトルのIssueは1件だけ開いた状態で持つ。

| タイトル | 意味 | 実行の結果 |
|---|---|---|
| `週次監査: 逸脱あり` | 週次監査が、所有者の対処を待つ問題を見つけた | 成功(緑) |
| `週次監査: 判定不能` | 週次監査そのものが正しく動かず、問題の有無を確かめられなかった | 失敗(赤) |
| `カナリア照合: 逸脱あり` | 月次のカナリアPRで、検査が期待どおりに問題を検知しなかった | 成功(緑) |
| `カナリア照合: 判定不能` | カナリア照合そのものが正しく動かず、照合できなかった | 失敗(赤) |

表の「実行の結果」は、結果をIssueへ反映できた場合のもの。どの結果でも、Issueへの反映が失敗したときは
実行が赤で終わる(「受容した残余リスク」の6)。

逸脱ありのときに実行が緑で終わるのは、PRのCIを止めないため。PRのCIは週次監査が10日以内に
完了しているかだけを確かめており、逸脱が見つかったこと自体ではPRは止まらない。

### 逸脱ありのIssueを受けたとき

1. Issue本文の報告を読む。判定項目ごとに、対象のPR番号・チェック名・判定の根拠が載っている。
   所有者の承認待ちだけで止まっているDependabotのPRは逸脱として扱わず、同じ報告の中に「承認待ち」の一覧として出る
2. 報告の項目に応じて、この文書の該当する節の対処に従う
   - 定期スキャンが止まっている: 週次監査の項目8
   - Dependabotの滞留: 週次監査の項目6
   - カナリアの検知漏れ・カナリアPRの欠落: 月次監査の項目1
   - 期待一覧とrulesetの必須チェックが一致しない: 報告に「期待一覧のみに存在」「rulesetのみに存在」の
     チェック名が出る。期待一覧(`.github/audit/required-checks.json`)と、GitHub側の設定
     (Settings → Rules → Rulesets → `main` の必須チェック)のどちらが正しいかを判断し、
     ずれを解消する。期待一覧を直す場合はIssueで指示する。例文: 「週次監査で、期待一覧にしか無い必須チェック `xxx` が報告された。rulesetから外したのが正しいので、`.github/audit/required-checks.json` から削除してほしい」。
     rulesetの側を直す場合は、所有者が画面で設定を戻す
   - 必須チェックがスキップのままマージされたPRがある: 報告にPR番号とチェック名が出る。
     常に実行されるはずのチェックが、実行されないままマージされたことを意味する。
     Issueで原因の調査と是正を指示する。例文: 「週次監査で、#123 が必須チェック `xxx` をスキップしたままマージされたと報告された。スキップの原因(設定・変数・ワークフローの故障)を調べて直してほしい」。
     意図的に止めているチェックは、期待一覧で停止中として記録すれば(`state` を `paused` にし、理由と参照Issueを書く。codex-review が実例)違反として扱われなくなり、報告の「停止中と記録されている必須チェックのスキップ」に出る
3. 対処が要るものは、新しいIssueを起票して指示する。例文は各節にある

### 判定不能のIssueを受けたとき

判定不能は、監査の仕組みの故障を意味する。この状態の監査は逸脱を見つけられないため、先に直す。

1. Issue本文の報告で、判定できなかった項目と理由を読む。本文の実行へのリンクから実行ログも開ける
2. 一時的な失敗(APIの一時的なエラーなど)が疑われるときは再実行する。再実行の方法は監査の種類で違う
   - **週次監査**: 失敗した実行を開き、**Re-run で再実行する。新規の手動実行(Run workflow)は使わない。**
     スキップのままマージされたPRの確認は、前回の実行(結果を問わない)から今回の実行までの期間を対象にしている。
     新規に手動実行すると、失敗した実行が前回として扱われ、失敗した実行が受け持つはずだった期間が確認されないまま残る。
     Re-run なら同じ実行として流し直すので、期間はずれない
   - **カナリア照合**: Re-run と新規の手動実行(Actions → Canary Verify → Run workflow)のどちらでもよい
3. 再実行しても判定不能が続くときは、報告の理由を添えてIssueで原因の調査と修正を指示する。例文: 「週次監査が判定不能のまま続いている。`週次監査: 判定不能` のIssueの報告を見て原因を調べ、修正してほしい」

### Issueの閉じ方と追記

- **人間はこのIssueを閉じない。** 次の実行で問題が解消していれば、解消したことを追記して自動で閉じる。
  逸脱ありのIssueは逸脱が無くなったとき、判定不能のIssueは監査が正しく動いたときに閉じる
- 同じ問題が続いている間は、新しいIssueは作られず、開いているIssueに実行のたびに追記が1件ずつ増える。
  **Re-run で再実行したときも追記が1件増える。これは正常な動作で、重複ではない**
- 判定不能の間は、逸脱ありのIssueには触らない(問題の有無が分からないため、閉じも追記もしない)
- 担当者の割り当てが付かないことがある(GitHub側で黙って無視される場合がある)。その場合も本文のメンションで通知は届く

### 導入時の受信確認

Issueで届く仕組みを入れたPR(#347)のマージ後に、一度だけ次を確認する。

1. Actions → Audit Weekly → Run workflow で、週次監査を手動実行する
2. 導入時点では Dependabot の #342・#346 が止まっているため、結果は逸脱ありになる。
   `週次監査: 逸脱あり` のIssueが作られ、実行が緑で終わることを確かめる
3. そのIssueについて、GitHubの通知(通知一覧またはメール)が所有者に届いたことを確かめる
4. Issueの担当者に所有者が付いているかを見る。付いていなければ、本文のメンションが代わりの経路になっているかを確かめる
5. 所有者のアカウントで、このリポジトリのWatch設定を確かめる。担当者とメンションの両方が届かなかったときに残る経路はWatchだけになる(下の「受容した残余リスク」の8)

### この仕組みで捉えられないこと

「受容した残余リスク」の6〜8を読む。要点は、通知のIssue操作そのものが失敗したときは通知が出ないこと。

## 週次監査(目安5分。項目6・8は自動化済みで、Issueが届いたときだけ対処する)

### 1. Claude Codeの利用量の確認

なぜ: ループの暴走や作業の無駄な膨らみは、トークン消費の内訳の偏りに表れる。

- **どこを開くか**: Claude Codeのセッションで `/usage` を実行する
- **何を見るか**: トークン使用量の内訳(スキル・サブエージェント・MCP別)の偏り
- **正常の目安**: 1つの項目が全体の半分を超えておらず、心当たりのない項目が上位に入っていない(初期値の提案)
- **異常時の行動**: 半分を超えた項目・心当たりのない項目について、次のいずれかを行う
  - ゴール駆動コマンド(/goal-implement 等)なら、渡す対象を1画面・1テストファイル単位に絞る
  - 定期ループなら `/loop` の実行間隔を伸ばす(例: 30分を60分にする)
  - 解消しなければIssueを起票して指示する。例文: 「定期ループのトークン消費が内訳の半分を超えている。`.claude/loop.md` の手順から設計図の乖離確認を外して、消費を減らしてほしい」

### 2. レビューのやり直し回数の確認(廃止)

2026-09-06 に #310 の判定で廃止した。上限5往復は `codex-review.yml` が機械強制しており、
打ち切りはCIの失敗として現れる(イベント駆動)。定期的に開いて数える作業は行わない。
打ち切りに達したPRへの対処(仕様の差し戻し・タスク分割・PR破棄のいずれかを指示し、
PRを閉じて新しいブランチでやり直す)は、通知が来たときにこの節の履歴を参照する。

### 6. DependabotのPRが滞留していないかの確認(自動化済み)

2026-09-06 に #310 の自動化へ移行した。`audit-weekly.yaml` が毎週月曜に、必須チェックが
failure / cancelled / timed_out / action_required で止まっているDependabot PRを検知し、
`週次監査: 逸脱あり` のIssueで知らせる(「[監査の通知Issueを受けたとき](#監査の通知issueを受けたとき)」)。
所有者の承認待ちだけで止まっているPR(dependency-gate / escape-hatch / pre-merge-check の赤)は
異常として扱わず、「承認待ち」の一覧として報告に出る。定期的にPR一覧を開く作業は不要。
以下は、逸脱のIssueで滞留が報告されたとき・承認するときに読む対処手順として残す。

- **承認待ちのGitHub ActionsのPRをApproveするとき**: `.github/` はCODEOWNERS保護のため所有者のApproveが要る。差分が `uses: owner/repo@<40桁のSHA> # vX.Y.Z` の形のまま、SHAとコメントの両方が書き換わっていることだけ確認してApproveする。タグ参照(`@v6` など)に戻っていたらApproveせず、Issueで指示する。コードは読まない
- dockerのPRに `@dependabot rebase` を使ってはいけない(理由は下の「dockerのPRをcloseしない」)
- frontendのPRが `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` で落ちている場合は、公開から72時間経てば解消する。Issueは起票せず、時間をおいてチェックを再実行する
- 上記以外の理由で滞留が報告されたときは、原因を見てIssueで指示する。例文: 「Dependabotの #45 が frontend-test で落ちている。原因を調べて対応してほしい」
- **自動検知の対象外**(気づいたときに見る): アラートが残っているのにPRが作られていない場合は、Security → Dependabot alerts で該当アラートのエラー内容を確認する。修正可能な版が無い、または依存解決ができないものにはPRが作られないため、通常のPRで対応する(Insights → Dependency graph → Dependabot は version updates のジョブログで、用途が違う)

#### ブランチが最新化されずに止まったとき

PRは `Require branches to be up to date` により、mainが進むと out-of-date になって
マージできなくなる。`update-pr-branches.yaml` がmainへのpushで自動的に最新化する。

- **何を見るか**: 「This branch is out-of-date with the base branch」で止まっているPRと、
  Actionsタブの `Update PR Branches` の直近の実行結果
- **正常の目安**: out-of-date のまま止まっているPRが無い
- **異常時の行動**:
  - `Update PR Branches` が赤なら、実行ログの警告を読む。
    `BOT_GITHUB_TOKEN` の失効が最も多い原因で、その場合は手順に従って登録し直す
  - 衝突しているPRは自動では最新化できない。警告に出るので、内容を見てIssueで指示する
  - 特定のPRだけが最新化されない場合は、PR画面の **Update branch** を押して切り分ける
  - 急いでマージしたい場合は、Settings → Rules → Rulesets → `main` で
    `Require branches to be up to date` を一時的に外す。他の必須チェックは効いたまま

#### dockerのPRをcloseしない

**closeすると、そのイメージの更新が恒久的に止まる。復旧経路は限られている。**

Dependabotは `イメージ名 + タグ + ディレクトリ` を照合キーにしており、digestを見ていない。`eclipse-temurin:21-jre` のようにタグが動かないイメージでは、一度closeするとその後の別digestへの更新PRも同じキーとしてブロックされ続ける。`@dependabot recreate` と `rebase` はcloseされたPRには効かず、`@dependabot reopen` コマンドは2026-01-27に廃止された。

closeしてしまった場合、PRのブランチが残っていて(削除済みならRestore branchで復元して)マージ済みでもなければ、**GitHubの標準UIでPRをReopenし、openになったPRに `@dependabot recreate` とコメントする**ことで復旧できる。Reopen自体をGitHubが拒否する場合は行き止まりになる。

開いたまま放置するのも解決にならない。定期ジョブは「同じキーのPRが既にある」と判断して打ち切るため、開いているPRが新しいdigestに更新されることはない。

赤で止まったときの出口は次の2つ。**どちらもcloseを含まない。**

| 出口 | 手順 | 使いどころ |
|---|---|---|
| A(既定) | 上流に新しいベースイメージが出て、**その公開から3日以上経ってから** PRに `@dependabot recreate` とコメントする。最新のdigestに更新されて緑になったらマージする | 通常はこちら |
| B | `.github/container-scan-suppressions.json` に期限付きの抑制を1件足してマージする。判断基準は「[コンテナイメージの脆弱性が見つかったときの手順](#コンテナイメージの脆弱性が見つかったときの手順)」を読む | 上流の修正を待てない場合 |

**出口Aの3日待ちは厳守する。早打ちは「何も起きない」では済まない。** 公開から3日(Dependabotの既定のクールダウン)以内に `@dependabot recreate` を打つと、Dependabotは依存を最新と判定し、**開いているPRを自らcloseする**。closeは上記のとおり更新停止に直結するため、必ず3日待ってから打つ。`@dependabot rebase` も内部では同じ処理を通るため同様に危険で、dockerのPRのブランチ最新化にはコメントコマンドではなくPR画面の **Update branch** ボタンを使う。

**マージを保留したいときはauto-mergeの解除で行わない。** 解除してもDependabotのpushで予約が付け直される。保留は pre-merge-check ラベルをPRに付けて行う(必須チェックが赤になり、予約が残っていてもマージされない)。

#### 脆弱性以外の理由で赤くなっている場合

上の出口A・出口Bは、**脆弱性が見つかって赤くなったPRをどう終わらせるか**の2択である。
`container-scan` が赤いときは、まずそのどちらの話なのかを見分ける。

- **どこを見るか**: `container-scan` ジョブの実行結果の要約と `::error::` の注釈

| 赤の理由 | 見分け方 | 対応 |
|---|---|---|
| 脆弱性を検出した | `修正版のある CRITICAL / HIGH の脆弱性が N 件あります。` の注釈がある。要約に脆弱性の表が出ている | 出口A または 出口B |
| 検査そのものができなかった | `終了コード 2` の注釈がある。要約に表が無い、またはアーキテクチャ不一致の表が出ている | 下の切り分けを読む |
| Trivy の版が指定と違う | ビルドの前のステップで落ちている | 2本のワークフローの `env.TRIVY_VERSION` が揃っているかを見る。片方だけ更新されている場合は揃える(食い違いは週次監査でも検知される) |
| 組み立てに失敗した | 組み立てのステップで落ちている | 通常のビルド失敗と同じ。ベースイメージの取得がレート制限で失敗した場合は再実行で解消する |
| 30分を超えた | ジョブがタイムアウトで打ち切られている | 再実行して再現するかを見る。再現するなら実行時間の内訳をIssueで報告し、上限の見直しを判断する |

**「検査そのものができなかった」の切り分け**は3つある。いずれもIssueで指示する。

- **抑制の記録が読めない・記録の不備**: `.github/container-scan-suppressions.json` の
  必須項目(`id` / `reason` / `expires`)の欠落、日付の形式違反、識別子の重複。
  注釈にどの記録の何が悪いかが出る
- **検査対象のアーキテクチャが期待と違う**: 本番と別の実行環境向けのイメージを検査している。
  ビルドの指定が変わっていないかを見る
- **Trivy の出力の形が変わった**: スキーマの変更を疑う。Trivy の版を上げた直後であれば
  まずそれを疑う

#### 実行を手動でキャンセルした場合は、再実行しないと先に進まない

`container-scan` は実行が長い(本番イメージの組み立てを含む)ため、手で止めたくなる場面がある。
**止めても緑にはならない。** キャンセルされたジョブは `cancelled` として報告され、
必須ステータスチェックとしては成功にならない(2026-08-20 実測)。
検査の実行中に止めた場合も、始まる前に止めた場合も同じだった。

ただし**そのあとに再検査を発火させるイベントが無い。** 放置すると赤のまま止まり続ける。

新しいコミットを積んだときの自動キャンセルは、新しい実行がチェックを引き継ぐので問題にならない。
close→reopen もトリガに `reopened` を含めているため再検査される。

- **どうするか**: 手動でキャンセルしたら、**`container-scan` を再実行する。**
  Actionsタブの該当 run から Re-run すればよい
- 自律側(Claude Code)にはキャンセルを禁止している(CLAUDE.md)

### 7. Medium以下の指摘だけで通ったPRの抜き取り確認(凍結中)

2026-09-06 に #310 の判定で凍結した。codex-review が停止中(#166)で母数が無い。
codex-review を再開したら、この節の本文をgit履歴から復元して再開する。

### 8. 稼働中イメージの脆弱性監視が動いているかの確認(自動化済み)

2026-09-06 に #310 の自動化へ移行した。`audit-weekly.yaml` が毎週月曜に、定期スキャン
(Scheduled Container Image Vulnerability Scan)の直近の成功が8日以上無ければ、
`週次監査: 逸脱あり` のIssueで知らせる
(「この実行が止まっても普段のPRは緑のまま進む」ため、止まったこと自体を検知する)。
定期的にActionsタブを開く作業は不要。以下は逸脱のIssueでこの項目が報告されたときの対処手順として残す。

- **結論は脆弱性の有無に左右されない。** 表しているのは「稼働中のイメージを特定し、取得し、
  検査を完走できたか」だけ。脆弱性が見つかった週も `success` で終わる。
  `failure` はイメージの特定・取得の失敗か、検査そのものができなかったことを意味する
- **逸脱のIssueでこの項目が報告されたときの行動**:
  - 成功が無いだけで実行はある(遅延・失敗): 直近の実行ログを見る。実行自体が無い場合は
    `workflow_dispatch` で手動実行する(`schedule` は混雑時に遅延・スキップされる)。
    手動実行も失敗する場合はIssueで指示する
  - `failure` で終わっている: 実行ログの `::error::` を読む。**イメージを特定できない・
    取得できない場合と、検査を完走できなかった場合の2つがある。**
    ECRのライフサイクルは最新5世代しか保持しないため、デプロイが続いた週は
    稼働中イメージがECRから消えていることがある。この場合は取得の失敗として現れる
  - **`failure` の週は脆弱性のIssue(ラベル `container-vuln`)が一切更新されていない。** これは設計どおり。検査できなかった
    ことを検出0件と取り違えて未解消のIssueを閉じないための挙動

#### 起票されたIssueの扱い

検出した脆弱性は、識別子ごとに1件のIssueとして自動で起票される(タイトルは
`コンテナ脆弱性: <識別子>`、ラベルは `container-vuln`)。**人間はこのIssueを閉じない。**

| 状態 | 週次の動作 |
|---|---|
| 新しく検出された | 起票する |
| 前週から続いている | 同じIssueに今回の検出結果を追記する |
| 止める対象から外れたが、イメージにはまだある | 追記のみ。**閉じない** |
| イメージから検出されなくなった | 解消を記録して閉じる |

3行目が重要で、修正版の情報が撤回されたり深刻度が下げられたりすると、その識別子は
止める対象から外れるが脆弱性はイメージに残っている。ここで閉じると追跡が消える。

- **自動で閉じなかった場合**: 脆弱性がまだイメージに残っている。閉じずに、解消の見込みを
  Issueに書く。上流のベースイメージ待ちであれば、Dependabot の docker レーンが digest 更新の
  PRを出すのを待つ(こちらから何かする必要は無い)
- **タイトルが規約の形でないIssue**: 週次は操作せず警告だけを出す。人手でタイトルに
  追記したIssueが対象になる。**追記した文字を消すと、次回から自動で扱われるようになる**

## 月次監査(目安10分。項目1は自動化済みで、Issueが届いたときだけ対処する)

### 1. わざと問題を入れたPRで、検査が機能しているかの点検(自動化済み)

2026-09-06 に #310 の自動化へ移行した。`canary-verify.yaml` が毎月4日(生成の3日後)に、
カナリアPR6件それぞれの期待チェックの結論を3値で照合し、逸脱があれば
`カナリア照合: 逸脱あり` のIssueで知らせる(「[監査の通知Issueを受けたとき](#監査の通知issueを受けたとき)」)。
照合の結果は次のとおり報告される:

- `failure` → 正常(検査が問題を検知した)
- `success` → **実行されたが検知しなかった(判定側の故障)**
- `skipped`・実行なし → **検査が実行されていない**(判定側の故障とは区別して報告される)
- 6件そろっていない場合は生成側の異常として報告される

種別ごとの期待チェックの対応表は照合スクリプト(`.github/scripts/check-canary-results.sh`)が
定数として持つ。停止中と記録された期待チェック(現在は codex-review、#166)は失敗と区別して
「停止中(記録済み)」と報告される。定期的にPRを開いて見比べる作業は不要。
「判定側の故障」「実行されていない」「6件そろっていない」は、いずれも `カナリア照合: 逸脱あり` のIssueの報告に出る。
照合そのものができなかったとき(APIの失敗など)は、別の `カナリア照合: 判定不能` のIssueになる。
以下は逸脱のIssueを受けたときの対処として残す。

- **報告に「判定側の故障」「実行されていない」が出ているとき**: どちらも検出漏れとして扱い、Issueで原因分析と検査強化を指示する。例文: 「今月のカナリアで known-bug が検知されなかった。原因を分析し、検査強化のIssueを起票してほしい」
- **報告に「6件そろっていない」が出ているとき**: カナリアの生成側が動いていない。`canary.yaml` の実行結果と `BOT_GITHUB_TOKEN` の有効期限を確認する
- **container-vuln では `docker-smoke` も同時に走る**(`Dockerfile.prod` を変更するため)。期待する失敗は `container-scan` だけで、`docker-smoke` は緑が正常
- **vulnerable-dep の検出漏れの切り分け**: 経路の断絶(生成・送信・取り込み・比較のどこか)と、カナリアの失効(アドバイザリの取り下げ・格下げ)の2つがある。`gh api "/advisories?ecosystem=maven&affects=org.apache.pdfbox:pdfbox"` で該当のアドバイザリが残っているかを先に見る。残っていれば経路の断絶、消えていれば版を選び直す
- **後始末は不要**。カナリアPRのcloseとブランチ削除は、翌月の生成側が自動で行う

### 2. テストが本当にバグを見つけられるかの測定結果の確認

なぜ: カバレッジが高くても、バグを検知できないテストでは意味がない。

- **どこを開くか**: GitHubのActionsタブ → 「Mutation Report」の最新実行 → Artifacts(stryker-report / pitest-report)
- **何を見るか**: frontend(Stryker)とbackend(PIT)それぞれの全体スコア
- **正常の目安**: 前月から5ポイント以上下がっていない(初期値の提案)
- **異常時の行動**: 5ポイント以上下がっていたらIssueで指示する。例文: 「backendのmutationスコアが72%から64%に低下した。レポートで検知漏れが集中しているdomain層の該当クラスに、壊した箇所を検知できるテストを追加してほしい」

### 3. すり抜けた問題の改善Issueが放置されていないかの確認(廃止)

### 4. 自動更新の対象外になっているバージョン固定の確認

なぜ: 次の2つはDependabotが構造的に検知できず、誰も見なければ永久に古いまま残る。

- **どこを開くか**: 下の表の各ファイルと、それぞれの最新版

| 固定しているもの | 書いてある場所 | 最新版の調べ方 |
|---|---|---|
| checkov | `docker/terraform/Dockerfile` の `pip install checkov==...` の行 | https://pypi.org/project/checkov/ |
| tflint | `docker/terraform/Dockerfile` の `COPY --from=ghcr.io/terraform-linters/tflint:...` の行 | https://github.com/terraform-linters/tflint/releases |
| Trivy | `.github/workflows/container-scan.yaml` と `.github/workflows/container-scan-scheduled.yaml` の `env.TRIVY_VERSION`(**2本とも**) | https://github.com/aquasecurity/trivy/releases |

> Trivy は2本のワークフローで別々に宣言している。**片方だけ更新すると、PRゲートと週次で
> 違う版が動く。** 更新するときは必ず両方を揃える。実行時の版が宣言と一致することは
> `check-trivy-version.sh` が毎回確かめる。2本の宣言が揃っているかは週次監査
> (`check-audit-trivy-version.sh`)が確かめ、食い違えば `週次監査: 逸脱あり` のIssueで
> 知らせる(#334)。ここで人間が見るのは最新版との差だけでよい。

- **何を見るか**: 書いてあるバージョンと最新版の差
- **正常の目安**: マイナー版で2つ以内の差(初期値の提案)
- **異常時の行動**: 更新のIssueを起票する。例文: 「`docker/terraform/Dockerfile` の tflint が v0.60.0 のまま最新から離れている。最新版に更新し、`/verify-terraform` が通ることを確認してほしい」

## 人間の承認が必要なPRを承認するときの手順

DBマイグレーション・ライブラリの入手先やビルド設定の変更・チェック設定の変更を含むPR、および人間がIssueに pre-merge-check ラベルを付けたPRは、人間の承認が無いとマージされない。

**依存のバージョンを上げるだけのPRは承認の対象ではない。** `package.json` `pnpm-lock.yaml` `libs.versions.toml` `gradle-wrapper.properties` の変更は、次の3つの検査が代わりを務める。承認を求められなくなった代わりに、この3つが機能しているかを監査で見る。

| 検査 | 何を止めるか |
|---|---|
| dependency-review | そのPRで新しく増えた脆弱性 |
| dependency-cooldown | 公開から72時間を経過していないライブラリ |
| gradle-wrapper | 公式でない配布元・公表値と異なるチェックサム |

1. **承認ボタンを押す順番**: Codexレビューの指摘対応が終わり、CIの必須チェックがすべて成功した最後の段階で押す。承認後にコミットが積まれると承認は自動で無効になり、再承認が必要になる(安全側の正しい動きなので変更しない)
2. **DBマイグレーションを含むPR**: 承認する前に、必ずローカルで適用と巻き戻しを確認する

   ```bash
   docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
   ```

   対象ブランチを `./start-dev.sh` で起動してマイグレーションが適用されること、後方互換を保つ2段階変更(追加だけを先に行い、削除や制約強化は次のリリースに分ける)になっていることを確認してからApproveする
3. **ライブラリの入手先、またはbackendのビルド設定の変更を含むPR**: PR本文の変更理由と代替検討を読み、採否を判断してApproveする。対象は次の4つで、中身によらず変更そのものが承認対象になる

   | ファイル | なぜ機械の検査で代替できないか |
   |---|---|
   | `frontend/.npmrc` | ライブラリの入手先を差し替えられる。dependency-review は名前とバージョンしか見ず、入手先を検証しない |
   | `frontend/.pnpmfile.cjs` / `.pnpmfile.mjs` | インストール時に実行されるコードそのもの |
   | `frontend/pnpm-workspace.yaml` | 差し替えと待機期間の設定を含む。防御の設定そのものを機械の防御では守れない |
   | `backend/**/*.gradle` `*.gradle.kts` | 任意のコードであり、入手先の定義を含む。バージョンだけの変更かを静的に判別できない |

4. **pre-merge-check ラベルを付けたPR**: 対象ブランチを `./start-dev.sh` で起動して画面を確認し、問題がなければApproveする。問題があればPRコメントで具体的に指摘して差し戻す(Issueの再起票はしない)。承認後にコミットが積まれると承認は無効になり、このチェックも赤に戻る(手順1と同じ)
5. **チェック設定の変更を含むPR**: 変更が「チェックを弱める方向」でないことを確認する。該当する場合は、正当な理由(retrospectiveのIssue等)がPR本文に書かれているかを確認し、無ければ理由を質して Request changes で差し戻す。弱める方向の具体例は次のとおり
   - 閾値の引き下げ(カバレッジ基準・PRサイズ上限の緩和)
   - 検知対象の削除(検査回避チェックの検知パターンを消す等)
   - 除外の追加(除外リスト・静的解析の除外設定への追加)
   - 必須チェックの削除や、実行をスキップする条件の追加
   - CODEOWNERSからの保護パスの削除

## コンテナイメージの脆弱性が見つかったときの手順

`container-scan` が脆弱性で赤くなったとき、あるいは週次の監視でIssueが起票されたときの
判断の順序。**まず出口Aを検討し、選べないときだけ出口Bを使う。**

### 順序

1. **その脆弱性はどこから来たのか**を見る。実行結果の要約の表に、パッケージ名と導入版が出る
   - **ベースイメージ同梱**: こちらでは直せない。上流が新しいイメージを出すのを待つ
   - **アプリの依存**: 依存を上げれば消える。多くは Spring Boot の BOM 経由で入る推移的依存で、
     `backend/gradle/libs.versions.toml` に宣言が無い
2. **上流に修正版が出ているか**を確かめる。出ていれば依存の更新Issueを起票して、そちらで直す
3. **どちらも選べない場合に限り**、期限付きの抑制を使う

### 抑制を使ってよい条件

**次の3つをすべて満たすときだけ。**

- **上流に修正版が無い**、または修正版はあるが**こちらでは適用できない**(ベースイメージ同梱など)
- その脆弱性が**このアプリの使い方では成立しない**、あるいは**成立しても影響が限定される**
  ことを説明できる
- **待つ期限を決められる**。上流の修正の見込み、あるいは次に見直す日

**満たさないのに抑制を足すのは「見かけの合格」にあたる。** マージを通すためだけの抑制は使わない。

### 抑制の書き方

`.github/container-scan-suppressions.json` に1件足す。

```json
{
  "suppressions": [
    {
      "id": "CVE-2026-12345",
      "reason": "上流に修正版が無く、当該コードパスを呼ばないため",
      "expires": "2026-09-30"
    }
  ]
}
```

| 項目 | 規則 |
|---|---|
| `id` | 必須。空にしない。脆弱性の識別子と完全に一致させる |
| `reason` | 必須。空にしない。**上の3条件のどれに当たるかが読み取れる書き方にする** |
| `expires` | 必須。`YYYY-MM-DD`。実在する日付にする |

- **同じ識別子を2回書かない。** 重複は検査で赤になる
- **期限の当日までが有効。** 翌日からは抑制として扱われず、マージを止める側に戻る
- **期限を長く取らない。** 上流の見込みが立たないときでも、次に見直す日を入れる
- 抑制は**PRゲートにしか効かない。** 週次の監視は抑制を判定に用いず、抑制中の脆弱性も
  毎週見える形で報告する。抑制は「マージを止めない」判断であって「危険が無くなった」ではない

### 承認の手順

`.github/container-scan-suppressions.json` は `.github/` 配下にあるため、
**CODEOWNERS と escape-hatch の二重の網で所有者の承認が必須になる。**
自律側が自分の判断で足すことはできない(CLAUDE.md で禁止し、機械でも止まる)。

承認するときに見るのは次の3点。コードは読まない。

1. `reason` が上の3条件のどれに当たるかを説明しているか。「マージしたいため」の類は差し戻す
2. `expires` が妥当か。**根拠なく1年先などになっていないか**
3. 足したのが1件か。**複数を一度に足すPRは、件ごとに理由が要る**

### 期限が切れたあと

期限を過ぎた抑制は、記録に残っていてもマージを止める側に戻る。**記録の行は自動では消えない。**
脆弱性が解消していれば行を削除するPRを、まだ残っていれば期限を延ばすPRを出す。
どちらも所有者の承認が要る。

### AWSの権限の確認(週次の監視に必要)

週次の監視は、稼働中のイメージを特定するために ECS と ECR を参照する。
**この権限が欠けると週次だけが赤くなり、PRゲートには影響しない。**

```bash
aws iam get-role-policy --role-name keirekipro-github-actions-scan-role   --policy-name keirekipro-container-scan-read
```

必要なのは `ecs:DescribeServices`、`ecs:DescribeTaskDefinition`、ECR からの取得の3つ。
週次の監視は**参照専用の `keirekipro-github-actions-scan-role`** を使う(2026-08-21 以降)。
構築権限を持つ `keirekipro-github-actions-role` は使わない。

**これらのロールは terraform の管理外で、AWSコンソールでの手動管理になっている。**
権限の内容を変更したときは、`doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md` の
記述も合わせて直す。文書と実物がずれても機械では気づけない(実際に2026-08-20 まで
ずれていた)。

## 自動チェックの一覧(監査対象)

監査で見るべき自動チェックの全体像。どれかが機能しなくなっていないかをカナリア結果・すり抜け実績から確認する。

| 種類 | 実体 | 何を防ぐか |
|---|---|---|
| テストとカバレッジ基準 | Vitest / JUnit(Testcontainers)、カバレッジ基準値(vite.config.ts / quality.gradle) | ロジックの破壊、テストの薄い変更 |
| 静的解析 | ESLint(境界ルールとsonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | アーキテクチャ境界の違反、アサーションの無いテスト、型の逸脱 |
| 検査回避の検知 | escape-hatchチェック(guardrails.yaml) | テストのskip化、@Disabledや@ts-ignoreの追加、インラインでのlint無効化、アサーションの削除、品質チェック配線の改変 |
| 差分サイズの検査 | size-check(guardrails.yaml) | 仕様書の裏付けなしにコード差分200行を超える変更が入ること(注1) |
| 依存の脆弱性検査 | dependency-review(dependency-review.yaml) | そのPRで新しく増えた、moderate以上の既知の脆弱性。開発依存も対象で、既存の依存では赤にならない(注2) |
| 依存グラフの空洞化の検知 | check-dependency-snapshot(dependency-review.yaml / dependency-graph.yaml) | 依存解決が空のまま送信されること。空のスナップショットが送られると、脆弱性とクールダウンの検査が「追加0件」と判定して緑になり、backendのDependabotアラートも出なくなる。捉えるのは「空」までで、部分的に欠けたグラフと、送信より後の区間は月次のカナリア(vulnerable-dep)が受け持つ |
| 公開直後の版の遮断(backend) | dependency-cooldown(dependency-review.yaml) | 公開から72時間を経過していないライブラリ。そのPRで新しく追加されたものを、推移的依存とGradleプラグインまで含めて見る(注3) |
| Gradle本体の検証 | gradle-wrapper(guardrails.yaml) | ビルドが取得するGradle本体が公式のものでなくなること。配布元ホストが `services.gradle.org` であること、チェックサムと `gradle-wrapper.jar` が公式リリースと一致することを見る。wrapper関連の変更が無いPRでは外部への問い合わせを行わず通す |
| 入手先と防御設定の検査 | dependency-gate | ライブラリの入手先(`.npmrc`)、インストール時に実行されるコード(`.pnpmfile.*`)、差し替えと待機期間の設定(`pnpm-workspace.yaml`)、backendのビルドスクリプト(`*.gradle` `*.gradle.kts`)が承認なしに変更されること。中身は解析せず変更の有無で判定する。バージョン宣言そのものは対象外で、上の3つの検査が代わりを務める |
| コンテナイメージのビルド確認 | docker-smoke(ci.yaml) | ベースイメージの更新でDockerfileがビルドできなくなること。Dockerfileの変更だけではテスト系のジョブが動かないため、変更されたDockerfileを実際にビルドして確認する。検証はamd64で行い、arm64に固有の破綻はリリース時のビルドで検知する |
| コンテナイメージの脆弱性検査 | container-scan(container-scan.yaml) | 本番イメージのOS層と同梱 fat jar に、修正版のある CRITICAL/HIGH の脆弱性を持ち込む変更がマージされること。既存の依存も対象で、`dependency-review`(そのPRで新しく増えた分だけを見る)とは補完の関係にある |
| 週次の自動監査 | audit-weekly(audit-weekly.yaml) | 定期スキャンの停止(成功から8日)、Dependabot PRの滞留(failure/cancelled/timed_out/action_required)、必須チェックがスキップのままマージされたPR、期待一覧(`.github/audit/required-checks.json`)とrulesetのずれ、PRの検査と定期検査の `TRIVY_VERSION` の食い違い。逸脱は `週次監査: 逸脱あり`、監査の故障は `週次監査: 判定不能` のIssueで所有者に知らせる(ラベル `audit`)。逸脱ありでも実行は緑で終わる。赤になるのは、判定不能のときと、Issueへの反映が失敗したとき |
| 監査自体の死活 | ci.yaml の audit-liveness ステップ | 週次監査が止まったこと(完了した実行が10日無ければPRのCIが赤。結果が逸脱ありでも判定不能でも完了として数える)。番人の連鎖を作らず、PRが無い期間は問わない |
| カナリアの自動照合 | canary-verify(canary-verify.yaml) | 毎月のカナリア6件が期待チェックで赤になっていること(3値判定。判定側の故障と実行漏れを区別)。逸脱は `カナリア照合: 逸脱あり`、照合の故障は `カナリア照合: 判定不能` のIssueで知らせる。逸脱ありでも実行は緑で終わる。赤になるのは、判定不能のときと、Issueへの反映が失敗したとき。カナリアPRのcloseは行わない |
| 稼働中イメージの脆弱性監視 | container-scan-scheduled.yaml(週次) | マージ後に公表された脆弱性が、稼働中のイメージについて誰にも気づかれないまま残ること |
| IaCの静的検査 | terraform-static(terraform-plan.yaml) | フォーマット崩れ・構文と参照の誤り・tflintの指摘・checkovの新規指摘(注4) |
| アクション参照の固定 | check-action-pinning(guardrails.yaml) | `uses: owner/repo@<40桁のSHA> # vX.Y.Z` 以外の形式のアクション参照。タグは上流で差し替え可能で、こちらを変更しなくても実行内容が変わり得るため |
| 公開直後の版の遮断(frontend) | pnpm の minimumReleaseAge(72時間) | 公開から72時間以内のパッケージのインストール。悪意ある版は数時間で削除されるため、寝かせることで大半を避ける。ただし公開日時のメタデータが無いパッケージは素通りする(`minimumReleaseAgeIgnoreMissingTime` の既定が true のため) |
| DBマイグレーションの承認 | CODEOWNERS(migrationディレクトリ) | スキーマ変更が人間の確認なしにマージされること |
| チェック設定の保護 | CODEOWNERS + settings.jsonの編集拒否 | 品質チェックの設定がAIの判断で変更されること |
| シークレットスキャン | gitleaks | 認証情報などの混入 |
| 別AIによるレビュー | codex-review(判定はジョブの成否で行い、コメントの偽装は効かない) | バグ、セキュリティ問題、仕様との不一致、チェックを形だけ通す変更 |
| リリースの分離 | release.yaml(手動実行) | マージだけで本番に反映されること |
| 健全性の確認 | canary.yaml(月次) | チェックの仕組み自体が気づかないうちに壊れること |

- 注1: specの実在・必須4ファイル・プレースホルダ残存・spec.jsonの3段階承認フラグを検証する。承認フラグはAIの自己申告であり、人間が承認した証明にはならない(受容済みリスク: #177)
- 注2: baseとheadの依存グラフを比較する。backendの基準は、mainへのpushで dependency-graph.yaml が送信したスナップショット。required status check には generate / submit / review の3つすべてを指定すること。1つでも外すと、そのジョブが失敗したときに後続がスキップ(Success扱い)になり、検査されないままマージされる。フォークPRでは送信ジョブがスキップされ、Gradleの差分は未検査になる(受容済み)
- 注3: Dependabotが作成したPRは対象外(自動化側の待機期間が効いており、脆弱性対応の更新を遅らせないため)。フォークPRも対象外(スナップショットが送られず追加を特定できない)。公開時刻を取得できない場合、スナップショットが揃っていない場合、比較APIが失敗した場合はいずれも赤になる
- 注4: checkovの既存67件は `terraform/.checkov.baseline` で凍結してあり、baselineに無い指摘が出れば赤になる。checkovはDockerfileでバージョンを固定しており、更新は人間が明示的に行う。baselineを作り直すときは `.checkov.yaml` の `baseline:` 行を一時的に外してから実行する(有効なまま `--create-baseline` するとbaselineが空になる)

## 受容した残余リスク

機械の検査で守れないと分かったうえで受け入れているもの。半期に一度、増えていないかを見る。増えている場合は、検査の追加で埋められないかを検討する。

### 1. Gradle本体の検証は信頼の根が1つしかない

gradle-wrapper は配布元ホストを `services.gradle.org` に固定し、同じホストが公表するチェックサムと照合する。配布元が侵害されると配布物と公表値の両方が同時に偽装されるため、実質的に効いているのはホストの固定で、チェックサムの照合は手作業による書き換えとの不整合検知と位置づけている。あわせて、Gradle自身のチェックサム検証はダウンロード時にしか行われず、キャッシュ済みの環境では誤った値でも素通りする。ローカルで確認するときはキャッシュを削除してから実行する。

### 2. プロジェクト自身の `package.json` に任意のコマンドを書ける

pnpm 10 以降、依存パッケージのインストール時スクリプトは既定で実行されないが、遮断されるのは依存パッケージのものだけで、`frontend/package.json` の `scripts` に書いたコマンドは実行される。`package.json` を承認の対象から外したため、この経路は機械の検査を通らない。エージェントが書いたコードがCIと開発環境で実行されることは既に受け入れている範囲であり(`src` のコードもテストも同じ)、新しい信頼水準を要求するものではないと判断した。

### 3. フォークからのPRではbackendの依存が検査されない

フォークPRでは書き込み権限が得られず、依存グラフのスナップショットを送信できない。このため dependency-cooldown は対象外になり、dependency-review もfrontendしか見られない。このリポジトリのPRはすべて所有者のbotが同一リポジトリのブランチから作る運用であり、フォークPRは初回コントリビュータのワークフロー実行承認と人間のレビューを経る。

### 4. PRで追加されたワークフローは、マージ前に実行される

`pull_request` で発火するワークフローは、**PRを出した時点で動く。** CODEOWNERS と `check-escape-hatches.sh` の承認ゲートはマージを止めるものであって、実行は止めない。したがって、PRに置かれたワークフローはリポジトリのシークレットに触れられる。

**機構では塞げない。** GitHubに、同一リポジトリのブランチから出たPRのワークフロー実行を承認制にする設定は無い(フォークPRにはある)。実行後に検知する検査を足しても、実行そのものは防げない。

受容の根拠は、ブランチをpushできるのが所有者とbotの2アカウントに限られること。**bot のアクセストークンは2要素認証の保護を受けない**ため、ここが実質的な信頼の根になる。

なお、AWSへの経路は 2026-08-21 に分離済みで、PRから引き受けられるのは参照専用のロールのみ(`doc/インフラ設計/AWS設計/IAMロール・ポリシー設計.md` の 3.5)。**残っているのはリポジトリのシークレットへの露出である。**

### 5. `.github/` へのエージェントの書き込みは、ツールの禁止だけでは塞げない

`.claude/settings.json` は `Write` / `Edit` ツールによる `.github/**` の変更を拒否するが、**シェル経由の書き込み(`cp` / `sed -i` / リダイレクト / `python -c` など)は通る。** 書き方が無数にあり、コマンド文字列の照合で網羅できない。

**この禁止はうっかり編集の防止であって、安全対策ではない。** 本体はマージ前の所有者承認で、そちらは機械で強制されている。

**現在エージェントがこの経路で直接書いているのは、ゲート整備中の時限的な特例である**(#216)。ゲートそのものを作っている期間は、変更のほとんどが `.github/` 配下に集中し、1件ごとに人手で配置する手順が実務にならないため。**整備が一段落した時点で、本来の手順(エージェントが内容を用意し、人間が配置する)に戻す。** 判断と復帰の条件は #216 で追う。

塞ぐ機構を足すかどうかは、復帰時にあらためて決める。この受容は特例の期間に限る。

### 6. 監査の通知そのものが失敗すると、通知は出ない

監査の結果をIssueに書き込む処理が失敗した場合(通知の処理の自己テストの失敗、Issueの作成・追記・クローズの失敗)は、
Issueは作られず、実行が赤で終わるだけになる。定期実行の失敗通知はcronを最後に書き換えた利用者(監査のワークフローではbot)にしか届かないため、この赤は所有者には届かない。
通知の失敗を別の仕組みで見張ると、その仕組みの失敗もまた見張る必要が出て切りがないため受け入れた。

あわせて、この赤の実行も週次監査の「前回の実行」として数えられ、スキップのままマージされたPRの確認期間の区切りになる。
このため、その実行が受け持つはずだった期間が確認されないまま残る。
気づいたときは、**その実行を Re-run で再実行すれば**、確認されない期間は埋まる。

### 7. PRのCIの死活確認は、判定が行われたかどうかまでは見ない

PRのCIが確かめるのは、週次監査の実行が10日以内に完了しているかだけ。
手動でキャンセルされた実行や、通知の処理の自己テストで落ちた実行も「完了」に数える。
監査が実際に判定できたかどうかは、`週次監査: 判定不能` のIssueで見る。

### 8. 担当者の割り当てとメンションの両方が届かないと、残る経路はWatchだけになる

監査のIssueは、所有者を担当者に割り当て、本文で所有者にメンションする。
どちらも届かなかった場合に所有者が気づく経路は、所有者がこのリポジトリをWatchしていることだけになる。
導入時の受信確認(「[監査の通知Issueを受けたとき](#監査の通知issueを受けたとき)」)で、Watch設定もあわせて確かめる。

## 緊急時対応(本番を前の状態に戻す)

- frontend: Actionsの「Frontend Rollback」に、過去の成功したCI runのIDを指定して実行する
- backend: ECSタスク定義を前のリビジョンへ戻す(`doc/インフラ設計/手順書/手動作業手順.md`)
- DB: 後方互換を保つ2段階変更の運用により、直前リリースとの互換が保たれている
