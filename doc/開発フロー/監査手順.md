# 監査手順

人間がコードを読む代わりに行う、仕組みの点検の手順。人間がこの文書を開く場面ごとに節を分けている。
自動チェックの一覧と受容した残余リスクは、[ワークフロー設計](../インフラ設計/Github%20Actions設計/ワークフロー設計.md)の2章にある。

## 定期作業

どの項目も、判断は人間が行う。気になる点があれば、Issueを起票して Claude Code に指示する。

| 周期 | 開く場所 | 見ること | 気になったときの指示 |
|---|---|---|---|
| 週次 | Claude Code で `/usage` を実行する | トークン消費の内訳(スキル・サブエージェント・MCP別)に、偏りや心当たりのない項目が無いか | ループの実行間隔を伸ばす、ゴール駆動コマンドに渡す対象を絞る、原因の調査を指示する |
| 月次 | Issue「メトリクス台帳: mutationスコア」 | 毎月最初の土曜の行(全件を測り直す回)を、前月の同じ回の行と比べる。「取得できず」が続いていないか | 検知漏れの多い箇所にテストを足す |
| 月次 | 下の「版の確認先」の月次の行 | 使っている版と最新版の差 | 版を上げる |
| 半期 | 下の「版の確認先」の半期の行 | サポート期限と、次のメジャー版が出ているか | メジャー版を上げる |
| 半期 | 直近のCI(frontend-test / backend-test)のカバレッジ実測と、基準値(`frontend/vite.config.ts`・`backend/gradle/quality.gradle`) | 実測が基準値を安定して上回っていないか | 基準値を引き上げる。基準値の変更は所有者の承認が要る |
| 半期 | `REVIEW.md`、`.github/scripts/check-escape-hatches.sh` の検知対象、`gh issue list --label retrospective --state all` | 各項目がある理由を説明できるか。すり抜けた実績と合っているか | 説明できない項目や実績と合わない項目を書き直す |
| 半期 | ワークフロー設計の「受容した残余リスク」 | 増えていないか。検査の追加で埋められるものが無いか | 検査を足す |

AIレビューのモデルの見直し(`.github/workflows/codex-review.yml` の `--model`)は、codex-review が止まっている間は行わない(#166)。
`CODEX_REVIEW_ENABLED` を戻したら半期の作業に加える。

| 周期 | 対象 | 書いてある場所 | 確認先 |
|---|---|---|---|
| 月次 | tflint | `docker/terraform/Dockerfile` の `COPY --from=` の行 | https://github.com/terraform-linters/tflint/releases |
| 月次 | tflint の AWS 用ルールセット | `terraform/.tflint.hcl` の `plugin "aws"` | https://github.com/terraform-linters/tflint-ruleset-aws/releases |
| 月次 | checkov | `docker/terraform/Dockerfile` の `pip3 install` の行 | https://pypi.org/project/checkov/ |
| 月次 | Trivy | `.github/workflows/container-scan.yaml` と `container-scan-scheduled.yaml` の `TRIVY_VERSION`。2本を必ず揃える | https://github.com/aquasecurity/trivy/releases |
| 半期 | Java | `docker/backend/Dockerfile`・`Dockerfile.prod` の `eclipse-temurin` | https://endoflife.date/eclipse-temurin |
| 半期 | Node.js | `docker/frontend/Dockerfile` の `node` | https://endoflife.date/nodejs |
| 半期 | PostgreSQL | `docker/db/Dockerfile`(開発)と `terraform/modules/rds/main.tf` の `engine_version`(本番) | https://endoflife.date/postgresql 、https://endoflife.date/amazon-rds-postgresql |
| 半期 | Redis / Valkey | `docker/redis/Dockerfile`(開発)と `terraform/modules/elasticache/main.tf` の `engine_version`(本番) | https://endoflife.date/redis 、https://endoflife.date/valkey |

## 監査の通知Issueを受けたとき

週次監査(`audit-weekly.yaml`、毎週月曜)とカナリア照合(`canary-verify.yaml`、毎月4日)の結果は、ラベル `audit` のIssueで届く。
所有者が担当者に付き、本文でメンションされる。所有者はこのリポジトリをWatchしておく(担当者とメンションの両方が届かなかったときに残る経路になる)。

| タイトル | 意味 |
|---|---|
| `週次監査: 逸脱あり`、`カナリア照合: 逸脱あり` | 所有者の対処を待つ問題が見つかった |
| `週次監査: 判定不能`、`カナリア照合: 判定不能` | 監査そのものが正しく動かず、問題の有無が分からない |

**人間はこれらのIssueを閉じない。** 次の実行で解消していれば自動で閉じる。問題が続く間は、同じIssueに実行のたびに追記が増える。

### 逸脱ありのとき

本文に、判定項目ごとの対象(PR番号・チェック名)と根拠が載っている。項目に応じて次のように対処する。

- **Dependabot のPRの滞留**: 下の「PRが止まったとき」に従う。所有者の承認待ちだけで止まっているPRは、逸脱ではなく「承認待ち」の一覧に出る
- **定期スキャンが止まっている**: 実行ログを見る。実行自体が無ければ Actions から手動で実行する。手動でも失敗するなら原因の調査を指示する
- **期待一覧とrulesetの必須チェックが食い違う**: どちらが正しいかを決める。期待一覧(`.github/audit/required-checks.json`)が誤りなら修正を指示し、rulesetが誤りならリポジトリの Settings にある Rulesets の `main` で戻す
- **必須チェックがスキップのままマージされたPRがある**: 原因(設定・変数・ワークフローの故障)の調査を指示する。意図して止めているチェックは、期待一覧で `state` を `paused` にし、理由と参照Issueを書けば違反として扱われない
- **Trivy の版が2本のワークフローで食い違う**: 揃えるよう指示する
- **カナリアの検知漏れ(「判定側の故障」「実行されていない」)**: 原因の分析と検査の強化を指示する
- **カナリアPRが6件そろっていない**: `canary.yaml` の実行結果と `BOT_GITHUB_TOKEN` の有効期限を確かめる

### 判定不能のとき

監査の仕組みが故障している。この間は逸脱を見つけられないため、先に直す。

1. 本文で、判定できなかった項目と理由を読む
2. 一時的な失敗が疑われるときは再実行する。**週次監査は、失敗した実行を開いて Re-run する。新規の手動実行(Run workflow)は使わない。** スキップのままマージされたPRの確認は前回の実行からの期間を対象にしており、新規に実行すると失敗した実行の受け持ち期間が確認されずに残る。カナリア照合はどちらでもよい
3. 再実行しても続くときは、原因の調査と修正を指示する

## PRが止まったとき

### Dependabot のPRが赤いとき

**Dependabot のPRを close しない。** とくに docker のPRは、close するとそのタグの更新が恒久的に止まる(Dependabot の照合キーに digest が含まれないため)。
close してしまったら、ブランチを復元したうえでPRを Reopen し、`@dependabot recreate` とコメントする。Reopen できなければ復旧できない。

docker のPRが脆弱性で赤いときの出口は次の2つ。

| 出口 | 手順 |
|---|---|
| A(通常) | 上流に新しいベースイメージが出て、**その公開から3日以上経ってから** `@dependabot recreate` とコメントする。3日以内に打つと、Dependabot がPRを自ら close する |
| B(待てないとき) | 期限付きの抑制を1件足す。下の「脆弱性の抑制を承認するとき」の条件を満たす場合に限る |

- docker のPRの最新化には、`@dependabot rebase` ではなくPR画面の **Update branch** を使う(rebase も recreate と同じ危険がある)
- マージを保留したいときは、auto-merge の解除ではなく `pre-merge-check` ラベルを付ける(解除しても Dependabot の push で予約が付け直される)
- GitHub Actions のPRを承認するときは、差分が `uses: owner/repo@<40桁のSHA> # vX.Y.Z` の形のまま、SHAとコメントの両方が変わっていることだけを確かめる。タグ参照に戻っていたら承認しない
- 脆弱性以外の理由で赤いときは、原因の調査を指示する

### ブランチが最新化されずに止まったとき

mainが進むとPRは out-of-date になり、`update-pr-branches.yaml` が自動で最新化する。止まっているときは、その実行結果を見る。

- 赤なら実行ログの警告を読む。多い原因は `BOT_GITHUB_TOKEN` の失効で、[基盤構築手順](基盤構築手順.md)に従って登録し直す
- 衝突しているPRは自動では最新化できない。内容を見て指示する
- 急いでマージしたいときは、Rulesets の `main` で `Require branches to be up to date` を一時的に外す。他の必須チェックは効いたまま残る

### container-scan をキャンセルしたとき

キャンセルしたジョブは成功にならず、そのあと再検査を起こすイベントも無い。**手動でキャンセルしたら、その実行を Re-run する。**

## 承認を求められたとき

承認ボタンは、指摘への対応が終わり必須チェックがすべて成功した最後の段階で押す。承認のあとにコミットが積まれると承認は無効になり、再承認が要る。

依存のバージョンを上げるだけのPR(`package.json` `pnpm-lock.yaml` `libs.versions.toml` `gradle-wrapper.properties`)は承認の対象ではない。dependency-review・dependency-cooldown・gradle-wrapper が代わりに止める。

| PRの種類 | 承認する前に確かめること |
|---|---|
| DBマイグレーションを含む | 対象ブランチを `./start-dev.sh` で起動し、マイグレーションが適用されること(`docker compose exec -w /home/spring/app backend ./gradlew flywayInfo`)。後方互換を保つ2段階の変更(追加を先に行い、削除や制約の強化は次のリリースに分ける)になっていること |
| ライブラリの入手先・ビルド設定の変更(`frontend/.npmrc`、`.pnpmfile.*`、`pnpm-workspace.yaml`、`backend/**/*.gradle`) | PR本文の変更理由と代替の検討を読み、採否を判断する。機械の検査では中身を確かめられないため、変更そのものが承認対象になっている |
| `pre-merge-check` ラベル付き | 対象ブランチを `./start-dev.sh` で起動して画面を確かめる。問題があればPRコメントで具体的に指摘して差し戻す |
| チェック設定の変更 | チェックを弱める変更でないこと。閾値の引き下げ、検知対象の削除、除外の追加、必須チェックの削除やスキップ条件の追加、CODEOWNERSの保護パスの削除は、正当な理由がPR本文に無ければ差し戻す |

### 脆弱性の抑制を承認するとき

`.github/container-scan-suppressions.json` への追加は、所有者の承認が要る。**次の3つをすべて満たすときだけ承認する。**

- 上流に修正版が無い、またはこちらでは適用できない(ベースイメージ同梱など)
- その脆弱性がこのアプリの使い方では成立しない、または影響が限られることを説明できる
- 待つ期限(上流の修正の見込み、または次に見直す日)を決められる

承認するときに見るのは、`reason` が上の3条件のどれに当たるかを説明しているか、`expires` が根拠なく遠くないか、足したのが1件か(複数なら件ごとに理由があるか)。
期限を過ぎた抑制はマージを止める側に戻るが、記録の行は自動では消えない。脆弱性が解消していれば削除を、残っていれば期限の延長を指示する。

### 脆弱性のIssueを受けたとき

週次の監視は、検出した脆弱性を識別子ごとに1件のIssue(ラベル `container-vuln`)にする。**人間はこのIssueを閉じず、タイトルも書き換えない。** イメージから検出されなくなれば自動で閉じる。
週次の監視が使う AWS のロールは terraform の管理外で、手動で管理している。権限を変えたときは [IAMロール・ポリシー設計](../インフラ設計/AWS設計/IAMロール・ポリシー設計.md)も直す。
