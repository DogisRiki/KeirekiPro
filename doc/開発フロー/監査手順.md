# 監査手順(人間の役割2「ループの設計・監視・改善」の定例作業)

コードを読む代わりに、**ループとゲートが機能し続けているか**を監査する。

## 週次監査(目安15分)

1. **コスト確認**: Claude Codeで `/usage` を実行し、スキル・サブエージェント・MCP別の
   トークン内訳を確認する。増え続けている場合はループ設計を小さく戻す
2. **レビュー往復数**: 直近1週間のPRの review-loop 往復数を確認する
   (`gh pr list --state merged --search "sort:updated-desc"` + PRコメントの `## review-loop 往復<N>`)。
   平均が3往復を超えるならspecの解像度かレビュープロンプトを見直す
3. **`codex-overruled` の優先サンプリング**: ラベル付きPRを開き、「誤検知」判定の根拠が
   妥当だったかを往復ログで確認する(コードは読まない。判断の筋だけを見る)

```bash
gh pr list --label codex-overruled --state all --limit 10
```

4. **誤検知閾値**: 誤検知判定が週3件を超えていたら、レビュープロンプト
   (`.github/workflows/codex-review.yml`)の見直しをIssue起票する
5. **Java検知の昇格判定**: guardrails の「Javaテスト アサーション有無レポート」を確認し、
   誤検知は理由付きで `.github/scripts/java-assertion-exclusions.txt` へ追加する。
   **除外リスト整備完了かつ検出バックログゼロ**になったら、
   `report-java-test-assertions.sh` をブロックモード(exit 1)へ昇格する(レポートのまま放置しない)

## 月次監査(目安30分)

1. **カナリア結果の確認**: 「Canary Gate Check」実行後の3つのカナリアPRを開き、
   期待どおり赤になっているかを確認する:

| カナリア | 期待される検出 |
|---|---|
| known-bug | codex-review(コード品質軸)が CHANGES REQUESTED |
| assertless-test | frontend-test(ESLint sonarjs)が赤 |
| skipped-test | escape-hatch が赤 |

   - **検出漏れがあった場合**: `/retrospective` で「ゲート追加」を必須として起票する
   - 確認後、カナリアPRをクローズしブランチを削除する(次回実行時にも自動クローズされる)
2. **mutationスコアの確認**: 「Mutation Report」のartifact(Stryker/PIT)を確認し、
   前月からのスコア低下があれば `/retrospective` の入力にする
3. **retrospectiveの棚卸し**: `doc/開発フロー/retrospective.md` の「提案」状態の項目を
   Issue起票 or 実施済みへ進める

## 半期ごと

- レビュー基準の書き直し: `REVIEW.md`・codex-reviewプロンプト・escape-hatch検知対象を、
  この半年のすり抜け実績に基づいて全面的に見直す(認知的降伏の防止。
  「AIがそう言うので」を判断基準にしない)
- カバレッジ閾値のratchet: 実測が閾値を安定して上回っていれば、閾値を実測付近まで引き上げる
  (`vite.config.ts` / `backend/gradle/quality.gradle`。CODEOWNERS対象のため自分のApproveで反映)

## 例外ゲート承認の手順(役割4)

1. **順番**: 承認ボタンは、Codexレビューの指摘対応が終わり、CIの必須チェックがすべて成功した
   **最後の段階**で押す(ブランチ保護の Dismiss stale approvals により、承認後にコミットが積まれると
   承認が無効化され再承認が必要になるため。これは安全側の正しい挙動)
2. **DBマイグレーションPR**: 承認前に必ずローカルDBで適用・巻き戻しを確認する:

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```

   ローカル起動(`./start-dev.sh`)でマイグレーションが適用されることと、
   expand-contract規約(後方互換)を満たすことを確認してからApproveする
3. **依存追加PR**: PR本文の追加理由・代替検討を読み、採否を判断してApproveする
   (Approveすると dependency-gate が緑に再評価され、auto-mergeが成立する)
4. **ゲート設定変更PR**: 変更が「ゲートを弱める方向」でないことを差分の意図から判断する
