# 監査手順

人間がコードを読む代わりに行う、仕組みの点検のチェックリスト。
週次・月次・半期の各項目を上から順に実行する。

> 本文中の数値の目安には「初期値の提案」と付けてある。運用実績に合わせて調整し、
> 変えた場合はこの文書を書き換えること。

## 週次監査(目安15分)

### 1. Claude Codeの利用量の確認

ループの暴走や作業の無駄な膨らみは、トークン消費の内訳の偏りに表れるため。

- **どこを開くか**: Claude Codeのセッションで `/usage` を実行する
- **何を見るか**: トークン使用量の内訳(スキル・サブエージェント・MCP別)の偏り
- **正常の目安**: 内訳のうち1つの項目が全体の半分を超えていない、かつ心当たりのない項目が
  上位に入っていない(初期値の提案)
- **異常時の行動**: 半分を超えた項目・心当たりのない項目について、次のいずれかを行う
  - その項目がゴール駆動コマンド(/goal-implement 等)なら、渡す対象を小さくする(1画面・1テストファイル単位に絞る)
  - その項目が定期ループなら、`/loop` の実行間隔を伸ばす(例: 30分を60分にする)
  - それでも偏りが解消しなければ、定期ループの作業内容を減らすIssueを起票してClaude Codeに指示する。
    例文: 「定期ループのトークン消費が内訳の半分を超えている。`.claude/loop.md` の手順から設計図の乖離確認を外して、消費を減らしてほしい」

### 2. レビューのやり直し回数の確認

レビューの往復が多いのは、仕様が曖昧なまま実装が始まっているサインのため。

review-loopは、レビュー担当AI(Codex)の指摘にClaude Codeが対応する修正ループのこと。往復の記録はPRコメントに残る。

- **どこを開くか**: 次のコマンドで直近のマージ済みPRを一覧し、各PRのコメント欄を開く

```bash
gh pr list --state merged --limit 10
```

- **何を見るか**: PRコメントの「review-loop 往復N」という見出しの、PRごとの最大N
- **正常の目安**: 平均2往復以内、最大でも3往復(初期値の提案)
- **異常時の行動**: 4往復以上のPRが週に2件以上あれば、指摘の内容を読んで原因を切り分け、Issueを起票してClaude Codeに指示する
  - 仕様の曖昧さが原因の場合の例文: 「PR #12 でレビューが5往復し、原因は要件の解釈違いだった。`.kiro/settings/templates/` のrequirementsテンプレートに、受け入れ基準へ具体例を書く欄を追加してほしい」
  - 指摘のブレが原因の場合の例文: 「PR #13 で同じ箇所に往復ごとに逆の指摘が出た。`.github/workflows/codex-review.yml` のプロンプトに、このプロジェクトの例外処理の方針を追記してほしい」

### 3. AIレビューの指摘をAIが不当に握りつぶしていないかの抜き取り確認

面倒な指摘を誤検知扱いで退けることを許すと、レビューが形だけになるため。

codex-overruledは、Codexの指摘をClaude Codeが誤検知と判定して退けたPRに付くラベルのこと。

- **どこを開くか**:

```bash
gh pr list --label codex-overruled --state all --limit 10
```

- **何を見るか**: 各PRのコメントに書かれている、指摘を退けた理由。次の3つの質問で確認する
  1. 退けた理由が、仕様・テスト結果・実際のコードの動作のどれかを根拠にしているか
  2. 「対応コストが高い」だけを理由にしていないか(コストは指摘を退ける理由にならない)
  3. 退けた指摘と同種の問題が、その後実際に起きていないか
- **正常の目安**: サンプリングしたすべてのPRで、3つの質問全部に「はい」と答えられる
- **異常時の行動**: 「いいえ」があるPRは、Issueを起票してClaude Codeに対応を指示する。
  例文: 「PR #15 で退けられた『日付の境界値が未検証』という指摘は、根拠が『既存テストで十分』としか書かれていない。本修正として境界値テストを追加してほしい」

### 4. 指摘を退けた件数が増えすぎていないかの確認

退ける判定が増えるのは、レビューの指示文とプロジェクトの実態がずれてきたサインのため。

- **どこを開くか**: 項目3と同じラベル一覧で、今週作成されたPRの件数を数える
- **何を見るか**: 今週、指摘を誤検知と判定した件数
- **正常の目安**: 週3件以内(初期値の提案)
- **異常時の行動**: 4件以上ならIssueを起票してClaude Codeに指示する。
  例文: 「今週の誤検知判定が5件あり、いずれもテスト網羅に関する指摘だった。`.github/workflows/codex-review.yml` のプロンプトに、テスト方針(ユニットテストの粒度)を追記して誤検知を減らしてほしい」

### 5. 何も検証していないJavaテストの検出状況と、検出を厳格化するかの判断

何も検証しないテストは、カバレッジの数字だけ稼いで品質を保証しないため。

guardrailsは、PRごとに検査回避・差分サイズ・シークレット混入などを検べるワークフロー(guardrails.yaml)のこと。
何も検証していないJavaテストは、静的解析ツールPMDのルール(UnitTestShouldIncludeAssert)で検出する。
現在は警告のみで、ビルドやPRを止めない。

- **どこを開くか**: GitHubのActionsタブ → 直近のPRの「Guardrails」実行 → java-assertion-reportジョブのSummary
  (backendに変更が無いPRでは実行されない)
- **何を見るか**: 検出件数と、それが誤検知(ヘルパーメソッド経由で検証しているテスト)かどうか
- **正常の目安**: 誤検知はPMDの設定に整理済みで、実検出が0
- **異常時の行動**:
  - 誤検知がある場合の指示の例文: 「ResumeServiceTest#buildResume はヘルパーメソッド内で検証しているため誤検知。`backend/config/pmd/ruleset.xml` の extraAssertMethodNames に検証メソッド名を追加してほしい」
  - 実検出がある場合の指示の例文: 「XxxTest#yyy が何も検証していない。対象の振る舞いを検証するアサーションを追加してほしい」
  - 誤検知の設定整理が完了し実検出0が続いた場合の指示の例文: 「実検出0が4週続いた。`backend/gradle/quality.gradle` のPMD設定 ignoreFailures を false にして、検出があればビルドが失敗するよう昇格してほしい」。警告のみのまま放置しない

### 6. Dependabotのバージョン更新PRが滞留していないかの確認

security updateのPRは自動マージされるが、**version updateのPRは自動マージされない**ため。
レビュー対象の差分があるPRを無レビューで自動マージしない設計上、所有者のマージ操作が必要になる。
放置すると依存の更新が止まり、いずれ大きなバージョン差の解消を迫られる。

- **どこを開くか**: 次のコマンドでDependabotの未マージPRを一覧する

```bash
gh pr list --state open --author "app/dependabot"
```

- **何を見るか**: 開いたままのPRの件数と、最も古いPRの作成日。各PRのチェックが緑かどうか
- **正常の目安**: 開いたままのPRが3件以内、かつ最も古いものが2週間以内(初期値の提案)
- **異常時の行動**:
  - 緑のPRが溜まっている場合は、その場でマージする(コードは読まない。チェックが緑であることを確認するだけでよい)
  - 赤で止まっているPRがあれば、原因を見てIssueを起票してClaude Codeに指示する。
    例文: 「Dependabotの #45 が frontend-test で落ちている。原因を調べて対応してほしい」
  - frontendのPRだけが4週以上作られていない場合は、pnpmのlockfile形式をDependabotが
    解析できなくなっている可能性を疑う(https://github.com/dependabot/dependabot-core/issues/14919)
  - マージ操作の頻度が負担になってきた場合は、version updatesの完全自動化を検討する
    (`OPENAI_API_KEY` をDependabot secretsへ複製し、codex-reviewをversion updatesでも実行する案)

## 月次監査(目安30分)

### 1. わざと問題を入れたPRで、検査が機能しているかの点検

検査の仕組み自体が壊れても、普段のPRでは気づけないため。

カナリアPRは、検査が検知できるはずの問題をわざと含めた健康診断用のPRのこと。毎月1日に3件自動生成される。
escape-hatchは、テストの無効化などの検査回避を検知するCIチェックのこと。

- **どこを開くか**:

```bash
gh pr list --label canary --state open
```

- **何を見るか**: 3件それぞれのチェック結果が、期待どおり失敗しているか

| カナリアPR | 期待される失敗 |
|---|---|
| known-bug | codex-review が失敗(もっともらしいバグをレビューが検知) |
| assertless-test | frontend-test が失敗(何も検証しないテストをESLintが検知) |
| skipped-test | escape-hatch が失敗(テストのskip追加を検知) |

- **正常の目安**: 3件すべてが期待どおりのチェックで失敗している
- **異常時の行動**: 検出漏れがあればClaude Codeで `/retrospective` を実行し、検査強化のIssueを起票させる。
  指示の例文: 「今月のカナリアで known-bug のPRがcodex-reviewを通過してしまった。/retrospective で原因を分析し、検査強化のIssueを起票してほしい」
- **後始末(毎回行う)**: 確認が済んだら3件のPRをクローズし、ブランチを削除する

### 2. テストが本当にバグを見つけられるかの測定結果の確認

カバレッジが高くても、バグを検知できないテストでは意味がないため。

mutation testingは、わざとコードを壊してテストが失敗するかを見ることで、テストの実効性を測る仕組みのこと。
毎週土曜に自動実行される。

- **どこを開くか**: GitHubのActionsタブ → 「Mutation Report」の最新実行 → Artifacts(stryker-report / pitest-report)
- **何を見るか**: frontend(Stryker)とbackend(PIT)それぞれの全体スコア
- **正常の目安**: 前月から5ポイント以上下がっていない(初期値の提案)
- **異常時の行動**: 5ポイント以上下がっていたらIssueを起票してClaude Codeに指示する。
  例文: 「backendのmutationスコアが72%から64%に低下した。レポートで検知漏れが集中しているdomain層の該当クラスに、壊した箇所を検知できるテストを追加してほしい」

### 3. すり抜けた問題の改善Issueが放置されていないかの確認

改善Issueが放置されると、同じすり抜けが繰り返されるため。

retrospectiveは、チェックをすり抜けた問題を仕組みの改善につなげる振り返りのIssueのこと(同名のラベルが付く)。

- **どこを開くか**:

```bash
gh issue list --label retrospective --state open
```

- **何を見るか**: openのままのIssueの内容と、作成からの経過期間
- **正常の目安**: 2ヶ月以上放置されているIssueが無い(初期値の提案)
- **異常時の行動**: 各Issueについて次のいずれかを行う
  - 承認が必要な強化案は、採否をコメントで指示する。
    例文: 「この強化案を採用する。escape-hatchチェックに検知パターンを追加するPRを作ってほしい」
  - 対応が完了しているものはcloseする
  - やらないと決めたものは、理由をコメントしてcloseする。
    例文: 「この事象は依存の更新で解消済みのため対応しない」

## 半期ごと

### 1. レビュー基準が実態と合っているかの見直しと書き直し

基準を惰性で維持すると、実態と合わない検査を信じ続けることになるため。

- **どこを開くか**: `REVIEW.md`、`.github/workflows/codex-review.yml` のプロンプト部分、
  `.github/scripts/check-escape-hatches.sh` の検知対象。あわせて次のコマンドでこの半年のすり抜け実績を一覧する

```bash
gh issue list --label retrospective --state all
```

- **何を見るか**: 基準の各項目が、この半年の実績(実際にすり抜けたもの・一度も検知していないもの)と合っているか
- **正常の目安**: 基準のすべての項目について、なぜその項目があるのかを自分の言葉で説明できる
- **異常時の行動**: 説明できない項目・実績と合わない項目は、書き直しのPRをClaude Codeに指示する。
  例文: 「この半年でPDF出力まわりのバグが2件すり抜けた。REVIEW.md の重大と判定する条件に帳票出力の検証を追加し、一度も検知していない○○の項目は削ってほしい」

### 2. AIレビューが使うモデルの見直し

AIのモデルは廃止や世代交代が速く、指定したまま放置すると突然レビューが失敗したり、
より安く高性能な選択肢を逃したりするため。

- **どこを開くか**: `.github/workflows/codex-review.yml` の `--model` 指定と、
  OpenAIのAPI価格ページ(提供中のモデル一覧が載っている)
- **何を見るか**: 指定中のモデルがまだ提供されているか。後継や同等性能で安いモデルが出ていないか
- **正常の目安**: 指定中のモデルが提供中で、明らかに有利な後継が出ていない
- **異常時の行動**: モデル指定を更新するPRをClaude Codeに指示する。
  例文: 「codex-reviewで指定中の gpt-5.6-terra の後継として GPT-5.7 系が出ている。
  価格と性能を確認し、`--model` の指定を更新してほしい」

### 3. テスト網羅率の基準値の引き上げ

実測との差が開いたまま放置すると、テストが減っても検査で気づけなくなるため。
基準値は下げない運用のため、実測が上がったら基準値も追いかけて上げる。

- **どこを開くか**: 直近のCI実行(frontend-test / backend-test)のカバレッジ実測値と、
  基準値の定義ファイル(`frontend/vite.config.ts`・`backend/gradle/quality.gradle`)
- **何を見るか**: 実測値と基準値の差
- **正常の目安**: 差が5ポイント以内(初期値の提案)
- **異常時の行動**: 実測が基準値を安定して5ポイント以上上回っていれば、引き上げのPRをClaude Codeに指示し、自分でApproveして反映する(基準値の定義ファイルは変更に所有者の承認が必要なため)。
  例文: 「frontendのLines実測が88%で基準値80%を3ヶ月上回り続けている。基準値を87%へ引き上げてほしい」

## 人間の承認が必要なPRを承認するときの手順

DBマイグレーション・依存パッケージの追加・チェック設定の変更を含むPR、および人間がIssueに
pre-merge-check ラベルを付けたPRは、人間の承認が無いとマージされない。
承認するときは次の手順で行う。

1. **承認ボタンを押す順番**: Codexレビューの指摘対応が終わり、CIの必須チェックがすべて成功した
   **最後の段階**で押す。ブランチ保護の設定により、承認後にコミットが積まれると承認は自動で無効になり、
   再承認が必要になる(これは安全側の正しい動きなので変更しない)
2. **DBマイグレーションを含むPR**: 承認する前に、必ずローカルで適用と巻き戻しを確認する

```bash
docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
```

   対象ブランチを `./start-dev.sh` で起動してマイグレーションが適用されること、
   後方互換を保つ2段階変更(追加だけを先に行い、削除や制約強化は次のリリースに分ける)に
   なっていることを確認してからApproveする
3. **依存パッケージの追加を含むPR**: PR本文の追加理由と代替検討を読み、採否を判断してApproveする。
   Approveすると保留されていたチェックが成功に変わり、自動マージが進む
4. **pre-merge-check ラベルを付けたPR**: マージ前にローカルで画面を確認したい変更に使う。
   対象ブランチを `./start-dev.sh` で起動して画面を確認し、問題がなければApproveする。
   問題があればPRコメントで具体的に指摘して差し戻す(Issueの再起票はしない)。
   承認後にコミットが積まれると承認は無効になり、このチェックも赤に戻る(手順1と同じ)
5. **チェック設定の変更を含むPR**: 変更が「チェックを弱める方向」でないことを確認する。
   弱める方向の具体例は次のとおり。該当する場合は、正当な理由(retrospectiveのIssue等)が
   PR本文に書かれているかを確認し、無ければ理由を質して Request changes で差し戻す。
   コメントの例文: 「この変更でカバレッジ基準が80%から70%に下がるが、理由が書かれていない。理由を追記するか、基準値を戻してほしい」
   - 閾値の引き下げ(カバレッジ基準・PRサイズ上限の緩和)
   - 検知対象の削除(検査回避チェックの検知パターンを消す等)
   - 除外の追加(除外リスト・静的解析の除外設定への追加)
   - 必須チェックの削除や、実行をスキップする条件の追加
   - CODEOWNERSからの保護パスの削除

## 自動チェックの一覧(監査対象)

監査で見るべき自動チェックの全体像。どれかが機能しなくなっていないかを
カナリア結果・すり抜け実績から確認する。

| 種類 | 実体 | 何を防ぐか |
|---|---|---|
| テストとカバレッジ基準 | Vitest / JUnit(Testcontainers)、カバレッジ基準値(vite.config.ts / quality.gradle) | ロジックの破壊、テストの薄い変更 |
| 静的解析 | ESLint(境界ルールとsonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | アーキテクチャ境界の違反、アサーションの無いテスト、型の逸脱 |
| 検査回避の検知 | escape-hatchチェック(guardrails.yaml) | テストのskip化、@Disabledや@ts-ignoreの追加、インラインでのlint無効化、アサーションの削除、品質チェック配線の改変 |
| 差分サイズの検査 | size-check(guardrails.yaml) | 仕様書の裏付けなしにコード差分200行を超える変更が入ること |
| 依存追加の検査 | dependency-gate | 依存パッケージが承認なしに追加されること(所有者が承認するとチェックが成功に変わり、マージが進む) |
| DBマイグレーションの承認 | CODEOWNERS(migrationディレクトリ) | スキーマ変更が人間の確認なしにマージされること |
| チェック設定の保護 | CODEOWNERS + settings.jsonの編集拒否 | 品質チェックの設定がAIの判断で変更されること |
| シークレットスキャン | gitleaks | 認証情報などの混入 |
| 別AIによるレビュー | codex-review(判定はジョブの成否で行い、コメントの偽装は効かない) | バグ、セキュリティ問題、仕様との不一致、チェックを形だけ通す変更 |
| リリースの分離 | release.yaml(手動実行) | マージだけで本番に反映されること |
| 健全性の確認 | canary.yaml(月次) | チェックの仕組み自体が気づかないうちに壊れること |

## 緊急時対応(本番を前の状態に戻す)

- frontend: Actionsの「Frontend Rollback」に、過去の成功したCI runのIDを指定して実行する
- backend: ECSタスク定義を前のリビジョンへ戻す(`doc/インフラ設計/手順書/手動作業手順.md`)
- DB: 後方互換を保つ2段階変更の運用により、直前リリースとの互換が保たれている
