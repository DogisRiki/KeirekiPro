# 監査手順

人間がコードを読む代わりに行う、仕組みの点検のチェックリスト。
週次・月次・半期の各項目を上から順に実行する。

> 数値の目安のうち「初期値の提案」と付けたものは、運用実績に合わせて調整する。
> 変えた場合はこの文書を書き換えること。

## 用語

| 用語 | 意味 |
|---|---|
| review-loop | レビュー担当AI(Codex)の指摘にClaude Codeが対応する修正ループ。往復の記録はPRコメントに残る |
| codex-overruled | Codexの指摘をClaude Codeが誤検知と判定して退けたPRに付くラベル |
| guardrails | PRごとに検査回避・差分サイズ・シークレット混入などを検べるワークフロー(guardrails.yaml) |
| escape-hatch | テストの無効化などの検査回避を検知するCIチェック |
| dependency-gate | ライブラリの入手先や防御設定の変更を承認対象として止めるチェック。所有者がApproveすると成功に変わる |
| カナリアPR | 検査が検知できるはずの問題をわざと含めた健康診断用のPR。毎月1日に5件自動生成される |
| mutation testing | わざとコードを壊してテストが失敗するかを見て、テストの実効性を測る仕組み。毎週土曜に自動実行される |
| retrospective | チェックをすり抜けた問題を仕組みの改善につなげる振り返りのIssue(同名のラベルが付く) |

## 週次監査(目安15分)

### 1. Claude Codeの利用量の確認

なぜ: ループの暴走や作業の無駄な膨らみは、トークン消費の内訳の偏りに表れる。

- **どこを開くか**: Claude Codeのセッションで `/usage` を実行する
- **何を見るか**: トークン使用量の内訳(スキル・サブエージェント・MCP別)の偏り
- **正常の目安**: 1つの項目が全体の半分を超えておらず、心当たりのない項目が上位に入っていない(初期値の提案)
- **異常時の行動**: 半分を超えた項目・心当たりのない項目について、次のいずれかを行う
  - ゴール駆動コマンド(/goal-implement 等)なら、渡す対象を1画面・1テストファイル単位に絞る
  - 定期ループなら `/loop` の実行間隔を伸ばす(例: 30分を60分にする)
  - 解消しなければIssueを起票して指示する。例文: 「定期ループのトークン消費が内訳の半分を超えている。`.claude/loop.md` の手順から設計図の乖離確認を外して、消費を減らしてほしい」

### 2. レビューのやり直し回数の確認

なぜ: レビューの往復が多いのは、仕様が曖昧なまま実装が始まっているサイン。

- **どこを開くか**: 直近のマージ済みPRを一覧し、各PRのコメント欄を開く

```bash
gh pr list --state merged --limit 10
```

- **何を見るか**: PRコメントの「Codex Review(自動クロスレビュー)」の件数(=往復回数)
- **正常の目安**: 中央値2往復以内。5往復に達するとCIが自動で打ち切る
- **異常時の行動**:
  - 打ち切りに達したPRは「仕様の差し戻し」「タスクの分割」「PR破棄」のいずれかを指示する。どの場合もPRを閉じ、新しいブランチでやり直す(往復回数はheadブランチ単位で数えるため、同じブランチで作り直しても打ち切りのまま)
  - 4往復以上のPRが週に2件以上あれば、指摘を読んで原因を切り分け、Issueで指示する。仕様の曖昧さが原因なら例文: 「PR #12 でレビューが5往復し、原因は要件の解釈違いだった。`.kiro/settings/templates/` のrequirementsテンプレートに、受け入れ基準へ具体例を書く欄を追加してほしい」。指摘のブレが原因なら例文: 「PR #13 で同じ箇所に往復ごとに逆の指摘が出た。`.github/workflows/codex-review.yml` のプロンプトに、例外処理の方針を追記してほしい」

### 3. AIレビューの指摘をAIが不当に握りつぶしていないかの抜き取り確認

なぜ: 面倒な指摘を誤検知扱いで退けることを許すと、レビューが形だけになる。

- **どこを開くか**:

```bash
gh pr list --label codex-overruled --state all --limit 10
```

- **何を見るか**: 各PRのコメントに書かれた、指摘を退けた理由。次の3つの質問で確認する
  1. 退けた理由が、仕様・テスト結果・実際のコードの動作のどれかを根拠にしているか
  2. 「対応コストが高い」だけを理由にしていないか(コストは指摘を退ける理由にならない)
  3. 退けた指摘と同種の問題が、その後実際に起きていないか
- **正常の目安**: サンプリングしたすべてのPRで、3つの質問全部に「はい」と答えられる
- **異常時の行動**: 「いいえ」があるPRはIssueで対応を指示する。例文: 「PR #15 で退けられた『日付の境界値が未検証』という指摘は、根拠が『既存テストで十分』としか書かれていない。本修正として境界値テストを追加してほしい」

### 4. 指摘を退けた件数が増えすぎていないかの確認

なぜ: 退ける判定が増えるのは、レビューの指示文とプロジェクトの実態がずれてきたサイン。

- **どこを開くか**: 項目3と同じラベル一覧で、今週作成されたPRの件数を数える
- **何を見るか**: 今週、指摘を誤検知と判定した件数
- **正常の目安**: 週3件以内(初期値の提案)
- **異常時の行動**: 4件以上ならIssueで指示する。例文: 「今週の誤検知判定が5件あり、いずれもテスト網羅に関する指摘だった。`.github/workflows/codex-review.yml` のプロンプトに、テスト方針(ユニットテストの粒度)を追記して誤検知を減らしてほしい」

### 5. 何も検証していないJavaテストの検出状況と、検出を厳格化するかの判断

なぜ: 何も検証しないテストは、カバレッジの数字だけ稼いで品質を保証しない。

検出は静的解析ツールPMDのルール(UnitTestShouldIncludeAssert)で行う。現在は警告のみで、ビルドやPRを止めない。

- **どこを開くか**: GitHubのActionsタブ → 直近のPRの「Guardrails」実行 → java-assertion-reportジョブのSummary(backendに変更が無いPRでは実行されない)
- **何を見るか**: 検出件数と、それが誤検知(ヘルパーメソッド経由で検証しているテスト)かどうか
- **正常の目安**: 誤検知はPMDの設定に整理済みで、実検出が0
- **異常時の行動**:
  - 誤検知がある場合の例文: 「ResumeServiceTest#buildResume はヘルパーメソッド内で検証しているため誤検知。`backend/config/pmd/ruleset.xml` の extraAssertMethodNames に検証メソッド名を追加してほしい」
  - 実検出がある場合は、対象の振る舞いを検証するアサーションの追加を指示する
  - 実検出0が4週続いたら、`backend/gradle/quality.gradle` のPMD設定 ignoreFailures を false にする昇格を指示する。警告のみのまま放置しない

### 6. DependabotのPRが滞留していないかの確認

なぜ: DependabotのPRにはauto-mergeが予約されるため、検査が緑になれば自動でマージされる。開いたまま残っているPRは、検査が赤で止まっているか承認待ちのどちらかにあたる。とくにdockerのPRは、1本開いたまま止まるとそのイメージの次の更新PRも作られなくなるため、滞留がそのまま更新の停止を意味する。

- **どこを開くか**:

```bash
gh pr list --state open --author "app/dependabot"
```

- **何を見るか**: 開いたままのPRの件数と最も古いPRの作成日、各PRのチェックの状態
- **正常の目安**: 開いたままのPRが3件以内、かつ最も古いものが2週間以内(初期値の提案)
- **PRの種類ごとの対応**: 緑になり次第マージされるため、通常は何もしない。コードは読まない

| PRの種類 | 通常の状態 | 対応 |
|---|---|---|
| docker(ベースイメージ) | 自動マージ | 何もしない。赤で止まっている場合は下の「dockerのPRをcloseしない」を読む |
| backend(Gradle) | 自動マージ | 何もしない |
| frontend(脆弱性修正) | 自動マージ | 何もしない |
| GitHub Actions | 承認待ちで止まる | `.github/` はCODEOWNERS保護のため所有者のApproveが要る。差分が `uses: owner/repo@<40桁のSHA> # vX.Y.Z` の形のまま、SHAとコメントの両方が書き換わっていることだけ確認してApproveする。タグ参照(`@v6` など)に戻っていたらApproveせず、Issueで指示する |

- **そのほかの異常時の行動**:
  - dockerのPRに `@dependabot rebase` を使ってはいけない(理由は下の「dockerのPRをcloseしない」)
  - frontendのPRが `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` で落ちている場合は、公開から72時間経てば解消する。Issueは起票せず、時間をおいてチェックを再実行する
  - 上記以外のチェックが赤で止まっているPRは、原因を見てIssueで指示する。例文: 「Dependabotの #45 が frontend-test で落ちている。原因を調べて対応してほしい」
  - アラートが残っているのにPRが作られていない場合は、Security → Dependabot alerts で該当アラートのエラー内容を確認する。修正可能な版が無い、または依存解決ができないものにはPRが作られないため、通常のPRで対応する(Insights → Dependency graph → Dependabot は version updates のジョブログで、用途が違う)
  - frontend(npm)はversion updatesの対象外(pnpm 11未対応)。脆弱性修正のPRは作成され得るため確認対象に含め、バージョン更新は通常のPRで行う

#### マージ列で止まったとき

PRは必須チェックが緑になるとマージ列に入り、列の中で再検査されてからマージされる。
列の中で赤になったPRは自動で列から外れ、理由がPRのタイムラインに出る。

- **何を見るか**: PRのタイムラインの除外理由と、マージ列でのチェック結果
- **正常の目安**: 列に入ったPRが順にマージされ、滞留していない
- **異常時の行動**:
  - 特定のPRだけが落ちる場合は、そのPRの問題として扱う。通常のPRと同じくIssueで指示する
  - **どのPRを入れても同じチェックで落ちる場合は、そのチェックがマージ列に対応できていない。**
    Settings → Rules → Rulesets → `main` で **Require merge queue** を一時的に外し、
    原因のワークフローを直すIssueを起票する。無効化してもPRの必須チェックは効いたままになる
  - 列から手動で取り出すときはPR画面の **Remove from queue** を押す。`gh` では取り出せない
  - キューを無効化したあと、待機していたPRには `gh pr merge --auto --squash` を打ち直す。
    予約は冪等で、何度打っても問題ない

> `gh pr merge --auto --squash` はキューが有効な間、マージ方式がキュー側の設定で決まるため
> `--squash` を無視した旨の警告を出す。動作に影響はない。

#### dockerのPRをcloseしない

**closeすると、そのイメージの更新が恒久的に止まる。復旧経路は限られている。**

Dependabotは `イメージ名 + タグ + ディレクトリ` を照合キーにしており、digestを見ていない。`eclipse-temurin:21-jre` のようにタグが動かないイメージでは、一度closeするとその後の別digestへの更新PRも同じキーとしてブロックされ続ける。`@dependabot recreate` と `rebase` はcloseされたPRには効かず、`@dependabot reopen` コマンドは2026-01-27に廃止された。

closeしてしまった場合、PRのブランチが残っていて(削除済みならRestore branchで復元して)マージ済みでもなければ、**GitHubの標準UIでPRをReopenし、openになったPRに `@dependabot recreate` とコメントする**ことで復旧できる。Reopen自体をGitHubが拒否する場合は行き止まりになる。

開いたまま放置するのも解決にならない。定期ジョブは「同じキーのPRが既にある」と判断して打ち切るため、開いているPRが新しいdigestに更新されることはない。

赤で止まったときの出口は次の2つ。**どちらもcloseを含まない。**

| 出口 | 手順 | 使いどころ |
|---|---|---|
| A(既定) | 上流に新しいベースイメージが出て、**その公開から3日以上経ってから** PRに `@dependabot recreate` とコメントする。最新のdigestに更新されて緑になったらマージする | 通常はこちら |
| B | 抑制設定を入れてマージする | 上流の修正を待てない場合 |

**出口Aの3日待ちは厳守する。早打ちは「何も起きない」では済まない。** 公開から3日(Dependabotの既定のクールダウン)以内に `@dependabot recreate` を打つと、Dependabotは依存を最新と判定し、**開いているPRを自らcloseする**。closeは上記のとおり更新停止に直結するため、必ず3日待ってから打つ。`@dependabot rebase` も内部では同じ処理を通るため同様に危険で、dockerのPRのブランチ最新化にはコメントコマンドではなくPR画面の **Update branch** ボタンを使う。

**マージを保留したいときはauto-mergeの解除で行わない。** 解除してもDependabotのpushで予約が付け直される。保留は pre-merge-check ラベルをPRに付けて行う(必須チェックが赤になり、予約が残っていてもマージされない)。

### 7. Medium以下の指摘だけで通ったPRの抜き取り確認

なぜ: Blocker/High が無ければマージを止めない運用のため、Mediumの定義が広すぎると実害のある指摘が素通りする。

- **どこを開くか**: 項目2と同じマージ済みPR一覧から、Codex Reviewのコメントを開く
- **何を見るか**: Medium/Lowの指摘を残したままマージされたPRを1本選び、その指摘を読む
- **正常の目安**: 選んだPRの指摘が、保守性・可読性・テスト不足・文言の範囲に収まっている
- **異常時の行動**: 実行時の欠陥・検査のすり抜け・セキュリティに当たる内容がMediumに分類されていたら、`.github/workflows/codex-review.yml` の severity のアンカー定義の見直しをIssueで指示する。例文: 「PR #58 で『変更ファイルが多いと判定を誤る』という指摘がMediumで通った。実行時の誤判定はHighに分類されるよう、severity定義を直してほしい」

## 月次監査(目安30分)

### 1. わざと問題を入れたPRで、検査が機能しているかの点検

なぜ: 検査の仕組み自体が壊れても、普段のPRでは気づけない。

- **どこを開くか**:

```bash
gh pr list --label canary --state open
```

- **何を見るか**: カナリアPR5件のチェック結果が、期待どおり失敗しているか

| カナリアPR | 期待される失敗 |
|---|---|
| known-bug | codex-review が失敗(もっともらしいバグをレビューが検知) |
| assertless-test | frontend-test が失敗(何も検証しないテストをESLintが検知) |
| skipped-test | escape-hatch が失敗(テストのskip追加を検知) |
| backend-failure | backend-test が失敗(backendの変更が検知され、テストが実際に実行されている) |
| vulnerable-dep | dependency-review が失敗(pdfboxのアドバイザリを検知) |

- **正常の目安**: **5件すべてが存在し、かつ期待どおりのチェックで失敗している**
- カナリアPRはマージ列に入らない。auto-mergeを予約しておらず、常に赤で投入の条件を満たさないため
- **異常時の行動**: 次の3つは意味が違うので分けて扱う
  - **緑になっている**: 検出漏れ。Issueで指示する。例文: 「今月のカナリアで known-bug のPRがcodex-reviewを通過してしまった。/retrospective で原因を分析し、検査強化のIssueを起票してほしい」
  - **スキップされている**: これも検出漏れ。スキップは成功として扱われるため、検査が実行されていない状態でマージできてしまう。緑と同じ扱いでIssueを起票する
  - **PRが5件そろっていない**: カナリアの生成側が動いていない。`canary.yaml` の実行結果と `BOT_GITHUB_TOKEN` の有効期限を確認する
- **vulnerable-dep が緑だった場合の切り分け**: 経路の断絶(生成・送信・取り込み・比較のどこか)と、カナリアの失効(アドバイザリの取り下げ・格下げ)の2つがある。`gh api "/advisories?ecosystem=maven&affects=org.apache.pdfbox:pdfbox"` で該当のアドバイザリが残っているかを先に見る。残っていれば経路の断絶、消えていれば版を選び直す
- **後始末(毎回行う)**: 確認が済んだら5件のPRをクローズし、ブランチを削除する

### 2. テストが本当にバグを見つけられるかの測定結果の確認

なぜ: カバレッジが高くても、バグを検知できないテストでは意味がない。

- **どこを開くか**: GitHubのActionsタブ → 「Mutation Report」の最新実行 → Artifacts(stryker-report / pitest-report)
- **何を見るか**: frontend(Stryker)とbackend(PIT)それぞれの全体スコア
- **正常の目安**: 前月から5ポイント以上下がっていない(初期値の提案)
- **異常時の行動**: 5ポイント以上下がっていたらIssueで指示する。例文: 「backendのmutationスコアが72%から64%に低下した。レポートで検知漏れが集中しているdomain層の該当クラスに、壊した箇所を検知できるテストを追加してほしい」

### 3. すり抜けた問題の改善Issueが放置されていないかの確認

なぜ: 改善Issueが放置されると、同じすり抜けが繰り返される。

- **どこを開くか**:

```bash
gh issue list --label retrospective --state open
```

- **何を見るか**: openのままのIssueの内容と、作成からの経過期間
- **正常の目安**: 2ヶ月以上放置されているIssueが無い(初期値の提案)
- **異常時の行動**: 各Issueについて次のいずれかを行う
  - 承認が必要な強化案は、採否をコメントで指示する。例文: 「この強化案を採用する。escape-hatchチェックに検知パターンを追加するPRを作ってほしい」
  - 対応が完了しているものはcloseする
  - やらないと決めたものは、理由をコメントしてcloseする。例文: 「この事象は依存の更新で解消済みのため対応しない」

### 4. 自動更新の対象外になっているバージョン固定の確認

なぜ: 次の2つはDependabotが構造的に検知できず、誰も見なければ永久に古いまま残る。

- **どこを開くか**: `docker/terraform/Dockerfile` と、それぞれの最新版

| 固定しているもの | 書いてある場所 | 最新版の調べ方 |
|---|---|---|
| checkov | `pip install checkov==...` の行 | https://pypi.org/project/checkov/ |
| tflint | `COPY --from=ghcr.io/terraform-linters/tflint:...` の行 | https://github.com/terraform-linters/tflint/releases |

- **何を見るか**: 書いてあるバージョンと最新版の差
- **正常の目安**: マイナー版で2つ以内の差(初期値の提案)
- **異常時の行動**: 更新のIssueを起票する。例文: 「`docker/terraform/Dockerfile` の tflint が v0.60.0 のまま最新から離れている。最新版に更新し、`/verify-terraform` が通ることを確認してほしい」

## 半期ごと

### 1. レビュー基準が実態と合っているかの見直しと書き直し

なぜ: 基準を惰性で維持すると、実態と合わない検査を信じ続けることになる。

- **どこを開くか**: `REVIEW.md`、`.github/workflows/codex-review.yml` のプロンプト部分、`.github/scripts/check-escape-hatches.sh` の検知対象。あわせてこの半年のすり抜け実績を一覧する

```bash
gh issue list --label retrospective --state all
```

- **何を見るか**: 基準の各項目が、この半年の実績(実際にすり抜けたもの・一度も検知していないもの)と合っているか
- **正常の目安**: 基準のすべての項目について、なぜその項目があるのかを自分の言葉で説明できる
- **異常時の行動**: 説明できない項目・実績と合わない項目は、書き直しのPRを指示する。例文: 「この半年でPDF出力まわりのバグが2件すり抜けた。REVIEW.md の重大と判定する条件に帳票出力の検証を追加し、一度も検知していない○○の項目は削ってほしい」

### 2. AIレビューが使うモデルの見直し

なぜ: AIのモデルは廃止や世代交代が速く、放置するとレビューが突然失敗したり、安く高性能な選択肢を逃したりする。

- **どこを開くか**: `.github/workflows/codex-review.yml` の `--model` 指定と、OpenAIのAPI価格ページ(提供中のモデル一覧が載っている)
- **何を見るか**: 指定中のモデルがまだ提供されているか。後継や同等性能で安いモデルが出ていないか
- **正常の目安**: 指定中のモデルが提供中で、明らかに有利な後継が出ていない
- **異常時の行動**: モデル指定を更新するPRを指示する。例文: 「codex-reviewで指定中の gpt-5.6-terra の後継として GPT-5.7 系が出ている。価格と性能を確認し、`--model` の指定を更新してほしい」

### 3. テスト網羅率の基準値の引き上げ

なぜ: 実測との差が開いたまま放置すると、テストが減っても検査で気づけない。基準値は下げない運用のため、実測が上がったら基準値も追いかけて上げる。

- **どこを開くか**: 直近のCI実行(frontend-test / backend-test)のカバレッジ実測値と、基準値の定義ファイル(`frontend/vite.config.ts`・`backend/gradle/quality.gradle`)
- **何を見るか**: 実測値と基準値の差
- **正常の目安**: 差が5ポイント以内(初期値の提案)
- **異常時の行動**: 実測が基準値を安定して5ポイント以上上回っていれば、引き上げのPRを指示し、自分でApproveして反映する(基準値の定義ファイルは変更に所有者の承認が必要)。例文: 「frontendのLines実測が88%で基準値80%を3ヶ月上回り続けている。基準値を87%へ引き上げてほしい」

### 4. ランタイムとミドルウェアのメジャー版の棚卸し

なぜ: Dependabotはメジャー更新を除外している。ここが唯一の検知経路になる。放置するとサポート切れの版で動き続けることになる。

- **どこを開くか**: `docker/` 配下のDockerfileに書いてあるバージョンと、それぞれの提供元

| 対象 | 書いてある場所 | 見るもの |
|---|---|---|
| Java | `docker/backend/Dockerfile` / `Dockerfile.prod` の `eclipse-temurin` | https://adoptium.net/support/ のサポート期限 |
| Node.js | `docker/frontend/Dockerfile` の `node` | https://nodejs.org/en/about/previous-releases のサポート期限 |
| PostgreSQL | `docker/db/Dockerfile` の `postgres` | https://www.postgresql.org/support/versioning/ のサポート期限。本番のRDSのエンジン版も合わせて見る |
| Terraform | `docker/terraform/Dockerfile` の `hashicorp/terraform` | https://github.com/hashicorp/terraform/releases |
| Redis | `docker/redis/Dockerfile` の `redis` | https://github.com/redis/redis/releases |
| LocalStack | `docker/localstack/Dockerfile` の `localstack/localstack` | https://github.com/localstack/localstack/releases 。年.月のバージョン表記のため、年が変わるタグ更新はメジャー扱いで除外される |
| Docker(dind) | `docker/dind/Dockerfile` の `docker` | https://docs.docker.com/engine/release-notes/ |

- **何を見るか**: 使っている版のサポート期限と、次のメジャー版が出ているか
- **正常の目安**: サポート期限まで1年以上ある
- **異常時の行動**: メジャー更新のIssueを起票する。例文: 「Java 21 のサポート期限が近い。Java 25 への更新を検討し、影響範囲を調べてIssueに追記してほしい」

## 人間の承認が必要なPRを承認するときの手順

DBマイグレーション・ライブラリの入手先やビルド設定の変更・チェック設定の変更を含むPR、および人間がIssueに pre-merge-check ラベルを付けたPRは、人間の承認が無いとマージされない。

**依存のバージョンを上げるだけのPRは承認の対象ではない。** `package.json` `pnpm-lock.yaml` `libs.versions.toml` `gradle-wrapper.properties` の変更は、次の3つの検査が代わりを務める。承認を求められなくなった代わりに、この3つが機能しているかを監査で見る。

| 検査 | 何を止めるか |
|---|---|
| dependency-review | そのPRで新しく増えた脆弱性 |
| dependency-cooldown | 公開から72時間を経過していないライブラリ |
| gradle-wrapper | 公式でない配布元・公表値と異なるチェックサム |

1. **承認ボタンを押す順番**: Codexレビューの指摘対応が終わり、CIの必須チェックがすべて成功した最後の段階で押す。承認後にコミットが積まれると承認は自動で無効になり、再承認が必要になる(安全側の正しい動きなので変更しない)
2. **DBマイグレーションを含むPR**: 承認する前に、必ずローカルで適用と巻き戻しを確認する

   ```bash
   docker compose exec -w /home/spring/app backend ./gradlew flywayInfo
   ```

   対象ブランチを `./start-dev.sh` で起動してマイグレーションが適用されること、後方互換を保つ2段階変更(追加だけを先に行い、削除や制約強化は次のリリースに分ける)になっていることを確認してからApproveする
3. **ライブラリの入手先、またはbackendのビルド設定の変更を含むPR**: PR本文の変更理由と代替検討を読み、採否を判断してApproveする。対象は次の4つで、中身によらず変更そのものが承認対象になる

   | ファイル | なぜ機械の検査で代替できないか |
   |---|---|
   | `frontend/.npmrc` | ライブラリの入手先を差し替えられる。dependency-review は名前とバージョンしか見ず、入手先を検証しない |
   | `frontend/.pnpmfile.cjs` / `.pnpmfile.mjs` | インストール時に実行されるコードそのもの |
   | `frontend/pnpm-workspace.yaml` | 差し替えと待機期間の設定を含む。防御の設定そのものを機械の防御では守れない |
   | `backend/**/*.gradle` `*.gradle.kts` | 任意のコードであり、入手先の定義を含む。バージョンだけの変更かを静的に判別できない |

4. **pre-merge-check ラベルを付けたPR**: 対象ブランチを `./start-dev.sh` で起動して画面を確認し、問題がなければApproveする。問題があればPRコメントで具体的に指摘して差し戻す(Issueの再起票はしない)。承認後にコミットが積まれると承認は無効になり、このチェックも赤に戻る(手順1と同じ)
5. **チェック設定の変更を含むPR**: 変更が「チェックを弱める方向」でないことを確認する。該当する場合は、正当な理由(retrospectiveのIssue等)がPR本文に書かれているかを確認し、無ければ理由を質して Request changes で差し戻す。弱める方向の具体例は次のとおり
   - 閾値の引き下げ(カバレッジ基準・PRサイズ上限の緩和)
   - 検知対象の削除(検査回避チェックの検知パターンを消す等)
   - 除外の追加(除外リスト・静的解析の除外設定への追加)
   - 必須チェックの削除や、実行をスキップする条件の追加
   - CODEOWNERSからの保護パスの削除

## 自動チェックの一覧(監査対象)

監査で見るべき自動チェックの全体像。どれかが機能しなくなっていないかをカナリア結果・すり抜け実績から確認する。

| 種類 | 実体 | 何を防ぐか |
|---|---|---|
| テストとカバレッジ基準 | Vitest / JUnit(Testcontainers)、カバレッジ基準値(vite.config.ts / quality.gradle) | ロジックの破壊、テストの薄い変更 |
| 静的解析 | ESLint(境界ルールとsonarjs)/ tsc / ArchUnit / Checkstyle / SpotBugs / tflint / checkov | アーキテクチャ境界の違反、アサーションの無いテスト、型の逸脱 |
| 検査回避の検知 | escape-hatchチェック(guardrails.yaml) | テストのskip化、@Disabledや@ts-ignoreの追加、インラインでのlint無効化、アサーションの削除、品質チェック配線の改変 |
| 差分サイズの検査 | size-check(guardrails.yaml) | 仕様書の裏付けなしにコード差分200行を超える変更が入ること(注1) |
| 依存の脆弱性検査 | dependency-review(dependency-review.yaml) | そのPRで新しく増えた、moderate以上の既知の脆弱性。開発依存も対象で、既存の依存では赤にならない(注2) |
| 依存グラフの空洞化の検知 | check-dependency-snapshot(dependency-review.yaml / dependency-graph.yaml) | 依存解決が空のまま送信されること。空のスナップショットが送られると、脆弱性とクールダウンの検査が「追加0件」と判定して緑になり、backendのDependabotアラートも出なくなる。捉えるのは「空」までで、部分的に欠けたグラフと、送信より後の区間は月次のカナリア(vulnerable-dep)が受け持つ |
| 公開直後の版の遮断(backend) | dependency-cooldown(dependency-review.yaml) | 公開から72時間を経過していないライブラリ。そのPRで新しく追加されたものを、推移的依存とGradleプラグインまで含めて見る(注3) |
| Gradle本体の検証 | gradle-wrapper(guardrails.yaml) | ビルドが取得するGradle本体が公式のものでなくなること。配布元ホストが `services.gradle.org` であること、チェックサムと `gradle-wrapper.jar` が公式リリースと一致することを見る。wrapper関連の変更が無いPRでは外部への問い合わせを行わず通す |
| 入手先と防御設定の検査 | dependency-gate | ライブラリの入手先(`.npmrc`)、インストール時に実行されるコード(`.pnpmfile.*`)、差し替えと待機期間の設定(`pnpm-workspace.yaml`)、backendのビルドスクリプト(`*.gradle` `*.gradle.kts`)が承認なしに変更されること。中身は解析せず変更の有無で判定する。バージョン宣言そのものは対象外で、上の3つの検査が代わりを務める |
| コンテナイメージのビルド確認 | docker-smoke(ci.yaml) | ベースイメージの更新でDockerfileがビルドできなくなること。Dockerfileの変更だけではテスト系のジョブが動かないため、変更されたDockerfileを実際にビルドして確認する。検証はamd64で行い、arm64に固有の破綻はリリース時のビルドで検知する |
| IaCの静的検査 | terraform-static(terraform-plan.yaml) | フォーマット崩れ・構文と参照の誤り・tflintの指摘・checkovの新規指摘(注4) |
| アクション参照の固定 | check-action-pinning(guardrails.yaml) | `uses: owner/repo@<40桁のSHA> # vX.Y.Z` 以外の形式のアクション参照。タグは上流で差し替え可能で、こちらを変更しなくても実行内容が変わり得るため |
| 公開直後の版の遮断(frontend) | pnpm の minimumReleaseAge(72時間) | 公開から72時間以内のパッケージのインストール。悪意ある版は数時間で削除されるため、寝かせることで大半を避ける。ただし公開日時のメタデータが無いパッケージは素通りする(`minimumReleaseAgeIgnoreMissingTime` の既定が true のため) |
| DBマイグレーションの承認 | CODEOWNERS(migrationディレクトリ) | スキーマ変更が人間の確認なしにマージされること |
| チェック設定の保護 | CODEOWNERS + settings.jsonの編集拒否 | 品質チェックの設定がAIの判断で変更されること |
| シークレットスキャン | gitleaks | 認証情報などの混入 |
| 別AIによるレビュー | codex-review(判定はジョブの成否で行い、コメントの偽装は効かない) | バグ、セキュリティ問題、仕様との不一致、チェックを形だけ通す変更 |
| リリースの分離 | release.yaml(手動実行) | マージだけで本番に反映されること |
| 健全性の確認 | canary.yaml(月次) | チェックの仕組み自体が気づかないうちに壊れること |

- 注1: specの実在・必須4ファイル・プレースホルダ残存・spec.jsonの3段階承認フラグを検証する。承認フラグはAIの自己申告であり、人間が承認した証明にはならない(受容済みリスク: #177)
- 注2: baseとheadの依存グラフを比較する。backendの基準は、mainへのpushで dependency-graph.yaml が送信したスナップショット。required status check には generate / submit / review の3つすべてを指定すること。1つでも外すと、そのジョブが失敗したときに後続がスキップ(Success扱い)になり、検査されないままマージされる。フォークPRでは送信ジョブがスキップされ、Gradleの差分は未検査になる(受容済み)
- 注3: Dependabotが作成したPRは対象外(自動化側の待機期間が効いており、脆弱性対応の更新を遅らせないため)。フォークPRも対象外(スナップショットが送られず追加を特定できない)。公開時刻を取得できない場合、スナップショットが揃っていない場合、比較APIが失敗した場合はいずれも赤になる
- 注4: checkovの既存67件は `terraform/.checkov.baseline` で凍結してあり、baselineに無い指摘が出れば赤になる。checkovはDockerfileでバージョンを固定しており、更新は人間が明示的に行う。baselineを作り直すときは `.checkov.yaml` の `baseline:` 行を一時的に外してから実行する(有効なまま `--create-baseline` するとbaselineが空になる)

## 受容した残余リスク

機械の検査で守れないと分かったうえで受け入れているもの。半期に一度、増えていないかを見る。増えている場合は、検査の追加で埋められないかを検討する。

### 1. Gradle本体の検証は信頼の根が1つしかない

gradle-wrapper は配布元ホストを `services.gradle.org` に固定し、同じホストが公表するチェックサムと照合する。配布元が侵害されると配布物と公表値の両方が同時に偽装されるため、実質的に効いているのはホストの固定で、チェックサムの照合は手作業による書き換えとの不整合検知と位置づけている。あわせて、Gradle自身のチェックサム検証はダウンロード時にしか行われず、キャッシュ済みの環境では誤った値でも素通りする。ローカルで確認するときはキャッシュを削除してから実行する。

### 2. プロジェクト自身の `package.json` に任意のコマンドを書ける

pnpm 10 以降、依存パッケージのインストール時スクリプトは既定で実行されないが、遮断されるのは依存パッケージのものだけで、`frontend/package.json` の `scripts` に書いたコマンドは実行される。`package.json` を承認の対象から外したため、この経路は機械の検査を通らない。エージェントが書いたコードがCIと開発環境で実行されることは既に受け入れている範囲であり(`src` のコードもテストも同じ)、新しい信頼水準を要求するものではないと判断した。

### 3. フォークからのPRではbackendの依存が検査されない

フォークPRでは書き込み権限が得られず、依存グラフのスナップショットを送信できない。このため dependency-cooldown は対象外になり、dependency-review もfrontendしか見られない。このリポジトリのPRはすべて所有者のbotが同一リポジトリのブランチから作る運用であり、フォークPRは初回コントリビュータのワークフロー実行承認と人間のレビューを経る。

## 緊急時対応(本番を前の状態に戻す)

- frontend: Actionsの「Frontend Rollback」に、過去の成功したCI runのIDを指定して実行する
- backend: ECSタスク定義を前のリビジョンへ戻す(`doc/インフラ設計/手順書/手動作業手順.md`)
- DB: 後方互換を保つ2段階変更の運用により、直前リリースとの互換が保たれている
