# 参加者セットアップ手順

開発に参加する人が、自分のPCごとに行う作業の手順書。上から順に実施する。
PCを再セットアップしたときも、この手順を最初からやり直す。

> 前提: [基盤構築手順](基盤構築手順.md) の、botアカウントの作成と、GitHub App を作ってインストールする手順が完了しており、
> App の秘密鍵のファイル、App の Client ID、インストールの番号を所有者から受け取っていること。

## 1. CLIのインストール(ホストOS)

### 1-1. GitHub CLI のインストールとログイン

Windows:

```bash
winget install --id GitHub.cli
```

macOS/Linux:

```bash
brew install gh
```

**自分のGitHubアカウント**(botアカウントではない)でログインする:

```bash
gh auth login
```

所有者は、`gh auth login` の対話でログインせず、[基盤構築手順](基盤構築手順.md) の、
所有者の gh の鍵を fine-grained PAT に作り直す手順のとおりにログインする。

### 1-2. Claude Code CLI のインストール

Windows:

```bash
winget install Anthropic.ClaudeCode
```

macOS/Linux:

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

ターミナルを開き直し、`claude --version` が返ることを確認する。

## 2. コミット・PR作成・push名義の固定

### 2-1. コミット名義の固定(git config)

リポジトリルートで一度だけ実行する:

```bash
git config user.name "DogisRiki-bot"
```

```bash
git config user.email "<botアカウントのnoreplyメールアドレス>"
```

確認する。botのアカウント名が返ればよい:

```bash
git config user.name
```

### 2-2. PR作成名義の固定(bot専用のgh設定ディレクトリ)

bot専用のgh設定ディレクトリを作り、そこに GitHub App の秘密鍵と設定を置いて、App のトークンを入れる。

ホストOSのターミナルで、**その端末に限って** `GH_CONFIG_DIR` を設定する。

Windows(PowerShell):

```bash
mkdir "$env:USERPROFILE\.gh-bot" -Force
```

```bash
$env:GH_CONFIG_DIR = "$env:USERPROFILE\.gh-bot"
```

macOS/Linux:

```bash
mkdir -p "$HOME/.gh-bot"
```

```bash
export GH_CONFIG_DIR="$HOME/.gh-bot"
```

前に `.gh-bot` へbotアカウントでログインしていた場合は、同じ端末でログアウトする
(ログインしていなかった場合は飛ばす):

```bash
gh auth logout --hostname github.com
```

続けて、所有者から受け取った App の秘密鍵のファイルを `.gh-bot` に移す。
`<秘密鍵のファイル>` は、受け取ったファイルのパスにする。

Windows(PowerShell):

```bash
Move-Item "<秘密鍵のファイル>" "$env:USERPROFILE\.gh-bot\github-app.private-key.pem"
```

macOS/Linux:

```bash
mv "<秘密鍵のファイル>" "$HOME/.gh-bot/github-app.private-key.pem"
```

続けて、`.gh-bot` に `github-app.env` を作る。`<Client ID>` と `<インストールの番号>` は、
所有者から受け取った値にする。

Windows(PowerShell):

```bash
Set-Content -Encoding ascii -Path "$env:USERPROFILE\.gh-bot\github-app.env" -Value "APP_CLIENT_ID=<Client ID>", "INSTALLATION_ID=<インストールの番号>", "PRIVATE_KEY_FILE=$env:USERPROFILE\.gh-bot\github-app.private-key.pem"
```

macOS/Linux:

```bash
printf 'APP_CLIENT_ID=%s\nINSTALLATION_ID=%s\nPRIVATE_KEY_FILE=%s\n' "<Client ID>" "<インストールの番号>" "$HOME/.gh-bot/github-app.private-key.pem" > "$HOME/.gh-bot/github-app.env"
```

置いたものを確かめる。1つ目は `APP_CLIENT_ID=`、`INSTALLATION_ID=`、`PRIVATE_KEY_FILE=` で始まる3行が出ればよく、
2つ目は `True`(macOS/Linuxではファイルの名前)が出ればよい。

Windows(PowerShell):

```bash
Get-Content "$env:USERPROFILE\.gh-bot\github-app.env"
```

```bash
Test-Path "$env:USERPROFILE\.gh-bot\github-app.private-key.pem"
```

macOS/Linux:

```bash
cat "$HOME/.gh-bot/github-app.env"
```

```bash
ls "$HOME/.gh-bot/github-app.private-key.pem"
```

続けて、同じ端末のリポジトリルートで、App のトークンを入れる。何も出力されずに終わればよい。
`refresh-token.sh:` で始まる文が出たら、その文が指すファイル(`github-app.env` か秘密鍵)を直してやり直す。

Windows(PowerShell):

```bash
& "C:\Program Files\Git\bin\bash.exe" .claude/scripts/github-app/refresh-token.sh --force
```

macOS/Linux:

```bash
bash .claude/scripts/github-app/refresh-token.sh --force
```

次に、リポジトリルートに `.claude/settings.local.json` を作成する。`<user>` は実際のユーザー名にし、
`$HOME` や `%USERPROFILE%` は使わず絶対パスで書く(環境変数は展開されない)。

Windows:

```json
{
    "env": {
        "GH_CONFIG_DIR": "C:\\Users\\<user>\\.gh-bot"
    }
}
```

macOS(Linuxでは `/home/<user>/.gh-bot`):

```json
{
    "env": {
        "GH_CONFIG_DIR": "/Users/<user>/.gh-bot"
    }
}
```

確認は4つとも行う。

1. トークンを入れた端末で次を実行し、github.com にログインしていることが表示され、誤りが出ないこと

```bash
gh auth status
```

2. トークンを入れた端末で次を実行し、KeirekiPro のリポジトリの説明が表示されること

```bash
gh repo view DogisRiki/KeirekiPro
```

3. **新しく開いた**ターミナルで次を実行し、**自分のアカウント名**が返ること。
   返らない場合は、その端末で 1-1 のとおりにログインし直して自分のアカウントに戻す

```bash
gh api user --jq .login
```

4. Claude Codeを再起動し、エージェントに「`gh repo view DogisRiki/KeirekiPro` を実行して結果を報告して」と
   依頼して、KeirekiPro のリポジトリの説明が返ること

> 注意: `GH_CONFIG_DIR` を常設の環境変数にしない。Windowsの `setx` も、macOS/Linuxの
> シェルのプロファイルへの追記も不可。人間のターミナルのghとgit pushまでbot名義になる。

> 注意: `.claude/settings.local.json` と `.gh-bot` ディレクトリ(`github-app.env` と秘密鍵を含む)は、どちらもgit管理外。
> PCの再セットアップ時は両方を作り直す。忘れるとPRが人間の名義になり、
> 保護パスを含むPRがマージ不能になる。

### 2-3. push名義の固定(HTTPS + gh の資格情報ヘルパー)

リモートをHTTPSにし、認証をghへ委ねる。リポジトリルートで一度だけ実行する:

```bash
git remote set-url origin https://github.com/DogisRiki/KeirekiPro.git
```

```bash
git config credential.https://github.com.helper ""
```

```bash
git config --add credential.https://github.com.helper "!gh auth git-credential"
```

2つ目は、グローバル設定のヘルパー(Git Credential Manager等)を打ち消すためのもの。
空を設定してからghのヘルパーを追加しないと、そちらが先に応答して人間の資格情報が使われる。

確認は2つとも行う。

1. Claude Codeのセッションでpushし、成功すること(GitHub App のトークンが使われる)
2. 人間がターミナルで次を実行し、成功すること(ghのkeyringの自分のアカウントが使われる)

```bash
git push --dry-run
```

> 注意: リモートをSSHにしない。SSH鍵はアカウントに紐づくため、セッション内のpushも
> 鍵の持ち主(人間)名義になり、名義の分離が崩れる。

## 3. Context7 MCP のAPIキーの環境変数設定(ホストOS)

Windows:

```bash
setx CONTEXT7_API_KEY "<Context7のAPIキー>"
```

macOS/Linux はシェルのプロファイル(`~/.zshrc` 等)に追記する:

```bash
export CONTEXT7_API_KEY="<Context7のAPIキー>"
```

## 4. LocalStack 認証トークンの設定

LocalStackは2026.03.0以降、非商用利用でもアカウント登録と認証トークンが必須になった。
旧Communityイメージ相当の機能は、非商用向けの無料プラン(Hobby)で利用できる。

### 4-1. アカウント作成とトークンの取得

1. [LocalStack Web Application](https://app.localstack.cloud/sign-up) でアカウントを作成する
2. ワークスペースのプランは無料の **Hobby**(非商用利用向け)を選択する
3. [Auth Tokens ページ](https://app.localstack.cloud/workspace/auth-tokens) を開き、認証トークンをコピーする

### 4-2. `.env.local` への記載

`docker/localstack/.env.local` が無ければ、リポジトリルートでexampleからコピーして作成する

```bash
cp docker/localstack/.env.local.example docker/localstack/.env.local
```

`.env.local` を編集し、次の1行を追記する:

```dotenv
LOCALSTACK_AUTH_TOKEN=<コピーした認証トークン>
```

確認する。localstackコンテナを作り直し、状態が `Up` になればよい:

```bash
docker compose up -d --force-recreate localstack
```

```bash
docker compose ps localstack
```

> 注意: 認証トークンはgit管理外の `.env.local` にのみ書き、コミットしない(`.gitignore` で除外済み)。
> 誤って公開した場合は、LocalStack Web Applicationでトークンを再発行する。

## 5. 本番を変えるターミナル(ops-shell)の設置

所有者だけが、自分のWindowsのPCで行う。所有者は、障害のときにこのターミナルで AWS を変える。

> 前提: [手動作業手順](../インフラ設計/手順書/手動作業手順.md) の「1.1 必要なツールのインストール」のとおり
> AWS CLI が入っており、普段のターミナルで `aws login` していること。

### 5-1. スクリプトと設定ファイルの設置

所有者は、スタートメニューで PowerShell を右クリックし、「管理者として実行」で開く。
以降のコマンドは、すべてこの管理者の PowerShell で実行する。

最新の main を取り込んだリポジトリルートに移る。`<リポジトリルート>` は実際のパスにする:

```bash
Set-Location "<リポジトリルート>"
```

AWS CLI が決まった場所にあることを確かめる。`True` が出ればよい:

```bash
Test-Path "C:\Program Files\Amazon\AWSCLIV2\aws.exe"
```

AWS のアカウントの番号を取る。2つ目のコマンドで `True` が出ればよい。
`False` が出たら、普段のターミナルで `aws login` してから、1つ目のコマンドからやり直す:

```bash
$accountId = aws sts get-caller-identity --query Account --output text
```

```bash
$accountId -match '^\d{12}$'
```

置き場を作り、`ops-shell.ps1` と `aws-config` の `<ACCOUNT_ID>` をアカウントの番号に置き換えて置く:

```bash
New-Item -ItemType Directory -Force "C:\Program Files\KeirekiPro"
```

```bash
(Get-Content -Raw "doc\インフラ設計\手順書\ops-shell\ops-shell.ps1").Replace('<ACCOUNT_ID>', $accountId) | Set-Content -NoNewline -Encoding ascii "C:\Program Files\KeirekiPro\ops-shell.ps1"
```

```bash
(Get-Content -Raw "doc\インフラ設計\手順書\ops-shell\aws-config").Replace('<ACCOUNT_ID>', $accountId) | Set-Content -NoNewline -Encoding ascii "C:\Program Files\KeirekiPro\aws-config"
```

同じ場所に、空の `empty-credentials` を作る:

```bash
New-Item -ItemType File -Force "C:\Program Files\KeirekiPro\empty-credentials"
```

確認は2つとも行う。

1. 次を実行し、何も出力されないこと(`<ACCOUNT_ID>` が残っていない)

```bash
Select-String -SimpleMatch -Pattern '<ACCOUNT_ID>' -Path "C:\Program Files\KeirekiPro\ops-shell.ps1", "C:\Program Files\KeirekiPro\aws-config"
```

2. 次を実行し、`0` が出ること(`empty-credentials` が空である)

```bash
(Get-Item "C:\Program Files\KeirekiPro\empty-credentials").Length
```

### 5-2. スタートメニューの項目「KeirekiPro ops」の作成

5-1 と同じ管理者の PowerShell で、全利用者のスタートメニューに項目を作る:

```bash
$lnkPath = "C:\ProgramData\Microsoft\Windows\Start Menu\Programs\KeirekiPro ops.lnk"
```

```bash
$lnk = (New-Object -ComObject WScript.Shell).CreateShortcut($lnkPath)
$lnk.TargetPath = "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe"
$lnk.Arguments = '-NoProfile -NoExit -ExecutionPolicy Bypass -File "C:\Program Files\KeirekiPro\ops-shell.ps1"'
$lnk.Save()
```

続けて、項目に「管理者として実行」を付ける:

```bash
$bytes = [System.IO.File]::ReadAllBytes($lnkPath)
$bytes[0x15] = $bytes[0x15] -bor 0x20
[System.IO.File]::WriteAllBytes($lnkPath, $bytes)
```

確認は2つとも行う。

1. 次を実行し、1行目に `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`、
   2行目に `-NoProfile -NoExit -ExecutionPolicy Bypass -File "C:\Program Files\KeirekiPro\ops-shell.ps1"` が出ること

```bash
$check = (New-Object -ComObject WScript.Shell).CreateShortcut($lnkPath); $check.TargetPath; $check.Arguments
```

2. 所有者がスタートメニューの「KeirekiPro ops」を左クリックで開き、Windows の確認の画面(ユーザーアカウント制御)が出ること。
   「はい」を押すと、6桁のコードを求める表示が出る。ここではコードを入れずにウィンドウを閉じる。
   変更用ロールへの切り替えは、[手動作業手順](../インフラ設計/手順書/手動作業手順.md) の手順で確かめる

> 注意: PCを再セットアップしたときと、リポジトリの `doc/インフラ設計/手順書/ops-shell/` のファイルが変わったときは、
> 5-1 と 5-2 をやり直す。

ここまでで、参加者セットアップは完了。spec駆動開発のコマンド(`/kiro-*`)とテンプレートは
リポジトリにコミット済みのため、クローンすればそのまま使える。各自のインストール作業は無い。
