# start

Issueに着手するときの手順。**所有者がすることは、spec が要るかどうかに依らず `/start #<Issue番号>` の1つだけにする。** spec が要るかどうかは所有者には判断できないため、AIがIssueの本文とその時点のコードを調べて決める。

- 進め方を決めるのはこのスキルだけである。ほかのスキル(file-issue、ship など)は、このスキルが決めた進め方に従って呼ばれる
- AIは状態を自分で覚えておかない。進み具合は、GitHub のIssue(親子と開閉)と spec.json から毎回読み直す。所有者が問いに答えたことは、AIがIssueの本文の「## 決めた方式」の節に書き足すので、会話が途切れても、AIはIssueの本文から答えを読み直せる

## 手順

### 着手するIssueの番号を確かめる

引数が無いとき、または引数からIssueの番号が読めないときは、AIは所有者に番号を尋ね、答えを待つ。

### Step 1: Issueを読む

AIは次のコマンドでIssueを読む。

```bash
gh issue view <N> --json number,title,body,state,url,parent,subIssues,subIssuesSummary
```

- `comments` は取得しない。`--comments` も付けない。コメントは進め方を決めるときの要望として扱わず、本文だけを基準にする
- 返る欄の形(2026-10-02 に #472、#466 で確かめた):
  - `state`: Issueは `OPEN` か `CLOSED`。gh issue view はPRの番号も失敗せずに読めてしまい、開いているPRは `OPEN` を返す。そのため `state` だけではIssueかPRかを見分けられない
  - `url`: Issueは `https://github.com/<owner>/<repo>/issues/<N>`、PRは `.../pull/<N>` になる。IssueかPRかはこの欄で見分ける
  - `parent`: 親が無ければ `null`
  - `subIssues`: `nodes`(分けた部分のIssueの一覧)と `totalCount`
  - `subIssuesSummary`: `total`(分けた部分の数)、`completed`(閉じた数)、`percentCompleted`
- 番号のIssueが無いとき(gh が「Could not resolve to an issue or pull request」と返す)は、AIは着手せず、そのIssueが無いことを所有者に伝えて終える
- `url` に `/pull/` を含むときは、その番号はPRの番号で、その番号のIssueは無い。AIは着手せず、#<N> はIssueではなくPRの番号であることを所有者に伝えて終える
- `state` が `OPEN` でないとき(閉じたIssue)は、AIは着手せず、そのIssueが閉じていることを所有者に伝えて終える
- それ以外の理由で gh の問い合わせに失敗したとき(認証やネットワークの失敗など)は、AIは進め方を判断せず、問い合わせに失敗したことと gh のエラーの文面を所有者に伝えて終える。推測で進めない

### Step 3: 分けてあるかを見る

AIは、この Step を、Step 1 のすぐあと、Step 1.5 より前に行う。

`subIssuesSummary.total` が1以上なら、このIssueはすでに分けて進められている。分けてあるIssueは着手の対象でないので、AIは分け方を決め直さず、Step 1.5 の `check-start` も呼ばない。実装の途中で分けた元のIssueの記録はブランチ付きで残るので、Step 1.5 を先に行うと、元のIssueに `/start` を打つたびに「続きから進めるか」と尋ねてしまうためである。

AIは `subIssues.nodes` から、分けた部分のIssueの番号・題名・開いているか閉じているかを一覧で示して終える。あわせて、所有者に、部分ごとに `/start #<分けた部分のIssueの番号>` を打つよう案内する。

```markdown
## してほしいこと
まだ開いている部分に着手するときは、部分ごとに `/start #<番号>` を打ってください。

## 分けた部分のIssue(全<total>件、閉じたもの<completed>件)
| 番号 | 題名 | 状態 |
|---|---|---|
| #<番号> | <題名> | 開いている / 閉じている |
```

`subIssuesSummary.total` が0なら、AIは Step 1.5 へ進む。

### Step 1.5: ほかのセッションとIssueの作りかけを調べる

AIは、同じ作業フォルダで作業中のほかのセッションと、Issue #N の作りかけ(spec、ブランチ、コミットしていない変更)が残っていないかを調べる。調べ終わるまで、AIは spec もブランチも作らない。

1. AIは、このセッションのIDを、会話の始めに SessionStart のフックが渡した `[parallel] このセッションのID: <ID>(並行作業のスクリプトに --session で渡す)` の文から取る。文が見つからなければ、AIは、この Step と Step 5.5、Step 7、「分けたあとの進め方」「ブランチの扱い」で呼ぶ `session.sh` のどのサブコマンドにも `--session <ID>` を付けずに呼ぶ
2. AIは次のコマンドで調べる。標準出力に JSON が1行出る。`check-start` は最初に片付け(`prune`)を行うので、終了コード0でも、片付けられなかったものの文が標準エラーに出ることがある。AIは、その文を JSON として読まない。片付けで消せなかったボリュームと DB の文(`[parallel] 消せなかった名前:` で始まる文)が標準エラーに出たときは、AIは、`[parallel]` で始まる標準エラーの行をすべて所有者に伝える。消せなかった理由(Docker につながらない、db が動いていない、など)は、名前とは別の行に出るためである。この文が出ても `check-start` の終了コードは0なので、AIは3の JSON の欄の扱いを続ける

   ```bash
   bash .claude/scripts/parallel/session.sh check-start <N> --session <ID>
   ```

   `check-start` は、`folder_conflict` `leftovers` `branch_only` がすべて空のときに、Issue #N の着手の予約を書く。この予約は、ほかのセッションが呼ぶ `check-start` には、`leftovers` の要素の種類(`kinds`)が `started` の作りかけとして見える

   終了コードが0でないとき(64 は呼び方の誤り、69 は git のリポジトリの外・設定の値の誤り・記録の錠を取れない・記録や予約を書けない)は、AIは着手せず、終了コードと標準エラーの文を所有者に伝えて止まる。推測で進めない
3. AIは、JSON の欄ごとに、次の表で所有者に出す問いと、答えに応じて呼ぶサブコマンドを決める。表の `session.sh` は `bash .claude/scripts/parallel/session.sh` を指し、どのサブコマンドにも1で取ったIDを `--session <ID>` で付ける(`end` は除く)

| JSON の欄 | AIが所有者に出す問い | 答えに応じて呼ぶサブコマンド |
|---|---|---|
| `folder_conflict` が空でない | やめたか | 「やめた」なら `session.sh end <ID>`(`<ID>` は要素の `session_id`) |
| `leftovers` の要素で `kinds` が `started` だけ | やめたか | 「やめた」なら `session.sh end <ID>`(`<ID>` は要素の `active_session` の `session_id`) |
| `leftovers` の要素で `is_self` が真 | 続きから進めるか | 「進める」なら `session.sh takeover <N> --from <いまの作業フォルダ>`(要素の `folder` と同じ) |
| `leftovers` の要素で `is_self` が偽、`active_session` が `null` でない | やめたか | 「やめた」なら `session.sh takeover <N> --from <folder>` |
| `leftovers` の要素で `is_self` が偽、`active_session` が `null` | 続きから進めるか | 「進める」なら `session.sh takeover <N> --from <folder>` |
| `branch_only` が空でない | ブランチ <branch> の続きから進めるか | 「進める」なら `session.sh takeover <N> --branch <branch>` |
| `capacity.active` の数が `capacity.limit` 以上 | 問いは出さない | なし |

- AIは、表の上の行から順に扱う。`folder_conflict` を、Issueの作りかけ(`leftovers` と `branch_only`)より先に扱う
- 問いを出すときは、AIは止まって所有者の答えを待つ。問いには、相手のセッションか作りかけを特定できることを添える。`folder_conflict` では、要素の `session_id` と、`started_at`(始めた時刻)と `last_seen`(最後に操作された時刻)を読める日時にしたもの。`leftovers` の要素で `kinds` が `started` だけのものでは、作業フォルダの場所(`folder`)と、そのセッションを始めた時刻と最後に操作された時刻(`active_session` の `started_at` と `last_seen` を読める日時にしたもの)と、そのセッションがまだブランチを作っていないこと。そのほかの `leftovers` の要素では、作りかけが残っている作業フォルダの場所(`folder`)、作りかけの種類(`kinds`)、ブランチ(`branch`)、その作業フォルダで作業中のセッションがあるかどうか(`active_session`)。`branch_only` では、残っているブランチの名前(`branch`)
- `folder_conflict` の問いには、同じ作業フォルダで別のセッションが作業中であることと、そのセッションをやめていないなら worktree を選んでセッションを開き直してほしいことを添える。要素が複数あるときは、要素ごとに尋ねる
- `kinds` に `started` のほかの種類もある `leftovers` の要素は、AIは `kinds` が `started` だけの行ではなく、その下の `leftovers` の行で扱う。この要素の `active_session` は `null` でないので、AIは「やめたか」を尋ね、「やめた」なら `session.sh takeover <N> --from <folder>` を呼ぶ。どちらの行でも、AIは1つの要素につき1回だけ尋ねる
- `leftovers` の要素が複数あるときは、AIはすべての場所を示したうえで、要素ごとに1つずつ尋ねる
- 所有者が問いに「やめた」「進める」以外で答えたら(「まだ進めている」「進めない」など)、AIはこのセッションではIssue #N の作業をせず、spec もブランチも作らずに止まる。止まるときは、`folder_conflict` では worktree を選んでセッションを開き直すよう、`leftovers` では作りかけが残っている作業フォルダの場所を、`branch_only` では残っているブランチの名前を、所有者に示す
- `end` か `takeover` を呼んだら、AIは結果を示してから `check-start` を呼び直し、残りの欄を同じ表で扱う。`takeover` が終了コード0で終わったときは、標準出力の、写したファイル(いまの作業フォルダのまま引き継いだときは作りかけ)の一覧と、いまのブランチを示す。標準エラーに注意の文が出ていれば、それも示す
- このセッションの Step 1.5 で `takeover` が終了コード0で終わったあとに呼び直した `check-start` に、`is_self` が真の要素(引き継いだいまの作業フォルダ)が出ても、AIは尋ね直さず、引き継いだものとして扱う。セッションのIDが無いと(`--session` を付けずに呼び、いまの作業フォルダのセッションの記録も無いとき)、`check-start` は自分の作りかけを除けず、引き継いだ作りかけを `is_self` の要素として出し続けるためである
- `end` か `takeover` が0でない終了コードで終わったら、AIは先へ進まず、終了コードと標準エラーの文を所有者に伝えて止まる。`takeover` は、引き継げなかったときに終了コード1で終わり、引き継げなかった理由と、あれば次の手を `[parallel] 引き継げない:` で始まる文で標準エラーに出す
- `capacity.active` の数が `capacity.limit` 以上のときは、AIは着手を続けたうえで、セッションが埋まっていることを所有者に報告する。`capacity.active` に出るのは、ほかの作業中のセッションのうち、その時点で Claude が返答している途中のものだけで、返答を終えて次の指示を待っているセッションは出ない。報告には、`capacity.active` の要素の `issue`(返答している途中のセッションのIssueの番号)と、このセッションの品質チェックと画面確認が順番待ちになることがあることを含める
- `check-start` の `folder_conflict` `leftovers` `branch_only` がすべて空のとき(呼び直したときも含む。上の箇条で引き継いだものとして扱う `is_self` の要素は、無いものとみなす)は、AIは `capacity` の行を扱ってから Step 2 へ進む。引き継いだときは、Step 2 以降が、引き継いだ spec の進み具合と次の手順を所有者に示す

### Step 2: 対応する spec を探す

AIは `.kiro/specs/*/spec.json` のうち、`issue` が N のもの、または `additional_issues` に N を含むものを探す。

見つからなければ Step 4 へ進む(Step 3 は Step 1.5 の前に済ませてある)。見つかったときは、進め方を決め直さない。AIはその spec の進み具合と、所有者が次に打つコマンドを示して終える。次のコマンドは、spec.json の `approvals` と tasks.md を見て、次の表の上から順に最初に当てはまる行で決める。

| spec の状態 | AIが示すこと |
|---|---|
| `phase` が `initialized`(要件がまだ作られていない) | `/kiro-spec-requirements <feature>` を打ってください |
| requirements が生成済みで未承認 | 要件の本文と審査の記録(`reviews/`)を読み、承認するなら `/kiro-spec-design <feature>` を打ってください |
| requirements が承認済みで、design が未生成 | `/kiro-spec-design <feature>` を打ってください |
| design が生成済みで未承認 | 設計の本文と審査の記録を読み、承認するなら `/kiro-spec-tasks <feature>` を打ってください |
| design が承認済みで、tasks が未生成 | `/kiro-spec-tasks <feature>` を打ってください |
| tasks が生成済みで未承認(`approvals.tasks.approved` が false) | タスクの本文と審査の記録を読み、承認するなら `/kiro-impl <feature>` を打ってください |
| tasks が承認済みで、tasks.md に未完了のタスク(`- [ ]`)がある | `/kiro-impl <feature>` を打ってください |
| tasks が承認済みで、tasks.md のタスクがすべて完了(`- [x]`) | 出荷の状況を確かめる(下記) |

- 進み具合は、どの段階まで生成・承認されたかと、tasks.md の完了の数(例: 12件中7件完了)で示す
- 最後の行だけは、示して終えるのではなく、AIが出荷の状況を確かめて進める。開いているPRのうち、本文に `Spec: .kiro/specs/<feature>` を含むものを探し、あればその番号を示して、`/ship` の CI を見届ける手順から続ける。無ければ、AIが `/ship` で出荷する

### Step 4: コードを調べる

AIは、Issueの本文に関わるコード・文書・ワークフローを読み、その時点で何があり、何を変えることになるかを確かめる。広く探す必要があるときは、Explore のサブエージェントに任せてよい。調べた結果は、次の判断の根拠(ファイルと行)に使う。

### Step 5: 判断する

AIは、下の「観点の定義」の4つの観点を、1つずつIssueに当てはめる。観点2と観点3は、下の「観点2と観点3の当てはめ方」の手順で当てはめる。

- 4つの観点のうち1つでも当たれば、spec が要る
- 4つの観点のどれにも当たらなければ、spec は要らない。すでにある spec に関わる変更でも、どれにも当たらなければ spec 無しで直す
- 変更の行数の見込みは、判断に使わない。200行の検査は、着手時の判断をすり抜けた変更を止める最後の網であり、着手時の判断の基準ではない

spec が要るときは、AIは続けて次の2つを決める。

1. 1つの spec に収まるか: Issueの中に、互いに関係なく別々に出荷できる関心事が2つ以上あり、それぞれが spec の要る大きさなら「収まらない」とし、判断は「Issueを分ける」にする。それ以外は「収まる」とし、2つ目へ進む。spec が要らないときは、この判断をしない(大きすぎると分かったときは、実装の途中で分ける)
2. 既存の spec の範囲か: 変更する動きが、既存の spec の design.md の `## 作るものと作らないもの` の節の `### 作るもの` に書かれた範囲に入るなら、判断は「spec <feature> を直す」にする。入らないとき、または既存の spec が無いときは、判断は「新しい spec を作る」にする

すでに spec がある機能を直す・広げるIssueでは、AIは「その spec を直す」「新しい spec を作る」「spec 無しで直す」のどれにするかを、上の決まりで決める。

進め方を決めたら、AIは、Step 6 で判断を示す前に、Step 5.5 でまとめる相手を探すかどうかを決める。

**観点の定義**

| 観点 | 当たる | 当たらない |
|---|---|---|
| 1. 新しい機能か | 今は無い機能を足し、所有者や利用者が新しく使えるもの(画面・API・コマンド・手順・通知)ができる | 今ある機能を本来の動きに直す。直すために中の仕組みを足しても、所有者や利用者が新しく使うものが増えなければ当たらない。今ある動きを意図して変えるだけの変更は、この観点では当たらないとし、観点2と3で判断する |
| 2. 作り方を選ぶ必要があるか | 作り方によって、マージしたあとに所有者や利用者が見るもの・すること・受け取るものが変わり、どの結果にするかを、Issueの本文からも3つの材料からも決められず、所有者に1回尋ねても決まらない。または、Issueの本文の「決めた方式」に沿ったまま作れる作り方が1つも無い。または、承認済みの spec の設計の「作るもの」の範囲の中で作れる作り方が1つも無い | どの作り方でも所有者や利用者から見える結果が同じで、違うのは中の作りと後からの直しやすさだけ。かかる時間の違いは、Issueの本文が時間について要望しているときだけ見える結果に数える |
| 3. Issueの本文だけで完成の形が決まらないか | Issueの本文で決まっていない、所有者や利用者から見える動きがあり、3つの材料のどれからも決められず、所有者に1回尋ねても決まらない | 決まっていない見える動きを、すべて3つの材料から決められる。または、所有者に1回尋ねれば決まる |
| 4. マージを取り消しても元に戻らないか | 保存されているデータの形を変える・消す(DBのマイグレーションなど)、外部に何かを送る、本番の設定を変える | PRを取り消せば元の状態に戻る |

- 3つの材料: 1つ目は今の動きのまま変えないこと。2つ目はIssueの本文の「やりたいこと」と「どうなれば解決か」に書かれた目的。3つ目は既存の文書(承認済みの spec、README、CLAUDE.md、スキルの手順)に書かれた本来の動き。2つ目に「やりたいこと」を含めるのは、「どうなれば解決か」の節が無いIssueでも、AIが「やりたいこと」の節から目的を読めるようにするためである
- 1回尋ねれば決まる: AIが問いをすべて1回にまとめて出せ、どの問いの答えもほかの問いの答えで変わらず、AIが問いごとに推奨する答えを付けられ、所有者がコードを読まずに答えられること

観点4の名前は、要件の「PRを差し戻しても元に戻らないか」と同じ意味である。審査で送り返す意味の「差し戻す」と取り違えないよう、「マージを取り消しても」と書く。

**観点2と観点3の当てはめ方**

AIは、この Step で、観点2と観点3を次の順に当てはめる。

1. AIは、考えられる作り方を挙げ、作り方ごとに「マージしたあとに、所有者や利用者が何を見るか・何をするか・何を受け取るか」を1文に書く。Issueに関わる承認済みの spec があるときは、AIは、作り方ごとに、その spec の design.md の「作るもの」の節の範囲の中で作れるかも書く。Issueの本文の「決めた方式」から外れる作り方は、AIは候補から外す。外れる作り方があることだけでは、AIは観点2に当たると判断しない
2. 作り方ごとの文がすべて同じなら、AIは観点2の1つ目の条件に当たらないと判断する。文が作り方ごとに違うときは、AIは、違いがIssueの本文と3つの材料から決められるかを確かめる。決められれば、AIはその結果になる作り方を選び、当たらないと判断する。決められなければ、AIはその違いを、所有者への問いの候補にする
3. AIは、観点2の2つ目の条件を、次の (a) と (b) に分けて別々に当てはめる。
   - (a) 「決めた方式」に沿ったまま作れる作り方が1つも無ければ、AIは当たると判断する
   - (b) Issueに関わる承認済みの spec があり、その「作るもの」の範囲の中で作れる作り方が1つも無ければ、AIは当たると判断する。(a) に当たらなくても、AIは (b) を当てはめる。Issueに関わる承認済みの spec が無いときは、AIは (b) を当てはめない。(b) に当たった変更は「作るもの」の範囲の外に出るので、この Step の「既存の spec の範囲か」の決め方では「新しい spec を作る」になる
   - 変更に関わる承認済みの spec が2本以上あるときは、AIは (b) を次のとおり当てはめる
     - AIは、作り方ごとに、変更を、関わる spec ごとの部分に分ける。AIは、ある部分にどの spec が関わるかを、ファイルの名前ではなく、各 spec の design.md の「ファイルの構成」の節の行の中身(その spec がそのファイルの中で作った箇所か変えた箇所)で決める。部分が変える箇所を、ある承認済みの spec の行の中身が挙げていれば、その spec がその部分に関わる。同じファイルを挙げていても、行の中身がその箇所を挙げていない spec は、その部分に関わらない
     - 「ファイルの構成」の行が部品の名前だけを書いているときは、AIは、その名前の部品の節まで辿って、その spec が作った箇所を読む
     - AIは、部分ごとに、その部分に関わる spec の design.md の「作るもの」の節の範囲の中で作れるかを書く。関わる spec が2本以上ある部分は、そのうち1本でも「作るもの」の範囲の中で作れれば、AIは範囲の中で作れる部分とする。関わる spec のどの「作るもの」にも、その部分が変える動きが無いときは、AIは範囲の中で作れない部分とする
     - どの承認済みの spec の「ファイルの構成」の行の中身にも挙がっていない箇所だけを変える部分(例: CLAUDE.md の、どの spec も作っていない決まりの文)は、関わる spec が無い部分である。AIは、承認済みの spec が無いときと同じく、その部分に (b) を当てはめない
     - どの部分も範囲の中で作れる作り方が1つでもあれば、AIは (b) に当たらないと判断する。どの作り方でも範囲の中で作れない部分が残れば、AIは (b) に当たると判断する。このとき、AIは、6 の (b) の根拠として、範囲の中で作れない部分と、その部分が外れる spec の「作るもの」の箇所を書く
4. AIは、Issueの本文で決まっていない、所有者や利用者から見える動きを1つずつ書き出し、それぞれに、決めた材料(今の動き、Issueの目的、既存の文書のファイルと行)を付ける。材料を付けられない動きだけが、所有者への問いの候補になる
5. 問いの候補が無ければ、AIは観点2と観点3のどちらにも当たらないと判断する。問いの候補があれば、AIは、候補をまとめて「1回尋ねれば決まる」の条件に当てはめる。条件をすべて満たせば、AIは当たらないと判断し、問いを出す。満たさなければ、AIは、候補の出どころの観点に当たると判断する
6. 観点2か観点3に当たると判断するときは、AIは、根拠の欄に次のことを書く。AIがこれらを書けなければ、AIは当たらないと判断する
   - 観点2の1つ目の条件: 作り方ごとに違う見える結果の文の組
   - 観点2の2つ目の条件の (a): 沿えない「決めた方式」の項目と、その項目に沿ったまま作れる作り方が無い理由
   - 観点2の2つ目の条件の (b): 外れる spec の「作るもの」の箇所と、その範囲の中で作れる作り方が無い理由
   - 観点3: 材料を付けられない見える動きと、その動きを3つの材料のどれからも決められない理由
7. AIは、材料で決めた動きと選んだ作り方を、作業の記録として控えておく。控えたものは、出荷のときにPR本文の「## AIが決めたこと」の節に書くためのものである。spec 無しのまま会話が途切れたときに備え、AIは Step 6 の「理由」の表の根拠にも、決めた材料を書く

### Step 5.5: まとめる相手を探す

AIは、Step 5 で進め方を決めたあと、Step 6 の報告を示す前に、Issue #N と1つにまとめたほうがよい、ほかの開いているIssue(まとめる相手)を、次の順に探す。同じ spec を直すIssueを別々に進めると、所有者がその spec の要件・設計・タスクの承認をIssueの数だけやり直すことになるためである。

1. 探すかを決める: AIは、進め方が「新しい spec を作る」か「spec <feature> を直す」のときだけ、2へ進む。次のときは、AIは相手を探さずに Step 6 へ進み、Step 6 の報告に「まとめる提案」の節も「まとめる相手は無かった」の1行も書かない
   - 進め方が「spec を作らずに実装する」か「Issueを分ける」のとき
   - Step 1.5 で `session.sh takeover` が終了コード0で終わったとき(前のセッションの作りかけを引き継いで進めているとき)。引き継いだ作りかけは、Issue #N のために進んでいた作業なので、まとめると、その作業をやり直すことになるためである
2. 候補を集める: AIは、次のコマンドで、開いているIssueのうち、ラベル `audit` `container-vuln` `blocked` のどれも付いていないものの番号だけを取る。ラベル `audit` と `container-vuln` は仕組みが起票したIssue(監査の通知、コンテナの脆弱性の通知)に付き、`blocked` は上流や外部の事情で着手できないIssueに付く。AIは、取った番号から #N を除く。AIは、この時点ではIssueの本文とコメントを取らない

   ```bash
   gh issue list --state open --limit 200 --json number,labels --jq '[.[] | select([.labels[].name] | any(. == "audit" or . == "container-vuln" or . == "blocked") | not) | .number]'
   ```

3. 外す: AIは、候補から次のIssueを除く
   - 親子の関係にあるIssue: Step 1 で読んだ #N の `parent`(親)と `subIssues`(子)のIssue。親があるときは、AIは `gh issue view <親の番号> --json subIssues` で親の子を読み、そのIssue(#N と同じ親を持つIssue)も除く。所有者が了承して分けたものを元に戻さないためである
   - spec があるIssueと、ほかのセッションが作業中のIssue: AIは次のコマンドを呼び、標準出力の JSON(例: `{"active":[507],"spec":[472,473,480]}`)の `spec` と `active` の番号のIssueを除く。`<ID>` は Step 1.5 の1と同じく取り、IDが無ければ `--session <ID>` を付けずに呼ぶ。`busy-issues` は記録を書かずに読むだけである。AIは、相手のIssueを調べるために `check-start` を呼ばない。`check-start` は、呼んだIssueの着手の予約を書いてしまうためである

     ```bash
     bash .claude/scripts/parallel/session.sh busy-issues --session <ID>
     ```

     `busy-issues` は、読めない spec.json を飛ばし、`[parallel] 読めない spec.json:` で始まる文を標準エラーに出すことがある。この文が出ても、終了コードが0なら、AIはその文を JSON として読まず、標準出力の JSON だけを使う

   - 開いているPRがあるIssue: AIは次のコマンドで、開いているPRの本文から、行の頭の `Closes #<番号>` と `Refs: #<番号>` の番号だけを取り、その番号のIssueを除く

     ```bash
     gh pr list --state open --limit 200 --json body --jq '[.[].body | scan("(?m)^(?:Closes|Refs:) #([0-9]+)") | .[0] | tonumber] | unique'
     ```

   - 2と3の2つの一覧は `--limit 200` で取るので、開いているIssueか開いているPRが200件を超えると、それより後ろを見ていない。2と3のコマンドの出力は、外したあとの番号なので、出力の数では200件に達したかが分からない。AIは、次のコマンドで、開いているIssueと開いているPRの件数を数える。どちらかが200なら、AIは、その一覧の200件より後ろのIssueかPRを見ていないことを、Step 6 の報告に1行で書く

     ```bash
     gh issue list --state open --limit 200 --json number --jq 'length'
     gh pr list --state open --limit 200 --json number --jq 'length'
     ```

   - 外したあとに残った候補ごとに、AIは `gh issue view <番号> --json number,title,body` で題名と本文を1件ずつ読む。AIは、候補のコメントを読まない
4. 当てる: AIは、残った候補の本文を読み、次の条件A・条件B・条件Cのどれかに当たる候補を、まとめる相手の候補にする
   - 条件A「同じことを求めている」: #N と候補が同じことを求めている。または、片方のIssueが求めていること(「やりたいこと」と「どうなれば解決か」)が、もう片方のIssueが求めていることにすべて含まれている
   - 条件B「同じ spec を直すことになる」: 進め方が「spec <feature> を直す」のときだけ、AIは、条件Aに当たらない候補に条件Bを当てる。AIは、まず、候補の本文が、spec <feature> の design.md の「作るもの」の節にある動き(スキル・スクリプト・画面・手順の名前)に触れるかで絞る。触れる候補にだけ、AIは Step 4 と Step 5 と同じ判断(コードを調べ、4つの観点と既存の spec の範囲を当てる)を行う。その判断で、候補のために直す spec が spec <feature> になれば、その候補は条件Bに当たる。2つのIssueが求めていることが違っていても、条件Bには当たる
   - 条件C「同じ既存の spec の範囲に関わる」: 進め方が「新しい spec を作る」のときだけ、AIは、条件Bの代わりに、条件Aに当たらない候補に条件Cを当てる。新しい spec はまだ無く、2つのIssueが同じ spec を直すかを、条件Bでは比べられないためである。AIは、まず、Step 5 で #N に当てた判断から、#N が変える動きを design.md の「作るもの」の節に持つ承認済みの spec を挙げる。挙げた spec が無ければ、AIは条件Cを当てない。挙げた spec があれば、AIは、候補の本文が、挙げた spec の design.md の「作るもの」の節にある動き(スキル・スクリプト・画面・手順の名前)に触れるかで絞る。触れる候補にだけ、AIは Step 4 と Step 5 と同じ判断(コードを調べ、4つの観点と既存の spec の範囲を当てる)を行う。その判断で、候補も spec が要り、かつ候補が変える動きに、挙げた spec のうち1つの spec の「作るもの」の節に書かれた動きが含まれれば、その候補は条件Cに当たる。#N と候補が変える動きは、その spec の「作るもの」の同じ箇条でなくてよい。その判断で候補が spec を作らずに直せるなら、その候補は条件Cに当たらない。まとめても、所有者が spec を承認する回数が減らないためである
   - AIは、CLAUDE.md や README の記述を、変えた動きに合わせてそろえるためだけの直しを、#N と候補のどちらでも、条件Cの「変える動き」に数えない
5. 食い違いを見る: AIは、当たった候補ごとに、#N と候補の「決めた方式」と「どうなれば解決か」の項目を突き合わせる。片方のIssueの項目のとおりに作ると、もう片方のIssueの項目のとおりにならない組があれば、2つの項目は食い違う。食い違う組がある候補は、AIはまとめる相手から外し、Step 6 の報告に「#<候補の番号> とは、<節の名前>の「<項目>」と「<項目>」が食い違うため、まとめる提案を出さない」と1行で書く。どちらの項目に合わせるかは所有者が決めることで、AIがまとめた本文を作ると、AIが片方の項目を消すか書き換えることになるためである
6. 推奨を決める: AIは、残った相手ごとに、まとめるかどうかの推奨を決める。AIは、原則として「まとめる」を推奨する。まとめたあとの本文が、Step 5 の「1つの spec に収まるか」で「収まらない」になる相手には、AIは「まとめない」を推奨し、理由に「まとめると1つの spec に収まらない」と書く
7. 残すIssueを決める: AIは、#N と、「まとめる」を推奨した相手のうち、番号の最も小さいIssueを、まとめたあとも開いたままにするIssue(残すIssue)にする。AIは、推奨のとおりにまとめたときの残すIssueの本文の全文を作り、scratchpad のファイルに書いておく。閉じるほうのIssueは、残すIssueでない、#N と「まとめる」を推奨した相手である。AIは、全文を、file-issue の「まとめるときに本文を書き換えるとき」の節の「本文の作り方」のとおりに作る
   - 「まとめる」を推奨した相手が1つも無いときは、AIは残すIssueを決めず、全文も作らない
8. 相手が残らなければ(どの候補も条件に当たらなかったか、当たった候補がすべて食い違いで外れたとき)、AIは Step 6 の報告に「まとめる相手は無かった」と1行で書く。相手が1つ以上残れば、AIは Step 6 の報告に「## まとめる提案」の節を置く(Step 6 の「まとめる提案があるときの報告の書式」)

`session.sh busy-issues` が0でない終了コードで終わったとき、または相手を探すための gh の問い合わせ(2と3のコマンド、親の子を読む `gh issue view`、候補の本文を読む `gh issue view`)が失敗したときは、AIは相手を探すのをやめる。AIは、Step 6 の報告に、まとめる相手を調べられなかったことと失敗した内容(`busy-issues` のときは終了コードと標準エラーの文、gh のときはエラーの文面)を1行で書き、まとめる提案の無い報告として進む。これは、Step 1 の「gh の問い合わせに失敗したら、進め方を判断せずに終える」とは扱いが違う。相手を探せなくても、Step 5 で決めた進め方そのものは正しいためである。

### Step 6: 判断を示す

AIは、決めた判断を次の書式で所有者に示す。

```markdown
## してほしいこと
<次のどれか1つ>
- 何もしなくて大丈夫です。このまま実装を始めます。判断がおかしいと思ったら止めてください
- 次のコマンドを打ってください: `<コマンド>`
- 下の分け方を見て、よければ了承してください
- 下の問いに答えてください。答えはIssueの本文の「決めた方式」に書き足してから実装を始めます
- 下のまとめる提案に、相手ごとにまとめるかどうか答えてください。答えを受けてから、打つコマンドを示します

## 判断: <spec を作らずに実装する | 新しい spec を作る | spec <feature> を直す | Issueを分ける>

## 理由
| 観点 | 当たるか | 根拠 |
|---|---|---|
| 新しい機能か | 当たる/当たらない | <Issue本文の見出し、またはファイルと行> |
| 作り方を選ぶ必要があるか | ... | ... |
| Issueの本文だけで完成の形が決まらないか | ... | ... |
| マージを取り消しても元に戻らないか | ... | ... |
```

所有者に尋ねる問いがあるとき(Step 5 の「観点2と観点3の当てはめ方」の5で、問いの候補が「1回尋ねれば決まる」の条件を満たしたとき)は、AIは「## 理由」のあとに次の節を置く。

```markdown
## 問い
1. <問い>
   - 決まること: <この答えで決まる、所有者や利用者から見える動き>
   - 推奨: <推奨する答え>(<推奨の理由>)
2. ...

「全部推奨で」のように、まとめて答えてもかまいません。
```

- 「してほしいこと」を最初に置く。判断が「spec を作らずに実装する」で問いが無ければ1つ目、「spec を作らずに実装する」で問いがあれば4つ目、「新しい spec を作る」「spec <feature> を直す」なら2つ目、「Issueを分ける」なら3つ目を使う。ただし、「新しい spec を作る」「spec <feature> を直す」で、Step 5.5 でまとめる相手が1つ以上残ったときは、2つ目ではなく5つ目を使う(下の「まとめる提案があるときの報告の書式」)
- 問いがあるときも、判断は「spec を作らずに実装する」のままにする。「1回尋ねれば決まる」の条件を満たす問いは、観点2と観点3に当たる理由にならないためである
- AIは、問いを、専門用語を使わず、主語と目的語のある文で書く。AIは、答えるためにコードを読む必要がある問いを出さない
- AIは、問いを AskUserQuestion の選択肢にせず、チャットの本文に全文を書く。AskUserQuestion の前文と preview は所有者に見えないためである
- AIは、問いの数に上限を置かない。「1回尋ねれば決まる」の条件を満たす限り、AIはすべての問いを1回の報告にまとめて出す
- 判断が「spec を作らずに実装する」で問いがあるときは、AIは、問いを含むこの報告を示す前に、Step 7 の「spec を作らずに実装する」の手順1のとおり、ブランチを作って記録する。ブランチを作らずに止まったときは、AIは問いを出さず、止まった理由を所有者に伝える
- 理由の表には、4つの観点すべてを、当たるか当たらないかと根拠を添えて書く。当たらない観点も省かない
- 根拠には、AIが調べたファイルと行(例: `.claude/skills/ship/SKILL.md` L42)、またはIssue本文の見出しを書く
- 判断が「spec <feature> を直す」のときは、「してほしいこと」に、コマンドを打つと取り消される承認の段階(その spec の spec.json で承認済みになっている要件・設計・タスクのうちのどれか)を添える
- 判断が「新しい spec を作る」「spec <feature> を直す」で、まとめる提案が無いときは、AIは、コマンドを打つよう依頼するこの報告を示す前に、Step 7 の「spec を作らずに実装する」の手順1と同じく、ブランチを作って記録する。ブランチを作らずに止まったときは、AIはコマンドを打つ依頼を出さず、止まった理由を所有者に伝える
- 判断が「新しい spec を作る」「spec <feature> を直す」で、まとめる提案があるときは、AIは、この報告の前にブランチを作らず、`session.sh claim` も呼ばない。所有者の答えによって、ブランチを作るIssue(残すIssue)が変わるためである。AIは、答えを受けて残すIssueが決まってから、Step 7 の「まとめる提案の答えを受けたとき」の手順で、残すIssueのブランチを作り、`session.sh claim` で記録する。答えを待つ間は、Step 1.5 の `check-start` が書いた #N の着手の予約が、ほかのセッションに、#N が作業中であることを示す
- 専門用語を使わず、主語(所有者・AI)を立てた文で書く。「誰が」「どれを」するのかを、文ごとに分かるようにする
- Step 5.5 で相手を探したときは、AIは、Step 5.5 が報告に書くとした1行(「まとめる相手は無かった」、食い違いで外した相手の行、200件より後ろを見ていないことの行、相手を調べられなかったことの行)を、「## 理由」の表のあとに置く。「## まとめる提案」の節を置くときは、その節の前に置く

**まとめる提案があるときの報告の書式**

Step 5.5 でまとめる相手が1つ以上残ったときは、AIは、「してほしいこと」に5つ目の「下のまとめる提案に、相手ごとにまとめるかどうか答えてください。答えを受けてから、打つコマンドを示します」を使う。判断の行と「## 理由」の表は、まとめる提案が無いときと同じに出す。AIは、「## 理由」のあとに次の節を置く。

```markdown
## まとめる提案
| 相手のIssue | 題名 | まとめたほうがよい理由 | 推奨 |
|---|---|---|---|
| #<番号> | <題名> | <同じことを求めている | 同じ spec(<feature>)を直すことになる | 同じ既存の spec(<feature>)の範囲に関わる> | <まとめる | まとめない(<理由>)> |

残すIssue: #<番号>(まとめるIssueのうち、番号の最も小さいIssue)

### 推奨のとおりにまとめたときの #<残すIssueの番号> の本文
<全文>

「全部推奨で」のように、まとめて答えてもかまいません。
```

- AIは、まとめる相手をすべて1つの表に載せ、所有者が相手ごとにまとめるかどうかを答えられるようにする。「まとめたほうがよい理由」の列は、条件Aに当たった相手は「同じことを求めている」、条件Bに当たった相手は「同じ spec(<feature>)を直すことになる」と直す spec の名前を添えて、条件Cに当たった相手は「同じ既存の spec(<feature>)の範囲に関わる」と、#N と相手がどちらも「作るもの」の動きを変える既存の spec の名前を添えて書く
- 「残すIssue」の行と全文の節には、Step 5.5 の7で決めた残すIssueと、scratchpad に書いておいた全文を載せる。AIは、全文を省かずにチャットの本文に書く
- 「まとめる」を推奨した相手が1つも無いときは、AIは、「残すIssue」の行と全文の節を置かず、代わりに「推奨のとおりなら、どのIssueともまとめない」と1行で書く
- 食い違いで提案から外した相手は、AIは、この節の前に1行ずつ書く(Step 5.5 の5の文)
- AIは、この報告では、spec を始めるコマンド(`/kiro-spec-init` など)を所有者に依頼しない。所有者が相手ごとにまとめるかどうかを答えるまで、AIはコマンドを依頼しない。判断が「spec <feature> を直す」でも、取り消される承認の段階は、この報告では添えず、コマンドを依頼するときに添える
- AIは、この報告を示したら止まり、所有者の答えを待つ

### Step 7: 判断ごとに進む

AIは、Step 6 で示した判断に応じて、次のとおり進む。

**spec を作らずに実装する**

AIは、Step 5 で決めた、所有者に尋ねる問いがあるかどうかで、進み方を分ける。

- 問いが無いとき: Step 5 の「観点2と観点3の当てはめ方」で、問いの候補が1つも出なかったときである。つまり、作り方ごとに違う見える結果が無いか、その違いをIssueの本文と3つの材料から決められ(観点2から来る候補が無い)、かつ、Issueの本文で決まっていない、所有者や利用者から見える動きが無いか、その動きをすべて3つの材料で決めた(観点3から来る候補が無い)ときである。AIは、判断を示したら、所有者の返事を待たずに、下の手順1から実装を始める
- 問いがあるとき: 問いの候補(Issueの本文と3つの材料から決められない、作り方ごとに違う見える結果と、3つの材料で決められない見える動き)が残り、候補が「1回尋ねれば決まる」の条件を満たしたときである。AIは、判断を示す前に、下の手順1でブランチを作り、`session.sh claim` で記録する。続けて、AIは、Step 6 の書式で判断と「## 問い」の節を示し、止まって所有者の答えを待つ。所有者が答えるまで、AIは実装を始めない。答えを受けたら、AIは、下の「問いの出し方と答えの書き足し」の手順で進め、すべての問いが答えで決まったときだけ、手順2から実装を始める
- 問いの候補が「1回尋ねれば決まる」の条件を満たさないとき(1回の問いにできないとき)は、判断は「spec を作らずに実装する」にならない。Step 5 の「観点2と観点3の当てはめ方」の5のとおり、候補の出どころの観点に当たるので、AIは spec が要るときの判断で進む

1. AIは `.branch_name_template` に従って、最新の main からブランチを作る。`git fetch origin` を実行してから、`git switch --no-track -c <type>/<short-description> origin/main` で作る。いまいるブランチから作らない(別の feature ブランチにいるときに `/start` を打たれると、そのブランチのコミットを引き継いでしまうため)。git が管理しているファイルにコミットしていない変更があるとき(`git status --porcelain --untracked-files=no` の出力があるとき)は、AIはブランチを作らず、そのことを所有者に伝えて止まる(`origin/main` から作っても、コミットしていない変更は新しいブランチへ持ち越され、持ち越せないときは `git switch` が失敗するため)。git が管理していないファイルは、この判定に含めない。ブランチを作ったら、AIはすぐに `bash .claude/scripts/parallel/session.sh claim <N> --branch <作ったブランチ> --session <ID>` を呼び、Issue #N のブランチとして記録する(`--session` は Step 1.5 の1のとおりに付ける)。`claim` が0でない終了コードで終わったら、AIは先へ進まず、終了コードと標準エラーの文を所有者に伝えて止まる。`claim` の終了コード1は、ほかのセッションが同じIssueに着手したことを表す。このとき、AIは作ったブランチを使わずに止まり、標準エラーの `[parallel] 着手できない:` で始まる文を所有者に伝える
   - Step 1.5 で引き継いだ(`session.sh takeover` を呼んだ)あとで、いまのブランチ(`git branch --show-current` の出力)が、Issueの記録 `issues/<N>.json` の `branch` と同じときは、AIはこの手順1を丸ごと飛ばす。新しいブランチを作らず、`session.sh claim` も呼ばずに、いまのブランチで進む。引き継いだブランチのコミットを置き去りにしないためである。Issueの記録は、`git rev-parse --path-format=absolute --git-common-dir` の出力のディレクトリの下の `keirekipro-parallel/issues/<N>.json` にある。記録が無いとき、または記録の `branch` が空のときは、同じとはみなさず、この手順1のとおり新しいブランチを作る
2. AIはIssueの本文のとおりに実装する。問いに答えてもらったときは、AIは、本文の「決めた方式」に書き足した答えのとおりに実装する。実装の途中は、「途中で見立てが外れたとき」の見直しの時点で、4つの観点を当て直す
3. AIは `/verify-all` の手順で、変更した領域の verify を通す
4. AIは `/ship` を自分で実行して出荷する。所有者に `/ship` を打つよう頼まない

**問いの出し方と答えの書き足し**

AIが問いを出したあと、所有者が答えたら、AIは次の順に進める。

1. AIは、所有者の返事を問いごとに読み、答えを1つずつ決める。「全部推奨で」は、すべての問いに推奨を答えたものとして読む。問いに答えていない返事(別の話や、どちらとも読める返事)の問いは、答えで決まらない問いとして扱う
2. AIは、答えをIssueの本文の「## 決めた方式」の節に書き足す。書き足しの手順は、file-issue の「着手のときの答えを本文に書き足すとき」の節に従う。AIは、書き足す箇条の文を、問いの「決まること」に答えを当てはめた、所有者や利用者から見える動きの文にする。所有者が推奨のとおりに答えた項目には、AIは末尾に「(AIの提案を了承)」を付ける。書き足しに失敗したとき、または書き足したあとに読み直した本文が食い違っていたときは、AIは実装を始めず、その節のとおりに所有者に示して止まる
3. 答えで決まらない問いが残ったら、AIは判断を「spec が要る」に改める。AIは、Step 5 の、spec が要るときに続けて決める2つ(1つの spec に収まるか、既存の spec の範囲か)で進め方を決め、Step 6 の書式で、改めた判断と、どの問いが決まらなかったかを示す。このとき、ブランチはすでに作って記録してあるので、AIはブランチを作り直さず、`session.sh claim` も呼び直さない。AIは、受けた答えを2のとおりIssueの本文に書き足してから、所有者に spec を始めるコマンドを依頼して終える。spec の要件を作るときに、答えが所有者の決めたこととして読まれるためである
4. すべての問いが答えで決まったら、AIは、答えをIssueの本文に書き足したことを所有者に1行で知らせ、返事を待たずに上の手順2から実装を始める
5. 実装の途中の見直しの時点(「途中で見立てが外れたとき」の「見直しの時点」)で問いを出すときも、AIは Step 6 の同じ書式と、この1・2・4の手順に従う。問いは、見直しの時点ごとに1回にまとめる。ブランチはすでにあるので、AIは「spec を作らずに実装する」の手順1を行わない。すべての問いが答えで決まったら、AIは止めたところから実装を再開する。答えで決まらない問いが残ったときは、AIは3を使わない。AIは、2のとおり受けた答えをIssueの本文に書き足してから、候補の出どころの観点に当たったものとして、「途中で見立てが外れたとき」の「手順」の2から進む(実装はすでに止めてあるので、その手順の1は済んでいる)

所有者が答えの代わりに止めたときは、AIは Step 8 の「所有者が止めたとき」の手順に従う。

**新しい spec を作る**

AIは、依頼の前に、「spec を作らずに実装する」の手順1と同じく、最新の main からブランチを作り、`session.sh claim` で記録する。引き継いだあとで手順1を丸ごと飛ばす決まりも、ここに当てはめる。続けて、AIは、所有者に `/kiro-spec-init #<N>` を打つよう依頼して終える。所有者がコマンドを打つまで、AIは実装を始めない。

Step 6 でまとめる提案を示したときは、AIは、この依頼の前にブランチを作らない。AIは、所有者の答えを受けて残すIssueが決まってから、下の「まとめる提案の答えを受けたとき」の手順で、残すIssueのブランチを作り、`session.sh claim` で記録する。

**spec <feature> を直す**

AIは、依頼の前に、「spec を作らずに実装する」の手順1と同じく、最新の main からブランチを作り、`session.sh claim` で記録する。引き継いだあとで手順1を丸ごと飛ばす決まりも、ここに当てはめる。続けて、AIは、所有者に `/kiro-spec-init #<N> <feature>` を打つよう依頼して終える。依頼には、コマンドを打つと取り消される承認の段階を添える。取り消される段階は、その spec の spec.json の `approvals` で承認済み(`approved` が true)になっている要件・設計・タスクである。所有者がコマンドを打つまで、AIは実装を始めない。

Step 6 でまとめる提案を示したときは、AIは、この依頼の前にブランチを作らない。AIは、所有者の答えを受けて残すIssueが決まってから、下の「まとめる提案の答えを受けたとき」の手順で、残すIssueのブランチを作り、`session.sh claim` で記録する。

**まとめる提案の答えを受けたとき**

Step 6 でまとめる提案を示したあと、所有者が答えたら、AIは次の順に進める。答えを待つ間は、AIはブランチを作らず、`session.sh claim` も呼ばない。その間は、Step 1.5 の `check-start` が書いた #N の着手の予約が、ほかのセッションに、#N が作業中であることを示す。

1. AIは、所有者の返事を相手ごとに読み、相手ごとにまとめるかどうかを決める。「全部推奨で」は、すべての相手に推奨を答えたものとして読む。どちらとも読めない返事の相手は、AIはまとめないものとして扱い、そのことを次の報告に1行で書く
2. すべての相手をまとめないときは、AIは、`/start` を打ったIssue #N だけで進める。AIは、「spec を作らずに実装する」の手順1と同じく、#N のブランチを最新の main から作って `session.sh claim` で記録し、Step 6 の書式で、コマンドを打つよう依頼する報告を出し直す。この報告の「してほしいこと」には、2つ目の「次のコマンドを打ってください」を使い、判断が「spec <feature> を直す」なら、取り消される承認の段階を添える。AIは、まとめないという答えを、Issueの本文にもほかの場所にも書き残さない
3. 1つ以上の相手をまとめるときは、AIは、#N と、所有者がまとめると答えた相手のうち、番号の最も小さいIssueを、残すIssueに決め直す。AIは、決め直した残すIssueで、Step 5.5 の7と同じ形で、まとめたときの本文の全文を作り直し、scratchpad のファイルに書く。残すIssueか全文が、提案のときに示したものと変わるとき(所有者の答えが推奨と違うとき)は、AIは、決め直した残すIssueと全文を省かずにチャットの本文に示し直し、止まって所有者の了承を待つ。所有者が了承するまで、AIは本文を書き換えず、Issueを閉じない
4. AIは、file-issue の「まとめるときに本文を書き換えるとき」の節の手順で、残すIssueの本文を、最後に所有者に示した全文に書き換え、読み直して確かめてから、閉じるほうのIssue(残すIssueでない、まとめるIssue)をそれぞれ閉じる。本文の書き換えに失敗したとき、または読み直した本文が最後に示した全文と違うときは、AIは、ほかのIssueを閉じずに、失敗したことと gh のエラーの文面と書き換えるはずだった全文を所有者に示して止まる。閉じる操作に失敗したときは、AIは、残すIssueの本文をそのままにし、閉じられなかったIssueの番号と gh のエラーの文面を所有者に示して止まり、所有者がそのIssueを閉じてよいと答えたら、閉じる操作をやり直してから5か6へ進む
5. 残したIssueが #N のときは、AIは、書き換えた本文を `gh issue view <N> --json number,title,body` で読み直し、まとめた本文で Step 4 と Step 5 をやり直す。AIは Step 5.5 を飛ばし、まとめる相手をもう一度は探さない。AIは、やり直して決めた進め方で、Step 6 の報告を出し直し、報告に、まとめて閉じたIssueの番号を1行で添える。この報告にはまとめる提案が無いので、AIは、Step 6 と Step 7 の、まとめる提案が無いときの決まりのとおりの時点で、#N のブランチを作り、`session.sh claim` で記録する。やり直した判断が「Issueを分ける」なら、AIは、Step 7 の決まりのとおりブランチを作らない
6. 残したIssueが #N でないとき(残したIssueを #M とする)は、AIは、#M を着手の対象にして、Step 1 からやり直す。所有者は `/start #M` を打たない。AIは、#M の Step 5.5 を飛ばし、まとめる相手をもう一度は探さない。ブランチは、#M の Step 6 と Step 7 の、まとめる提案が無いときの決まりのとおりに、#M のブランチとして作り、`session.sh claim <M>` で記録する。やり直した判断が「Issueを分ける」なら、AIは、Step 7 の決まりのとおりブランチを作らない。#N のために Step 1.5 で書かれた着手の予約は、#N が閉じているので、残しておいても、ほかのセッションの着手を止めない。AIは、この予約を消す操作をしない

まとめたあとの作業のPRの本文の `Closes` と `Refs:` には、AIは、残したIssueの番号だけを書き、まとめて閉じたIssueの番号を書かない。

**すでに spec がある機能を spec 無しで直す**

すでに spec がある機能に関わる変更でも、4つの観点のどれにも当たらないときは、判断は「spec を作らずに実装する」になる。AIは「spec を作らずに実装する」と同じく、返事を待たずに実装し、`/ship` で出荷する。

**Issueを分ける**

AIは、Step 6 の報告に続けて、次の書式で分け方を示し、止まって所有者の返事を待つ。所有者が了承するまで、AIは分けたどの部分にも着手しない。この判断のときは、AIはブランチを作らず、`session.sh claim` も呼ばない。

```markdown
## 分け方
| 部分 | 内容 | 進め方の見込み | 理由 |
|---|---|---|---|
| 1 | <この部分で変えること> | spec を作らずに実装する / 新しい spec を作る / spec <feature> を直す | <4つの観点のどれに当たるか、当たらないか> |

## 分けた部分のIssueの案
### 部分1: <題名>
<本文の案。file-issue の「本文の書式」に従い、最初の行に「#<元の番号> を分けた部分です。」と書く>

ラベル: <種類のラベル>、<場所のラベル>
```

- 「進め方の見込み」の列は見込みとして示す。部分ごとの着手のときの判断は、所有者が部分ごとに打った `/start` の中で、AIが改めて行う
- AIは、部分ごとのラベルを、file-issue の「ラベルの選び方」の節に従って選び、「ラベル:」の行に書く。場所のラベルを2つ以上選んだときは、AIは場所のラベルを「、」で区切って並べる。場所のラベルを選ばなかったときは、AIは「、<場所のラベル>」を書かず、種類のラベルだけを書く
- 所有者が了承したら、AIは file-issue の「分けた部分のIssue」の手順(「所有者が了承した分け方で分けるとき」)で、部分ごとにIssueを起票する。了承された案のとおりに起票し、ラベルも了承された案の「ラベル:」の行のとおりに付ける。起票のあとは下の「分けたあとの進め方」で進める
- 所有者が分け方や案の修正を求めたら、AIは直した分け方と案を同じ書式で示し、改めて了承を待つ
- 起票が途中で失敗したら、AIは起票できたIssueの番号と、起票できなかった部分を所有者に示して止まる。起票できたIssueは閉じずに残す(file-issue の「起票が途中で失敗したとき」)。次に所有者が `/start #<元の番号>` を打つと、Step 3 が起票できたIssueを一覧に出す

### Step 8: 所有者が止めたとき

spec を作らずに実装している途中で所有者が止めたら、AIは次のとおりにする。

1. AIは実装を止める
2. AIは、それまでの変更を失わないよう、いまのブランチにコミットする。コミットはローカルだけにし、push しない。コミットの形は `/ship` の手順3(メッセージをファイルに書き、変更したファイルを個別に `git add` し、`git commit -F` で記録する)に従う
3. AIは、所有者の指示に従って、進め方を決め直す。決め直した進め方は、Step 6 の書式で示す

## 分けたあとの進め方

**「Issueを分ける」で部分のIssueを起票したあと**

AIは、その会話ではどの部分にも着手しない。AIは、Step 3 と同じく部分のIssueの番号と題名を一覧で示し(分け方で示した進め方の見込みを添える)、所有者に、部分ごとに `/start #<部分の番号>` を打つよう案内して終える。案内には、並行して進める部分は worktree を選んで開いた新しいセッションで打つことと、1つはその会話で打ってもよいことを添える。

```markdown
## してほしいこと
部分ごとに `/start #<番号>` を打ってください。並行して進める部分は、worktree を選んで新しいセッションを開き、そこで打ってください。1つはこの会話で打ってもかまいません。

## 分けた部分のIssue(全<total>件)
| 番号 | 題名 | 進め方の見込み |
|---|---|---|
| #<番号> | <題名> | spec を作らずに実装する / 新しい spec を作る / spec <feature> を直す |
```

- 1つの作業フォルダが2つ以上の spec を同時に抱えると、ブランチを切り替えたときに spec が手元から消えるか別のブランチに混ざり、別のセッションからも引き継げない。そのため、部分は、それぞれ所有者が打つ `/start` で進める
- 分けた部分のIssueは、所有者が `/start` を打ったときに、ふつうのIssueと同じく Step 1.5 と Step 5 から Step 7 を通る。ブランチの作成と `session.sh claim` は、Step 7 のとおりに行われる。PRは部分ごとに1つ作り、`Refs:` と `Closes` にはその部分のIssueの番号を書く(`/ship` の手順5の決まり)
- 会話が途切れたとき: 所有者が、まだ開いている部分ごとに `/start #<分けた部分のIssueの番号>` を打てば続きから進む。対応する spec があれば Step 2 が spec の進み具合を示し、元のIssueの番号で打ったときは Step 3 が分けた部分の一覧を示す。spec の無い部分は、Step 4 から調べ直して進め方を決める

**実装の途中で分けたとき(「途中で見立てが外れたとき」の「小さく分ける」)**

最初の部分の変更がいまのブランチにすでにあるので、AIは最初の部分だけをその会話で続ける。

- AIは、最初の部分のIssueを起票した直後に、`bash .claude/scripts/parallel/session.sh claim <最初の部分の番号> --branch <いまのブランチ> --session <ID>` を呼ぶ(`--session` は Step 1.5 の1のとおりに付ける)。200行の検査で止まって新しいブランチを作り直すときは、最新の main から作った直後に、作ったブランチで呼ぶ(下の「ブランチの扱い」)。`claim` が0でない終了コードで終わったら、AIは先へ進まず、終了コードと標準エラーの文を所有者に伝えて止まる
- 残りの部分は、上と同じく部分ごとの `/start` で進める。AIは、起票したIssueの番号と題名を示すときに、残りの部分ごとに `/start #<部分の番号>` を打つよう案内する。この会話では最初の部分を続けるので、案内には、残りの部分を並行して進めるときは worktree を選んで開いた新しいセッションで打つことを添える

## 途中で見立てが外れたとき

spec を作らずに実装している途中で、着手時の判断(4つの観点のどれにも当たらない)が外れたと分かったときの扱い。

### 見直しの時点

spec を作らずに実装している間、AIは次の時点で、Step 5 の4つの観点を当て直す。

- 作り方の方針を決めたとき、または変えたとき
- Issueの本文に書かれていない動きを決める必要が出たとき
- 保存されているデータ、外部への送信、本番の設定に触れる変更を書こうとしたとき
- `/ship` を始める前

観点2と観点3は、AIは Step 5 の「観点2と観点3の当てはめ方」の手順で当て直す。当て直した結果、問いの候補があり、候補が「1回尋ねれば決まる」の条件を満たすときは、AIは実装を止めて問いを出す。問いの出し方と、答えを受けたあとの進め方は、Step 7 の「問いの出し方と答えの書き足し」の5のとおりにする。問いは、見直しの時点ごとに1回にまとめる。候補が条件を満たさないときは、候補の出どころの観点に当たるので、AIは下の「手順」で進める。

### 手順

1. 見直しの時点で、4つの観点のどれか1つにでも当たると分かったら、AIはその時点で実装を止める
2. AIは、変更を部分に分けて考え、どちらに進むかを決める。分けたどの部分も4つの観点のどれにも当たらないなら「小さく分ける」、そうでなければ「spec に切り替える」にする。AIは、決めたことと理由を、次の書式で所有者に示す
   ```markdown
   ## してほしいこと
   <次のどれか1つ>
   - 次のコマンドを打ってください: `/kiro-spec-init #<N>`
   - 何もしなくて大丈夫です。下の分け方で進めます。判断がおかしいと思ったら止めてください

   ## 判断: <spec に切り替える | 小さく分ける>

   ## 理由
   <当たると分かった観点と、その根拠(ファイルと行、またはIssue本文の見出し)。小さく分けるときは、部分ごとに4つの観点のどれにも当たらない根拠>
   ```
3. spec に切り替えるとき:
   - AIは、それまでの変更を失わないよう、いまのブランチにコミットする。コミットはローカルだけにし、push しない。コミットの形は `/ship` の手順3(メッセージをファイルに書き、変更したファイルを個別に `git add` し、`git commit -F` で記録する)に従う
   - AIは、変更を残したブランチの名前を所有者に示す
   - AIは、所有者に `/kiro-spec-init #<N>` を打つよう依頼する
   - spec の実装の段階(所有者が `/kiro-impl` を打ったあと)に入るまで、AIは実装を再開しない
   - ブランチに残した変更を使うかどうかは、spec の tasks で決める
4. 小さく分けるとき:
   - AIは、分け方と理由を示す。書式は Step 7 の「Issueを分ける」の「分け方」の表と同じにする(進め方の見込みの列はすべて「spec を作らずに実装する」になる)
   - AIは、所有者の返事を待たずに、file-issue の「分けた部分のIssue」の手順(「実装の途中で小さく分けるとき」)で、部分ごとにIssueを起票する。本文は、元のIssueの本文からの抜き出しだけで作る。言い換えず、元のIssueに無い要望を足さない
   - ブランチは、下の「ブランチの扱い」のとおりにする
   - 起票のあとは、AIは最初の部分だけをこの会話で続け、最初の部分のIssueを起票した直後(200行の検査で止まったときは、最初の部分の新しいブランチを作った直後)に `session.sh claim` で最初の部分のブランチとして記録する。残りの部分は部分ごとの `/start` で進める(「分けたあとの進め方」の「実装の途中で分けたとき」)
5. 200行の検査(size-check)でPRが止まったとき:
   - AIは、1と同じく、その時点で実装を止める。PRを直して push し直すことはしない
   - AIは、2と同じく、spec に切り替えるか小さく分けるかを決めて、理由を示す
   - spec に切り替えるときは、AIはPRを閉じ(`gh pr close <PRの番号>`。ブランチを消す `--delete-branch` は付けない)、ブランチを残して3に進む。変更はすでに push されているので、3のコミットは、まだコミットしていない変更があるときだけ行う
   - 小さく分けるときは、AIはPRを閉じ(`gh pr close <PRの番号>`)、4に進む。ブランチは、下の「ブランチの扱い」の「200行の検査で止まったとき」のとおりにする

### ブランチの扱い

小さく分けるときのブランチの扱いは、どこで分けると決めたかで変わる。

- 実装の途中で分けるとき: いまのブランチに最初の部分だけを残し、ほかの部分の変更を取り除く。AIは、最初の部分のIssueを起票した直後に、`session.sh claim <最初の部分の番号> --branch <いまのブランチ> --session <ID>` を呼ぶ。取り除いた部分は、所有者が部分ごとに打った `/start` の中で、その部分のブランチで作り直す
- 200行の検査で止まったとき: PRを閉じ、最初の部分の新しいブランチを、「spec を作らずに実装する」の手順1と同じく最新の main(`origin/main`)から作る。AIは、作った直後に `session.sh claim <最初の部分の番号> --branch <作ったブランチ> --session <ID>` を呼び、最初の部分を新しいブランチで作り直す。残りの部分は、所有者が部分ごとに打った `/start` の中で、その部分のブランチで作り直す

どちらの場合も、PRは部分ごとに1つ作り、`Refs:` と `Closes` にはその部分のIssueの番号を書く(`/ship` の手順5の決まり)。
