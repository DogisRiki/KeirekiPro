# request

壁打ちの会話から、要望のIssueと検討メモを作って起票する。**起票の前に案を所有者に見せ、了承を得る。**

監査の通知(`audit`)や振り返り(`retrospective`)のIssueは対象外。それぞれの様式に従う。

## 本文とコメントの分担

| 置き場所 | 書くもの | 読む側 |
|---|---|---|
| Issue本文(要望) | 困っていること、やりたいこと、その理由、どうなれば解決か、やらないこと | spec-reviewer と codex-review が判定の基準にする |
| Issueのコメント(検討メモ) | 調べた事実と根拠、方式の案、退けた案とその理由、specが要るかの見立て、未決事項 | kiro-spec-init / requirements / design と、小修正の実装者が参考に読む |

分ける理由: spec-reviewer と codex-review は本文だけを読む。requirements のレビューは、Issue本文に書かれていない部分をAIが解釈で埋めた箇所を「申告」として所有者に見せる。本文に方式や設計判断が入ると、それが要望として扱われ、申告に上がらない。

### 本文の書式

```markdown
## 困っていること

## やりたいこと

## どうなれば解決か

## やらないこと
```

- 所有者の言葉の水準で書く。「どうなれば解決か」は、画面・動作・ファイルの中身など、確かめられる結果で書く
- **書かないもの**: 方式(どのファイルをどう変えるか、何の道具を使うか)、検証の手段(どう試験するか)、設計判断、原因の調査結果。これらは検討メモに書く
- 中身の無い見出しは省く。「困っていること」と「やりたいこと」の少なくとも一方は書く

### 検討メモの書式

**1行目は必ず `## 検討メモ(要望ではない)` にする。** 後段のスキルはこの見出しでコメントを見分ける。

```markdown
## 検討メモ(要望ではない)

壁打ちの記録。specのレビューとCodexのレビューはIssue本文だけを基準にし、このコメントは基準に含めない。

### 調べた事実(<日付>時点)

### 方式の案

### 退けた案

### 見立て

### 関連
```

- 調べた事実には、ファイルと行、コマンド、URLなどの根拠を付ける
- 中身の無い見出しは省く

## 手順

### Step 1: 決まったことを集める

会話を読み返し、所有者が決めたことを集める。引数に補足があれば加える。

各項目の出どころを次の3つに分ける。

- **あなたの発言**: 所有者が自分で言ったこと
- **提案して了承済み**: AIが提案し、所有者が了承したこと
- **AIの補い**: 所有者がまだ何も言っていないこと

何を作るかが会話から読み取れないときは、案を作らずに所有者に尋ねる。

### Step 2: 似たIssueを探す

`gh issue list --state open --search "<キーワード>"` で、同じ要望の開いたIssueが無いか探す。あれば、新しく起票せずにそのIssueへ追記する案を所有者に示す。

### Step 3: 案を書く

本文と検討メモを、scratchpad にそれぞれファイルとして書く。

書いたら本文を見直す。方式・検証の手段・原因の調査結果が混じっていれば、検討メモへ移す。

### Step 4: 所有者に見せる

チャットに次を出す。

- 題名
- 本文の全文。各項目の末尾に、Step 1 の出どころを言葉で付ける(「あなたの発言」「提案して了承済み」「AIの補い」)。**出どころはIssueには載せない**
- 検討メモの見出しと要点
- 関連するIssue

AIの補いは、本文から外して検討メモに移すのを基本にする。本文に残したものがあれば、それぞれ残すか外すかを尋ねる。

尋ねるのは「この内容で起票してよいか」の1点にまとめる。直すよう言われたら、直して Step 4 をやり直す。

### Step 5: 起票する

了承を得たら、1つずつ実行する。

```
gh issue create --title "<題名>" --body-file <本文のファイル>
gh issue comment <番号> --body-file <検討メモのファイル>
```

### Step 6: 次の手順を案内する

- spec が要る(新機能・複数の層にまたがる変更・実装の差分が200行を超える見込み): `/kiro-spec-init #<番号>`
- spec が要らない: 検討メモを読んだうえで実装に進む

## 制約

- **了承を得ずに起票しない**
- 起票したIssueの本文を、所有者に断らずに書き換えない。本文は判定の基準になる
- このスキルは起票の型と確認の手順であり、ほかの方法での起票を止める仕組みではない
