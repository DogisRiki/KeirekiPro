# retrospective

## Job

ループの5ステップ目「経験還元」。ゲートすり抜けを**個別の修正で終わらせず**、
「同種の問題を機械が拾えるようにするゲート強化」へ変換して記録する。

発動タイミング:
- 本番・ローカル確認で見つかった不具合(=全ゲートをすり抜けた)
- カナリアPR(月次)の検出漏れ
- mutation testing(週次)のスコア低下
- Codexレビューの誤検知が週の閾値(3件)を超えたとき

## Steps

1. **事象の記録**: 何がすり抜けたか、どのゲートで拾えるべきだったかを特定する。

2. **ゲート強化案の作成**: 次の順で「機械化できる最も強い層」を選ぶ:
   1. テスト追加(再発を直接検知する回帰テスト)
   2. Lint/ArchUnitルール追加(同種のパターンを静的に禁止)
   3. escape-hatch/guardrails CIへの検知追加
   4. Codexレビュープロンプト(codex-review.yml)への観点追加
   5. CLAUDE.md/Skillへの規約追記(機械化できない場合の最終手段)

3. **記録**: GitHub Issueとして起票する。状態管理はIssueのopen/closedで行う。

   ラベルは `.github/labels.json` が持ち、ワークフローがGitHubに作るので、この手順では作らない。

   ラベルは、起票の決まり(`.claude/skills/file-issue/SKILL.md`)の「ラベルの選び方」の節に従って選ぶ。
   種類のラベルは、ラベルの一覧のファイルの選ぶときの決まり(`selection_rule`)が振り返りの手順を名指ししているラベルがあれば、それを選ぶ。
   場所のラベルは、選んだ種類のラベルの `area_required` が `true` のときだけ付ける。

   起票コマンド(タイトルは事象の短い題名、本文は次の様式):

```
gh issue create --label <種類のラベル> [--label <場所のラベル>] --title "<事象の短い題名>" --body "..."
```

```markdown
## 事象
<何が起きたか>

## 見逃した検査
<どの検査で拾えるはずだったか>

## 強化案
<Step 2 の5つの層のうち、どの層に何を足すか。層は、番号でなく「テストの追加」のような名前で書く>
```

   起票したら、Issueの番号と付けたラベルを所有者に示す。

4. **実行**: 強化案のうち自分で実施できるもの(テスト追加等)は実施し、完了したらIssueをcloseする。
   ゲート設定ファイル(CODEOWNERS保護対象)の変更が必要なものは、Issue本文に人間の承認が必要な旨を
   明記してopenのままにする(月次監査で棚卸しされる)。

## Rules

- 「修正しました」で終わらせない。**ゲート追加まで行って完了**(発見時はゲート追加が必須の運用ルール)
- 回帰テストは、まず不具合を再現して赤になることを確認してから修正する
