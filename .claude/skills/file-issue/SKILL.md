# file-issue

Issueを起票するときの決まり。**起票の前に案を所有者に見せ、了承を得る。**

どの経路の起票にも使う。

- 作業中に別の問題や障害を見つけ、AIが「Issueにしますか」と提案して所有者が了承したとき
- 所有者が「起票して」と頼んだとき
- `/request` の最後(記録ファイルを受け取る)
- 1つのIssueを分けて進めるとき(「分けた部分のIssue」の節に従う)

監査の通知(定期実行が起票する `audit`)と振り返り(`retrospective`)のIssueは対象外。それぞれの様式に従う。

## 要望の定義

Issue本文は要望を書く。要望とは、**所有者が引き受けると決めたこと**である。AIが見つけた不具合を所有者が直すと決めたものも含む。

## Issueは本文だけにする

Issueは本文だけにする。調べた事実、原因の調査結果、方式の案、見立てを書き残すコメントは付けない。

**本文に載せるかどうかは「誰が決めたか」で分ける。** 所有者が決めたことは、方式であっても本文に載せる。AIの提案を所有者が了承しただけの方式、AIの補い、調べた事実、原因の調査結果は載せない。方式は仕様を決める段階(design)で考え、事実は仕様づくりや実装のときに調べ直す。

載せない理由: spec-reviewer と codex-review は本文だけを読む。requirements のレビューは、Issue本文に書かれていない部分をAIが解釈で埋めた箇所を「申告」として所有者に見せる。AIが決めたことが本文に入ると、所有者の要望として扱われ、申告に上がらない。

## 出どころの分け方

本文の各項目には、次のいずれかの出どころがある。

| 出どころ | 意味 |
|---|---|
| 所有者の発言 | 所有者が自分で言ったこと |
| AIの提案を了承 | AIが提案し、所有者が了承したこと |
| AIの補い | 所有者がまだ何も言っていないこと |
| 会話から拾った(記録なし) | 記録が始まる前の会話、または記録ファイルの無い会話から拾ったもので、出どころを確かめられないもの |

## 本文の書式

```markdown
## きっかけ

## 困っていること

## やりたいこと

## どうなれば解決か

## 決めた方式

## やらないこと
```

- **きっかけ**: 所有者の言葉があれば、原文を1〜2行そのまま引用する。無ければ、見つけた経緯を1行で書く(例: 「#384 の作業中(PR #393)にAIが見つけ、所有者が起票を指示」)
- **どうなれば解決か**: 画面・動作・ファイルの中身など、確かめられる結果で書く
- **決めた方式**: 所有者が決めて、変えてはいけない方式だけを書く
- 中身の無い見出しは省く。「困っていること」と「やりたいこと」の少なくとも一方は書く
- 本文に残した項目の出どころが「AIの提案を了承」なら、項目の末尾に「(AIの提案を了承)」と書く。spec-review はこの印の項目を所有者の発言として扱わず、Issueに記載があっても通常の申告基準で申告するかを判断する

## 手順

### Step 1: 項目と出どころを集める

`/request` から記録ファイルを受け取った場合は、「決定」から本文の項目と出どころを取る。「起票済み」の行で示された項目は除く。

記録ファイルが無い場合は、会話を読み返して項目を集め、出どころを「会話から拾った(記録なし)」にする。

### Step 2: 似たIssueを探す

`gh issue list --state open --search "<キーワード>"` で、同じ内容の開いたIssueが無いか探す。あれば、新しく起票せずにそのIssueに足す案を所有者に示す。本文を変えるときは、所有者の了承を得る。

### Step 3: 案を書く

本文を、scratchpad にファイルとして書く。複数件あるときは件ごとに分ける。

書いたら本文を見直す。出どころが「AIの補い」の項目、AIの提案を了承しただけの方式、調べた事実、原因の調査結果が残っていれば、本文から外す。

### Step 4: 所有者に見せる(確認は1回)

チャットに次を出す。

- 題名
- 本文の全文。各項目の末尾に出どころを付ける。**出どころの表示はIssueには載せない**(「(AIの提案を了承)」の印は除く)
- 関連するIssue

出どころが「会話から拾った(記録なし)」の項目は、所有者に出どころを答えてもらう(「自分で決めた」「AIの案を了承した」「覚えがない」)。「覚えがない」と答えられた項目は本文から外す。

尋ねるのは「この内容で起票してよいか」の1点にまとめる。複数件あるときも1回にまとめる。直すよう言われたら、直して Step 4 をやり直す。

### Step 5: 起票する

了承を得たら実行する。

```
gh issue create --title "<題名>" --body-file <本文のファイル>
```

記録ファイルから起票した場合は、記録ファイルの末尾に `起票済み: #<番号>(<起票した要望の見出し>)` を追記する。

### Step 6: 次の手順を案内する

所有者に「着手するときは `/start #<番号>` を打ってください」とだけ案内する。spec の要否は案内しない(着手のときに `/start` が決める)。

## 分けた部分のIssue

1つのIssueを分けて進めると決まったとき(`/start` で決まる)は、分けた部分ごとにIssueを起票する。

- 起票は次のコマンドで行う。親子の関係は GitHub のサブIssueで表し、元のIssueと分けた部分のIssueのどちらの画面からも相手が見える

  ```
  gh issue create --title "<題名>" --body-file <本文のファイル> --parent <元のIssueの番号>
  ```

- 本文の書式は「本文の書式」と同じ。本文の最初に「#<元の番号> を分けた部分です。」と1行書く
- 本文は scratchpad に部分ごとのファイルとして書く。起票したIssueの番号は、`gh issue create` が出力するURLから取る

### 所有者が了承した分け方で分けるとき

- 本文は、元のIssueの本文のうちその部分に当たる項目と、了承された分け方のうちその部分の範囲だけで作る
- 分け方の提案の中で本文の案を所有者に見せ、了承を得ているので、Step 4 を改めて行わない。了承された案のとおりに起票する

### 実装の途中で小さく分けるとき

`/start` の「途中で見立てが外れたとき」で小さく分けると決めたときは、**所有者の了承を待たずに起票する。これは「了承を得ずに起票しない」の例外である。**

- 本文は、元のIssueの本文からの抜き出しだけで作る。言い換えず、元のIssueに無い項目を足さない
- 「(AIの提案を了承)」などの出どころの印も、元のIssueのとおりに写す
- 起票したら、起票したIssueの番号と題名を所有者に示す

### 起票が途中で失敗したとき

複数の部分を起票している途中で失敗したら、起票できたIssueの番号と、失敗した部分を所有者に示して止まる。起票できたIssueは閉じずに残す(次の `/start` が一覧に出す)。

## 制約

- **了承を得ずに起票しない**。例外は「分けた部分のIssue」の「実装の途中で小さく分けるとき」だけである
- 起票したIssueの本文を、所有者に断らずに書き換えない。本文は判定の基準になる
