# requirements の観点

## 前提

Issue は要望の水準で書かれている(あれをやりたい、これをやりたい)。それを厳密に定義するのが requirements である。したがって、**Issue に書かれていない部分を AI が解釈で埋めている。** その埋めた場所を所有者に見せるのが申告の役目。

生成側には書く前の自己点検(`.claude/skills/kiro-spec-requirements/rules/requirements-review-gate.md`)がある。そこに書かれている機械的な検査(数値ID、受入基準の存在、実装語の混入)と重なる指摘は出さなくてよい。**ただし「gate にあるから効いている」とは考えない。** 実際の本文を見て判断する。

spec.json の `spec_format` が2の spec では、見出しと目印を `.kiro/settings/rules/spec-writing.md` の対応表の新しい名前で読む。要件は `### 要件N 題名` の見出しで始まる。`#### Acceptance Criteria` の見出しが無いので、受入基準は各要件の番号付きの項目である。`spec_format` の欄が無い spec では、今の名前のまま読む。

## 観点

### 1. 申告

`common.md` の申告の規則に従う。requirements では、**Issue に書かれていない部分を解釈で埋めたところ**が対象。

Issue 本文で「(AIの提案を了承)」の印が付いた項目は、所有者の発言ではなく AI の提案である。Issue に書かれていても、申告の規則(他にありえた選択肢があり、外れていたときの手戻りが大きいか)に当てはめて申告するかを判断する。

### 2. 要望の取りこぼし

Issue に書かれた「やりたいこと」のうち、対応する要件が1つも無いものが無いか。Issue が厚い場合は項目ごとに確認する。

**取りこぼしは最も重い種類の欠陥である。** 要件に書かれていないものは実装されず、PR 段階の codex-review も要件を判定の基準にするため、永久に検出されない。

spec.json に `additional_issues` があるとき(既存の spec を新しいIssueのために更新したとき)の見方は、観点9に従う。

### 3. 勝手な追加

Issue に無い「やりたいこと」を、AI が要件として足していないか。厳密化(書かれていたことを具体的にする)ではなく、新しい機能の追加を指す。承認すると実装される。

spec.json に `additional_issues` があるときの見方は、観点9に従う。

### 4. 厳密になっていない要件

受入基準が、判定する側が何を見ればよいかまで書けているか。形式が整っていても中身が曖昧なものを見る。

### 5. 検証する手段が無い要件

その要件を満たしたかどうかを確かめる方法が、このリポジトリに存在するか。tasks の完了条件は「テストが無い受入基準を残さない」と定めているため、ここで漏れると tasks 段階で requirements まで戻ることになる。

### 6. 要件同士の矛盾

ある要件と別の要件が食い違っていないか。実装がどちらに従うべきか決まらない状態を探す。

**この観点は、修正の後に効く。** 生成側の自己点検は書く前に1回走るだけで、指摘を受けて直した後の姿を見ていない。

### 7. steering との整合

`.kiro/steering/product.md` `tech.md` `structure.md` と矛盾する前提を置いていないか。

### 8. 誤字脱字

`common.md` の分類に従う。

### 9. 更新した spec の基準

spec.json に `additional_issues` があるとき、その spec は既存の spec を新しいIssueのために更新したものである。`issue`(元のIssue)と `additional_issues` のすべてのIssueの本文を基準にする。要件と受入基準に付いた印で、どのIssueに対するものかを見分ける。

| 印 | 意味 |
|---|---|
| 末尾に `(#N)` | Issue #N のために足した項目 |
| 末尾に `(#N で変更)` | Issue #N のために直した既存の項目 |
| 先頭に `(#N で取りやめ)` | Issue #N のために取りやめた既存の項目(本文は残る) |
| 印が無い | 元のIssue(`issue`)に対する項目 |

- **取りこぼし**(観点2): 追加のIssue #N の「やりたいこと」のうち、`(#N)`、`(#N で変更)`、`(#N で取りやめ)` のいずれかの印が付いた要件・受入基準が1つも対応していないものは、取りこぼしである
- **勝手な追加**(観点3): どのIssueの本文にも無い「やりたいこと」を足した要件は、勝手な追加である。`(#N)` の印が付いた要件は、Issue #N の本文を基準に見る。Issue #N の本文に無いとき、どのIssueの本文にも無ければ勝手な追加とし、別のIssueの本文にあれば印の誤りとする
- **印の無い要件**は、元のIssueの本文を基準に見る
- 印の付け方そのものの誤り(Issue #N のための変更なのに印が無い、印の番号が `additional_issues` に無い、印の番号が、その要望の書かれたIssueと違う)も指摘する。印が誤っていると、どのIssueの要望かを見分けられず、取りこぼしと勝手な追加を判定できない
