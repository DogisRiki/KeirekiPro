# requirements の観点

## 前提

Issue は要望の水準で書かれている(あれをやりたい、これをやりたい)。それを厳密に定義するのが requirements である。したがって、**Issue に書かれていない部分を AI が解釈で埋めている。** その埋めた場所を所有者に見せるのが申告の役目。

生成側には書く前の自己点検(`.claude/skills/kiro-spec-requirements/rules/requirements-review-gate.md`)がある。そこに書かれている機械的な検査(数値ID、受入基準の存在、実装語の混入)と重なる指摘は出さなくてよい。**ただし「gate にあるから効いている」とは考えない。** 実際の本文を見て判断する。

## 観点

### 1. 申告

`common.md` の申告の規則に従う。requirements では、**Issue に書かれていない部分を解釈で埋めたところ**が対象。

### 2. 要望の取りこぼし

Issue に書かれた「やりたいこと」のうち、対応する要件が1つも無いものが無いか。Issue が厚い場合は項目ごとに確認する。

**取りこぼしは最も重い種類の欠陥である。** 要件に書かれていないものは実装されず、PR 段階の codex-review も要件を判定の基準にするため、永久に検出されない。

### 3. 勝手な追加

Issue に無い「やりたいこと」を、AI が要件として足していないか。厳密化(書かれていたことを具体的にする)ではなく、新しい機能の追加を指す。承認すると実装される。

### 4. 厳密になっていない要件

受入基準が、判定する側が何を見ればよいかまで書けているか。形式が整っていても中身が曖昧なものを見る。

### 5. 検証する手段が無い要件

その要件を満たしたかどうかを確かめる方法が、このリポジトリに存在するか。tasks の完了条件は「テストが無い受入基準を残さない」と定めているため、ここで漏れると tasks 段階で requirements まで戻ることになる。

### 6. 要件同士の矛盾

ある要件と別の要件が食い違っていないか。実装がどちらに従うべきか決まらない状態を探す。

**この観点は、修正の後に効く。** 生成側の自己点検は書く前に1回走るだけで、指摘を受けて直した後の姿を見ていない。

### 7. steering との整合

`.kiro/steering/product.md` `tech.md` `structure.md` と矛盾する前提を置いていないか。

### 8. 誤字脱字

`common.md` の分類に従う。
