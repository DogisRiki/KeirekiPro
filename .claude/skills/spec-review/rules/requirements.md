# requirements の観点

## 前提

Issue は要望の水準で書かれている(あれをやりたい、これをやりたい)。それを厳密に定義するのが requirements である。したがって、**Issue に書かれていない部分を AI が解釈で埋めている。** その埋めた場所を所有者に見せるのが申告の役目。

生成側には書く前の自己点検(`.claude/skills/kiro-spec-requirements/rules/requirements-review-gate.md`)がある。そこに書かれている機械的な検査(数値ID、受入基準の存在、実装語の混入)と重なる指摘は出さなくてよい。**ただし「gate にあるから効いている」とは考えない。** 実際の本文を見て判断する。

見出しと目印は、`.kiro/settings/rules/spec-writing.md` の「見出しと目印の一覧」の名前で読む。Issueの印の決まりは、`.kiro/settings/rules/spec-writing.md` の「Issueの印」の節で読み、印の付け方の誤りも指摘する。要件は `### 要件N 題名` の見出しで始まる。受入基準は各要件の番号付きの項目である。

## 観点

### 1. 申告

`common.md` の申告の規則に従う。requirements では、**Issue に書かれていない部分を解釈で埋めたところ**が対象。

Issue 本文で「(AIの提案を了承)」の印が付いた項目は、所有者の発言ではなく AI の提案である。Issue に書かれていても、申告の規則(他にありえた選択肢があり、外れていたときの手戻りが大きいか)に当てはめて申告するかを判断する。

### 2. 要望の取りこぼし

Issue に書かれた「やりたいこと」のうち、対応する要件が1つも無いものが無いか。Issue が厚い場合は項目ごとに確認する。

**取りこぼしは最も重い種類の欠陥である。** 要件に書かれていないものは実装されず、PR 段階の codex-review も要件を判定の基準にするため、永久に検出されない。

spec.json に `additional_issues` があるとき(既存の spec を新しいIssueのために更新したとき)の見方は、観点9に従う。

### 3. 勝手な追加

Issue に無い「やりたいこと」を、AI が要件として足していないか。厳密化(書かれていたことを具体的にする)ではなく、新しい機能の追加を指す。承認すると実装される。

spec.json に `additional_issues` があるときの見方は、観点9に従う。

### 4. 厳密になっていない要件

受入基準が、判定する側が何を見ればよいかまで書けているか。形式が整っていても中身が曖昧なものを見る。

**範囲を限らない書き方の受入基準は、当てはまる場面と当てはまらない場面が書かれているかを見る。** 範囲を限らない書き方とは、「〜を正解とする」「〜と同じにする」「すべての〜」「どの〜でも」「常に〜」のように、その受入基準が当てはまる場面を限る言葉が無い書き方である。決まりは `.kiro/settings/rules/spec-writing.md` の「範囲を限らない受入基準と、逆のことを決める受入基準」の節にある。範囲を限らない書き方の受入基準に、当てはまる場面と当てはまらない場面が書かれていなければ、指摘する。当てはまらない場面が無い受入基準には、例外が無いことが書かれていればよい。

範囲を限らない受入基準は、書いた Claude が考えていなかった場面にも当てはまる。実装する Claude は、その場面でも受入基準のとおりに作る。書き方の点検役は、当てはまらない場面を決められない。当てはまらない場面を書き足すと、決めごとの中身が変わるためである。そのため、この外れは審査役が指摘する。

### 5. 検証する手段が無い要件

その要件を満たしたかどうかを確かめる方法が、このリポジトリに存在するか。tasks の完了条件は「テストが無い受入基準を残さない」と定めているため、ここで漏れると tasks 段階で requirements まで戻ることになる。

### 6. 要件同士の矛盾

ある要件と別の要件が食い違っていないか。実装がどちらに従うべきか決まらない状態を探す。

**この観点は、修正の後に効く。** 生成側の自己点検は書く前に1回走るだけで、指摘を受けて直した後の姿を見ていない。

**受入基準を並べて読むだけで済ませず、受入基準の組を具体的な場面に当てはめる。** 2つの受入基準が別々の要件にあり、違う言葉で書かれていると、並べて読んでも、どちらも正しく見えるためである。審査役は、次の手順で確かめる。

1. 組を作る。次の2種類の受入基準を、同じ対象について決めている別の受入基準と組にする。同じ対象とは、同じ操作、同じデータ、同じ画面、同じ相手への答えのことである
   - 範囲を限らない書き方の受入基準(観点4)。範囲を限らない受入基準は、別の受入基準が決めている場面にも当てはまることが多い
   - 「〜してよい」「〜しない」「〜に限る」「ただし〜」のように、何かを許すか、禁じるか、例外を決めている受入基準
2. 組ごとに、2つの受入基準がどちらも当てはまる具体的な場面を探す。場面は、誰が、何を、どんな値で行うかまで書く。どちらも当てはまる場面が無い組は、食い違わない
3. その場面で、それぞれの受入基準のとおりにすると何が起きるかを書く。片方の受入基準のとおりにすると、もう片方の受入基準のとおりにならないときは、2つの受入基準は、その場面で逆のことを決めている
4. 逆のことを決めている組では、その場面でどちらに従うかが requirements に書かれているかを確かめる。書かれていなければ、指摘する。直し方の案には、どちらに従うかを、どの受入基準に書くかを書く

**Issue の本文か requirements の本文が別の spec の受入基準を指しているときは、指された受入基準も同じ手順で確かめる。** 審査役は、指された受入基準を、その spec の requirements.md から読む。審査役は、指された受入基準どうしの組と、指された受入基準と審査している spec の受入基準の組を作る。指された受入基準どうしが逆のことを決めていて、どちらに従うかが、指された spec の requirements にも、審査している spec の requirements にも書かれていなければ、指摘する。直し方の案は、審査している spec の requirements に、どちらに従うかを書く案にする。別の spec の本文は、審査している spec の往復では直せないためである。

審査の範囲が「差分」のときは、差分の中の受入基準を、差分の外の受入基準と組にする。差分の外の受入基準には、指された別の spec の受入基準を含める。差分の外の受入基準どうしの組は作らない。

審査役は、どちらも当てはまる場面があった組を、記録の `### 同じ場面に当てはまる受入基準の組` の表に書く(書式は `common.md`)。頭の中で「食い違いは無さそうだ」と考えるだけで済ませない。場面と結果を書き出さないと、逆のことを決めている組に気づけないためである。

### 7. steering との整合

`.kiro/steering/product.md` `tech.md` `structure.md` と矛盾する前提を置いていないか。

### 8. 誤字脱字

`common.md` の分類に従う。

### 9. 更新した spec の基準

spec.json に `additional_issues` があるとき、その spec は既存の spec を新しいIssueのために更新したものである。`issue`(元のIssue)と `additional_issues` のすべてのIssueの本文を基準にする。要件と受入基準に付いた印で、どのIssueに対するものかを見分ける。

| 印 | 意味 |
|---|---|
| 末尾に `(#N)` | Issue #N のために足した項目 |
| 末尾に `(#N で変更)` | Issue #N のために直した既存の項目 |
| 先頭に `(#N で取りやめ)` | Issue #N のために取りやめた既存の項目(本文は残る) |
| 末尾に `(PR #<番号> で変更済み)` | spec 無しのPRで変わった動きを、spec を更新するときに反映した項目。実装は済んでいる |
| 印が無い | 元のIssue(`issue`)に対する項目 |

- **取りこぼし**(観点2): 追加のIssue #N の「やりたいこと」のうち、`(#N)`、`(#N で変更)`、`(#N で取りやめ)` のいずれかの印が付いた要件・受入基準が1つも対応していないものは、取りこぼしである
- **勝手な追加**(観点3): どのIssueの本文にも無い「やりたいこと」を足した要件は、勝手な追加である。`(#N)` の印が付いた要件は、Issue #N の本文を基準に見る。Issue #N の本文に無いとき、どのIssueの本文にも無ければ勝手な追加とし、別のIssueの本文にあれば印の誤りとする
- **印の無い要件**は、元のIssueの本文を基準に見る
- **`(PR #<番号> で変更済み)` の印の付いた要件・受入基準**は、取りこぼしと勝手な追加の判定から外す。審査役は `gh issue view` しか実行できずPRの本文を読めないため、この印の項目の文がPRの動きと合っているかは判定しない
- 印の付け方そのものの誤り(Issue #N のための変更なのに印が無い、印の番号が `additional_issues` に無い、印の番号が、その要望の書かれたIssueと違う)も指摘する。印が誤っていると、どのIssueの要望かを見分けられず、取りこぼしと勝手な追加を判定できない
