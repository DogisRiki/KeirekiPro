# tasks の観点

## 前提

tasks は実装の順序と粒度を決める。requirements と design の両方と照合できる。

生成側には2つの仕組みがある。

- 書く前の自己点検(`.claude/skills/kiro-spec-tasks/rules/tasks-generation.md` の `Task Plan Review Gate`)
- `kiro-spec-tasks` の Step 3.5(新しいサブエージェントによる独立レビュー)

**Step 3.5 と重なる観点も出してよい。** Step 3.5 は書いたのと同じモデルで走り、書く前に1回だけで、結果が残らない。ただし、Step 3.5 が既に潰しているだけの指摘を機械的に並べない。実際の本文を見て判断する。

## 観点

### 1. 申告

`common.md` の申告の規則に従う。tasks で申告するのは次の2種類。

- やらないと決めたこと(タスクから外した作業、後回しにした検証)
- テストを省略可能な印(`- [ ]*`)にしたこと

**申告しないもの**: タスクの分け方と順序。これは技術的な組み立てで、誤っていれば指摘の側で扱う。

### 2. 要件カバレッジ

すべての受入基準が、少なくとも1つのタスクの `_Requirements:_` に現れるか。逆に、requirements に存在しない番号を参照しているタスクが無いか。

### 3. design カバレッジ

design のコンポーネント・契約・統合点・実行時の前提・検証事項が、それぞれ少なくとも1つのタスクで扱われているか。タスクの `_Boundary:_` が、design の File Structure Plan に載っているファイルの範囲に収まっているか。

### 4. スコープ膨張

requirements の `Out of scope` や design の `Non-Goals` `Out of Boundary` に書いたことを、タスクがやっていないか。**生成側の点検は「足りない」方向だけを見ており、「余計なものが入っている」方向を見ていない。**

### 5. 完了条件の4項目

`.kiro/settings/templates/specs/tasks.md` が全タスク共通の完了条件として定める4項目(受入基準の引用とテストの対応付け、verify の実行、ゴールハック禁止、新規テストの赤の確認)について、次を見る。

- 4項目が書かれているか
- **置き換えている場合に理由が書かれているか。** 変更領域に該当する verify Skill が無い場合など、理由を添えた置き換えは正当である。理由の無い欠落だけを指摘する

### 6. 並列と依存の妥当性

`(P)` の指定、`_Depends:_`、`_Boundary:_` が互いに整合しているか。並列に動かして衝突しないか。

### 7. tasks 内の矛盾

タスク同士が食い違っていないか。

### 8. 前の段階への指摘

タスクに落とそうとして初めて分かった、requirements または design の穴。`common.md` の規則に従い、別の節に書く。**どちらに戻るのかを明記する。**

### 9. 誤字脱字

`common.md` の分類に従う。
