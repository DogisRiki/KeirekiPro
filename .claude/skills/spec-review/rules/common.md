# spec レビューの共通ルール

全段階に共通する、レベル・申告・指摘の番号・記録の書式を定める。段階ごとの観点は `requirements.md` `design.md` `tasks.md` に書く。

## レベル

承認した後にどこまで戻ることになるかで決める。

| レベル | 意味 |
|---|---|
| 高 | 承認した後、誰も気づかないまま実装が終わる。または気づいたときには作り直しになる |
| 中 | 承認した後、後の工程で必ず発覚し、戻って直すことになる |
| 低 | 実装に影響しない |

段階ごとの例。

- requirements: 要件が抜けている(高) / 要件が曖昧で design を書けない(中)
- design: 前提にした外部機能が実際には使えない(高) / 要件に対応するコンポーネントが無い(中)
- tasks: 完了条件が抜けてテストが書かれない(高) / 並列の指定が誤っていて実装中に衝突する(中)

**観点の種類とレベルは対応しない。** 同じ「要望の取りこぼし」でも、落ちたものが中心的な要望なら高、細かい要望なら低になる。指摘ごとに判断する。

### 事実の誤り

spec が今あるもの(コード、設定、開発環境、CI、置き換える前の版の動き)について書いた文が、リポジトリの実ファイルと食い違うときは、**低にしない。** 実装に影響しないように見えても、中以上にする。食い違う文を残したまま承認すると、後の段階で Claude がその文をもとに作り、作り直しになるためである。指摘には、食い違う実ファイルとその行を書く。

### 誤字脱字

- 意味が変わる誤記(「8日」を「3日」と書いた)は、影響で高か中に分類する
- 意味が変わらない誤字脱字は低に分類する

## 指摘の番号

`{段階}{サイクル}-{往復}-{連番}` の形式で振る。

- 段階: `R`(requirements) / `D`(design) / `T`(tasks)
- サイクル: その段階のレビューを新しく始めるたびに1つ増える。初回は1。差し戻しや本文の変更で再レビューになったら2、以降同様
- 往復: そのサイクルの中の往復番号
- 連番: その往復の中の通し番号

例: `R2-1-3` は requirements のサイクル2、往復1、3件目。

メインセッションから渡された `CYCLE` と `ROUND` をそのまま使う。自分で推測しない。

## 申告

AI が決めたことのうち、**他にありえた選択肢があり、外れていたときの手戻りが大きいもの**を一覧にする。他の選択肢が書けないもの(リポジトリの規約で決まっているもの)は申告しない。

1件につき4項目を書き、**外れていたときの影響が大きいものを上に並べる**。

- Issue に何が書いてあったか
- 何を決めたか
- 他に何がありえたか
- 外れていたら何が起きるか

申告は欠陥ではない。所有者が読んで判断するための材料であり、往復の終了条件には数えない。

## 前の段階への指摘

design と tasks の審査中に前の段階(requirements / design)の穴を見つけたら、**その段階への指摘としてではなく、別の節に書く。** 作るものが変わる穴は、メインセッションが直さずに所有者に報告する。作るものが変わらない穴は、メインセッションが前の段階の承認を残して直す。直す手順は、spec-review スキルの Step 4 にある。

### 作るものが変わる穴と変わらない穴

- 作るものが変わる穴は、受入基準、外から見える動き、権限、方式の選び直しのどれかに関わる穴である
- 作るものが変わらない穴は、前の段階の文が古い、足りない、節どうしで数や名前が合わない、のどれかに当たり、受入基準、外から見える動き、権限、方式の選び直しのどれにも関わらない穴である
- 両方の説明に当たる穴と、どちらか決められない穴は、作るものが変わる穴として記録する

### 前の段階の穴のレベル

前の段階の穴にも、「レベル」の節のとおりに高・中・低を付ける。「事実の誤り」の決まりも、前の段階の穴に当てはまる。前の段階の、今あるものについての文が実ファイルと食い違えば、その穴を中以上にする。

### 往復の件数への数え方

`STATUS` と、review の節の最後の `- 往復:` の行の件数には、いまの段階の指摘の高と中に加えて、作るものが `変わらない` 前の段階の穴の高と中を数える。作るものが `変わる` 前の段階の穴は数えない。作るものが変わる穴があれば、メインセッションが往復を止めて所有者に報告するので、往復を終えるかどうかの判定に要らないためである。

### 後ろの段階に回した食い違い

前の段階の穴を記録する前に、前の段階の `<前の段階>-review.md` と `<前の段階>-response.md` を、いまの段階の名前(`design` か `tasks`)で検索する。

- 食い違いを後ろの段階で書くと記録されていて、いまの段階の本文にそのとおりに書かれていれば、その食い違いを記録しない
- 記録されているのに、いまの段階の本文にそのとおりに書かれていなければ、その食い違いを `### 指摘` の表に、いまの段階の指摘として書く。内容の欄には、前の段階の記録の指摘のIDを書く

## 記録の書式

`REVIEW_FILE` に追記する。既にある節を書き換えない。

```markdown
## サイクル<N> 往復<M>(<日付>)

### 審査の範囲

範囲: <全体 | 差分>

- <影響を受けると判断した箇所>: <そう判断した理由>

### 実ファイルで確かめた文

- <本文の箇所>「<文の要旨>」: <開いたファイルと行> / 合っていた | 食い違っていた(<指摘のID>)

### 同じ場面に当てはまる受入基準の組

| 受入基準の組 | どちらも当てはまる場面 | それぞれのとおりにした結果 | どちらに従うかが書かれた箇所 |
|---|---|---|---|
| <要件の番号.受入基準の番号> と <要件の番号.受入基準の番号> | <誰が、何を、どんな値で行うか> | <1つ目の受入基準のとおりにした結果> / <2つ目の受入基準のとおりにした結果> / 両立する か 両立しない | <見出しか行。両立するときは「要らない」。無ければ「無い(<指摘のID>)」> |

### 受入基準ごとの確かめ方

| 受入基準 | 確かめる道具 | 動かす場所 | 動かすのに要るもの | design の箇所 |
|---|---|---|---|---|
| <要件の番号.受入基準の番号> | <テストや筋書きの名前> | <コンテナか CI の検査> | <利用者、値、ポートなど> | <見出しか行。無ければ「無い(<指摘のID>)」> |

### 確かめの道具を作るタスク

| 道具 | 作るタスク | 確かめる成果物を作るタスク | 並び |
|---|---|---|---|
| <テスト、コマンド、筋書き、値の名前> | <タスクの番号。無ければ「無い」> | <タスクの番号> | 前 / 後ろ(<指摘のID>) |

### 申告

**1. <決めたこと>** — <該当箇所>

- Issue の記載: <あり/なしと内容>
- 決めたこと: <内容>
- 他にありえた選択肢: <内容>
- 外れていた場合: <影響>

### 指摘

| ID | レベル | 該当箇所 | 内容 | 直し方の案 |
|---|---|---|---|---|
| R1-1-1 | 高 | requirements.md 要件3 | ... | ... |

### 前の段階への指摘

| ID | 対象 | レベル | 作るもの | 該当箇所 | 内容 | 直し方の案 |
|---|---|---|---|---|---|---|
| D1-1-5 | requirements | 中 | 変わらない | 要件2の受入基準 | ... | ... |

### 承認を残して直した前の段階の審査

- 直しの番号 <no>: <もとになった穴のID>: 埋まった | 埋まっていない(<新しい行のID>) / 作るもの: 変わらない | 変わる(<新しい行のID>)

- 往復: <M>回目 / 高<件数> 中<件数> 低<件数>
```

`### 審査の範囲` には、起動の文で決まった範囲を書く(決め方は `.claude/agents/spec-reviewer.md` の「審査の範囲」)。

- 範囲が「全体」のときは、`範囲: 全体` の1行だけを書く
- 範囲が「差分」のときは、`範囲: 差分` と書き、その下に、差分で影響を受けると判断した箇所(ファイルと、要件・節・タスクの番号や見出し)と、そう判断した理由を1件1行で書く。影響を受ける箇所が無いと判断したときは、無いと判断した理由を1行で書く
- 差分が空のときは、`範囲: 差分` と書き、その下に「差分は空(本文を直していない)」の1行と、確かめた却下の指摘のIDと、却下の理由が事実として正しかったかを1件1行で書く
- `### 実ファイルで確かめた文` には、審査の範囲の中にある、今あるもの(コード、設定、開発環境、CI、置き換える前の版の動き)について書いた文を、1件1行で書く。範囲の中にそうした文が無いときは、「範囲の中に、今あるものについて書いた文は無い」の1行を書く
- `### 同じ場面に当てはまる受入基準の組` は、requirements の審査だけで書く。`rules/requirements.md` の観点6の手順で作った組のうち、2つの受入基準がどちらも当てはまる場面があった組を、1組1行で書く。別の spec の受入基準は、`<spec の名前> の <要件の番号.受入基準の番号>` の形で書く。どちらも当てはまる場面があった組が無いときは、「どちらも当てはまる場面があった組は無い」の1行を書く。design と tasks の審査では、この小見出しを書かない
- `### 受入基準ごとの確かめ方` は、design の審査だけで書く。審査の範囲の中にある受入基準を、1件1行で書く。範囲が「差分」のときは、差分で影響を受ける受入基準だけを書く。requirements と tasks の審査では、この小見出しを書かない
- `### 確かめの道具を作るタスク` は、tasks の審査だけで書く。審査の範囲の中にあるタスクの「完了の確かめ方」に出てくる道具を、1件1行で書く。requirements と design の審査では、この小見出しを書かない
- `### 前の段階への指摘` の「作るもの」の欄には、`変わる` か `変わらない` を書く(分け方は「前の段階への指摘」の節)。「直し方の案」の欄は、メインセッションが作るものが変わらない穴を直すときの手がかりになる
- `### 承認を残して直した前の段階の審査` は、起動の文に `## 承認を残して直した前の段階の差分` があったときだけ書く。もとになった穴のIDごとに1行を書く。直しの番号は、起動の文の `### <no>. <段階>(もとになった穴: …)` の見出しの番号である。メインセッションは、この番号で、まだ審査されていない直しを見分ける。直しで穴が埋まっていなければ、`埋まっていない` のあとに、`### 前の段階への指摘` に足した新しい行のIDを書く。直しが作るものを変えていれば、`変わる` のあとに、`### 前の段階への指摘` に足した新しい行のIDを書く
- `### 審査の範囲` と `### 実ファイルで確かめた文` と `### 同じ場面に当てはまる受入基準の組` と `### 受入基準ごとの確かめ方` と `### 確かめの道具を作るタスク` と `### 承認を残して直した前の段階の審査` の中に、行頭が `## ` の行と、行頭が `- 往復:` の行を書かない。行頭が `## サイクル` の行は、フックが最新の節を見分けるのに使う。行頭が `- 往復:` の行は、最終行の完了の印と紛れる

**最終行は必ず次のどちらかにする。** フックがこの行を読んで、レビューが完了したかを判断する。

- 収束した場合: `- 往復: <M>回で収束 / 未解決: 0件`
- 3往復で高か中が残った場合: `- 往復: 3回 / 未解決: <件数>件`

## 処置(メインセッションが response ファイルに書くもの)

レビュー役は書かない。突き合わせのために形式だけ示す。

| 処置 | 使う場面 |
|---|---|
| 修正 | 高・中の指摘を直した。作るものが変わらない前の段階の穴で、高・中のものを前の段階の承認を残して直した |
| 却下 | 指摘が誤検知である(理由を書く)。所有者が承認を残した直しを残さないことを選んだ |
| 記録のみ | 低の指摘と、作るものが変わらない前の段階の穴のうち低のもので、事実の誤りでないもの。直さない |
| 未解決 | 3往復に達し、高か中が残った。3往復目で見つかった、作るものが変わらない前の段階の穴の高と中も含む |
| 所有者判断待ち | 作るものが変わる前の段階の穴を含む往復の、前の段階への指摘のすべて |
