# spec レビューの共通ルール

全段階に共通する、レベル・申告・指摘の番号・記録の書式を定める。段階ごとの観点は `requirements.md` `design.md` `tasks.md` に書く。

## レベル

承認した後にどこまで戻ることになるかで決める。

| レベル | 意味 |
|---|---|
| 高 | 承認した後、誰も気づかないまま実装が終わる。または気づいたときには作り直しになる |
| 中 | 承認した後、後の工程で必ず発覚し、戻って直すことになる |
| 低 | 実装に影響しない |

段階ごとの例。

- requirements: 要件が抜けている(高) / 要件が曖昧で design を書けない(中)
- design: 前提にした外部機能が実際には使えない(高) / 要件に対応するコンポーネントが無い(中)
- tasks: 完了条件が抜けてテストが書かれない(高) / 並列の指定が誤っていて実装中に衝突する(中)

**観点の種類とレベルは対応しない。** 同じ「要望の取りこぼし」でも、落ちたものが中心的な要望なら高、細かい要望なら低になる。指摘ごとに判断する。

### 誤字脱字

- 意味が変わる誤記(「8日」を「3日」と書いた)は、影響で高か中に分類する
- 意味が変わらない誤字脱字は低に分類する

## 指摘の番号

`{段階}{サイクル}-{往復}-{連番}` の形式で振る。

- 段階: `R`(requirements) / `D`(design) / `T`(tasks)
- サイクル: その段階のレビューを新しく始めるたびに1つ増える。初回は1。差し戻しや本文の変更で再レビューになったら2、以降同様
- 往復: そのサイクルの中の往復番号
- 連番: その往復の中の通し番号

例: `R2-1-3` は requirements のサイクル2、往復1、3件目。

メインセッションから渡された `CYCLE` と `ROUND` をそのまま使う。自分で推測しない。

## 申告

AI が決めたことのうち、**他にありえた選択肢があり、外れていたときの手戻りが大きいもの**を一覧にする。他の選択肢が書けないもの(リポジトリの規約で決まっているもの)は申告しない。

1件につき4項目を書き、**外れていたときの影響が大きいものを上に並べる**。

- Issue に何が書いてあったか
- 何を決めたか
- 他に何がありえたか
- 外れていたら何が起きるか

申告は欠陥ではない。所有者が読んで判断するための材料であり、往復の終了条件には数えない。

## 前の段階への指摘

design と tasks の審査中に前の段階(requirements / design)の穴を見つけたら、**その段階への指摘としてではなく、別の節に書く。** メインセッションはこれを直さず、所有者に報告する。

## 記録の書式

`REVIEW_FILE` に追記する。既にある節を書き換えない。

```markdown
## サイクル<N> 往復<M>(<日付>)

### 申告

**1. <決めたこと>** — <該当箇所>

- Issue の記載: <あり/なしと内容>
- 決めたこと: <内容>
- 他にありえた選択肢: <内容>
- 外れていた場合: <影響>

### 指摘

| ID | レベル | 該当箇所 | 内容 | 直し方の案 |
|---|---|---|---|---|
| R1-1-1 | 高 | requirements.md 要件3 | ... | ... |

### 前の段階への指摘

| ID | 対象 | 該当箇所 | 内容 |
|---|---|---|---|
| R1-1-5 | requirements | 要件2の受入基準 | ... |

- 往復: <M>回目 / 高<件数> 中<件数> 低<件数>
```

**最終行は必ず次のどちらかにする。** フックがこの行を読んで、レビューが完了したかを判断する。

- 収束した場合: `- 往復: <M>回で収束 / 未解決: 0件`
- 3往復で高か中が残った場合: `- 往復: 3回 / 未解決: <件数>件`

## 処置(メインセッションが response ファイルに書くもの)

レビュー役は書かない。突き合わせのために形式だけ示す。

| 処置 | 使う場面 |
|---|---|
| 修正 | 高・中の指摘を直した |
| 却下 | 指摘が誤検知である(理由を書く) |
| 記録のみ | 低の指摘。直さない |
| 未解決 | 3往復に達し、高か中が残った |
| 所有者判断待ち | 前の段階への指摘 |
