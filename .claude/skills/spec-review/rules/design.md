# design の観点

## 前提

design は「どう作るか」を決める。requirements が「何を」しか言わないため、要件が縛らない部分は design が決めている。

requirements と違い、**照合できる相手がある**(requirements.md)。ただし厳密化した中身は照合できない。

生成側には書く前の自己点検(`.claude/skills/kiro-spec-design/rules/design-review-gate.md`)がある。**その点検は `## プロジェクトの決まりを守っているか` の節に一切言及していない。** ここが最も空いている。

見出しと目印は、`.kiro/settings/rules/spec-writing.md` の「見出しと目印の一覧」の名前で読む。Issueの印の決まりは、`.kiro/settings/rules/spec-writing.md` の「Issueの印」の節で読み、印の付け方の誤りも指摘する。

## 観点

### 1. 申告

`common.md` の申告の規則に従う。design で申告するのは次の3種類。

- 人間の承認が要る領域に触れる決定(マイグレーション、新しいライブラリ、ゲート設定の変更)
- 運用から見える振る舞いの決定(失敗したときの扱い、再試行、通知)
- 後から変えにくい決定(データの持ち方、外部サービスへの依存)

**申告しないもの**: リポジトリの規約で決まっているもの(backend の層配置、frontend の feature 境界、server state は TanStack Query、client state は Zustand)。選ぶ余地が無いため。

### 2. 要件カバレッジ

すべての要件が design に現れ、具体的なコンポーネント・契約・フロー・データモデル・運用上の決定のいずれかで裏付けられているか。ID が出てくるだけで実現する要素が無いものを探す。

### 3. `## プロジェクトの決まりを守っているか` と本文の矛盾

審査の基準にする雛形は `.kiro/settings/templates/specs/design.md` である。その雛形が定める7項目(「backend のコードを置く層」「frontend の機能ごとの境界」「frontend の状態の持ち方」「データベースの表の形」「新しいライブラリの追加」「品質チェックの設定」「使う外部の機能がこのリポジトリで使えるか」)について、次を見る。

- 関係のある項目に中身が書かれているか。関係のない項目が「関係のない項目:」の1行に名前だけで並んでいるか。7つの項目のすべてがどちらかに出ているか
- **この節の記載と設計本文が矛盾していないか。** 例: 「品質チェックの設定を変えずに済む」と書きながら `## ファイルの構成` に `.github/` のファイルが並んでいる。「新しいライブラリを足さない」と書きながら新しいライブラリが出てくる
- 7項目目「使う外部の機能がこのリポジトリで使えるか」について、**実測したという主張に、いつ何をどう確かめたかが書かれているか。** 「実測済み」の一言で済ませていないか

### 4. 境界と本文の食い違い

`## 作るものと作らないもの` の節の `### 作るもの` と `### 作らないもの` に書いたことを、設計本文が破っていないか。`### 作らないもの` に挙げたものを実質的に扱っていないか。

### 5. 設計内の矛盾

ある節と別の節が違うことを言っていないか。

### 6. 実現できない設計

前提にした外部サービスの機能が、このリポジトリの条件(アカウントの種別、プラン、リポジトリの可視性、地域、有効化の要否)で実際に使えるか。**設定項目が何かではなく、そもそも使えるかを見る。** ここを外すと、実装して初めて分かり、設計からやり直しになる。

### 7. 今あるコード・設定・旧版の動きとの食い違い

design が今あるものについて書いた文を、審査役は1つずつリポジトリの実ファイルを読んで確かめる。読まずに「書いてあるとおりだろう」と通さない。対象は次のような文である。

- 今あるファイルの場所、関数や型の名前、設定の値、欄の名前、ポート、数(「偽の AWS は2つ」のような数も含む)
- 開発環境(`compose.yaml`、`docker/`)、CI(`.github/workflows/`)、コンテナイメージ(Dockerfile が何を写すか)が今どうなっているか
- 置き換える前の版(旧版)のコードが今どう動いているか

実ファイルと食い違う文は、`common.md` の「事実の誤り」のとおり、低にしない。指摘には、食い違う実ファイルとその行を書く。

認証の spec(`backend-go-auth`)では、design を承認したあとに、「応答の時間を測る環境の偽の AWS の数」と「JWT の見分け方」の2つの文が事実と違うと分かり、design の承認を取り消した。どちらも、実ファイルを読めば承認の前に分かった食い違いである。

### 8. 作るときと確かめるときに要る前提の抜け

審査役は、requirements の受入基準を1つずつ取り、実装のあとに Claude がその受入基準を満たしたとどう確かめるかを、design の本文だけを使って書き出す。書き出したものは、記録の `### 受入基準ごとの確かめ方` の表に書く(書式は `common.md`)。頭の中で「タスクに分けられそうだ」と考えるだけで済ませない。書き出さないと、確かめるのに要るものの抜けに気づけないためである。受入基準ごとに書き出すのは次の4つである。

- 確かめる道具: どのテスト、筋書き、測る仕組み、画面の確認で確かめるか
- 動かす場所: 開発環境のどのコンテナか、CI のどの検査か
- 動かすのに要るもの: 利用者、テスト用の値と鍵、ポートと戻り先の URL、イメージに入れるファイル。受入基準が決める状態(期限切れ、時間切れ、回数の上限、応答の時間)を、道具がどうやって作るか、どうやって測るか
- それを決めた design の箇所: 見出しか行

審査役は、動かすのに要るものごとに、それを決めた design の箇所を挙げる。挙げられないものは design の抜けなので、中以上で指摘する。今の開発環境や CI に既にあるものに頼るときは、審査役は実ファイルを開いて、そのまま使えるかを確かめる。たとえば、版ごとにポートが違わないか、データベースに初期の利用者があるか、Dockerfile がそのファイルをイメージに写すかを確かめる。

あわせて、審査役は、作るものと確かめる道具が変えるファイルが、`## ファイルの構成` にすべて載っているかを確かめる。載っていないファイルを変えないと作れないなら、中以上で指摘する。

これらの抜けは、承認のあとの tasks の作成か実装で必ず見つかり、design に戻ることになる。認証の spec では、tasks の作成の中の点検が、design の承認のあとに次の抜けを見つけ、design の承認を2回取り消した: 2段階認証の確認の応答の時間の測り方、Go 版のイメージにメールのひな形が入らないこと、開発環境に API の説明画面でログインする利用者が無いこと、Google と GitHub のログインで版ごとに戻り先の URL のポートが違うこと、JWT の期限切れを筋書きで作れないこと。

### 9. 前の段階への指摘

設計に落とそうとして初めて分かった、requirements の不足・曖昧さ・矛盾。`common.md` の規則に従い、別の節に書く。

### 10. 誤字脱字

`common.md` の分類に従う。
