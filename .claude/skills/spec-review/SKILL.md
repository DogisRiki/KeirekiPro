# spec-review Skill

spec 文書を `spec-reviewer` にレビューさせ、指摘に対応して記録を残す。審査の前には毎往復、`spec-style-checker` に本文の書き方を点検させる。**各段階の生成直後に実行する。** 所有者が承認するときに、本文と記録の両方が手元にある状態を作るのが目的。

レビュー役のモデルは、spec.json の `review_model` で決まる。既定は Fable 5.1 で、所有者は spec ごとに Opus 5.5 を選べる。Fable 5.1 が上限に達してレビュー役が動かないときは、Opus 5.5 に替えてレビューを続ける(Step 3)。

## 役割の分担

| 誰が | 何をするか | 書くファイル |
|---|---|---|
| spec-style-checker(サブエージェント) | 本文の書き方を点検し、外れと直し方の案を返す | なし |
| spec-reviewer(サブエージェント) | 審査して指摘を書く | `reviews/{段階}-review.md` だけ |
| このスキル(メインセッション) | 点検の案と指摘に対応して本文を直す | spec 本文、`reviews/{段階}-style.md`、`reviews/{段階}-response.md` |

**`{段階}-review.md` に書かない。** レビュー役だけが書くファイルである。

## 呼び出し方(引数)

引数は `<feature> <段階> [changed]` である。3つ目の `changed` は、前回のレビューのあとに本文を直したことを示す。

- cc-sdd の生成のスキルは、生成の直後に `changed` を付けずにこのスキルを呼ぶ
- 実装セッションは、本文を直したあとにこのスキルを呼ぶとき、`changed` を付ける。次の3つの場面である
  - 所有者が承認の前に本文を直したとき
  - 未解決を残した段階を、所有者が直すことにしたとき
  - 承認済みの段階を、所有者の指示で直したとき

`changed` を付けると、往復1から、前回のレビューのときの本文との差分を審査させる(Step 2 の手順2)。

## 手順

### 会話が要約されたあとに続けるとき

`/spec-review` の途中で会話が要約されたあと、Claude は、続きを始める前に、次の手順で往復の位置をファイルから決め直す。`reviews/{STAGE}-review.md` が無いときは、往復が始まっていないので、Claude は Step 1 から始める。

1. Claude は、`reviews/{STAGE}-review.md` の最後の `## サイクル<N> 往復<M>` の見出しから、`CYCLE` を N に、`ROUND` を M にする。最後の `## サイクル<N> 往復<M>` の節が `- 往復:` の行で終わっていなければ、審査役が途中で止まった節なので、Claude は Step 3 の「上限のときの切り替え」のとおり、`CYCLE` を 1 増やし、`ROUND` を 1 にして審査役を起動し直す
2. `reviews/{STAGE}-response.md` に `## サイクル<CYCLE> 往復<ROUND> への対応` の見出しが無ければ、Claude は、その往復の Step 4(指摘への対応)から続ける
3. 見出しがあり、`reviews/{STAGE}-review.md` の最終行が収束か未解決の終わり(`- 往復: <n>回で収束 / 未解決: 0件` か `- 往復: 3回 / 未解決: <n>件`)のとき、本文(`.kiro/specs/{FEATURE}/{STAGE}.md`)が `reviews/{STAGE}-review.md` より新しくなければ、Claude は Step 7(所有者への報告)から続ける。本文のほうが新しければ、前の回のあとに新しい回(`changed` 付きの回、差し戻しの回、作り直した段階の回)を始め、その往復1の審査がまだ書かれていない。そのため Claude は、`CYCLE` を N+1 に、`ROUND` を 1 にし、Step 1.5 から続ける。前の回が終わったあとに本文が書き換わるのは新しい回を始めたときだけで、判定のスクリプト `spec-review-scan.sh` の「本文がレビューより新しい」と同じ比べ方(ファイルの変更日時)である
4. それ以外なら、Claude は `ROUND` を 1 増やし、Step 1.5(書き方の点検)から続ける
5. 却下した指摘の一覧は、Claude が `reviews/{STAGE}-response.md` の、そのサイクルの処置が「却下」の行から作り直す
6. Claude は、審査の範囲(`SCOPE`)を、Step 2 の手順2のとおり、控え(`.reviewed.md`)があれば差分にし、無ければ全体にする。`CHANGED` の有無が要約から分からないまま往復1の審査役を起動するときは、Claude は `SCOPE` を全体にする。全体を審査すれば、見落としは増えないためである
7. その往復の点検の記録(`reviews/{STAGE}-style.md` の節)を書いたかどうかが分からないときは、Claude は Step 1.5 をやり直す

### Step 1: 準備

1. 引数から `FEATURE` と `STAGE` を取る。`STAGE` は `requirements` / `design` / `tasks` のいずれか。3つ目の引数が `changed` なら `CHANGED` を「あり」にし、無ければ「なし」にする
2. `.kiro/specs/{FEATURE}/reviews/` が無ければ作る
3. `CYCLE` を決める: `reviews/{STAGE}-review.md` にある最大のサイクル番号 + 1。ファイルが無ければ 1
4. `ROUND` を 1 にする

### Step 1.5: 書き方の点検

審査役を起動する前に、本文の書き方を点検し、中身の変わらない直しを本文に入れる。この工程は審査役の起動の前にだけ行い、最終往復の審査役の後には行わない。

1. Agent ツールで `spec-style-checker` を起動する。**モデルを指定しない**(起動したセッションと同じモデルを使わせるため)。渡すもの:
   - spec の名前(`FEATURE`)
   - 段階(`STAGE`)
   - 本文のパス(`.kiro/specs/{FEATURE}/{STAGE}.md`)
2. 点検役の最終応答を読む。応答は「外れは無い」の1行か、`## 文の書き方の外れ` `## 組み立て・design.md の書き方・繰り返しの外れ` `## まとめ` の3つの見出しを持つ形のどちらかである。どちらの形でもないときは、点検役を1回だけ起動し直す
3. 「中身が変わるか: 変わらない」の外れについて、案のとおりに本文を直す
   - 文の書き方の外れ: 原文の文を、書き直しの案の文に置き換える
   - 組み立て・design.md の書き方・繰り返しの外れ: 直し方の案のとおりに、節を足す、消す、まとめる
4. 「中身が変わるか: 変わる(…)」の外れでは、本文を直さない。該当する文や節と、括弧の中の理由を控えておく(記録と Step 7 の報告に使う)
5. **本文を直し終えてから**、`reviews/{STAGE}-style.md` の末尾に節を1つ足す。ファイルが無ければ作る。前に書いた節は書き換えない。外れが無かったときも、0件の節を足す
   - 判定のスクリプト `spec-review-scan.sh` は、点検の記録の変更日時が本文より新しいことを確かめる。そのため、本文を直す前に記録を書かない

点検の記録の書式(日時は UTC の ISO 8601):

```markdown
## 点検 2026-10-02T07:10:00Z

- 直した文: 3
- 直した節: 1
- 直さなかった外れ: 1
  - 42行目「…」: 書き直すと、承認を取り消す段階が変わるため
```

- `直した文` は文の書き方の外れで直した件数、`直した節` は組み立て・design.md の書き方・繰り返しの外れで直した件数である
- 直さなかった外れは1件ごとに1行書く。文の外れは `<行番号>行目「<原文>」: <理由>`、節の外れは `節「<見出し>」: <理由>` の形にする

所有者が承認の前に本文を直したら、`changed` を付けて `/spec-review` を流し直す。そのとき点検役は、所有者が直した文を含めて本文の全体を点検し、このスキルは所有者が書いた文も、直しても中身が変わらない範囲で直す。本文には所有者が書いた文を区別する手段が無く、直しても決めごとの中身は変わらないからである。

### Step 2: レビュー役を起動する

レビュー役を起動するたびに、次の手順で行う。

1. spec.json の `review_model` を読み直す
   - 値が無ければ `fable` とみなす。所有者がモデルを選んでいない spec と、モデルを選べるようになる前から進めている spec は、値が無い
   - `fable` と `opus` のどちらでもない値があれば、往復を止め、値を `fable` か `opus` に直すよう所有者に頼む。値を推し量ってモデルを選ばない
   - 起動のたびに読み直すので、所有者が往復の途中で選び直したモデルは、次の起動から使われる
   - このスキルは `review_model` を読むだけで、書かない。上限で Opus 5.5 に替えたときも書き換えない
2. 審査の範囲(`SCOPE`)を決める。控えは `.claude/.state/spec-review/{FEATURE}__{STAGE}.reviewed.md`、本文は `.kiro/specs/{FEATURE}/{STAGE}.md` である
   - `ROUND` が 1 で `CHANGED` が「なし」なら、`SCOPE` は「全体」である。段階の本文を生成した直後の最初のレビューにあたる
   - それ以外(往復2以降、`changed` 付きの往復1、差し戻しで本文を直したあとの新しいサイクル)は、控えとの差分を取る
     - まず控えがあるかを確かめる。控えが無ければ、`git diff` を実行せず、`SCOPE` を「全体」にする。控えは作業フォルダごとに置かれるので、別の作業フォルダで続きを進めると無い
     - 控えがあれば、作業フォルダの最上位で `git diff --no-index --no-color <控え> <本文>` を実行し、終了コードで決める。0 なら差分が空で、`SCOPE` は「差分」である。1 なら差分があり、`SCOPE` は「差分」である(`git diff --no-index` は差分があると1を返すので、1を失敗とみなさない)。2以上なら比べられなかったので、`SCOPE` は「全体」である
     - `git diff --no-index` は、ファイルを開けないときも、差分があるときと同じ1を返す(2026-10-13 に git 2.56 で実測)。そのため、終了コードが1でも、出力が空で `error:` の文面だけが出たときは、比べられなかったとみなし、`SCOPE` を「全体」にする
   - 比べられないことを理由に往復を止めない。全体を審査すれば、見落としは増えない
3. 本文を仮の控えに写す: `mkdir -p .claude/.state/spec-review` のあと、本文を `.claude/.state/spec-review/{FEATURE}__{STAGE}.pending.md` に `cp` で写す(前の仮の控えがあれば上書きする)
   - 控えを上書きするのは、レビュー役の結果に構造化ブロックがあったときだけである。そのとき、仮の控えを控え(`.reviewed.md`)に `cp` で写して上書きする(Step 3)
   - 仮の控えを消すのは、レビュー役が最後まで動かずに往復を止めるときだけである。そのとき、控えは前のまま残す。前回の審査のあとに直した箇所が、次の起動の差分に残るようにするためである
4. Agent ツールで `spec-reviewer` を起動する。モデルは `review_model` に従って決める
   - `fable` なら、**モデルを指定しない**(定義ファイルの `claude-fable-5-1` を使わせるため)
   - `opus` なら、`model: opus` を指定する(起動時の指定は定義より優先される)

渡すもの:

- `FEATURE` / `STAGE` / `CYCLE` / `ROUND` / `REVIEW_FILE`(`.kiro/specs/{FEATURE}/reviews/{STAGE}-review.md`)
- **直前1往復分**の review と response の該当部分(`ROUND` が 2 以上のとき)
- **却下された指摘の一覧**(そのサイクルの全往復分。ID とレベルと1行の要約だけ)
- `SCOPE` が「差分」のときは、前回からの差分。起動の文の最後に、次の形で置く。`SCOPE` が「全体」のときは、この見出しを置かない

差分があるとき(`git diff` の出力を、要約せず、どこを審査するかも選ばずに、そのまま置く):

````markdown
## 前回からの差分

```diff
diff --git a/.claude/.state/spec-review/<feature>__<段階>.reviewed.md b/.kiro/specs/<feature>/<段階>.md
...(git diff の出力の全部)
```
````

差分が空のとき(却下だけで本文を直さなかった往復):

```markdown
## 前回からの差分

差分は空(本文を直していない)
```

- 差分の中に spec 本文のコードブロックの区切り(バッククォート3つ)が入ることがある。そのときは、差分を囲む区切りに、差分の中のどの区切りよりも長いバッククォートの並びを使う

材料は読ませない。レビュー役が自分で読む。

### Step 3: 応答から構造化ブロックを読む

レビュー役の結果を、次の順に判定する。

1. 結果に構造化ブロック(`- STATUS:` の行)があれば、レビュー役は最後まで動いたとみなす。上限の判定をしない。`- FEATURE:` から `- STATUS:` までのブロックを読み、`- STATUS:` 行だけを厳密に見る
2. 構造化ブロックが無く、結果に `Agent terminated early due to an API error:` で始まる行があれば、その1行の中の、この語句よりあとの部分(失敗の詳細)だけを見る
   - 詳細が `limit` の語を含み、`529` と `Overloaded` のどちらも含まなければ、上限で止まったとみなす。公式の失敗の詳細の例は `You've hit your session limit` と `weekly limit` である
   - 詳細がそれ以外なら、上限以外の理由で止まったとみなす
   - `Everything below is PARTIAL output` よりあとの途中の出力は、判定に使わない
3. 構造化ブロックも `Agent terminated early` の行も無ければ、構造化ブロックの形が違うだけとみなす。レビュー役は最後まで動いている

判定の例:

| 結果の文面 | 判定 |
|---|---|
| `Agent terminated early due to an API error: You've hit your weekly limit` | 上限(詳細が `limit` を含み、`529` も `Overloaded` も含まない) |
| `Agent terminated early due to an API error: Repeated 529 Overloaded errors` | 上限以外(詳細が `529` と `Overloaded` を含む) |

判定のあとは、次のとおりにする。

- **構造化ブロックがあった**: 仮の控え(`.pending.md`)を控え(`.reviewed.md`)に写して上書きし、Step 4 へ進む
- **構造化ブロックの形が違うだけ**: モデルを切り替えず、同じモデルで**ブロックだけを出力させる再起動を1回行う**。このとき `REVIEW_FILE` に追記させない(同じ往復が二重に残るため)。再起動の前に Step 2 の手順1〜3をやり直さず、仮の控えを残す。ブロックが返ったら、上の「構造化ブロックがあった」のとおりにする
- **上限で止まった**: 下の「上限のときの切り替え」のとおりにする
- **上限以外の理由で止まった**(結果に `529` か `Overloaded` を含むとき、通信の失敗のとき、所有者が止めたときなど): モデルを替えない。往復を止め、仮の控えを消し(控えは前のまま残す)、止まった理由と結果の文面を所有者に知らせる

#### 上限のときの切り替え

- Fable 5.1 のレビュー役が上限で止まったら、所有者に尋ねずに、`model: opus` で同じ材料のレビュー役を起動し直す
  - 起動し直す前に、`reviews/{STAGE}-review.md` に、今回の `## サイクル<CYCLE> 往復<ROUND>` の節が書かれていないかを確かめる
  - 書かれていたら、`CYCLE` を 1 増やし、`ROUND` を 1 にして起動し直す。このとき、止まったサイクルで却下した指摘の一覧も、新しいサイクルのレビュー役に渡す。新しいサイクルの往復の上限は3回である。サイクルを進めるのは、同じサイクルと往復の節が review のファイルに2つ残り、指摘のIDが重なるのを避けるためである
  - 往復の番号と、Step 5 の往復の上限の判定と、review のファイルの最終行の往復の数は、今までどおり同じ数を指す
  - 起動し直すときは、Step 1.5 と、Step 2 の手順1〜3(`review_model` の読み直し、審査の範囲の決定、仮の控えへの写し)をやり直さない。仮の控えを消さず、同じ審査の範囲と同じ差分を渡す
  - 起動し直したレビュー役の結果に構造化ブロックがあれば、残しておいた仮の控えで控えを上書きする。止まったレビューのあとに起動し直しても控えは止まる前のままなので、前回の審査のあとに直した箇所は差分に残る
- 上限で Opus 5.5 に替えても、spec.json の `review_model` を書き換えない。所有者がモデルを選んでいない spec にも `opus` を書かない。次にレビュー役を起動するときは、Step 2 の手順1のとおり、`review_model` のモデル(値が無ければ Fable 5.1)からまた試す。Fable 5.1 がまだ上限に達していれば、またこの切り替えを行う
- Opus 5.5 のレビュー役が上限で止まったら(所有者が Opus 5.5 を選んだときも、Fable 5.1 から替えたときも)、往復を止め、仮の控えを消し(控えは前のまま残す)、レビュー役が上限で動かないことと結果の文面を所有者に知らせる

### Step 4: 指摘に対応する

`reviews/{STAGE}-review.md` の今回の往復を読み、`reviews/{STAGE}-response.md` に追記する。

| 指摘 | すること | 処置 |
|---|---|---|
| 高・中 | 本文を直す | 修正 |
| 高・中で誤検知と判断した | 直さない。根拠を具体的に書く | 却下 |
| 低 | 直さない | 記録のみ |
| 前の段階への指摘 | 直さない。Step 6 へ | 所有者判断待ち |

**`review.md` の全指摘に処置を書く。** 書き漏らすと Stop フックが止める。

節の表の前に、レビュー役のモデル、レビュー役が使った量、審査の範囲の3行を書く。

- モデルは、その往復の審査を最後まで行ったレビュー役のモデルを、次の3つのどれかで書く: `Fable 5.1` / `Opus 5.5(所有者が選んだ)` / `Opus 5.5(Fable 5.1 が上限に達したため替えた)`
- 量は、レビュー役の結果の末尾の `<usage>` にある `subagent_tokens` の値である。値が結果に無ければ「不明」と書く
- 審査の範囲は、Step 2 の手順2で決めた `SCOPE` を書く。本文の全体を審査させた往復では「全体」、差分を渡した往復では「前回からの差分」と書く。差分が空だった往復も「前回からの差分」と書く
- Fable 5.1 が上限で止まった起動の量が結果に載っていれば、「- 上限で止まった Fable 5.1 の起動が使った量: <数> トークン」の行も足す

response の書式:

```markdown
## サイクル<N> 往復<M> への対応(<日付>)

- レビュー役のモデル: Opus 5.5(Fable 5.1 が上限に達したため替えた)
- レビュー役が使った量: 126457 トークン
- 上限で止まった Fable 5.1 の起動が使った量: 8210 トークン
- 審査の範囲: 全体

| ID | 処置 | 内容 |
|---|---|---|
| R1-1-1 | 修正 | requirements.md 要件3の受入基準に観測点を追記した |
| R1-1-2 | 却下 | 要件2.3 に既定があり、指摘は事実誤認。該当行を引用: ... |
| R1-1-4 | 記録のみ | 表現の指摘。実装に影響しない |
```

### Step 5: 往復の判定

- `STATUS` が `converged`(高と中が0件)なら終了。Step 7 へ
- `unresolved` で `ROUND` が 3 未満なら、`ROUND` を 1 増やして Step 1.5 へ。Step 4 で直した本文を、審査役の前にもう一度点検するためである。往復2以降なので、Step 2 の手順2で審査の範囲は差分になる(控えと本文を比べられないときは全体)
- `unresolved` で `ROUND` が 3 なら、**本文を直さずに**終了する。残った高と中を「未解決」として response に書き、Step 7 へ

**最終往復の後に本文を直さない。** 直すと、直した内容を誰もレビューしないまま承認に上がる。Step 1.5 の点検も、終了した後には行わない。

### Step 6: 前の段階への指摘があった場合

1. 往復を止める
2. 所有者に報告する。報告には次を含める
   - 指摘の内容と、どの段階に戻るのか
   - **その spec で何回目の差し戻しか**(review ファイルの再レビューの節を数える)
   - **2回目以降は、直す以外の選択肢も並べる**: spec を分割する / requirements から作り直す
3. 所有者が直すと判断した場合
   - **取り消す前に、承認を `approval_history` に写す。** 戻る段階とその後続の段階のうち、`approved` が `true` の段階ごとに、spec.json の `approval_history` に次の要素を1つ追記する(配列が無ければ作る)。書式は kiro-spec-init の更新の形と同じ
     ```json
     {
       "stage": "requirements",
       "approved_by": "<approvals.requirements.approved_by>",
       "approved_at": "<approvals.requirements.approved_at>",
       "issues": [<issue>, <additional_issues の各番号>],
       "revoked_at": "<現在の ISO 8601 の日時>",
       "revoked_for": "<差し戻しの理由。指摘のIDと1行の要約>"
     }
     ```
     - `issues` には、その承認のときに spec が対象にしていたIssue(`issue` と、いまの `additional_issues`)を入れる
     - `revoked_for` の例: `"D1-1-3 による requirements への差し戻し: 要件4の受入基準が design の前提と食い違う"`
     - `approval_history` は追記だけにし、書いてある要素を書き換えたり消したりしない
   - 戻る段階とその後続の段階について、spec.json の `approved` を `false` にし、`approved_by` と `approved_at` を削除する
   - 本文を直す
   - その段階について、`CYCLE` を 1 増やし、`ROUND` を 1 にし、`CHANGED` を「あり」にして Step 1.5 からやり直す(往復は新たに最大3回)。本文を直したあとなので、往復1から、Step 2 の手順2で審査の範囲は差分になる(控えと本文を比べられないときは全体)
   - 後続の段階は自分で作り直さない。所有者に、後続の段階のコマンドを順に打つよう依頼する(requirements に戻るときは `/kiro-spec-design <feature>` と `/kiro-spec-tasks <feature>`、design に戻るときは `/kiro-spec-tasks <feature>`)。各段階のコマンドには `disable-model-invocation` が付いており、AIからは起動できない。所有者が打って生成された段階は、それぞれこのスキルでレビューする

### Step 7: 所有者への報告

チャットには件数と場所だけ出す。あわせて、次の3つを出す。

- 往復ごとのレビュー役のモデルと量と審査の範囲。1往復につき1行で出す。Fable 5.1 から Opus 5.5 に替えた往復があれば、替えたことと、Fable 5.1 が上限に達していたことを書く
- 書き方の点検で直した文と節の数。この回の `/spec-review` の全往復の合計を出す
- 直さなかった外れのすべて。1件ごとに、該当する文や節と、直さなかった理由を示す

```
requirements のレビューが終わりました(サイクル1、往復2で収束)。
高 0件 / 中 0件 / 低 2件 / 未解決 0件
申告 3件
レビュー役:
  - サイクル1 往復1: Fable 5.1 / 98012 トークン / 全体
  - サイクル1 往復2: Opus 5.5(Fable 5.1 が上限に達したため替えた) / 126457 トークン / 前回からの差分
書き方の点検: 直した文 5件 / 直した節 1件 / 直さなかった外れ 1件
  - requirements.md 42行目「…」: 書き直すと、承認を取り消す段階が変わるため

.kiro/specs/{feature}/requirements.md
.kiro/specs/{feature}/reviews/requirements-review.md
.kiro/specs/{feature}/reviews/requirements-response.md
.kiro/specs/{feature}/reviews/requirements-style.md
```

## 制約

- **spec 本文を直すのはこのスキルだけ。** レビュー役には直させない
- 往復は最大3回。`kiro-impl` と同じく上限で打ち切る
- 低の指摘は直さない。記録に残す
- 同じ指摘で3往復を使い切った場合は、所有者に判断を仰ぐ
